## 1. 是什么：CAP 三要素

**一句话记忆**：分布式系统在**网络分区**时，只能在**一致性**和**可用性**之间选一个——CAP 说的就是这三者的不可兼得。

| 要素 | 英文 | 含义 |
|---|---|---|
| **一致性 C** | Consistency | 所有节点同一时刻数据一样（读到最新数据） |
| **可用性 A** | Availability | 每个请求都能在合理时间得到响应（不报错） |
| **分区容错 P** | Partition tolerance | 网络分区/节点故障时系统仍能工作 |

> 💡 **记忆锚点**：**C=数据一致，A=总有响应，P=分区也能扛**。分布式系统**必须选 P**（网络故障不可避免），所以在 C 和 A 之间二选一。

---

## 2. 为什么只能三者取二

**核心**：网络分区（P）是分布式系统的**客观现实**，无法避免，所以必须选 P。剩下的问题在 **C 和 A 之间取舍**：

```
网络分区（一部分节点无法通信）时，出现一个写请求：
├── 选 C（一致性）：放弃响应，等待分区恢复同步 → 牺牲 A
│     → 客户端可能超时/等待，但数据一致
└── 选 A（可用性）：立即响应（各分区自洽）→ 牺牲 C
      → 客户端拿到响应，但分区间的数据可能不一致

→ CAP 说：分区时 C 和 A 只能选一个，无法同时满足
```

**关键理解**：
- **P 是必选的**（网络分区不可避免），所以实际是 **CP 或 AP 二选一**
- 网络正常时 C 和 A 可以同时满足；**只有分区时才被迫取舍**
- CAP 说的"三选二"严格说是"分区时 C/A 二选一 + 必须 P"

> ⚠️ **易错点**：**CAP 不是说"三个都要选两个"这么简单**，而是"P 必选，分区时 C 和 A 二选一"。别答成"随便选两个都行"。

## 3. 一致性 vs 可用性的权衡

| 选型 | 分区时行为 | 适用系统 |
|---|---|---|
| **CP**（重一致） | 牺牲可用性，等分区恢复 | Zookeeper、Etcd、MySQL 主从 |
| **AP**（重可用） | 牺牲一致性，各分区自洽 | Redis、Cassandra、Eureka |

### 典型系统 CAP 侧重

| 系统 | 侧重 | 说明 |
|---|---|---|
| **Zookeeper** | **CP** | 强一致，少数节点不可用则服务不可用 |
| **Etcd** | **CP** | 强一致，分布式协调 |
| **MySQL 主从** | **CP** | 主从强一致同步（严格模式） |
| **Redis** | **AP**（默认） | 主从异步复制，可能读到旧数据 |
| **Eureka** | **AP** | 服务注册发现，优先可用 |
| **Cassandra** | **AP** | 最终一致 |

> 💡 **记忆锚点**：**协调/存储类倾向 CP（Zookeeper/Etcd），缓存/注册类倾向 AP（Redis/Eureka）**——看业务更怕"数据不一致"还是"服务不可用"。

## 4. BASE 理论

### 4.1 是什么

**BASE** 是对 CAP 中"AP"一方的实践总结，核心是**对强一致性的降级妥协**——允许数据短时间不一致，换取高可用。

| 要素 | 含义 |
|---|---|
| **Basically Available**（基本可用） | 核心功能可用，允许降级 |
| **Soft state**（软状态） | 状态允许不一致（短暂） |
| **Eventually consistent**（最终一致） | 最终数据会一致 |

> 💡 **记忆锚点**：**BASE = "反正最终会一致，先保证可用"**。它不追求强一致，接受"软状态"，靠异步同步最终收敛。

### 4.2 BASE vs ACID

| 维度 | ACID（单机事务） | BASE（分布式） |
|---|---|---|
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 牺牲（事务阻塞） | 优先可用 |
| 典型 | 数据库事务 | 分布式系统、微服务 |
| 思想 | 严格保证 | 妥协降级 |

---

## 5. 选型应用

**CAP/BASE 如何指导架构**：

| 业务场景 | 侧重 | 理由 |
|---|---|---|
| 订单/转账（金融） | **CP**（重一致） | 不能接受资金不一致 |
| 商品信息/用户资料 | **AP**（重可用） | 短暂不一致可接受，要可用 |
| 服务注册发现 | **AP** | 不能因少数节点挂了就不可用 |
| 分布式协调/选主 | **CP** | 必须一致，否则脑裂 |

> ⚠️ **易错点**：**不是所有系统都该追求 CP**。缓存、注册中心、消息等很多场景"最终一致"足够，强一致反而牺牲可用性和性能。按业务容忍度选。

## 6. 面试追问 Q&A

### 6.1 CAP 为什么只能三选二？

因为**分区容错 P 必须选**（网络分区不可避免），剩下的只能在一致性 C 和可用性 A 之间取舍：分区时若保证一致就牺牲可用（等待同步），保证可用就牺牲一致（各分区自洽）。所以实际是 **CP 或 AP**。

### 6.2 什么是 BASE 理论？

BASE 是对 AP 的实践总结：**基本可用 + 软状态 + 最终一致**。它放弃强一致，允许数据短暂不一致，靠异步同步最终收敛，换取高可用，是微服务/分布式的主流思想。

### 6.3 Zookeeper 是 CP 还是 AP？

**CP**（强一致）。它用 ZAB 协议保证强一致，少数节点故障时宁可不可用也不给不一致数据，适合分布式协调、选主。

### 6.4 Redis 是 CP 还是 AP？

**AP**（默认）。主从采用异步复制，主节点故障时可能丢失部分未同步数据，从节点可能读到旧数据——重可用，最终一致（可通过 WAIT 等配置提升一致性）。
