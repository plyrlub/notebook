## 3. 核心知识点

### 知识点一：为什么需要分布式锁

**一句话记忆**：**单机锁管"一个 JVM 内的线程"，分布式锁管"多台机器上的进程"——跨进程互斥**。

#### ① 是什么

| 锁类型 | 作用范围 | 典型场景 |
|---|---|---|
| JVM 锁（synchronized / ReentrantLock） | **单进程内**多线程 | 单机应用 |
| **分布式锁** | **跨进程/跨服务器** | 多台机器扣库存、抢券、定时任务防重 |

#### ② 为什么：分布式环境下的竞争

```
单机：两个线程抢库存 → synchronized 锁住 ✅
分布式：两台服务器同时扣同一商品库存 →
  各自 JVM 的 synchronized 互不相识 → 都读到库存=1 → 都扣成 0 → 超卖!
需要一把"两台机器都认"的锁 → 分布式锁
```

#### ③ 必须解决的三个核心问题（面试基础分）

| 问题 | 场景 | 解决 |
|---|---|---|
| **死锁** | 拿锁后进程崩溃，锁永远不放 | 加锁时设**过期时间** |
| **误删** | 锁过期被 B 拿走，A 的释放逻辑却把 B 的锁删了 | value 存**唯一 token**，删除前校验 |
| **原子性** | 加锁与设过期分开两条命令，中间崩溃 | `SET NX PX` **一条命令原子完成** |

> 💡 **记忆锚点**：**分布式锁 = 跨机器的互斥 + 三个防坑（过期防死锁、token 防误删、原子防半截）**。

#### ④ 追问

- 面试官："分布式锁和分布式事务什么关系？"→ 锁解决"互斥访问"，事务解决"多步操作的一致性"；TCC/Seata 里"预扣"隐含锁思想，但锁不保证事务性。详见 [04-分布式事务详解](04-分布式事务详解.md)。

### 知识点二：Redis 实现分布式锁

**一句话记忆**：**加锁 `SET key token NX PX ttl` 一条命令原子完成；释放用 Lua 脚本"校验 token 是自己的才删"**。

#### ① 基础版（必须会写）

```bash
# 加锁：NX=不存在才设置（互斥），PX=过期时间（防死锁），一条命令（原子）
SET lock_key unique_token NX PX 10000
# 返回 OK → 拿到锁；返回 nil → 锁被占用

# 释放锁：校验 value 是自己的才删（Lua 原子，防误删）
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**三个细节为什么**：

| 细节 | 为什么 |
|---|---|
| `NX` | 只有 key 不存在才设置 → 互斥 |
| `PX 10000` | 自动过期 → 客户端崩溃不死锁 |
| value=唯一 token（UUID） | 释放前校验是自己的 → 不误删别人的锁 |

#### ② 为什么必须 Lua 释放

"先 get 再 del"是两条命令，中间锁可能被换手（A 的锁过期 → B 拿到 → A 的 del 删掉 B 的锁）。Lua 脚本把"校验+删除"合并成**单次原子执行**，杜绝换手窗口。

#### ③ 业务与锁的时间竞争（容易被问的细节）

```
A 拿锁(ttl=10s) → 业务跑了 12s → 锁已过期 → B 拿到锁 → A 业务还在写
→ A 和 B 同时写 → 数据竞争! 单靠"锁过期"防不住
```

解法：① Redisson 看门狗自动续期（见知识点三）；② 业务侧用**版本号/幂等**兜底（A 写时带自己的 token，B 已覆盖则 A 的更新被拒绝）。

#### ④ 追问

- 面试官："锁过期时间设多长？"→ 没有标准答案：短了业务没跑完锁没了，长了崩溃后长时间不可用。生产用看门狗（动态续期）+ 兜底幂等。

### 知识点三：Redisson 看门狗（WatchDog）——自动续期机制

**一句话记忆**：**看门狗 = 给锁自动续命的守护线程——锁默认 30s 超时，每 10s 续期一次，业务没跑完锁不过期；锁释放/客户端挂掉就停**。

#### ① 问题背景

固定 ttl（如 10s）：业务跑 12s → 锁过期 → 并发进入。把 ttl 设很大（如 30s）：客户端崩溃 → 锁 30s 才释放 → 长时间不可用。**看门狗解决"锁寿命跟随业务"**。

#### ② 机制（源码级理解）

```
lock.lock() 流程:
1. Redis 执行 Lua: 锁 key 不存在 → 设 value=threadId, ttl=30000ms(默认锁超时)
2. 成功 → 启动"看门狗"定时任务: 每 10s(ttl/3) 执行一次续期 Lua
   续期 Lua: 检查锁还是自己的 → 是 → 重新设置 ttl=30000ms
3. unlock() 时: 删锁 + 取消看门狗任务
4. 客户端崩溃 → 看门狗线程也没了 → 锁在 30s 后自然过期 ✅
```

```java
RLock lock = redisson.getLock("myLock");
lock.lock();                 // 看门狗自动续期（默认 30s/续 10s）
try { /* 业务 */ } finally { lock.unlock(); }  // 完成释放，取消续期

// 自定义 ttl 的 lock 不会启动看门狗:
lock.lock(10, TimeUnit.SECONDS);   // 显式 ttl → 无看门狗，到期自动释放
```

| API | 行为 |
|---|---|
| `lock()` | 阻塞获取，**看门狗自动续期**（默认 30s/10s） |
| `lock(ttl, unit)` | 阻塞获取，**固定 ttl，无看门狗** |
| `tryLock(wait, lease, unit)` | 等待 wait 时间获取，lease 过期自动释放（lease>0 无看门狗） |
| `unlock()` | 释放，取消看门狗 |

> ⚠️ **易错点（面试高频）**：**用了带 ttl 的 `lock(10, SECONDS)` 就没有看门狗**！只有无参 `lock()`（默认 30s）才自动续期。回答"看门狗默认续期到 30s、每 10s 一次"是标准答案。

#### ③ 为什么续期间隔是 ttl/3

默认锁超时 30s、看门狗每 10s 续期：即使一次续期失败，还有两次机会（20s 余量）内再次续期，避免网络抖动导致锁提前释放。

#### ④ 追问

- 面试官："看门狗怎么知道业务做完了？"→ 不知道，它只按固定节奏续期；业务做完调 `unlock()` 时取消续期任务。业务不结束锁就一直续——所以**业务必须 finally unlock**，否则锁永不释放（仅靠 JVM 退出兜底）。

### 知识点四：Redisson 锁家族

**一句话记忆**：**Redisson 一套 API 提供 8 种锁，最常用可重入锁（默认）与红锁（多节点）**。

| 锁类型 | 类 | 特点 |
|---|---|---|
| **可重入锁** | `RedissonLock` | 同一线程可重复加锁（计数），默认锁 |
| 公平锁 | `RedissonFairLock` | 按请求顺序排队（Redis 列表实现），FIFO |
| 读写锁 | `RedissonReadWriteLock` | 读读共享、读写互斥（Java 语义搬到分布式） |
| 信号量 | `RedissonSemaphore` | 限流 N 个并发 |
| 闭锁/门闩 | `RedissonCountDownLatch` | 等待 N 个线程完成 |
| **红锁** | `RedissonRedLock` | 多节点多数派（Redlock 的 Redisson 实现） |

**可重入的实现**：value 不存 UUID 而是 `threadId`，Lua 里 `exists → 校验 owner 是当前线程 → 计数+1`，unlock 计数-1 到 0 才真正删除。所以**同一个线程重复 lock() 不会阻塞自己**。

#### 追问

- 面试官："可重入有什么用？"→ 锁内再调用了同样加锁的方法（如 A→B 都加同一把锁）不会死锁；分布式场景对应"同一线程的嵌套调用"。

### 知识点五：ZooKeeper 实现分布式锁

**一句话记忆**：**临时顺序节点 + Watch：创建自己的节点，看自己是不是最小号，不是就监听前一个节点——临时节点保证崩溃自动释放，顺序号保证公平**。

#### ① 原理

```
1. 在 /locks 下创建【临时顺序节点】→ /locks/lock_0000000001
2. 获取 /locks 下所有子节点，排序
3. 自己是最小序号 → 拿到锁 ✅
4. 不是最小 → Watch 监听【前一个节点】，前一个删除后唤醒重新判断
5. 释放：删除自己的临时节点（客户端崩溃也自动删，不死锁）
```

#### ② 为什么 ZK 锁更"安全"（vs Redis）

| 特性 | 说明 |
|---|---|
| **临时节点** | 客户端崩溃 → 会话结束 → 节点自动删除 → **不死锁**（Redis 靠 ttl，可能有窗口） |
| **顺序节点** | 序号 FIFO → **天然公平**（Redis 不保证公平） |
| **Watch 通知** | 前一个释放后**推送通知**，不用轮询自旋 |
| **ZAB 强一致** | 节点创建/删除是 CP 共识，无 Redis 主从切换丢锁问题 |

#### ③ Curator 客户端（ZK 锁的工程实现）

```java
InterProcessMutex lock = new InterProcessMutex(client, "/locks/myLock");
lock.acquire();                 // 阻塞获取（内部就是临时顺序节点+Watch）
try { /* 业务 */ }
finally { lock.release(); }
```

Curator 锁家族：`InterProcessMutex`（可重入）、`InterProcessReadWriteLock`（读写）、`InterProcessSemaphoreMutex`（不可重入）、`InterProcessMultiLock`（多锁）。

> ⚠️ **易错点**：ZK 锁**性能差**（每次创建/删除节点是 ZAB 写，高频下是 ZooKeeper 写瓶颈），高并发下别用 ZK 做锁；但**可靠性/公平性**最好。

#### ④ 追问

- 面试官："ZK 锁有羊群效应吗？"→ 原始"监听父节点所有子节点"有（一个释放唤醒全部）；Curator 优化为**只监听前一个节点**，把惊群降到 O(1) 唤醒。

### 知识点六：Redis vs ZooKeeper 锁对比与选型

**一句话记忆**：**Redis 锁 = 高性能（AP 思路），ZK 锁 = 高可靠（CP 思路）；高并发扣库存用 Redis，强一致/可靠性用 ZK**。

| 维度 | Redis 锁 | ZooKeeper 锁 |
|---|---|---|
| 性能 | **高**（内存 + 单条命令） | 低（ZAB 写 + 节点操作） |
| 死锁风险 | 靠过期时间（有窗口） | **低**（临时节点自动删） |
| 公平性 | 不保证 | **公平**（顺序节点 FIFO） |
| 可靠性 | 单点需红锁/主从 | **高**（ZAB 强一致） |
| 客户端崩溃恢复 | ttl 到期（秒级） | 会话超时（可配置，秒级） |
| 框架 | Redisson | Curator |
| CAP 侧重 | AP（可用性优先） | CP（一致性优先） |
| 适用 | 高并发、性能敏感 | 可靠性优先、低并发 |

**选型口诀**：默认 **Redis + Redisson**（99% 场景够用）；对"锁一定不能失效"（如金融强一致）且低并发 → **ZK + Curator**。

### 知识点七：Redlock 争议（面试加分点）

**一句话记忆**：**Redlock 想解决"Redis 主从切换丢锁"，用多节点多数派；但被质疑'时钟假设+故障窗口没真正消除'——生产多数场景单节点 + 看门狗够用**。

#### ① 为什么有 Redlock

单 Redis 锁的失效场景：

```
A 在 master 拿到锁 → master 宕机 → 锁未同步到 replica → replica 升级为新 master
B 在新 master 拿到锁 → 同一时刻 A、B 都"持有锁" → 互斥失效!
```

Redlock：对 **N 个独立 Redis 节点**（如 5 个）依次加锁，**多数派（≥N/2+1）成功**才算拿到。

```
加锁: for 5 个节点: SET key token NX PX (带短超时,避免节点挂了阻塞)
      成功节点 ≥ 3 且总耗时 < ttl → 拿到锁
释放: 对所有节点执行 Lua 释放
```

#### ② 争议双方（Kleppmann vs Antirez，2016 经典论战）

| 观点 | 提出者 | 核心论点 |
|---|---|---|
| **反对 Redlock** | Martin Kleppmann（《数据密集型应用系统设计》作者） | ① 依赖**时钟**（节点时钟漂移会让 ttl 失效）；② 加锁成功后仍有 **GC pause/网络延迟**窗口，锁可能已过期但客户端不知道；③ 没有"fencing token"机制，无法防住"过期锁的旧客户端"继续写 |
| **支持 Redlock** | Salvatore Sanfilippo（Redis 作者 Antirez） | ① Redlock 的分布式锁**不保证**绝对互斥，但保证"进程崩溃恢复"场景下的安全；② 时钟漂移假设不现实（NTP 保证）；③ 任何分布式锁（包括 ZK）都有类似窗口 |

**社区共识**：Redlock 既不"完美"也不"一无是处"；生产**多数场景单节点 Redisson + 看门狗够用**，Redlock 用于跨数据中心/极端可靠性，且**业务侧必须用幂等 + 版本号兜底**（fencing token 思路）。

#### ③ fencing token 思路（Kleppmann 的补救）

```
锁服务每次发锁时分配单调递增的 token:
A 拿锁 → token=10 → A 写请求带 token=10
B 拿锁 → token=11 → B 写请求带 token=11
存储端: 只接受 token 更大的写 → A 的过期写(10)被拒 ✅
```

这就是"**锁 + 版本号**"的通用防护：分布式锁只管互斥，**数据一致性最后靠业务幂等/版本兜底**。

#### ④ 追问

- 面试官："Redlock 还有人在用吗？"→ Redisson 有 `RedissonRedLock` 实现；但很多团队评估后回到单节点+看门狗+业务幂等。面试答出"争议+双方观点+fencing token"即加分。

### 知识点八：分布式锁 vs Seata 全局锁 vs MySQL 行锁（选型边界）

**一句话记忆**：**MySQL 行锁管"单库单表行"，Seata 全局锁管"全局事务内的行"，分布式锁管"业务级跨服务互斥"——三层粒度不同**。

| 维度 | MySQL 行锁 | Seata 全局锁 | 分布式锁（Redis/ZK） |
|---|---|---|---|
| 粒度 | 单库单表的**行** | 全局事务涉及的**记录**（跨库） | **业务语义**（如"商品1"、"用户2"） |
| 触发 | SQL 执行时自动 | AT 一阶段提交前自动申请 | 代码显式加锁 |
| 范围 | 单数据库 | 跨库跨服务（TC 维护） | 跨服务（Redis/ZK 独立部署） |
| 是否业务侵入 | 无（SQL 层） | 低（注解+代理） | 显式 lock/unlock |
| 场景 | 单库并发写 | 分布式事务写隔离 | 防重、限流、任务互斥 |
| 一致性基础 | 数据库 MVCC | TC 锁表 | Redis 单线程/ZK ZAB |

**选型口诀**：**单库并发写 → MySQL 行锁天然够；跨库写一致 → Seata 全局锁；跨服务业务互斥（防重/限流/任务）→ 分布式锁**。三者互补不冲突——Seata 内部抢锁靠 TC，业务层还能再套分布式锁防重。

#### 追问

- 面试官："扣库存用分布式锁还是 MySQL 条件更新？"→ 单库直接用 `update stock set count=count-1 where count>0`（行锁+条件，最简单可靠）；跨服务/预扣场景才需要分布式锁或 TCC。

### 知识点九：场景设计——分布式锁的完整落地

**一句话记忆**：**加锁要原子（SET NX PX）、续期要看门狗、释放要 Lua 校验、业务要幂等兜底、锁粒度要细**。

#### ① 定时任务防重复执行

```
多台机器同一 cron → 只有一台能执行
方案: Redis 锁 key=task:xxx, ttl=执行上限, 拿到才跑
```

#### ② 秒杀扣库存（分布式锁版）

```
1. SET stock_lock {orderId} NX PX 3000
2. 拿到 → Redis 预减库存 → 异步落库（带版本号）
3. 释放: Lua 校验 token 删除
4. 幂等兜底: 落库按 orderId 唯一键去重
```

#### ③ 锁粒度优化（易被问）

| 粒度 | 示例 | 问题 |
|---|---|---|
| 粗（全局锁） | `lock("inventory")` 锁所有商品 | 并发全串行，吞吐低 |
| 细（分片锁） | `lock("inventory:" + productId)` | 不同商品并行 ✅ |
| 更细（分段） | `lock("inventory:" + productId + ":" + segId)` | 同商品也分段（配合分段库存） |

**原则：锁粒度越细，并发越高**；但太细管理复杂。经典组合 = 商品级锁 + 业务幂等。

#### ④ 追问

- 面试官："锁的 key 设计要注意什么？"→ ① 加业务前缀防冲突；② 粒度匹配业务（商品/订单/用户）；③ 考虑 TTL 兜底；④ 大 key 热点需分片。

## 4. 最佳实践

- **默认 Redisson**：`lock()`（看门狗续期）+ `unlock()` finally 释放，别手写 SETNX（易漏续期/误删）。
- **释放必须 Lua 校验**：手写场景 token 校验 + 删除原子。
- **业务幂等兜底**：锁不是银弹——过期/换手窗口用版本号/唯一键兜底（fencing token 思想）。
- **锁粒度细分**：商品级/订单级，别全局一把锁。
- **监控锁竞争**：等待时间、持锁时间、超时次数；长持锁 = 业务慢或死锁隐患。
- **ZK 锁低并发用**：别拿 ZK 锁扛高并发（ZAB 写瓶颈）。
- **多实例部署注意**：Redis 单节点锁在"主从切换"场景有失效窗口，重要场景评估 Redlock 或 ZK。

## 5. 常见踩坑

- 加锁和过期分开两条命令 → 崩溃死锁（必须 `SET NX PX` 原子）。
- 释放不校验 token 直接 del → 误删别人锁（必须 Lua）。
- 用 `lock(ttl)` 却以为有看门狗 → 业务超时锁提前释放（无参 `lock()` 才续期）。
- 忘记 finally unlock → 看门狗一直续期 → 锁永不释放。
- 全局一把锁 → 并发全串行（粒度要细分）。
- 依赖锁做数据一致性，不做幂等 → 过期窗口数据竞争。
- Redis 主从切换丢锁 → 强一致场景评估 Redlock/ZK。

## 6. 小结

- 分布式锁 = 跨进程互斥；三个核心问题：死锁（过期）、误删（token）、原子（SET NX PX）。
- **Redis 锁**：高性能（AP）；Redisson 看门狗默认 30s/10s 续期；释放 Lua 校验。
- **ZK 锁**：高可靠（CP）；临时顺序节点 + Watch，无死锁、公平；性能差。
- **Redlock**：多节点多数派；有争议（时钟/GC 窗口/fencing token），生产默认单节点+幂等。
- 选型：高并发 Redis、强一致 ZK；与 MySQL 行锁/Seata 全局锁粒度互补。
