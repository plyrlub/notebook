## 3. 核心知识点

### 知识点一：为什么需要 Hash 分布

**一句话记忆**：**Hash 把数据/请求"均匀 + 可定位"地映射到集群节点——知道 key 就能 O(1) 算出它在哪台机器**。

#### ① 是什么

分布式场景两个核心用途：

1. **请求负载均衡**：按 key（IP/用户/URL）hash 分发到不同服务器。
2. **数据分片**：按数据 key hash 决定存到哪个节点（缓存分片、数据库分片）。

#### ② 基础 Hash 算法（复习）

| 算法 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| 直接寻址 | 数组下标=值 | O(1) | 浪费空间 |
| 除留余数法 | `hash(key) % N` | 简单 | 冲突、N 变化全乱 |
| 开放寻址/拉链 | 冲突处理 | 解决冲突 | 实现复杂 |

> 💡 **记忆锚点**：分布式关注的核心不是"怎么算 hash"（用现成函数），而是 **"hash 结果如何映射到节点、节点变化时映射如何受影响"**——这正是一致性 Hash 解决的。

---

### 知识点二：普通取模 Hash 的问题——雪崩式重映射

**一句话记忆**：**`server = hash(key) % N` 的致命伤：N（节点数）一变，几乎全部 key 的映射都变——缓存全部失效、数据大量搬家**。

#### ① 问题演示

```
有 3 台服务器: key → hash(key) % 3
扩容到 4 台:   key → hash(key) % 4   ← 模数变了!
→ 绝大多数 key 的结果都变了（只有少量巧合不变）
→ 缓存: 全部 miss（雪崩）; 存储: 需要迁移几乎所有数据
```

**后果**：扩容/缩容本来是"加一台机器"，结果触发**全量数据搬迁 + 缓存雪崩**，比不加机器还糟。

#### ② 为什么模数一变就全乱

取模是把 hash 值**均匀切成 N 段**，N 变 = 切法变 = 每个 key 的归属段几乎都变。数学上，变更后不变的 key 比例约 **1/N**（N 小更惨）。

> ⚠️ **易错点**：很多人以为"加一台机器只影响 1/N 数据"——那是**一致性 Hash** 的性质；**普通取模是 (N-1)/N 的数据都受影响**，两者天壤之别。

---

### 知识点三：一致性 Hash——哈希环原理 ★核心

**一句话记忆**：**把 hash 值空间 [0, 2^32-1] 首尾相连成环，服务器和 key 都 hash 落环上，key 顺时针找第一个服务器——节点增减只影响环上局部**。

#### ① 核心思路

```
1. 服务器 hash(如 IP) → 落环上一点
2. 数据/请求 key hash → 落环上一点
3. key 沿环【顺时针】找第一个服务器 → 归属它
```

```
          0 / 2^32-1
        ↗           ↖
      ↙               ↘
   服务器A            服务器C
      ↘               ↗
        ↖           ↗
          keyX → 顺时针 → 服务器B（keyX 归 B）
```

#### ② 为什么节点增减只影响局部（核心价值）

**节点下线**（服务器 B 下线）：

```
B 下线 → 原本归 B 的 key 顺时针找下一个 → 归 C
其余 key（归 A、C 的）完全不受影响
受影响比例 ≈ B 在环上覆盖的范围 ≈ 1/N
```

**节点新增**（插入 D）：

```
D 落环 → 只接管"D 与它前一个节点之间"的 key
其余不变; 受影响比例同样 ≈ 1/N
```

**对比**：普通取模受 (N-1)/N 影响，一致性 Hash 只受 **1/N** 影响 → 缓存命中率大幅保住、数据迁移量最小化。

> 💡 **记忆锚点**：**一致性 Hash 的收益 = "节点变化时，只动环上相邻的一小段"**。这是它存在的全部意义。

#### ③ 数据迁移量精确分析（面试进阶）

```
3 节点 → 4 节点（一致性 Hash）:
- 新节点 D 在环上随机落点 → 接管其逆时针方向到前一节点之间的 key
- 期望迁移量 = 1/4 = 25%（且集中在 D 附近）
对比取模: 迁移量 ≈ 75%

节点越多, 单节点增减影响越小 (1/N → 0)
```

**注意**：一致性 Hash 保证的是"迁移量小"，**不保证迁移均匀**（可能集中在环上某段）——虚拟节点改善这一点（见知识点五）。

---

### 知识点四：数据倾斜——少节点的分布不均

**一句话记忆**：**节点少时，环上分布可能"扎堆"——一个大段全归一台机器，负载失衡**。

#### ① 问题演示

```
环上只有 2 台服务器 A、B:
若 A、B 距离很近 → 环上 90% 的区域顺时针归 A → A 扛 90% 流量
```

**根因**：服务器 hash 落点是**随机的**，节点少时随机性无法"摊平"，容易出现大片空白段归同一节点。

#### ② 为什么节点越少越严重

- 每个节点的"管辖范围"= 它与前一节点之间的弧长。
- 节点少 → 单段弧长方差大 → 有的段巨大（热点）、有的段极小（闲置）。
- 数学上：N 个随机点的间距分布方差与 N 成反比，N 小则方差大。

> ⚠️ **易错点**：**一致性 Hash 不等于"均匀分布"**——它只保证"增减影响小"，均匀性要靠虚拟节点补。面试答"一致性 Hash 天然均匀"会被纠。

---

### 知识点五：虚拟节点——解决倾斜 ★核心

**一句话记忆**：**给每台服务器"克隆"出很多虚拟点撒满环（如 160 个），管辖范围被摊碎摊匀——热点消失，增减更平滑**。

#### ① 原理

```
服务器 A → 虚拟节点 A#1, A#2, ..., A#160（每台 160 个）
环上从"每台 1 个点"变成"每台 160 个点"
key 顺时针找到虚拟节点 → 映射回物理服务器（A#37 → 服务器 A）
```

#### ② 为什么有效（两层收益）

| 收益 | 原理 |
|---|---|
| **分布均匀** | 160×N 个随机点撒环，各段的方差按 1/(160N) 缩小 → 管辖范围趋近等分 |
| **增减平滑** | 一台机器下线 = 它的 160 个虚拟点同时消失 → 管辖范围分散给 160 个邻居，而不是整体压给 1 个节点 → **负载再均衡更平滑** |

#### ③ 虚拟节点数怎么定

- 经验值：**每台 100~200 个**（ketama 默认 160），越多越均匀但内存/计算开销越大。
- 工程上常按权重调整：大机器虚拟节点多、小机器少（加权一致性哈希）。

#### ④ 追问

- 面试官："虚拟节点的 key 怎么生成？"→ 常见两种：① `hash(serverId + "#" + i)`（字符串拼接再 hash）；② 用不同 hash 函数（如 MD5 的多个字节段）。ketama 用 `md5(serverId + "-" + i)` 的 4 字节切片生成 4 个点（160 点 = 40 个 md5 × 4 切片）。

---

### 知识点六：ketama——一致性哈希的经典实现

**一句话记忆**：**ketama = "Karger 一致性哈希 + 虚拟节点"的工程落地，Nginx/Memcached 客户端用它，默认每服务器 160 个虚拟点**。

#### ① 核心实现细节（面试加分）

```
1. 每台服务器生成 160 个虚拟点:
   for i in 0..39: md5 = MD5(serverId + "-" + i)
      4 个 4 字节切片 → 4 个 uint32 值 → 4 个环上点
2. 环上点按值排序存数组（二分查找定位）
3. key 同样 hash → 二分找第一个 ≥ 它的点 → 对应服务器
4. 服务器增减 → 重建虚拟点集合（重新排序）
```

**关键点**：

- 环上的点**预先排序存储**（有序数组/红黑树）→ 查找 O(log N)，不是每次遍历。
- 虚拟点数量固定（160）→ 增减服务器时只影响"该服务器对应的点"，重排开销可控。

#### ② 与"一致性哈希"的关系

| 术语 | 说明 |
|---|---|
| 一致性 Hash | 算法本身（Karger 1997：环 + 顺时针寻址） |
| ketama | 工程实现（虚拟节点默认 160、md5 拼接、有序存储） |
| 使用方 | Nginx `consistent` 参数、Memcached 客户端（spymemcached）、一致性哈希负载均衡库 |

---

### 知识点七：与 Redis 哈希槽 / Nginx 的对照 ★对比

**一句话记忆**：**一致性 Hash 适合"节点数会变 + 数据可容忍倾斜"（缓存分片）；Redis 哈希槽用固定槽位换"均匀 + 可迁移"；Nginx consistent 是 ketama 的负载均衡应用**。

#### ① Redis 为什么用 16384 哈希槽，不用一致性 Hash

| 维度 | 一致性 Hash | Redis 哈希槽 |
|---|---|---|
| 分布方式 | 服务器 hash 落环（随机） | **固定 16384 槽**，槽均匀分给节点 |
| 均匀性 | 需虚拟节点 | **天然均匀**（槽均分） |
| 增减节点 | 只动局部 key | **迁移"整段槽"**（`CLUSTER SETSLOT`），可控可回滚 |
| 迁移单位 | 逐个 key 判断 | 按槽批量（亿级 key 也能按槽迁） |
| 实现复杂度 | 低 | 中（客户端要算 CRC16 % 16384） |

**结论**：Redis Cluster 要"**均匀分布 + 按槽可控迁移**"，哈希槽比一致性 Hash 更合适——这是 16384 槽设计的核心动机。

> 补充：为什么是 16384？① 槽位 = `CRC16(key) % 16384`；② 16384 是 2^14，槽位足够细（均匀）+ 心跳包 bitmap 2KB 可接受；③ 官方权衡了"槽粒度 vs 通信开销"。**面试答"16384 = 均匀性 + 心跳包体积折中"即可**。

#### ② Nginx 的一致性哈希（ketama 应用）

```nginx
upstream cache_backend {
    hash $request_uri consistent;   # consistent 开启一致性哈希(ketama)
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

| Nginx 指令 | 行为 | 适用 |
|---|---|---|
| `ip_hash` | 按 IP 固定（会话保持） | 有状态会话（见 [09-分布式Session详解](09-分布式Session详解.md)） |
| `hash $uri`（无 consistent） | 普通取模 | 节点稳定的简单场景 |
| `hash $uri consistent` | **ketama 一致性哈希** | **缓存后端**（节点增减缓存命中率不崩） |

#### ③ 三方案总对照

| 技术 | 分布方式 | 节点增减影响 | 均匀性 | 适用 |
|---|---|---|---|---|
| 取模 Hash | `hash % N` | **(N-1)/N 全乱** | 均匀 | 节点固定 |
| 一致性 Hash | 环 + 虚拟节点 | **1/N 局部** | 需虚拟节点 | 缓存分片、Nginx LB、动态节点 |
| Redis 哈希槽 | 16384 槽均分 | 按槽迁移（可控） | 天然均匀 | Redis Cluster 分片 |

### 知识点八：工程实践与面试总结

**一句话记忆**：**一致性 Hash 用对场景才有价值——缓存分片/动态扩缩容是它的主场；固定节点数用取模更简单，要均匀可控用哈希槽**。

#### ① 使用场景清单

| 场景 | 用不用一致性 Hash | 理由 |
|---|---|---|
| 缓存分片（Memcached/Redis 分片） | ✅ | 扩缩容缓存不雪崩 |
| Nginx 后端负载均衡（缓存型） | ✅ | `hash $uri consistent` |
| 数据库分库分表 | ⚠️ 谨慎 | 分片后迁移困难，更多用**范围/哈希预分片**（如 1024 逻辑分片） |
| 固定节点数（内网服务） | ❌ | 取模更简单 |
| Redis Cluster | ❌ | 哈希槽已覆盖 |

#### ② 实践要点

- **虚拟节点必配**：节点少时没有虚拟节点 = 严重倾斜。
- **hash 函数选择**：要**均匀 + 稳定**（同一 key 永远同一结果），MD5/SHA 系；避免用不稳定的 hash。
- **一致性哈希不解决"数据迁移逻辑"**：它只决定"key 归谁"，迁移时仍需显式搬数据/回源重建。
- **监控**：各节点负载方差（倾斜检测）、迁移量、命中率。

#### ③ 追问

- 面试官："一致性 Hash 有什么缺点？"→ ① 不保证均匀（需虚拟节点）；② 不解决"已存数据的迁移"（只影响新映射）；③ 环上数据分布不可控（不像槽位可手动规划）；④ 热点 key 依然热点（需热点感知/分层）。

## 4. 最佳实践

- **缓存分片默认一致性 Hash + 虚拟节点**（160/台起步）。
- **节点数少（<10）时虚拟节点数加倍**，倾斜可测（负载方差）。
- **哈希函数用稳定均匀的**（MD5/SHA-256 截断），别用 Java `hashCode`（不均匀、可被构造碰撞）。
- **Redis Cluster 用哈希槽**，别硬套一致性 Hash。
- **Nginx 缓存后端**用 `hash $uri consistent`；普通后端轮询即可。
- **分库分表预分片**（逻辑分片 1024 个 + 映射表），比动态一致性 Hash 更可控。

## 5. 常见踩坑

- 取模 Hash 用于动态集群 → 扩容缓存雪崩（N 一变全乱）。
- 一致性 Hash 不加虚拟节点 → 少节点严重倾斜。
- 用 `hashCode()` 做分布 → 不均匀 + 易碰撞（String hash 可构造）。
- 以为一致性 Hash 保证均匀 → 它只保证"增减影响小"，均匀靠虚拟节点。
- 用一致性 Hash 管 Redis Cluster → 与哈希槽冲突，集群迁移逻辑错乱。
- 忘记迁移数据 → 一致性 Hash 只改映射，旧数据要显式搬/回源。

## 6. 小结

- 取模 Hash：简单但节点增减 **(N-1)/N 数据重排**（雪崩）。
- 一致性 Hash：**环 + 顺时针寻址**，节点增减只影响 **1/N** 局部。
- 数据倾斜 → **虚拟节点**（每台 160 个点）摊碎管辖范围。
- ketama：工程实现（md5 拼接 + 有序存储 + 二分查找）。
- 对照：Redis 哈希槽（16384，均匀+按槽迁移）＞一致性 Hash（动态场景）；Nginx `consistent` 是 ketama 应用。
