## 1. 是什么：为什么需要分布式锁

**一句话记忆**：**单机锁只在同一个 JVM/进程内有效，分布式环境跨进程，需要"跨进程的锁"**来保证多个服务器互斥访问共享资源。

| 锁类型 | 作用范围 | 适用 |
|---|---|---|
| JVM 锁（synchronized/ReentrantLock） | **单进程内** | 单机多线程 |
| **分布式锁** | **跨进程/跨服务器** | 多台机器操作共享资源 |

**典型场景**：多台服务器同时扣库存、抢优惠券、执行定时任务——需要保证**同一时刻只有一个节点**能做。

> 💡 **记忆锚点**：**分布式锁 = "跨机器的锁"**。单机锁解决线程竞争，分布式锁解决**机器之间**的竞争。

## 2. Redis 实现分布式锁

### 2.1 基础版：SETNX + 过期（原子）

```bash
# 加锁：NX=不存在才设置，PX=过期时间（原子，一条命令）
SET lock_key unique_token NX PX 10000
# 成功=拿到锁；失败=锁被占用

# 业务操作...

# 释放锁：必须校验 value 是自己的（Lua 原子，防误删）
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 2.2 三个核心问题（必须解决）

| 问题 | 场景 | 解决 |
|---|---|---|
| **死锁** | 拿锁后崩溃，锁永远不放 | 加锁时设**过期时间**（PX 10000） |
| **误删** | 锁过期后被别人拿到，自己又去删 | value 存**唯一 token**，删除前校验 |
| **原子性** | setnx + expire 分开，中间崩溃 | 用 **`SET NX PX` 一条命令**（原子） |

> ⚠️ **易错点（面试高频）**：
> - **加锁和设过期必须原子**（`SET key val NX PX ttl`），分开两条会死锁
> - **释放锁必须校验 value 是自己的**（Lua 脚本原子"校验+删除"），否则误删别人的锁
> - value 用**唯一 token**（UUID），不是固定字符串

### 2.3 Redisson 看门狗（自动续期）

**问题**：固定过期时间（如 10s）下，业务跑超过 10s，锁自动过期 → 别人拿到锁 → 并发问题。

**Redisson 看门狗（WatchDog）**：加锁后**自动续期**（默认每 10s 续到 30s），业务没跑完锁不过期，完成释放停止。

```java
RLock lock = redisson.getLock("myLock");
lock.lock();          // 看门狗自动续期
try { /* 业务 */ }
finally { lock.unlock(); }
```

> 💡 **记忆锚点**：**看门狗 = 给锁"自动续命"**——防止业务没跑完锁先过期。Redisson 内置可重入锁、公平锁、读写锁等多种。

## 3. Zookeeper 实现分布式锁

### 3.1 原理（临时顺序节点 + 监听）

Zookeeper 用**临时顺序节点 + 事件监听**实现分布式锁：

```
1. 在 /locks 下创建临时顺序节点（如 /locks/lock_01）
2. 检查自己是否是最小的节点
   ├── 是 → 拿到锁
   └── 否 → 监听前一个节点，它释放后自己获取
3. 释放锁：删除自己的临时节点
```

### 3.2 为什么 ZK 锁更"安全"

| 优势 | 说明 |
|---|---|
| **临时节点** | 客户端崩溃时**临时节点自动删除**，不会死锁 |
| **顺序节点** | 天然公平（FIFO），先到先得 |
| **监听机制** | 前一个节点释放时**通知**，不用无效自旋 |

> ⚠️ **易错点**：ZK 锁**性能比 Redis 差**（频繁创建/删除节点 + 同步），高并发下不建议用 ZK 做锁；但**可靠性、公平性更好**（无死锁风险）。

## 4. Redis vs Zookeeper 锁对比

| 维度 | Redis 锁 | Zookeeper 锁 |
|---|---|---|
| **性能** | 高（内存操作） | 低（节点操作 + 同步） |
| **死锁风险** | 需自己防（过期时间） | 低（临时节点自动删） |
| **公平性** | 不保证 | 公平（顺序节点 FIFO） |
| **可靠性** | 单点需 Redlock | 高（ZAB 强一致） |
| **框架** | Redisson | Curator |
| **适用** | 高并发、性能敏感 | 可靠性优先、低并发 |

> 💡 **记忆锚点**：**Redis 锁=高性能，ZK 锁=高可靠**。高并发扣库存用 Redis，强调强一致/可靠性用 ZK。

## 5. Redlock（集群版 Redis 锁）

**问题**：单 Redis 锁在**主从切换时可能失效**（锁在主节点，主节点挂了，锁没同步到新主，别人拿到锁）。

**Redlock**：在**多个独立 Redis 节点**上加锁，**多数派（N/2+1）成功才算拿到锁**，提高可靠性。

```
对 N 个独立 Redis 依次加锁（如 N=5）：
- 超过半数（3）成功 → 拿到锁
- 否则 → 释放所有已加的锁，重试
```

> ⚠️ **易错点**：Redlock **有争议**（Redis 作者反对比尔·盖茨文章批评，社区讨论多），且**性能差**（要访问多个节点）。生产**多数场景单节点 Redisson 够用**，Redlock 只用于极端可靠性场景。

## 6. 面试追问 Q&A

### 6.1 分布式锁解决什么问题？

单机锁只在同一进程内有效，分布式环境多个服务器操作共享资源时需要**跨进程互斥**。分布式锁保证同一时刻只有一个节点能访问共享资源。

### 6.2 Redis 分布式锁怎么防死锁？

加锁时设置**过期时间**（`SET key val NX PX` 原子），即使客户端崩溃，锁也会自动过期释放。关键：加锁和设过期必须原子，否则中间崩溃会死锁。

### 6.3 为什么释放锁要校验 value？

锁可能因**过期被别的客户端拿到**，如果直接 delete，会误删别人刚拿到的锁。所以 value 存唯一 token，删除前用 **Lua 脚本原子校验"是自己的才删"**。

### 6.4 Redis 锁和 Zookeeper 锁怎么选？

**高并发、性能敏感**用 Redis（Redisson，性能高）；**可靠性优先、低并发**用 Zookeeper（Curator，临时节点无死锁、公平）。Redis 单点需考虑 Redlock。
