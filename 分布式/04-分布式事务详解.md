## 1. 是什么：为什么需要分布式事务

**一句话记忆**：单机事务保证一个数据库的原子性，**分布式事务要保证多个服务/数据库的操作"要么全成功要么全回滚"**。

**典型场景**：下单 = 订单服务 + 库存服务 + 账户服务，三个服务跨库操作，任何一步失败都要全部回滚。

> 💡 **记忆锚点**：**单机事务管一个库，分布式事务管"多个库/多个服务"的一致性**。跨服务无法用本地事务保证原子性，需要分布式事务方案。

## 2. 刚性事务：2PC / 3PC

### 2.1 2PC（两阶段提交）

**2PC** 引入一个**协调者**，分两个阶段协调所有参与者：

```
协调者                参与者1  参与者2
  │---准备(prepare)-----▶│        │
  │---准备(prepare)--------▶│        │
  │◀----就绪/失败---------│        │
  │◀----就绪/失败-----------------│
  │（全部就绪？）
  │---提交/回滚(commit/rollback)--▶│
  │---提交/回滚-------------------▶│
```

| 阶段 | 说明 |
|---|---|
| **准备阶段** | 协调者问所有参与者"能提交吗"，参与者执行事务但不提交，反馈结果 |
| **提交阶段** | 全就绪→协调者发提交；任一失败→发回滚 |

**优缺点**：
- ✅ **强一致**（所有参与者要么全提交要么全回滚）
- ❌ **性能低**（多次网络交互 + 资源锁长时间占用）
- ❌ **单点阻塞**（协调者故障则卡住）

### 2.2 3PC（三阶段提交）

3PC 在 2PC 基础上，把"准备"拆成"询问 + 准备"，**降低阻塞、引入超时**，但**极端网络下仍可能不一致**。复杂度高，实际少用。

> ⚠️ **易错点**：**2PC 强一致但性能差、有单点阻塞**；3PC 改善阻塞但无法完全避免不一致。刚性事务适合**并发度低、一致性要求高**的场景（如金融转账），不适合高并发。

## 3. 柔性事务：TCC

### 3.1 什么是 TCC

**TCC** 是**业务侵入型**柔性事务，把每个操作拆成 **Try、Confirm、Cancel** 三个阶段：

| 阶段 | 含义 | 示例（扣款） |
|---|---|---|
| **Try** | 预留资源（不实际生效） | 冻结 100 元 |
| **Confirm** | 确认提交（真正生效） | 真正扣款 |
| **Cancel** | 取消/回滚（释放预留） | 解冻 100 元 |

**流程**：
```
Try 全部成功 → Confirm 全部提交
Try 任一失败 → Cancel 全部回滚（补偿）
```

> 💡 **记忆锚点**：**TCC = "先 Try 预留，全成功 Confirm，有失败 Cancel"**。它把业务拆成可补偿的片段，实现**最终一致**。

### 3.2 优缺点

- ✅ **高可用、性能好**（不长时间锁资源）
- ✅ **最终一致**，适合高并发（支付、库存）
- ❌ **业务侵入强**（每个操作要写 Try/Confirm/Cancel 三段）
- ❌ **实现复杂**，要求**幂等**（Confirm/Cancel 可能重复执行）

> ⚠️ **易错点**：**TCC 的 Confirm/Cancel 必须幂等**（可能被重复调用），且 Cancel 要有对应的业务补偿逻辑（不能简单回滚）。依赖 [05-分布式ID与幂等设计详解](05-分布式ID与幂等设计详解.md)。

## 4. 柔性事务：Saga 与本地消息表

### 4.1 Saga（长事务/流程编排）

**Saga** 把一个长事务拆成多个子事务，每个子事务配一个**补偿操作**：

```
正常流程：A → B → C
任一步失败 → 反向补偿：C补偿 → B补偿 → A补偿
```

| 特点 | 说明 |
|---|---|
| 适用 | **长事务、跨服务流程**（如订票+酒店+保险） |
| 方式 | 每个子事务有正向 + 补偿（Cancel） |
| 一致性 | **最终一致**（先部分执行，失败再补偿） |

### 4.2 本地消息表

**本地消息表 + 消息队列**：写业务和写消息在**同一个本地事务**，消息表保证最终投递。

```
1. 本地事务：业务操作 + 写"待发送消息"表（同库同事务）
2. 定时/异步：扫描消息表，把消息发到 MQ
3. 消费方：消费并处理（幂等），成功后标记消息已发送
```

> 💡 **记忆锚点**：**本地消息表 = "业务和消息写同一个库的事务，保证消息不丢"**。适合订单-积分、异步通知等最终一致场景。

## 5. 方案对比与选型

| 方案 | 一致性 | 性能 | 复杂度 | 业务侵入 | 适用 |
|---|---|---|---|---|---|
| **2PC** | 强一致 | 低 | 中 | 低 | 金融转账、低并发 |
| **3PC** | 强一致（不完全） | 中低 | 高 | 低 | 需减阻塞的强一致 |
| **TCC** | 最终一致 | 高 | 高 | **高** | 高并发（支付/库存） |
| **Saga** | 最终一致 | 中 | 高 | 中 | 长事务、跨服务流程 |
| **本地消息表** | 最终一致 | 高 | 低 | 低 | 订单-积分、异步通知 |

**选型建议**：
- **一致性要求极高 + 低并发**（转账）→ **2PC/XA**
- **高并发 + 可接受最终一致**（支付/库存）→ **TCC**
- **长流程 / 跨服务**（订票+酒店）→ **Saga**
- **异步通知**（订单-积分）→ **本地消息表 + MQ**

> ⚠️ **易错点**：**微服务主流是"柔性事务 + 最终一致"（TCC/Saga/本地消息表）**，而非 2PC。因为强一致的 2PC 性能差、阻塞，不符合微服务高可用理念。

## 6. 面试追问 Q&A

### 6.1 分布式事务有哪些解决方案？

刚性事务（2PC/3PC，强一致）+ 柔性事务（TCC、Saga、本地消息表 + MQ，最终一致）。微服务主流用柔性事务。

### 6.2 2PC 的缺点？

**性能低**（多次网络交互 + 资源锁长时间占用）、**单点阻塞**（协调者故障卡住）。强一致但只适合低并发、一致性要求高的场景。

### 6.3 TCC 和 2PC 的区别？

2PC 是**数据库级**强一致（自动提交/回滚），TCC 是**业务级**柔性事务（Try/Confirm/Cancel 手动实现，最终一致）。TCC 性能好、适合高并发，但业务侵入强、要求幂等。

### 6.4 什么是最终一致？

BASE 理论的核心：允许数据**短暂不一致**，通过异步同步、补偿、重试等机制**最终收敛一致**。柔性事务（TCC/Saga/本地消息表）都基于最终一致思想。
