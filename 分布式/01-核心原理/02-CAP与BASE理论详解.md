## 3. 核心知识点

### 知识点一：CAP 三要素

**一句话记忆**：**C=数据一致，A=总有响应，P=分区也能扛——分布式系统必须选 P，分区时在 C 和 A 之间二选一**。

| 要素 | 英文 | 准确含义 |
|---|---|---|
| **一致性 C** | Consistency | 所有节点**同一时刻**看到相同数据（读到最新已提交写入）；强调**原子性可见**（读要么读到最新值，要么报错） |
| **可用性 A** | Availability | **每个请求**都能在合理时间得到**非错误响应**；强调"总有回应"（即使返回旧数据也算可用） |
| **分区容错 P** | Partition tolerance | **网络分区/节点故障**时系统仍能继续工作；强调"部分失联不瘫痪" |

> ⚠️ **易错点**：CAP 的 C 是**线性一致性**（读到最新值），不是数据库 ACID 的"事务一致性"！两个 C 含义不同，面试答混会扣分。

### 知识点二：为什么只能三选二（准确版）

**核心**：**P 是必选的**——网络分区是分布式系统的客观现实，无法避免。所以问题退化为"分区时 C 和 A 二选一"：

```
网络分区（一部分节点无法通信），此时来一个写请求：
├── 选 C（一致性）：放弃响应，等待分区恢复同步 → 牺牲 A
│     → 客户端可能超时/等待，但数据一致
└── 选 A（可用性）：立即响应（各分区自洽）→ 牺牲 C
      → 客户端拿到响应，但分区间的数据可能不一致
→ CAP 说：分区时 C 和 A 只能选一个，无法同时满足
```

**关键理解**：

- **P 必选**：所以实际是 **CP 或 AP 二选一**。
- **网络正常时 C 和 A 可以同时满足**；只有分区时才被迫取舍。
- "三选二"是简化说法，**严格说**是"P 必选 + 分区时 C/A 二选一"。
- **分区是罕见事件**：日常运行时系统通常"三全满足"，CAP 只在分区瞬间生效。

> 💡 **记忆锚点**：**CAP 不是"三个选两个随便选"，而是"P 逃不掉，C 和 A 才是选择题"**。

### 知识点三：CP vs AP——典型系统判断

| 系统 | 侧重 | 说明 |
|---|---|---|
| **ZooKeeper** | **CP** | ZAB 强一致，少数节点不可用则服务不可用（宁可不可用不给错数据） |
| **etcd** | **CP** | Raft 强一致，分布式协调/配置 |
| **MySQL 主从** | **CP**（同步模式） | 同步复制强一致；异步复制实际是 AP 倾向 |
| **Redis** | **AP**（默认） | 主从异步复制，可能读到旧数据（可用 WAIT 提升） |
| **Eureka** | **AP** | 注册中心，优先可用（节点间互相注册，挂了也能注册） |
| **Cassandra** | **AP** | 最终一致（可配 QUORUM 提升一致性） |
| **Nacos** | 混合 | 临时实例 AP（注册），持久实例 CP（配置） |

> 💡 **记忆锚点**：**协调/存储类倾向 CP（ZK/etcd），缓存/注册类倾向 AP（Redis/Eureka）**——看业务更怕"数据不一致"还是"服务不可用"。

### 知识点四：BASE 理论

**一句话记忆**：**BASE = "反正最终会一致，先保证可用"——对强一致性的降级妥协，是 AP 侧的实践总结**。

| 要素 | 含义 |
|---|---|
| **Basically Available**（基本可用） | 核心功能可用，允许降级（如限流、返回旧缓存） |
| **Soft state**（软状态） | 状态允许短暂不一致（中间态） |
| **Eventually consistent**（最终一致） | 靠异步同步/补偿，数据最终收敛一致 |

**BASE vs ACID**：

| 维度 | ACID（单机事务） | BASE（分布式） |
|---|---|---|
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 牺牲（事务阻塞） | **优先可用** |
| 隔离性 | 有 | 无/弱 |
| 典型 | 数据库事务 | 微服务、消息队列 |
| 思想 | 严格保证 | 妥协降级 |

> 💡 **记忆锚点**：**ACID 是"数据库的理想"，BASE 是"分布式的现实"**。柔性事务（TCC/Saga/消息表）都是 BASE 思想的落地，详见 [04-分布式事务详解](04-分布式事务详解.md)。

### 知识点五：PACELC——对 CAP 的完善（面试加分）

**一句话记忆**：**CAP 只讲了"分区时"的取舍；PACELC 补充"无分区时"还要在延迟 L 和一致性 C 之间选——于是有了 PA/PC/EL/EC 四个组合**。

#### ① 为什么需要 PACELC

CAP 只讨论**分区发生时的取舍**，但系统 99.9% 时间**没有分区**——这时一致性 vs 延迟的取舍才是日常决定。Daniel Abadi 2012 年提出：

```
PACELC:
P = Partition（分区时）
A = Availability（可用）   → 分区时 选可用
C = Consistency（一致）    → 分区时 选一致
E = Else（无分区时）
L = Latency（低延迟）      → 无分区时 选低延迟
C = Consistency（一致）    → 无分区时 选一致
```

#### ② 四种组合与典型系统

| 组合 | 分区时 | 平时 | 代表系统 | 例子 |
|---|---|---|---|---|
| **PA/EL** | 可用 | 低延迟 | DynamoDB、Cassandra（默认）、Redis | 平时异步复制（快），分区时各自为政 |
| **PA/EC** | 可用 | 一致 | MongoDB（某些配置）、DynamoDB（强一致读） | 平时同步等多数派（慢一点），分区时保可用 |
| **PC/EL** | 一致 | 低延迟 | ZooKeeper、etcd（多数派内） | 分区时拒绝服务保一致，平时多数派即快 |
| **PC/EC** | 一致 | 一致 | Spanner（同步复制） | 任何时候都强一致，代价是高延迟（跨地域） |

> 💡 **记忆锚点**：**CAP 回答"分区时怎么办"，PACELC 回答"平时怎么办"**。面试答完 CAP 再补 PACELC，立刻和只会背 CAP 的候选人拉开差距。

#### ③ 追问

- 面试官："Redis 是 PA/EL 还是 PA/EC？"→ 默认 **PA/EL**（异步复制，快但可能丢/旧）；开启 WAIT 或 Redis Cluster 强一致选项才偏 PA/EC。ZK 是 **PC/EL**（分区宁可不可用，平时多数派确认）。

### 知识点六：一致性模型谱系（面试进阶）

**一句话记忆**：**一致性从强到弱：线性 > 顺序 > 因果 > 最终——强度越高实现越贵，系统按需选择**。

| 模型 | 强度 | 含义 | 典型系统 | 代价 |
|---|---|---|---|---|
| **线性一致性**（Linearizability） | 最强 | 所有操作按**全局实时序**执行，读必读到最新已提交写；等价于"单机执行" | etcd 写、ZK 写、Spanner、MySQL 单机 | 高延迟（同步多数派） |
| **顺序一致性**（Sequential） | 强 | 所有操作按**某种全局顺序**执行（不必与实时一致），各进程看到的顺序一致 | ZooKeeper 读（session 内）、部分分布式 DB | 中 |
| **因果一致性**（Causal） | 中 | 有**因果关系**的操作顺序一致，无因果的可乱序 | COPS、CRDT 系统、消息队列（部分） | 低 |
| **最终一致**（Eventual） | 弱 | 无新写入后，副本**最终**收敛一致；期间读可能旧 | DynamoDB、Cassandra、DNS、Redis 主从 | 最低（异步） |

**为什么线性一致性最强**：它要求操作顺序和**真实时间**一致——两个并发操作，先发生的一定先生效。Raft/Paxos 提交保证线性一致（见 [07-Raft与Paxos共识算法详解](07-Raft与Paxos共识算法详解.md)）。

**各模型判断口诀**：

- 线性 = "像只有一个节点，且按真实时间"
- 顺序 = "像只有一个节点，但时间可重排"
- 因果 = "有因果的必须有序，没因果随便"
- 最终 = "最终一样，中间随便"

> ⚠️ **易错点**：**ZooKeeper 读不保证线性一致**（读可能打到旧数据节点），只保证"顺序一致性 + session 内因果"——面试说"ZK 读强一致"会被纠。etcd 通过 ReadIndex 保证线性读。

### 知识点七：CAP/BASE/PACELC 选型应用

**一句话记忆**：**选型 = 问业务三件事——能不能接受不一致？能不能接受不可用？延迟多重要？然后对号入座**。

| 业务场景 | 侧重 | 理由 |
|---|---|---|
| 订单/转账（金融） | **CP**（重一致） | 不能接受资金不一致 |
| 商品信息/用户资料 | **AP**（重可用） | 短暂不一致可接受，要可用 |
| 服务注册发现 | **AP** | 不能因少数节点挂了就不可用 |
| 分布式协调/选主 | **CP** | 必须一致，否则脑裂 |
| 社交动态/计数 | **AP + 最终一致** | 延迟敏感，一致性要求低 |
| 跨地域多活 | **PC/EC 或 PA/EC** | 看业务对全局强一致的需求（如 Spanner vs DynamoDB Global Tables） |

**决策流程**：

```
1. 业务能否容忍数据短暂不一致?
   ├── 不能 → CP 系（ZK/etcd/同步复制）→ 再问: 能否容忍低延迟? → PC/EC
   └── 能   → AP 系（Redis/异步复制）→ 再问: 延迟重要吗? → PA/EL 或 PA/EC
2. 强一致需求但又要可用 → 混合架构（如 Redis 缓存 + 落库强一致）或 Saga 最终一致
```

> ⚠️ **易错点**：**不是所有系统都该追求 CP**。缓存、注册中心、消息等场景"最终一致"足够，强一致反而牺牲可用性和性能。按业务容忍度选。

## 4. 最佳实践

- **先定 CAP 侧重再选中间件**：注册中心选 AP（Eureka/Nacos 临时实例），配置中心选 CP（etcd/ZK/Nacos 持久实例）。
- **读多写少 + 允许旧读**：加缓存（AP）+ 异步失效，别为读强一致上 CP。
- **资金链路**：核心写走强一致（数据库行锁/分布式事务），读可走缓存（如余额可延迟显示）。
- **跨地域**：能接受最终一致用异步复制（PA/EL），要强一致用 Spanner 式同步（PC/EC，贵）。
- **面试答 CAP 三步走**：定义三要素 → 说清 P 必选 → 补 PACELC 和一致性谱系。

## 5. 常见踩坑

- 把 CAP 的 C 当 ACID 的一致性（两个 C 含义不同）。
- 答"三个随便选两个"（P 必选，只有 C/A 是选择题）。
- 以为网络正常时也三选二（正常时 C+A 可兼得，只有分区时取舍）。
- 说"ZK 读线性一致"（ZK 只保证顺序一致性 + session 因果）。
- 无脑追求 CP（很多场景 AP + 最终一致更合适）。
- 只背 CAP 不补 PACELC（面试进阶点）。

## 6. 小结

- **CAP**：P 必选，分区时 C/A 二选一 → 实际是 CP 或 AP。
- **BASE**：基本可用 + 软状态 + 最终一致，是 AP 的实践总结（柔性事务的理论根基）。
- **PACELC**：补充"无分区时 L vs C"的取舍 → PA/EL、PA/EC、PC/EL、PC/EC 四组合。
- **一致性谱系**：线性 > 顺序 > 因果 > 最终；强度越高越贵。
- 选型：先问业务"能不能不一致/不可用"，再对号入座 CP/AP。
