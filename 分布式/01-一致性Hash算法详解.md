## 1. 为什么需要 Hash

**一句话记忆**：Hash 把数据/请求**均匀映射**到存储或服务器，实现 O(1) 快速查找，是分布式数据分布的基础。

**Hash 算法应用场景**（分布式集群中最主要两个）：
1. **请求的负载均衡**：把客户端请求按 hash 分配到不同服务器
2. **分布式存储**：把数据按 hash 分配到不同存储节点

> 💡 **记忆锚点**：**Hash 解决"数据/请求该放哪台机器"**。设计好的 Hash 算法能让查询时间复杂度接近 **O(1)**。

### 1.1 常见基础 Hash 算法

以存查数据 `1,3,7,9,34,56` 为例：

| 算法 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **直接寻址法** | 申请大小为最大数(56)的数组，按下标存 | 查询 O(1)，快 | 浪费内存、无法存大数 |
| **除留余数法** | 取数组长度做除数，余数为下标 | 空间紧凑 | 余数冲突无法存 |
| **开放寻址/拉链法** | 冲突时用链表/再寻址解决 | 解决冲突 | 实现复杂 |

> 这些是基础 Hash 思想，分布式场景主要关心**取模分布**和**一致性**。

## 2. 普通 Hash 算法的问题

**取模 Hash**（最简单）：`服务器 = hash(key) % N`（N 为服务器数）。

**致命问题**：**当服务器数量变化（增减），几乎所有请求都会重新映射到不同服务器**。

```
有 3 台服务器 N=3：key 映射到 server = hash(key) % 3
新增到 4 台 N=4：key 映射到 server = hash(key) % 4  ← 模数变了！
→ 绝大多数 key 的映射结果都变了 → 大量数据/请求"搬家"
```

> ⚠️ **易错点**：**取模 Hash 的模数 N 变化会导致雪崩式重映射**。比如 Nginx 后端服务器数量一变，缓存命中的 key 全部失效（因为 hash(key)%N 结果全变），这是普通 Hash 在集群场景的根本缺陷。

---

## 3. 一致性 Hash 算法

### 3.1 核心思路：哈希环

**一致性 Hash** 解决"服务器增减导致大量重映射"的问题。核心是**哈希环**：

```
把 hash 值范围 [0, 2^32-1] 首尾相连，形成一个环（哈希环）
```

```
          0/2^32-1
        ↗         ↖
      ↙             ↘
    服务器A ←←←←←←← 请求X（顺时针找到 A）
     ↘             ↗
       ↘         ↗
        服务器B
```

**映射规则**：
1. 把每台**服务器** hash 后放在环上
2. 把每个**请求/数据 key** hash 后放在环上
3. 请求**顺时针**找到的第一个服务器 = 处理它的服务器

> 💡 **记忆锚点**：**"服务器和请求都落在环上，请求顺时针找最近的服务器"**。环是关键——它让映射不依赖模数，从而服务器增减只影响局部。

### 3.2 服务器下线的影响

**只有被下线服务器及其附近请求受影响，其余不变**：

```
服务器B 下线后：
- 原本映射到 B 的请求，顺时针找到下一个服务器 C
- 其他请求（映射到 A、C 的）不受影响
```

对比普通取模（N 变化全重排），一致性 Hash **只影响局部**，这是它的核心价值。

### 3.3 新增服务器的影响

```
新增服务器 D：
- 只有环上 D 与其"前一个服务器"之间的请求被 D 接管
- 其余请求不受影响
```

**结论**：一致性 Hash 在**服务器增减时，只影响环上局部范围的映射**，避免大量数据搬家，适合缓存分片、负载均衡等场景。

## 4. 现存问题：数据倾斜

**问题**：当**服务器节点很少**时，节点在环上分布可能**不均匀**，导致大量请求/数据集中在少数服务器，某些服务器负载过高。

```
环上只有 2 台服务器 A、B，且 A、B 距离很近：
- 环上大部分区域都由 A"覆盖"（顺时针）→ A 承担绝大多数请求 → 倾斜
```

> ⚠️ **易错点**：**节点越少，哈希环分布越不均匀，越容易数据倾斜**。服务器数量少时，一致性 Hash 反而可能比取模更不均。

---

## 5. 虚拟节点（解决倾斜）

**思路**：给每台服务器创建多个"虚拟节点"（hash 后加编号再 hash），让每台物理服务器在环上有多个分布点，从而分布更均匀。

```
服务器 A 创建虚拟节点 A#1、A#2、A#3
服务器 B 创建虚拟节点 B#1、B#2、B#3
→ 环上从 2 个点变成 6 个点，分布更均匀

请求顺时针找到虚拟节点 → 再映射回实际服务器
（如请求找到 A#2 → 实际由服务器 A 处理）
```

> 💡 **记忆锚点**：**虚拟节点 = "给每台服务器在环上多画几个点"**，让分布更均匀、更平滑。虚拟节点越多，分布越均匀，但管理开销越大。

| 方案 | 解决 | 代价 |
|---|---|---|
| 无虚拟节点 | — | 节点少时倾斜严重 |
| **虚拟节点** | 数据倾斜 | 需维护虚拟节点映射 |

## 6. 与 Redis 哈希槽、Nginx 的对照

### 6.1 Redis 为什么用哈希槽，不用一致性 Hash

**Redis Cluster 用固定 16384 个哈希槽，不是一致性 Hash**。原因：
- **哈希槽**：`槽位 = CRC16(key) % 16384`，槽位均匀分配到节点，**数据分布天然均匀**
- **一致性 Hash**：节点少时可能倾斜（需虚拟节点缓解）
- **哈希槽迁移简单**：节点增减只需**移动槽**（整段槽迁走），不用逐个 key 重哈希

> 🔍 **关键对比**：Redis 选择了**哈希槽**而非一致性 Hash，正是因为哈希槽**分布更均匀 + 迁移更简单**。详见 **04-Redis高可用架构详解**（见知识库）。

### 6.2 Nginx 的一致性哈希

Nginx 用 `hash $key consistent` 指令实现一致性哈希负载均衡（`consistent` 参数开启）：
- 默认 `hash` 是取模；加 `consistent` 用一致性哈希（ketama 算法）
- 适合：**缓存服务**后端（服务器增减时缓存命中不大量失效）
- 与 `ip_hash` 区别：`ip_hash` 固定按 IP 分配（会话保持），一致性哈希按 key 均匀分布且增减影响小

| 技术 | 数据分布方式 | 适用 |
|---|---|---|
| **一致性 Hash** | 哈希环 + 虚拟节点 | 缓存分片、Nginx 负载均衡 |
| **Redis 哈希槽** | 固定 16384 槽 | Redis 集群分片 |
| **取模 Hash** | hash(key) % N | 节点稳定的简单场景 |

## 7. 面试追问 Q&A

### 7.1 一致性 Hash 解决了什么根本问题？

解决**普通取模 Hash 在服务器增减时导致大量数据重映射（雪崩）**的问题。通过哈希环，服务器增减只影响环上局部范围，其余映射不变，适合缓存分片等场景。

### 7.2 一致性 Hash 的缺点？

**数据倾斜**：节点少时分布不均匀，需要**虚拟节点**缓解。另外它不保证数据绝对均匀，只能"相对均匀"。

### 7.3 为什么 Redis 不用一致性 Hash？

Redis Cluster 用固定 **16384 哈希槽**（CRC16 % 16384），因为哈希槽**数据分布更均匀、节点增减只需迁移槽**，比一致性 Hash 更适合 Redis 的分片需求。

### 7.4 虚拟节点是怎么工作的？

给每台物理服务器 hash 后加编号创建多个虚拟节点，让每台在环上有多个分布点，使数据分布更均匀。请求顺时针找到虚拟节点后，再映射回对应物理服务器。
