## 1. 为什么需要分布式 ID

**一句话记忆**：单机数据库用自增主键，**分布式/分库分表后多个节点不能共用自增序列**，需要**全局唯一**的 ID。

**场景**：分库分表后，多个库不能都用自增主键（会重复），需要全局唯一 ID 标识每条数据。

> 💡 **记忆锚点**：**分布式 ID = "跨库/跨服务不重复的唯一标识"**。自增主键只在单库有效，分库分表/分布式必须用分布式 ID 方案。

---

## 2. 雪花算法（Snowflake）

### 2.1 是什么

**雪花算法**由 Twitter 提出，生成 64 位的全局唯一、趋势递增的 ID，常用于分布式系统。

### 2.2 64 位结构

```
 1位     41位          10位        12位
符号位   时间戳        机器ID      序列号
(0)   (毫秒级,41位)  (数据中心+机器)  (同毫秒内自增)

0 | 时间戳(41位,约69年) | 机器ID(10位) | 序列号(12位,4096个/毫秒)
```

| 部分 | 位数 | 说明 |
|---|---|---|
| 符号位 | 1 | 恒为 0 |
| **时间戳** | 41 | 毫秒级，约可用 69 年 |
| **机器 ID** | 10 | 数据中心(5位) + 机器(5位)，最多 1024 台 |
| **序列号** | 12 | 同毫秒内自增，每毫秒 4096 个 |

### 2.3 优缺点

| 优点 | 缺点 |
|---|---|
| **全局唯一** + **趋势递增**（利于索引） | 依赖**机器时钟**（时钟回拨会重复） |
| 性能高（内存计算，无网络 IO） | 机器 ID 需分配管理 |
| 每秒可生成数百万 | 序列号/时间戳耗尽需处理 |

> ⚠️ **易错点**：雪花算法**依赖机器时钟**，**时钟回拨**（NTP 同步）可能导致 ID 重复。需处理回拨（等待/拒发），或结合 **01-服务器时钟同步问题**（见知识库） 保证时钟稳定。

## 3. 分布式 ID 方案对比

| 方案 | 唯一性 | 趋势递增 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|---|
| **UUID** | 唯一 | 否（无序） | 高 | 低 | 非索引主键、简单场景 |
| **雪花算法** | 唯一 | **是** | 高 | 中 | 分库分表主键、订单号 |
| **号段模式**（Leaf） | 唯一 | 是 | 高 | 中 | 需可控/可追溯 |
| **数据库自增** | 单库唯一 | 是 | 低 | 低 | 单库、非分布式 |

> 💡 **记忆锚点**：
> - **UUID** 简单无序（不适合作索引主键）
> - **雪花算法** 全局唯一 + 趋势递增（**分库分表首选**）
> - **号段模式** 从 DB 批量取号段，可控可追溯（Leaf）
> - 生产**分库分表主键首选雪花算法**（或号段模式）

> ⚠️ **易错点**：**UUID 不适合作主键**（无序，导致 B+ 树索引频繁分裂、页分裂，性能差）。要**趋势递增**的 ID 用雪花/号段。

## 4. 什么是幂等性

**一句话记忆**：**幂等 = 同一个请求执行多次，结果和一次一样**（不重复扣款、不重复插入）。

**为什么需要**：网络重试、消息重复消费、用户重复点击提交，都可能导致**重复执行**。

| 场景 | 重复执行的后果 |
|---|---|
| 扣款 | 多扣钱 |
| 下单 | 重复插入订单 |
| 消息消费 | 积分重复发放 |

> 💡 **记忆锚点**：**幂等 = "防重复"**。接口设计要保证"重复调用和调一次结果一致"，是分布式补偿、消息消费的基础（[04-分布式事务详解](04-分布式事务详解.md) 提到 Confirm/Cancel/消费要幂等）。

## 5. 防重复提交方案

### 5.1 全局唯一 ID（去重）

**核心**：每个操作带一个**唯一业务 ID**，服务端用唯一索引/缓存判断是否处理过。

```
客户端提交请求（带 requestId）
   │
   ▼
服务端判断 requestId 是否已处理
   ├── 已处理 → 直接返回上次结果（幂等）
   └── 未处理 → 执行操作 + 记录 requestId
```

```java
// 用 Redis setnx 去重（幂等）
boolean first = redis.setIfAbsent("order:" + requestId, "1");
if (!first) return "已处理";      // 重复请求，直接返回
// 首次 → 执行业务
```

### 5.2 唯一约束（数据库兜底）

表上加**唯一索引**（如业务号），重复插入会报错，天然幂等：

```sql
-- 订单表，order_no 唯一
ALTER TABLE orders ADD UNIQUE KEY uk_order_no (order_no);
-- 重复插入同 order_no → 唯一约束报错，不会重复
```

### 5.3 乐观锁（防并发覆盖）

用 `version` 字段，更新时校验版本：

```sql
-- 乐观锁：版本号一致才更新
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = ? AND version = ?;
-- 版本不符 → 更新 0 行 → 说明已被改过（并发冲突）
```

> ⚠️ **易错点**：**幂等不等于"加锁"**。幂等是"重复执行结果一致"（用唯一 ID/唯一约束/乐观锁），加锁是"同一时刻只有一个能执行"（用 [03-分布式锁原理详解](03-分布式锁原理详解.md)）。两者目的不同，常配合使用。

## 6. 常见踩坑

- **UUID 当分库分表主键** → 无序导致索引分裂，性能差，用雪花/号段。
- **雪花算法时钟回拨重复** → 需处理时钟回拨，保证机器时钟稳定。
- **接口不幂等** → 网络重试/重复点击导致重复扣款、重复下单，必须设计幂等。
- **只用加锁防重复** → 加锁保证互斥，不保证幂等；防重复用唯一 ID/唯一约束。
- **乐观锁忘加 version** → 并发覆盖旧数据。

## 7. 面试追问 Q&A

### 7.1 为什么分库分表不用自增主键？

自增主键是**单库维护**的，分库分表后多个库的自增序列会**重复**。且跨库无法保证全局唯一，需要分布式 ID（雪花/号段）。

### 7.2 雪花算法为什么趋势递增？

ID 高位是**时间戳**，所以整体随生成时间递增（趋势递增）。利于数据库索引（B+ 树顺序插入，避免页分裂），优于无序的 UUID。

### 7.3 什么是幂等？怎么实现？

幂等 = 同一个请求执行多次结果一致。实现：**全局唯一 ID 去重**（Redis setnx / 数据库唯一索引）+ **乐观锁**（version）。分布式补偿和消息消费必须幂等。

### 7.4 雪花算法时钟回拨怎么办？

时钟回拨会导致 ID 重复。处理：**短回拨等待**（等时钟追上）、**长回拨拒绝生成/报错**，或给序列号/机器 ID 加偏移。保证机器时钟稳定（NTP 同步）也是关键。
