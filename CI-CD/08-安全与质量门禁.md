## 8.1 DevSecOps 全景：安全左移与门禁体系

### 8.1.1 为什么安全扫描不能等到发布前（安全左移原则）

**传统模式的问题**：安全团队在发布前做一次渗透测试 → 发现高危漏洞 → 开发团队紧急修复 → 发版延期 3 天。这种"安全右移"模式有三个致命问题：

1. **修复成本指数级增长**：同一个漏洞，在 PR 阶段修复成本 = 1（开发者自己改 10 分钟），在发布前修复成本 = 10（需要拉安全+开发+PM 开会、走紧急变更流程），在生产环境修复成本 = 100（需要回滚 + 数据修复 + 通告客户）
2. **Pipeline 卡脖子**：所有安全检查堆在发布前，发布日变成"安全扫雷日"，团队压力大、容易放过
3. **反馈延迟**：开发提交代码到收到安全反馈间隔几天甚至几周，开发者早就忘了这块代码的逻辑，修复效率低

**安全左移的核心思想**：把安全检查**尽可能早地**放到 Pipeline 前端，PR 阶段就跑 SAST + Secret Detection，让开发者在写代码的当天就收到安全反馈。

```
传统模式（安全右移）：
  PR ──→ Merge ──→ Build ──→ Deploy ──→ [安全团队手工渗透测试] ──→ 发现高危 ──→ 紧急修复
                                                                         ↑ 成本 100x

DevSecOps 模式（安全左移）：
  PR ──→ [SAST + Secret + SCA 自动扫描] ──→ 高危阻断 ──→ 开发者当场修 ──→ Merge
         ↑ 成本 1x                                    ↑ 只放行低危
```

**左移的收益**（NIST 研究数据）：

| 发现漏洞的阶段 | 平均修复成本 | 对比 |
| -------------- | ------------ | ---- |
| 代码编写 / PR 阶段 | $80 | 1x |
| 测试阶段 | $1,200 | 15x |
| 生产环境 | $30,000 | 375x |

> 小团队不需要安全团队，但**必须**把安全扫描自动化到 Pipeline 里。一次 SAST 扫描 3 分钟，能拦住 90% 的代码层安全漏洞（SQL 注入、硬编码密码、XSS），ROI 极高。

### 8.1.2 四类安全扫描定位（SAST / SCA / DAST / Secret Detection）

**表 8-1：四类安全扫描对比**

| 维度 | SAST（静态安全测试） | SCA（软件组成分析） | Secret Detection（密钥泄露） | DAST（动态安全测试） |
| ---- | ---- | ---- | ---- | ---- |
| **扫什么** | 源代码本身的安全缺陷 | 第三方依赖库的已知漏洞 | 代码里硬编码的密钥/Token | 运行中应用的漏洞 |
| **怎么扫** | 语法分析 + 数据流追踪 + 规则匹配 | 解析锁文件 → 匹配 NVD/CVE 数据库 | 正则匹配 + 熵检测 | 模拟攻击者向应用发恶意请求 |
| **不需要运行** | ✅ 只需要源码 | ✅ 只需要锁文件 | ✅ 只需要源码 | ❌ 需要应用跑起来 |
| **能发现什么** | SQL 注入、XSS、硬编码密码、不安全的反序列化 | log4j 漏洞、Django CVE、requests 库漏洞 | AWS Key、数据库密码、API Token | 运行时 XSS、SQL 注入、CSRF、目录遍历 |
| **Pipeline 位置** | PR 阶段（Test 之后） | PR 阶段（与 SAST 并行） | PR 阶段（最前面，秒级） | stage 环境（部署后） |
| **执行速度** | 中（1~5 分钟） | 快（30 秒~2 分钟） | 极快（< 30 秒） | 慢（5~30 分钟） |
| **误报率** | 中高（需要调规则） | 低（CVE 精确匹配） | 中（需要白名单） | 低（实际攻击验证） |
| **典型工具** | SonarQube / CodeQL / Bandit / Semgrep | Trivy fs / GitLab DS / Snyk / Dependabot | Gitleaks / TruffleHog / GitLab SD | OWASP ZAP / Burp Suite |
| **06 章已覆盖** | ❌ | ✅ 镜像层（Trivy image） | ❌ | ❌ |
| **08 章聚焦** | ✅ 代码层 | ✅ 代码层（锁文件） | ✅ | ✅（补充） |

**关键结论**：四类扫描**互不替代**。SAST 找代码逻辑漏洞但不知道依赖库有没有漏洞；SCA 找依赖库漏洞但不知道你的代码逻辑有没有缺陷；Secret Detection 专找密钥泄露；DAST 验证运行时漏洞。一个成熟的 Pipeline 应该**四类都配**，但按成本和优先级分阶段引入。

**小团队引入顺序建议**：
```
第一步（必须有）：Secret Detection（< 30 秒，防止密钥泄露，零成本）
第二步（必须有）：SAST 轻量版（Bandit/Semgrep，< 2 分钟，拦截 80% 代码漏洞）
第三步（推荐有）：SCA 依赖扫描（GitLab 原生或 Trivy fs，< 2 分钟，防 log4j 类漏洞）
第四步（有空了）：SAST 完整版（SonarQube，含质量门 + 覆盖率 + 重复率）
第五步（进阶）：DAST（OWASP ZAP，stage 环境跑，5~30 分钟）
```

### 8.1.3 三类门禁（Quality Gate / Security Gate / Deployment Gate）

> 对应 [01 章 1.3.3 三个门禁概念](./01-认知地基.md)。

**表 8-2：三类门禁对比**

| 门禁类型 | 管什么 | 谁定标准 | 阻断方式 | 典型条件 |
| -------- | ---- | -------- | -------- | -------- |
| **Quality Gate（质量门）** | 代码质量 | 开发团队 | CI Job 失败 → 不允许合并 | 覆盖率 ≥ 80%、重复率 < 3%、Blocker issues = 0 |
| **Security Gate（安全门）** | 安全漏洞 | 安全/SRE | CI Job 失败 → 不允许合并 | CRITICAL 漏洞 = 0、密钥泄露 = 0、CVSS ≥ 7 依赖 = 0 |
| **Deployment Gate（部署门）** | 发布审批 | PM/SRE | 人工确认（`when: manual`） | stage UAT 通过 + 人工确认才部署 prod |

**关键**：Quality Gate 和 Security Gate **不是同一个东西**。一个项目可能有 100% 覆盖率（Quality Gate 通过）但有一个 SQL 注入漏洞（Security Gate 失败）。两个门禁独立判断，任何一个失败都不允许合并。

> **和 P1.3 的关系**：P1.3 中 feature 分支独立合入每个环境（不做逐级 merge），门禁按环境递进——dev/test 段自动跑 Quality + Security Gate；stage 段加 Deployment Gate（人工确认）；main 段只验证不发布。

## 8.2 SAST 静态应用安全测试

> S9 专题已覆盖 SonarQube / CodeQL 的 GitHub Actions 集成配置（→ [S9 4.1 / 4.2](./补充专题/S9-质量安全扫描集成.md)），本节聚焦 **GitLab CI + Python** 的落地配置和质量门设计。

### 8.2.1 SonarQube 质量门体系（规则集 + 质量门条件 + 阻断策略）

**SonarQube 的三层体系**：

```
规则集（Rules）  →  你项目选哪些规则开（Quality Profile）
      ↓
质量门（Quality Gate）  →  扫描结果达到什么条件才放行
      ↓
项目配置（sonar-project.properties）  →  扫哪些目录、排除哪些、覆盖率报告在哪
```

**sonar-project.properties（Python 项目示例）**：

```properties
# === 项目标识 ===
sonar.projectKey=myorg:myapp
sonar.projectName=My FastAPI App
sonar.projectVersion=1.0

# === 扫描范围 ===
sonar.sources=app
sonar.tests=tests
sonar.exclusions=**/migrations/**,**/__pycache__/**,**/.venv/**

# === Python 覆盖率 ===
sonar.python.coverage.reportPaths=coverage.xml
sonar.python.version=3.12

# === 质量门（在 SonarQube UI 配置，不在 properties 里写） ===
# 以下条件在 SonarQube Web UI → Quality Gates 里配：
# - Coverage < 80% → FAIL
# - Duplicated lines > 3% → FAIL
# - Blocker issues > 0 → FAIL
# - Critical issues > 0 → FAIL
# - Security Rating < A → FAIL（A = 0 高危）
# - Technical Debt Ratio > 5% → FAIL
```

**质量门条件设计建议**（小团队起步版）：

| 条件 | 推荐值 | 为什么 | 严格度 |
| ---- | ------ | ------ | ------ |
| Coverage on New Code | < 80% → FAIL | 新代码必须有测试，老代码允许逐步还债 | ⭐⭐⭐⭐⭐ 必配 |
| Blocker Issues | > 0 → FAIL | Blocker = 最严重的安全/逻辑缺陷 | ⭐⭐⭐⭐⭐ 必配 |
| Critical Issues | > 0 → FAIL | Critical = 高危漏洞 | ⭐⭐⭐⭐⭐ 必配 |
| Security Rating | < A → FAIL | A = 0 高危，B = ≤ 5 高危 | ⭐⭐⭐⭐⭐ 必配 |
| Duplicated Lines on New Code | > 3% → FAIL | 新代码重复率过高 = 复制粘贴 | ⭐⭐⭐⭐ 推荐 |
| Technical Debt Ratio on New Code | > 5% → FAIL | 新代码技术债比率 | ⭐⭐⭐ 有空配 |
| Major Issues | > 0 → WARN | Major 不阻断，只告警 | ⭐⭐ 可选 |

> **关键**：所有条件都加 "on New Code"（只检查新增代码），不要加 "on Overall Code"。否则老代码的历史债会导致质量门永远 FAIL，团队会直接关掉质量门。**新代码严格、老代码宽松**是质量门能落地的核心原则。

### 8.2.2 Python 专用：Bandit + Semgrep 轻量级 SAST

**为什么不只用 SonarQube**：SonarQube 需要自建服务（JVM + PostgreSQL），小团队可能暂时没有。Bandit 和 Semgrep 是**零基础设施**的轻量级 SAST，直接在 CI 里跑，不需要额外服务。

**Bandit（Python 专用 SAST，AST 级别扫描）**：

```ini
# .bandit（项目根目录，配置 Bandit 规则）
[bandit]
# 排除测试目录和迁移目录
exclude = tests,migrations,.venv

# 跳过的规则（B101 = assert 语句，测试代码里正常用）
skips = B101

# 阈值：只报 MEDIUM 以上（LOW 不报，减少噪音）
level = MEDIUM

# 聚焦的高危规则（不可跳过）：
# B602: subprocess shell=True → 命令注入
# B608: SQL 语句拼接 → SQL 注入
# B105: 硬编码密码
# B301: pickle.loads → 反序列化攻击
# B311: random → 安全场景应该用 secrets
```

**Semgrep（多语言 SAST，规则可自定义，社区规则库丰富）**：

```yaml
# .semgrep.yml（项目根目录）
rules:
  # === Python 安全规则 ===
  - id: python-sql-injection-fstring
    pattern: |
      cursor.execute(f"SELECT ... FROM ... WHERE id = {user_input}")
    message: "SQL 注入风险：f-string 拼接 SQL 语句，应使用参数化查询"
    severity: ERROR
    languages: [python]

  - id: python-hardcoded-secret
    pattern-regex: '(password|secret|api_key|token)\s*=\s*["\'][^"\']{8,}["\']'
    message: "硬编码密钥风险：不要在代码里写死密码/Token，应从环境变量读"
    severity: ERROR
    languages: [python]

  - id: fastapi-debug-mode
    pattern: |
      app = FastAPI(..., debug=True)
    message: "生产环境不要开 debug=True，会暴露堆栈信息"
    severity: WARNING
    languages: [python]

  # === 自定义业务规则（示例）===
  - id: no-bare-except
    pattern: |
      except:
        ...
    message: "不要用裸 except，会吞掉所有异常包括 KeyboardInterrupt"
    severity: WARNING
    languages: [python]
```

**Bandit vs Semgrep vs SonarQube 选型**：

| 维度 | Bandit | Semgrep | SonarQube |
| ---- | ------ | ------- | --------- |
| 安装复杂度 | `pip install bandit` | `pip install semgrep` | 自建服务（JVM + PG） |
| 执行速度 | < 30 秒 | 30~60 秒 | 1~5 分钟 |
| 规则数量 | ~80（Python 专用） | ~2000+（社区规则库） | ~5000+（全语言） |
| 自定义规则 | ❌ 不支持 | ✅ YAML 写规则，极灵活 | ✅ 但需要 Java 知识 |
| 质量门（覆盖率/重复率） | ❌ | ❌ | ✅ 完整质量门体系 |
| 适合小团队 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐（有服务运维成本） |
| 推荐 | **起步必配** | **和 Bandit 互补** | **服务 > 5 个再上** |

> **小团队最佳组合**：Bandit（Python 专用规则，秒级）+ Semgrep（自定义业务规则 + 社区规则）。两个加起来 < 1 分钟，覆盖 80% 的 SAST 场景。SonarQube 等服务 > 5 个且需要统一质量看板时再上。

### 8.2.3 GitLab CI SAST 完整配置（GitLab 原生 + SonarQube + Bandit）

**GitLab CI SAST 有三种方式，按团队情况选**：

**方式一：GitLab 原生 SAST（Ultimate 版才全功能，免费版功能受限）**：

```yaml
# .gitlab-ci.yml（GitLab 原生 SAST，零配置）
include:
  - template: Security/SAST.gitlab-ci.yml

sast:
  stage: security_scan
  variables:
    SAST_EXCLUDED_PATHS: "tests,migrations,.venv"
    # 扫描器选 bandit（Python）
    SAST_DEFAULT_ANALYZERS: "bandit,semgrep"
  artifacts:
    reports:
      sast: gl-sast-report.json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

> GitLab 免费版可以跑 SAST，但**安全报告面板**（Security Dashboard）需要 Ultimate 版。免费版看 JSON 报告也够用。

**方式二：手动 Bandit + Semgrep（免费版推荐，完全可控）**：

```yaml
# .gitlab-ci.yml（手动集成 Bandit + Semgrep）
sast:bandit:
  stage: security_scan
  image: python:3.12-slim
  before_script:
    - pip install bandit[toml] --quiet
  script:
    - bandit -r app/ -c .bandit -f json -o bandit-report.json || true
    # 解析报告，有 MEDIUM 以上问题就失败
    - python -c "
import json, sys
report = json.load(open('bandit-report.json'))
high_medium = [r for r in report.get('results', []) if r['issue_severity'] in ('HIGH', 'MEDIUM')]
if high_medium:
    print(f'Bandit 发现 {len(high_medium)} 个 HIGH/MEDIUM 问题：')
    for r in high_medium:
        print(f\"  [{r['issue_severity']}] {r['filename']}:{r['line_number']} - {r['issue_text']}\")
    sys.exit(1)
print('Bandit 扫描通过，无 HIGH/MEDIUM 问题')
"
  artifacts:
    when: always
    paths:
      - bandit-report.json
    reports:
      codequality: bandit-codequality.json  # MR 里展示代码质量评论
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

sast:semgrep:
  stage: security_scan
  image: returntocorp/semgrep:latest
  script:
    - semgrep --config .semgrep.yml --config p/python --config p/owasp-top-ten --json -o semgrep-report.json app/
    # 有 ERROR 级别问题就失败
    - python -c "
import json, sys
report = json.load(open('semgrep-report.json'))
errors = [r for r in report.get('results', []) if r.get('extra', {}).get('severity') == 'ERROR']

    sys.exit(1)

"
  artifacts:
    when: always
    paths:
      - semgrep-report.json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
```

**方式三：SonarQube 集成（需要自建 SonarQube 服务）**：

```yaml

    name: sonarsource/sonar-scanner-cli:latest
```

> - 团队 5~15 人 + 有 GitLab Ultimate → **方式一 + 方式二**（GitLab 原生 + 自定义 Semgrep 规则）

## 8.3 SCA 软件组成分析（依赖漏洞扫描）

> **和 06 章的区分**：06 章用 Trivy 扫**镜像层**依赖（系统包 + Python 包打进镜像后的状态）；08 章扫**代码层**依赖（直接读 `requirements.txt` / `pyproject.toml` 锁文件，在 Build 之前就能发现问题）。两者互补：08 章 Build 前扫代码层 → 06 章 Build 后扫镜像层。

### 8.3.1 SCA 扫描原理与工具选型

**SCA 扫描四步流程**：

```
1. 解析锁文件           → requirements.txt / pyproject.toml / pom.xml / package-lock.json
    ↓
2. 提取依赖清单         → requests==2.31.0, django==4.2.0, ...
    ↓
3. 匹配 CVE 数据库       → NVD (National Vulnerability Database) + 厂商 advisory
    ↓
4. 评级 + 报告           → CVSS 评分（0~10）→ CRITICAL/HIGH/MEDIUM/LOW
```

**表 8-3：SCA 工具选型对比**

| 工具 | 扫描方式 | 优势 | 劣势 | 推荐场景 |
| ---- | -------- | ---- | ---- | -------- |
| **GitLab Dependency Scanning** | 锁文件解析 | GitLab 原生集成、MR 里直接展示、零配置 | Ultimate 版全功能 | GitLab Ultimate 团队 |
| **Trivy fs** | 文件系统扫描 | 免费、速度快、覆盖 OS + 语言包 | 无 MR 评论集成 | **小团队首选** |
| **Snyk** | 锁文件 + 镜像 | 漏洞情报准、自动修复 PR | 收费版不便宜 | 预算充足的团队 |
| **OWASP Dependency-Check** | 锁文件 | 开源免费、可自建 | NVD 下载慢、误报多 | 合规要求自建的场景 |
| **pip-audit** | Python 专属 | 官方维护、极快、只扫 Python | 只支持 Python | **Python 小团队必备** |
| **Renovate / Dependabot** | 锁文件 + 自动升级 PR | 自动发升级 PR、减少人工 | 不做阻断（只提醒） | 所有团队都应配 |

**小团队推荐组合**：`pip-audit`（Python 专属，秒级扫描）+ `Trivy fs`（通用兜底）+ `Renovate`（自动升级 PR）。三个全免费，覆盖 SCA 全场景。

### 8.3.2 依赖升级策略（Renovate / Dependabot 自动 PR + 人工 Review）

**为什么要自动升级 PR**：依赖漏洞不是一次性扫描就能解决的，需要持续跟踪上游安全更新。靠人工每周检查依赖更新不现实，用 Renovate / Dependabot 自动发 PR 是 2026 年的标准做法。

**Renovate 配置（GitLab CI 集成，推荐）**：

```json
// renovate.json（项目根目录）
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended"],
  "schedule": ["before 6am on Monday"],
  "timezone": "Asia/Shanghai",

  // 分组策略：安全补丁自动合并，minor/major 人工 review
  "packageRules": [
    {
      "description": "安全补丁（patch）自动合并",
      "matchUpdateTypes": ["patch"],
      "addLabels": ["auto-merge"],
      "automerge": true,
      "automergeType": "pr"
    },
    {
      "description": "minor 版本需要人工 review",
      "matchUpdateTypes": ["minor"],
      "addLabels": ["needs-review"]
    },
    {
      "description": "major 版本需要人工 review + 手动测试",
      "matchUpdateTypes": ["major"],
      "addLabels": ["major-upgrade", "needs-review", "needs-testing"]
    },
    {
      "description": "Django/FastAPI 等 major 升级单独分组",
      "matchPackagePatterns": ["^(django|fastapi|uvicorn)$"],
      "groupName": "Python Web Framework",
      "addLabels": ["framework-upgrade"]
    }
  ],

  // 限制并发 PR 数量（避免一次发 20 个 PR 淹没 MR 列表）
  "prConcurrentLimit": 5,
  "prHourlyLimit": 2
}
```

> Renovate 可以跑在 GitLab CI 里（`renovate-bot/renovate-runner`），也可以用 Mend 提供的免费 GitHub App。GitLab 自身也有 [Dependency Proxy](https://docs.gitlab.com/ee/user/packages/dependency_proxy/) 但功能不同。

**自动合并的安全边界**：
- ✅ patch 版本（1.2.3 → 1.2.4）：API 不变，安全补丁，自动合并 + CI 验证
- ⚠️ minor 版本（1.2.3 → 1.3.0）：可能有新 API，人工 review 1 分钟
- ❌ major 版本（1.2.3 → 2.0.0）：大概率 Breaking Change，人工 review + 手动测试

## 8.4 密钥泄露扫描（Secret Detection）

> **为什么单独成节**：密钥泄露是**最常见、最致命、最容易被忽略**的安全事故。一个 AWS Access Key 泄露到 Git 仓库 → 30 分钟内被自动化脚本扫到 → 挖矿机器人启动 → 云账单 $50,000。Secret Detection 扫描 < 30 秒，应该是 Pipeline 里**第一个跑**的安全检查。

### 8.4.1 Gitleaks 原理（正则 + 熵检测）与配置

**Gitleaks 的两种检测方式**：

1. **正则匹配**：预置 100+ 规则（AWS Key、GitHub Token、私钥、数据库连接串等），按 pattern 匹配
2. **熵检测（Entropy）**：计算字符串的 Shannon 熵，高熵字符串（如 `AKIAIOSFODNN7EXAMPLE`）疑似密钥。弥补正则规则覆盖不到的私有 API Key

**.gitleaks.toml（自定义规则 + 白名单）**：

```toml
# .gitleaks.toml（项目根目录）

title = "My App Secret Detection Rules"

# === 扩展规则（Gitleaks 预置规则之外的私有规则）===
[[rules]]
id = "custom-db-connection-string"
description = "数据库连接串泄露"
regex = '''postgres(ql)?://[^\s]+:[^\s]+@[^\s]+:\d+/\w+'''
tags = ["database", "high"]

[[rules]]
id = "custom-fastapi-secret-key"
description = "FastAPI SECRET_KEY 硬编码"
regex = '''SECRET_KEY\s*=\s*["\'][a-zA-Z0-9]{32,}["\']'''
tags = ["fastapi", "high"]

[[rules]]
id = "custom-jwt-secret"
description = "JWT Secret 硬编码"
regex = '''JWT_SECRET\s*=\s*["\'][^"\']{16,}["\']'''
tags = ["jwt", "high"]

# === 白名单（允许的路径/模式）===
[allowlist]
description = "Allowed patterns and paths"

# 允许的文件路径（测试文件、示例文件）
paths = [
  '''(^|/)tests/.*\.py$''',
  '''(^|/)test_.*\.py$''',
  '''(^|/)\.env\.example$''',
  '''(^|/)docs/examples/.*''',
]

# 允许的模式（测试用假密钥、占位符）
regexes = [
  # 测试用的假密钥
  '''test_key_[a-z0-9]{20}''',
  '''example_password_\d+''',
  # 占位符
  '''<your-api-key-here>''',
  '''YOUR_SECRET_KEY_HERE''',
  # .env.example 里的示例值
  '''changeme''',
  '''your-password-here''',
]

# 允许的 commit（历史遗留的误报，不想改历史）
commits = [
  # "abc1234",  # 评估过，是测试数据
]
```

**方式二：手动 Gitleaks（需要更灵活的自定义规则时）**：

```yaml
# .gitlab-ci.yml（手动 Gitleaks 集成）
secret:gitleaks:
  stage: security_scan
  image:
    name: zricethezav/gitleaks:latest
    entrypoint: [""]
  script:
    # 扫描当前 MR 的变更（只扫增量，不扫全量历史，速度快）
    - |
      if [ -n "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME" ]; then
        # MR 模式：只扫 MR 里的新 commit
        gitleaks detect \
          --source . \
          --config .gitleaks.toml \
          --report-format json \
          --report-path gitleaks-report.json \
          --log-opts "origin/${CI_MERGE_REQUEST_TARGET_BRANCH_NAME}..HEAD" \
          --exit-code 1
      else
        # 非 MR 模式（push 到 main）：扫最近 5 个 commit
        gitleaks detect \
          --source . \
          --config .gitleaks.toml \
          --report-format json \
          --report-path gitleaks-report.json \
          --log-opts "HEAD~5..HEAD" \
          --exit-code 1
      fi
  artifacts:
    when: always
    paths:
      - gitleaks-report.json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
  allow_failure: false  # 密钥泄露 = 硬阻断，不允许合并
```

### 8.4.3 误报处理与白名单管理

**常见的误报场景**：

| 误报类型 | 例子 | 处理方式 |
| -------- | ---- | -------- |
| 测试用假密钥 | `test_api_key = "test_key_abc1234567890"` | `.gitleaks.toml` 的 `regexes` 白名单 |
| .env.example 占位符 | `DATABASE_URL=postgresql://user:pass@localhost:5432/db` | `.gitleaks.toml` 的 `paths` 白名单 |
| 文档里的示例 | `docs/examples/config.md` 里的示例配置 | `.gitleaks.toml` 的 `paths` 白名单 |
| 第三方库里的字符串 | `.venv/` 里依赖包的代码 | `.gitleaks.toml` 的 `paths` 白名单 + CI 变量 `SECRET_DETECTION_EXCLUDED_PATHS` |
| 历史遗留误报 | 3 年前的 commit 里的测试数据 | `commits` 白名单（不想改 Git 历史） |

**白名单管理铁律**：
1. **每条白名单必须有注释说明为什么允许**：3 个月后没人记得为什么加的
2. **定期 review 白名单**：每季度过一次，过期的一律删
3. **不要为了消除误报而关闭整条规则**：宁可加精确的白名单，不要关规则

> **密钥泄露的应急响应流程**（如果真的泄露了密钥到 Git 仓库）：
> 1. **不要**试图用 `git rebase` 删历史（别人可能已经 clone 了）
> 2. **立刻**到云平台/服务方轮换（Revoke + 重新生成）泄露的密钥——这是唯一正确的操作
> 3. 轮换后清理 Git 历史里的密钥（用 `git filter-repo` 或 BFG Repo-Cleaner）
> 4. 通知团队所有人 force pull
> 5. 复盘：为什么 Secret Detection 没拦住？是规则缺失还是白名单太宽？

## 8.5 质量门禁设计与阻断策略

### 8.5.1 质量门条件设计（覆盖率 / 重复率 / 代码异味 / 技术债）

> 完整的 SonarQube 质量门配置参见 [8.2.1](#821-sonarqube-质量门体系规则集--质量门条件--阻断策略)，本节聚焦**条件设计原则**和**小团队分阶段方案**。

**质量门条件分阶段引入建议**：

| 阶段 | 条件 | 目的 | 何时引入 |
| ---- | ---- | ---- | -------- |
| **起步期** | Blocker Issues = 0 | 拦截最严重的安全/逻辑缺陷 | 项目第一天 |
| **起步期** | Secret Detection = 0 | 拦截密钥泄露 | 项目第一天 |
| **成长期** | Coverage on New Code ≥ 70% | 新代码有基本测试覆盖 | 项目 1~3 个月 |
| **成熟期** | Coverage on New Code ≥ 80% | 提高覆盖要求 | 项目 3~6 个月 |
| **成熟期** | Duplicated Lines on New Code < 3% | 控制复制粘贴 | 项目 3~6 个月 |
| **成熟期** | Critical Issues = 0 | 拦截高危漏洞 | 有 SonarQube 后 |
| **优化期** | Technical Debt Ratio < 5% | 控制技术债 | 项目 6~12 个月 |
| **优化期** | Security Rating = A | 安全评级最高 | 有 SonarQube 后 |

> **不要一开始就配 8 个条件**。起步期只配 Blocker + Secret（2 条），团队适应后再逐步加。一开始就配满 8 条 → 团队因为历史债永远过不了 → 直接关掉质量门 → 比不配还糟。

**覆盖率门禁的两个陷阱**：

1. **只看数字不看质量**：覆盖率 80% 但全是 `assert True` 的无用测试。解决：加 Mutation Testing（`mutmut` for Python）或 Code Review 时抽查测试质量
2. **Overall Code vs New Code**：只对 New Code 设覆盖率要求（新写的代码必须有测试），不要对 Overall Code 设要求（老代码的历史债慢慢还）。SonarQube 的 "on New Code" 选项就是这个目的

### 8.5.2 阻断策略矩阵（硬阻断 / 软告警 / 不阻断）

**表 8-4：阻断策略矩阵**

| 扫描类型 | CRITICAL | HIGH | MEDIUM | LOW | INFO |
| -------- | -------- | ---- | ------ | --- | ---- |
| **Secret Detection** | 🔴 硬阻断 | 🔴 硬阻断 | 🔴 硬阻断 | 🟡 软告警 | ⚪ 不阻断 |
| **SAST（Bandit/Semgrep）** | 🔴 硬阻断 | 🔴 硬阻断 | 🟡 软告警 | ⚪ 不阻断 | ⚪ 不阻断 |
| **SCA（pip-audit/Trivy fs）** | 🔴 硬阻断 | 🔴 硬阻断 | 🟡 软告警 | ⚪ 不阻断 | ⚪ 不阻断 |
| **质量门（SonarQube）** | — | Blocker/Critical = 0 → 硬阻断 | Major → 软告警 | Minor → 不阻断 | Info → 不阻断 |
| **DAST（OWASP ZAP）** | 🔴 硬阻断 | 🟡 软告警 | 🟡 软告警 | ⚪ 不阻断 | ⚪ 不阻断 |

**阻断策略的 GitLab CI 实现**：

```yaml
# 硬阻断：CI Job 失败 → MR 不允许合并
sast:bandit:
  allow_failure: false  # 默认就是 false，显式写出更清晰

# 软告警：CI Job 失败但 MR 仍可合并（会显示黄色警告）
sast:bandit:low-only:
  allow_failure: true   # 只有 LOW 问题的 Job 允许失败

# Secret Detection 永远硬阻断（即使 LOW 也不放过）
secret:gitleaks:
  allow_failure: false
```

**GitLab MR 合并策略配置**（Settings → Merge Requests）：
- ✅ 勾选 "Pipelines must succeed"（CI 全绿才能合并）
- ✅ 勾选 "All threads must be resolved"（所有讨论要解决）
- ❌ 不勾选 "Allow merge trains"（小团队不需要）

### 8.5.3 白名单与例外管理

**表 8-5：各类白名单文件管理对照**

| 白名单文件 | 对应工具 | 用途 | 管理原则 |
| ---------- | -------- | ---- | -------- |
| `.trivyignore` | Trivy（06 章） | 忽略特定 CVE | 每条带 CVE + 理由 + 过期日期 |
| `.gitleaks.toml` [allowlist] | Gitleaks | 忽略特定路径/模式/commit | 每条带注释说明为什么允许 |
| `sonar.exclusions` | SonarQube | 排除不扫的目录 | 只排除 migrations/.venv/node_modules |
| `.bandit` skips | Bandit | 跳过特定规则 | 只跳 B101（assert），不跳安全规则 |
| `.semgrep.yml` | Semgrep | 不适用（直接不写规则） | 在规则层面控制，不做文件级排除 |
| `pip-audit --ignore-vuln` | pip-audit | 忽略特定 CVE | 同 .trivyignore，带理由 + 过期 |

**白名单铁律（适用于所有工具）**：
1. **每条忽略必须有 CVE 编号 + 评估理由 + 过期日期**
2. **每季度 review 一次**，过期的删，上游已修的删
3. **忽略列表不能超过 10 条**，超过 10 条说明你的依赖/代码有系统性问题
4. **不要忽略 Secret Detection 的任何告警**，密钥泄露没有"可接受的风险"

**.trivyignore 示例（带过期管理）**：

```text
# .trivyignore
# 格式：CVE-XXXX-XXXXX  # [评估人] [评估日期] [过期日期] 理由

CVE-2023-12345  # [张三] [2026-06-01] [2026-09-01] 仅影响未使用的 XML 解析模块，已确认不受影响
CVE-2024-67890  # [李四] [2026-07-15] [2026-08-15] 上游已修但 ubuntu:24.04 镜像未更新，等 8 月补丁
```

## 8.6 P1.3 四段环境下的安全扫描落地

> 本节是 08 章的核心实战部分：把前面所有安全扫描工具，按你的 **[P1.3 环境晋升触发机制](./我的实践记录.md)**（dev/test/stage/main 四段）落地到 GitLab CI。

### 8.6.1 feature 分支贯穿所有环境的扫描策略

> **P1.3 核心流程回顾**（→ [我的实践记录 P1.3](./我的实践记录.md)）：feature 从 main 切出，**独立合入每个环境**，不做逐级 merge：
>
> ```
> main ──────────────────────────────────────────────────────
>   │                                                         ↑
>   ├─ feature-A ──→ merge dev ──→ merge test ──→ merge stage ──→ merge main（批次到才合）
>   │     ↑              │             │              │
>   │     └──────────────┘             │              │
>   │     (bug 修复后重新走 dev)        │              │
>   │     └────────────────────────────┘              │
>   │     (bug 修复后重新走 dev → test)                │
>   │     └───────────────────────────────────────────┘
>   │     (bug 修复后重新走 dev → test → stage)
>   │
>   ├─ feature-B ──→ merge dev ──→ merge test ──→ ... (不同批次，暂不 merge main)
> ```
>
> **关键规则**：
> 1. **feature 贯穿所有环境**：dev/test/stage/main 都是 feature 直接 merge 进去，**不允许 dev→test、test→stage 逐级 merge**
> 2. **发现问题回 feature 修**：任何环境发现问题，都在 feature 分支修复，然后重新从 dev 开始走验证
> 3. **批次到了才 merge main**：不是该批次的 feature 不 merge main，main 始终保持"已验证通过的批次合集"
> 4. **main 只验证不发布**：merge main 触发 CI 验证但不部署，打 Tag 才发布（两段式机制）

**表 8-6：P1.3 环境晋升 × 安全扫描矩阵**

| 扫描类型 | feature 分支（MR 阶段） | dev（feature→merge dev） | test（feature→merge test） | stage（feature→merge stage） | main（feature→merge main） | Tag（prod 发布） |
| -------- | --------------------- | ---------------------- | ------------------------- | --------------------------- | ------------------------- | --------------- |
| **Secret Detection** | ✅ 每次 push | ✅ | ✅ | ✅ | ✅ | ✅ |
| **SAST（Bandit+Semgrep）** | ✅ 每次 push | ✅ | ✅ | ✅ | ✅ | ✅ |
| **SCA（pip-audit+Trivy fs）** | ⚠️ 只扫 lock 文件变更 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Trivy 镜像扫描**（06 章） | ❌（不构建镜像） | ❌（不构建镜像） | ✅ Build 后 | ✅ Build 后 | ✅ Build 后 | ✅ |
| **SonarQube 质量门** | ⚠️ 轻量（只扫增量） | ✅ 完整 | ✅ 完整 | ✅ 完整 | ✅ 完整 | ❌（已扫过） |
| **DAST（OWASP ZAP）** | ❌ | ❌ | ❌ | ✅ 部署后跑 | ❌ | ❌ |
| **SBOM + Cosign**（06 章） | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| **阻断策略** | 高危阻断 | 高危阻断 | 高危阻断 | 高危阻断 + 人工 UAT | 高危阻断（不部署） | 高危阻断 |

**设计原则**：
1. **安全扫描越早越好**：feature MR 阶段就跑 Secret + SAST（< 1 分钟），问题在源头发现，不进 dev
2. **dev 聚焦联调**：dev 段跑完整 SAST + SCA + SonarQube，确保联调时代码质量和依赖安全
3. **test 起构建镜像**：test 段开始 Build 镜像 + Trivy 镜像扫描，验证镜像层安全（06 章衔接）
4. **重的扫描往后放**：DAST 需要应用跑起来，只在 stage 部署后跑
5. **main 只验证不发布**：main 段跑全套扫描确认没问题，但**不部署到 prod**（P1.3 两段式机制）
6. **Tag 发布时复用 main 的扫描结果**：不重复扫，只追加 Trivy 镜像扫描 + Cosign 签名（06 章已覆盖）

### 8.6.2 GitLab CI 完整安全流水线（含 P1.3 四段 rules）

```yaml
# .gitlab-ci.yml（08 章完整安全流水线，P1.3 四段落地版）
# 06 章的镜像扫描/签名/推送 Job 这里省略，聚焦代码层安全

stages:
  - lint
  - test
  - security_scan    # ← 08 章核心：四类安全扫描并行
  - build            # 06 章 Kaniko
  - publish          # 06 章 推送 + 签名
  - deploy           # 07 章 部署
  - verify           # 07 章 部署后验证 + 08 章 DAST

# ========================================
# 1. Secret Detection（最前面，秒级，所有环境都跑）
# ========================================
secret_detection:
  stage: security_scan
  image:
    name: zricethezav/gitleaks:latest
    entrypoint: [""]
  script:
    - gitleaks detect --source . --config .gitleaks.toml
        --report-format json --report-path gitleaks-report.json
        --log-opts "$GITLEAKS_LOG_OPTS" --exit-code 1
  variables:
    GITLEAKS_LOG_OPTS: ""  # MR 里动态设置
  before_script:
    - |
      if [ -n "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME" ]; then
        export GITLEAKS_LOG_OPTS="origin/${CI_MERGE_REQUEST_TARGET_BRANCH_NAME}..HEAD"
      else
        export GITLEAKS_LOG_OPTS="HEAD~5..HEAD"
      fi
  artifacts:
    when: always
    paths: [gitleaks-report.json]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG
  allow_failure: false  # 密钥泄露永远硬阻断

# ========================================
# 2. SAST（Bandit + Semgrep 并行，dev/test/stage/main 都跑）
# ========================================
sast:bandit:
  stage: security_scan
  image: python:3.12-slim
  before_script:
    - pip install bandit[toml] --quiet
  script:
    - bandit -r app/ -c .bandit -f json -o bandit-report.json || true
    - python scripts/check-bandit.py bandit-report.json  # MEDIUM 以上 → exit 1
  artifacts:
    when: always
    paths: [bandit-report.json]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
  allow_failure: false

sast:semgrep:
  stage: security_scan
  image: returntocorp/semgrep:latest
  script:
    - semgrep --config .semgrep.yml --config p/python --config p/owasp-top-ten
        --json -o semgrep-report.json app/
    - python scripts/check-semgrep.py semgrep-report.json  # ERROR → exit 1
  artifacts:
    when: always
    paths: [semgrep-report.json]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
  allow_failure: false

# ========================================
# 3. SCA（pip-audit + Trivy fs，dev 只扫 lock 变更，test+ 完整扫）
# ========================================
sca:pip-audit:
  stage: security_scan
  image: python:3.12-slim
  before_script:
    - pip install pip-audit --quiet
  script:
    - pip-audit --strict --desc --format json -o pip-audit-report.json || true
    - python scripts/check-pip-audit.py pip-audit-report.json
  artifacts:
    when: always
    paths: [pip-audit-report.json]
  rules:
    # dev 段：只有 pyproject.toml / requirements.txt 变了才跑（减少流水线时间）
    - if: $CI_COMMIT_BRANCH == "dev"
      changes: [pyproject.toml, requirements.txt, requirements*.txt]
    # test/stage/main：每次都跑
    - if: $CI_COMMIT_BRANCH =~ /^(test|stage|main)$/
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: [pyproject.toml, requirements.txt, requirements*.txt]
  allow_failure: false

sca:trivy-fs:
  stage: security_scan
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  script:
    - trivy fs --severity CRITICAL,HIGH --exit-code 1 --format json -o trivy-fs-report.json .
  artifacts:
    when: always
    paths: [trivy-fs-report.json]
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(test|stage|main)$/
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  allow_failure: false

# ========================================
# 4. SonarQube 质量门（test 及以上才跑，dev 太频繁）
# ========================================
sonarqube-check:
  stage: security_scan
  image:
    name: sonarsource/sonar-scanner-cli:latest
    entrypoint: [""]
  needs: ["test:unit"]  # 依赖覆盖率报告
  script:
    - sonar-scanner
        -Dsonar.host.url=$SONAR_HOST_URL
        -Dsonar.login=$SONAR_TOKEN
        -Dsonar.projectKey=myorg:myapp
        -Dsonar.python.coverage.reportPaths=coverage.xml
    - python scripts/check-sonar-gate.py  # 轮询质量门状态
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(test|stage|main)$/
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  allow_failure: false

# ========================================
# 5. DAST（只有 stage 部署后跑）
# ========================================
dast:zap:
  stage: verify
  image:
    name: ghcr.io/zaproxy/zaproxy:stable
    entrypoint: [""]
  needs: ["deploy:stage"]
  script:
    - mkdir /zap/wrk
    # Baseline 扫描（被动 + 主动，不攻击认证后页面）
    - zap-baseline.py -t http://stage-app.internal:8000
        -c zap-rules.tsv -J zap-report.json -r zap-report.html
        -I  # 退出码：有 HIGH 告警 → 1
  artifacts:
    when: always
    paths: [zap-report.json, zap-report.html]
  rules:
    - if: $CI_COMMIT_BRANCH == "stage"
  allow_failure: true  # DAST 误报多，先软告警不阻断
```

> **流水线时长分析**：Secret Detection（30s）+ Bandit（30s）+ Semgrep（60s）+ pip-audit（20s）+ Trivy fs（30s）= 并行跑约 **2 分钟**。SonarQube（3 分钟）单独串行。总安全扫描时长 < 5 分钟，不会成为流水线瓶颈。

### 8.6.3 并行化与流水线时长优化

**优化前（串行，总时长 12 分钟）**：
```
Secret(30s) → Bandit(30s) → Semgrep(60s) → pip-audit(20s) → Trivy(30s) → SonarQube(3min) → ...
```

**优化后（并行，总时长 3.5 分钟）**：
```
┌─ Secret(30s) ────────────────────────┐
├─ Bandit(30s) ────────────────────────┤
├─ Semgrep(60s) ───────────────────────┤  → SonarQube(3min，需等覆盖率) → ...
├─ pip-audit(20s) ─────────────────────┤
└─ Trivy fs(30s) ──────────────────────┘
                    ↑ 并行完成 ≈ 1 分钟
```

**并行化实现**：GitLab CI 里同一个 `stage` 的多个 Job **自动并行**。上面的配置里 `secret_detection` / `sast:bandit` / `sast:semgrep` / `sca:pip-audit` / `sca:trivy-fs` 都在 `security_scan` stage，自动并行跑。只有 `sonarqube-check` 需要等覆盖率报告（`needs: ["test:unit"]`）。

**进一步优化**：
1. **GitLab CI Cache**：缓存 Bandit/Semgrep/pip-audit 的安装包，减少 `pip install` 时间
2. **增量扫描**：Secret Detection 和 Semgrep 只扫 MR 的 diff（不是全量扫描），用 `--log-opts` 和 `--diff` 参数
3. **feature MR 轻量化**：feature MR 阶段只跑 Secret + Bandit（< 1 分钟），SCA 和 SonarQube 留到 merge dev 时跑（feature MR 太频繁，完整扫描会拖慢开发节奏）
4. **定时全量扫描**：用 GitLab Scheduled Pipeline 每周日凌晨跑一次全量安全扫描（所有工具 + 全量历史），不阻塞日常开发

## 8.7 DAST 动态安全测试（进阶补充）

> DAST 是 08 章四类扫描里**最重、最慢、最容易误报**的一类。小团队可以推迟引入，但需要知道它存在的价值和引入时机。

### 8.7.1 DAST vs SAST 区别与互补

**表 8-7：DAST vs SAST 对比**

| 维度 | SAST（静态） | DAST（动态） |
| ---- | ------------ | ------------ |
| **扫什么** | 源代码 | 运行中的应用 |
| **要不要跑起来** | ❌ 只读代码 | ✅ 必须部署 + 运行 |
| **能发现什么** | 代码逻辑漏洞（SQL 注入、硬编码密码） | 运行时漏洞（XSS、CSRF、目录遍历、未授权访问） |
| **误报率** | 中高（理论分析，不验证） | 低（实际发请求验证） |
| **漏报率** | 中（死代码、反射调用扫不到） | 中（没被路由到的页面扫不到） |
| **Pipeline 位置** | PR 阶段（Build 前） | stage 部署后（Verify 阶段） |
| **执行时间** | 1~5 分钟 | 5~30 分钟 |
| **维护成本** | 低（规则自动更新） | 中（需配置认证、排除规则） |
| **典型工具** | SonarQube / Bandit / Semgrep | OWASP ZAP / Burp Suite / Nuclei |

**关键结论**：SAST 和 DAST **互补不替代**。SAST 能发现 DAST 找不到的硬编码密码（DAST 看不到源码）；DAST 能发现 SAST 找不到的运行时配置问题（SAST 看不到运行环境）。最佳实践是两者都配，但 DAST 可以晚一步引入。

### 8.7.2 OWASP ZAP 集成（stage 环境跑）

**OWASP ZAP Baseline 扫描**（最轻量，适合 CI）：

```yaml
# .gitlab-ci.yml（DAST：OWASP ZAP Baseline 扫描，stage 环境部署后跑）
dast:zap:
  stage: verify
  image:
    name: ghcr.io/zaproxy/zaproxy:stable
    entrypoint: [""]
  needs: ["deploy:stage"]   # 等 stage 部署完成
  variables:
    # ZAP 扫描目标（stage 环境地址）
    ZAP_TARGET: "http://stage-app.internal:8000"
    # 扫描时长（分钟），小应用 5 分钟够了
    ZAP_DURATION: "5"
  script:
    - mkdir /zap/wrk
    # Baseline 扫描：被动扫描 + 有限主动扫描
    # -t 目标 URL / -J JSON 报告 / -r HTML 报告 / -I 有 HIGH 就返回非 0
    - zap-baseline.py
        -t $ZAP_TARGET
        -J zap-report.json
        -r zap-report.html
        -c zap-rules.tsv        # 自定义规则文件
        -I                      # HIGH 告警 → exit 1
        -d                      # 详细日志
  after_script:
    # 把 ZAP 报告复制到 artifacts 目录
    - cp /zap/wrk/zap-report.json . || true
    - cp /zap/wrk/zap-report.html . || true
  artifacts:
    when: always
    paths:
      - zap-report.json
      - zap-report.html
    reports:
      dast: zap-report.json
  rules:
    - if: $CI_COMMIT_BRANCH == "stage"
  allow_failure: true   # DAST 先软告警，等规则调好了再改 false
```

**zap-rules.tsv（自定义规则：忽略/升级/降级）**：

```text
# zap-rules.tsv
# 格式：规则ID  级别  描述
# 级别：HIGH / MEDIUM / LOW / INFO / EXCLUDE

# EXCLUDE：完全忽略（误报）
10010  EXCLUDE  # Cookie 没设 HttpOnly（stage 环境用了 Nginx 代理，ZAP 扫不到真实 Cookie 设置）
10017  EXCLUDE  # Source Code Disclosure（ZAP 对 FastAPI 误报）

# 降级到 INFO（已知风险可接受）
10024  INFO     # Information Disclosure - Sensitive Information in URL（API 设计需要 query 参数传 ID）

# 升级到 HIGH（业务特别关注）
40026  HIGH     # Cross Site Scripting（XSS 是业务高危）
```

> **DAST 引入时机建议**：
> - 团队 < 5 人 / 服务 < 3 个：暂时不引入，靠 SAST + Secret + SCA 覆盖 90% 场景
> - 团队 5~10 人 / 有公开 API：引入 ZAP Baseline，stage 环境跑，先 `allow_failure: true`（软告警）
> - 团队 > 10 人 / 有合规要求：ZAP Full Scan + 认证扫描，配 Nuclei 做补充

## 8.8 生产常见问题与事故复盘

> 和 06 章 6.8 / 07 章 7.9 对称结构，08 章安全扫描类事故统一集中于此。

### 8.8.1 安全扫描过严导致团队绕过门禁（管理事故）

**事故**：团队新配了 SonarQube 质量门，设了 8 个条件（覆盖率 ≥ 80% + 重复率 < 3% + Blocker/Critical/Major = 0 + ...），结果所有 MR 都因为老代码的历史债 FAIL。两周后开发者发现可以在 GitLab MR 设置里 "Allow merge when pipeline fails"，于是所有 MR 都勾了这个选项，质量门名存实亡。

**根因**：
1. 一开始就配了太多条件（8 条），没有分阶段引入
2. 条件设的是 "Overall Code" 而不是 "New Code"，老代码的历史债拖垮新代码
3. 没有和团队沟通就直接开质量门

**修复**：
1. 所有条件改成 "on New Code"（只检查新增代码）
2. 起步只配 2 条（Blocker = 0 + Secret = 0），团队适应 1 个月后再加覆盖率
3. GitLab MR 设置里关闭 "Allow merge when pipeline fails"
4. 和团队同步：质量门是帮大家发现问题的，不是找茬的；历史债单独排期还，不影响新代码合入

### 8.8.2 .trivyignore 变成"漏洞垃圾桶"（安全事故）

**事故**：`.trivyignore` 从 3 条 CVE 增长到 47 条，没人 review，其中 12 条上游早已修复但没人删。一个 CRITICAL 级别的 CVE（log4j 类）被加到 `.trivyignore` 后忘了处理，3 个月后被打包进生产镜像，被外部安全审计发现，P0 事故。

**根因**：
1. `.trivyignore` 没有"过期日期"机制，加了就永远在
2. 没有定期 review 流程
3. 开发者把忽略当"消除 CI 红色"的快捷方式

**修复（铁律）**：
1. `.trivyignore` 每条必须带 `[评估人] [评估日期] [过期日期] 理由`（8.5.3 节格式）
2. CI 里加一个 Job 检查 `.trivyignore` 里有没有过期的 CVE：
```yaml
check:trivyignore:
  stage: security_scan
  image: python:3.12-slim
  script:
    # 检查 .trivyignore 里有没有过期的条目
    - python scripts/check-trivyignore-expiry.py .trivyignore
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  allow_failure: false  # 有过期未删的 → 阻断
```
3. 忽略列表超过 10 条自动告警（CI Yellow Warning），提醒团队做依赖升级

### 8.8.3 SAST 误报太多导致开发者直接忽略所有告警（狼来了效应）

**事故**：Semgrep 配了 20 条社区规则 + 10 条自定义规则，每次 MR 都报 30+ 个告警，90% 是误报（比如把 `test_password = "test123"` 误报为硬编码密码）。一个月后开发者不再看 SAST 告警，一个真正的 SQL 注入漏洞（f-string 拼接）被忽略了，进生产后被白帽子报告。

**根因**：
1. 规则太宽，没有配白名单
2. 误报不处理，累积成"噪音"，真告警被淹没

**修复**：
1. 每次误报都要加精确白名单（不是关规则），把误报率降到 < 5%
2. SAST 告警按严重级别分流：ERROR → CI 阻断；WARNING → MR 评论但不阻断；INFO → 只记录不展示
3. 每月 review 一次 SAST 告警统计：总告警数 / 误报数 / 真实漏洞数，持续调规则

### 8.8.4 密钥泄露后用 git rebase 删历史（错误操作导致二次泄露）

**事故**：开发者不小心把 AWS Access Key commit 到了 main 分支。运维用 `git rebase -i` 删了那个 commit 并 `git push --force`。但：
1. 密钥已经在 Git 历史里存在了 2 小时，外部爬虫可能已经扫到
2. `--force` 推送后，已经 clone 仓库的开发者本地仍然有密钥
3. **最致命的**：没有立刻轮换密钥，而是先删 Git 历史，等了 4 小时才去 AWS 轮换 → 这 4 小时内攻击者用密钥启动了 20 台 EC2 挖矿

**正确流程**（铁律，顺序不能错）：
1. **第一步永远是轮换密钥**（Revoke + 重新生成），不是删 Git 历史
2. 轮换后才清理 Git 历史（`git filter-repo` 或 BFG Repo-Cleaner）
3. 通知所有人 force pull
4. 检查云平台日志，确认密钥没有被滥用
5. 复盘：为什么 Secret Detection 没拦住？

### 8.9.2 现阶段最佳实践速记（2026）

- **安全左移**：Secret Detection → SAST → SCA → DAST，按成本和速度依次引入，PR 阶段就跑
- **小团队起步组合**：Gitleaks（密钥）+ Bandit（Python SAST）+ pip-audit（SCA），三个全免费，< 2 分钟
- **质量门分阶段**：起步只配 Blocker = 0 + Secret = 0（2 条），适应后再加覆盖率（70% → 80%）
- **阻断策略**：Secret Detection 永远硬阻断；SAST/SCA 按 HIGH/CRITICAL 硬阻断、MEDIUM 软告警
- **白名单管理**：每条带 CVE + 理由 + 过期日期；季度 review；不超过 10 条
- **P1.3 落地**：feature MR 跑 Secret+SAST（< 1 分钟）；merge dev 加 SCA+SonarQube；merge test 加镜像扫描；merge stage 加 DAST；merge main 全套验证不发布
- **并行化**：同 stage 的安全扫描 Job 自动并行，总时长 < 5 分钟
- **密钥泄露应急**：第一步轮换密钥（不是删 Git 历史）→ 第二步清理历史 → 第三步通知对齐
