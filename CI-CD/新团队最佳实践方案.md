# 新团队最佳实践方案

> 面向 5~15 人、预算有限、**不上 K8s** 的新团队，使用 Docker Compose / Docker Swarm 落地 CI/CD。
> 目标：3 个月内把 DORA 四指标从 Low 抬到 Medium，让"合入即验证、打 Tag 即发布"成为团队肌肉记忆。
> 关联：本方案是对 [03-工具选型与对比](./03-工具选型与对比.md)（GitLab CE 选型）、[06-容器化与制品管理](./06-容器化与制品管理.md)（Harbor/镜像）、[07-部署与发布策略](./07-部署与发布策略.md)（Swarm 部署）、[09-监控可观测性与回滚](./09-监控可观测性与回滚.md)（Prometheus/Loki）的工程化落地，分支模型严格遵循 [我的实践记录 P1](./我的实践记录.md#p1-分支即环境-dev--test--stage--main--prod)。

## 0. 读者画像与边界

| 维度 | 设定 |
| ---- | ---- |
| 团队规模 | 5~15 名后端工程师 + 0~1 名兼职运维 |
| 技术栈 | Python 为主（Flask/FastAPI），可能含少量 Java |
| 基础设施 | 自建 1~3 台物理机/云主机，**不上 K8s** |
| 部署形态 | Docker Compose（单机）→ Docker Swarm（2~3 节点） |
| 预算约束 | 月度基础设施总成本 ≤ 1500 元 |
| 当前 DORA | Low（部署频率周级、变更前置时间天级、MTTR 小时级、变更失败率 > 30%） |
| 目标 DORA | Medium（部署频率日级、变更前置时间小时级、MTTR 分钟级、变更失败率 10~15%） |

**不做的事**（明确边界，避免过度设计）：
- 不引入 K8s / Argo CD / Flux（运维成本超出 5~15 人团队承受力）
- 不做多集群多地域容灾
- 不做 Service Mesh
- 不自建 SAST/DAST 引擎，复用 SonarQube + Trivy 现成规则包

## 1. 架构总览

### 1.1 文字描述

整体采用 **"GitLab CE 单体 + Swarm 集群 + 可观测性三件套"** 的扁平架构：

- **代码与流水线**：GitLab CE（含内置 Container Registry 备用）+ GitLab Runner（Shell + Docker executor 混用）
- **制品与安全**：Harbor（私有镜像仓 + Trivy 集成 + 复制策略）+ SonarQube（代码质量门）
- **运行时**：Docker Swarm（manager + 1~2 worker），服务用 `docker stack` 编排
- **可观测性**：Prometheus（指标）+ Grafana（面板）+ Loki（日志聚合）+ Alertmanager（告警）
- **配置与密钥**：环境变量 + `.env` 文件 + Docker secrets（生产敏感数据）

### 1.3 组件选型理由（一句话版）

| 组件 | 选型 | 为什么不是别的 |
| ---- | ---- | -------------- |
| 代码托管 | GitLab CE | Jenkins+Gitea 拼装维护成本高；GitHub Actions 私有化部署弱 |
| 流水线 | GitLab CI | YAML 声明式，`rules` 原生支持 P1 模型 |
| 镜像构建 | Kaniko | 无需 Docker-in-Docker，更安全更快（[06 章 6.4](./06-容器化与制品管理.md)） |
| 制品仓 | Harbor | 自带漏洞扫描 + 复制策略 + 项目隔离，比 Registry 强 |
| 质量门 | SonarQube Community | 免费版覆盖 Python/Java 主流规则 |
| 编排 | Docker Swarm | K8s 学习/运维成本太高；Swarm 内置在 Docker，2~3 节点足够 |
| 监控 | Prometheus + Grafana | 行业事实标准 |
| 日志 | Loki | 与 Grafana 同面板，资源占用比 ELK 低一个数量级 |

更多对比见 [03-工具选型与对比](./03-工具选型与对比.md)。

## 2. 最小化落地清单（4 周计划）

> 原则：**每周交付一个可演示的能力**，避免"做了 3 个月还没人能用"。
> 前置假设：GitLab CE 已装好（Omnibus 一键包，2C4G 即可），代码已托管。

### 2.1 第 1 周：Git 工作流 + GitLab CI 跑通 lint/test/build

**目标**：开发者 push 任一环境分支 → 5 分钟内流水线反馈 lint/test/build 结果。

**任务清单**：
1. 创建 4 条长期分支：`dev` / `test` / `stage` / `main`，设置 `main` 保护分支（只许 MR 合入、不许直推）
2. 在 `main` 上写 `CONTRIBUTING.md`，固化 P1 流程："feature 从 main 切 → 各自合入 dev/test/stage/main"
3. 安装 1 个 GitLab Runner（Shell executor 即可），注册到 GitLab
4. 写最小 `.gitlab-ci.yml`：lint（ruff）+ test（pytest）+ build（先不接 Harbor，仅本地构建验证 Dockerfile）
5. 配置 MR 强制 CI 通过才能合并（Settings → Merge Requests → Pipelines must succeed）

**验收**：
- 提一个 MR 到 dev，CI 跑绿才能合
- 故意写一行 lint 错误，CI 拦截成功
- 平均流水线时长 ≤ 5 分钟

**关联**：[02-环境与前置技能](./02-环境与前置技能.md)、[05-构建与测试](./05-构建与测试.md)。

### 2.2 第 2 周：Docker 镜像 + Harbor 推送 + Trivy 扫描

**目标**：CI 产出的镜像进 Harbor，且必须通过 Trivy 漏洞扫描才允许 push stable tag。

**任务清单**：
1. 部署 Harbor（`docker-compose.yml` 官方版，2C4G 够用）
2. 创建 Harbor 项目：`app`（私有）、`app-cache`（缓存）
3. 在 GitLab CI/CD Variables 配置 `HARBOR_URL` / `HARBOR_USER` / `HARBOR_PASSWORD`（masked + protected）
4. 改造 build stage 用 Kaniko 推 Harbor，镜像 tag 命名 `${CI_COMMIT_REF_SLUG}-${CI_COMMIT_SHORT_SHA}`
5. 加 scan stage：Trivy 扫描镜像，CRITICAL 漏洞数 > 0 则 fail
6. 在 Harbor 启用 Trivy 自动扫描 + 拒绝漏洞镜像部署（Deployer 防护）

**验收**：
- push 到 dev 分支，Harbor 出现 `app:dev-abc12345` 镜像
- 故意引入一个有 CRITICAL 漏洞的旧基础镜像，CI 拦截
- Harbor 控制台可看到扫描报告

**关联**：[06-容器化与制品管理](./06-容器化与制品管理.md)、[08-安全与质量门禁](./08-安全与质量门禁.md)、[补充专题 S11 包仓库](./补充专题/S11-包仓库Nexus-Harbor-GitLabRegistry.md)。

### 2.3 第 3 周：Docker Swarm 部署 + 健康检查 + 回滚脚本

**目标**：merge 到 dev/test 自动部署，stage/main 手动确认；部署失败 60 秒内自动回滚。

**任务清单**：
1. 初始化 Swarm 集群：`docker swarm init`（manager）+ `docker swarm join`（worker）
2. 在 manager 创建 `/opt/stacks/{dev,test,stage,prod}/` 目录，放 `docker-compose.yml`
3. Harbor 凭据用 `docker secret` 注入（不写明文）
4. 写 deploy stage：SSH 到 manager → `docker stack deploy -c compose.yml --with-registry-auth app-dev`
5. 写 verify stage：轮询 `/healthz` 接口，30 次失败则触发回滚
6. 写 `rollback.sh`：`docker service rollback app_app` 一键回滚到上一版本
7. 在 GitLab 配置 `deploy:stage` / `deploy:prod` 为 `when: manual`

**验收**：
- merge 到 dev，60 秒内 dev 环境 `/healthz` 返回 200
- 故意写一个会 crash 的镜像，60 秒后自动回滚到上一版本
- 手动点 `deploy:prod`，prod 环境更新成功

**关联**：[07-部署与发布策略](./07-部署与发布策略.md)、[09-监控可观测性与回滚](./09-监控可观测性与回滚.md)。

### 2.4 第 4 周：SonarQube 质量门 + Prometheus 监控 + Loki 日志

**目标**：质量门拦截坏代码；监控告警覆盖 4 条核心规则；日志可在 Grafana 检索。

**任务清单**：
1. 部署 SonarQube Community（`docker-compose.yml`，4G 内存）
2. 在 GitLab 配置 `SONAR_TOKEN`，CI 加 sonar-scanner stage
3. 配置 Quality Gate：新增异味 > 0 / 覆盖率 < 60% / 严重漏洞 > 0 则 fail
4. 部署 Prometheus + Grafana + Loki + Promtail（一套 `docker-compose.yml`）
5. Prometheus 抓取 Swarm 节点 Node Exporter + app `/metrics`
6. Alertmanager 配 4 条告警（见 [§7](#7-监控告警最小集)），webhook 到飞书/钉钉
7. Promtail 收集 `/var/lib/docker/containers/*/*.log`，推 Loki
8. Grafana 建 3 个看板：服务总览 / DORA 指标 / 日志检索

**验收**：
- 故意写一个空 except，SonarQube 拦截 MR
- CPU 打满某节点，1 分钟内飞书收到告警
- Grafana 能搜到 app 容器日志

**关联**：[08-安全与质量门禁](./08-安全与质量门禁.md)、[09-监控可观测性与回滚](./09-监控可观测性与回滚.md)、[补充专题 S9 质量安全扫描集成](./补充专题/S9-质量安全扫描集成.md)、[补充专题 S3 DORA 四指标](./补充专题/S3-DORA四指标.md)。

## 3. 分支管理策略（P1 模型 + rules 配置）

### 3.1 分支模型回顾

严格遵循 [P1 实践](./我的实践记录.md#p1-分支即环境-dev--test--stage--main--prod)：

```
图 3-1：P1 分支即环境模型
┌─────────────────────────────────────────────────────────────────────┐
│  main (v1.0 = prod，演化终点站)                                       │
│                                                                     │
│  feature/f1 ──► dev ──► test ──► stage ──► main ──► tag v1.1         │
│  feature/f2 ──► dev ──► (终止则下游零污染)                            │
│  feature/f3 ──► dev ──► test ──► ...                                 │
│                                                                     │
│  规则：feature 从 main 切；各自独立合入 dev/test/stage/main；不做逐级 merge │
│  main 合入只验证不发布；打 Tag 才触发生产部署                          │
└─────────────────────────────────────────────────────────────────────┘
```

**4 条环境分支的触发策略**（来自 [P1.3 表 P1.3-1](./我的实践记录.md#p13-环境晋升触发机制与门禁设计p1-子增强)）：

| 分支 | 触发方式 | 部署门禁 |
| ---- | -------- | -------- |
| dev | push 自动 | 无 |
| test | push 自动 | 无 |
| stage | push 自动 CI，**部署人工确认** | `when: manual` |
| main | push 自动 CI（**只验证不发布**） | 不触发部署 |
| Tag `v*` | tag push | 自动部署 prod |

### 3.2 `.gitlab-ci.yml` 的 `rules` 完整配置示例

> 这是本方案的"分支-环境"映射核心。所有 Job 通过 `rules` 控制在哪个分支/tag 触发。

```yaml
# ============================================================
# 公共 rules 片段：所有 CI Job 复用
# ============================================================
# 触发条件：4 条环境分支 push，或匹配 v 开头 Tag
.rules:on-env-branch:
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/

.rules:on-tag:
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/

# ============================================================
# workflow:rules —— 控制整条流水线何时创建
# ============================================================
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: never                    # MR 不创建双流水线，避免重复
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/
    - when: never                    # feature 分支不跑完整流水线，靠 MR 的 CI 反馈

# ============================================================
# 各 Job 的 rules（具体见 §4 完整模板）
# ============================================================
# lint / test / build / scan：4 条环境分支 + Tag 都跑
# push：4 条环境分支 + Tag 都跑
# deploy:dev   : 仅 dev 分支，自动
# deploy:test  : 仅 test 分支，自动
# deploy:stage : 仅 stage 分支，when: manual
# deploy:prod  : 仅 Tag，自动（Tag 即审批）
# verify       : 各环境 deploy 后跟随
# record-dora  : 各环境 deploy 成功后跟随
```

**关键设计**：
1. `workflow:rules` 把 feature 分支排除在完整流水线外，只在 MR 时跑 CI 反馈（节省 Runner 资源）
2. main 分支跑 CI 但不部署，对应 [P1.3.3 两段式机制](./我的实践记录.md#p133-main-的两段式机制关键设计)
3. Tag 自动部署 prod：打 Tag = 人工审批动作，无需再 `when: manual`

## 4. 完整 `.gitlab-ci.yml` 模板（Python 项目）

> 用 `needs` 构造 DAG，让 lint/test 并行、scan 跟 build 后、deploy 跟 push 后。
> 镜像 tag 用 `${CI_COMMIT_REF_SLUG}-${CI_COMMIT_SHORT_SHA}`，便于追溯环境跑的是哪个 commit。

```yaml
# ============================================================
# 新团队 CI/CD 模板 · Python · P1 分支模型 · Harbor + Swarm
# 关联：我的实践记录 P1 / P1.1 / P1.3
# ============================================================
stages:
  - lint
  - test
  - build
  - scan
  - push
  - deploy
  - verify
  - record

variables:
  IMAGE_TAG: ${CI_COMMIT_REF_SLUG}-${CI_COMMIT_SHORT_SHA}
  IMAGE: ${HARBOR_URL}/app/app:${IMAGE_TAG}
  GIT_DEPTH: "20"
  PIP_CACHE_DIR: ${CI_PROJECT_DIR}/.cache/pip

workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: never
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/
    - when: never

# ---------- 公共片段 ----------
.py-base: &py-base
  image: python:3.12-slim
  cache:
    key: pip-${CI_COMMIT_REF_SLUG}
    paths: [.cache/pip]

# ============================================================
# 1. lint（ruff）
# ============================================================
lint:
  <<: *py-base
  stage: lint
  before_script:
    - pip install --cache-dir=.cache/pip ruff
  script:
    - ruff check app/
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/

# ============================================================
# 2. test（pytest + coverage）
# ============================================================
test:
  <<: *py-base
  stage: test
  before_script:
    - pip install --cache-dir=.cache/pip -r requirements.txt pytest pytest-cov
  script:
    - pytest --cov=app --cov-report=xml --cov-report=term
  coverage: '/TOTAL.*\s+(\d+\%)$/'
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
    paths: [coverage.xml]
    expire_in: 7 days
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/

# ============================================================
# 3. build（Kaniko，无 dind）—— 与 lint/test 并行
# ============================================================
build:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  script:
    - /kaniko/executor
      --context "${CI_PROJECT_DIR}"
      --dockerfile "${CI_PROJECT_DIR}/Dockerfile"
      --destination "${IMAGE}"
      --build-arg "GIT_COMMIT=${CI_COMMIT_SHA}"
      --build-arg "BUILD_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ)"
      --build-arg "VERSION=${IMAGE_TAG}"
      --cache=true
      --cache-repo "${HARBOR_URL}/app/app-cache"
      --destination "${HARBOR_URL}/app/app:${IMAGE_TAG}"
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/

# ============================================================
# 4. scan（Trivy，依赖 build）
# ============================================================
scan:
  stage: scan
  image: aquasec/trivy:0.54.1
  needs: [build]
  variables:
    TRIVY_USERNAME: ${HARBOR_USER}
    TRIVY_PASSWORD: ${HARBOR_PASSWORD}
    TRIVY_AUTH_URL: ${HARBOR_URL}
  script:
    - trivy image --exit-code 1 --severity CRITICAL --ignore-unfixed
      --format json --output trivy-report.json "${IMAGE}"
  artifacts:
    paths: [trivy-report.json]
    expire_in: 30 days
    when: always
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+/

# ============================================================
# 5. push stable tag（依赖 scan 通过）
#    同时给镜像打 ${IMAGE_TAG} 和 latest-${env} 双 tag，方便回滚定位
# ============================================================
push:stable:
  stage: push
  image: docker:24
  services: [docker:24-dind]
  needs: [scan]
  before_script:
    - echo "${HARBOR_PASSWORD}" | docker login -u "${HARBOR_USER}" --password-stdin "${HARBOR_URL}"
  script:
    - docker pull "${IMAGE}"
```

## 6. Docker Swarm 部署脚本

### 6.1 部署 / 滚动更新 / 回滚

```bash
#!/usr/bin/env bash
# /opt/stacks/bin/deploy.sh —— 由 GitLab CI 的 deploy stage SSH 调用
set -euo pipefail

ENV="${1:?usage: deploy.sh <env>}"
STACK="app-${ENV}"
COMPOSE_FILE="/opt/stacks/${ENV}/docker-compose.yml"
IMAGE_TAG="${IMAGE_TAG:?IMAGE_TAG must be set}"

# 1. 备份当前服务状态（用于审计 + 手动回滚参考）
docker service inspect "${STACK}_app" > "/opt/stacks/${ENV}/.last-service.json" 2>/dev/null || true

# 2. 注入镜像 tag 并部署（滚动更新）
export IMAGE_TAG
docker stack deploy -c "${COMPOSE_FILE}" --with-registry-auth "${STACK}"

# 3. 等待滚动完成
echo "Waiting for rollout..."
sleep 5
until docker service ps "${STACK}_app" --filter desired-state=running --format '{{.CurrentState}}' \
      | grep -v -E 'Running [0-9]+ second' | grep -q 'Running'; do
  echo -n "."
  sleep 3
done
echo "Rollout complete."
```

```bash
#!/usr/bin/env bash

# Swarm 内置回滚：把 service 回退到上一个 task spec

# 等待回滚完成
```

### 6.3 蓝绿切换（可选，stage/prod 用）

Swarm 原生只支持滚动更新，蓝绿需用两套 stack 实现：

```bash
#!/usr/bin/env bash
# blue-green.sh —— 蓝绿切换：active=blue，新部署 green，验证后切流量
set -euo pipefail
ENV="${1:?usage: blue-green.sh <env>}"
ACTIVE="$(cat /opt/stacks/${ENV}/.active 2>/dev/null || echo blue)"
NEXT=$([ "$ACTIVE" = blue ] && echo green || echo blue)

# 1. 部署 NEXT stack（占用资源但 nginx 还没切过去）
IMAGE_TAG="${IMAGE_TAG}" docker stack deploy -c /opt/stacks/${ENV}/compose-${NEXT}.yml --with-registry-auth "app-${ENV}-${NEXT}"

# 2. 健康检查 NEXT
for i in $(seq 1 30); do
  curl -fsS "http://127.0.0.1:8081/healthz" && break || sleep 2
done

# 3. 切换 nginx upstream 指向 NEXT 并 reload
sed -i "s/${ACTIVE}/${NEXT}/g" /opt/stacks/${ENV}/nginx/nginx.conf
docker service update --force "app-${ENV}_nginx"

# 4. 记录 active，老 stack 保留 30 分钟后清理
echo "${NEXT}" > /opt/stacks/${ENV}/.active
echo "Switched to ${NEXT}. Old ${ACTIVE} kept for 30min."
( sleep 1800 && docker stack rm "app-${ENV}-${ACTIVE}" ) &
```

```yaml
# /etc/prometheus/rules/core.yml
groups:
  - name: core
    rules:
      # 1. CPU 持续 5 分钟 > 85%
      - alert: HighCpuUsage
        expr: 100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.instance }} CPU > 85% 持续 5 分钟"
          description: "当前值 {{ $value | printf \"%.1f\" }}%，请检查是否需要扩容或限流"

      # 2. 内存可用 < 10%
      - alert: HighMemoryUsage
        expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100 > 90
        for: 3m
        labels: { severity: critical }
        annotations:
          summary: "{{ $labels.instance }} 内存使用 > 90%"
          description: "可用内存不足 10%，可能触发 OOM"

      # 3. app HTTP 5xx 5 分钟内 > 1%
      - alert: HighHttp5xxRate
        expr: |
          sum(rate(http_requests_total{job="app",status=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{job="app"}[5m])) > 0.01
        for: 2m
        labels: { severity: critical }
        annotations:
          summary: "app 5xx 错误率 > 1%"
          description: "5 分钟内 5xx 占比 {{ $value | printf \"%.2f%%\" }}，请立即排查"

      # 4. 部署失败（DORA 变更失败率）
      - alert: DeployFailed
        expr: increase(deploy_success{env="prod"}[15m]) == 0 and increase(deploy_attempt{env="prod"}[15m]) > 0

        labels: { severity: critical }
        annotations:
          summary: "生产部署失败"
```

## 9. DORA 指标埋点

> DORA 四指标定义见 [补充专题 S3 DORA 四指标](./补充专题/S3-DORA四指标.md)。
> 这里给出最小化埋点方案：CI 事件 → Pushgateway → Prometheus → Grafana。

### 9.1 四指标采集方式

| 指标 | 数据源 | 采集方式 |
| ---- | ------ | -------- |
| 部署频率 | CI deploy 成功事件 | CI job 推 Pushgateway |
| 变更前置时间 | Git commit 时间 → 部署成功时间 | CI 计算差值推 Pushgateway |
| 变更失败率 | CI verify 失败 + 告警 DeployFailed | CI 推失败计数 |
| MTTR | 告警触发 → 告警 resolved | Alertmanager webhook 推 Pushgateway |

### 9.2 CI 端埋点脚本

```bash
#!/usr/bin/env bash
# scripts/record-dora.sh —— 在 CI record stage 调用
set -euo pipefail
ENV="${APP_ENV:?}"
IMAGE_TAG="${IMAGE_TAG:?}"
PG="pushgateway:9091"
TS=$(date +%s)

# 1. 部署成功计数（部署频率）
cat <<EOF | curl --data-binary @- http://${PG}/metrics/job/ci/instance/${CI_RUNNER_ID}
deploy_success{env="${ENV}",version="${IMAGE_TAG}"} 1
EOF

# 2. 变更前置时间（commit → deploy 成功，单位秒）
COMMIT_TS=$(git show -s --format=%ct ${CI_COMMIT_SHA})
LEAD_TIME=$((TS - COMMIT_TS))
cat <<EOF | curl --data-binary @- http://${PG}/metrics/job/ci/instance/${CI_RUNNER_ID}
lead_time_seconds{env="${ENV}",version="${IMAGE_TAG}"} ${LEAD_TIME}
EOF

# 3. 部署尝试计数（变更失败率分母）
cat <<EOF | curl --data-binary @- http://${PG}/metrics/job/ci/instance/${CI_RUNNER_ID}
deploy_attempt{env="${ENV}",version="${IMAGE_TAG}"} 1
EOF
```

### 9.3 Alertmanager 端 MTTR 埋点

```yaml
# alertmanager config.yml —— 告警 webhook 同时推 Pushgateway
receivers:
  - name: feishu-and-dora
    webhook_configs:
```

```python
# alertmanager-bridge.py —— 中转：记录告警触发与恢复时间
from flask import Flask, request
import requests, time, json

app = Flask(__name__)
INCIDENT_START = {}  # alertname → start_ts

@app.route('/webhook', methods=['POST'])
def webhook():
    data = request.json
    for alert in data.get('alerts', []):
        name = alert['labels']['alertname']
        if alert['status'] == 'firing':
            INCIDENT_START[name] = time.time()
        else:  # resolved
            start = INCIDENT_START.pop(name, None)
            if start:
                mttr = int(time.time() - start)
                requests.post('http://pushgateway:9091/metrics/job/alertmanager',
                              data=f'mttr_seconds{{alert="{name}"}} {mttr}\n')
    return '', 200
```

## 10. 常见误区与避坑

### 误区 1：把 GitLab Runner 装在 GitLab 同机且用 Shell executor 跑所有 Job

**症状**：CI 一跑高，GitLab 卡顿，push 拉不动。
**根因**：Shell executor 与 GitLab 抢 CPU/内存；构建任务有副作用污染宿主。
**正确做法**：Runner 独立机器或独立容器；构建类 Job 用 Docker executor；只有 deploy 类 Job 才用 Shell executor（需 SSH 到 manager）。

### 误区 2：镜像 tag 用 `latest`，回滚时找不到上一版

**症状**：出问题想回滚，发现 Harbor 里 `latest` 已经被覆盖，不知道上一版 SHA。
**根因**：`latest` 是可变 tag，无法追溯。
**正确做法**：所有镜像 tag 用 `${branch}-${short_sha}` 或 `${commit_tag}`；额外打 `latest-${env}` 仅作便捷引用，回滚一律用 commit SHA。详见 [06 章 6.5](./06-容器化与制品管理.md)。

### 误区 3：CI/CD 变量直接写在 `.gitlab-ci.yml` 里

**症状**：仓库泄漏 Harbor 密码、SSH 私钥。
**根因**：变量明文提交。
**正确做法**：所有敏感变量走 GitLab CI/CD Settings → Variables，勾选 **Masked** + **Protected**（Protected 变量只在受保护分支/Tag 可见）。SSH 私钥单独用 `file` 类型变量，落到 `/builds/.../` 路径。详见 [补充专题 S1 Secret 管理](./补充专题/S1-Secret管理.md)。

### 误区 4：SonarQube 质量门设太严，第一天就把所有 MR 卡死

**症状**：上线第一天，所有 MR 都被 Quality Gate 拦截，团队抵触。
**根因**：直接套用 SonarQube 默认 Quality Gate（覆盖率 80% / 0 异味），老代码历史包袱一次性爆发。
**正确做法**：
1. 上线第 1 个月只看"新增代码"指标（`New Code` 模式）
2. 阈值从松到紧：覆盖率 50% → 60% → 70%；新增异味 5 → 2 → 0
3. 老代码用 `sonar.exclusions` 临时排除，分批偿还

### 误区 5：Swarm 滚动更新 `parallelism` 设成 `replicas`，等同于重建

**症状**：滚动更新时服务全量重启，瞬间不可用。
**根因**：`parallelism: 3` + `replicas: 3` = 一次换光。
**正确做法**：`parallelism: 1` + `order: start-first` + `delay: 10s`，保证至少 N-1 个实例在跑。

### 误区 6：Prometheus 抓 app `/metrics` 不加超时

**症状**：app 卡死时 Prometheus 抓取超时堆积，自身 OOM。
**根因**：默认 `scrape_timeout` 等于 `scrape_interval`，慢实例拖垮整条 pipeline。
**正确做法**：`scrape_timeout: 10s`，且 app `/metrics` 必须 P95 < 1s；抓取失败用 `up == 0` 告警。

### 误区 7：Loki 直接收 stdout，不限制日志大小

**症状**：磁盘一周爆，Loki 崩溃。
**根因**：Swarm 服务默认无日志限制。
**正确做法**：每个 service 加 `logging.options.max-size: 10m` + `max-file: 3`；Loki 侧配 `retention_period: 30d`。

### 误区 8：打 Tag 触发 prod 部署，但 Tag 是基于旧 main 分支打的

**症状**：打 Tag v1.2.0 部署后，发现 prod 跑的不是最新的 main 代码。
**根因**：用户从 1 周前的 main commit 打 Tag，期间 main 又合入了新 feature。
**正确做法**：打 Tag 前先 `git checkout main && git pull`，从最新 main 打 Tag；或直接用 `git tag v1.2.0 main` 显式指定。CI 的 `tag-release` job 应校验 Tag commit 必须是 main HEAD 或近 N 个 commit。

## 12. 三个月里程碑验收

| 月份 | 里程碑 | DORA 指标目标 |
| ---- | ------ | ------------- |
| M1 | 4 周最小化落地完成，4 环境自动部署跑通 | 部署频率周级 → 日级（dev/test） |
| M2 | 质量门 + 监控 + DORA 看板上线，团队形成 MR 习惯 | 变更失败率 30% → 15%，MTTR 小时级 → 30 分钟级 |
| M3 | 回滚演练 + 故障演练 + 文档完善 | DORA 四指标全部进入 Medium 区间 |

**M3 验收清单**：
- [ ] 任意环境 5 分钟内完成一次部署
- [ ] 任意环境 60 秒内完成一次回滚
- [ ] Grafana 上可看到 4 个 DORA 指标趋势
- [ ] 故意制造一次故障，1 分钟内飞书收到告警
- [ ] 每条 MR 都有 CI 反馈，无 CI 不能合并
- [ ] 团队所有成员都能独立打 Tag 发版

> 完成上述清单，即从"靠人保障"过渡到"靠流水线保障"，对应 [10-进阶与工程化](./10-进阶与工程化.md) 的"工程化"心智。
