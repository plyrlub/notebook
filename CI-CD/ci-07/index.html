          • 7.9 生产事故踩坑录（汇总醒目）
            • 7.9.1 Expand-Contract 三大生产事故复盘（对应 7.7.4）
              • 事故 1：Step 1 Expand + Step 3 Contract 放同一版本 → 回滚直接全量 5xx（爆炸半径 100%）
              • 事故 2：双写没定「谁为准」+ 回填以 mobile 覆盖 phone → 运营改的 42 万条用户手机号全部回滚旧值（数据事故 P0）
              • 事故 3：2000 万行大表直接 ALTER ADD COLUMN → 锁表 31 分钟，所有写请求卡住（可用性事故 P1）
            • 7.9.2 Feature Flag 四大技术债坑（对应 7.5 Flag/Unleash/自建）
              • 坑 1：Release Flag 开完 100% 忘了删 → 3 个月后遍布 if/else 变「永远 True 的死代码」，没人敢动
              • 坑 2：Kill Switch 配在了调用方（订单服务里），不是被调方（积分服务里）→ 熔断了一半
              • 坑 3：Unleash 自建最小版里，ConfigMap 改了 Flag，应用没热更新，要等重启 → 紧急关不了（Kill Switch 秒级变分钟级）
              • 坑 4：组合爆炸没测 → 4 个 Release Flag 在 stage 单独测都好，prod 全开一起用触发死锁（测试覆盖盲区）
            • 7.9.3 ArgoCD 生产落地七招（对应 7.4.3，事故坑 + 正确做法）
            • 7.9.4 K8s 生产 Checklist Top5 漏配事故（对应 7.3.4）
              • Top1：没配 PodDisruptionBudget → 节点维护时 3 个 Pod 全被驱逐，服务挂 12 分钟
              • Top2：内存没设 requests = limits（超卖）→ 深夜 Batch 任务触发 OOM Kill，订单 Pod 随机被杀
              • Top3：慢启动应用没配 StartupProbe → 每 10 秒 Liveness 查一次，Pod 启动要 40 秒，连续 3 次失败被 K8s 反复重启（CrashLoopBackOff）
              • Top4：镜像 tag 用 latest → 晚上有人手动改了 latest 的 image，第二天滚动发布自动拉错版本，回滚不知道滚哪版
              • Top5：没配 readOnlyRootFilesystem → Spring Boot 应用被打进恶意内存马（写入 /tmp/classes/ 恶意 class，Spring Boot 热加载直接加载）
            • 7.9.5 main 分支回退 / 强推事故（对应 7.4.4）
              • 事故：用 git push --force（没加 -with-lease）强推 main → 把同事刚 push 正在跑 CI 的功能 D 给冲掉了，CI 还显示通过
            • 7.9.6 纯 Docker / Docker Compose / Swarm 部署六类坑（对应 7.6.4，小团队不养 K8s 必看）
              • 坑 1：SSH 私钥直接写进 deploy.sh 明文脚本或 CI 变量没 masked → 被 CI 日志打印出私钥 → 机器被扫
              • 坑 2：docker run 把宿主机 /var/run/docker.sock 挂进容器 → 容器里拿 docker 命令 = 宿主机 root（权限穿透）
              • 坑 3：compose 没配 healthcheck → up 了之后服务还没 Ready，Nginx 就把流量切过去导致 5xx
              • 坑 4：compose 滚动发布用 --force-recreate 而不是 --scale 2 → --scale 1 → 旧容器先删再启，中间 20 秒服务 0 副本
              • 坑 5：Swarm 里 Secret 图省事写在 environment 里明文，没走 docker secret create + secrets: 挂载 → docker inspect 一查就看到密码
              • 坑 6：Swarm stack deploy 没有配 update_config.failure_action: rollback → 更新失败了停在中间状态（2 个新 + 1 个旧）没人管

    7.2 三种经典发布策略¶

    三种策略的核心差异 = 切换流量时的新旧版本并存方式，决定了爆炸半径、资源成本、回滚速度。

    7.2.1 滚动发布（Rolling Update）¶

    图 7-1：滚动发布示意

    初始状态：10 个 V1 Pod 处理 100% 流量
  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│
  └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
          ↓ 逐步替换（每次换 2 个）
  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  │V2│ │V2│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│ │V1│
  └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
          ↓ 继续替换
  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
  │V2│ │V2│ │V2│ │V2│ │V2│ │V2│ │V2│ │V2│ │V2│ │V2│
  └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
最终状态：10 个 V2 Pod 处理 100% 流量

    K8s 配置：

    # K8s Deployment（滚动发布，默认策略）
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2        # 最多同时起 2 个新 Pod（超出期望副本数的量）
      maxUnavailable: 0  # 最多不可用 0 个（先起新的再停旧的，零停机）

    特点：
    - ✅ 零额外资源（maxSurge=2 只需多 2 个 Pod 量）
    - ✅ K8s 默认，零配置
    - ⚠️ 新版本有问题时，可能已经有部分用户切到 V2 了（爆炸半径 20%）
    - ⚠️ 新旧版本并存期间，API 兼容性要求高（同时有 V1 V2 响应）

    7.2.2 蓝绿发布（Blue/Green / Red/Black）¶

    图 7-2：蓝绿发布示意

    初始状态：蓝环境（V1）10 个 Pod 处理 100% 流量
  LB ──→ 蓝(V1) × 10     绿（未启动）
          ↓ 部署绿环境
  LB ──→ 蓝(V1) × 10     绿(V2) × 10（跑内部验证，无公网流量）
          ↓ 验证通过，LB 一刀切换
  LB     蓝(V1) × 10     绿(V2) × 10 ←── 100% 流量（秒级切换）
          ↓ 稳了就停蓝环境
         （保留蓝做回滚候选，10 分钟后关）

    流程：
    1. 绿环境（V2）完整部署好（和蓝环境相同副本数），零流量
    2. 在绿环境跑内部 E2E + 冒烟测试
    3. 验证通过 → LoadBalancer 把流量 100% 切绿
    4. 稳了就关蓝环境；出问题就 LB 切回蓝（秒级）

    特点：
    - ✅ 回滚最快（LB 切回，秒级）
    - ✅ 新旧不并存，无 API 兼容性问题
    - ❌ 需要两倍资源（蓝 + 绿），成本最高
    - ❌ 全量切换 = 新版本有问题就 100% 用户受影响（爆炸半径最大）

    7.2.3 金丝雀发布（Canary / Incremental Rollout）¶

    图 7-3：金丝雀发布示意

    1% 流量 → 金丝雀(V2) × 1     99% 流量 → 生产(V1) × 99
   ↓ 观察 30 分钟，无异常
5% 流量 → 金丝雀(V2) × 5     95% 流量 → 生产(V1) × 95
   ↓ 观察 30 分钟，无异常
20% 流量 → 金丝雀(V2) × 20   80% 流量 → 生产(V1) × 80
   ↓ 观察，无异常
100% 流量 → 生产(V2) × 100   停 V1

    典型流量阶梯：1% → 5% → 20% → 50% → 100%（每个阶段观察 15-30 分钟）

    实现方式：
    - 简单版：通过 K8s Service 下不同版本 Pod 的副本数比例实现流量分配（不精确但不用额外组件）
    - 专业版：用 Service Mesh（Istio / Linkerd）按用户 ID、地区、Header、Cookie 等精确切流量
    - 专业版工具：Argo Rollouts / Flagger（专门做金丝雀发布的 Operator）

    特点：
    - ✅ 爆炸半径最小（1% 先出问题，99% 用户不受影响）
    - ✅ 可精确控制流量、可按用户灰度
    - ⚠️ 发布时间最长（1% 观察完才能继续推进）
    - ⚠️ 需要流量治理组件（Istio / Argo Rollouts），运维成本高

    7.2.4 三种策略对比与选型¶

    表 7-1：三种发布策略对比

    维度 滚动发布 蓝绿发布 金丝雀发布
    额外资源 0 ~ maxSurge 量 2×（两套完整环境） 1% ~ 逐步增量
    回滚速度 中（滚动回退，需分钟级） 最快（LB 秒级切换） 中（切回 V1 副本数，分钟级）
    爆炸半径 中（maxSurge 量） 最大（100% 同时切） 最小（1% 起步）
    发布时间 快（和副本数成正比） 中（部署绿环境 + 切流量） 最慢（多阶段观察）
    API 兼容性要求 高（新旧并存） 低（不并存） 高（长期并存）
    运维复杂度 极低（K8s 默认） 低 高（需流量治理组件）
    2026 推荐度 ⭐⭐⭐⭐（大多数场景） ⭐⭐⭐（对 API 不兼容的情况） ⭐⭐⭐⭐⭐（生产高要求场景）

    选型建议：

    团队/业务特征 推荐策略
    小团队起步、业务要求不高 滚动发布（K8s 默认，零成本）
    发布窗口紧 + API 经常不兼容 蓝绿发布（一刀切换，秒级回滚）
    核心业务、生产稳定性要求高 金丝雀发布（1% 起步，最小爆炸半径）
    有 Service Mesh 能力 金丝雀（Argo Rollouts + Istio 自动化灰度）

    你的 P1.3 实践（四个环境手动 merge 晋升）+ 滚动发布 是小团队的合理组合。等团队规模大了之后，把 prod 的滚动发布升级成金丝雀发布，就很稳了。

    7.2.5 Argo Rollouts 生产级金丝雀示例（带 Prometheus 自动分析）¶

    参考来源：Argo Rollouts 官方文档 argoproj.github.io/argo-rollouts + 掘金《云原生宕机上线的秘密：Argo Rollouts 金丝雀发布实战》+ CSDN Argo Rollouts Canary 基础。

    什么时候值得引入 Argo Rollouts：
    - 手动滚动发布每次发版都要盯着监控看 30 分钟，太费人力
    - 核心业务 > 30+ 服务，每个发版日 5+ 个服务要上线
    - 爆炸半径要求严格（>1% 出问题就不能接受）

kind: Deployment

  name: myapp
  namespace: production
  labels:
    app: myapp
    version: v1.2.3       # 版本号，和镜像 tag 对应
spec:
  replicas: 3
  revisionHistoryLimit: 5  # 保留最近 5 个历史 ReplicaSet，回滚用

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 每次多起 1 个新 Pod
      maxUnavailable: 0   # 不可用 Pod 数 0 → 先起新的再停旧的，零停机

  selector:
    matchLabels:
      app: myapp

  template:
    metadata:
      labels:
        app: myapp
        version: v1.2.3
    spec:
      # 6.2.3 运行时安全加固
      securityContext:
        runAsNonRoot: true
        runAsUser: 65532   # distroless nonroot 的 uid
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]

      containers:
        - name: myapp
          image: registry.example.com/mygroup/myapp:v1.2.3
          imagePullPolicy: IfNotPresent

          # 资源限制（防止单个 Pod 吃光节点）
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "2"
              memory: "1Gi"

          # 端口暴露
          ports:
            - containerPort: 8080
              name: http

          # 临时可写目录（只读 FS 模式下 /tmp 需可写）
          volumeMounts:
            - name: tmp
              mountPath: /tmp

          # === 三类探针（7.3.3 详解） ===
          # 1. 启动探针：防止慢启动应用被 Liveness 误杀（FastAPI 启动快，10 秒足够）
          startupProbe:
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 30
            periodSeconds: 2

          # 2. 就绪探针：通过了才把 Pod 加入 Service（流量切进来）
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
            failureThreshold: 3

          # 3. 存活探针：不通过就重启 Pod（服务死锁/卡死场景）
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 30
            failureThreshold: 3

          # 从 ConfigMap / Secret 读配置，不要写死在镜像里
          envFrom:
            - configMapRef:
                name: myapp-config
            - secretRef:
                name: myapp-secret

      # 优雅停机：发 SIGTERM 后给 60 秒处理完请求再杀
      terminationGracePeriodSeconds: 60

      volumes:
        - name: tmp
          emptyDir: {}

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:

    matchLabels:

    # Horizontal Pod Autoscaler：根据 CPU 使用率自动扩缩副本数
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 3           # 最小 3 个（保证高可用）
  maxReplicas: 20          # 最大 20 个（防峰值打爆）
  metrics:
    # 按 CPU 使用率扩缩（Deployment 的 request=500m，这里 60% = 300m 触发扩容）
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
    # 还可以按内存、QPS、自定义指标（如 Prometheus 业务指标）扩缩
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

    扩缩容原理：
    - 每 15 秒 HPA 查一次当前平均 CPU 使用率
    - 60% 以上 → 增加 Pod，直到使用率回落或到达 maxReplicas
    - 30% 以下且持续 5 分钟 → 减少 Pod，直到 minReplicas
    - 缩容有冷却期（默认 5 分钟），防止抖动

    7.3.3 三类探针 + 自动回滚¶

    三类探针职责与触发时机：

    探针 什么时候开始检查 不通过的后果 目的
    StartupProbe（启动） Pod 启动后立刻查，最长 30×2=60 秒 超时仍不通过就重启 Pod 保护慢启动应用不被 Liveness 误杀
    ReadinessProbe（就绪） StartupProbe 通过后每 10 秒查 不通过就把 Pod 从 Service Endpoints 里摘下来，流量不切它 滚动发布的关键：新 Pod Ready 了才停旧 Pod
    LivenessProbe（存活） StartupProbe 通过后每 30 秒查 连续 3 次不通过就重启 Pod 处理死锁、GC 卡顿等"进程活着但服务不可用"场景

    顺序：Startup → Readiness/Liveness。没有 StartupProbe 时，Liveness 从 initialDelaySeconds 之后开始查。慢启动应用必须配 StartupProbe，否则会被反复重启。

    自动回滚机制：

    # 在 Deployment 的 progressDeadlineSeconds 里配置
spec:
  progressDeadlineSeconds: 300  # 5 分钟内滚动发布没完成就标记失败 → 自动回滚
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

    触发条件：5 分钟之内，新 Pod 还没全部 Ready + 旧 Pod 还没全部停掉 → K8s 认为部署失败，自动 kubectl rollout undo 回滚到上一个 Revision。

    手动回滚命令：kubectl rollout undo deployment/myapp --to-revision=3（回到第 3 个历史版本）。Revision 列表用 kubectl rollout history deployment/myapp 查看。

    参考来源：Kubernetes 官方生产就绪指南 + 2025-2026 社区总结的 K8s 部署踩坑清单。

    把下面这张表打印出来，每次有新项目上生产时一项一项勾：

    类别 检查项 为什么必须配 勾
    高可用 replicas >= 3 单副本 = 单点故障，节点维护或 Pod 重启时服务就没了 ☐
    PodDisruptionBudget（PDB）minAvailable >= 2 节点维护/驱逐时，K8s 会先起新 Pod 再停旧的，不会全杀 ☐
    topologySpreadConstraints 跨节点分布 3 个 Pod 都跑到同一个节点上 = 单点故障。强制 Pod 分散到不同节点 ☐
    资源 resources.requests 和 resources.limits 都配了 没 requests 调度器不知道放哪；没 limits 单个 Pod 可能吃光节点 CPU/内存 ☐
    CPU requests ≈ limits 的 1/3 ~ 1/2 CPU 是可压缩资源，超卖一点没问题；requests 给太小会导致调度不合理 ☐
    内存 requests = limits（几乎相等） 内存不可压缩，超卖会触发 OOM Kill，Pod 随机被杀；建议内存 requests/limits 设成一样 ☐
    探针 三类探针都配了（Startup + Readiness + Liveness） 少 Startup 慢启动被误杀；少 Readiness 新 Pod Ready 前就进流量；少 Liveness 死锁不重启 ☐
    progressDeadlineSeconds = 300 滚动发布超时自动回滚，防止卡半小时还在挂着 ☐
    安全 Pod 级 securityContext.runAsNonRoot: true 即使 Dockerfile USER 写了，K8s 层面再卡一道，防止有人改 Dockerfile 忘加 ☐
    readOnlyRootFilesystem: true + /tmp 挂 emptyDir 防止攻击者写入恶意文件；需要可写的目录（/tmp、缓存）单独挂 volume ☐
    capabilities.drop: [ALL] 去掉所有 Linux 能力，最小权限原则 ☐
    版本 revisionHistoryLimit >= 5 保留至少 5 个历史 ReplicaSet，出问题时 kubectl rollout undo 才有东西可以回 ☐
    imagePullPolicy: IfNotPresent（不要写 Always） Always 每次重启都重新拉镜像，镜像仓挂了会导致 Pod 起不来；IfNotPresent 本地有就用本地 ☐
    terminationGracePeriodSeconds = 60 给应用 60 秒处理完正在处理的请求（优雅停机），默认 30 秒对长请求不够 ☐
    配置 配置从 ConfigMap / Secret 读，不写死在镜像里 DB 密码、第三方 API Key 等不能打在镜像里（镜像仓随便谁都能拉下来看） ☐
    image: tag 不要用 latest latest 不可追溯，回滚都不知道回哪个（这个前面 6.2.4 已经强调了，这里再提醒） ☐

    最小化起步版（小团队资源不够时）：上面 17 项不全做也能跑，但最少要勾以下 8 项：replicas>=3 + PDB + resources 全配 + ReadinessProbe + LivenessProbe + runAsNonRoot + 不用 latest + 配置不写死。其他项等有空了补上。

    场景 commit 关系图（新→旧） 推荐操作 其他开发者受影响吗？
    MR 还没合并，发现功能不要了 —— GitLab UI 直接 Close MR ❌ 无
    已合并到 main，功能独立无依赖，90% 的场景 D(功能C) → C(功能B) → B(功能A 错误) → A(基线) ① git checkout main && git pull ② git revert <B> ③ push → 生成反向 commit，功能 B/C 的历史保留 ❌ 不用重提 MR，pull 一下即可
    已合并 + 后续功能依赖 A 的代码（有交叉） D(C用到A) → C(B用到A) → B(功能A 有严重问题) → A ① 先 git revert B ② 冲突点手动解（保留A的辅助函数，只删业务逻辑）③ 补 1~2 个小修复 commit ❌ 不用重提 MR（只需几十分钟修复冲突）
    已合并 + A 有严重安全问题/污染DB，必须从历史抹掉（CRITICAL，极少用） 同上 用 git rebase --onto A B D（等价 reset + cherry-pick C/D）→ git push --force-with-lease origin main，然后通知大家 git fetch && git reset --hard origin/main 对齐本地 main ⚠️ 不用重开发代码，但所有人本地 main 强制对齐一次

    铁律：
    1. 禁止 git push --force，只能 --force-with-lease：--force 不管远端当前状态直接覆盖，--force-with-lease 只有远端和你本地看到的 HEAD 一致时才成功，防止同事刚推的新代码被冲掉。
    2. revert 是 90% 场景的首选；rebase --onto 只在 CRITICAL 安全问题才用，且必须提前群里通知所有人。
    3. 如果 B 是 Merge Commit（MR squash 后的合并 commit），git revert -m 1 <merge-commit> 选主分支 parent 做反向。

    经典事故复盘（main 回退操作不当触发的线上故障）统一收录于 7.9.5。

    7.5 Feature Flag 灰度与熔断¶

    完整的 Feature Flag 分类、工具选型、落地示例参见 S7 Feature Flag 解耦部署。本节聚焦和部署策略的配合。

    7.5.1 Release Flag 与发布解耦¶

    核心思想：功能上线和代码部署解耦——部署了新代码，功能默认关着（Flag=False），随时可以用管理后台开关（不改代码、不重新部署）。

    表 7-4：Feature Flag 四种类型（S3 速览）

    类型 生命周期 例子 是否长期留代码里
    Release Flag（发布开关） 短期（发布后 2-4 周删） new-checkout-ui：新结账页上线开关 ❌ 用完就删，不要留技术债
    Experiment Flag（实验开关） 短期（A/B 测试结束就删） search-algorithm-v2：新算法和旧算法 A/B 对比 ❌ 实验结束删
    Ops Flag（运维开关） 长期 disable-heavy-report：大促时临时关重型报表接口保核心 ✅ 长期保留
    Kill Switch（总闸） 长期 order-service-enabled：订单服务一键熔断 ✅ 长期保留

    和发布策略的配合：

    • 蓝绿发布：切换前 Feature Flag 全关 → 切流量后，先开 1% → 5% → 观察 → 全开
    • 金丝雀发布：金丝雀流量里的用户 Feature Flag 先开 → 观察没问题 → 扩大流量 + 扩大 Flag 范围
    • 滚动发布：用 Flag 控制功能可见性，即使新版本已经跑在生产，功能默认关着 → 逐步开

    关键收益：把"部署"和"功能上线"两件事拆开。部署失败就回滚镜像（P1.3 回滚旧 Tag），功能出问题就关 Flag（秒级，不用重新部署）。双重保险。

    7.5.2 灰度策略¶

    灰度方式 说明 典型场景 实现复杂度
    按百分比 1% → 5% → 20% → 50% → 100% 逐步放量 通用功能灰度 低（随机数取模）
    按用户 ID 用户 ID 尾号在某个范围内的用户开 Flag B 端指定客户先上 中（需要用户 ID）
    按地区 / 机房 上海机房先开，没问题再开其他 多地域发布 中（地区标识）
    按员工 / 白名单 内部员工先试用（Dogfood） 风险大的新功能 低（邮箱/ID 白名单）
    按租户 / 企业 SaaS 场景下指定租户先开 大客户定制化 中（租户标识）

    Release Flag 灰度完 100% 后，立刻把 Flag 代码删掉，不要留。半年后代码里遍布"永远为 True 的 Flag"是巨大技术债。

    7.5.3 Kill Switch（一键关功能）与熔断¶

    和 Release Flag 不同，Kill Switch 是长期保留的总闸，用于应对突发场景：

    场景举例：
  1. 大促流量峰值到来，关非核心接口保核心链路
     Kill Switch: disable-non-critical-features = True

  2. 第三方支付接口大面积超时
     Kill Switch: payment-channel-A-enabled = False（自动切到通道 B）

  3. 新上线的大查询接口把 DB 打挂了
     Kill Switch: big-report-enabled = False（秒级止损）

    和 K8s 自动回滚的区别：
    - K8s 自动回滚 = Pod 级别（服务整体有问题时回滚）
    - Kill Switch = 功能级别（只有某个接口/功能有问题时关那个功能，其他不受影响，爆炸半径最小）

    最佳实践：每个重要的外部依赖、每个重型功能，都配一个 Kill Switch。出问题先关 Flag 止损，再查根因。

    7.5.4 Unleash 开源 Feature Flag 落地要点（真实生产踩坑补遗）¶

    参考来源：Unleash 官方文档（CNCF 毕业级 Feature Flag 开源项目）+ 头条《feature flag 这套东西，我们在生产用了快两年的总结》+ 掘金开源项目推荐。

    为什么选 Unleash（2026 开源 Feature Flag 第一选择）：
    - 完全开源：核心服务端 + 所有 SDK 都是 Apache 2.0 协议，免费商用无限制
    - 客户端 SDK 丰富：Python/Java/Go/Node.js 全覆盖（Python 有官方 SDK），Lua 社区版也有
    - 性能优秀：Flag 规则在客户端 SDK 内存里本地计算，判断开关不产生网络请求
    - 管控界面友好：自带 UI 管理开关、灰度规则、Kill Switch，不用自己写管理后台

    Unleash 架构速览（小团队一台 2C/4G 机器就能跑）：

                        ┌─────────────────────┐
                    │   Unleash Server    │  ← 管理 UI + Flag 持久化（PostgreSQL）
                    │  + PostgreSQL DB    │
                    └─────────┬───────────┘
                              │ 每 30 秒拉一次全量 Flag 配置（HTTP）
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌───────────────┐    ┌───────────────┐    ┌───────────────┐
│  Python SDK   │    │  Java SDK    │    │  Frontend SDK │
│  (FastAPI)    │    │  (Spring)    │    │  (React/Vue)  │
└───────────────┘    └───────────────┘    └───────────────┘
   内存里存所有 Flag → 判断 isEnabled("new-ui") = True/False → 无网络请求

    Python FastAPI 集成示例（代码语言符合你的偏好）：

    # app/main.py（FastAPI + Unleash Python SDK）
from UnleashClient import UnleashClient
from fastapi import FastAPI, Request

# 应用启动时初始化 Unleash（只初始化一次）
app = FastAPI()

@app.on_event("startup")
def init_unleash():
    # URL：你的 Unleash Server 地址；API Token：Unleash UI 里给后端的 Client Token
    global unleash
    unleash = UnleashClient(
        url="http://unleash.internal.example.com/api",
        app_name="order-service",        # 每个服务有自己的 app_name（用于细粒度统计）
        custom_headers={"Authorization": "Bearer *:unleash-client-token-xxx"},
        cache_directory="/tmp/unleash",
        refresh_interval=30,              # 每 30 秒拉一次最新 Flag 配置
    )
    unleash.initialize_client()

# ===== 用法 1：Release Flag（发版开关，短期用完就删） =====
@app.get("/api/v1/orders")
def get_orders(request: Request, user_id: str):
    # 按用户 ID 灰度：前 5% 的用户先看到新版订单页
    if unleash.is_enabled("new-order-page",
                         userId=user_id):          # userId 用于按比例/白名单切
        return render_new_order_page()             # 新版逻辑
    else:
        return render_old_order_page()             # 旧版逻辑（兜底）

# ===== 用法 2：Kill Switch（长期保留，一键熔断） =====
@app.post("/api/v1/heavy-report")
def generate_heavy_report():
    # 大促流量高峰，关重型报表接口保核心链路
    if unleash.is_enabled("disable-heavy-report", default=False):
        return {"error": "Heavy report disabled, try again later"}, 503

    # 正常逻辑：查 DB + 聚合计算 + 生成报表（可能 20 秒 + 吃大量 CPU）
    return generate_report_logic()

    Unleash 的 4 个生产使用要点（头条内部踩坑总结）：

    1. Release Flag 必须加「到期时间 + TODO 清理」：
    2. 开 Flag 时就在代码里加注释：# TODO: 2026-08-20 删除 new-order-page Flag（灰度完 100%）
    3. 超过到期时间 Flag 还在代码里，CI Lint 任务报错，强制开发者清理

    4. 头条的经验：超过半年的 Feature Flag 90% 永远都是 True，变成了没人敢删的技术债

    5. 不要滥用 Flag：一个版本最多 3-5 个 Release Flag，否则开关组合爆炸，测试覆盖不全

    6. 反例：一个版本开了 10 个 Flag，组合数 = 2^10=1024 种，测试不可能测全

    7. 正确做法：只给「有风险的大改动」加 Flag；小改直接合入、直接部署

    8. Kill Switch 默认值一定要是 False（关闭状态 = 功能正常用）：

    9. 如果默认值是 True，Unleash Server 挂了或 SDK 没连上，整个功能就直接不可用了

    10. unleash.is_enabled("disable-heavy-report", default=False) → 默认 False = 不关，出问题再手动开 True

    11. 和你的 P1.3 Tag 发版机制配合：

    12. Flag 默认值在代码里设好（dev/test 环境默认 False）
    13. stage 环境打 Tag 前，在 Unleash UI 里先把 stage 环境的 Flag 调成 True，跑 UAT
    14. prod 打 Tag 发版后，Flag 默认还是 False → 先在 Unleash UI 按 1% → 5% → 20% 逐步调大
    15. 100% 全部开启后，下个版本把 Flag 代码删除

    小团队简化版：如果只有 2-3 个服务、暂时不想部署 Unleash，用「K8s ConfigMap + 应用代码读 + 热更新」也能实现 60% 的功能；等 Flag 数量 > 10 个或需要按用户/地域灰度时再上 Unleash 不晚。

    7.5.5 Feature Flag 分层实现方案（低侵入组合策略，精简结论）¶

    完整 Feature Flag 分类、工具选型、生命周期管理参见 S7 Feature Flag 解耦部署，本节聚焦分层实现方案。

    核心原则：改动粒度越粗 → 越往上/左层放（0 代码入侵）；改动越细 → 越往下/右层放（少量入侵）。不要试图一种方案覆盖所有场景。

    四层架构（从上到下 = 从粗到细）：

    用户请求 → Nginx/OpenResty（粗粒度） → Gateway/Lua（中粒度）→ 应用层自建最小if-else（细粒度）→ Unleash专业平台（全局管理+报表）

    四层能力对比表（选哪层一目了然）：

    维度 Nginx / OpenResty 分流 Gateway / Lua 按 user_id 分流 应用层最小自建（ConfigMap + 200行模块） Unleash 专业平台
    不入侵代码 ✅✅ 0 入侵 ✅ 0 入侵应用代码 ❌ 每个 Flag 写 1 行 if ❌ 同样写 if，但 SDK 标准化
    整接口/整服务切新版 Pod ✅ ✅ ❌ ❌
    按 user_id/租户/白名单百分比切流量 ❌ ✅（Lua + Redis 存规则） ✅（Python/Java 本地哈希取模） ✅✅（多条件组合）
    函数级/逻辑段级开关（只关优惠券，不关查用户+下单） ❌ ❌ ✅ ✅
    Kill Switch（秒级关某段逻辑） ⚠️（需拆微服务+独立 upstream） ⚠️（同左） ✅（改 ConfigMap，可选热更新） ✅✅（管理后台点按钮，SDK 30s 内生效）
    管理后台/产品自操作 ❌（改配置文件） ⚠️（产品同学不会改 Redis） ❌（kubectl 改 ConfigMap） ✅✅
    新增组件 0（已有 Nginx） Redis 存规则（或 ConfigMap） 0（用现有 K8s ConfigMap） Unleash + PostgreSQL
    小团队起步推荐度 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐（已有 Gateway/Lua 才推荐） ⭐⭐⭐⭐⭐（最推荐起步） ⭐⭐（Flag>20 或产品要自操作）

    OpenResty（Nginx+Lua）按 user_id 百分比分流核心伪代码（不入侵应用代码，用户ID级切）：

    -- access_by_lua：解 user_id → Redis 读规则 → 选 upstream
local red = require "resty.redis":new()
red:connect("127.0.0.1", 6379)
local user_id = ngx.var.cookie_user_id or ngx.req.get_headers()["X-User-Id"]
local flag = "new_order_page"
local enabled = red:get("feature:" .. flag .. ":enabled") == "1"
if enabled and user_id then
    local pct = tonumber(red:get("feature:" .. flag .. ":percentage") or "0")
    if ngx.crc32_short(flag .. ":" .. user_id) % 100 < pct then
        ngx.var.upstream = "upstream_new_app"   -- 切到新版 Deployment
        return
    end
end
ngx.var.upstream = "upstream_old_app"

    落地建议（针对你的小团队 + Python FastAPI + 低侵入诉求）：
    1. 粗/中粒度（整接口、整服务按 user_id 切） → Nginx / Gateway Lua 方案，0 代码入侵
    2. 细粒度（Kill Switch 关某段逻辑、单函数级开关、弹窗差异化） → 应用层最小 200 行自建模块 + ConfigMap 热更新，入侵量极低（完整自建模块代码模板参见 S3 专题的『最小自建方案』章节）
    3. 两个版本周期内人工观察清理 Flag，Unleash 专业平台等出现「Flag>20 个 + 产品/运营要自操作开关」两个信号再部署，之前成本远大于收益
    4. 升级路径平滑：未来把 Redis/ConfigMap 换 Unleash SDK 即可，分层结构不动

    Flag 生命周期管理踩坑（过期 Flag 变技术债、组合爆炸测试覆盖不全等）统一收录于 7.9.2。

    stage 人工确认的 3 个价值（你之前总结的）：
    1. 防误推：test 过了但还没准备好上 stage，CI 不会自动推
    2. 业务窗口：发版窗口期到了，人才点按钮（业务低峰期发布）
    3. 合规审计：谁、什么时候、在什么条件下点的 stage，GitLab 全留痕

    7.6.4 纯 Docker / Docker Compose / Swarm 部署（小团队不养 K8s 方案）¶

    适用场景：<3 个核心服务、单/双物理机、团队无专职 SRE/K8s 运维知识储备。不追求 100% 云原生能力，够用 + 低成本为第一优先级。你的 P1.3 四段晋升机制、Feature Flag、Cosign 验证完全不受部署平台影响，Deploy 阶段把 kubectl 换成下面三种命令即可。

    方案一：Docker Compose（单机部署，最推荐起步）¶

    部署结构：1 台 4C/8G 机器就能跑 3~5 个服务。所有服务用 compose.yml 定义版本 + healthcheck，dev/test/stage/prod 四个环境分别 4 套 compose.yml（或一个 compose.yml + .env 区分）。

export NEW_TAG=v1.2.4 && docker compose -f docker-compose.prod.yml up -d --scale myapp=2 --no-recreate myapp

# Nginx upstream 里把 myapp:8000（docker DNS 自动轮询两容器）流量都接入了
# 最后停旧的（--scale 回 1，compose 会保留新的那个）
export NEW_TAG=v1.2.4 && docker compose -f docker-compose.prod.yml up -d --scale myapp=1 myapp

    蓝绿发布（零停机 + 秒级回滚）：两套 compose 项目 + 一套 Nginx。蓝 100% 流量时绿起容器跑内部验证，Nginx 改一行配置 reload 秒切。回滚时反向改回来即可。

    运维复杂度 ⭐ 0 门槛 ⭐⭐ 半天学会 ✅ 扛得住

    7.7 数据库迁移与 Expand-Contract 模式¶

    完整的 DB 迁移对比、Expand-Contract 步骤图、常见工具参见 S6 数据库迁移。本节聚焦和部署流程的配合。

    7.7.1 为什么 DB 变更不能和部署强绑定¶

    反例（踩坑无数）：
  部署 Job 里：先跑 DB Migration → 再部署新代码
  → DB Migration 把表结构改了（比如删了某列）
  → 部署新代码的过程中（滚动发布，还有一半老 Pod 在跑）
  → 老代码写 DB 时用了被删的列 → 报错 → 5xx
  → 因为滚动发布时新旧代码并存，DB 改了两边都受影响

    核心原则：DB 迁移永远向前兼容。任何一次 Migration 跑完后，新旧两版代码都要能正常跑（因为滚动发布期间两者并存）。

    7.7.2 Expand-Contract 三步法（迁移不停服）¶

    表 7-5：Expand-Contract 模式示意（例：用户表加 phone 字段替换旧的 mobile 字段）

    阶段 动作 DB Migration 代码版本 兼容性
    Step 1：Expand（扩，部署前执行） 加新列 phone、加双写逻辑、旧列 mobile 不删 ALTER TABLE users ADD COLUMN phone VARCHAR(20); V1（老代码）+ V2.1（双写代码）同时跑 ✅ 兼容
    Step 2：Transition（转，持续一段时间） 后台 Job 把历史 mobile 的数据回填到 phone，所有读都先读 phone 再 fallback mobile （不跑新 Migration） V2.1 → V2.2（只读 phone，双写保留） ✅ 兼容
    Step 3：Contract（缩，确认没问题后） 删双写逻辑 + 删旧列 mobile ALTER TABLE users DROP COLUMN mobile;（单独一个发版周期） V3（只用 phone） ❌ 和 V1 不兼容，但此时线上全是 V2.2+

    关键：Step 1 和 Step 3 不要放在同一个发版周期。Step 1 过 1-2 周确认没问题了，Step 3 单独一个发版做收缩。

    7.7.3 Flyway / Alembic 在 CI 中的执行时机¶

    正确的执行顺序（任何时候都保持 DB 向前兼容）：

    1. 合入 test 分支 → CI Job 跑 DB Migration（test 库）
   ↓ 部署应用到 test（代码是双写版）
   ↓ 测试跑（确认新旧代码都兼容）

2. 合入 stage 分支 → CI Job 跑 DB Migration（stage 库）
   ↓ 部署应用到 stage（双写）
   ↓ UAT 跑

3. 合入 main 分支（不发布）
   ↓ 打 Tag 发布 prod
   ↓ 先跑一个专门的 DB Migration Job（prod 库！单独一个 Job，before_script 连 prod DB）
   ↓ Migration 成功后，才跑 deploy:prod 滚动发布

    重点：prod 的 DB Migration 是单独一个 Job，不和部署写在同一个 script 里。出了 Migration 失败就停，不要继续部署代码。Migration 成功了再 deploy。

    工具选型（S5 展开）：Python → Alembic，Java → Flyway / Liquibase，Node → Prisma。原理一样，都走 Expand-Contract。

    7.7.4 Expand-Contract 生产踩坑与大表处理（真实事故复盘）¶

    参考来源：Flyway 官方数据库迁移最佳实践 + Alembic 生产迁移常见问题 + 2026 各厂 DBA 内部复盘。

    Expand-Contract 理论简单，但真实生产踩坑非常多。下面几条都是「至少出过一次线上事故」才沉淀下来的经验：

    踩坑 1：Step 1 Expand 和 Step 3 Contract 放在同一个发版周期 → 回滚不了（最常见事故）

    反例事故：
v1.2.0 版本同时包含：①加 phone 列 + 双写（Step1 Expand）②删 mobile 列（Step3 Contract）
  → 发布后发现 phone 字段写入逻辑有 bug（比如区号没加）
  → 想回滚 → v1.1.0 的代码读 mobile 列，但 Contract 已经把 mobile 列删了
  → 回滚后老代码直接报「列不存在」→ 全量 5xx

    正确做法（铁律，不要破）：Step 1 Expand 和 Step 3 Contract 之间至少隔 1-2 个发版周期（建议 2 周以上），确认 Expand 的双写、读逻辑都跑稳了，独立一个发版再做 Contract。

    踩坑 2：双写时「以哪一列为准」没想清楚 → 数据不一致

    Expand 的双写阶段（Step 1 + Step 2 Transition），写操作同时写 phone 和 mobile 两列。但如果某一次写入时 phone 成功、mobile 失败（比如 DB 唯一索引冲突只影响一列），或者旧代码跑的时候只写了 mobile，数据就不一致了。

    必须明确「读哪一列 + 冲突时谁覆盖谁」：

    # 正确的双写逻辑（Python 伪代码）
def update_user_phone(user_id, new_phone):
    # 写：两列都写，phone 先写（phone 最终为准）
    update_sql = "UPDATE users SET phone = :new_phone, mobile = :new_phone WHERE id = :id"
    db.execute(update_sql, {"new_phone": new_phone, "id": user_id})

def get_user_phone(user_id):
    # 读：优先读 phone（新列），phone 空的话 fallback 到 mobile（旧列回填）
    row = db.query("SELECT phone, mobile FROM users WHERE id = :id", {"id": user_id}).first()
    if row.phone:
        # 新列有值 → 直接返回
        return row.phone
    elif row.mobile:
        # 新列空但旧列有值 → 数据是 Expand 之前就有的，顺手回填一下新列
        db.execute("UPDATE users SET phone = :mobile WHERE id = :id", {"mobile": row.mobile, "id": user_id})
        return row.mobile
    else:
        return None

    读的时候顺便回填（lazy repair），比专门跑回填任务方便，缺点是如果某条数据长期没人读就不会被修。所以 Transition 阶段最后还要跑一个全量数据对账 Job（每晚跑一次），把「phone != mobile」的行全部找出来，以 phone 为准覆盖 mobile 或反之。

    踩坑 3：大表（千万级/亿级）直接 ALTER TABLE 加列 → 锁表 30 分钟，写请求全卡住

    MySQL/PostgreSQL 对大表直接 ALTER TABLE ... ADD COLUMN 不同版本行为差异很大：
    - MySQL 5.6/5.7 以前：加列会锁表，期间所有写入被阻塞，千万级表可能锁 30 分钟以上
    - MySQL 8.0 +：Instant DDL 支持秒级加列（仅部分场景），但有条件（加的列必须是最后一列、无默认值或默认值是字面量常量）
    - PostgreSQL 11+：加有默认值的列会重写全表；加无默认值的列是秒级（只是元数据变更）

    大表加列的正确做法（不管什么数据库，最稳妥的通用方案）：

    数据库 方案 工具
    MySQL 用「在线加列工具」，不锁表，后台慢慢拷数据 pt-online-schema-change（Percona Toolkit）或 gh-ost（GitHub 出品）
    PostgreSQL 加列时分两步：①先加无默认值的列（秒级）；②后台分批回填默认值；③确认数据都回填完了，最后把列改成 NOT NULL（如果需要） 自己写 Python/Shell 脚本分批 UPDATE，每批 1000 行，每批之间 sleep 1 秒让其他写入有机会跑
    通用 用 CDC 工具（Canal / Debezium）监听 binlog，把旧表数据实时同步到新表，最后切读流量到新表 代价高但对业务完全无感，适合百亿级超大表

    Alembic（Python）+ pt-online-schema-change 真实生产配置（给你的 Python 项目参考）：

    # alembic.ini（配置 pt-online-schema-change 作为大表迁移工具）
# 迁移大表时不用默认的 op.add_column()，用 op.execute() 直接调用 pt-osc
[alembic]
script_location = alembic

    # alembic/versions/20260803_add_phone_column_xxx.py（大表加 phone 列）
from alembic import op
import sqlalchemy as sa

def upgrade():
    # users 表有 2000 万行，直接 ALTER 会锁表
    # 用 pt-online-schema-change 在线加列：创建影子表 → 拷数据 → 切表
    op.execute("""
        pt-online-schema-change
            --alter="ADD COLUMN phone VARCHAR(20) NULL COMMENT '用户手机号(Expand阶段)'"
            --chunk-size=1000
            --max-lag=1s
            --recursion-method=processlist
            h=mysql-prod.example.com,D=appdb,t=users
            --execute
    """)

def downgrade():
    # 回滚也用 pt-osc，不要直接 DROP COLUMN
    op.execute("""
        pt-online-schema-change
            --alter="DROP COLUMN phone"
            --chunk-size=1000
            h=mysql-prod.example.com,D=appdb,t=users
            --execute
    """)

    小表（< 100 万行）直接 ALTER 没问题；100 万 ~ 1000 万行看业务流量，低峰期直接 ALTER 也行；1000 万行以上必须用在线加列工具，不要拿运气赌生产稳定性。

    Expand-Contract 最严重的三大真实生产事故复盘（Step1+Step3 同周期 → 回滚变 5xx / 双写准星未定 → 数据不一致 / 大表直接 ALTER → 锁表 30 分钟）完整过程 + 修复命令 + 事故后 RTO 指标对比，统一收录于 7.9.1。知识性流程（三步法）保留在本小节 7.7.2~7.7.3，7.9.1 只放踩坑（事故+解）。

    7.9.1 Expand-Contract 三大生产事故复盘（对应 7.7.4）¶

    事故 1：Step 1 Expand + Step 3 Contract 放同一版本 → 回滚直接全量 5xx（爆炸半径 100%）¶

    事故过程：v1.2.0 同时做了 ①加 phone 列 + 双写（Step 1 Expand）和 ②删 mobile 列（Step 3 Contract）。发布 15 分钟后发现 phone 写入逻辑漏加国际区号，想回滚 v1.1.0，结果 v1.1.0 代码只认 mobile 列，但 Contract 已经把 mobile 删了 → 所有用户读写手机字段的请求直接 Unknown column 'mobile' → 订单/用户中心全挂。

    为什么回滚不了：Contract 已经 DROP COLUMN 了，DB 结构不可逆，老代码就算拉起来也直接报列不存在，相当于「新版本有 bug + 老版本跑不了 + DB 改不回去」。

    修复命令（RTO ≈ 38 分钟，复盘时算二级事故 P1）：

    -- Step 1：立刻把 mobile 列加回来（只能加 NULL，数据已丢，需要用备份回填）
ALTER TABLE users ADD COLUMN mobile VARCHAR(20) NULL;
-- Step 2：从 binlog/备份里把 15 分钟前的 mobile 数据回填回来（DBA 介入）
-- Step 3：立刻回滚应用到 v1.1.0，先恢复服务（先止血，再修数据）
-- Step 4：v1.2.1 修复版：只保留 Step 1 Expand（加 phone + 双写，不删 mobile），下周再单独发 v1.2.2 做 Step 3

    铁律（以后所有团队成员都要背）：Step 1 Expand 与 Step 3 Contract 至少相隔 1~2 个独立发版周期（≈ 2 周以上）。在同一个版本里做 Expand + Contract，是把「回滚」这个最宝贵的逃生通道自己封死了。

    事故 2：双写没定「谁为准」+ 回填以 mobile 覆盖 phone → 运营改的 42 万条用户手机号全部回滚旧值（数据事故 P0）¶

    事故过程：Expand 双写期运营在后台手动改了一批 phone（新列），但老代码某次 MR 合入时又写了只改 mobile（旧列）的逻辑。晚上跑对账 Job 时，脚本里写的是「如果两列不一样，以 mobile 为准覆盖 phone」（错误决策）→ 运营手动改过的 42 万条新值全部被旧列 mobile 的历史值覆盖。

    修复（RTO ≈ 3 小时，P0 数据事故）：
    - 从 binlog 把 24h 内所有 UPDATE users SET phone 的 SQL 拉出来，按时间顺序重新回放一遍；
    - 修正对账脚本规则：永远以新列 phone 为准覆盖旧列 mobile。Contract 之前旧列只是「只读兜底 + 备份」，绝不能让旧列反向覆盖新列。

    准星规则（写在每一次双写方案评审 Checklist 第一项）：
    1. 写：两列都写，新列先写（phone = 最终准星）
    2. 读：优先读新列 phone，NULL 才 fallback mobile，读的时候顺手把 phone 填上（lazy repair）
    3. 对账：永远以新列覆盖旧列（phone 覆盖 mobile），绝不能反过来

    事故 3：2000 万行大表直接 ALTER ADD COLUMN → 锁表 31 分钟，所有写请求卡住（可用性事故 P1）¶

    事故过程：新人 DBA 直接跑 ALTER TABLE orders ADD COLUMN pay_channel TINYINT NULL;，orders 表 2000 万行 + MySQL 5.7，锁表 31 分钟，期间所有支付完成回调写订单的请求全卡住，积压 30 多万条支付成功但订单状态未更新的异步任务，后面清了 4 小时。

    通用修复/预防方案（以后 1000 万行以上一律走这个流程，不让人直接 ALTER）：

    DB 方案 命令 停机/锁表时间
    MySQL 5.7/8.0（通用稳） pt-online-schema-change（Percona Toolkit）或 gh-ost pt-online-schema-change --alter="ADD COLUMN pay_channel TINYINT NULL" --chunk-size=1000 --max-lag=1s h=mysql-prod,D=appdb,t=orders --execute 0（后台拷贝+切表，最后秒级 RENAME 不锁）
    PostgreSQL 11+（加无默认值的列） ①秒级加空列 ②分批回填 ③最后 ALTER SET NOT NULL ①ALTER TABLE orders ADD COLUMN pay_channel SMALLINT NULL;（秒级） ②Python 脚本：UPDATE orders SET pay_channel=1 WHERE id BETWEEN :a AND :b 每批 1000 行 sleep 1s ③ALTER TABLE orders ALTER COLUMN pay_channel SET NOT NULL; 0（全程不锁表）

    100 万行以下的表，低峰期直接 ALTER 就行，但必须把表行数作为必查项写在 Migration Review Checklist 里，超 1000 万行自动转 pt-osc 或分批。

    7.9.2 Feature Flag 四大技术债坑（对应 7.5 Flag/Unleash/自建）¶

    坑 1：Release Flag 开完 100% 忘了删 → 3 个月后遍布 if/else 变「永远 True 的死代码」，没人敢动¶

    现象：new-checkout-ui 这个 Release Flag 灰度 100% 之后没删，代码里 37 处 if flag.new_checkout_ui:。6 个月后新人重构时想删，发现没人知道 37 处 else 分支里的老代码「是不是还有业务方在用」，怕一删就炸。

    解决流程（以后所有 Release Flag 合入 MR 时就绑定）：
    1. 合 MR 时 Flag 名 + 负责人 + 「计划删除版本号」写进 MR 描述（例：new-checkout-ui 预计 v1.5.0 发版后删除）
    2. Unleash 侧给每个 Release Flag 加「过期时间 Tag」，过期自动在管理后台变红色告警
    3. 每个版本（例如 v1.4.0 → v1.5.0）的发版清单里必须有一项「Flag 清理情况」，过了期的强制清

    坑 2：Kill Switch 配在了调用方（订单服务里），不是被调方（积分服务里）→ 熔断了一半¶

    现象：订单服务里写了 if flag.integral_service_enabled: integral_client.add_points()，积分服务自己没配总闸。某次积分服务 hang 住 30 秒，订单服务虽然跳了 add_points，但积分服务自己的线程池已经被之前的请求占满，新进来的非积分 API（如积分记录查询）也全挂了。

    规则：Kill Switch / Ops Flag 永远放在被依赖的那一方服务里。调用方只是「感知超时快速失败」，真正的「总闸」要在被调方自己那一层。积分服务入口写的 is_service_enabled False，直接返回 503 快速失败，线程池不会被占。

    坑 3：Unleash 自建最小版里，ConfigMap 改了 Flag，应用没热更新，要等重启 → 紧急关不了（Kill Switch 秒级变分钟级）¶

    现象：用自建 ConfigMap + Python 代码读 Flag，ConfigMap 改了之后应用还是用内存里的旧值，要重启 Pod 才生效。生产发现 flag 关错了，等了 8 分钟 Deployment RollingUpdate 才全量生效。

    修复（一劳永逸的 30 行）：在 FastAPI 里加个后台线程，每 5 秒 reload 一次 ConfigMap 挂载的本地文件：

    # config.py：Flag 热更新（不用重启 Pod）
import threading, time, os, json
_flag_cache: dict = {}
_flag_file = "/etc/feature-flags/flags.json"   # ConfigMap 挂载到这里

def _reload_forever():
    global _flag_cache
    while True:
        try:
            if os.path.exists(_flag_file):
                with open(_flag_file) as f:
                    _flag_cache = json.load(f)
        except Exception:
            pass   # 加载失败就用上一次缓存，不要因为 ConfigMap 写错了把服务搞挂
        time.sleep(5)

threading.Thread(target=_reload_forever, daemon=True).start()

def is_enabled(name: str, default: bool = False) -> bool:
    return _flag_cache.get(name, default)

    坑 4：组合爆炸没测 → 4 个 Release Flag 在 stage 单独测都好，prod 全开一起用触发死锁（测试覆盖盲区）¶

    现象：new-inventory、new-order、new-pay、new-promotion 四个 Flag 每个单独开在 stage 都过了 UAT，但 prod 当天一起全开 → 新流程里 new-order 加写锁和 new-inventory 加写锁的顺序反过来了，触发 MySQL 死锁，20% 的下单请求报 1213。

    防法：有 N ≥ 3 个 Flag 要在同一版本里从 False 切 True 时，stage 环境必须加一份「所有 Flag = True」的专项 UAT Case，并且跑一次压力/并发测试。

    7.9.3 ArgoCD 生产落地七招（对应 7.4.3，事故坑 + 正确做法）¶

    参考来源：博客园《告别 GitOps 翻车！7 招让 ArgoCD 稳如老狗》（整理自 Regina Voloshin "Declarative...ish? Fixing Hidden Argo CD Pitfalls" + Red Hat OpenShift GitOps 推荐实践）。

    七条全部来自多团队多集群真实翻车案例，一条一条对照：

    第 1 招：ArgoCD 自身也要设 requests/limits，别让它把节点内存吃光

    翻车事故：单 ArgoCD 管 80 个 Application，application-controller 没设内存 limits，某晚 Application 状态同步高峰（一个 ConfigMap 改了导致 60 个 App 同时 Refresh）→ controller 内存涨到 7G → 该节点所有业务 Pod 被 K8s 驱逐（Evicted）→ 凌晨 3 点 P1。

    参考配置（按 Application 数量调整）：

    组件 requests limits
    argocd-server（UI/API） CPU 250m / 内存 512Mi CPU 500m / 内存 1Gi
    argocd-application-controller CPU 500m / 内存 1Gi CPU 1 / 内存 2Gi（管理 100+ App → 4Gi）
    argocd-repo-server（拉 Git + 渲染 Helm/Kustomize） CPU 250m / 内存 512Mi CPU 500m / 内存 1Gi

    第 2 招：原始 YAML 维护四份环境 = 迟早不一致 → Helm 或 Kustomize 二选一

    翻车型：dev/test/stage/prod 四份 Deployment YAML 复制粘贴，stage 环境加了个 readinessProbe 忘了同步到 prod → prod 滚动发布时新 Pod 没 Ready 就切了流量。

    选型建议：
    - 有 Chart 生态 / 要标准化发布模板 → Helm（推荐）
    - 平台级 CRD + overlay 结构复杂（多集群多租户）→ Kustomize
    - 小团队 2~3 个服务，Kustomize 零学习成本也能用，Helm 等服务 > 5 个再上

    第 3 招：Source 仓和 Manifest 仓必须分开（GitOps 安全底线）

    把源码仓和 ArgoCD Application YAML 放一起，有 3 个大坑：
    1. 生命周期不同：源码每天变，Manifest 几周才变，Git 历史混乱
    2. 权限混淆：开发有源码 MR 权 ≠ 有上线权，但一个仓就等于有了
    3. 供应链风险：源码仓被破 → 攻击者改 ArgoCD YAML 指向恶意镜像

    正确结构：
    - Source Repo（源码仓）：group/app-python.git，开发团队所有人可提 MR
    - Manifest Repo（清单仓）：单独一个 group/gitops-manifests.git，SRE/平台 3~4 人才有写权限

    第 4 招：All-in Git，Web UI 只「看」不「改」

    ArgoCD UI 里手动点 Sync Policy / Auto-Sync / Target Revision 改的东西不会自动同步回 Git 仓。下一次 CI 推 Manifest 时，被手动改过的值又会被覆盖回去，排查问题时 Git 里的 YAML 和集群状态对不上，根本不知道谁改了。

    规则：所有对 Application/Manifest 的修改，必须走 Git 提交 → CI 审核 → 合并 → ArgoCD 自动同步。Web UI 只允许三件事：
    - 看 Sync 状态（红/绿/OutOfSync 原因）
    - 应急手动触发一次 Sync（CI 挂了才用）
    - Rollback（紧急回滚，事后把回滚的版本号重新 commit 回 Manifest 仓，对齐状态）

    第 5 招：用 AppProject 做隔离，别所有 App 都挂在 default 下面

    AppProject 是 ArgoCD 多租户的基石。没有它后面所有 RBAC/权限隔离全是空谈。最少要按「业务线/团队」分：

    # 示例：Team B 独立 AppProject（只让它看自己的仓 + 自己的命名空间）
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-b-project
  namespace: argocd
spec:
  sourceRepos:
    - 'https://gitlab.example.com/team-b/manifests.git'
  destinations:
    - namespace: 'team-b-*'
      server: 'https://kubernetes.default.svc'
  namespaceResourceWhitelist:
    - { group: 'apps', kind: 'Deployment' }
    - { group: '',     kind: 'Service' }
    - { group: '',     kind: 'ConfigMap' }

    现实比例：10 人以下小团队 2~3 个 AppProject（业务线分）；中团队「每个团队 1 个 Project」。

    第 6 招：漂移（OutOfSync）要监控告警，别等出了事故才看到

    ArgoCD 自动把集群拉回 Git 里的状态。有人手动 kubectl edit 改了一个 ConfigMap，ArgoCD 会默默改回去，你完全看不到。必须加告警：
    - Prometheus 监控 argocd_app_info{sync_status="OutOfSync"} 指标，非 0 就告警
    - 或 ArgoCD notifications-controller 发飞书/钉钉/企业微信
    - CI 里跑 argocd app diff <app> --exit-code，漂移就 CI 失败

    第 7 招：按组织结构拆分实例，不要一个 ArgoCD 管全公司所有集群

    • 10 人以下 / <10 服务：1 个共享实例 + Helm/Kustomize 足够了
    • 平台 + 多业务单元：必须 1 个 Manifest 仓 + N 个 AppProject + 严格 RBAC

    • 100 服务 + 多地域 + 跨境集群：每个团队独立 ArgoCD 实例，一个团队的 ArgoCD controller OOM 不会把其他团队的应用同步挂掉

    7.9.4 K8s 生产 Checklist Top5 漏配事故（对应 7.3.4）¶

    Top1：没配 PodDisruptionBudget → 节点维护时 3 个 Pod 全被驱逐，服务挂 12 分钟¶

    事故：运维升级节点内核，drain 了一个节点。3 个 myapp Pod 刚好全在这个节点上，没设 PDB → 三个一起被驱逐。新 Pod 调度到其他节点需要拉镜像 + 启动，总共 12 分钟 0 副本可用。

    修复（一行 YAML，配了之后节点维护永远不会全杀）：

    apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2   # 任何时候最少 2 个副本活着，K8s drain 时只会先起新 Pod 再停旧的
  selector:
    matchLabels:
      app: myapp

    Top2：内存没设 requests = limits（超卖）→ 深夜 Batch 任务触发 OOM Kill，订单 Pod 随机被杀¶

    事故：Deployment 只设了 requests=512Mi 没设 limits，凌晨大促报表任务把节点内存占满 → K8s OOM Killer 按「QoS 低的优先杀」选到了 myapp（因为 QoS=Burstable）→ 正在处理的 300 多个支付请求中断。

    修复（Checklist 里内存 requests/limits 必须相等）：

    resources:
  requests: { memory: "1Gi", cpu: "500m" }
  limits:   { memory: "1Gi", cpu: "2" }   # 内存一定和 requests 写一样，CPU 超卖 1/3 ~ 1/2 可以

    → QoS 升为 Guaranteed，节点内存满时 OOM Killer 最后才会动它。

    Top3：慢启动应用没配 StartupProbe → 每 10 秒 Liveness 查一次，Pod 启动要 40 秒，连续 3 次失败被 K8s 反复重启（CrashLoopBackOff）¶

    事故：订单服务启动要加载 20w 商品到本地缓存，40 秒才能处理请求。Deployment 只配了 Liveness（initialDelaySeconds=15）→ 启动 15s 后 Liveness 开始查，连续 3 次（15+10×3=45s 刚好）失败被 K8s 杀掉，进入 CrashLoopBackOff，永远起不来。

    修复：

    startupProbe:            # 只给慢启动应用加
  httpGet: { path: /health, port: 8080 }
  failureThreshold: 30   # 最多 30 次失败机会（10s×30 = 最长 5 分钟启动窗口）
  periodSeconds: 10
readinessProbe:          # 启动好之后，Ready 了才进流量
  httpGet: { path: /health, port: 8080 }
  periodSeconds: 10
livenessProbe:           # Ready 之后，处理死锁/GC 卡顿
  httpGet: { path: /health, port: 8080 }
  periodSeconds: 30

    StartupProbe 通过后，Readiness + Liveness 才开始。慢启动应用就不会被误杀了。

    Top4：镜像 tag 用 latest → 晚上有人手动改了 latest 的 image，第二天滚动发布自动拉错版本，回滚不知道滚哪版¶

    事故：Deployment 写了 image: myapp:latest。有个工程师手动构建镜像 docker build -t myapp:latest && docker push 测试没打 Tag，第二天滚动发布新 Pod 把这个未合并的最新代码拉到了 prod。

    修复：Deployment YAML 永远用 git tag 生成的语义化版本号（v1.2.3），CI 把 $CI_COMMIT_TAG 替换进去。latest 只允许本地 Docker 开发用，不许进 CI/CD。

    Top5：没配 readOnlyRootFilesystem → Spring Boot 应用被打进恶意内存马（写入 /tmp/classes/ 恶意 class，Spring Boot 热加载直接加载）¶

    事故：攻击者通过上传接口突破，把 .class 写到 /tmp 目录下，利用 Spring Boot DevTools 默认的类加载器把恶意代码加载到 JVM 里。K8s 文件系统是可写的，写进去直接生效。

    修复：

    securityContext:
  runAsNonRoot: true
  readOnlyRootFilesystem: true      # 根文件系统只读，写不进去
  capabilities: { drop: ["ALL"] }
volumeMounts:                       # 真要写的目录（/tmp、/var/cache）单独挂 emptyDir
  - name: tmp
    mountPath: /tmp
volumes:
  - name: tmp
    emptyDir: {}

    7.9.5 main 分支回退 / 强推事故（对应 7.4.4）¶

    事故：用 git push --force（没加 -with-lease）强推 main → 把同事刚 push 正在跑 CI 的功能 D 给冲掉了，CI 还显示通过¶

    事故过程：功能 A 误合 main，运维用 git reset --hard A && git push --force origin main 强推。但同时同事刚 push 了功能 D（比本地 main 新 2 个 commit）。--force 直接把远端覆盖成了本地旧 main（不含 D）。CI 跑了，过了；大家以为 D 在 main 里，实际没了。一周后 release 阶段发现 D 功能"消失"，才查出来是被冲掉的。

    铁律（所有人强制）：
    1. 禁止 git push --force，只能 git push --force-with-lease origin main
    - --force-with-lease 只有「远端 HEAD == 本地拉的时候那个 HEAD」才成功，远端有新 commit 就会失败（保护别人刚推的代码）
    2. revert 是 90% 场景首选（独立功能/无依赖时，零影响），rebase --onto（等价 reset + cherry-pick）只在严重安全问题/数据污染用，用之前必须大群通知所有人对齐本地分支
    3. Merge Commit 回退用 git revert -m 1 <merge-commit>（-m 1 选 main/master 做父分支）

    7.9.6 纯 Docker / Docker Compose / Swarm 部署六类坑（对应 7.6.4，小团队不养 K8s 必看）¶

    坑 1：SSH 私钥直接写进 deploy.sh 明文脚本或 CI 变量没 masked → 被 CI 日志打印出私钥 → 机器被扫¶

    正确做法：GitLab CI 变量 DEPLOY_SSH_PRIVATE_KEY 必须勾 Masked + Protected（Protected 只对 main/Tag 生效），脚本里永远用 echo "$VAR" | ssh-add - 这种写法，不要 echo $VAR 打印。

    坑 2：docker run 把宿主机 /var/run/docker.sock 挂进容器 → 容器里拿 docker 命令 = 宿主机 root（权限穿透）¶

    现象：有人图省事，在 Jenkins Runner / GitLab Runner 里挂 /var/run/docker.sock 做 docker build。只要 Runner 里一个漏洞（比如任意脚本执行）→ 直接拿到宿主机 root。

    修复：小团队 Kaniko 构建（不需要 Docker daemon，06 章方案）或 Docker-in-Docker（dind）Service 隔离。

    坑 3：compose 没配 healthcheck → up 了之后服务还没 Ready，Nginx 就把流量切过去导致 5xx¶

    修复（对应 7.6.4 的 compose 模板）：myapp 容器必配 healthcheck + depends_on.condition: service_healthy，让 Nginx 只依赖健康的 myapp。

    坑 4：compose 滚动发布用 --force-recreate 而不是 --scale 2 → --scale 1 → 旧容器先删再启，中间 20 秒服务 0 副本¶

    修复：零停机 compose 滚动发布必须先 scale 扩容一个新的 → 健康了再 scale 缩掉旧的（直接用 7.6.4 那段 Bash 两行方案），别用 --force-recreate。

    坑 5：Swarm 里 Secret 图省事写在 environment 里明文，没走 docker secret create + secrets: 挂载 → docker inspect 一查就看到密码¶

    修复（Swarm Secret 铁律）：密码/Token 全部 docker secret create 提前建好，stack.yml 里 secrets: [{source: ...}] 挂载到 /run/secrets/，代码里从文件读（DB_PASSWORD_FILE），绝不能写在 environment:。

    坑 6：Swarm stack deploy 没有配 update_config.failure_action: rollback → 更新失败了停在中间状态（2 个新 + 1 个旧）没人管¶

    修复（7.6.4 Swarm 模板里要写）：

    deploy:
  update_config:
    parallelism: 1
    failure_action: rollback    # 更新失败自动回滚，绝不能停在半新半旧
    monitor: 30s

    7.10.2 现阶段最佳实践速记（2026）¶

    • 发布策略：小团队起步用滚动发布；核心业务上金丝雀（1% 起步）；API 不兼容场景用蓝绿
    • K8s 必配：三类探针（Startup 防误杀 + Readiness 控制流量 + Liveness 处理死锁）+ PDB + HPA + 只读 FS + non-root
    • 自动回滚：progressDeadlineSeconds=300 + maxUnavailable=0（零停机 + 超时自动回滚）
    • 门禁：P1.3 四段触发 + 两段式机制（main 只验证、Tag 才发布）+ stage 人工确认（when:manual）
    • 演进到 GitOps：P1.3 触发逻辑不变，deploy Job 里 kubectl apply 换成更新 Manifest 仓 image tag
    • Feature Flag：Release Flag 用完就删；Kill Switch 长期保留，每个核心依赖/重型功能配一个
    • DB 迁移：Expand-Contract 三步；Step 1 Expand 和 Step 3 Contract 不同周期；prod Migration 单独 Job，成功后才部署
    • 凭证保护：kubeconfig 存 GitLab masked + protected variable，不要 commit 到仓库
