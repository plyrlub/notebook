## 4.1 工具学习路径与本章范围

### 4.1.1 学习顺序建议

第 03 章给出五大工具全景，本章只攻**三大 CI 工具的语法**（Argo CD / Tekton 留到第 07 章 / 进阶）。学习顺序按"上手难度递增"：

```
GitHub Actions（最简单，YAML + 上手 30 分钟）
       ↓
GitLab CI（结构与 Actions 类似，但概念更完整，——你实际用的重点学）
       ↓
Jenkins（Groovy + Pipeline + Shared Library，最复杂）
```

### 4.1.2 三大工具的语法层级对照

**表 4-1：三大工具语法层级对照**

| 层级 | GitHub Actions | GitLab CI | Jenkins |
| ---- | -------------- | --------- | ------- |
| 流水线 | Workflow | Pipeline | Pipeline |
| 阶段 | job（通过 needs 编排） | stage | stage |
| 任务 | step | job | step |
| 复用 | Reusable Workflow / Composite Action | include / Components | Shared Library |
| 触发器 | `on:` | `rules:` / `workflow:` | `triggers {}` / `when:` |
| 矩阵 | `strategy.matrix` | `parallel:matrix` | 没原生（用 Shared Library 循环） |
| 缓存 | `cache:` / `actions/cache` | `cache:` | `stash` / 插件 |
| 制品 | `actions/upload-artifact` | `artifacts:` | `archiveArtifacts` |
| 环境 | `environment:` | `environment:` | `environment {}` |

### 4.1.3 学习方法

1. **不要死记语法**：工具语法会变，掌握"概念 + 查文档能力"即可
2. **用对照表学**：先学一个工具的概念，再对照到其他工具
3. **写最小可运行 Demo**：每个工具写一条 Lint→Test→Build 的最小流水线
4. **官方文档优先**：本章示例是入门骨架，深度参数看官方文档

## 4.2 GitHub Actions 语法深入

### 4.2.1 文件位置与基本结构

```yaml
# .github/workflows/<name>.yml
name: <workflow 名称>

on: <触发器>

permissions:
  contents: read      # 显式声明最小权限（参见 S5）

jobs:
  <job-id>:
    runs-on: <runner>
    steps:
      - <step 1>
      - <step 2>
```

### 4.2.2 触发器（on）

```yaml
on:
  push:
    branches: [main, 'release/**']
    tags: ['v*']
    paths:
      - 'src/**'
      - '.github/workflows/**'
  pull_request:
    types: [opened, synchronize, reopened]
  schedule:
    - cron: '0 2 * * *'    # 每天 02:00 UTC
  workflow_dispatch:        # 手动触发（UI 按钮）
    inputs:
      env:
        description: 'Target environment'
        default: 'dev'
  workflow_call:            # 被其他 workflow 调用（Reusable Workflow）
    inputs:
      python-version:
        default: '3.12'
  repository_dispatch:      # 外部 API 触发
```

### 4.2.3 Job 与 Step

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 30      # 超时保护
    env:
      PYTHONDONTWRITEBYTECODE: '1'
    steps:
      # 1. 拉代码
      - uses: actions/checkout@v4
        with:
          fetch-depth: 1     # 浅克隆

      # 2. 装依赖
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip          # 自动缓存

      - run: pip install -r requirements.txt

      # 3. 跑测试
      - name: Run tests
        run: pytest --cov

      # 4. 条件执行
      - name: Notify on failure
        if: failure()
        run: echo "Tests failed, sending alert..."

  build:
    needs: test               # 等 test 通过
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - run: docker build -t app:${{ github.sha }} .
```

### 4.2.4 矩阵（多版本/多平台并行）

#### 4.2.4.1 矩阵是什么（关键认知）

矩阵 **不是"从几个里选一个"**，而是 **"自动生成 N 个 Job 并行跑全部组合"**。

> 用途：兼容性测试（同一份代码在多个版本/平台/数据库上验证是否都能跑通）。
> 不适用：构建生产镜像（生产镜像只构建一个版本，不用矩阵）。

#### 4.2.4.2 示例

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false        # 一个失败不取消其他
      matrix:
        os: [ubuntu-latest, macos-latest]
        python-version: ['3.10', '3.11', '3.12']
        exclude:
          - os: macos-latest
            python-version: '3.10'   # 排除特定组合
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest
```

#### 4.2.4.3 这段配置会生成 5 个 Job 并行执行

GitHub Actions 看到 `strategy.matrix` 后，会**自动展开**为多个独立的 Job（笛卡尔积，再减去 exclude）：

| Job 序号 | matrix.os | matrix.python-version |
| -------- | --------- | --------------------- |
| test (ubuntu, 3.10) | ubuntu-latest | 3.10 |
| test (ubuntu, 3.11) | ubuntu-latest | 3.11 |
| test (ubuntu, 3.12) | ubuntu-latest | 3.12 |
| test (macos, 3.11) | macos-latest | 3.11 |
| test (macos, 3.12) | macos-latest | 3.12 |

原本 2×3=6 个组合，exclude 掉 `macos + 3.10`，剩 5 个 Job **并行跑**。

#### 4.2.4.4 与 GitLab CI 矩阵的对照

| 维度 | GitHub Actions | GitLab CI |
| ---- | -------------- | --------- |
| 关键字 | `strategy.matrix` | `parallel:matrix` |
| 排除组合 | `exclude:` | 多个 matrix 项分别声明 |
| 失败策略 | `fail-fast: false` | 默认不取消其他 |
| 变量引用 | `${{ matrix.xxx }}` | `$MATRIX_XXX`（自定义变量名） |

> 参见 [4.3.4 GitLab CI 矩阵](#434-矩阵parallelmatrix) 的详细说明。

### 4.2.5 缓存与制品

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 缓存依赖
      - uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}
          restore-keys: |
            ${{ runner.os }}-pip-

      - run: pip install -r requirements.txt
      - run: python -m build

      # 上传制品（同 workflow 内传递）
      - uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: dist/
          retention-days: 7   # 参见 S10.3 保留策略
```

### 4.2.6 环境与部署门禁

```yaml
jobs:
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: production        # 在 GitHub UI 配置审批人
      url: https://app.example.com
    steps:
      - run: echo "Deploying to production..."
```

### 4.2.7 Reusable Workflow（跨仓库复用）

```yaml
# .github/workflows/python-ci.yml（被调用的 reusable workflow）
on:
  workflow_call:
    inputs:
      python-version:
        default: '3.12'
        type: string

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ inputs.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest
```

```yaml
# 另一个 workflow 调用它
jobs:
  ci:
    uses: org/repo/.github/workflows/python-ci.yml@main
    with:
      python-version: '3.12'
```

### 4.2.8 第三方 Action 安全使用

```yaml
# 反模式：浮动 tag（容易被劫持）
- uses: actions/checkout@v4

# 正确：锁 SHA（参见 S5）
- uses: actions/checkout@<commit-sha>
  with:
    fetch-depth: 1
```

## 4.3 GitLab CI 语法深入（重点）

> 本节是你实际工作的主战场，**每个小节都按矩阵标准扩充**：先讲"这是什么 + 为什么需要"，再给示例，最后给"常见坑 / 与其他机制对比"。

### 4.3.1 文件位置与基本结构

#### 4.3.1.1 最小结构说明

GitLab CI 的配置文件叫 `.gitlab-ci.yml`，放在仓库根目录。最基本的四件套：

```yaml
# .gitlab-ci.yml
stages:          # ①
  - lint
  - test
  - build
  - deploy

variables:       # ②
  GLOBAL_VAR: value

<job-name>:      # ③
  stage: <stage>
  image: <docker-image>
  script:
    - <command>
  rules:          # ④
    - if: <condition>
```

| 序号 | 字段 | 是什么 | 类比 |
| ---- | ---- | ------ | ---- |
| ① | `stages:` | **流程阶段的顺序清单**，决定 stage 谁先谁后 | 工厂流水线的"工位顺序表"：先组装后检测再打包 |
| ② | `variables:` | **全局变量**，所有 Job 都能读到 | 车间墙上贴的"公共参数公告" |
| ③ | `<job-name>`（无冒号的对象键） | **具体任务**，必须挂在某个 stage 下 | 某个工位上的具体操作 |
| ④ | `rules:` | **触发条件**，决定这个 Job 什么情况下执行 | "只有 main 分支的 push 才跑这个 Job" |

> 注意：你之前看到的公司配置（`include` + `extends`）是**在这个最小结构基础上引入了复用**，本质没变。参见 [4.3.6 include 与 Components](#436-include-与-components复用)。

#### 4.3.1.2 变量作用域（从高到低优先级）

| 优先级（由高到低） | 来源 | 举例 |
| ------------------ | ---- | ---- |
| 1 | Trigger / Scheduled / Manual 的变量 | 手动点跑时在 UI 填的变量 |
| 2 | Job 内的 `variables:` | 某一个 job 里写的 `variables:` |
| 3 | `environment:` 里的环境变量 | prod 环境的 DB_PASSWORD |
| 4 | Group 级 Variables（UI 配置） | 公司某个组统一配的变量 |
| 5 | Project 级 Variables（UI 配置） | 当前项目配的变量 |
| 6 | `.gitlab-ci.yml` 顶层 `variables:` | 上面例子里的 GLOBAL_VAR |
| 7 | 内置预定义变量 | `$CI_COMMIT_SHA`、`$CI_REGISTRY_IMAGE` |

**优先级高的会覆盖优先级低的**。常遇到的坑：在 `.gitlab-ci.yml` 里改了个变量，但 Job 里没生效——排查是不是 Group 级变量覆盖了你。

### 4.3.2 触发条件（rules + workflow:rules）

#### 4.3.2.1 为什么用 rules 而不是 only/except？

GitLab 早年用 `only/except`，**2026 已官方弃用**，统一用 `rules`。

| 对比项 | rules | only/except（旧） |
| ------ | ----- | ----------------- |
| 多条件组合 | 用 `&&` / `\|\|` 自由组合 | 要写多个 only 数组，难读 |
| 控制 pipeline 是否创建 | 有 `workflow:rules` | 做不到 |
| 官方推荐 | ✅ 推荐 | ❌ 弃用 |

#### 4.3.2.2 rules 常用条件速查表

```yaml
test:
  stage: test
  rules:
    # 1. MR 事件（最常用）
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

    # 2. main 分支 push 时
    - if: $CI_COMMIT_BRANCH == "main"

    # 3. 打 tag 时
    - if: $CI_COMMIT_TAG

    # 4. 手动触发时
    - if: $CI_PIPELINE_SOURCE == "web"

    # 5. 多条件组合：MR 或 main 分支，且改动了 src/ 下文件
    - if: ($CI_PIPELINE_SOURCE == "merge_request_event" || $CI_COMMIT_BRANCH == "main")
        && $CI_CHANGES_FILES =~ /^src\//

    # 6. 其他情况不跑（默认兜底）
    - when: never
  script:
    - pytest
```

**常用 `CI_PIPELINE_SOURCE` 值速查**：

| 值 | 含义 |
| -- | ---- |
| `push` | 代码 push 触发 |
| `merge_request_event` | MR 创建/更新触发 |
| `web` | UI 手动点 Run pipeline |
| `schedule` | 定时任务触发 |
| `trigger` | 另一条 pipeline API 触发 |
| `tag` | 打 tag 触发（不是 COMMIT_TAG，注意） |

#### 4.3.2.3 workflow:rules（控制整条 pipeline 是否创建）

`rules` 是 Job 粒度，`workflow:rules` 是**整条 pipeline 粒度**——决定"这次事件要不要创建 pipeline"。

```yaml
# 放在 .gitlab-ci.yml 最前面（stages 之前）
workflow:
  rules:
    # 1. MR 事件创建 pipeline
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    # 2. main/master 分支 push 创建 pipeline
    - if: $CI_COMMIT_BRANCH == "main"
    # 3. 打 tag 创建 pipeline
    - if: $CI_COMMIT_TAG
    # 4. 其他情况（比如 feature 分支 push）不创建 pipeline
    - when: never
```

> 你公司的项目常见场景：dev/test/stage/main 分支 push 才创建 pipeline，feature 分支只有 MR 时才跑——就用 workflow:rules + rules 双层控制。

#### 4.3.2.4 常见坑

1. **rules 是按顺序匹配的**，匹配到第一个就执行，后面的不再看
2. **`changes` 只在 MR 和 push 事件里生效**，tag/schedule 里用 `changes` 永远是假
3. 没写 `rules` 的 Job **默认一直跑**

### 4.3.3 Job 与 needs（DAG）

#### 4.3.3.1 两种编排模式对比

GitLab CI 有两种**完全不同**的 Job 依赖编排方式：

| 模式 | 怎么实现 | 执行逻辑 | 类比 |
| ---- | -------- | -------- | ---- |
| **A. stage 串行（默认）** | 只写 `stage:`，不写 `needs` | 上一个 stage 全部通过，下一个 stage 所有 Job 才能开始 | 工位制：所有工人必须一起走完工位 1，才能一起开工位 2 |
| **B. needs DAG** | 显式写 `needs: [其他 job]` | 只等 `needs` 里指定的 Job 通过，不等其他同 stage Job | 分工制：每个人只等自己需要的前置工作完成，不等别人 |

#### 4.3.3.2 needs 示例（打破 stage 串行）

```yaml
stages:
  - build
  - test
  - deploy

build:backend:
  stage: build
  script: [make backend]

build:frontend:
  stage: build
  script: [make frontend]

# 关键：test:backend 只等 build:backend 完成
#     不等 build:frontend！
test:backend:
  stage: test
  needs: [build:backend]
  script: [pytest backend]

test:frontend:
  stage: test
  needs: [build:frontend]
  script: [npm test]

# deploy 等所有测试通过
deploy:
  stage: deploy
  needs: [test:backend, test:frontend]
  script: [kubectl apply -f k8s/]
```

**时间线对比（假设 build:backend 2 分钟，build:frontend 10 分钟）：**

```
stage 串行（无 needs）：
  0m ───────── build:backend(2m) ────────┐
  0m ──────────────────── build:frontend(10m) ─────┐
  时间轴：──────────────────────────────────────── test(12m才开始)
  总耗时 ≈ 10m（build）+ 测试 + deploy

needs DAG：
  0m ───────── build:backend(2m) ─┐── test:backend(2m开始) ──┐
  0m ────────────── build:frontend(10m) ──────────── test:frontend ──┐
  时间轴：test:backend 提前 8 分钟开始
  总耗时 ≈ 2m（test:backend）+ 10m（test:frontend）+ deploy
```

#### 4.3.3.3 needs 的特殊用法

| 写法 | 含义 |
| ---- | ---- |
| `needs: []`（空数组） | 这个 Job 不需要等待任何前置 Job，pipeline 一创建就立刻跑（用于 lint 等前置检查） |
| `needs: [job_a, job_b]` | 同时依赖两个 Job，都通过才执行 |
| `needs: - job: job_a artifacts: true` | 依赖 job_a 并自动下载其 artifacts |
| `needs: - pipeline: $CI_PIPELINE_ID` | 跨 pipeline 依赖（父子 pipeline 用） |

> 你的"分支即环境"模式里（P1 实践），dev/test/stage/main 四条分支的流水线通常是独立的，needs 主要用在单条流水线内部：build 完成后 test 才能跑。

### 4.3.4 矩阵（parallel:matrix）

> 本节在之前已经按矩阵标准细化了，这里保持完整（三级编号从 4.3.4.1 开始）。

#### 4.3.4.1 矩阵是什么（关键认知）

矩阵 **不是"从几个里选一个"**，而是 **"自动生成 N 个 Job 并行跑全部组合"**。

> 用途：兼容性测试（同一份代码在多个版本/平台/数据库上验证是否都能跑通）。
> 不适用：构建生产镜像（生产镜像只构建一个版本，不用矩阵）。

#### 4.3.4.2 示例

```yaml
test:
  stage: test
  image: python:${MATRIX_PYTHON}-slim
  parallel:
    matrix:
      - MATRIX_PYTHON: ['3.10', '3.11', '3.12']
        MATRIX_OS: [ubuntu, alpine]
  script:
    - pip install -r requirements.txt
    - pytest
```

#### 4.3.4.3 这段配置会生成 6 个 Job 并行执行

GitLab 看到 `parallel:matrix` 后，会**自动展开**为 6 个独立的 Job（笛卡尔积）：

| Job 序号 | MATRIX_PYTHON | MATRIX_OS | 实际用的 image |
| -------- | ------------- | --------- | -------------- |
| test [3.10 ubuntu] | 3.10 | ubuntu | python:3.10-slim |
| test [3.10 alpine] | 3.10 | alpine | python:3.10-slim |
| test [3.11 ubuntu] | 3.11 | ubuntu | python:3.11-slim |
| test [3.11 alpine] | 3.11 | alpine | python:3.11-slim |
| test [3.12 ubuntu] | 3.12 | ubuntu | python:3.12-slim |
| test [3.12 alpine] | 3.12 | alpine | python:3.12-slim |

6 个 Job **并行跑**（受 Runner 并发数限制），**全部通过**这个 stage 才算通过。

#### 4.3.4.4 矩阵的常见 4 种用途

| 用途 | 矩阵变量 | 例子 |
| ---- | -------- | ---- |
| 多语言版本兼容 | Python 3.10/3.11/3.12 | 库开发必测 |
| 多 OS 平台兼容 | ubuntu/macos/windows | CLI 工具必测 |
| 多数据库兼容 | mysql/postgres/mariadb | ORM 库必测 |
| 多架构构建 | amd64/arm64 | 容器镜像多架构（配合 buildx） |

#### 4.3.4.5 排除特定组合

如果某个组合不需要跑（比如 Python 3.10 在 alpine 上不支持），用多个 matrix 项排除：

```yaml
test:
  parallel:
    matrix:
      # 第一组：Python 3.11/3.12 在所有 OS 上跑
      - MATRIX_PYTHON: ['3.11', '3.12']
        MATRIX_OS: [ubuntu, alpine]
      # 第二组：Python 3.10 只在 ubuntu 上跑（排除 alpine）
      - MATRIX_PYTHON: '3.10'
        MATRIX_OS: ubuntu
```

#### 4.3.4.6 矩阵 vs 单次构建（重要对比）

| 场景 | 用矩阵？ | 例子 |
| ---- | -------- | ---- |
| 测试在多 Python 版本下是否兼容 | ✅ 用 | `['3.10', '3.11', '3.12']` 全跑 |
| 构建生产 Docker 镜像 | ❌ 不用 | 只构建一个 `python:3.12-slim` 镜像 |
| 多架构镜像构建 | ⚠️ 看工具 | GitLab 矩阵可行；更推荐 `docker buildx --platform` |
| 多环境部署（dev/test/prod） | ❌ 不用 | 用 `rules` 区分环境，不用矩阵 |

### 4.3.5 缓存与制品（cache vs artifacts）

#### 4.3.5.1 cache 和 artifacts 是完全不同的两个东西（必懂）

| 对比项 | cache | artifacts |
| ------ | ----- | --------- |
| **目的** | **加速重复构建**（依赖包缓存） | **在不同 stage/Jobs 之间传递文件**（构建产物） |
| **生命周期** | 跨 pipeline 复用（保存在 Runner 机器上） | 同一 pipeline 内传递，过期自动删除 |
| **存储位置** | Runner 本地缓存目录 | GitLab 服务器（对象存储） |
| **典型内容** | `.m2/`、`node_modules/`、`.cache/pip` | `target/*.jar`、覆盖率报告、打包好的镜像 |
| **保留时间** | 手动清理或 Runner 磁盘不足时被淘汰 | `expire_in` 控制，默认永久 |
| **下载时机** | Job 开始前自动拉取 | `dependencies:` / `needs:` 控制下载 |

> 一句话记：**cache 是"为了下次更快"，artifacts 是"为了下游 Job 拿到我的产物"。**

#### 4.3.5.2 cache 详解

```yaml
build:
  stage: build
  image: maven:3.9
  cache:
    # Key 策略：pom.xml 变了缓存就失效
    key:
      files: [pom.xml]
    paths:
      - .m2/repository          # 缓存 Maven 依赖
    policy: pull-push           # pull-push（默认）= 开始拉 + 结束回写
                                # pull         = 只拉不写回（读多写少场景）
  script:
    - mvn -B -Dmaven.repo.local=$PWD/.m2/repository package
```

**关键字段**：

| 字段 | 说明 | 推荐值 |
| ---- | ---- | ------ |
| `key.files` | 基于哪些文件的 hash 生成缓存 key | `requirements.txt` / `pom.xml` / `pnpm-lock.yaml` |
| `policy: pull-push` | 默认：开始拉 + 结束写回 | 大部分 Job |
| `policy: pull` | 只读，用于下游 test Job（避免多个写缓存冲突） | 只有 build Job 写 cache，其他 Job 用 pull |

> 参见 [S10.2 缓存最佳实践](./补充专题/S10-Pipeline各环节最佳实践.md)（缓存 key 策略、大小上限等 10 条规则）。

#### 4.3.5.3 artifacts 详解

```yaml
build:
  stage: build
  image: maven:3.9
  script:
    - mvn -B package
  artifacts:
    # 要传的文件路径
    paths:
      - target/*.jar
      - target/surefire-reports/
    # 过期时间（到了自动删，省存储）
    expire_in: 7 days
    # 报告（GitLab UI 里专门展示）
    reports:
      junit: target/surefire-reports/*.xml        # 测试报告
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml                        # 覆盖率
```

**artifacts 的传递关系**：

```yaml
# 下游 deploy Job 会自动拿到 build Job 的 target/*.jar
deploy:
  stage: deploy
  needs: [build]      # 或者写 dependencies: [build]
  script:
    - ls target/      # 能看到 build 传过来的 jar 包
```

> 参见 [S10.3 制品保存最佳实践](./补充专题/S10-Pipeline各环节最佳实践.md)（命名规范、保留策略、跨 Stage 传递 4 条规则）。

### 4.3.6 include 与 Components（复用）

#### 4.3.6.1 include 的四种形式

include 就是"把另一个 YAML 内容文本插入当前文件"。

| 形式 | 写法 | 用途 |
| ---- | ---- | ---- |
| **project**（跨项目拉） | `include: project: 'bhpc/ci' ref: master file: '/java11.yml'` | **你公司在用的方式**：从 CI 模板库拉模板 |
| **local**（本仓库内引） | `include: local: '/ci/jobs/docker.yml'` | 大项目拆分多文件管理 |
| **remote**（远程 URL 拉） | `include: remote: 'https://example.com/ci.yml'` | 从 HTTP 文件服务器拉 |
| **template**（官方模板） | `include: template: Jobs/SAST.gitlab-ci.yml` | 直接用 GitLab 官方内置模板 |

#### 4.3.6.2 你公司配置的实际效果

回顾你发的：

```yaml
include:
  - project: 'bhpc/ci'
    ref: master
    file:
      - '/java11.yml'

build-java:
  extends: .build-java
```

**这两段做的事情展开相当于**：

```yaml
# ── include 进来的 java11.yml 内容（隐藏模板 Job） ──
.build-java:          # 以 . 开头 = 只是模板，不实际跑
  stage: build
  image: maven:3.9-jdk-11
  script:
    - mvn -B clean package
    - docker build --build-arg APP_ENTRY=$APP_ENTRY ...
    - docker push ...
    - kubectl set image ...
  rules:
    - when: always

# ── 你文件里的 extends ──
build-java:            # 实际会执行的 Job
  stage: build                            │
  image: maven:3.9-jdk-11                 │  全部
  script: [...]                           │  继承
  rules: [...]                            │

# ── variables 作为填空参数传给模板 ──
# APP_ENTRY / APP_ENTRY_SUB / APP_HTTP_PORT / ...
# 模板里的 $APP_ENTRY 会被替换成 "bh-server"
```

所以业务项目非常轻量：**只要 include 模板 + extends + 填 variables**，完全不用写具体 script。

#### 4.3.6.3 include 的坑（重要）

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| **include 是纯文本插入** | 不做输入校验，模板改了你这边立即生效 | `ref` 用 tag 不用 master |
| **变量是运行时替换** | 你文件里的 variables 要在 include 模板里被用到，变量名必须匹配 | 模板文档里有"接受哪些变量"的清单 |
| **同名 Job 会合并** | 你定义的 build-java 和 include 进来的同名 build-java 会 merge | include 的模板用 `.` 开头的隐藏 Job（如 `.build-java`），不会和实际 Job 冲突 |

**强烈建议你的 ref 改成 tag**：

```yaml
# 不好：跟随 master 浮动，模板改了你立即变
include:
  - project: 'bhpc/ci'
    ref: master
    file: '/java11.yml'

# 好：锁版本 tag，你想升级时手动改
include:
  - project: 'bhpc/ci'
    ref: v1.2.3        # 改这里才会升级模板版本
    file: '/java11.yml'
```

#### 4.3.6.4 Components（2024+ 新方式，替代 include）

include 是"文本拼接"，Components 是"有输入输出契约的组件"，两者的差异：

| 维度 | include（传统） | Components（2024+） |
| ---- | --------------- | ------------------- |
| 输入契约 | ❌ 没有，靠变量名约定 | ✅ `inputs:` 显式声明要传的参数、默认值、类型 |
| 输出 | ❌ 没有 | ✅ 可以有 outputs |
| 调试 | 难（冲突靠猜） | 易（参数没传直接报错） |
| 复用粒度 | 文件级 | 组件级 |
| 2026 推荐 | 老项目兼容 | **新项目首选** |

写法示例：

```yaml
include:
  # 调用 CI Catalog 里的组件
  - component: gitlab.com/my-org/python-ci@v1.2
    inputs:
      python_version: '3.12'
      enable_sast: true
```

> 你公司的模板体系（bhpc/ci）就是 Components 的前身。未来升级建议：把 include + extends 体系迁移到 Components + CI Catalog，**有输入输出契约**后，模板团队和业务团队的协作会更清晰。

### 4.3.7 环境与部署门禁（environment）

#### 4.3.7.1 environment 解决什么问题？

把"部署动作"与"环境实体"绑定起来，获得：
1. **环境级凭据隔离**：prod 凭据只有 prod environment 能读
2. **审批门禁**：部署前需要人点批准
3. **部署历史**：GitLab 里能看到这个环境被部署了什么版本
4. **回滚按钮**：UI 里一键回滚到上一版本

#### 4.3.7.2 5 大字段详解

```yaml
deploy:prod:
  stage: deploy
  environment:
    name: production                     # ① 环境名
    url: https://app.example.com         # ② 访问地址（UI 里变成按钮）
    deployment_tier: production          # ③ 部署层级（见下）
    auto_stop_in: 1 week                 # ④ 自动停机（review 环境用）
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  when: manual                          # ⑤ 手动触发（部署按钮）
  script:
    - kubectl apply -f k8s/prod/
```

| 字段 | 含义 | 常用值 |
| ---- | ---- | ------ |
| `name` | 环境唯一标识。带 `/` 分组，如 `review/feature-xxx` | `dev` / `test` / `staging` / `production` / `review/<mr>` |
| `url` | 这个环境的访问地址，GitLab UI 里显示"打开环境"按钮 | 应用域名 |
| `deployment_tier` | 环境层级（GitLab 内置分层权限） | `production` / `staging` / `testing` / `development` / `other` |
| `auto_stop_in` | 多久后自动销毁环境（只适合 review 临时环境） | `1 week` / `2 days` |
| `action: stop` | 停止环境的 Job 里写，配合 `on_stop` 用（见下节） | 见 4.3.8 |

#### 4.3.7.3 when: manual 和 allow_failure 的组合

```yaml
# 组合 A：prod 常用——不按按钮不跑；按了就必须成功（失败则 pipeline 整体失败）
deploy:prod:
  when: manual
  allow_failure: false    # ← 关键
```

```yaml
# 组合 B：stage 常用——不按按钮不跑；即使不按，pipeline 也算成功（不阻塞）
deploy:stage:
  when: manual
  allow_failure: true     # 默认值
```

### 4.3.8 动态环境（MR 临时 Review 环境）

#### 4.3.8.1 这是什么场景？

每个 MR 都自动部署一个**独立的临时环境**，QA 直接在浏览器访问验证，不用在本地搭。验证完后自动销毁。

```
MR !123 (feature/login) → 部署到 https://login.review.example.com → QA 验证 → MR 关闭 → 自动销毁
```

#### 4.3.8.2 配置示例

```yaml
# 1. 启动 review 环境的 Job
deploy:review:
  stage: deploy
  environment:
    # 每个 MR 一个独立环境名（$CI_COMMIT_REF_SLUG = 分支名转 URL 安全格式）
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    # 关键：当 MR 被合并/关闭时，自动触发下面的 stop_review Job
    on_stop: stop_review
    auto_stop_in: 3 days    # 3 天不用了也自动销毁（兜底）
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - helm upgrade --install review-$CI_COMMIT_REF_SLUG ./charts
      --set image.tag=$CI_COMMIT_SHORT_SHA
      --set domain=$CI_COMMIT_REF_SLUG.review.example.com

# 2. 清理 review 环境的 Job（被 on_stop 自动触发）
stop_review:
  stage: deploy
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop            # 告诉 GitLab：这是停止环境的 Job
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: manual
  script:
    - helm uninstall review-$CI_COMMIT_REF_SLUG
```

#### 4.3.8.3 on_stop 触发时机一览

| 事件 | 是否触发 `on_stop: stop_review`？ |
| ---- | ------------------------------- |
| MR 被合并（merged） | ✅ 触发 |
| MR 被关闭（closed，未合并） | ✅ 触发 |
| MR 原分支被删除 | ✅ 触发 |
| `auto_stop_in` 时间到 | ✅ 触发 |
| 只是 commit push（MR 继续开着） | ❌ 不触发 |

> 这个机制适合你公司的 dev 环境：feature 分支 merge 到 dev 时部署，独立环境互不干扰，稳定后再推进。

### 4.3.9 变量体系：masked / protected / 优先级（masked 重点说明）

> masked 概念你要求细化，放这里最合适（变量与凭据的交叉点），同时 [4.8.2 节](#482-gitlabmasked-变量-vs-protected-变量重点) 再横向与其他工具对比。

在 GitLab 项目 UI → Settings → CI/CD → Variables 里添加变量时，有两个关键 checkbox：

```
┌──────────────────────────────────────────────┐
│ Add variable                                 │
│                                              │
│ Key     : DB_PASSWORD                        │
│ Value   : *******                            │
│ Type    : Variable                           │
│                                              │
│ ☑️ Protect variable       ← protected 变量    │
│ ☑️ Mask variable          ← masked 变量       │
│                                              │
│ [ Add variable ]                             │
└──────────────────────────────────────────────┘
```

#### 4.3.9.1 Masked 变量（防止日志泄露）

**作用**：如果变量值不小心出现在 CI 日志里（比如脚本里写了 `echo $DB_PASSWORD`），会被自动替换成 `[MASKED]`，不会真正打印。

**真实效果**：

```bash
# 你的脚本里写了
echo "My password is: $DB_PASSWORD"

# 但 CI 日志里实际看到的是
My password is: [MASKED]
```

**Masked 变量的限制条件（变量值必须满足，不然 mask 不生效）**：

| 限制 | 说明 |
| ---- | ---- |
| 长度 | 8 到 1024 字符之间（太短 GitLab 不 mask，防止误 mask 通用词） |
| 字符集 | 只能包含大小写字母 + 数字 + `@ : . ~ _ - / += , # |` |
| 包含换行符 | ❌ 不允许（多行长密钥用 base64 编码再 mask） |
| 开头结尾空格 | ❌ 不允许（自动 trim，这是常见坑） |

> 常见坑：SSH 私钥有换行符，直接 mask 不行，做法是把私钥做 base64：
> ```
> # 本地：
> base64 -w0 ~/.ssh/deploy_key > deploy_key.b64
> # UI 里把 deploy_key.b64 内容配置成变量 SSH_KEY_B64（masked）
> # CI 里使用：
> echo $SSH_KEY_B64 | base64 -d > ~/.ssh/deploy_key
> ```

#### 4.3.9.2 Protected 变量（防止被非受保护分支读到）

**作用**：变量**只能在受保护分支/受保护 tag 的流水线里才能被读到**。feature 分支/MR 的流水线读不到。

| 分支类型 | 能不能读到 protected 变量？ |
| -------- | -------------------------- |
| `main` / `master`（默认受保护） | ✅ 能 |
| `dev` / `test` / `stage`（如果你在项目里设置为 protected） | ✅ 能 |
| 任意 `feature/*` 分支（不受保护） | ❌ 不能 |
| 任意 MR（merge_request_event） | ❌ 不能（因为 MR 可能来自 fork 项目，安全隔离） |

#### 4.3.9.3 Masked + Protected 组合速查表

| 场景 | Protected？ | Masked？ | 原因 |
| ---- | :---------: | :------: | ---- |
| prod 的 DB 密码 | ✅ 是 | ✅ 是 | 只能 main 分支读 + 日志不泄露 |
| stage 的 DB 密码 | ✅ 是 | ✅ 是 | 同上 |
| Docker Registry 密码 | ✅ 是 | ✅ 是 | 只能受保护分支推镜像 |
| 普通全局变量（如 `APP_HTTP_PORT`） | ❌ 否 | ❌ 否 | 不敏感，所有分支都能用 |
| 测试用的假 API Key | ❌ 否 | ❌ 否 | MR 里要用来跑测试，不能 protected |

> 你公司的配置里，部署机的 `SSH_PRIVATE_KEY` 一定是 `protected + masked` 双勾选。

### 4.3.10 综合实战：分支即环境的完整 CI 配置（对应 P1.3 实践）

> 本节把前面学的 `workflow:rules`（4.3.2）+ `environment`（4.3.7）+ `when: manual`（4.3.7.3）+ 变量体系（4.3.9）综合起来，实现你的 [P1.3 环境晋升触发机制与门禁设计](./我的实践记录.md#p13-环境晋升触发机制与门禁设计p1-子增强)。

#### 4.3.10.1 实践回顾：P1.3 的触发策略

| 环境 | 触发方式 | 门禁机制 |
| ---- | -------- | -------- |
| dev | push 自动触发 | 无（全自动） |
| test | push 自动触发 | 无（全自动） |
| stage | push 自动触发 | **人工确认部署** |
| main | push 自动触发 CI | **只验证不发布** |
| prod | **打 Tag 手动触发** | 人工打 Tag |

#### 4.3.10.2 完整 .gitlab-ci.yml

```yaml
# ============================================================
# 分支即环境：dev / test / stage / main(prod) + Tag 发版
# 对应 P1.3 实践：两段式机制（合入 main 只验证，打 Tag 才发布）
# ============================================================

stages:
  - lint
  - test
  - build
  - deploy

# --- 全局变量 ---
variables:
  IMAGE_NAME: "$CI_REGISTRY_IMAGE"
  # 镜像 tag 用 commit short SHA，每次构建唯一
  IMAGE_TAG: "$CI_COMMIT_SHORT_SHA"

# --- workflow:rules 控制整条 pipeline 是否创建 ---
workflow:
  rules:
    # dev/test/stage/main 分支 push → 创建 pipeline
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    # 打 Tag → 创建 pipeline（生产发布）
    - if: $CI_COMMIT_TAG
    # MR 事件 → 创建 pipeline（跑 lint + test，不部署）
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    # 其他情况不创建 pipeline（feature 分支 push 不白跑）
    - when: never

# ============================================================
# Stage 1: Lint（所有环境都跑，快速失败）
# ============================================================
lint:
  stage: lint
  image: python:3.12-slim
  needs: []                    # 不等任何前置，pipeline 创建就立刻跑
  script:
    - pip install ruff
    - ruff check app/
  rules:
    - when: on_success         # 默认都跑

# ============================================================
# Stage 2: Test（所有环境都跑）
# ============================================================
test:
  stage: test
  image: python:3.12-slim
  needs: [lint]                # DAG：lint 过了就跑，不等 build
  script:
    - pip install -r requirements.txt pytest pytest-cov
    - pytest --cov=app --cov-report=xml:coverage.xml
  artifacts:
    when: always
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
      junit: test-results.xml
  rules:
    - when: on_success

# ============================================================
# Stage 3: Build（所有环境都构建镜像）
# ============================================================
build:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  needs: [test]
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile Dockerfile
      --destination $IMAGE_NAME:$IMAGE_TAG
      --cache=true
  rules:
    # main 分支 push → 只构建不发布（两段式机制：合入 = 验证）
    # Tag → 构建 + 后续发布
    # dev/test/stage → 构建 + 后续部署对应环境
    - when: on_success

# ============================================================
# Stage 4: Deploy（各环境触发策略不同）
# ============================================================

# --- dev 环境：push 自动部署，无门禁 ---
deploy:dev:
  stage: deploy
  needs: [build]
  environment:
    name: dev
    url: https://dev.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "dev"
  script:
    - echo "Deploy to dev"
    - kubectl set image deployment/app app=$IMAGE_NAME:$IMAGE_TAG -n dev
    # 健康检查
    - kubectl rollout status deployment/app -n dev --timeout=120s

# --- test 环境：push 自动部署，无门禁 ---
deploy:test:
  stage: deploy
  needs: [build]
  environment:
    name: test
    url: https://test.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "test"
  script:
    - echo "Deploy to test"
    - kubectl set image deployment/app app=$IMAGE_NAME:$IMAGE_TAG -n test
    - kubectl rollout status deployment/app -n test --timeout=120s

# --- stage 环境：CI 通过后人工确认才部署 ---
deploy:stage:
  stage: deploy
  needs: [build]
  environment:
    name: staging
    url: https://stage.example.com
    deployment_tier: staging
  when: manual                 # ← 关键：人工确认
  allow_failure: false         # ← 按了就必须成功（否则 pipeline 失败）
  rules:
    - if: $CI_COMMIT_BRANCH == "stage"
  script:
    - echo "Deploy to stage (manual confirmation)"
    - kubectl set image deployment/app app=$IMAGE_NAME:$IMAGE_TAG -n stage
    - kubectl rollout status deployment/app -n stage --timeout=180s

# --- main 分支 push：只验证不发布 ---
# 合入 main → CI 全跑（lint/test/build），但不部署到 prod
# 这是 P1.3 的"两段式机制"第一阶段
deploy:main:verify:
  stage: deploy
  needs: [build]
  environment:
    name: production-verify    # 注意：不是 production，只是验证
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  script:
    - echo "main 分支 push → CI 验证通过，不部署到 prod"
    - echo "等待发版窗口打 Tag 才会触发生产部署"
  # 这个 Job 不做实际部署，只是占位让 pipeline 完整

# --- prod 发布：只有打 Tag 才触发 ---
# 这是 P1.3 的"两段式机制"第二阶段
deploy:prod:
  stage: deploy
  needs: [build]
  environment:
    name: production
    url: https://app.example.com
    deployment_tier: production
  rules:
    - if: $CI_COMMIT_TAG       # ← 关键：只有打 Tag 才触发
  script:
    - echo "Release $CI_COMMIT_TAG → Deploy to prod"
    - kubectl set image deployment/app app=$IMAGE_NAME:$IMAGE_TAG -n prod
    - kubectl rollout status deployment/app -n prod --timeout=300s
    # 发版后打 Slack 通知
    - |
      curl -X POST $SLACK_WEBHOOK -d "{\"text\": \"🚀 Released $CI_COMMIT_TAG to prod\"}"
```

#### 4.3.10.3 配置逐段解析

| 配置块 | 对应 P1.3 设计 | 关键字段 |
| ------ | -------------- | -------- |
| `workflow:rules` | 只 4 条环境分支 + Tag + MR 创建 pipeline | `if: $CI_COMMIT_BRANCH =~ /^(dev\|test\|stage\|main)$/` |
| `lint` / `test` / `build` | 所有环境全跑（验证阶段） | `when: on_success` |
| `deploy:dev` | dev 自动部署，无门禁 | `if: $CI_COMMIT_BRANCH == "dev"` |
| `deploy:test` | test 自动部署，无门禁 | `if: $CI_COMMIT_BRANCH == "test"` |
| `deploy:stage` | stage 人工确认 | `when: manual` + `allow_failure: false` |
| `deploy:main:verify` | main 只验证不发布（两段式第一阶段） | `if: $CI_COMMIT_BRANCH == "main"`，不做实际部署 |
| `deploy:prod` | 打 Tag 才发布（两段式第二阶段） | `if: $CI_COMMIT_TAG` |

#### 4.3.10.4 两段式机制的 pipeline 表现

```
场景 1：feature 合入 main（只验证不发布）
  workflow:rules 匹配 main → 创建 pipeline
  lint ✅ → test ✅ → build ✅ → deploy:main:verify ✅（只 echo，不部署）
  pipeline 绿 → main 保持稳定，等待发版窗口

场景 2：发版窗口打 Tag v1.2.0
  workflow:rules 匹配 $CI_COMMIT_TAG → 创建 pipeline
  lint ✅ → test ✅ → build ✅ → deploy:prod ✅（实际部署到 prod + Slack 通知）
  pipeline 绿 → v1.2.0 发布成功

场景 3：feature 合入 stage
  workflow:rules 匹配 stage → 创建 pipeline
  lint ✅ → test ✅ → build ✅ → deploy:stage ⏸️（等人工点按钮）
  人工确认 → 部署到 stage ✅
  人工不确认 → pipeline 卡在 deploy:stage，不算失败也不算成功
```

#### 4.3.10.5 常见坑

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| `when: manual` 的 Job 不点不算失败 | stage 人工确认如果不点，pipeline 默认是 "passed with manual job"，不算失败 | 如果要求"必须确认才算发版完成"，用 `allow_failure: false` |
| `deploy:main:verify` 看起来多余 | 有人觉得 main 分支 build 完了直接结束就行，不需要一个 verify Job | 加这个 Job 是为了让 pipeline 有明确的 "deploy stage completed" 状态，方便外部系统（Slack/钉钉）监听 pipeline 状态 |
| Tag 触发时 `CI_COMMIT_BRANCH` 为空 | 打 Tag 时 `$CI_COMMIT_BRANCH` 是空的，不能用 `$CI_COMMIT_BRANCH == "main"` 判断 | Tag 触发用 `$CI_COMMIT_TAG`，分支触发用 `$CI_COMMIT_BRANCH` |
| feature 分支 push 不会创建 pipeline | `workflow:rules` 里 feature 分支被 `- when: never` 挡掉了 | 这是设计：feature 分支只通过 MR 跑 CI，不直接 push 触发 pipeline |
| stage 的 `environment.name` 写成 `stage` | GitLab 的 `deployment_tier` 有标准值，`staging` 才对应 `staging` 层级 | 用 `name: staging` + `deployment_tier: staging`，不要用 `stage`（容易和 `stage:` 字段混淆） |

### 4.4.2 声明式 Pipeline 完整示例

```groovy
pipeline {
  agent {
    // 用 K8s 动态 Pod
    kubernetes {
      yaml '''
        apiVersion: v1
        kind: Pod
        spec:
          containers:
          - name: python
            image: python:3.12-slim
            command: ['sleep', 'infinity']
          - name: docker
            image: docker:24
            command: ['sleep', 'infinity']
            securityContext:
              privileged: true
      '''
    }
  }

  options {
    timeout(time: 30, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
    disableConcurrentBuilds()
  }

  environment {
    IMAGE = "registry.example.com/app:${env.BUILD_NUMBER}-${env.GIT_COMMIT?.take(8) ?: 'unknown'}"
  }

  stages {
    stage('Checkout') {
      steps {
        checkout scm
      }
    }

    stage('Lint') {
      steps {
        container('python') {
          sh 'pip install ruff'
          sh 'ruff check app/'
        }
      }
    }

    stage('Test') {
      steps {
        container('python') {
          sh 'pip install -r requirements.txt pytest pytest-cov'
          sh 'pytest --cov'
        }
      }
      post {
        always {
          junit 'reports/**/*.xml'
          publishCoverage adapters: [cobertura('coverage.xml')]
        }
      }
    }

    stage('Build') {
      steps {
        container('docker') {
          sh "docker build -t ${IMAGE} ."
          sh "docker push ${IMAGE}"
        }
      }
    }

    stage('Deploy') {
      when {
        branch 'main'
      }
      steps {
        input(message: 'Deploy to production?', ok: 'Deploy')
        sh "kubectl set image deployment/app app=${IMAGE}"
      }
    }
  }

  post {
    success { echo 'Pipeline succeeded' }
    failure { echo 'Pipeline failed' }
    always {
      archiveArtifacts artifacts: 'dist/**/*', allowEmptyArchive: true
    }
  }
}
```

## 4.6 Runner / Agent 体系对比与选型

### 4.6.1 三工具的执行器对比

**表 4-3：Runner / Agent 体系对比**

| 维度 | GitHub Actions | GitLab CI | Jenkins |
| ---- | -------------- | --------- | ------- |
| **云托管** | GitHub-hosted | SaaS 自带 | 无（CloudBees 商业版有） |
| **自建** | Self-hosted Runner | GitLab Runner | Jenkins Agent |
| **executor 类型** | VM/容器（一 Job 一 VM） | shell / docker / kubernetes / parallels | shell / docker / kubernetes |
| **推荐类型** | GitHub-hosted（公网）/ Self-hosted（内部） | docker（默认）/ kubernetes（大规模） | docker / kubernetes |
| **隔离粒度** | 一 Job 一 VM（最强） | 一 Job 一容器（中） | 一 Job 一容器/节点（中） |
| **扩缩容** | 手动加 Runner / K8s mode | K8s mode 自动扩缩 | K8s Plugin 自动扩缩 |
| **缓存共享** | 同类 Runner 共享 | 同 Runner 共享 | 同节点共享 |
| **成本** | 2026-03 起 self-hosted 收费 | 自建免费 | 仅服务器成本 |

### 4.6.2 GitLab Runner executor 选择（重点）

| executor | 隔离 | 速度 | 复杂度 | 推荐场景 |
| -------- | ---- | ---- | ------ | -------- |
| shell | 差（共享宿主，密钥/进程都能看到） | 最快 | 低 | **不推荐**（安全风险，参见 S5） |
| docker | 中（每 Job 一容器，用完销毁） | 快 | 中 | **小团队首选** |
| kubernetes | 强（每 Job 一 Pod，强隔离 + 自动扩缩） | 中（调度开销） | 高 | **大规模/K8s 团队** |
| parallels | 中（macOS VM） | 慢 | 高 | iOS/macOS 构建 |

> 详细安全分析参见 [S5 流水线自身安全](./补充专题/S5-流水线自身安全.md)。

## 4.7 复用机制对比

### 4.7.1 三工具的复用方案

**表 4-4：复用机制对比**

| 维度 | GitHub Actions | GitLab CI | Jenkins |
| ---- | -------------- | --------- | ------- |
| **step 级复用** | Composite Action | Hidden Job (`.` 前缀) | Shared Library 函数 |
| **流水线级复用** | Reusable Workflow | include / Components | Shared Library 标准化 Pipeline |

- **Jenkins**：Shared Library 是唯一选择，但门槛高（Groovy）

## 4.8 凭据与密钥管理对比

### 4.8.1 三工具的凭据机制对照

**表 4-5：凭据与密钥管理对比**

| 维度 | GitHub Actions | GitLab CI | Jenkins |
| ---- | -------------- | --------- | ------- |
| **存储位置** | Settings → Secrets | Settings → CI/CD → Variables | Credentials Store / Folder Credentials |
| **加密存储** | 是（libsodium） | 是（数据库加密） | 是（JCI 加密） |
| **日志脱敏** | 自动 `::add-mask::`（密钥变量自动） | **masked 变量自动脱敏** | `MaskPasswordsBuildWrapper` 插件 |
| **环境级凭据** | `environment` + Protection | `environment` + **Protected Variables** | Folder + Role-based |
| **OIDC 支持** | 原生（`permissions: id-token: write`） | 原生（GitLab 16+） | 插件（AWS Credentials 等） |
| **轮换** | 手动 / API | 手动 / API | Credentials 更新插件 |
| **审计** | Audit Log | Audit Log | Audit Trail 插件 |

### 4.8.2 GitLab：masked 变量 vs protected 变量（重点）

> **本节是 masked 概念的专门细化**，承接 4.3.9 节。这两个 checkbox 在 UI 里紧邻，但作用完全不同——**一个管"看不看得见"，一个管"能不能读"**。

#### 4.8.2.1 功能区别

| | **masked（Mask variable）** | **protected（Protect variable）** |
| - | --------------------------- | -------------------------------- |
| **保护对象** | **CI 日志里泄露** | **被非受保护分支读取** |
| **保护逻辑** | 变量值出现在日志时替换成 `[MASKED]` | 变量只在受保护分支/受保护 tag 的流水线里注入环境 |
| **变量本身能否被脚本读到？** | ✅ 能（正常 echo 会 mask 但值真实存在） | ❌ 非受保护分支里根本读不到（值为空） |
| **适用层** | 层 1：防止"**不小心打印了**" | 层 2：防止"**根本不该拿到的场景拿到了**" |

#### 4.8.2.2 组合的防御层次

```
第 1 层防御（protected）：
  只有 main/dev/test/stage（protected 分支）的流水线里才注入 DB_PASSWORD
  feature 分支 / 外部 MR 的流水线 → 变量为空，根本拿不到 ✅

第 2 层防御（masked）：
  即使在 main 分支里，脚本不小心写了 echo $DB_PASSWORD
  CI 日志显示 [MASKED]，值不会真正打印出来 ✅

第 3 层防御（审计）：
  变量访问、修改都在 GitLab Audit Log 里留痕
```

#### 4.8.2.3 masked 不生效的常见坑（结合真实项目）

| 现象 | 原因 | 解决 |
| ---- | ---- | ---- |
| 配了 masked，但日志里**还是打印了明文** | 变量值 < 8 字符；或包含非法字符（空格、换行、中文） | 改值或用 base64 编码后存 |
| `base64` 后的 SSH Key 配了 masked，但 CI 里解码后 `cat` 私钥又泄露了 | mask 只在 CI 日志处理时生效，你 `base64 -d` 后重新 `echo` 的内容不是原变量，GitLab 不会重新识别 | 解码后别 echo；用文件传递不打印到 stdout |
| 非 protected 分支的 MR 想跑测试要用真密钥（真的有需要） | protected 变量读不到（这是设计） | 单独建一组"测试用假凭据"，不勾 protected，MR 里用 |
| Mask 后想看变量是否真的 mask 了 | 不能通过 echo 验证（你看到 [MASKED] 就对了） | 写测试脚本把变量写文件，再 `wc -c` 看字节数是否符合预期 |

### 4.8.3 最佳实践（统一）

1. **OIDC 优先**：所有云部署用 OIDC，不用长期密钥（参见 [S1 Secret 管理](./补充专题/S1-Secret管理.md)）
2. **环境隔离**：dev / staging / prod 凭据分开，prod 凭据只能在 prod environment 里读（GitLab：environment + protected variables 双隔离）
3. **最小权限**：每个 pipeline 只给必需的凭据
4. **日志脱敏**：所有密钥变量都要 mask；多行长密钥用 base64
5. **定期轮换**：至少每季度轮换一次
6. **Protected 分支设置**：别只有 main，把 dev / test / stage 也加到 Protected Branches 列表里

## 4.9 现阶段最佳实践（2026）

### 4.9.1 三工具共通的实践

1. **流水线即代码**：所有配置入库，UI 配置只用于凭据和 Runner 注册
2. **Code Review CI 改动**：CI 配置改动与业务代码同等对待
3. **失败快停（Fail Fast）**：lint 放最前，贵的检查放后面
4. **缓存依赖**：pip / Maven / Docker layer 都要缓存
5. **制品命名规范**：`app-{gitSHA}-{buildNumber}`，不用 `latest` 部署生产
6. **第三方依赖锁版本**：Action 锁 SHA / Component 用 `@version` / Shared Library 用 `@tag` / **GitLab include/project 必须用 tag 不用 master**

### 4.9.2 各工具特有实践

#### GitHub Actions
- `permissions:` 显式声明最小权限
- `concurrency:` 控制同分支并发
- Reusable Workflow + Composite Action 双重复用
- 用 `environment` 做部署门禁

#### GitLab CI
- 用 `rules` 替代老 `only/except`
- 用 `needs` 构建 DAG，打破 stage 串行
- 新项目用 Components 替代 include；老项目 include 的 ref 必须锁 tag
- `workflow:rules` 控制 pipeline 是否创建（避免 feature 分支 push 白跑）
- **凭据双隔离**：所有敏感变量同时勾选 Protected + Masked
- **变量级别覆盖**：遇到 Job 变量值和预期不一样，按优先级表排查（4.3.1.2）

#### Jenkins
- 声明式 Pipeline（不用脚本式）
- Shared Library 用版本 tag
- 用 K8s Plugin 动态 Pod
- `options { disableConcurrentBuilds() }` 防并发

### 4.9.3 避坑指南（10 条）

1. **不要在 CI 里硬编码密钥**：用凭据系统或 OIDC
2. **不要用 `latest` 部署生产**：用 gitSHA 或语义版本
3. **CI 不要直连生产 DB 跑迁移**：迁移脚本进制品，部署时执行（参见 [S6](./补充专题/S6-数据库迁移.md)）
4. **Self-hosted Runner 不跑公网 PR**：零信任输入
5. **第三方 Action 不用浮动 tag**：锁 SHA
6. **缓存 key 要带 lockfile hash**：避免缓存陈旧依赖
7. **矩阵测试不要 fail-fast**：除非确定有强依赖
8. **Jenkins 不要用 UI 配置 Pipeline**：全部 Jenkinsfile
9. **GitLab 不要用 `only/except`**：用 `rules`
10. **GitHub Actions 不要用 `${{ }}` 注入到 run**：用 env 中转，防注入

### 4.10.2 现阶段最佳实践速记（2026）

- 三工具都用 YAML（除 Jenkins 用 Groovy），核心概念高度相通
- 复用机制：Actions 用 Reusable + Composite，GitLab 用 Components（老项目 include 锁 tag），Jenkins 用 Shared Library
- 凭据：GitLab 必勾选 Protected + Masked 双隔离；GitHub 用 Environment Protection；OIDC 优先
- Runner：docker executor 优先，shell executor 不推荐
- 第三方依赖必锁版本（SHA / tag / include 的 ref）
- 流水线即代码，CI 改动必须 Code Review
