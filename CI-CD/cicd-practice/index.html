    P1. 分支即环境（dev / test / stage / main = prod）¶

    P1.1 做法¶

    仓库长期维护四个分支，main 即 prod 环境。每个 feature 独立合入通过验证的环境，不做逐级 merge，防止 dev 里未通过的功能污染下游：

    图 P1-1：P1 模型的 feature 推进链路
┌──────────────────────────────────────────────────────────────────────┐
│                     main (v1.0 = prod, 演化终点站)                    │
│                                                                      │
│  ┌── 切出 feature/f1 ───────────────────────────────────────────┐    │
│  │                                                               │    │
│  │  开发完成                                                     │    │
│  │   ├──── merge ─────► dev 环境（f1 进入开发验证，可含任意在途）   │    │
│  │   │                 dev 验证通过 ✅                            │    │
│  │   ├──── merge ─────► test 环境（只合 f1，不带 dev 其他代码）    │    │
│  │   │                 QA 通过 ✅                                 │    │
│  │   ├──── merge ─────► stage 环境（只合 f1，与 dev/test 独立）    │    │
│  │   │                 预发通过 ✅                                 │    │
│  │   └──── merge ─────► main = prod（只合 f1）→ 打 Tag v1.1       │    │
│  │                                                               │    │
│  └── 切出 feature/f2 ──► dev ──►（不通过则终止，下游零污染）         │    │
│                                                                      │
│  └── 切出 feature/f3 ──► dev ──► test ──► ...（各自独立推进）        │    │
└──────────────────────────────────────────────────────────────────────┘

    P1.2 关键特征（7 条）¶

    1. main = prod：main 是演化终点站，不是独立 prod 分支
    2. feature 从 main 切出：所有新功能基于"线上稳定状态"开发（保证基线天然对齐）
    3. feature 独立合入每个环境：从 feature 分支合 dev、合 test、合 stage、合 main，不做 dev→test→stage 逐级 merge
    4. 下游环境零污染：dev 里未通过的 feature 不会被意外带入 test/stage/main，因为下游环境永远只合"已单独确认的 feature 分支"
    5. 冲突在 feature 合入时各自消化：到 main 时冲突已在前面几次合入中解决，main 保持稳定
    6. 发版 = main 打 Tag（详见 P1.1）
    7. 应急机制：dev 被"坏代码"污染时，从 main 重新切 dev，开发重新 merge 仍需保留的 feature

    P1.3 模型归类¶

    这是 GitFlow 环境化变体的改良版，核心创新在于打破逐级 merge、改为 feature 独立合入每个环境。

    表 P1-1：P1 与经典 GitFlow / 纯 GitFlow 变体对比

    维度 经典 GitFlow 纯 GitFlow 变体（逐级 merge） P1（feature 独立合入）
    feature 切出 从 develop 切 从 main 切 从 main 切
    环境合入 develop → release → main dev → test → stage → main（逐级） feature → dev/test/stage/main（独立）
    下游污染风险 中（release 包含整个 develop） 中（test 包含整个 dev） 低（只合指定 feature）
    推进控制粒度 批次级 环境级 单 feature 级

    P1.4 适用场景¶

    • 小团队、传统行业、强合规（每个环境晋升都需要显式 merge 审批）
    • 发布频率不高（按周/按迭代）
    • 运维侧心智模型偏好"分支可见即环境可见"

    P1.5 优点（8 条）¶

    1. 心智模型直观：分支与环境一一对应，新人 5 分钟看懂。
    2. 晋升有强制把关：每个 feature 合入各环境都要单独 merge，天然带 Code Review，环境晋升不会"偷偷"发生。
    3. main 永远等于线上：main = prod，hotfix 直接从 main 切，无分叉问题。
    4. 下游环境零污染：P1 最精妙的设计——不做逐级 merge，test/stage/main 永远只合"已单独确认的 feature 分支"，dev 里的坏代码、未通过功能绝不可能意外流入下游。
    5. 推进控制粒度最细：单 feature 级推进，可以精确控制"每个功能进哪个环境"，比逐级 merge（批次级）灵活得多。
    6. 基线天然对齐：feature 从 main 切，新合入的代码天然与 main 基线一致，正常流程下基线漂移很小。
    7. 应急机制清晰：dev 被坏代码污染时直接从 main 重置，不用纠结"怎么把坏代码从 dev 退出来"。
    8. 回滚语义清晰：生产出问题，回滚 = main 回退到上一个 Tag（详见 P1.1）。

    P1.6 局限（7 条）¶

    1. 同一 feature 要 merge 多次 = 4 次冲突处理 + 4 次构建
    2. f1 分别合 dev、合 test、合 stage、合 main，可能遇到 4 次冲突，每次都要解决一遍；同时构建 4 次，严格意义上是 4 个不同制品。
    3. 逐级 merge 模型只需要解决第一次（dev）的冲突，下游是快进合并。

    4. 权衡：用"重复处理冲突"换来了"下游零污染"，安全与效率的典型 trade-off。

    5. 卡住的 feature 会积累成基线漂移（低环境）

    6. 前提：正常流程下基线漂移很小（feature 从 main 切，推进到 main 后代码两边一致）。
    7. 问题：当某个 feature 卡在 dev/test（因业务搁置、优先级下调），长期不到 main，dev/test 会逐渐积累 main 没有的代码。

    8. 解法：长期卡住的 feature 要么推进要么废弃；定期（每迭代）评估 dev 上遗留 feature 的去留。

    9. 应急重置 dev 后"被遗忘的 feature"风险

    10. dev 从 main 重置时，必须确保所有"仍需保留但还没到 main"的 feature 分支重新合到新 dev。
    11. 若开发团队沟通不到位，可能出现"某个 feature 在旧 dev 上存在、重置后被忘了合"的情况。

    12. 解法：重置前发公告，列出所有在途 feature 分支，确认哪些要重新合。

    13. 违背"不可变制品"原则（最大的结构性差距）

    14. f1 合 dev 构建一次制品、合 test 再构建一次、合 stage 一次、合 main 一次——同一 feature 构建 4 次，严格意义上是 4 个不同制品。
    15. 业界共识：同一份制品应原封不动地推过所有环境，只改配置不改制品。

    16. 这是从 P1 升级到现代 GitOps 模型的最核心跃迁点。

    17. 环境晋升 ≠ 版本号管理

    18. merge 是代码流动作，但"test 环境当前跑了哪些 feature"在 P1 模型下不直观，需要查 test 分支的 merge 历史。

    19. 现代实践中，版本号（如 v1.2.0）是制品的唯一标识，哪个环境跑哪个版本一目了然。

    20. 并行多版本困难

    21. 同时在 test 测 v1.2、在 main 热修 v1.1，分支拓扑会拧成麻花。

    22. 不符合 2026 主流 Trunk-based 趋势

    23. 主流方向是"单一主干 + 版本号/Tag 驱动环境"，分支数越少越好。

    P1.1. 发版打 Tag + 手动触发重发（P1 子增强：审计 / 回滚）¶

    P1.1.1 做法¶

    前置机制（详见 P1.3.3）：feature 合入 main 只触发 CI 验证（Lint + Build + Test + Security Scan），不触发生产部署；只有打 Tag 才触发生产发布流程。这是 main 的"两段式机制"——合入 = 验证，打 Tag = 发布。

    • 每个敏捷周期发版时，在 main 分支上打 Tag（如 v1.2.0）
    • Tag 作为该次发版的可审计快照，记录"这次上线跑的是哪个代码版本"
    • 后续两种典型操作：
    • 审计：查 Tag 即知某次发版对应代码
    • 回退/重发：手动点击某个历史 Tag → 重新触发该版本的 CI/CD 流程

    P1.1.2 价值：已触及现代实践的边缘¶

    打 Tag 这一步已经半只脚踏进"版本号驱动环境"：

    表 P1.1-1：P1 vs P1.1 vs 现代不可变制品，五维对比

    维度 纯分支即环境（P1） + 打 Tag（P1.1） 现代不可变制品
    环境状态可见性 看分支 HEAD commit 看 Tag 列表 看部署仓版本号
    审计追溯 查 commit 历史 查 Tag 即可 查制品仓 + 部署仓
    回滚操作 回退分支 commit 点 Tag 重发 revert 部署仓版本号 PR
    制品复用 每次重新构建 可能重新构建 同一制品原样推过各环境
    配置与代码解耦 否 否 是

    P1.1.3 与现代实践的关键差距（3 条）¶

    1. Tag 标记的是"代码版本"，不是"制品版本"
    2. 点 Tag 重发时，CI 会重新构建一次制品。
    3. 严格意义上，重新构建出来的镜像/包与原版本不是同一个制品（构建时间、底层依赖版本可能漂移）。
    4. 现代实践要求："回滚 = 把同一个镜像重新拉起来"，而不是"用同一份代码再构建一次"。

    5. 这个差异在合规审计严格的场景（金融/医疗）会被重点追问。

    6. 配置仍随分支走

    7. dev 分支和 prod 分支里的配置文件（数据库地址、密钥引用）可能不同。

    8. 现代实践是：制品里不含环境配置，配置由部署环境注入（ConfigMap / Secret / 环境变量）。

    9. Tag 重发是手动动作，缺自动化护栏

    10. "手动点击 Tag 重发"依赖操作者的判断，没有自动化的"该 Tag 是否通过了所有环境门禁"校验。
    11. 现代实践：部署系统会拒绝部署"没在低环境验证过"的版本。

    P1.1.4 一句话评价¶

    P1.1 是面向审计与回滚的实用增强，在传统团队里已经是相当不错的实践。
    它的局限不在"打 Tag"这个动作本身（现代 GitOps 也打 Tag），而在于"Tag 驱动的是代码重建，不是制品复用"。

    P1.2. 团队协作模式——"先合完的人闲着吗？"（P1 子讨论）¶

    P1.2.1 场景¶

    敏捷迭代中，a、b、c 三人任务量不同，a 先完成并合入了当前发版分支。b、c 还在开发。

    P1.2.2 P1 模式下的实际工作流（用户真实做法）¶

    实际做法并不是"批次制空等"，而是短期 feature 分支模式：

    图 P1.2-1：a 不会空等 —— f1 发版链路与 f2 开发解耦
┌────────────────────────────────────────────────────────────┐
│  a 从 main 切 feature/f1 → 开发 → 合 dev → 合 test → 合 stage → 合 main │
│                                 │                            │
│                                 ▼  还没到发版窗口             │
│  a 从 main 切 feature/f2 → 开发 f2                            │
│     （f2 的开发与 f1 在 dev→test→stage→main 的链路完全独立）  │
│                                 │                            │
│                                 ▼  发版窗口到                 │
│  a 关注 f1 发版 → 没问题 → 拉最新 main → 把 f2 合 dev 继续推进 │
└────────────────────────────────────────────────────────────┘

    这本质是"短期 feature 分支 + 主干集成"，已接近 Trunk-based。结论：a 并不会结构性空等，f2 的开发与 f1 的发版流程互不干扰。

    P1.2.3 Trunk-based + Feature Flag 模式下的对照¶

    图 P1.2-2：Trunk-based + Flag 推进示意
┌──────────────────────────────────────────────────────────┐
│  a 合 main [Flag: OFF] → a 立刻接下个任务（合 main，新 Flag 关） │
│  b 合 main [Flag: OFF] → 不受 a 干扰                        │
│  c 合 main [Flag: OFF] → 不受 a/b 干扰                      │
│                                                           │
│  发版窗口到 → 挑出"本次要开启的 Flag 集合"发布               │
│              （未完成的 Flag 保持 OFF，不阻塞发版）          │
└──────────────────────────────────────────────────────────┘

    a 可以立刻做的事：
    1. 接下个迭代任务（合 main，新 Flag 关闭，与当前版本无关）
    2. 帮 b、c 做 Code Review、补测试、做重构、还技术债
    3. 提前做发版准备（E2E、灰度计划）

    P1.2.4 真正的差距：环境晋升最小单位（不是团队协作）¶

    P1 与现代实践的真正差距不在团队协作（用户已用 feature 分支 + 独立合入解决了协作与污染问题），而在环境晋升的"最小单位"不同：

    表 P1.2-1：P1 vs GitOps，环境晋升模型六维对比

    环节 P1（用户实际做法） GitOps（现代实践）
    环境晋升最小单位 单 feature + 代码 merge（每个 feature 分别合 4 个环境） 不可变制品版本号（同一份制品推过所有环境，只改版本号）
    功能集成 feature 合 dev（从 main 切） feature 合 main（直接合主干）
    制品构建次数 同一 feature 合 4 个环境 = 构建 4 次（4 个不同制品） 构建 1 次，同一份制品原封不动推过所有环境
    f1 在 dev 流动期间 f1 独立推进，main 不变化；其他 feature 各自独立推进 main 持续演进，prod 跑某个镜像 SHA，与 main HEAD 解耦
    环境推进可追溯性 查各分支的 merge 历史（4 条分支 × N 个 feature） 查部署仓的 commit 历史（一个仓库、一个版本号字段）
    回滚 回退 main 到上一个 Tag / 点 Tag 重发（重建制品） revert 部署仓版本号 PR（复用制品，秒级回滚）

    P1.2.5 P1 模型真正的两个痛点（修正后）¶

    1. 同一 feature 要 merge 多次 = 多次冲突处理 + 多次构建
    2. f1 分别合 dev、合 test、合 stage、合 main，可能遇到 4 次冲突，每次都要解决一遍；同时构建 4 次，严格意义上是 4 个不同制品。

    3. 这是"零污染"带来的效率成本，安全与效率的典型 trade-off。

    4. 环境晋升是"代码 merge"而非"制品版本号推进"

    5. 这是与现代 GitOps 模型的最大结构性差距。
    6. 现代实践中，制品在构建阶段只产生一次（带唯一 SHA/Signature），"推进环境"只是改部署仓里的版本号字段，制品本身不变。
    7. 与 P1.1 的"Tag 标记代码版本而非制品版本"一脉相承。

    P1.2.6 核心认知跃迁¶

    P1 → 现代实践的升级，不是"让 a 不闲"（a 本来就不闲），而是把环境晋升从"代码动作"升级为"制品版本号动作"。

    P1.3. 环境晋升触发机制与门禁设计（P1 子增强）¶

    本节记录各环境的触发方式与门禁设计，是 P1 模型"怎么从代码到上线"的操作层补充。

    P1.3.1 feature 合入各环境的操作规范¶

    feature 开发完成后，按以下步骤合入目标环境分支：

    1. 本地拉取目标环境最新代码（如 git fetch origin dev && git checkout dev && git pull）
    2. 将 feature 分支 merge 到本地环境分支（如 git merge feature/f1，在本地解决冲突）
    3. push 到远程（git push origin dev）
    4. push 成功后自动触发该环境的 CI/CD 流程
    图 P1.3-1：feature 合入操作链路
┌─────────────────────────────────────────────────────────────┐
│  本地 feature/f1 开发完成                                     │
│    │                                                         │
│    ▼  git fetch + pull 目标环境最新代码                       │
│  本地 dev（最新）                                             │
│    │                                                         │
│    ▼  git merge feature/f1（本地解决冲突）                    │
│  本地 dev（含 f1）                                            │
│    │                                                         │
│    ▼  git push origin dev                                    │
│  远程 dev 分支更新 → 自动触发 dev 环境 CI/CD                   │
└─────────────────────────────────────────────────────────────┘

    关键点：冲突在本地解决，不推到远程让别人处理；push 即触发，无需额外手动操作。

    P1.3.2 各环境触发策略与门禁（核心设计）¶

    表 P1.3-1：四环境 + 发版的触发策略与门禁

    环境 触发方式 门禁机制 说明
    dev push 自动触发 无（全自动） 开发验证环境，快速反馈
    test push 自动触发 无（全自动） QA 测试环境，自动部署
    stage push 自动触发 人工确认部署 CI 通过后需人工确认才部署到预发
    main push 自动触发 CI 只验证不发布 合入 main 只跑 CI 验证，不触发生产部署
    prod 打 Tag 手动触发 人工打 Tag 只有打 Tag 才触发生产发布流程

    P1.3.3 main 的两段式机制（关键设计）¶

    main 合入与生产发布是两个独立动作，这是 P1 模型最精妙的门禁设计之一：

    图 P1.3-2：main 的两段式机制
┌──────────────────────────────────────────────────────────┐
│  阶段一：feature 合入 main                                │
│  ┌──────────────────────────────────────────────────┐    │
│  │  git merge feature/f1 → main → push              │    │
│  │  → 触发 CI（Lint + Build + Test + Security Scan）  │    │
│  │  → CI 通过 ✅ → 不部署到 prod                      │    │
│  │  → main 分支保持稳定，等待发版窗口                  │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  阶段二：发版窗口打 Tag                                   │
│  ┌──────────────────────────────────────────────────┐    │
│  │  git tag v1.2.0 → push tag                       │    │
│  │  → 触发生产部署 Pipeline                           │    │
│  │  → 构建 → 推镜像 → 部署 prod → 健康检查             │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────┘

    为什么这样设计（3 条）：

    1. 合入 main ≠ 上线：避免"有人合入 main 就意外触发生产部署"，防止误操作
    2. 发版窗口统一管控：只有打 Tag 才真正发布，发版时机由人控制，不被代码合入节奏绑架
    3. main 持续保持 CI 绿：合入即验证，问题在合入时暴露，不留到发版时才发现

    P1.3.4 stage 人工确认的价值¶

    stage 是"最后一道关"，人工确认的 3 个价值：

    1. 防误推：自动流程可能因配置错误误部署，人工确认兜底
    2. 业务窗口意识：stage 部署到预发，需确认"现在适合预发吗"（如大促期间冻结）
    3. 合规审计：人工确认留有审批记录，满足合规要求

    P1.3.5 与现代实践的对照¶

    表 P1.3-2：P1.3 触发门禁 vs 现代 GitOps 门禁

    维度 P1.3（用户实践） 现代实践（GitOps）
    触发粒度 分支 push / Tag 版本号 PR
    门禁方式 stage 人工确认 + Tag 手动 环境晋升 PR 审批
    main 合入行为 只验证不发布 合入即构建制品，不等于部署
    发布触发 打 Tag 修改部署仓版本号 PR merge
    本质 分支 / Tag 驱动 制品版本号驱动

    对照 P1.2.4 的结论：P1 与现代实践的差距不在团队协作，而在环境晋升最小单位（代码 merge vs 制品版本号）。P1.3 的两段式机制已经触及"合入 ≠ 发布"的现代理念，只是触发载体仍是 Tag 而非制品版本号。

    §2. 业界 2026 主流替代方案（供学习时对照）¶

    本章节不是用户实践，而是用来与 P1 做对照升级参考。

    §2.A 方案 A：Trunk-based + Tag/版本号驱动环境¶

    • 单一 main 主干，所有人 PR 合并到 main
    • main 通过 CI → 打 Tag（如 v1.2.3-rc.1）→ 自动部署到 dev
    • dev 验证通过 → 手动/自动 promote 到 test（不改代码，只改"当前环境跑哪个 Tag"）
    • 以此类推到 stage → prod
    • 关键升级：环境晋升从"代码 merge"变成"版本号推进"，同一份制品原封不动走过所有环境。

    §2.B 方案 B：GitOps + 独立部署仓库 + 环境目录（进阶，2026 推荐）¶

    • 应用代码仓库：trunk-based，CI 只管构建镜像
    • 独立部署配置仓库，按环境分目录：
      图 §2.B-1：独立部署仓的环境目录结构
deploy/
├── dev/      # 镜像 tag: v1.2.3-rc.1
├── test/     # 镜像 tag: v1.2.2
├── stage/    # 镜像 tag: v1.2.1
└── prod/     # 镜像 tag: v1.2.0
    • 环境晋升 = 修改对应目录里的镜像版本号（一个 PR）
    • Argo CD / Flux 持续把部署仓库的期望状态同步到集群
    • 优势：代码与环境配置彻底解耦；环境状态可审计、可回滚（回滚 = revert 那个版本号 PR）。

    §2.C 方案 C：Release Flow（Microsoft 模式，折中）¶

    • main 主干日常开发
    • 发版时从 main 切 release/1.2 分支
    • 环境部署由 release 分支或其 Tag 驱动
    • 热修走 release 分支再反合并回 main
    • 介于 GitFlow 与 Trunk-based 之间，适合中等发布频率。

    §2.D 核心升级方向一句话¶

    从"分支驱动环境"升级到"制品版本驱动环境"：环境间流转的是同一个不可变制品，配置随环境变，制品不变。

    §3. 总结：不否定原实践¶

    P1（含 P1.1、P1.2）在小团队、强合规、低频发布场景下依然是合理选择，不要因为"主流变了"就认为它错。

    学习的目的不是"推翻过去"，而是"知道什么场景用什么模型，以及为什么"。

    §3 表 1：P1 各子部分的定位与升级方向

    子部分 当前状态（做得好的地方） 待升级方向
    P1 分支即环境 心智直观、合规友好、下游零污染、推进粒度最细 从"4 次代码 merge"升级为"1 次制品 + 版本号推进"
    P1.1 打 Tag 重发 审计与回滚的实用增强，已触及版本号驱动 Tag 从"标记代码 commit"升级为"标记制品 SHA + 签名"
    P1.2 团队协作 短期 feature 分支模式已接近 Trunk-based，a 不会空等 推进解耦从"feature 分支 + 独立合入"升级为"合主干 + Feature Flag"
    P1.3 触发门禁 两段式机制（合入验证 / Tag 发布）已触及"合入 ≠ 发布"理念；stage 人工确认合规友好 触发载体从"Tag"升级为"制品版本号 PR"
    总体主线 小团队、低频发布、合规场景下已经是不错的实践 升级主线 = 环境晋升最小单位从"代码 merge"→"制品版本号"
