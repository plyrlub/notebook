    10.1 流水线复用与模板化¶

    10.1.1 为什么要复用（DRY 原则在 CI/CD 中的应用）¶

    反模式：每个项目仓库里都有一份 .gitlab-ci.yml，10 个服务 = 10 份 300 行的 YAML，90% 内容相同（都是 lint → test → build → deploy）。某天要给所有服务加一个安全扫描 Job，需要改 10 个仓库的 10 份 YAML——漏改一个就是安全漏洞。

    复用后的效果：10 个服务的 .gitlab-ci.yml 各只有 10 行（引用公共模板），公共逻辑集中在 1 个 ci-templates 仓里。改 1 次，10 个服务全部生效。

    表 10-1：复用前 vs 复用后

    维度 复用前（每仓一份） 复用后（模板 + include）
    新服务接入 CI/CD 复制粘贴 300 行 YAML，改 1 小时 写 10 行 include，5 分钟
    全局变更（如加安全扫描） 改 N 个仓库，漏改风险高 改 1 个模板仓，全部生效
    流水线规范一致性 每个仓库自己一套，逐渐分化 统一模板，强制规范
    学习成本 新人要看每个仓的 CI 才知道怎么跑 看模板仓一次，所有仓都懂

    10.1.2 GitLab CI include + template + extends 三种复用机制¶

    机制一：include（引用外部 YAML 文件）

    # myapp/.gitlab-ci.yml（业务仓库，只有 10 行）
include:
  # 引用 ci-templates 仓的 Python 模板
  - project: 'devops/ci-templates'
    ref: 'v2.1.0'           # 锁定版本，不要用 main（防止模板改了炸所有项目）
    file: '/python/fastapi-base.yml'

  # 引用安全扫描模板
  - project: 'devops/ci-templates'
    ref: 'v2.1.0'
    file: '/security/sast-scan.yml'

# 只写本项目特有的配置
variables:
  APP_NAME: myapp
  SERVICE_PORT: "8000"

# 覆盖模板里的默认值（如改 deploy 目标）
deploy:prod:
  variables:
    DEPLOY_HOST: prod-myapp-01.internal

    机制二：extends（继承 + 覆盖单个 Job）

    # ci-templates/python/fastapi-base.yml（模板仓）
# 定义可复用的 Job 模板（用 . 开头表示隐藏 Job，不直接执行）
.test-template:
  stage: test
  image: python:3.12-slim
  before_script:
    - pip install -e ".[dev]" --quiet
  script:
    - pytest --cov=app --cov-report=xml --cov-report=term
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml

# 业务仓继承 + 覆盖
test:unit:
  extends: .test-template          # 继承模板
  variables:
    COVERAGE_THRESHOLD: "80"       # 覆盖/追加变量
  script:
    - pytest tests/unit/ --cov=app --cov-report=xml    # 覆盖 script
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

    机制三：trigger（跨仓流水线触发）

    # myapp/.gitlab-ci.yml
# 镜像构建完成后，触发部署仓的流水线（解耦构建和部署）
trigger:deploy:
  stage: deploy
  needs: ["build:kaniko"]
  trigger:
    project: 'devops/deploy-pipeline'   # 触发另一个项目的 CI
    branch: main
    strategy: depend                     # 等待下游 CI 完成才算本 Job 成功
  variables:
    IMAGE_TAG: $CI_COMMIT_TAG            # 传递变量给下游
    TARGET_ENV: prod

    三种机制对比：

    机制 用途 粒度 适合场景
    include 引入整份 YAML 文件 文件级 公共流水线模板（所有 Python 服务共享）
    extends 继承 + 覆盖单个 Job Job 级 微调模板里的某个 Job（改 image / 改 script）
    trigger 触发另一个项目的 CI 项目级 构建仓和部署仓分离、Monorepo 触发子项目

    ci-templates 仓库结构：

├── python/
│   ├── fastapi-base.yml        # FastAPI 基础模板（lint + test + build）
│   ├── django-base.yml         # Django 基础模板
│   └── library-base.yml        # Python 库模板（发布到 PyPI）

    版本化引用铁律：
    1. 永远用 ref: 'vX.Y.Z' 锁定版本，不要用 ref: 'main'——模板改了会直接炸所有引用方
    2. 模板变更走 MR + Code Review，和业务代码同等对待
    3. Breaking Change 升大版本号（v1→v2），给引用方时间迁移
    4. 模板仓的 CHANGELOG.md 记录每次变更，方便引用方判断要不要升级

    小团队起步建议：先用 GitLab CI 原生的 include:template（GitLab 自带模板），等服务 > 5 个再建自己的 ci-templates 仓。不要一上来就建模板仓——过早抽象比重复更痛苦。

    10.2 Monorepo CI/CD 策略¶

    10.2.1 Monorepo vs Polyrepo 权衡（什么时候该上 Monorepo）¶

    表 10-2：Monorepo vs Polyrepo 对比

    维度 Polyrepo（多仓） Monorepo（单仓）
    仓库结构 每个服务一个 Git 仓 所有服务在一个 Git 仓
    跨服务修改 改 2 个仓 + 2 个 MR + 2 次 CI 改 1 个仓 + 1 个 MR + 1 次 CI
    代码共享 发包到内部 PyPI/私有 npm 直接 import 同仓代码
    版本一致性 服务 A 依赖服务 B v1.2，B 已经 v1.3 了 所有服务同一次 commit 里版本一致
    CI/CD 复杂度 ⭐ 简单（每仓独立流水线） ⭐⭐⭐⭐ 复杂（需要变更检测 + 增量构建）
    仓库体积 小 大（需要 Git LFS / 部分克隆）
    权限隔离 天然隔离（每仓独立权限） 需要工具（CODEOWNERS + 路径权限）
    适合规模 < 5 个服务 5~50 个服务

    什么时候该上 Monorepo：
    1. 跨服务修改频繁（改一个接口要同时改 3 个服务）
    2. 有大量共享代码（公共库 / DTO / proto 定义）
    3. 团队 > 5 人但 < 30 人（超 30 人需要 Bazel 等专业工具）
    4. 愿意投入 CI/CD 基础设施（变更检测 + 增量构建 + 依赖图）

    什么时候不该上：
    1. 只有 2~3 个独立服务，很少跨服务修改
    2. 团队 < 5 人，没有精力维护 Monorepo CI 基础设施
    3. 服务间技术栈完全不同（Python + Java + Go 混在一起会增加复杂度）

    小团队建议：< 5 个服务用 Polyrepo + ci-templates 仓（10.1 节方案）就够了。Monorepo 的 CI 复杂度远超收益。等跨服务修改痛到受不了再迁移。

    10.2.2 Monorepo 流水线核心：变更检测 + 增量构建 + 依赖图¶

    Monorepo 最大的 CI 挑战：一个仓里 10 个服务，改了服务 A，不应该触发服务 B 的 CI（否则每次 push 跑 10 个服务的流水线 = 巨大浪费）。

    变更检测（只对变更的服务跑 CI）：

    # .gitlab-ci.yml（Monorepo 变更检测）
# 仓库结构：
# services/
# ├── user-service/
# ├── order-service/
# └── payment-service/
# shared/
# ├── proto/           # 共享 proto 定义
# └── utils/           # 共享工具库

# === 1. 变更检测 Job：找出哪些服务变了 ===
detect-changes:
  stage: .pre
  script:
    - |
      # 获取本次 push 变更的文件列表
      CHANGED_FILES=$(git diff --name-only HEAD~1 HEAD)
      CHANGED_SERVICES=""

      # 检测哪些服务有变更
      for service in services/*/; do
        service_name=$(basename "$service")
        if echo "$CHANGED_FILES" | grep -q "^services/$service_name/"; then
          CHANGED_SERVICES="$CHANGED_SERVICES $service_name"
        fi
      done

      # shared/ 变了 → 所有服务都要跑（因为都依赖 shared）
      if echo "$CHANGED_FILES" | grep -q "^shared/"; then
        echo "shared 目录变更，所有服务都需要跑 CI"
        CHANGED_SERVICES="user-service order-service payment-service"
      fi

      # 写入环境变量供下游 Job 使用
      echo "CHANGED_SERVICES=$CHANGED_SERVICES" >> .changed-services.env
  artifacts:
    reports:
      dotenv: .changed-services.env
  rules:
    - if: $CI_COMMIT_BRANCH

# === 2. 动态生成子流水线 ===
trigger-services:
  stage: build
  needs: ["detect-changes"]
  script:
    - |
      for service in $CHANGED_SERVICES; do
        echo "触发 $service 的子流水线"
      done
  trigger:
    include:
      - local: '/services/$SERVICE/.gitlab-ci.yml'   # 每个服务有自己的 CI 配置
    strategy: depend
  parallel:
    matrix:
      - SERVICE: $CHANGED_SERVICES
  rules:
    - if: $CI_COMMIT_BRANCH

    增量构建（只构建变更的服务镜像）：

    # services/order-service/.gitlab-ci.yml（子流水线）
build:order-service:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:debug
    entrypoint: [""]
  script:
    - |
      /kaniko/executor \
        --context=$CI_PROJECT_DIR/services/order-service \
        --dockerfile=$CI_PROJECT_DIR/services/order-service/Dockerfile \
        --destination=$CI_REGISTRY_IMAGE/order-service:$CI_COMMIT_SHORT_SHA \
        --cache=true \
        --cache-repo=$CI_REGISTRY_IMAGE/order-service:cache
  rules:
    - if: $CI_COMMIT_BRANCH

    依赖图（shared 变了，下游服务怎么自动发现）：

    shared/proto/  →  services/user-service/
                →  services/order-service/
                →  services/payment-service/

shared/utils/  →  services/user-service/
                →  services/order-service/

# 如果 shared/proto/order.proto 变了 → 只重建 order-service + payment-service
# 如果 shared/utils/common.py 变了 → 重建所有用了 utils 的服务

    Monorepo CI 的投入产出比拐点：服务 < 5 个时，每次跑全量 CI 也就 10 分钟，变更检测的复杂度不值得。服务 > 10 个时，不做变更检测每次跑 30+ 分钟，必须做。5~10 个之间看团队承受能力。

    10.2.3 Monorepo 下的 P1.3 四段环境适配¶

    Monorepo + P1.3 的挑战：feature 分支包含多个服务的变更，merge 到 dev/test/stage/main 时，每个服务都要独立部署到对应环境。

    适配方案：

    feature/order-v2（同时改了 order-service + payment-service）
    │
    ├─ merge dev
    │   ├─ deploy order-service → dev 环境
    │   └─ deploy payment-service → dev 环境
    │
    ├─ merge test
    │   ├─ deploy order-service → test 环境
    │   └─ deploy payment-service → test 环境
    │
    └─ merge main（批次到了）
        ├─ deploy order-service → main 验证（不发布）
        └─ deploy payment-service → main 验证（不发布）

    关键规则：
    1. 一个 feature 可以改多个服务，但 merge 时所有变更的服务一起部署到目标环境
    2. 回滚时一起回滚（feature 里改的多个服务是一个原子单元，不能只回滚其中一个）
    3. 批次发布时所有服务一起打 Tag（order-service v1.2.0 + payment-service v1.2.0 同批次发布）

    10.3 IaC 基础设施即代码¶

    10.3.1 IaC 是什么（Terraform / Ansible / Pulumi 定位与选型）¶

    IaC 的核心思想：基础设施（服务器、网络、数据库、负载均衡）用代码描述，而不是手动在云控制台点击。代码存 Git 仓库，走 CI/CD，可 Review、可回滚、可审计。

    手动 vs IaC 的差距：
    - 手动：创建一台 VM → 登录云控制台 → 点 20 下 → 15 分钟 → 没人记得配了什么
    - IaC：terraform apply → 30 秒 → Git 里有完整配置历史

    表 10-3：IaC 工具选型对比

    工具 类型 语言 优势 劣势 适合场景
    Terraform 声明式 HCL 生态最大、Provider 最全、state 管理 HCL 学习曲线、state 文件管理 云资源管理（首选）
    Pulumi 声明式 Python/TS/Go 用熟悉的编程语言写 IaC 生态小、企业版收费 开发团队偏好编程语言
    Ansible 过程式 YAML 简单、不需要 Agent、配置管理强 不擅长云资源创建 服务器配置管理（首选）
    Crossplane 声明式 YAML（K8s CRD） 用 K8s 管理 everything 学习成本高、成熟度低 K8s 原生团队

    小团队推荐组合：Terraform（管云资源：VM/VPC/RDS）+ Ansible（管服务器配置：装 Nginx/Python/配置文件）。两个都是免费开源，覆盖 90% 场景。

    state 管理（Terraform 最关键的概念）：

    # backend.tf（state 文件存远程，不要存本地）
terraform {
  backend "oss" {              # 阿里云 OSS（AWS 用 S3，腾讯云用 COS）
    bucket = "terraform-state-prod"
    prefix = "myapp/prod"

    10.3.3 IaC + CI/CD：基础设施变更也走 Pipeline¶

    核心理念：基础设施变更和代码变更一样走 CI/CD——terraform plan 在 CI 里跑（预览变更），terraform apply 需要人工确认（防止误操作）。

    # .gitlab-ci.yml（IaC 流水线，和业务代码流水线分离）
stages:
  - validate
  - plan
  - apply

# === 1. 语法校验 ===
terraform:validate:
  stage: validate
  image: hashicorp/terraform:latest
  script:
    - cd terraform/environments/$TF_ENV
    - terraform init -backend=false
    - terraform fmt -check        # 格式检查
    - terraform validate          # 语法校验
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: ["terraform/**/*"]

# === 2. Plan（预览变更，MR 里展示） ===
terraform:plan:
  stage: plan
  image: hashicorp/terraform:latest
  script:
    - cd terraform/environments/$TF_ENV
    - terraform init
    - terraform plan -out=tfplan      # 生成 plan 文件
    - terraform show -json tfplan > tfplan.json
  artifacts:
    paths:
      - tfplan
      - tfplan.json
    reports:
      terraform: tfplan.json          # GitLab MR 里展示 Terraform 变更预览
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: ["terraform/**/*"]

# === 3. Apply（人工确认后执行） ===
terraform:apply:
  stage: apply
  image: hashicorp/terraform:latest
  needs: ["terraform:plan"]
  script:
    - cd terraform/environments/$TF_ENV
    - terraform init
    - terraform apply -auto-approve tfplan
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      changes: ["terraform/**/*"]
      when: manual        # 人工确认才执行，不自动 apply
  environment:
    name: $TF_ENV

    IaC CI/CD 铁律：
    1. plan 自动跑，apply 人工确认——terraform apply 会改真实基础设施，必须人工把关
    2. 绝不手动改云资源——所有变更必须走 Terraform MR，否则 state 会 drift（和实际不一致）
    3. prod 环境 apply 需要两人 Review——Terraform MR 的 Approve 规则设 ≥ 2 人
    4. state 文件上锁——用 Terraform Cloud / Atlantis 防止并发 apply 导致 state 冲突

    采集实现（在 GitLab CI Deploy Job 里埋点）：

    # .gitlab-ci.yml（Deploy 成功后埋点 DORA 指标）
deploy:prod:
  stage: deploy
  # ... 部署逻辑 ...
  after_script:
    # 1. 记录部署次数（部署频率）
    - |
      curl -X POST http://pushgateway:9091/metrics/job/deploy \
        -d "deploy_total{env=\"prod\",service=\"myapp\",version=\"$CI_COMMIT_TAG\"} 1"
    # 2. 记录变更前置时间（commit → 部署 的时长）
    - |
      COMMIT_TIME=$(git show -s --format=%ct $CI_COMMIT_SHA)
      NOW=$(date +%s)
      LEAD_TIME=$(( (NOW - COMMIT_TIME) / 60 ))  # 分钟
      curl -X POST http://pushgateway:9091/metrics/job/deploy \
        -d "lead_time_minutes{env=\"prod\",service=\"myapp\"} $LEAD_TIME"
  rules:
    - if: $CI_COMMIT_TAG

    Panel PromQL Elite 基线

    10.6 生产常见问题与事故复盘¶

    10.6.1 ci-templates 仓改了模板导致所有项目 CI 一起挂（模板管理事故）¶

    事故：ci-templates 仓的维护者在 fastapi-base.yml 里改了 before_script 的 pip 安装命令，没通知引用方。所有用 ref: 'main' 引用的项目（15 个服务）CI 一起挂——pip install 报错。因为模板引用没锁版本，main 一改全部生效。

    根因：
    1. 模板引用用了 ref: 'main' 而不是 ref: 'v2.1.0'
    2. 模板变更没有灰度过程（没有先在 1 个项目验证）

    修复：
    1. 所有引用必须锁版本号 ref: 'vX.Y.Z'，禁止用 ref: 'main'
    2. 模板变更走 MR + Code Review，MR 描述里写明"会影响哪些引用方"
    3. Breaking Change 先发 vX.Y.0-rc.1 预发布版，让 1~2 个项目先试用，稳定后再发正式版
    4. CI 里加检查：扫描所有项目 .gitlab-ci.yml，如果有 ref: 'main' 就告警

    10.6.2 Monorepo 变更检测漏判 → 改了 shared 没触发下游 CI（漏构建事故）¶

    事故：Monorepo 里 shared/proto/order.proto 改了字段，但变更检测脚本只检查了 services/*/ 目录，没检测 shared/ → order-service 没重建 → 部署后旧镜像用旧 proto 反序列化新数据 → 线上反序列化错误。

    根因：变更检测脚本没有覆盖 shared → 下游的依赖关系。

    修复：
    1. 变更检测必须包含 shared 目录：shared/ 变了 → 所有依赖 shared 的服务都触发 CI
    2. 用依赖图工具（如 Bazel query / nx affected）自动计算影响范围，不靠手动维护
    3. CI 里加一致性检查：shared 变了但下游服务没重建 → CI 失败

    10.6.3 Terraform state 文件误删 → 所有基础设施"消失"（IaC 灾难事故）¶

    事故：运维清理 OSS 存储桶时误删了 terraform-state-prod/ 目录。Terraform state 文件丢了 → terraform plan 认为所有资源都不存在（因为 state 是空的）→ terraform apply 会尝试创建所有资源 → 但资源实际还在（云上）→ 冲突报错。恢复花了 3 小时（从 OSS 版本控制里找回 state 文件）。

    根因：
    1. state 文件存 OSS 但没开版本控制
    2. 清理脚本没有白名单保护

    修复：
    1. state 文件存储必须开版本控制（OSS 版本控制 / S3 Versioning）——误删可以恢复
    2. state 文件存储桶加生命周期保护（MFA Delete / 软删除）
    3. 定期 terraform plan 检查 state drift——state 和实际不一致时提前发现
    4. terraform import 批量导入——如果 state 真丢了，用 import 把云上已有资源重新导入 state

    10.6.4 DORA 指标采集后没人看 → 度量变成摆设（管理事故）¶

    事故：团队花 2 周搭了 DORA 仪表盘，数据采集正常，但没有人定期看。3 个月后部署失败率从 5% 涨到 15%，MTTR 从 30 分钟涨到 2 小时——仪表盘上都有数据，但没人发现，直到客户投诉。

    根因：
    1. 仪表盘没有告警——指标恶化不会主动通知
    2. 没有"度量回顾会"——数据采了不看等于没采

    修复：
    1. DORA 指标加告警：失败率 > 10% → P1 告警；MTTR > 1 小时 → P1 告警
    2. 每月度量回顾会：团队每月看一次 DORA 仪表盘，讨论"哪里退步了、怎么改进"
    3. 把 DORA 指标和团队目标绑定：季度 OKR 里写"部署频率 > 3 次/周 + 失败率 < 5%"
    4. 仪表盘放在显眼位置：Grafana 大屏投到办公区电视上，让所有人随时看到
