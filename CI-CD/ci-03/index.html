    3.1.1 五大工具定位分类¶

    3.1.3 三个关键认知¶

    1. CI 工具和 CD 工具不是一回事
    2. GitHub Actions / GitLab CI / Jenkins 是 CI 强、CD 弱（能部署但不是强项）
    3. Argo CD / Flux 是 CD 专精（不管构建，只管把 Git 里的声明同步到集群）

    4. 现代实践主流：CI 工具 + 专用 CD 工具组合（如 GitHub Actions + Argo CD）

    5. Jenkins 是"上一代"但没死

    6. 2026 年依然是大企业首选：插件生态、复杂编排能力无可替代

    7. 中小团队被 Actions / GitLab CI 抢走，但 Jenkins 在金融/制造/政企仍统治级

    8. Tekton 是"框架"不是"产品"

    9. 没有开箱即用的 UI 和触发器，是给"构建 CI/CD 平台的人"用的底座
    10. Google Cloud Build、Jenkins X、Tekton Chains 都基于它
    11. 除非你自建平台，否则不会直接用 Tekton

    3.2 GitHub Actions 详解¶

    3.2.1 定位¶

    GitHub 仓库内置的 CI/CD 服务，2019 年推出，2026 年已是 GitHub 托管项目的事实标准。配置文件 .github/workflows/*.yml 与代码同仓库。

    3.2.2 核心概念¶

    概念 说明
    Workflow 一条流水线，YAML 文件
    Event 触发器：push / PR / schedule / workflow_dispatch / repository_dispatch
    Job 流水线中的一个执行单元（含多个 step），可并行或串行
    Step Job 内最小执行单元，可以是 shell 命令或 Action
    Action 可复用的 step 单元（如 actions/checkout@v4）
    Runner 执行 Job 的机器：GitHub-hosted（云）/ Self-hosted（自建）
    Reusable Workflow 可被其他 workflow 调用的 workflow（复用机制）
    Composite Action 多 step 打包成的单个 Action（另一种复用机制）

    3.2.3 最小示例¶

    # .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 1   # 浅克隆，参见 S10
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'      # 自动缓存 pip
      - run: pip install -r requirements.txt
      - run: pytest --cov

    3.2.4 2026 新变化（重要）¶

    1. Self-hosted Runner 收费（2026-03-01 起）
    2. 自托管 Runner 不再"免费白嫖"，GitHub 收 0.002 美元/分钟的云平台服务费
    3. 影响：纯自建 Runner 的成本优势大幅缩小，需重新算 TCO（参见 S2 成本与配额）

    4. 应对：评估是否迁移到 GitLab CI 自建，或用 Actions 自建 + 限额

    5. OIDC 默认推荐：所有云部署用 OIDC Token，不用长期密钥（参见 S1 Secret 管理）

    6. Reusable Workflow + Composite Action 双复用机制成熟：跨仓库共享流水线逻辑已成标配

    3.2.5 适用场景¶

    适合 不适合
    代码托管在 GitHub 的项目 代码在 GitLab / 自建 Gitea 的项目
    中小团队、开源项目 需要深度自建 Runner 网络的复杂环境
    希望零运维、开箱即用 需要 UI 编排、复杂审批流的传统企业
    Python / Node / 容器化项目 强依赖 Jenkins 插件生态的传统栈

    3.2.6 主要限制¶

    • 单 Job 最长 6 小时（免费）/ 35 天（付费）
    • 并发受套餐限制（免费 20 个并发）
    • 私有仓库免费额度 2000 分钟/月（pro 账号 3000）
    • Self-hosted Runner 不支持公网 PR（安全风险，参见 S5 流水线自身安全）

    3.3 GitLab CI 详解¶

    3.3.1 定位¶

    GitLab 仓库内置的 CI/CD 服务，2015 年推出，比 GitHub Actions 早 4 年。配置文件 .gitlab-ci.yml 与代码同仓库。自建版（GitLab CE/EE）市场占有率极高，是国内中大型企业的主流选择。

    3.3.2 核心概念¶

    概念 说明
    Pipeline 一条流水线
    Stage 流水线的逻辑分组，串行执行（同 Stage 内 Job 并行）
    Job 最小执行单元，属于某个 Stage
    Runner 执行 Job 的机器，按 executor 类型分：shell / docker / kubernetes
    .gitlab-ci.yml 配置文件
    Include 拆分/复用配置（类似 Reusable Workflow）
    Rules 控制 Job 何时跑（替代老版本的 only/except）
    needs 跨 Stage 依赖（打破串行 Stage，可构建 DAG）

    3.3.3 最小示例¶

    # .gitlab-ci.yml
stages:
  - test
  - build

variables:
  PYTHON_IMAGE: python:3.12-slim

test:
  stage: test
  image: $PYTHON_IMAGE
  cache:
    key: pip-${CI_COMMIT_REF_SLUG}
    paths: [.cache/pip]
  before_script:
    - pip install --cache-dir=.cache/pip -r requirements.txt
  script:
    - pytest --cov
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

build:
  stage: build
  image: docker:24
  services: [docker:24-dind]
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

    3.3.4 与 GitHub Actions 的核心差异¶

    维度 GitHub Actions GitLab CI
    结构层次 workflow > job > step pipeline > stage > job
    DAG 支持 通过 needs 字段 通过 needs 字段（更早支持）
    Runner 类型 GitHub-hosted / Self-hosted Shared / Specific / Group Runner
    缓存机制 cache: + actions/cache cache: 内置
    制品仓 需外接（GitHub Packages 较弱） 内置 GitLab Registry（镜像 + 包一体）
    环境管理 environment environment + 动态环境
    私有部署 只能 Self-hosted Runner，代码必须在 GitHub GitLab CE 完全私有化，代码 + CI 一体
    复用机制 Reusable Workflow + Composite Action Include + Templates + Components（2024+）
    2026 趋势 Self-hosted 收费，自建成本上升 私有化首选，国内大厂主流

    3.3.5 适用场景¶

    适合 不适合
    代码在 GitLab（自建或 SaaS） 代码在 GitHub
    需要私有化部署（金融/政企/国内大厂） 极小团队（运维成本高）
    需要一体化 DevOps 平台（Issue/MR/CI/CD/Registry） 只想要轻量 CI
    多语言混合栈、容器化项目 —

    3.3.6 GitLab Components（2024+ 新复用机制）¶

    2024 年起 GitLab 推出 Components（比 include 更标准化的复用方式），2026 已成主流：

    # 引用组件库
include:
  - component: gitlab.com/components/sast/sast@2.0.0
    inputs:
      stage: test
  - component: gitlab.com/my-org/python-ci@v1.2
    inputs:
      python_version: '3.12'

    3.4 Jenkins 详解¶

    3.4.1 定位¶

    2005 年（前身 Hudson）诞生的老牌 CI/CD 工具，插件生态无可匹敌（1800+ 插件）。2026 年仍是金融/制造/政企的首选，但在互联网/初创领域被 Actions / GitLab CI 大幅取代。

    3.4.2 为什么 2026 仍然没死¶

    1. 插件生态护城河：与 SAP / Oracle / 大型机 / 传统中间件的集成，只有 Jenkins 插件成熟
    2. 复杂编排能力：多阶段审批、人工节点、跨机器分发，Jenkins 自由度最高
    3. 不绑定 SCM：可同时拉 GitHub / GitLab / SVN / Perforce，适合多源代码环境
    4. 完全自建可控：金融/政企对数据出域的硬要求，Jenkins 自建满足合规
    5. Jenkinsfile as Code 已成熟：声明式 Pipeline + Shared Library 可工程化

    3.4.3 核心概念¶

    概念 说明
    Controller（原 Master） Jenkins 主节点，调度
    Agent（原 Slave） 真正执行 Job 的节点
    Pipeline 流水线，Jenkinsfile 定义
    Stage 流水线阶段
    Step 最小执行单元
    Shared Library 跨 Pipeline 复用代码（Groovy 仓库）
    Plugin 扩展点（几乎所有功能都靠插件）

    3.4.4 声明式 Pipeline 示例¶

    // Jenkinsfile (Declarative)
pipeline {
  agent {
    kubernetes {
      yaml '''
        apiVersion: v1
        kind: Pod
        spec:
          containers:
          - name: python
            image: python:3.12-slim
            command: ['sleep', 'infinity']
      '''
    }
  }
  stages {
    stage('Test') {
      steps {
        container('python') {
          sh 'pip install -r requirements.txt'
          sh 'pytest --cov'
        }
      }
    }
    stage('Build') {
      steps {
        sh 'docker build -t my-app:$BUILD_NUMBER .'
      }
    }
  }
  post {
    always {
      junit 'reports/**/*.xml'
      archiveArtifacts 'dist/**/*'
    }
  }
}

    3.4.5 主要痛点¶

    1. UI 老、配置散：部分配置仍在 UI，Pipeline as Code 不彻底
    2. 维护成本高：插件冲突、版本升级风险、Controller 单点
    3. K8s 友好度一般：Kubernetes Plugin 可用但不如 GitLab/Tekton 原生
    4. 学习曲线陡：Groovy + Shared Library 需要专门学习
    5. 资源消耗大：Controller JVM 内存吃得多，小团队不划算

    3.4.6 适用场景¶

    适合 不适合
    大企业、复杂编排、多源 SCM 中小团队、互联网初创
    金融/制造/政企（合规要求） 希望零运维的团队
    需要与 SAP/Oracle/大型机集成 K8s 原生项目
    已有大量 Jenkins 插件资产 全新项目（除非有特殊需求）

    3.5 Argo CD 详解¶

    3.5.1 定位（重要：CD 不是 CI！）¶

    Argo CD 不是 CI 工具，不管构建、不管测试。它只做一件事：把 Git 仓库里的 K8s 声明（YAML/Helm/Kustomize）同步到集群。属于 CD 专精工具，基于 GitOps 模型。

    3.5.2 GitOps Pull 模型（核心）¶

    图 3-2：Argo CD 的 Pull 模型 vs 传统 Push 模型

【传统 Push 模型】                【Argo CD Pull 模型】
CI 流水线                         CI 流水线
  │                                 │
  ▼ 构建镜像                        ▼ 构建镜像
  │                                 │
  ▼ 推镜像仓                        ▼ 推镜像仓
  │                                 │
  ▼ kubectl apply（推到集群）       ▼ 修改部署仓的镜像版本号（Git commit）
                                    │
                                    ▼ Git 仓变更
                                    │
                                    │   ┌─────────────────┐
                                    └──►│   Argo CD        │
                                        │  (集群里运行)     │
                                        │  持续 watch Git   │
                                        └────────┬────────┘
                                                 │ 检测到 Git 与集群不一致
                                                 ▼ Pull 模型同步
                                            K8s 集群

    3.5.3 核心概念¶

    概念 说明
    Application 一个 Argo CD 应用（对应一个 Git 仓目录 + 一个目标集群）
    Sync 把 Git 期望状态同步到集群
    Health 应用健康状态（Healthy / Degraded / Progressing）
    Sync Status Git 与集群是否一致（Synced / OutOfSync）
    Project Argo CD 项目（多租户隔离）
    App-of-Apps 用一个 Application 管理多个 Application（集群级）

    3.5.4 Application 示例¶

    # argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app-prod
  namespace: argocd
spec:
  source:
    repoURL: https://gitlab.com/my-org/deploy-manifests.git
    targetRevision: main
    path: prod/my-app           # 部署仓的目录
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true               # 自动删除 Git 里删掉的资源
      selfHeal: true            # 集群手动改动自动回滚到 Git 状态
    syncOptions:
      - CreateNamespace=true

    3.5.5 为什么 2026 主流¶

    1. K8s 原生：CRD 定义，本身就是 K8s 资源
    2. 集群侧 Pull：不需要给 CI 系统 cluster-admin 权限（安全）
    3. 多集群管理：一个 Argo CD 管理多个集群
    4. Git 即审计：所有部署变更都有 Git commit
    5. 漂移自愈：手动改集群？自动回滚到 Git 状态
    6. UI 直观：可视化 Git 与集群差异

    3.5.6 局限¶

    • 只管 K8s：非 K8s 环境（VM、Serverless 部分场景）用不了
    • 不管 CI：必须配 CI 工具一起用
    • 学习曲线：GitOps 心智模型与传统 Push 模型差异大
    • 首次部署慢：大型集群首次 Sync 可能几分钟

    3.5.7 主要竞品：Flux¶

    维度 Argo CD Flux
    UI 强（开箱即用） 弱（需配 wego/weave-gitops）
    多租户 Project 隔离清晰 较弱
    学习曲线 较平 较陡
    Helm 支持 好 好
    社区 CNCF Graduated CNCF Graduated
    2026 占比 互联网主流 偏极客/技术派

    国内市场 Argo CD 占有率明显高于 Flux，建议优先学 Argo CD。

    3.6 Tekton 详解¶

    3.6.1 定位（K8s 原生 CI/CD 框架）¶

    Tekton 是 CD 基金会托管的 K8s 原生 CI/CD 框架，由 Google 开源。它不是产品，是框架/底座——没有开箱即用的 UI 和触发器，需要自建或嵌入其他系统。

    3.6.2 核心概念（全 CRD）¶

    CRD 说明
    Step 最小执行单元（一个容器）
    Task 多个 Step 串行/并行的集合
    Pipeline 多个 Task 的 DAG
    PipelineRun Pipeline 的一次执行实例
    TaskRun Task 的一次执行实例
    PipelineResource 输入/输出资源（已废弃，改用 workspace + params）
    Workspace 共享存储卷（Task 间传递数据）
    Trigger / EventListener 事件触发（Webhook 接收）

    3.6.3 Task 示例¶

    # tekton-task.yaml
apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: python-test
spec:
  workspaces:
    - name: source
  params:
    - name: python-version
      default: '3.12'
  steps:
    - name: install
      image: python:$(params.python-version)
      workingDir: $(workspaces.source.path)
      script: |
        #!/bin/sh
        pip install -r requirements.txt
    - name: test
      image: python:$(params.python-version)
      workingDir: $(workspaces.source.path)
      script: |
        #!/bin/sh
        pytest --cov

    3.6.4 与 Jenkins 的关系¶

    Tekton 经常被定位为"Jenkins 的 K8s 原生继任者"，但实际上：

    • Jenkins 是完整产品（UI + 触发器 + 插件 + Pipeline）
    • Tekton 是底层引擎（只有 CRD + Controller）

    Jenkins X 项目曾尝试基于 Tekton 重新构建 Jenkins，但商业化不成功。2026 年 Tekton 主要被云厂商和平台团队用作底座（如 Red Hat OpenShift Pipelines）。

    3.6.5 适用场景¶

    适合 不适合
    自建 CI/CD 平台的团队 直接拿来用的中小团队
    云厂商构建 CI 服务 需要开箱即用 UI
    K8s 极度原生信仰团队 Jenkins 已稳定运行的团队
    Red Hat OpenShift 用户（内置） 时间紧、要快速上手的项目

    3.6.6 2026 现状¶

    Tekton 在 2026 年仍是小众但重要的存在：
    - 直接终端用户少（远低于 Argo CD / GitLab CI）
    - 但作为"底座"被广泛使用（OpenShift、Jenkins X、Tekton Chains 镜像签名）
    - 建议：了解概念即可，除非你在平台团队，否则不必深学

    3.10.4 小企业轻量方案：GitLab CI + Docker（1-50 人团队）¶

    中型/大型组合（GitLab CI + Argo CD）需要 K8s，对小企业太重。小企业（1-50 人）的优质选择是 GitLab CE + Docker 单机/双机方案，与 P1 实践完美兼容。

    1. 方案定位¶

    "Docker" 在这里有三重含义：
    - 构建产物：CI 构建 Docker 镜像推到 Registry（所有方案的基础）
    - Runner executor：GitLab Runner 用 docker executor 跑 Job（隔离好、清理简单）
    - 部署方式：生产用 docker run / docker-compose 跑应用（无需 K8s）

    2. 优势（5 条）¶

    优势 说明
    一体化、零额外组件 GitLab CE 自带代码托管 + CI + Registry + Issue，不需要 Jenkins/Nexus/Harbor
    成本极低 一台 4C8G VM 跑 GitLab + Runner + Registry，小团队够用
    学习曲线平缓 只需 .gitlab-ci.yml + Dockerfile + docker-compose.yml
    与 P1 实践兼容 分支即环境模型原样可跑，merge 触发对应环境 docker-compose 重启
    回滚简单 保留历史镜像，回滚 = 切换 tag + 重启容器

    场景 GitLab CI + Docker 够用 何时升级到 K8s + Argo CD

    服务数 < 10 ✅ > 10 个微服务

    手动回滚可接受 ✅ 要求秒级回滚
    配置管理简单 ✅ 多环境配置爆炸

    5. 注意事项（4 个坑）¶

    1. docker-compose 不是生产级编排：单机挂了全挂，重要业务至少双机 + nginx 负载均衡
    2. Docker-in-Docker 性能差：用 Kaniko 或 BuildKit 替代 dind，更快更安全
    3. Runner executor 选 docker 不选 shell：shell executor 隔离差、密钥易泄露（参见 S5 流水线自身安全）
    4. Registry 必须备份：GitLab 内置 Registry 数据要定期备份，关键镜像可同步推到 Docker Hub / 阿里云 ACR 异地备份

    3.11 现阶段最佳实践（2026）¶

    3.11.1 主流趋势（5 条）¶

    1. CI 与 CD 解耦：CI 工具只管构建/测试/推制品，部署交给 Argo CD（Pull 模型）
    2. 私有化首选 GitLab CE：Actions 的 self-hosted 收费后，国内企业私有化更倾向 GitLab
    3. K8s 部署 = Argo CD：K8s 项目里 Argo CD 已成事实标准，Flux 占比小
    4. Jenkins 存量稳固：传统行业不轻易迁移，新建项目则少选 Jenkins
    5. Tekton 仍是底座：终端用户少，但 OpenShift / Jenkins X / 自建平台都基于它

    3.11.2 避坑指南（8 条）¶

    1. 不要用 CI 工具直接 kubectl apply 到生产
    2. 反模式：CI 拿 cluster-admin 推到集群
    3. 正确：CI 只推镜像 + 改部署仓，Argo CD 同步
    4. 不要在 CI 里跑数据库迁移
    5. 反模式：CI 直接连生产 DB 跑 flyway migrate
    6. 正确：迁移脚本进制品，部署时 Init Container 或 Job 跑（参见 S6 数据库迁移）
    7. 不要用 latest 标签部署生产
    8. 反模式：镜像推 latest，prod 拉 latest
    9. 正确：用 gitSHA 或语义版本号，不可变标签
    10. CI 配置文件必须 Code Review
    11. CI 配置改动 = 流水线行为变更，与业务代码同等对待
    12. Self-hosted Runner 绝不跑公网 PR
    13. 公网 PR 是零信任输入，可能跑恶意代码偷密钥
    14. 第三方 Action/Plugin 锁 SHA
    15. 不用 @v4 浮动 tag，用 @<commit-sha>，防供应链劫持（参见 S5 流水线自身安全）
    16. 制品构建一次，所有环境复用
    17. 反模式：每个环境重新构建（如 P1 模型）
    18. 正确：构建一次，环境间只改配置（参见 我的实践记录.md P1.6 第 4 条）
    19. Jenkins 不要新建
    20. 除非有强需求（SAP/Oracle/合规），新项目选 GitLab CI 或 Actions
