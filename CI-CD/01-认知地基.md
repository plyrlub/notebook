## 1.1 三个 CD：CI / CDelivery / CDeployment

这是 CI/CD 学习中**第一个、也是最容易混一辈子的坑**。"CD" 在不同语境下指两个不同的东西。

### 1.1.1 概念对照表

**表 1-1：CI / CDelivery / CDeployment 三概念对照**

| 缩写 | 全称 | 中文 | 关键特征 |
| ---- | ---- | ---- | -------- |
| **CI** | Continuous Integration | 持续集成 | 代码**合并到主干** + **自动构建测试**，保证主干随时可建 |
| **CDelivery** | Continuous Delivery | 持续交付 | 主干**随时可一键发布**到生产（发布动作是**手动的**） |
| **CDeployment** | Continuous Deployment | 持续部署 | 每次通过 CI 的构建**自动推到生产**，连"一键"都省了 |

### 1.1.2 三者的递进关系

![CI / 持续交付 / 持续部署 递进关系图](./assets/01-ci-cd-progress.jpg)
*图 1-1：CI → 持续交付 → 持续部署 的三层递进关系。越往右人工介入越少、发布越快，但对测试成熟度要求越高。*

文本版递进示意：
```
CI（自动构建+测试）
    │
    ▼
Continuous Delivery（自动构建+测试+自动发布到预发，生产发布需人工按按钮）
    │
    ▼
Continuous Deployment（全自动，测试通过即上生产，人工不介入发布）
```

### 1.1.3 一个关键认知误区

很多人以为"上了 CI/CD 就等于自动上生产"，其实：

- **CI ≠ 自动部署**：CI 只管"主干能不能编译通过、测试能不能过"
- **持续交付 ≠ 持续部署**：交付要求"具备随时发布能力"，但**何时发布由人决定**
- **持续部署**才真正"机器自动上线"

**为什么大多数团队停在"持续交付"而不是"持续部署"？**
- 合规要求：金融、医疗等行业需要人工审批
- 业务节奏：营销活动有上线窗口
- 风险控制：自动部署要求测试极度充分，很多团队达不到

> **2026 现状**：互联网公司普遍做到持续部署（小步快跑），传统企业多停留在持续交付。面试时被问"你们是 Delivery 还是 Deployment"，要答得清楚。

### 1.1.4 用一句话区分（面试速答版）

> CI 解决"集成痛"（合并不冲突、主干可建）；持续交付解决"发布恐惧"（随时能发，按钮在我手上）；持续部署解决"发布速度"（人不挡路，测试通过即上线）。

## 1.2 流水线核心术语（跨工具对照）

理解术语是看懂任何 CI/CD 工具文档的前提。这些概念在 GitHub Actions / GitLab CI / Jenkins 中**名字不同但本质一样**。

### 1.2.1 术语对照表

**表 1-2：通用概念 vs GitHub Actions / GitLab CI / Jenkins 术语对照**

| 通用概念 | 含义 | GitHub Actions | GitLab CI | Jenkins |
| -------- | ---- | -------------- | --------- | ------- |
| **Pipeline（流水线）** | 一次完整的自动化流程 | Workflow | Pipeline | Pipeline |
| **Stage（阶段）** | 流程的逻辑分组，串行执行 | job（可用 needs 编排） | stage | stage |
| **Job / Step（任务/步骤）** | 最小执行单元 | step | job | step |
| **Runner / Agent（执行器）** | 真正跑 Job 的机器/容器 | runner | runner | agent / node |
| **Artifact（制品）** | 构建产物，可在阶段间传递 | artifact | artifacts | artifact |
| **Trigger（触发器）** | 什么事件启动流水线 | on | rules / only | triggers |
| **Secret（密钥）** | 加密的敏感变量 | secrets | variables (masked) | credentials |

### 1.2.2 几个最容易踩的术语坑

1. **GitHub Actions 的 "job" ≈ GitLab 的 "stage"**，不是同一个粒度。
   - GitHub Actions：`workflow > job > step`
   - GitLab CI：`pipeline > stage > job`
   - 这是初学者跨工具时最常晕的地方。

2. **Artifact 不是 Docker 镜像**。
   - Artifact 是泛指：jar 包、覆盖率报告、二进制、镜像都是 artifact。
   - 镜像只是 artifact 的一种，存到镜像仓（Harbor/registry）。

3. **Runner 的 executor 类型决定隔离级别**。
   - Shell executor：直接在宿主机跑，**隔离最差**，密钥易泄露
   - Docker executor：每个 job 一个容器，隔离较好（推荐）
   - K8s executor：每个 job 一个 Pod，隔离最好，适合大规模

> → 见补充专题 S5（流水线自身的安全）：Runner 隔离级别直接影响安全。

## 1.3 标准流水线的八个阶段（黄金八段）

记住这个"黄金八段"，任何工具的流水线都套这个模型。

### 1.3.1 八阶段全景图

![标准流水线八阶段全景图](./assets/01-pipeline-eight-stages.jpg)
*图 1-2：CI/CD 标准流水线八阶段（黄金八段）。从左到右按失败快停原则排列：便宜的检查前置，昂贵的检查后置。每个绿框左侧是失败时的处理策略。*

ASCII 版对照：
```
┌──────┐  ┌───────┐  ┌──────┐  ┌──────────┐  ┌────────┐  ┌─────────┐  ┌───────┐  ┌─────────┐
│ Lint │→ │ Build │→ │ Test │→ │ Security │→ │ Package│→ │ Publish │→ │ Deploy│→ │ Verify  │
│      │  │       │  │      │  │   Scan   │  │        │  │         │  │       │  │         │
└──────┘  └───────┘  └──────┘  └──────────┘  └────────┘  └─────────┘  └───────┘  └─────────┘
 代码检查    编译构建    测试     安全扫描       打包        发布制品     部署       部署后验证
```

### 1.3.2 各阶段职责表

**表 1-3：黄金八阶段的职责、典型工具、失败处理**

| 阶段编号 | 阶段 | 干什么 | 典型工具 | 失败应该怎样 |
| -------- | ---- | ------ | -------- | ------------ |
| 1 | **Lint** | 代码风格、静态错误 | ruff / eslint / golangci-lint | 阻断，让作者修 |
| 2 | **Build** | 编译成可运行产物 | mvn / pip / go build | 阻断 |
| 3 | **Test** | 单元 + 集成测试 | pytest / junit | 阻断，不允许进下游 |
| 4 | **Security Scan** | SAST / 依赖漏洞 / 密钥泄露 | SonarQube / Trivy / Gitleaks | 高危阻断，低危告警 |
| 5 | **Package** | 打成镜像 / jar / wheel | docker build / mvn package | 阻断 |
| 6 | **Publish** | 推到制品仓 | docker push / mvn deploy | 阻断（不然下游没制品） |
| 7 | **Deploy** | 部署到目标环境 | helm / kubectl / argocd | 阻断并告警 |
| 8 | **Verify** | 部署后健康检查、冒烟测试 | curl / 新版本探活 | 自动回滚 |

### 1.3.3 三个"门禁"概念

- **Quality Gate（质量门）**：测试覆盖率/代码 smells 达标才放行
- **Security Gate（安全门）**：无高危漏洞才放行
- **Deployment Gate（部署门）**：环境审批通过才部署（持续交付的"按钮"）

### 1.3.4 现阶段最佳实践（2026）

1. **失败要快（Fail Fast）**：便宜的检查（lint）放前面，贵的检查（E2E）放后面。
2. **并行化**：同阶段的多个 Job 并行跑（如多语言版本矩阵）。
3. **门禁前置**：安全扫描不要等到发布前，在 PR 阶段就跑。
4. **流水线即代码**：所有配置在仓库里，不依赖 UI 配置（见 1.5）。

## 1.4 CI/CD 与 DevOps / SRE / GitOps 的关系

这四个词经常并列出现，关系是**层次递进 + 互补**，不是替代。

### 1.4.1 层次嵌套关系图

![DevOps / CI-CD / GitOps / SRE 关系嵌套图](./assets/01-devops-gitops-sre.jpg)
*图 1-3：DevOps 为最外层（文化 + 实践），CI/CD 是 DevOps 的技术落地，GitOps 是 CI/CD 的一种实现方式（Pull 模型，Git 为唯一可信源），SRE 与上述正交，用工程方法解决可靠性问题。*

ASCII 版对照：
```
┌──────────────────────────────────────────────────────────┐
│                    DevOps（文化 + 实践）                  │
│  范围最大：组织文化、协作模式、自动化理念                  │
│                                                          │
│   ┌──────────────────────────────────────────────────┐   │
│   │           CI/CD（工程实践）                       │   │
│   │   DevOps 的技术落地，解决"代码→生产"的自动化      │   │
│   │                                                  │   │
│   │   ┌──────────────────────────────────────────┐   │   │
│   │   │      GitOps（部署模型）                   │   │   │
│   │   │   CI/CD 的一种实现方式：Git 作为唯一可信源  │   │   │
│   │   └──────────────────────────────────────────┘   │   │
│   └──────────────────────────────────────────────────┘   │
│                                                          │
│   SRE（站点可靠性工程）：与上述正交，关注"运行稳不稳"     │
│   用软件工程方法做运维，CI/CD 是 SRE 的工具之一           │
└──────────────────────────────────────────────────────────┘
```

### 1.4.2 一句话区分

**表 1-4：DevOps / CI/CD / GitOps / SRE 四概念一句话区分**

| 概念 | 一句话解释 | 类比 |
| ---- | ---------- | ---- |
| **DevOps** | 文化和实践，让开发和运维不再对立 | 公司的"协作价值观" |
| **CI/CD** | 代码到生产的自动化流水线 | "生产流水线"本身 |
| **GitOps** | 用 Git 当唯一真相源来驱动部署 | 流水线的"一种操作规程" |
| **SRE** | 用工程方法保证系统可靠 | "质检 + 维保团队" |

### 1.4.3 GitOps 的核心原则（2026 部署主流）

1. **声明式**：系统期望状态用代码描述（K8s YAML / Helm）
2. **版本化**：所有声明存在 Git，每次变更可追溯
3. **自动拉取**：部署不是"推"到集群，而是集群"拉"Git（Pull 模型）
4. **持续协调**：Agent（Argo CD/Flux）持续对比 Git 与集群，漂移自动修正

> GitOps 的 Pull 模型 vs 传统 CI/CD 的 Push 模型，是第 07 章的重点。

## 1.5 Pipeline as Code（流水线即代码）

### 1.5.1 为什么这是 2026 的事实标准

老一代做法（Jenkins UI 点击配置）的问题：
- 配置不在仓库里，**不可追溯、不可 Review**
- 换台 Jenkins 就要重配，**无法迁移**
- 配置和代码版本不同步，**"这套配置配的是哪个版本的代码"说不清**

Pipeline as Code 的核心：**流水线定义文件（YAML）和代码放同一个仓库，随代码版本演进**。

### 1.5.2 三大工具的配置文件模板

```yaml
# GitHub Actions: .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest
```

```yaml
# GitLab CI: .gitlab-ci.yml
stages:
  - test
test:
  stage: test
  image: python:3.12
  script:
    - pip install -r requirements.txt
    - pytest
```

```groovy
// Jenkins: Jenkinsfile (Declarative)
pipeline {
  agent any
  stages {
    stage('Test') {
      steps {
        sh 'pip install -r requirements.txt'
        sh 'pytest'
      }
    }
  }
}
```

### 1.5.3 现阶段最佳实践（2026）

1. **配置文件纳入 Code Review**：CI 改动和业务代码一样要 Review。
2. **复用 > 复制**：用 Reusable Workflow（GitHub）/ Include（GitLab）/ Shared Library（Jenkins）。
3. **版本锁定**：第三方 Action 用 SHA 锁定，不用 `@v4` 浮动 tag。
   > → 见补充专题 S5（流水线自身的安全）
4. **配置可测试**：用 `actionlint` / `yamllint` 校验配置本身。

## 1.6 用 Python 伪代码理解流水线本质（DAG）

抛开工具语法，一条流水线的本质就是一个**有向无环图（DAG）**：

```python
# 流水线本质的伪代码（Python 风格，非任何工具语法）
from dataclasses import dataclass
from typing import Callable

@dataclass
class Step:
    name: str
    run: Callable[[], bool]   # 返回 True 表示成功
    depends_on: list[str]     # 依赖哪些前置步骤

def pipeline(stages: list[Step]) -> dict[str, bool]:
    """执行流水线：拓扑排序后跑，任一失败则下游不跑。"""
    results = {}
    for step in stages:
        # 检查依赖是否全部成功
        if any(not results.get(dep) for dep in step.depends_on):
            print(f"[SKIP] {step.name}：依赖未通过")
            continue
        print(f"[RUN]  {step.name}")
        results[step.name] = step.run()
        if not results[step.name]:
            print(f"[FAIL] {step.name}：阻断后续")
    return results

# 定义一条标准流水线
stages = [
    Step("lint",     lambda: run_lint(),     []),
    Step("build",    lambda: run_build(),    ["lint"]),
    Step("test",     lambda: run_tests(),    ["build"]),
    Step("scan",     lambda: run_security(), ["build"]),   # 与 test 并行
    Step("package",  lambda: run_package(),  ["test", "scan"]),
    Step("publish",  lambda: run_publish(),  ["package"]),
    Step("deploy",   lambda: run_deploy(),   ["publish"]),
    Step("verify",   lambda: run_verify(),   ["deploy"]),
]

pipeline(stages)
```

**关键认知**：
- 流水线 = DAG + 失败阻断规则
- 任何工具（Actions/GitLab/Jenkins）都是这个模型的 YAML 化封装
- 理解了这个模型，学新工具只需要查"它怎么写 DAG"
