    老项目改进方案¶

    面向 3~5 年历史的 Java/Python 老项目团队，从"开发人员手工保证质量"过渡到 CI/CD 自动化。
    提供两套并行方案：
    - 方案 1（无 K8s）：Docker Compose/Swarm 部署，适合运维资源紧张的团队
    - 方案 2（已有 K8s）：Argo CD GitOps 改造，适合已容器化但靠手工 kubectl 部署的团队
    关联：本方案是对 01-认知地基、04-核心工具深入、06-容器化与制品管理、07-部署与发布策略、10-进阶与工程化 的工程化落地，分支模型遵循 我的实践记录 P1。

    0. 读者画像¶

    维度 设定
    项目年龄 3~5 年，单体为主，少量微服务
    技术栈 Java Spring Boot + Python Flask/Django，可能含 PHP/Node 遗留
    团队规模 8~20 名开发，0~2 名运维
    当前状态 有 Git 但分支混乱；有测试但靠手跑；有部署但靠 kubectl/SCP 脚本；出问题靠"老王"
    核心痛点 部署慢、回滚难、环境漂移、新人不敢上线、背锅文化
    目标 6 个月内从"手工保障"过渡到"流水线保障"，DORA 从 Low 升到 Medium

    老项目的 5 个典型特征（如果你命中 ≥ 3 个，本方案适用）：
    1. 生产部署依赖某位"懂运维的开发"，他请假就发不了版
    2. 同一份代码在 dev 跑得动、上 prod 就出问题（环境漂移）
    3. 数据库 schema 变更靠 DBA 手动执行 SQL，CI 里没人敢碰
    4. 没有统一的镜像版本号，回滚靠"再 build 一次旧 commit"
    5. 出了线上事故，复盘会上第一句话是"谁改的"

    1. 现状诊断清单（10 条自检项）¶

    逐条打勾，判断你的项目处于哪个阶段。0~3 命中 = 已初步 CI 化；4~7 = 半手工；8~10 = 全手工。

    # 自检项 命中说明
    1 仓库存在 master 与 main 并存、或长期分支 > 5 条 分支策略混乱
    2 默认分支允许直推，没有强制 MR/PR 缺 Code Review 门禁
    3 CI 文件 .gitlab-ci.yml/Jenkinsfile 不存在或仅跑 build CI 未闭环
    4 测试覆盖率 < 30%，或没有自动化测试 质量无保障
    5 部署用 scp + systemctl restart 或 kubectl apply 手工命令 CD 未自动化
    6 没有 Harbor/Nexus，镜像直接 docker build 后 docker save 传文件 缺制品仓
    7 数据库变更靠人肉执行 SQL，没有版本化工具 DB 迁移无管理
    8 配置文件随代码提交，application-prod.yml 在仓库里 配置耦合
    9 没有监控告警，或告警打到运维手机短信没人看 可观测性缺失
    10 出了事故靠口头复盘，没有事后报告与指标追踪 文化问题

    诊断结论与建议：

    命中数 阶段 起步方案
    0~3 已初步 CI 化 直接进入月 3~4 的 CD 自动化阶段
    4~7 半手工 完整执行 6 个月路线图，优先选方案 1
    8~10 全手工 前 2 个月必须先做版本控制规范化，禁止跳到 CD

    3. 启动时用 SPRING_DATASOURCE_URL 等环境变量覆盖

    4.3.2 蓝绿切换脚本¶

    #!/usr/bin/env bash
# /opt/stacks/bin/blue-green.sh —— 老项目蓝绿切换
set -euo pipefail
ENV="${1:?usage: blue-green.sh <env> [stack-suffix]}"
SUFFIX="${2:-}"                       # 可选，多服务时指定 java/py
STACK_DIR="/opt/stacks/${ENV}"
ACTIVE_FILE="${STACK_DIR}/.active"
ACTIVE="$(cat ${ACTIVE_FILE} 2>/dev/null || echo blue)"
NEXT=$([ "$ACTIVE" = blue ] && echo green || echo blue)

echo "[蓝绿] 当前 active=${ACTIVE}，部署 next=${NEXT}"

# 1. 部署 NEXT stack
IMAGE_TAG="${IMAGE_TAG:?}" docker stack deploy \
  -c "${STACK_DIR}/compose-${NEXT}.yml" \
  --with-registry-auth \
  "app-${ENV}-${NEXT}"

# 2. 等待 NEXT 健康检查通过（最多 5 分钟）
echo "[蓝绿] 等待 ${NEXT} 健康..."
for i in $(seq 1 30); do
  if docker service ps "app-${ENV}-${NEXT}_app-${NEXT}" \
       --filter desired-state=running --format '{{.CurrentState}}' \
       | grep -q "Running"; then
    sleep 10   # 多观察 10s 确保稳定
    break
  fi
  sleep 10
done

# 3. 健康检查 NEXT 端口
if ! curl -fsS "http://127.0.0.1:808${NEXT#blue}/actuator/health" | grep -q UP; then
  echo "[蓝绿] ${NEXT} 健康检查失败，保留 ${ACTIVE}，不切换流量"
  docker stack rm "app-${ENV}-${NEXT}"
  exit 1
fi

# 4. 切换 nginx upstream（重新部署 nginx service 用新 config）
#    nginx 配置文件软链切到 NEXT，然后 force update
sed -i "s/app-${ACTIVE}/app-${NEXT}/g" "${STACK_DIR}/nginx/${NEXT}.conf"
docker config create "nginx_${NEXT}_$(date +%s)" "${STACK_DIR}/nginx/${NEXT}.conf" || true
docker service update --force --config-rm "nginx_${ACTIVE}" --config-add "nginx_${NEXT}=${STACK_DIR}/nginx/${NEXT}.conf" "app-${ENV}_nginx"

# 5. 记录 active，老 stack 保留 30 分钟后清理
echo "${NEXT}" > "${ACTIVE_FILE}"
echo "[蓝绿] 流量已切到 ${NEXT}。老 stack ${ACTIVE} 保留 30 分钟后清理。"
( sleep 1800 && docker stack rm "app-${ENV}-${ACTIVE}" ) &

# 6. 自动回滚开关：发到 prod 时通知飞书
curl -s -X POST "https://open.feishu.cn/open-apis/bot/v2/hook/${FEISHU_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{\"msg_type\":\"text\",\"content\":{\"text\":\"[蓝绿] ${ENV} 切到 ${NEXT}，版本 ${IMAGE_TAG}\"}}"

    6.1.1 Harbor 复制策略生产配置¶

    场景：主 Harbor 故障，所有镜像拉不下来，CI 全堵。
    正确做法：配置 Harbor 复制策略到备用 Harbor，关键参数：
    - 复制模式：push-based（主推到备，避免备拉主时主故障）
    - 过滤器：{name: "legacy/*"} 按项目复制
    - 触发模式：event-based（push 即复制，不依赖定时）
    - 覆盖策略：always（保持主备一致）
    - 带宽限制：工作时段限速 50MB/s，避免占满带宽

    # Harbor 复制策略 API 创建示例
curl -X POST "https://harbor.example.com/api/v2.0/replication/policies" \
  -H "Authorization: Bearer ${HARBOR_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "legacy-to-backup",
    "src_registry": { "id": 1 },
    "dest_registry": { "id": 2 },
    "trigger": { "type": "event_based" },
    "filters": [{ "type": "name", "value": "legacy/*" }],
    "deletion": true,
    "override": true
  }'

    出处：Harbor Replication 官方文档 与社区 issue harbor/harbor#15000。

    6.1.2 Docker Swarm 蓝绿之 nginx 配置漂移¶

    场景：蓝绿切换后，nginx 还是把流量打到老 stack。检查发现 docker config 是只读的，sed 改文件后 nginx service 没 reload。
    正确做法：
    1. 不要 sed 改 nginx 配置后只 docker service update --force
    2. 必须创建新 docker config，再用 docker service update --config-rm --config-add 替换
    3. nginx 镜像默认监听 SIGTERM reload，确保镜像支持 nginx -s reload
    4. 验证切换：切换后立即 curl 验证 upstream，3 次失败立即切回

    出处：社区讨论 docker/swarmkit#2300 与 nginxinc/docker-nginx#316。

    6.1.4 Loki 收集老项目 stdout 日志的 label 爆炸¶

    场景：老项目每个请求都打 log，Loki 索引爆炸，查询慢。
    正确做法：
    1. Loki label 只用 service + env + level，不要用 request_id、user_id 等高基数字段
    2. Promtail 配置 pipeline_stages 提取关键字段为 label，其余留 message
    3. 老项目 log 格式统一改 JSON，方便 Promtail 解析

    # promtail-config.yml 片段
scrape_configs:
  - job_name: docker
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        filters: [{ type: label, values: ["com.docker.stack.namespace=app-prod"] }]
    pipeline_stages:
      - json:
          expressions:
            level: level
            msg: msg
      - labels:
          level:                              # 仅 level 入 label
    relabel_configs:
      - source_labels: [__meta_docker_container_name]
        regex: '/(.*)'
        target_label: service

    出处：Grafana Loki cardinality 最佳实践。

    6.1.5 DB 迁移 Expand-Contract 实战¶

    场景：老项目要把 user.phone 从 varchar(20) 改成 varchar(32)，直接 ALTER TABLE 锁表 30 秒，prod 报警。
    正确做法（5 步，跨 2 次发布）：

    图 6-1：Expand-Contract 改字段类型
┌────────────────────────────────────────────────────────────────────────┐
│  发布 v1.1（Expand，扩大）                                               │
│   - ALTER TABLE user ADD COLUMN phone_new varchar(32);  ← 不锁表         │
│   - 应用 v1.1：写时双写 phone + phone_new，读时仍用 phone                 │
│   - DB 迁移 Job：批量回填 phone_new = phone                              │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│  发布 v1.2（Switch，切换）                                               │
│   - 应用 v1.2：读改用 phone_new，写仍双写（保险）                          │
│   - 观察 1 周，确认无问题                                                 │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│  发布 v1.3（Contract，收缩）                                             │
│   - 应用 v1.3：只读写 phone_new，不再碰 phone                            │
│   - ALTER TABLE user DROP COLUMN phone;  ← 现在可以安全删除               │
│   - 可选：RENAME COLUMN phone_new TO phone                              │
└────────────────────────────────────────────────────────────────────────┘

    Flyway 脚本组织：
    - V1.1.0__expand_add_phone_new.sql：ADD COLUMN
    - V1.1.1__backfill_phone_new.sql：UPDATE 双写
    - V1.3.0__contract_drop_phone.sql：DROP COLUMN

    关键铁律：
    1. 一个 release 只做 Expand 或 Contract，不混合
    2. Expand 必须向后兼容（老应用读旧列仍能跑）
    3. Contract 前必须确认所有应用版本已升级（否则会读不到列）

    出处：Pramod Sadalage 的 Expand-Contract 模式 与 Flyway 社区案例。

    场景：某电商团队 Argo Rollouts 金丝雀，5% 流量时 analysis 通过，25% 时失败，但 Rollout 已经把 25% pod 起来了，回滚慢。
    正确做法：
    1. maxSurge: 1 maxUnavailable: 0，金丝雀阶段绝不减少 stable 副本
    2. analysis 模板 failureLimit: 1（不要 2，快速失败）
    3. 金丝雀 Service 用 nginx trafficRouting，pod 数可独立于流量比例
    4. 中止后立即 kubectl argo rollouts abort，不要等自动回滚
    5. 容器 preStop 加 30s sleep，确保 nginx 摘流量后才停 pod

    strategy:
  canary:
    maxSurge: 1
    maxUnavailable: 0
    trafficRouting:
      nginx:
        stableIngress: primary
        additionalIngressAnnotations:
          nginx.ingress.kubernetes.io/canary-weight: '5'

    出处：Argo Rollouts 社区 issue argoproj/argo-rollouts#900 与 ByteDance 工程博客。

    6.2.2 External Secrets + Vault 权限边界¶

    场景：External Secrets 拉不到 Vault 密钥，pod 起不来；查日志发现 K8s ServiceAccount 没 Vault auth 权限。
    正确做法：
    1. Vault 侧配 K8s auth role，绑定 namespace + serviceaccount
    2. ExternalSecret 与 SecretStore 必须同 namespace（或用 ClusterSecretStore）
    3. Vault policy 最小权限：只允许读 secret/data/<env>/<service>/*
    4. 加 refreshInterval: 1h，但 pod 启动时立即触发一次同步
    5. 监控 ExternalSecret 状态：external_secret_status{condition="Ready"} == 0 告警

    # Vault 配置示例
vault auth enable kubernetes
vault write auth/kubernetes/config kubernetes_host="https://k8s.example.com"
vault policy write java-service-prod - <<EOF
path "secret/data/prod/java-service/*" { capabilities = ["read"] }
EOF
vault write auth/kubernetes/role/java-service-role \
  bound_service_account_names=java-service \
  bound_service_account_namespaces=prod \
  policies=java-service-prod \
  ttl=1h

    出处：External Secrets 官方 Vault 示例 与社区 issue external-secrets/external-secrets#1800。

    6.2.3 Dependency-Track 与现有告警体系打通¶

    场景：Dependency-Track 扫出 CRITICAL 漏洞，但没人看；现有告警都在 Prometheus/Alertmanager。
    正确做法：用 Dependency-Track 的 webhook + Alertmanager 转发：

    # Dependency-Track 配置 webhook 到中转服务
# 中转服务把漏洞事件转成 Prometheus 指标推 Pushgateway

    # dtrack-bridge.py —— Dependency-Track 事件转 Prometheus 指标
from flask import Flask, request
import requests, json

app = Flask(__name__)

@app.route('/webhook', methods=['POST'])
def webhook():
    data = request.json
    # Dependency-Track 的 notification payload
    vulns = data.get('notification', {}).get('subjects', [])
    for v in vulns:
        proj = v.get('subject', {}).get('projectName', 'unknown')
        sev = v.get('subject', {}).get('vulnId', '')
        cve = v.get('subject', {}).get('cveId', '')
        # 推 Pushgateway，作为告警数据源
        metric = f'dtrack_vulnerability{{project="{proj}",severity="{sev}",cve="{cve}"}} 1\n'
        requests.post('http://pushgateway:9091/metrics/job/dtrack', data=metric)
    return '', 200

    # Alertmanager 告警规则
- alert: CriticalVulnerabilityDetected
  expr: dtrack_vulnerability{severity="CRITICAL"} > 0
  for: 1h
  labels: { severity: critical }
  annotations:
    summary: "{{ $labels.project }} 检测到 CRITICAL 漏洞 {{ $labels.cve }}"
    description: "请在 24 小时内升级依赖或缓解"

    出处：Dependency-Track 官方通知文档 与 OWASP 社区案例。

    6.2.4 K8s ConfigMap 滚动更新不生效¶

    场景：改了 ConfigMap，pod 没重新加载，老配置还在跑。
    根因：ConfigMap 是 volume mount，pod 不会自动重启。
    正确做法：
    1. 用 Reloader（开源工具）：ConfigMap/Secret 变更自动触发 rollout
    2. 或在 Deployment annotation 加 hash：

    spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print "$.Values.configMapData" | sha256sum) }}

    3. Spring Boot 用 spring-cloud-kubernetes 监听 ConfigMap 变更热刷新（避免重启）

    出处：Reloader 项目 与 K8s 社区 best practice。

    6.2.5 Argo CD selfHeal 把手动 hotfix 还原¶

    场景：prod 紧急 hotfix，运维直接 kubectl edit 改了 image，5 分钟后 Argo CD selfHeal 把它还原了，事故扩大。
    正确做法：
    1. prod 关闭 selfHeal，只保留 prune
    2. 紧急 hotfix 走 Argo CD 的 "Sync app from specific revision" 或直接改部署仓 + fast-track MR
    3. 配 Argo CD resource.customizations 对特定资源（如 ConfigMap）禁用 selfHeal
    4. 监控 argocd_app_info 指标，sync status 偏离立即告警
    5. 建立"禁直推 K8s"的铁律，违者复盘

    出处：Argo CD selfHeal 文档 与社区 ADR 案例。

    7.3 Spring 官方项目 Dockerfile + 扫描 + 部署¶

    Spring Boot 官方推荐的分层 Dockerfile（Layered JAR）：

    # Spring 官方推荐：分层构建，缓存利用率最高
FROM eclipse-temurin:21-jdk-jammy AS builder
WORKDIR /build
COPY mvnw .
COPY .mvn .mvn
COPY pom.xml .
RUN ./mvnw -B dependency:go-offline
COPY src ./src
RUN ./mvnw -B -DskipTests clean package spring-boot:repackage \
    && java -Djarmode=layertools -jar target/*.jar extract

FROM eclipse-temurin:21-jre-jammy
WORKDIR /app
COPY --from=builder /build/dependencies/ ./
COPY --from=builder /build/spring-boot-loader/ ./
COPY --from=builder /build/snapshot-dependencies/ ./
COPY --from=builder /build/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

    关键点：
    1. 分层：依赖层与应用层分离，依赖不变时只重建应用层（缓存命中）
    2. jarmode=layertools：Spring Boot 3.x 内置工具，自动分层
    3. CoSign 签名：官方推荐构建后用 CoSign 签名镜像

    # Spring 官方推荐的镜像签名流程
cosign sign --key cosign.key harbor.example.com/legacy/java-service:v1.2.0

cosign verify --key cosign.pub harbor.example.com/legacy/java-service:v1.2.0

    8. 风险控制（双轨并行与回滚预案）¶

    关联：07-部署与发布策略 与 09-监控可观测性与回滚。

    8.1 双轨并行切换策略¶

    核心原则：新流程上线时，老流程不下线，双跑一段时间，确认无问题再切换。

    图 8-1：双轨并行切换时间线
┌──────────────────────────────────────────────────────────────────────┐
│  T0：新流程搭建完成，开始双轨                                         │
│  ─ 老流程：手工 kubectl / scp 部署（仍为主）                          │
│  ─ 新流程：CI/CD 自动部署（仅 dev/test，shadow 模式）                 │
│  ─ 验证：新流程产出与老流程一致                                       │
├──────────────────────────────────────────────────────────────────────┤
│  T+2 周：dev/test 切到新流程                                          │
│  ─ dev/test 不再用老流程                                              │
│  ─ stage/prod 仍双轨                                                  │
├──────────────────────────────────────────────────────────────────────┤
│  T+1 月：stage 切到新流程                                             │
│  ─ stage 不再用老流程                                                  │
│  ─ prod 仍双轨，但新流程为主                                          │
├──────────────────────────────────────────────────────────────────────┤
│  T+2 月：prod 切到新流程，老流程下线                                  │
│  ─ 老流程脚本归档到 git history，文档标记 deprecated                  │
│  ─ 1 个月后删除老脚本                                                 │
└──────────────────────────────────────────────────────────────────────┘

    8.2 切换决策矩阵¶

    指标 阈值 决策
    新流程成功率 ≥ 95% 继续切换
    新流程成功率 80~95% 暂停切换，排查问题
    新流程成功率 < 80% 回退到老流程，重新评估
    新流程平均时长 ≤ 老流程 1.5 倍 继续
    事故数 1 个月内 ≥ 2 次新流程引发事故 立即回退

    8.3 回滚预案¶

    8.3.1 应用层回滚（方案 1）¶

    # Swarm：1 秒回滚
docker service rollback app-prod_app

# 蓝绿：切回老 stack
echo "blue" > /opt/stacks/prod/.active   # 改 active 指针
docker service update --force app-prod_nginx  # nginx 切回 blue

    8.3.2 应用层回滚（方案 2）¶

    # Argo CD：回滚到上一 revision
argocd app rollback java-service-prod

# 或用 kubectl
kubectl argo rollouts undo java-service -n prod

    8.3.3 DB 回滚（最难，必须预案）¶

    铁律：DB 变更必须遵守 Expand-Contract，Contract 阶段不可逆，所以：
    1. Expand 阶段可以回滚（drop 新列）
    2. Contract 阶段一旦执行（drop 旧列），只能重新做 Expand 恢复
    3. 每次 Contract 前必须备份：pg_dump / mysqldump
    4. Contract 必须有 rollback SQL 预先准备好

    # DB 回滚脚本示例
#!/usr/bin/env bash
set -euo pipefail
REV="${1:?usage: db-rollback.sh <revision>}"
BACKUP_FILE="/opt/backups/db/pre-${REV}-$(date +%Y%m%d).sql.gz"

if [ ! -f "${BACKUP_FILE}" ]; then
  echo "无备份文件 ${BACKUP_FILE}，无法回滚！"
  exit 1
fi

# 1. 应用回滚到 Contract 前版本
kubectl argo rollouts undo java-service -n prod

# 2. 恢复 DB（仅当 Contract 已执行且无新数据写入时）
read -p "确认要恢复 DB 备份吗？这将丢失 Contract 后的所有数据 [y/N]: " confirm
[ "$confirm" = "y" ] || exit 0
gunzip -c "${BACKUP_FILE}" | psql "${DB_URL}"

    9. 团队文化改造¶

    关联：01-认知地基 与 10-进阶与工程化。

    9.1 心智迁移：从"开发背锅"到"流水线背锅"¶

    老文化（开发背锅） 新文化（流水线背锅）
    出了事故问"谁改的" 出了事故问"流水线哪一步没拦住"
    Code Review 靠人情 Code Review 靠 MR 强制
    部署靠"老王"经验 部署靠脚本 + 流水线
    回滚靠记忆"上次跑哪个版本" 回滚靠 docker service rollback
    测试靠"我本地跑过" 测试靠 CI 必须绿
    文档靠 wiki 散落 文档靠 runbook 在仓库

    9.2 改造路径（4 步）¶

    步骤 1：建立"流水线是真理"的共识¶

    • 任何变更不通过流水线 = 违规
    • 出事故第一复盘"流水线漏了什么"，不是"谁错了"
    • 老王的知识必须落到脚本，不允许只在他脑子里

    步骤 2：消除"英雄文化"¶

    • 部署文档化：每次部署有 runbook
    • 知识民主化：每人都能跑部署，不是只有"运维专员"
    • 故障演练常规化：每月一次，全员轮值

    步骤 3：建立 blameless postmortem 文化¶

    • 事故复盘不点名、不追责
    • 复盘产出"流水线改进项"，不是"责任人处罚"
    • 每个改进项有 owner 和 deadline

    步骤 4：指标驱动¶

    • DORA 四指标公开看板，全员可见
    • 每月 review 指标趋势，不达标找根因
    • 把"变更失败率"作为团队 KPI（不是个人 KPI）

    9.3 老项目改造的常见文化阻力¶

    阻力 表现 应对
    "CI 太慢" 开发抱怨等不及 优化 CI 缓存、并行化；展示 ROI：CI 1 分钟 vs 排查 1 小时
    "质量门太严" 团队抵触 渐进式收紧（见 新团队方案 §10 误区 4）
    "老流程也能跑" 不愿切新流程 双轨并行 + 数据对比，让团队自己看到差距
    "运维不让我改" 部署权不放 用 GitOps 让"改部署 = 提 MR"，运维只审 MR
    "我习惯 kubectl" 个人习惯难改 老脚本归档 + 1 个月宽限期 + 培训
