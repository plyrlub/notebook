## 5.2 多语言构建：依赖管理与多阶段 Dockerfile

多阶段构建四原则：
1. **Builder 层装构建工具，Final 层只装运行时依赖**
2. **非 root 用户**运行
3. **HEALTHCHECK** 加探针
4. **LABEL** 打 gitSHA/版本号（参见 S10.3 制品映射）

### 5.2.1 Python：UV（2026 首选）+ pip/poetry（存量兼容）

#### 1. 依赖管理

| 工具 | 特点 | 2026 推荐度 |
| ---- | ---- | :--: |
| **UV**（uv pip + uv sync + uv publish 一套全栈） | Astral 出品，Rust 实现，替代 pip/poetry/pip-tools；安装速度比 poetry 快 10-100 倍；2026 Python 生态事实标准 | ⭐⭐⭐⭐⭐⭐（2026 首选） |
| pip + requirements.txt | 最简单，存量小项目可用 | ⭐⭐⭐ |
| poetry | lockfile + pyproject.toml，2020-2024 主流 | ⭐⭐⭐（存量迁移中） |

> **2026 定调**：新项目一律 UV；老项目如果已经用了 poetry 能跑就先跑，但新建项目 / 升级项目优先迁移到 UV。UV 兼容 `pyproject.toml`，从 poetry 迁移成本非常低（直接改锁文件即可）。

#### 2. 多阶段 Dockerfile（UV 标准模板 ← 2026 首选）

> UV 优势：不依赖 Python 解释器本身，二进制安装即可；Builder 层的 `--mount=type=cache` 配合 Docker BuildKit 缓存更极致（Kaniko 用 `UV_CACHE_DIR`）。

```dockerfile
# ========== Builder Stage：装依赖 + 编译 ==========
FROM python:3.12-slim AS builder

# 1. 装 UV（二进制，10MB，Rust 写的，不依赖 Python）
ENV UV_VERSION=0.6.6 \
    UV_LINK_MODE=copy \
    UV_CACHE_DIR=/root/.cache/uv

ADD --chmod=755 https://astral.sh/uv/${UV_VERSION}/install.sh /install-uv.sh
RUN sh /install-uv.sh && rm /install-uv.sh

WORKDIR /build

# 2. 先拷依赖文件 → Docker layer cache 命中就不用重新装
COPY pyproject.toml uv.lock ./

# 3. 装生产依赖到独立目录（--no-dev 只装生产、--frozen 严格按 lockfile，不一致就报错）
RUN --mount=type=cache,target=${UV_CACHE_DIR} \
    uv sync --frozen --no-dev --no-project

# 4. 最后拷源码（前面几层不失效，每次只有源码变了才重跑这步）
COPY app/ ./app/

# ========== Final Stage：最小运行时镜像 ==========
FROM python:3.12-slim AS final

# 非 root 用户
RUN groupadd -r appuser && useradd -r -g appuser appuser

WORKDIR /app

# 5. 从 builder 拷 .venv（UV 默认装在项目目录的 .venv）+ 源码
COPY --from=builder /build/.venv /app/.venv
COPY --from=builder /build/app /app/app

# 6. 把 .venv 的 bin 加到 PATH（让 CMD 直接 `python` 就能用装在 .venv 里的依赖）
ENV PATH="/app/.venv/bin:$PATH"

# 制品元数据标签
ARG GIT_COMMIT=unknown
ARG BUILD_DATE=unknown
ARG VERSION=unknown
LABEL org.opencontainers.image.revision="${GIT_COMMIT}" \
      org.opencontainers.image.created="${BUILD_DATE}" \
      org.opencontainers.image.version="${VERSION}"

USER appuser

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health', timeout=3)" || exit 1

# .venv/bin/python 在 PATH 里，直接写 python 即可
CMD ["python", "-m", "app.main"]
```

#### 3. 常见坑

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| UV 和 pip/poetry 混用 | 同时用 `pip install` 和 `uv sync` 会导致 site-packages 冲突 | 项目全流程只用 UV，别碰 pip |
| `uv.lock` 里的 `requires-python` 不兼容 | Builder 是 Python 3.12，但 `uv.lock` 要求 `>=3.13` | Builder 和 Final 的 Python 大版本必须和 uv.lock 里声明的一致 |
| UV 的虚拟环境路径没写对 | Final 层没把 `.venv/bin` 加到 PATH 导致 `import` 不到包 | Final 层一定要 `ENV PATH="/app/.venv/bin:$PATH"` |
| `UV_CACHE_DIR` 在 Kaniko 里不生效 | Kaniko 不支持 BuildKit 的 `--mount=type=cache` | Kaniko 场景别写 `--mount=type=cache`，改用 GitLab CI 原生 `cache:` 缓存 `UV_CACHE_DIR`（见 5.5.1） |

#### 4. 从 poetry 迁移到 UV 的最小步骤（5 步走）

1. `uv init --from poetry .` → 自动读 `pyproject.toml` 并生成 `uv.lock`（等价 `uv lock`）
2. 把 `Dockerfile` 里 poetry 那段换成上面的 UV Builder 模板
3. CI 里：把 `poetry install` → `uv sync --frozen --no-dev`
4. 删除 `poetry.lock`，保留 `pyproject.toml` + `uv.lock`
5. 本地验证：`uv sync && uv run pytest` 确认跑通

> pyproject.toml 结构不变，lock 文件换了而已。迁移风险低。

### 5.2.2 Java：Maven + Gradle

#### 1. 依赖管理

| 工具 | 特点 | 2026 推荐度 |
| ---- | ---- | :--: |
| Maven | XML 语法，稳定，企业级主流 | ⭐⭐⭐⭐⭐（存量项目） |
| Gradle | Groovy/Kotlin DSL，构建速度快 | ⭐⭐⭐⭐（新项目） |

#### 2. 多阶段 Dockerfile（Maven 模板）

```dockerfile
# ========== Builder Stage：Maven 编译打包 ==========
FROM maven:3.9-eclipse-temurin-17 AS builder

WORKDIR /build

# 先拷 pom.xml 下载依赖（层缓存）
COPY pom.xml ./
RUN mvn -B dependency:go-offline

# 再拷源码编译
COPY src ./src
RUN mvn -B clean package -DskipTests

# ========== Final Stage：JRE 只跑 jar ==========
FROM eclipse-temurin:17-jre-jammy AS final

# 非 root 用户
RUN groupadd -r spring && useradd -r -g spring spring
USER spring

WORKDIR /app

# 只拿 jar 包（多模块项目：找正确的 jar）
COPY --from=builder /build/target/*.jar /app/app.jar

ARG GIT_COMMIT=unknown
LABEL org.opencontainers.image.revision="${GIT_COMMIT}"

EXPOSE 8080

# Spring Boot 健康检查
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1

# JVM 内存参数由环境变量传入（不同环境调优）
ENTRYPOINT ["sh", "-c", "java ${JAVA_OPTS:- -Xms512m -Xmx512m} -jar /app/app.jar"]
```

#### 3. 常见坑

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| JDK 与 JRE 版本不一致 | Builder 用 JDK17 编译但 Final 用 JRE11 跑 → ClassVersionError | 统一版本系列 |
| 拿错 jar 包 | target/ 下有多个 jar（original + 可执行） | Spring Boot 插件配置 `finalName`，COPY 指定精确名 |

### 5.2.3 Lua：LuaRocks + OpenResty

> 完整专题参见 [S8 Lua 场景的 CI/CD](./补充专题/S8-Lua场景CICD.md)

#### 1. 依赖管理

| 工具 | 用途 | 2026 推荐度 |
| ---- | ---- | :--: |
| LuaRocks | Lua 包管理 | ⭐⭐⭐⭐⭐ |
| opm | OpenResty 扩展包 | ⭐⭐⭐⭐ |

#### 2. 多阶段 Dockerfile（OpenResty 模板）

```dockerfile
# ========== Builder Stage：装 LuaRocks 依赖 ==========
FROM openresty/openresty:1.27.1.1-alpine-fat AS builder

# 装编译工具（alpine-fat 自带 luarocks）
RUN apk add --no-cache gcc musl-dev make

# 装 Lua 依赖（先拷 rockspec 缓存层）
COPY myapp.rockspec ./
RUN luarocks install --tree /usr/local/openresty/luajit \
    lua-resty-redis \
 && luarocks make myapp.rockspec

# 拷 Lua 源码
COPY lua/ /usr/local/openresty/luajit/share/lua/5.1/

# ========== Final Stage：生产 OpenResty ==========
FROM openresty/openresty:1.27.1.1-alpine AS final

# 非 root
RUN addgroup -S appuser && adduser -S appuser -G appuser

WORKDIR /app

# 从 builder 拷 Lua 依赖和源码（不拷编译工具）
COPY --from=builder /usr/local/openresty/luajit/lib/lua/5.1/     /usr/local/openresty/luajit/lib/lua/5.1/
COPY --from=builder /usr/local/openresty/luajit/share/lua/5.1/   /usr/local/openresty/luajit/share/lua/5.1/

# 拷 Nginx 配置
COPY nginx.conf /usr/local/openresty/nginx/conf/nginx.conf

USER appuser

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:8080/health || exit 1

CMD ["/usr/local/openresty/bin/openresty", "-g", "daemon off;"]
```

#### 3. 常见坑（Lua 独有）

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| LuaJIT vs Lua5.1 行为差异 | 同一代码两边结果不同 | CI 必须两边都测（参见 S8） |
| package.path 容器里不一致 | luarocks 安装路径找不到 | 显式在 nginx.conf 里 `lua_package_path` 写死路径 |
| C 扩展 .so 跨架构 | Builder 是 amd64 但目标是 arm64 | 目标平台一致 |

## 5.3 测试分层金字塔与 Pipeline 集成策略

### 5.3.1 70-20-10 法则与测试金字塔

**图 5-1：测试金字塔与 Pipeline 执行策略**

```
          ┌─────────────────────────────────┐
          │        E2E / UI 测试（10%）      │  部署后跑，不阻塞 MR
          │         集成测试 / 慢 / 不稳定     │
          ├───────────────────────────────────┤
          │     集成 / 契约测试（20%）        │  Test Stage 第二批，并行
          │   依赖真实 DB/Redis/服务调用      │
          ├───────────────────────────────────┤
          │       单元测试（70%）             │  Test Stage 第一批，全并行
          │    纯内存，无外部依赖，毫秒级     │
          └───────────────────────────────────┘
```

**表 5-3：70-20-10 法则（业界共识）**

| 层级 | 比例 | 特点 | Pipeline 执行策略 |
| ---- | :--: | ---- | -------------- |
| 单元测试 | 70% | 多、快、稳 | 每个 PR 全量，并行跑，**失败硬阻断** |
| 集成测试 | 20% | 需要真实中间件 | 单元过了再跑，按模块并行，**失败硬阻断** |
| E2E / UI | 10% | 少、慢、易 flaky | **Post-Deploy Stage 跑**，只在 main + 发版 Tag；MR 里只手动触发，失败**不阻断 MR** |

> 参见 [S10.5 测试分层执行策略表](./补充专题/S10-Pipeline各环节最佳实践.md) 的六维对照表（触发条件/并行策略/失败后处理）

### 5.3.2 单元测试与覆盖率门控

#### 1. 覆盖率门控作用

覆盖率只是底线，不是目标。原则：**不要追求 100%（边际递减），守住 70-80% + 关键路径 100%**。

#### 2. 三语言配置模板

**Python（UV + pytest + pytest-cov + Cobertura XML）**

```yaml
# .gitlab-ci.yml（Python 单元测试 + 覆盖率门控）
unit:python:
  stage: test
  image: python:3.12-slim
  before_script:
    - curl -LsSf https://astral.sh/uv/0.6.6/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    - uv sync --frozen         # 装所有依赖（含 dev 依赖的 pytest pytest-cov）
    - uv run pytest tests/unit --cov=app --cov-report=xml:coverage.xml --cov-report=term
  coverage: '/TOTAL.*\s+(\d+\%)$'          # GitLab 解析 stdout 里的百分比
  artifacts:
    when: always                           # 即使失败也上传报告
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml                 # GitLab UI 覆盖率 MR 评论
      junit: test-results.xml
    paths:
      - coverage.xml
    expire_in: 7 days
```

> UV 要点：`uv sync --frozen` 装依赖，`uv run` 执行命令（自动激活 .venv）。不用再 `pip install`。

**Java（Maven + JUnit5 + JaCoCo）**

```yaml
unit:java:
  stage: test
  image: maven:3.9-eclipse-temurin-17
  script:
    # 跑单测 + JaCoCo 插桩，跳过集成测试
    - mvn -B test jacoco:report
  artifacts:
    when: always
    reports:
      junit: target/surefire-reports/*.xml
      coverage_report:
        coverage_format: cobertura
        path: target/site/jacoco/jacoco.xml
```

**Lua（busted + luacov → Cobertura XML）**

```yaml
unit:lua:
  stage: test
  image: openresty/openresty:1.27.1.1-alpine-fat
  before_script:
    - luarocks install busted
    - luarocks install luacov
    - luarocks install luacov-coveralls   # 转 XML
  script:
    - busted -c tests/unit/
    - luacov-coveralls -o coverage.xml   # 输出 Cobertura
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

#### 3. SonarQube Quality Gate（覆盖率阈值示例）

> SonarQube 的完整接入见 [5.6.2](#562-sonarqube-基础接入--quality-gate)，这里只给阈值参考。

| 指标 | 建议阈值 | 说明 |
| ---- | -------- | ---- |
| Coverage | ≥ 70% | 整体覆盖率底线 |
| Coverage on New Code | ≥ 80% | 只看新代码覆盖率更严格 |
| Duplicated Lines | ≤ 3% | 重复率高说明技术债重 |

### 5.3.3 集成测试与 GitLab services 机制

#### 1. 什么是集成测试

集成测试 = 单元测试 + 真实外部依赖（MySQL/Redis/Kafka 等），CI 里启动一个临时 MySQL。

#### 2. GitLab CI 的 services 机制（不用自己 docker-compose 起）

```yaml
# .gitlab-ci.yml
integration:
  stage: test
  image: python:3.12-slim
  # GitLab 自动起对应服务并注入到容器网络
  services:
    - name: mysql:8.0
      alias: mysql           # 别名 → 容器网络内域名
      command: ["--default-authentication-plugin=mysql_native_password"]
    - name: redis:7-alpine
      alias: redis
  variables:
    MYSQL_DATABASE: test_db
    MYSQL_ROOT_PASSWORD: testpass
    # 应用连 services 里的别名就是 host
    DB_HOST: mysql
    DB_PORT: 3306
    REDIS_HOST: redis
  before_script:
    - curl -LsSf https://astral.sh/uv/0.6.6/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    - uv sync --frozen
    - uv run pytest tests/integration/ -v
  artifacts:
    reports:
      junit: test-results.xml
```

> services 机制等价于 Docker Compose networks：启动服务别名就是 host，容器内部网络直接能通，不需要 `ports` 映射。

#### 3. services 常见坑

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| MySQL 启动慢 | services 刚启动时 MySQL 还没 ready | 在 script 开头用 `wait-for-it.sh` 探活后再跑测试 |
| MySQL 默认鉴权插件兼容问题 | MySQL 8.0 默认 `caching_sha2_password`，老客户端连不上 | 变量里用 `command` 设置 `mysql_native_password` |
| ports 不对外 | services 端口不需要映射到宿主机 | services 内部网络直接能通，不用写 `ports` |

### 5.3.4 契约测试（Pact）

> 微服务场景：消费者（Consumer）定义契约，提供者（Provider）必须遵守。

| 角色 | 职责 | Pipeline 动作 |
| ---- | ---- | ---------- |

## 5.4 Flaky Test 处理与重试机制

Flaky = 同样的代码，同样的测试，有时过有时失败。

### 5.4.1 Flaky 识别、定位、隔离

**图 5-2：Flaky 处理流程**

```
发现 Flaky（连续 2 次相同失败 = 真失败；1 次过 1 次失败 = Flaky）
    ↓
第 1 步：自动重跑（最多 2 次）—— 快速临时通过则标 Flaky
    ↓
第 2 步：自动重跑还过 → 隔离（移到 Quarantine 区不阻断）→ 开 Ticket 修 → 修好后归队
    ↓
第 3 步：持续 Flaky 率 >5% 的用例 → 必须修或删除
```

**Flaky 常见根因**：

| 根因 | 例子 | 解法 |
| ---- | ---- | ---- |
| 时间依赖 | 测试写死 100ms 期望 | 用 `freezegun` 伪造时间 |
| 测试间互相污染 | 全局变量没清理 | 每个测试 teardown 清理 |
| 并发问题 | 异步结果没等到就断言 | 加 awaitility / wait.until |
| 随机数据 | 随机生成边界情况 | Mock 随机源 seed |
| 外部依赖 flaky | 第三方 API 不稳 | Mock 外部服务 |

---

### 5.4.2 三工具里的重试策略对比

**表 5-4：三工具重试机制对比**

| 工具 | 重试语法 | 说明 | 2026 推荐度 |
| ---- | ------ | ---- | :--: |
| **GitLab CI** | `retry: max: 2 when: [runner_system_failure, ...]` | 原生支持按失败原因选择性重试 | ⭐⭐⭐⭐⭐ |
| **GitHub Actions** | `uses: nick-fields/retry@v3 with: max_attempts: 3` | 第三方 Action，只能 step 级重试 | ⭐⭐⭐⭐ |
| **Jenkins** | `retry(count) { ... }` | 声明式原生支持 | ⭐⭐⭐⭐ |

**GitLab CI 重试配置示例：**

```yaml
integration:
  stage: test
  script:
    - pytest tests/integration
  retry:
    max: 2                  # 最多额外再跑 2 次（含第 1 次共 3 次）
    when:
      - runner_system_failure        # Runner 挂了
      - api_failure                  # GitLab 自身问题
      - stuck_or_timeout_failure     # 超时（集成测试常见）
      - unknown_failure              # 网络抖动
      # 注意：不写 script_failure（测试代码真失败不重试，避免掩盖问题）
```

**关键原则**：**选择性重试外部原因**（runner/超时/网络），**不重试 `script_failure`**（代码/测试真实失败不重试，否则掩盖真问题）。

## 5.5 缓存优化（S10.1/S10.2 专题实操版）

### 5.5.1 三语言缓存键策略

**表 5-5：三语言缓存键策略对照（GitLab CI）**

| 语言 | 缓存对象 | cache key | paths | 预计命中率（>80%合格） |
| ---- | -------- | --------- | ----- | :-------------: |
| **Python（UV 2026 首选）** | UV 缓存目录 + .venv | `key: files: [uv.lock, pyproject.toml]` | `.cache/uv` `.venv` | ~88-92%（UV 自带缓存层） |
| **Python（poetry 存量）** | poetry 依赖 | `key: files: [poetry.lock, pyproject.toml]` | `.cache/poetry` `.venv` | ~85% |
| **Java** | Maven .m2/repository | `key: files: [pom.xml]` | `.m2/repository` | ~90% |
| **Java** | Gradle | `key: files: [build.gradle, settings.gradle]` | `.gradle/caches` | ~88% |
| **Lua** | LuaRocks 安装目录 | `key: files: [*.rockspec]` | `.luarocks` | ~80% |
| 通用 | Docker layer cache | Kaniko 用 `--cache-repo` | - | ~80%+ |

**完整 GitLab CI 三语言缓存配置示例：**

```yaml
# Python（UV 2026 首选）
variables:
  UV_CACHE_DIR: $CI_PROJECT_DIR/.cache/uv

build:python:uv:
  cache:
    key:
      files:
        - uv.lock
        - pyproject.toml
    paths:
      - .cache/uv
      - .venv
    policy: pull-push
  script:
    # 装 UV（Kaniko 场景下 Builder 层装，Runner 里也得装）
    - curl -LsSf https://astral.sh/uv/0.6.6/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
    - uv sync --frozen --no-dev --no-project
```

```yaml
# Python（poetry 存量兼容）
variables:
  POETRY_CACHE_DIR: $CI_PROJECT_DIR/.cache/poetry

build:python:poetry:
  cache:
    key:
      files:
        - poetry.lock
        - pyproject.toml
    paths:
      - .cache/poetry
      - .venv
    policy: pull-push
  script:
    - poetry config cache-dir $POETRY_CACHE_DIR
    - poetry install --only main
```

```yaml
# Java Maven
build:java:
  cache:
    key:
      files:
        - pom.xml
    paths:
      - .m2/repository
  script:
    - mvn -B -Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository package
```

### 5.5.2 缓存命中率监控与常见坑

| 坑 | 现象 | 避坑 |
| -- | ---- | ---- |
| key 不带 lockfile hash | lockfile 变了但 key 没变，每次都 miss，命中率 < 50% | cache key 必须包含 lockfile hash |
| 缓存大小 > 500MB | 上传下载比重新装还慢 | 拆小拆细；只缓存关键本地仓库，不缓存 `.venv` 整目录（可能 3GB） |
| 多 Job 同时写缓存 | 竞争互相覆盖（后写完的覆盖前面的） | 只给 build Job 用 `policy: pull-push`，其余 Job 用 `policy: pull` |
| 不同 Runner 机器 | Runner 本地缓存机器不共享，多个 Runner 命中率 ≈ 0 | 统一用分布式缓存（S3 / OSS / MinIO） |

### 5.5.3 Nexus 代理仓加速依赖拉取

> 5.5.1 的 GitLab CI `cache:` 是**Runner 本地缓存**，解决"同一个 Runner 上次跑过，这次不用重新下载"的问题。但如果缓存 miss（lockfile 变了 / 换了 Runner），还是要去公网拉包——**Nexus 代理仓**解决的就是这个"从公网拉包慢 / Rate Limit"的问题。

**两层缓存的关系**：

```
第一层：Nexus 代理仓（机房级别，所有 Runner 共享）
  公网（PyPI / Maven Central / npm）→ Nexus 缓存 → 所有 Runner 都能命中
  解决：跨 Runner 缓存不共享 + 公网拉取慢 + Rate Limit

第二层：GitLab CI cache（Runner 级别，单个 Runner 本地）
  Nexus → Runner 本地 .m2 / .cache/uv → 构建时直接用
  解决：同一个 Runner 上次拉过，这次不用再走 Nexus
```

**Nexus 代理仓三语言配置**：

```yaml
# ============================================================
# Python（UV）：UV_INDEX_URL 指向 Nexus PyPI 代理仓
# ============================================================
variables:
  UV_CACHE_DIR: $CI_PROJECT_DIR/.cache/uv
  # Nexus PyPI proxy repository 地址
  UV_INDEX_URL: "http://nexus.example.com:8081/repository/pypi-proxy/simple"

build:python:uv:
  cache:
    key:
      files: [uv.lock, pyproject.toml]
    paths: [.cache/uv, .venv]
    policy: pull-push
  before_script:
    - curl -LsSf https://astral.sh/uv/0.6.6/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    # UV 会读 UV_INDEX_URL 环境变量，所有包都从 Nexus 代理拉
    - uv sync --frozen --no-dev --no-project
```

```yaml
# ============================================================
# Java（Maven）：settings.xml 指向 Nexus Maven 代理仓
# ============================================================
build:java:
  cache:
    key:
      files: [pom.xml]
    paths: [.m2/repository]
    policy: pull-push
  before_script:
    # 生成 settings.xml，mirror 指向 Nexus Maven proxy
    - |
      mkdir -p ~/.m2
      cat > ~/.m2/settings.xml << EOF
      <settings>
        <mirrors>
          <mirror>
            <id>nexus</id>
            <mirrorOf>*</mirrorOf>
            <url>http://nexus.example.com:8081/repository/maven-proxy/</url>
          </mirror>
        </mirrors>
      </settings>
      EOF
  script:
    - mvn -B -Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository package
```

```yaml
# ============================================================
# Node.js（npm）：.npmrc 指向 Nexus npm 代理仓
# ============================================================
build:node:
  before_script:
    - npm config set registry http://nexus.example.com:8081/repository/npm-proxy/
  script:
    - npm ci
```

**Nexus 代理仓 vs GitLab CI cache 对比**：

| 维度 | Nexus 代理仓 | GitLab CI cache |
| ---- | ------------ | --------------- |
| 作用范围 | 机房级别（所有 Runner 共享） | Runner 级别（单台 Runner） |
| 缓存粒度 | 单个包级别（按包缓存） | 整个依赖目录级别（按 lockfile hash） |
| 命中条件 | 只要 Nexus 缓存过这个包版本就命中 | lockfile hash 不变才命中 |
| 解决问题 | 公网拉取慢 / Rate Limit | 同 Runner 重复拉取 |
| 需要额外部署 | ✅ 需要 Nexus 服务 | ❌ GitLab CI 内置 |
| 两者关系 | **互补，不互斥**（Nexus 第一层，cache 第二层） | — |

> **结论**：两层缓存配合使用。Nexus 解决"第一次拉包也要快"（公网 → Nexus 本地缓存），GitLab CI cache 解决"第二次拉包不用再走 Nexus"（Nexus → Runner 本地）。如果只配一层，要么跨 Runner 慢（只有 cache 没 Nexus），要么同 Runner 重复拉（只有 Nexus 没 cache）。

> Nexus 的完整部署与代理仓配置参见 [S11 包仓库 Nexus/Harbor/GitLab Registry](./补充专题/S11-包仓库Nexus-Harbor-GitLabRegistry.md)。

### 5.6.1 Gitleaks 凭据泄露扫描（PR / Lint 后立即跑）

**发现密钥立即终止，比晚发现好。**

```yaml
# .gitlab-ci.yml（放在 Lint Stage 之后，越前面越好）
gitleaks:
  stage: lint
  image: zricethezav/gitleaks:latest
  variables:
    GIT_DEPTH: ""   # 全历史扫描；首次全量，日常用 --log-opts 只扫增量
  script:
    # 日常增量：只扫当前 commit 与上一个 commit 之间
    - gitleaks detect --source . --report-format json --report-path gitleaks-report.json --log-opts $CI_COMMIT_BEFORE_SHA..$CI_COMMIT_SHA
    # 首次全量（第一次接入跑）：
    # - gitleaks detect --source .
  artifacts:
    when: always
    paths: [gitleaks-report.json]
  allow_failure: false    # 发现密钥 → 阻断（硬阻断）
```

**接入注意事项**：

1. **第一次接入可能爆历史问题很多** → 第一次接入用 `allow_failure: true` 软告警，清理历史密钥再开硬阻断
2. **Allowlist 误报**：写 `.gitleaksignore` 文件排除假阳性（如 `-----BEGIN PUBLIC KEY-----` 公开密钥）
3. **历史问题修复**：真发现历史密钥泄露了 → 立即 revoke（销毁重新生成）→ Git 历史重写（BFG / git-filter-repo），参见 S5.1 泄漏密钥处理流程
