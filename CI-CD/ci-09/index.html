    第九章：监控、可观测性与回滚¶

    9.1.1 监控 vs 可观测性（从"被动告警"到"主动探索"）¶

    传统监控：你预先知道"哪些问题可能发生"，针对每个问题配一条告警规则。比如 CPU > 80% 告警、磁盘 > 90% 告警。问题是你不可能预见所有问题——微服务架构下一个请求经过 5 个服务，某个服务因为 GC 卡顿 200ms，传统监控完全看不到。

    可观测性：你不需要预见问题，而是把系统内部的状态充分暴露出来（指标 + 日志 + 链路），出问题时可以主动探索：从告警切入 → 看指标趋势 → 查链路定位慢在哪 → 查日志确认错误原因。

    表 9-1：监控 vs 可观测性

    维度 传统监控 可观测性
    核心思想 预设告警，被动响应 暴露状态，主动探索
    数据来源 指标为主 指标 + 日志 + 链路
    应对未知问题 ❌ 没配告警就发现不了 ✅ 可以从数据中探索发现
    典型工具 Zabbix / Nagios Prometheus + Loki + OTel
    适合架构 单体应用 微服务 / 分布式系统

    小团队认知：可观测性不是"高大上的额外负担"，而是让你半夜不用爬起来看日志的基础设施。投入 2 天配好 Prometheus + Grafana + 结构化日志，后面每次出问题都能 5 分钟定位而不是 30 分钟 grep。

    三支柱的分工：

    支柱 回答什么问题 数据量 查询方式 成本

    Traces 链路 一个请求经过哪些服务、每段花了多久 中（采样后） Trace ID 查询 中

    三支柱联动流程（出问题时的标准排查路径）：

    告警触发（Metrics） → 看哪个指标异常
    ↓
查链路（Traces） → 定位是哪个服务/哪段慢
    ↓
查日志（Logs） → 确认具体错误原因
    ↓
修复 → 验证（Metrics 恢复）

    9.1.3 黄金信号（延迟/流量/错误/饱和度）+ USE/RED 方法¶

    表 9-2：Google SRE 四大黄金信号

    信号 含义 典型指标 为什么要看
    延迟 Latency 请求处理耗时 p50/p95/p99 延迟 慢 = 用户体验差，p99 比 p50 更重要
    流量 Traffic 系统负载 QPS / 请求量 / 并发数 容量规划基础，异常增长可能被攻击
    错误 Errors 失败请求比例 5xx 率 / 业务错误率 直接影响用户，SLO 核心指标
    饱和度 Saturation 资源使用率 CPU / 内存 / 磁盘 / 连接池 接近 100% = 快要崩了

    四信号必须同时看：只看错误率不够——延迟升高（黄金信号①）但还没报错（黄金信号③），说明系统正在恶化但用户还没感知到。四个信号一起看才能提前发现问题。

    两种应用视角的框架：

    框架 应用对象 四个维度 记忆
    USE 方法 资源（CPU/磁盘/网络） Utilization / Saturation / Errors 资源够不够用
    RED 方法 服务（API/应用） Rate / Errors / Duration 服务健不健康

    小团队落地建议：
    1. 每个服务先用 RED 方法配 3 个指标（QPS + 错误率 + p99 延迟）→ 覆盖黄金信号①②③
    2. 每个节点用 USE 方法配 3 个指标（CPU + 内存 + 磁盘）→ 覆盖黄金信号④
    3. 6 个指标就能覆盖 80% 的监控需求，不要一上来就配 100 个指标

    Pull 模式 vs Push 模式：

    维度 Pull（Prometheus） Push（StatsD/Datadog Agent）
    谁主动 Prometheus 拉应用 应用推给 Agent
    优势 知道目标列表、可观测、丢失立即发现 不需要暴露 /metrics 端点
    劣势 应用必须暴露 /metrics Agent 挂了不知道谁没推
    适合 长期运行的服务 短命任务（CI Job、Batch）

    Pushgateway 的特殊场景：CI Job / Cron Job 这类短命任务，Prometheus 来不及 Pull 就结束了。用 Pushgateway 做中转：任务结束时 push 指标到 Pushgateway，Prometheus 再从 Pushgateway pull。

    9.2.2 Python FastAPI 应用埋点（prometheus-client + 指标命名规范）¶

    指标类型选择：

    指标类型 用途 例子 什么时候用
    Counter 只增不减的计数 请求总数 / 错误总数 统计"发生了多少次"
    Gauge 可增可减的当前值 CPU 使用率 / 连接池占用 统计"现在是多少"
    Histogram 分布（分位数） 延迟分布 p50/p95/p99 统计"分布情况"
    Summary 分布（客户端算分位数） 延迟分位数 不推荐（聚合困难，用 Histogram）

    FastAPI 完整埋点示例：

    # app/metrics.py
from prometheus_client import Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST
from fastapi import FastAPI, Request, Response
import time

# === 指标定义（命名规范：<namespace>_<subsystem>_<name>_<unit>） ===

# RED 方法三指标
HTTP_REQUESTS_TOTAL = Counter(
    "myapp_http_requests_total",
    "HTTP 请求总数",
    labelnames=["method", "endpoint", "status"],
)

HTTP_REQUEST_DURATION = Histogram(
    "myapp_http_request_duration_seconds",
    "HTTP 请求延迟（秒）",
    labelnames=["method", "endpoint"],
    buckets=[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0],
    # buckets 设计：覆盖 5ms ~ 10s，按 10 的倍数递增
)

# 业务指标（自定义）
ORDER_CREATED_TOTAL = Counter(
    "myapp_order_created_total",
    "订单创建总数",
    labelnames=["channel", "status"],
)

# 资源指标
DB_CONNECTION_POOL = Gauge(
    "myapp_db_connection_pool_used",
    "数据库连接池已用连接数",
)

# === FastAPI 中间件：自动记录每个请求的 RED 指标 ===
def setup_metrics(app: FastAPI):
    @app.middleware("http")
    async def metrics_middleware(request: Request, call_next):
        start_time = time.perf_counter()

        # 提取 endpoint 模板（去掉路径参数，/orders/123 → /orders/{id}）
        # 防止高基数 label 爆炸（每个订单 ID 一个 label → 内存爆炸）
        endpoint = request.url.path
        # 简单处理：把 /orders/123 变成 /orders/:id
        parts = endpoint.split("/")
        normalized = "/".join(
            p if not p.isdigit() else ":id" for p in parts
        )

        response = await call_next(request)

        duration = time.perf_counter() - start_time

        # 记录 RED 指标
        HTTP_REQUESTS_TOTAL.labels(
            method=request.method,
            endpoint=normalized,
            status=str(response.status_code),
        ).inc()

        HTTP_REQUEST_DURATION.labels(
            method=request.method,
            endpoint=normalized,
        ).observe(duration)

        return response

    # /metrics 端点：Prometheus 抓取入口
    @app.get("/metrics")
    def metrics():
        return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

    指标命名规范（Prometheus 最佳实践）：

    # 命名格式：<app>_<subsystem>_<name>_<unit>
# ✅ 正确命名
myapp_http_requests_total          # myapp 应用 + http 子系统 + requests 计数 + total 后缀
myapp_http_request_duration_seconds # myapp + http + 延迟 + seconds 单位
myapp_db_connection_pool_used      # myapp + db + 连接池 + used

# ❌ 错误命名
requests                            # 没有应用前缀，多服务冲突
http_requests                       # 缺少单位
myapp_latency                       # latency 没单位，seconds 还是 ms？

    高基数 label 陷阱（最容易犯的坑）：

    # ❌ 致命错误：把 user_id / order_id 当 label
HTTP_REQUESTS_TOTAL.labels(user_id=str(user.id))  # 10 万用户 → 10 万时间序列 → 内存爆炸

# ✅ 正确：只用低基数的维度当 label
HTTP_REQUESTS_TOTAL.labels(method="GET", endpoint="/orders", status="200")

    label 基数安全线：每个 label 的不同值 × 所有 label 的组合数 < 10 万。超过 10 万时间序列，Prometheus 内存会吃紧。详见 9.10.1。

        ],
        wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
        logger_factory=structlog.PrintLoggerFactory(),
        cache_logger_on_first_use=True,
    )

    9.5 OpenTelemetry 链路追踪¶

    9.5.1 分布式追踪原理（Trace / Span / 上下文传播）¶

    图 9-4：一个请求的分布式 Trace

    用户请求 POST /checkout
    │
    ├─ Span 1: API Gateway (12ms)          trace_id=abc123
    │   ├─ Span 2: Auth Service (3ms)       parent=Span 1
    │   ├─ Span 3: Order Service (8ms)      parent=Span 1
    │   │   ├─ Span 4: DB Query (5ms)       parent=Span 3  ← 这里慢
    │   │   └─ Span 5: Payment API (2ms)    parent=Span 3
    │   └─ Span 6: Response (1ms)           parent=Span 1
    │
    总耗时 12ms，其中 DB Query 5ms 占 42%

    核心概念：

    概念 含义 例子
    Trace 一个完整请求的链路 用户下单 → 支付 → 扣库存 的全链路
    Span 链路中的一个操作 一次 DB 查询、一次 HTTP 调用
    trace_id 整条链路的唯一 ID abc123（所有 Span 共享）
    span_id 单个操作的唯一 ID span-1, span-2, ...
    parent_span_id 父操作的 span_id Span 4 的 parent = Span 3
    上下文传播 trace_id 通过 HTTP Header / 消息队列传递 traceparent: 00-abc123-span3-01

    上下文传播机制（W3C Trace Context 标准头）：

    # HTTP 请求头里携带 trace_id，下游服务提取后继续生成子 Span
traceparent: 00-{trace_id}-{span_id}-{flags}
# 例：00-abc123def456-span3-01

        "service.name": service_name,
        "service.version": "1.0.0",

        )

    SQLAlchemyInstrumentor().instrument()         # 自动追踪 DB 查询

    采样策略 适用场景 采样率 优势
    AlwaysOn dev/test 环境 100% 全量追踪，排障方便
    ParentBased(AlwaysOn) 默认策略 跟随父 Span 如果入口采样了，子 Span 全采

    9.6 SLO/SLI 设计与错误预算¶

    9.6.1 SLI / SLO / SLA 概念与区别¶

    表 9-6：SLI / SLO / SLA 概念

    概念 含义 例子 谁定
    SLI（Service Level Indicator） 服务水平的度量指标 "成功请求数 / 总请求数" 工程团队
    SLO（Service Level Objective） 服务水平的目标值 "99.9% 的请求成功" 工程团队 + PM
    SLA（Service Level Agreement） 服务水平的合同承诺 "月可用性 < 99.5% 则赔偿 10%" 法务/商务

    三者关系：SLI 是温度计（测量），SLO 是目标值（99.9%），SLA 是合同条款（达不到赔钱）。

    关键区别：SLO 是内部目标（团队自我约束），SLA 是外部合同（违反有法律后果）。SLO 通常比 SLA 更严格——SLO 99.9%，SLA 99.5%，中间 0.4% 是缓冲带。

    9.6.2 SLO 设计实战（可用性 / 延迟 / 错误率）¶

    SLO 定义文件示例（可以存为 Git 仓库中的 YAML，版本化管理）：

    # slo/myapp-slo.yaml
service: myapp
window: 28d          # SLO 评估窗口 28 天（4 周）

slos:
  # === SLO 1：可用性（请求成功率） ===
  - name: availability
    description: "99.9% 的 HTTP 请求返回非 5xx"
    sli:
      # SLI = 1 - (5xx 请求数 / 总请求数)
      query: |
        1 - (
          sum(rate(myapp_http_requests_total{status=~"5.."}[5m]))
          /
          sum(rate(myapp_http_requests_total[5m]))
        )
    target: 0.999        # 99.9%
    alerting:
      - fast_burn: "1小时内消耗 2% 错误预算 → P0 告警"
      - slow_burn: "24小时内消耗 5% 错误预算 → P1 告警"

  # === SLO 2：延迟（p99 < 500ms） ===
  - name: latency_p99
    description: "99% 的请求延迟 < 500ms"
    sli:
      # SLI = p99 < 0.5s 的请求比例
      query: |
        sum(rate(myapp_http_request_duration_seconds_bucket{le="0.5"}[5m]))
        /
        sum(rate(myapp_http_request_duration_seconds_count[5m]))
    target: 0.99          # 99% 的请求 < 500ms
    alerting:
      - fast_burn: "1小时内消耗 2% 错误预算 → P1 告警"

  # === SLO 3：关键业务（订单创建成功率） ===
  - name: order_success_rate
    description: "99.5% 的订单创建成功"
    sli:
      query: |
        sum(rate(myapp_order_created_total{status="success"}[5m]))
        /
        sum(rate(myapp_order_created_total[5m]))
    target: 0.995
    alerting:
      - fast_burn: "1小时内消耗 2% 错误预算 → P0 告警"

    SLO 分级建议（小团队起步只配前两个）：

    SLO 级别 目标值 适用场景 起步推荐
    用户面 API 99.9% 可用 + p99 < 500ms 对外暴露的 API ⭐⭐⭐⭐⭐
    关键业务 99.5% 成功率 下单 / 支付 / 登录 ⭐⭐⭐⭐⭐
    内部 API 99% 可用 管理后台 / 内部工具 ⭐⭐⭐
    Batch Job 95% 成功率 定时报表 / 数据同步 ⭐⭐

    9.6.3 错误预算与发布策略联动（烧完预算就冻结发布）¶

    错误预算计算：

    SLO = 99.9% 可用性
评估窗口 = 28 天（40320 分钟）

错误预算 = (1 - SLO) × 窗口时间
         = (1 - 0.999) × 40320
         = 0.001 × 40320
         = 40.32 分钟

→ 28 天内允许 40.32 分钟的不可用时间
→ 如果半个月就烧完了 40 分钟，剩下半个月必须 0 故障，否则 SLO 违约

    错误预算与发布策略联动：

    错误预算剩余 发布策略 团队行动
    > 50% 正常发布 正常节奏，可以激进发布
    25% ~ 50% 谨慎发布 只发布已充分测试的版本，减少发布频率
    10% ~ 25% 限制发布 只允许紧急修复，停止新功能发布
    < 10% 冻结发布 全面发布冻结，专注稳定性改进

    错误预算的核心价值：它给工程团队提供了数据化的"说不"的依据。当 PM 要求"这周必须上线"但错误预算已经烧了 90% 时，SRE 可以用数据说"上线会有 SLO 违约风险"，而不是凭感觉争论。这是 SRE 文化落地的关键机制。

    9.7 告警分级与 OnCall 机制¶

    9.7.1 告警分级（P0~P3）与通知渠道¶

    表 9-7：告警分级与响应要求

    级别 含义 响应时间 通知渠道 典型场景
    P0 生产环境完全不可用 < 5 分钟 电话 + 短信 + 飞书 全站 5xx、数据库宕机、支付全挂
    P1 核心功能受损 < 15 分钟 短信 + 飞书 错误率 > 5%、p99 > 5s、SLO 快速消耗
    P2 非核心功能异常 < 1 小时 飞书 某个非核心 API 5xx、磁盘 > 80%
    P3 预警趋势 工作日处理 邮件 / 飞书 CPU > 60%（趋势告警）、日志量异常增长

    告警分级铁律：
    1. P0 必须打电话：飞书/钉钉消息容易被忽略，P0 必须电话叫醒
    2. P0/P1 必须有人值班响应：不能"发个消息就完了"
    3. P3 不是告警：P3 是"趋势提醒"，不应该触发 OnCall，发邮件即可
    4. 告警必须有 runbook：每条告警附带排查步骤 + 修复命令，不要让人"收到告警后不知道该怎么办"

    9.7.2 Alertmanager 规则配置 + 告警抑制与静默¶

    Prometheus 告警规则（prometheus rules）：

    # prometheus/rules.yml
groups:
  - name: myapp_alerts
    rules:
      # === P0：全站 5xx > 10% ===
      - alert: HighErrorRateP0
        expr: |
          sum(rate(myapp_http_requests_total{status=~"5.."}[5m]))
          /
          sum(rate(myapp_http_requests_total[5m]))
          > 0.10
        for: 2m              # 持续 2 分钟才告警（避免瞬时抖动）
        labels:
          severity: P0
          service: myapp
        annotations:
          summary: "P0: myapp 错误率 > 10%"
          description: "当前错误率 {{ $value | humanizePercentage }}，超过 10% 阈值"
          runbook: "https://wiki.example.com/runbooks/high-error-rate"

      # === P1：p99 延迟 > 5s ===
      - alert: HighLatencyP1
        expr: |
          histogram_quantile(0.99, rate(myapp_http_request_duration_seconds_bucket[5m]))
          > 5
        for: 5m
        labels:
          severity: P1
          service: myapp
        annotations:
          summary: "P1: myapp p99 延迟 > 5s"
          runbook: "https://wiki.example.com/runbooks/high-latency"

      # === P1：SLO 错误预算快速消耗 ===
      - alert: SLOFastBurn
        expr: |
          (
            sum(rate(myapp_http_requests_total{status=~"5.."}[1h]))
            /
            sum(rate(myapp_http_requests_total[1h]))
          ) > 0.01
        # 1 小时内错误率 > 1% = 消耗 > 2% 的 28 天错误预算
        for: 10m
        labels:
          severity: P1
          service: myapp
        annotations:
          summary: "P1: SLO 错误预算快速消耗"

    9.7.3 OnCall 轮值机制与告警疲劳治理¶

    表 9-8：OnCall 轮值制度设计

    角色 轮值周期 职责 补偿
    主 OnCall 1 周轮换 P0/P1 第一响应人，5 分钟内响应 OnCall 津贴 + 调休
    备 OnCall 1 周轮换 主 OnCall 未响应 10 分钟后升级 OnCall 津贴（半额）
    技术专家 不轮换 复杂问题升级通道（数据库/网络专家） 按需

    告警疲劳治理（防止 OnCall 的人被淹没在告警里）：

    治理手段 做法 效果
    消除噪音告警 每月 review 告警统计，误报率 > 30% 的告警改阈值或删 减少 50% 无效告警
    告警聚合 Alertmanager group_by 聚合同类告警，不逐条发 避免告警风暴
    分级过滤 P3 不触发 OnCall，只发邮件/飞书 OnCall 只接 P0/P1
    静默窗口 维护窗口用 Alertmanager Silence 临时静默 避免维护期间的已知告警

    与 07 章的分工：07 章覆盖了"部署阶段"的回滚机制（K8s rollingUpdate、蓝绿切换、金丝雀 abort）；09 章聚焦"部署之后"通过监控发现异常后的回滚决策和执行，以及数据库回滚的特殊处理。

    9.8.1 K8s 回滚（kubectl rollout undo + Argo CD）¶

    K8s Deployment 回滚（07 章已覆盖命令，这里补充决策流程）：

    # 1. 查看发布历史
kubectl rollout history deployment/myapp -n production

# 2. 回滚到上一版本
kubectl rollout undo deployment/myapp -n production

# 3. 回滚到指定版本
kubectl rollout undo deployment/myapp --to-revision=3 -n production

# 4. 监控回滚进度
kubectl rollout status deployment/myapp -n production

    Argo CD 回滚（GitOps 模式）：

    # 方法 1：UI 操作（紧急）
# Argo CD Web UI → 选 Application → History and Rollback → 选版本 → Rollback

# 方法 2：Git 回滚（推荐，保持 Git 和集群状态一致）
git revert <commit-that-changed-image-tag>
git push origin main
# Argo CD 自动检测到 Git 变更 → 自动同步回旧版本

    GitOps 模式下的回滚铁律：紧急情况用 Argo CD UI 回滚（快），但事后必须在 Git 里做对应的 revert commit，否则下次 Argo CD 同步时会再次推到新版本（Git 里的"正确状态"还是新的有问题的版本）。

    Docker Compose 回滚（对应 7.6.4 的部署方式）：

# 只需改 Nginx upstream 指向蓝，reload Nginx，秒级回滚
nginx -s reload

    Docker Swarm 回滚（对应 7.6.4 的 Swarm 部署）：

    9.8.3 数据库回滚（前向兼容原则 + Expand-Contract 反向操作）¶

    数据库回滚是最复杂的回滚场景。参见 07 章 7.7 Expand-Contract 和 7.9.1 事故复盘。

    数据库回滚铁律：数据库变更必须前向兼容（Forward Compatible），否则回滚不了。

    表 9-9：数据库变更的回滚能力

    变更类型 能回滚吗 回滚方式 风险
    加列（nullable） ✅ ALTER TABLE DROP COLUMN 低（如果新代码没写数据）
    加列（NOT NULL + default） ✅ 同上 低
    删列 ❌ 不可回滚（数据已丢） 极高 → 必须用 Expand-Contract
    改列类型 ❌ 不可回滚（数据已转换） 极高 → 必须用 Expand-Contract
    加索引 ✅ DROP INDEX 低
    删索引 ✅ 重建索引 低（重建慢）
    加表 ✅ DROP TABLE 低
    删表 ❌ 不可回滚 极高 → 不可逆操作

    Expand-Contract 的反向操作（如果需要回滚到 Expand 阶段）：

    Step 3 Contract（删旧列）已经做了 → 无法回滚（数据丢了）
Step 2 Migrate（双写+回填）做了 → 可以回滚到只写旧列
Step 1 Expand（加新列）做了 → 可以回滚到没有新列

结论：Expand-Contract 的 Step 3 必须和 Step 1 相隔 1~2 个版本周期（→ 7.9.1 事故 1）

    9.8.4 回滚决策树（什么时候回滚 vs 什么时候热修）¶

    图 9-5：回滚决策流程

    监控告警触发
    │
    ├─ 是新版本部署后 < 30 分钟内出现的吗？
    │   │
    │   ├─ 是 → 回滚（大概率是新版本引入的问题）
    │   │   │
    │   │   ├─ 数据库变更了吗？
    │   │   │   ├─ 没有 → 直接回滚应用镜像 ✅
    │   │   │   └─ 有 → 检查 DB 变更能否回滚（→ 表 9-9）
    │   │   │       ├─ 能 → 回滚应用 + 回滚 DB
    │   │   │       └─ 不能 → 前向修复（发新版本修复，不回滚）
    │   │   │
    │   │   └─ 回滚后验证 → 监控恢复正常？
    │   │       ├─ 是 → 事故复盘
    │   │       └─ 否 → 升级 P0，叫更多人来
    │   │
    │   └─ 否（不是新版本引入）→ 热修（回滚没用，问题在别处）
    │       │
    │       ├─ 是基础设施问题（DB/CPU/网络）→ 修基础设施
    │       ├─ 是流量突增 → 限流 / 扩容
    │       └─ 是配置变更 → 回滚配置（不需要回滚应用）
    │
    └─ 决策时间：从告警触发到决定回滚或热修，应 < 5 分钟

    回滚决策的关键判断点：
    1. 时间关联性：问题是否在部署后 30 分钟内出现？是 → 大概率是新版本
    2. 数据库变更：如果有 DB 变更，能不能回滚？不能 → 只能前向修复
    3. 爆炸半径：回滚会让所有人恢复（整回滚）还是只部分恢复（蓝绿切回）
    4. 决策时间 < 5 分钟：不要开 1 小时的会讨论要不要回滚，5 分钟决定不了就先回滚再说

  image: alpine:latest

    # 3. 冒烟测试（关键 API）

    9.10 生产常见问题与事故复盘¶

    9.10.1 Prometheus 高基数 label 导致内存爆炸（最常见的事故）¶

    事故：开发者把 user_id 当 Prometheus label，10 万活跃用户 → 10 万时间序列。Prometheus 内存从 2G 涨到 16G → OOM Kill → 监控全挂。

    根因：Prometheus 的时间序列是 {label1=value1, label2=value2, ...} 的组合，每个唯一组合创建一条独立的时间序列。高基数 label（user_id / order_id / session_id）会让序列数爆炸。

    修复：
    1. label 基数铁律：只能用低基数维度当 label（method / endpoint / status / service），绝不用 user_id / order_id / trace_id 当 label
    2. 需要按 user_id 分析 → 用日志/链路追踪，不用 Prometheus
    3. Prometheus 配置 --storage.tsdb.max-block-duration=2h 限制内存使用
    4. 监控 Prometheus 自身的 prometheus_tsdb_head_series 指标，序列数 > 100 万告警

    9.10.2 告警风暴：数据库慢查询导致 200+ 条告警同时触发¶

    事故：数据库出现慢查询 → 所有依赖 DB 的服务都报错 → 每个服务触发 5xx 告警 + 延迟告警 + SLO 告警 → 2 分钟内收到 200+ 条飞书消息 → OnCall 的人手机卡死、无法判断根因。

    根因：没有配告警抑制（Inhibition），N 个服务的同类告警同时触发，没有识别到"根因是 DB 慢"。

    修复（Alertmanager inhibit_rules）：

    # DB 慢 → 抑制所有应用的错误率/延迟告警
inhibit_rules:
  - source_matchers: ['alertname="DBSlowQueries"']
    target_matchers: ['alertname=~"HighErrorRate|HighLatency"']
    equal: ['env']    # 同环境下的告警抑制

    + 每条告警的 runbook 里写明"收到告警先看是不是 DB 慢导致的级联故障"。

    9.10.3 Loki 查询把存储打满（大范围查询无限制）¶

    事故：有人在 Grafana 里查 Loki 最近 7 天的全量日志（{service="myapp"} 不加过滤），Loki 扫描 500GB 日志原文 → 磁盘 IO 打满 → Loki 超时 + 其他查询全部排队。

    根因：Loki 没有对查询范围做限制，一个大查询可以消耗所有资源。

    修复：
    1. Loki 配置查询限制（limits_config）：

    limits_config:
  max_query_series: 500        # 单次查询最多 500 个序列
  max_query_length: 721h       # 最大查询范围 30 天
  max_query_parallelism: 16    # 并行查询数限制
  query_timeout: 5m            # 查询超时 5 分钟
  retention_period: 30d        # 日志保留 30 天，超期自动删

    2. 日常查询加 label 过滤（{service="myapp", level="error"} 而不是 {service="myapp"}）
    3. 大范围分析用 Loki 的 rate() 指标查询，不用日志原文查询

    9.10.4 回滚时忘了数据库已经迁移（回滚变二次事故）¶

    事故：v1.2.0 部署后发现 bug，执行回滚到 v1.1.9。但 v1.2.0 的迁移脚本已经加了一列 phone（nullable），v1.1.9 的代码不认识 phone 列 → ORM 映射失败 → 回滚后服务起不来。

    修复：
    1. 回滚前必须检查 DB 迁移状态：回滚检查清单加一条"确认 DB 变更是否前向兼容"
    2. DB 变更必须前向兼容（→ 表 9-9）：新加的列必须是 nullable 或有 default，旧代码不认识新列也不报错
    3. 不可逆 DB 变更不能和代码同版本发布：删列 / 改列类型必须用 Expand-Contract，跨 2 个以上版本周期（→ 7.9.1）

    9.11.2 现阶段最佳实践速记（2026）¶

    • 三支柱起步：Prometheus（指标）+ Loki（日志）+ Grafana（可视化），小团队一个 docker compose 跑起来
    • RED + USE：每个服务配 RED 三指标（QPS + 错误率 + p99 延迟），每个节点配 USE 三指标（CPU + 内存 + 磁盘），6 个指标覆盖 80% 需求
    • 结构化日志：Python 用 structlog 输出 JSON，Loki 按字段查询，不要 print()
    • OTel 自动埋点：FastAPIInstrumentor + SQLAlchemyInstrumentor，零代码入侵追踪 HTTP/DB/Redis
    • SLO 起步：只配 2 个 SLO（可用性 99.9% + 延迟 p99 < 500ms），小团队不要一上来配 10 个
    • 告警分级：P0 电话、P1 短信+飞书、P2 飞书、P3 邮件；每条告警必须有 runbook
    • 告警抑制：基础设施故障抑制应用告警，避免告警风暴
    • 回滚决策 < 5 分钟：部署后 30 分钟内出问题先回滚；DB 不可逆变更只能前向修复
    • Grafana-as-Code：仪表盘 JSON 存 Git 仓库，CI 自动同步，版本化管理
    • P1.3 落地：dev 不监控、test 起步接 Prometheus、stage 完整演练、prod 全量 + OnCall
