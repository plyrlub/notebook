## 一、流水线自身

### #01 GitLab Runner 雪崩：共享 Runner 大并发拖垮主库 — P0

**场景描述**
某中型团队 200+ 仓库共用一套 8 节点共享 Runner。某日批量推送触发 600+ 并发 pipeline，Runner 纷纷回源 GitLab 拉代码、上传 artifacts，导致 GitLab 主库 PostgreSQL 连接池打满，Web 页面 502，所有项目 CI 同时瘫痪。

**根因分析**
- Runner 无并发上限（`concurrent = 10` × 8 节点 = 80，但每个 job 又触发多次 git clone/fetch）。
- artifacts 上传走 Sidekiq，堆积后反压到 PostgreSQL。
- 没有 `request_concurrency` 与队列优先级，长任务挤占短任务。

**修复方案**
1. 限制 Runner 并发与单 job 资源：

```toml
# /etc/gitlab-runner/config.toml
concurrent = 4
check_interval = 0
limit = 4
[[runners]]
  request_concurrency = 2
  [runners.cache]
    MaxUploadedArchiveSize = 5000000  # 5MB，超大 artifacts 走对象存储
```

2. artifacts 改走对象存储（S3/MinIO），不经过 Sidekiq：

```yaml
# gitlab.rb
gitlab_rails['artifacts_enabled'] = true
gitlab_rails['artifacts_object_store_enabled'] = true
gitlab_rails['artifacts_object_store_remote_directory'] = "gitlab-artifacts"
gitlab_rails['artifacts_object_store_connection'] = {
  'provider'             => 'AWS',
  'region'               => 'us-east-1',
  'aws_access_key_id'    => 'AKIAXXX',
  'aws_secret_access_key' => 'SECRET'
}
```

3. 用 Lua 脚本在 Nginx 层对 `git clone` 限速（OpenResty 场景）：

```lua
-- /usr/local/openresty/nginx/conf/gitlab_ratelimit.lua
local limit_req = require "resty.limit.req"
local lim, err = limit_req.new("gitlab_clone", 30, 60)  -- 30 r/s, burst 60
if not lim then ngx.log(ngx.ERR, err); return end
local delay, err = lim:enter(ngx.var.remote_addr)
if not delay then
    if err == "rejected" then
        ngx.exit(429)
    end
    return
end
```

**预防措施**
- 监控指标：`gitlab_runner_jobs`、`sidekiq_queue_length`、`postgres_connections_active`。
- CI 检查项：Runner `concurrent` ≤ CPU 核数的 1.5 倍；artifacts 单文件 ≤ 50MB。
- 引入分租户 Runner Pool（生产/测试/实验隔离）。

**来源**
- [GitLab Runner timeout 排查](https://blog.51cto.com/u_12790562/5848202)
- [GitLab CI Pipelines 架构](https://cloud.tencent.com/developer/article/1774897)

### #02 CI 缓存毒化：被污染的 pip 缓存让产物带后门 — P0

**场景描述**
某团队用 GitLab CI 的共享 cache 缓存 `~/.cache/pip`。某次一个被入侵的依赖（typosquatting 包 `requets`）混入缓存，后续所有构建都从缓存命中该恶意包，导致一周内 12 个服务镜像全部带后门。缓存 key 仅按 branch 分，未按 lockfile 哈希分。

**根因分析**
- cache key 过粗（`key: ${CI_COMMIT_REF_SLUG}`），分支内任意提交共享同一份缓存。
- 缓存可被任意 job 写入，无签名校验。
- pip 默认信任缓存目录，不再校验哈希。

**修复方案**
1. cache key 按 lockfile 内容哈希：

```yaml
# .gitlab-ci.yml
build:
  cache:
    key:
      files:
        - requirements.txt
        - poetry.lock
      prefix: pip-${CI_COMMIT_REF_SLUG}
    paths:
      - .cache/pip
    policy: pull-push  # 仅构建 job push，其余 pull
  variables:
    PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
  script:
    - pip install --require-hashes -r requirements.txt
```

2. 开启 pip 哈希校验，缓存被改也无法命中：

```bash
# requirements.txt 末尾固化哈希
requests==2.32.3 \
    --hash=sha256:55465c2f6f2c2c8c5c2c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1
pip install --require-hashes -r requirements.txt
```

3. 定期清理缓存（GitLab API）：

```python
# clear_cache.py
import requests, os
GITLAB = "https://gitlab.example.com/api/v4"
TOKEN = os.environ["GITLAB_TOKEN"]
pid = 123
for branch in ("main", "develop"):
    requests.delete(
        f"{GITLAB}/projects/{pid}/cache/branches/{branch}",
        headers={"PRIVATE-TOKEN": TOKEN},
    )
print("cache cleared")
```

**预防措施**
- 监控指标：缓存命中率突变（骤降可能是清理，骤升可能是毒化复用）。
- CI 检查项：`--require-hashes` 必须开启；私有 PyPI 走 HTTPS + token。
- 高敏项目用 `policy: pull` 只读缓存，写入集中到一个 `update-cache` job。

**来源**
- [CI/CD 供应链攻击挖掘实战](https://blog.csdn.net/2402_86373248/article/details/158570172)
- [恶意 npm 包潜入 GitHub Actions](https://m.sohu.com/a/954170706_122362510/)

### #03 密钥泄漏进构建日志：`$CI_JOB_TOKEN` 被打印 — P0

**场景描述**
某 Java 项目在调试阶段把 `mvn deploy` 输出重定向到日志，但 `-X`（debug）模式会把 `Authorization: Basic base64(user:pass)` 明文打到 stdout，日志被采集到 Loki 后任何内网员工可检索。事后审计发现 3 个仓库日志含明文 Nexus 凭据。

**根因分析**
- debug 日志未脱敏，凭据随 artifacts/日志流转。
- CI 日志默认对仓库所有 Developer 可见，权限过宽。
- 没有用 masked variable，而是普通 `variables`。

**修复方案**
1. GitLab 把变量标记为 masked（仅支持 base64 字符集的值）：

```yaml
variables:
  NEXUS_PASSWORD:
    value: ""
    description: "由 CI/CD Settings 注入，标记 Masked"
```

2. Java 项目用 `settings.xml` 读环境变量，不在命令行传参：

```xml
<!-- ~/.m2/settings.xml -->
<settings>
  <servers>
    <server>
      <id>nexus-releases</id>
      <username>${env.NEXUS_USER}</username>
      <password>${env.NEXUS_PASSWORD}</password>
    </server>
  </servers>
</settings>
```

```bash
mvn -s settings.xml deploy -DskipTests  # 不加 -X
```

3. 加日志脱敏前置脚本（Python 检查）：

```python
# check_log_secrets.py
import re, sys
PATTERNS = [
    r"Authorization:\s*Basic\s+[A-Za-z0-9+/=]+",
    r"AKIA[0-9A-Z]{16}",            # AWS access key
    r"-----BEGIN (RSA |EC )?PRIVATE KEY-----",
]
leak = False
for line in sys.stdin:
    for p in PATTERNS:
        if re.search(p, line):
            print(f"[LEAK] {line.strip()[:60]}...")
            leak = True
sys.exit(1 if leak else 0)
```

```yaml
after_script:
  - cat build.log | python check_log_secrets.py || exit 1
```

**预防措施**
- 监控指标：日志中 secret 命中数（接 Gitleaks / TruffleHog 扫历史日志）。
- CI 检查项：所有 `*_TOKEN`、`*_PASSWORD` 变量必须 masked；debug 日志默认关闭。
- 定期 rotate Nexus/Harbor/GitLab token，缩短泄漏窗口。

**来源**
- [Aqua Secrets Management](https://www.aquasec.com/cloud-native-academy/supply-chain-security/secrets-management/)
- [GitLab 身份认证绕过 CVE-2024-5655](https://www.secrss.com/articles/67563)

### #04 concurrency 失控：100 个并发任务同时部署生产 — P1

**场景描述**
某团队 monorepo 有 50 个微服务，每次 push 触发 50 条 pipeline，每条 pipeline 都有 `deploy:prod` job。一次合并大 PR 后 50 个 deploy 同时跑，Helm 并发 install 把目标集群 apiserver 打到 90% CPU，多个 release 半成品状态，回滚困难。

**根因分析**
- 没有 `resource_group` 或 `concurrency` 限制部署并发。
- monorepo 未做路径过滤，无关服务也部署。
- 集群无 PDB / LimitRange，apiserver 无优先级保护。

**修复方案**
1. GitLab 用 `resource_group` 串行化生产部署：

```yaml
deploy:prod:
  stage: deploy
  resource_group: production-deploy
  script:
    - helm upgrade --install api ./chart --wait --timeout 5m
  only:
    refs: [main]
    changes:
      - "services/api/**/*"
```

2. GitHub Actions 用 `concurrency`：

```yaml
deploy:
  concurrency:
    group: prod-deploy-${{ matrix.service }}
    cancel-in-progress: false
  strategy:
    matrix:
      service: [api, web, worker]
  steps:
    - run: kubectl rollout status deploy/${{ matrix.service }}
```

3. monorepo 路径过滤，避免无关服务部署（Python 脚本生成矩阵）：

```python
# gen_matrix.py
import os, json, subprocess
changed = subprocess.check_output(
    ["git", "diff", "--name-only", os.environ["PREV_SHA"], "HEAD"], text=True
).split()
services = sorted({l.split("/")[1] for l in changed if l.startswith("services/")})
print(json.dumps({"service": services}))
```

**预防措施**
- 监控指标：`apiserver_request_latencies_p99`、部署队列堆积深度。
- CI 检查项：生产 deploy job 必须 `resource_group`；monorepo 必须 changes 过滤。
- 集群侧加 `PriorityClass`，部署 controller 用高优先级避免被业务 pod 挤掉。

**来源**
- [AI 时代的 CI/CD 工具选型](http://m.toutiao.com/group/7668099451990327808/)
- [GitLab CI Pipelines 配置](https://cloud.tencent.com/developer/article/1774897)

### #05 `pull_request_target` 误用：恶意 PR 提权窃取 Token — P0

**场景描述**
某开源项目 GitHub Actions workflow 用了 `on: pull_request_target`，并在 job 里直接 `actions/checkout@v4` 拉取 PR 分支代码并执行 `npm test`。攻击者提交一个 PR，在测试脚本里 `echo $GITHUB_TOKEN` 并外传，盗取了仓库写权限 token，篡改 release 产物。

**根因分析**
- `pull_request_target` 用的是 base 分支的 secrets，权限等同写仓库。
- checkout PR 代码后执行任意命令 = 把 secrets 送给不可信代码。
- 对 fork PR 没有隔离沙箱。

**修复方案**
1. 永远不要在 `pull_request_target` 里 checkout PR 代码并执行；改为两阶段：

```yaml
# 阶段 1：低权限跑 PR 代码
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -e . && pytest
```

```yaml
# 阶段 2：PR 合并后才用 secrets
on:
  push:
    branches: [main]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker push ...
```

2. 若必须跑 PR 代码 + label 门禁，用 pull_request_target 仅做 label，再触发另一个 workflow：

```yaml
on: pull_request_target
jobs:
  label:
    if: github.event.action == 'opened'
    steps:
      - uses: actions/labeler@v5
        with:
          repo-token: ${{ secrets.GITHUB_TOKEN }}
```

3. 用 Java 写一个 token 最小化审计器（扫描 workflow 文件）：

```java
// WorkflowAudit.java
import java.nio.file.*;
import java.util.*;
public class WorkflowAudit {
  public static void main(String[] args) throws Exception {
    for (var f : Files.find(Paths.get(".github"), 10,
        (p,a) -> p.toString().endsWith(".yml")).toList()) {
      var lines = Files.readAllLines(f);
      boolean hasTarget = lines.stream().anyMatch(l -> l.contains("pull_request_target"));
      boolean hasCheckout = lines.stream().anyMatch(l -> l.contains("checkout") && l.contains("${{"));
      if (hasTarget && hasCheckout) {
        System.err.println("[DANGER] " + f + " mixes pull_request_target with PR checkout");
      }
    }
  }
}
```

**预防措施**
- 监控指标：workflow `secrets:` 引用次数、`pull_request_target` + checkout 组合告警。
- CI 检查项：扫描所有 workflow，禁止 `pull_request_target` 同 job 内 checkout PR。
- 对 fork PR 强制 `require approval`，token 最小化（只读）。

**来源**
- [CI/CD 供应链攻击挖掘实战](https://blog.csdn.net/2402_86373248/article/details/158570172)
- [2024 年顶级云原生威胁](https://www.51cto.com/article/811865.html)

### #06 Dockerfile 用 `latest` tag 导致构建不可复现 — P1

**场景描述**
某 Python 服务 `FROM python:latest`，某天上游推了 `python:3.13`，新构建里 `pip install` 因 `3.13` 移除的 `distutils` 失败，所有 PR 突然变红。开发者本地 `python:3.11` 却完全正常，排查 2 小时。

**根因分析**
- base image 用浮动 tag，上游变更直接破坏复现性。
- 没有 pin 到 digest。
- 没有锁 base image 版本的 CI 检查。

**修复方案**
1. 固定版本 + digest：

```dockerfile
# Dockerfile
FROM python:3.11.9-slim@sha256:abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-m", "app.main"]
```

2. 用 Renovate / Dependabot 自动升级 base image，PR 触发测试：

```yaml
# .github/renovate.json
{
  "extends": ["config:recommended"],
  "dockerfile": { "pinDigests": true },
  "packageRules": [
    { "matchDatasources": ["docker"], "schedule": ["before 6am on Monday"] }
  ]
}
```

3. CI 加 digest 一致性检查（Bash）：

**修复方案**

```bash
# 扫应用依赖（更严），扫 OS 包（看是否有 fix）
trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed myapp:ci
# 同时扫一次不 ignore，结果存档供审计
trivy image --scanners vuln --format json -o trivy-full.json myapp:ci
```

2. 用 `.trivyignore` 收敛已知误报（带原因 + 过期时间）：


```python
# trivy_policy.py
import json, sys
WHITELIST_PKGS = {"curl", "wget"}  # runtime 不调用
report = json.load(open(sys.argv[1]))
block = []
for r in report.get("Results", []):

        if v["PkgName"] in WHITELIST_PKGS:
            continue
        if v["Severity"] in ("HIGH", "CRITICAL") and v.get("FixedVersion"):
            block.append(f"{v['PkgName']} {v['VulnerabilityID']} -> fix to {v['FixedVersion']}")
if block:
    print("\n".join(block)); sys.exit(1)
print("policy passed")
```

```yaml
scan:

```

**预防措施**
- 监控指标：Trivy 漏报数（对比 NVD/OSV）、误报工单数。
- CI 检查项：`--ignore-unfixed` 结果与 full 结果都归档；ignore 列表有 owner + 过期时间。
- 定期用 `trivy image --db-update` 更新漏洞库。

```bash
#!/usr/bin/env bash

EXPECTED_DIGEST=$(curl -s "https://harbor-bj.example.com/api/v2.0/projects/prod/repositories/artifacts?tags=v2.3.2" \

    -H "Authorization: Bearer $HARBOR_TOKEN" | jq -r '.[0].digest // empty' || echo "")

echo "replication timeout"; exit 1
```


### #11 K8s 滚动更新卡死：readiness probe 配错触发 maxSurge 上限 — P0

**场景描述**
某 Java 服务滚动更新，新 Pod 一直 `0/1 Ready`，由于 `maxSurge=1 maxUnavailable=0`，deployment 卡在"新 Pod 不 Ready、旧 Pod 不能删"的状态，`kubectl rollout status` 等 10 分钟超时，生产仍是旧版本但用户已看到 502。

**根因分析**
- readiness probe 路径配错（`/health` 实际是 `/actuator/health`），新 Pod 永远不 Ready。
- `maxUnavailable=0` 把滚动锁死，没有腾挪空间。
- `progressDeadlineSeconds` 默认 600s，长时间不报错。

**修复方案**
1. 正确配置探针 + 滚动参数：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  minReadySeconds: 5
  progressDeadlineSeconds: 300
  template:
    spec:
      containers:
        - name: api
          image: api:v2.3.2
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 20
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 10
```

2. Java 用 Spring Boot Actuator 暴露 readiness group：

```java
// HealthConfig.java
import org.springframework.boot.actuate.health.*;
import org.springframework.context.annotation.*;

@Configuration(proxyBeanMethods = false)
public class HealthConfig {
  @Bean
  public HealthIndicator readinessIndicator(DbChecker db) {
    return () -> db.ping() ? Health.up().build() : Health.down().build();
  }
}
```

3. CI 部署脚本加超时 + 自动回滚：

```bash
#!/usr/bin/env bash
set -euo pipefail
kubectl set image deploy/api api=api:v2.3.2
if ! kubectl rollout status deploy/api --timeout=300s; then
  echo "rollout failed, rolling back"
  kubectl rollout undo deploy/api
  exit 1
fi
```

**预防措施**
- 监控指标：`kube_deployment_status_replicas_unavailable`、rollout 耗时 P95。
- CI 检查项：readinessProbe 必须配置；`progressDeadlineSeconds` ≤ 300。
- 生产部署前在 staging 用真实流量验证 probe。

### #12 Argo Rollouts 金丝雀误判：指标窗口太短自动全量 — P0

**场景描述**
某团队用 Argo Rollouts 做 canary，分析指标用 `successRate`，`count: 5`（窗口仅 5 个请求）。某次正常发布，前 5 个请求恰好有 1 个客户端超时，成功率 80% < 阈值 95%，Rollouts 自动 rollback。但 rollback 也没成功（镜像已被替换），最终 30% 流量卡在新版本，用户持续报错。

**根因分析**
- 分析窗口太小，单次抖动就被判失败。
- canary 没配 `maxSurge`/`maxUnavailable`，rollback 与 rollout 互相干扰。
- 指标查询没考虑 latency，只看成功率。

**修复方案**
1. 用更长窗口 + 多指标 AnalysisTemplate：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: success-rate
      interval: 30s
      count: 10              # 5 分钟窗口
      successCondition: result[0] >= 0.95
      failureLimit: 3
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",code!~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[2m]))
    - name: p99-latency
      interval: 30s
      count: 10
      successCondition: result[0] <= 500
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{service="{{args.service-name}}"}[2m])) by (le))
```

2. Rollout 配置稳健的 canary 步进：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      maxSurge: "20%"
      maxUnavailable: 0
      steps:
        - setWeight: 10
        - pause: { duration: 2m }
        - analysis:
            templates:
              - templateName: success-rate
                args:
                  - name: service-name
                    value: api
        - setWeight: 30
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: success-rate
        - setWeight: 100
```

**预防措施**
- 监控指标：Argo Rollouts `rollout_phase`、analysis 失败次数。
- CI 检查项：AnalysisTemplate 窗口 ≥ 2m，`failureLimit` ≥ 2；canary 步进 ≥ 3 步。
- rollback 流程预先演练，避免 rollback 自身失败。

### #13 蓝绿切换流量残留：Endpoint controller 慢导致双写 — P1

```java
// GracefulShutdown.java
import org.springframework.boot.web.context.*;
import org.springframework.context.*;
import org.springframework.stereotype.*;
import java.util.concurrent.atomic.AtomicBoolean;

@Component
public class GracefulShutdown implements ApplicationListener<WebServerGracefulShutdownEvent> {
  public static final AtomicBoolean ready = new AtomicBoolean(true);
  @Override
  public void onApplicationEvent(WebServerGracefulShutdownEvent event) {
    ready.set(false);
  }
}
// readiness handler 引用 ready，false 时 K8s 摘流量
```

```yaml
spec:
```

### #14 Feature Flag 误开：默认值未配置导致灰度变全量 — P1

**场景描述**
某团队用 LaunchDarkly 做 feature flag。某次新代码 `flag = ld.variation("new_checkout", user, None)`，但 flag 在控制台被误删，SDK 返回 `None`，代码逻辑 `if flag` 走 false 分支。但另一处代码 `if flag is None: flag = True`（兜底默认开），导致全量用户命中未测的新 checkout，下单失败率飙升。

**根因分析**
- flag 默认值不统一，有的 `True` 有的 `False` 有的 `None`。
- flag 被删除后无告警，SDK 静默兜底。
- 没有"flag 必须存在"的 CI 检查。

**修复方案**
1. 统一默认值策略（Python 示例，用 Unleash）：

```python
# flags.py
from UnleashClient import UnleashClient
import os

client = UnleashClient(url=os.environ["UNLEASH_URL"],
                       app_name="checkout",
                       custom_headers={"Authorization": os.environ["UNLEASH_TOKEN"]})
client.initialize_client()

# 所有调用走包装器，强制 default 显式
def flag(name: str, default: bool) -> bool:
    if not client.is_initialized():
        return default
    return client.is_enabled(name, default_value=default)

# 用法
if flag("new_checkout", default=False):
    new_flow()
else:
    old_flow()
```

2. CI 启动时校验所有引用的 flag 都存在：

```python
# check_flags.py
import re, os, subprocess, sys
code = subprocess.check_output(
    ["grep", "-rn", "-E", r"flag\(['\"]([^'\"]+)", "--include=*.py", "."], text=True
)
used = set(re.findall(r"flag\(['\"]([^'\"]+)", code))
import requests
flags = {f["name"] for f in requests.get(
    os.environ["UNLEASH_URL"] + "/api/client/features",
    headers={"Authorization": os.environ["UNLEASH_TOKEN"]}).json()["features"]}
missing = used - flags
if missing:
    print(f"missing flags: {missing}"); sys.exit(1)
```

3. flag 变更走 PR（配置即代码）：

```yaml
# flags/new_checkout.yml
name: new_checkout
type: release
enabled: false
strategies:
  - name: gradualRolloutUserId
    parameters: { percentage: 10 }
```

**预防措施**

### #15 DB 迁移 Expand-Contract 失败：删列后回滚崩溃 — P0

**场景描述**

- Contract 步骤（删列）与代码回滚不兼容，删列是不可逆操作。

- 部署与迁移没有解耦，迁移和代码同一次 deploy。

**修复方案**
1. 严格三阶段，每阶段独立 deploy，间隔 ≥ 1 个 release 周期：

```sql
-- V1: expand（加列，可立刻部署）
ALTER TABLE users ADD COLUMN email_v2 VARCHAR(255);

-- V2: 回填（后台任务，Python）

import os, psycopg2
conn = psycopg2.connect(os.environ["DATABASE_URL"])
cur = conn.cursor()
cur.execute("SELECT id, email FROM users WHERE email_v2 IS NULL LIMIT 1000")
while rows := cur.fetchall():
    cur.executemany("UPDATE users SET email_v2=%s WHERE id=%s",
                    [(r[1], r[0]) for r in rows])
    conn.commit()

-- V3: 切读（代码改读 email_v2，部署，观察 1 周）
-- V4: 删旧列（确认无回滚需求后）

```

2. 删列前用触发器/视图兜底，给老版本留后路：

```sql
-- 删列前先建兼容视图
CREATE OR REPLACE VIEW users_compat AS
SELECT id, email_v2 AS email FROM users;
-- 老代码改连 users_compat
```

3. CI 检查：DDL 脚本里禁用 `DROP COLUMN`/`DROP TABLE`，需 special approval：

```python
# check_ddl.py
import re, sys
```

- 监控指标：迁移前后表行数、关键查询 P99。

- 保留可回滚窗口（删列延后 ≥ 1 个 release）。


```yaml
# cosign policy
apiVersion: policy.sigstore.dev/v1beta1
kind: ClusterImagePolicy
metadata:
  name: must-be-signed-by-ci
spec:
  images:
    - glob: "harbor.example.com/prod/**"
  authorities:
    - name: gitlab-ci
      keyless:
        url: https://fulcio.sigstore.dev
```

### #21 Prometheus 告警风暴：单节点宕机触发 200 条告警 — P0

**场景描述**
某 K8s 集群一个 node 宕机，上面跑了 50 个 Pod。Prometheus 同时触发：node down、50× pod crashloop、50× 队列堆积、50× 上游超时……值班手机 5 分钟收到 200 条告警，pagerduty 限流，真正关键的"支付服务不可用"被淹没，MTTR 拉长到 40 分钟。

- 告警规则无分组（`group_by` 缺失），每条 alert 单发。
- 无 `inhibit` 规则，node down 时 pod down 不应再发。
- 无优先级分层，CRITICAL 与 INFO 同通道。

**修复方案**
1. Alertmanager 分组 + inhibit + 路由：

```yaml
# alertmanager.yml
route:
  group_by: ['alertname', 'cluster', 'service']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: 'oncall'
  routes:
    - matchers: ['severity=critical']
      receiver: 'pagerduty'
      group_by: ['cluster', 'service']  # 同服务聚一条
    - matchers: ['severity=warning']
      receiver: 'slack'
receivers:
  - name: 'pagerduty'
    pagerduty_configs:
      - routing_key: $PAGER_KEY
  - name: 'slack'
    slack_configs:
      - api_url: $SLACK_WEBHOOK
        channel: '#alerts'
inhibit_rules:
  - source_matchers: ['alertname=NodeDown']
    target_matchers: ['alertname=~"PodDown|CrashLoopBackOff"']
    equal: ['node']
  - source_matchers: ['alertname=ServiceDown', 'severity=critical']
    target_matchers: ['severity=warning']
    equal: ['service']
```

2. 用 Python 监控告警速率自动调阈值：

```python
# alert_throttle.py
import requests, os, time
AM = os.environ["ALERTMANAGER_URL"]
last = 0
while True:
    alerts = requests.get(f"{AM}/api/v2/alerts").json()
    firing = [a for a in alerts if a["status"]["state"] == "firing"]
    if len(firing) > 50:
        # 触发静默 10 分钟，仅留 critical
        requests.post(f"{AM}/api/v2/silences", json={
            "matchers": [{"name": "severity", "value": "warning", "isRegex": False}],
            "startsAt": "now", "endsAt": "in 10m", "createdBy": "auto",
            "comment": "alert storm throttle"
        })
    time.sleep(60)
```


### #22 Loki 日志丢失：Promtail 限速 + 丢弃导致丢关键日志 — P1

**场景描述**
某服务故障复盘需要查 ERROR 日志，但 Loki 里只有 INFO，ERROR 全丢。查 promtail 日志发现 `rate_limited` 持续 30 分钟，期间丢弃 12 万行。原因是某服务突发大量日志（debug 没关），把额度用光，ERROR 被顺带丢弃。

**根因分析**
- Promtail 默认 `readline_rate_drop` 在超限时丢日志，不区分级别。
- Loki ingestion rate 限制过严，突发流量被丢。
- 没有按 tenant/stream 区分优先级。

**修复方案**
1. Promtail 优先级标签 + 不丢 ERROR：

```yaml
# promtail.yml
positions:
  filename: /tmp/positions.yaml
clients:
  - url: http://loki:3100/loki/api/v1/push
    tenant_id: prod
scrape_configs:
  - job_name: app
    static_configs:
      - targets: [localhost]
        labels:
          job: app
          __path__: /var/log/app/*.log
    pipeline_stages:
      - regex:
          expression: '(?P<level>\w+)\s+'
      - labels:
          level:
      # 给 ERROR 加高优 stream
    relabel_configs:
      - source_labels: [level]
        regex: ERROR
        target_label: stream
        replacement: high
      - source_labels: [level]
        regex: (INFO|DEBUG)
        target_label: stream
        replacement: low
limits_config:
  readline_rate_enabled: true
  readline_rate: 10000
  readline_burst: 15000
  # 超限不丢，而是 block
  readline_rate_drop: false
```

2. Loki 按 stream 设独立 rate：

```yaml
# loki.yml
limits_config:
  ingestion_rate_mb: 16
  ingestion_burst_size_mb: 32
  per_stream_rate_limit: 10MB
  per_stream_rate_limit_burst: 20MB
  max_streams_per_user: 0
  # reject old samples 防止回填打爆
  reject_old_samples: true
```

```promql
# 故障 = 错误率 > 5% 持续 5m，恢复 = < 1% 持续 5m
```

```python
       "Accept": "application/vnd.pagerduty+json;version=2"}

             datetime.datetime.fromisoformat(inc["created_at"].replace("Z",""))).total_seconds()
```

**根因分析**
- Auto-Sync 没配 `selfHeal: false`，回滚被视为 drift 被纠正。
- kubectl 直改集群绕过 GitOps，与 ArgoCD 冲突。
- 没有 "ArgoCD 回滚应通过 git revert" 的规范。

**修复方案**
1. ArgoCD 回滚走 git，不在集群侧 kubectl undo：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 1. git revert 部署清单
git revert --no-edit HEAD
git push origin main
# 2. ArgoCD 自动 sync 到旧版本（git 历史 + 1）
# 3. 确认 sync 完成
argocd app wait prod-api --sync
```

2. 紧急情况用 ArgoCD 自身的 rollback（临时禁 selfHeal）：

```bash
argocd app set prod-api --sync-policy none       # 临时关 auto-sync
argocd app rollback prod-api <revision>
# 修复 git 后重新开
argocd app set prod-api --sync-policy automated --self-heal
```

3. App 配置加 `auto-sync` + `self-heal` 显式声明 + `prune`：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-api
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true           # 集群被改后自动拉回 git
    syncOptions:
      - CreateNamespace=true
```

> 紧急回滚 SOP：先 `argocd app set --sync-policy none`，再 `kubectl undo`，再 git revert，最后恢复 auto-sync。

**预防措施**
- 监控指标：ArgoCD `sync_status` OutOfSync 持续时间、selfHeal 触发次数。
- CI 检查项：生产 App 文档化"回滚必须走 git revert"；禁止集群侧 `kubectl set image`。
- 演练 ArgoCD 回滚流程，验证 selfHeal 行为。

```python
# write_manifest.py

    ["docker", "buildx", "imagetools", "inspect",
     f"harbor.example.com/prod/api:{os.environ['TAG']}", "--format", "{{.Manifest.Digest}}"], text=True).strip()

    "service": "api",
    "version": os.environ["TAG"],
    "digest": digest,
    "git_sha": subprocess.check_output(["git","rev-parse","HEAD"], text=True).strip(),

open(path, "w").write(json.dumps(manifest, indent=2))

subprocess.check_call(["git", "commit", "-m", f"release {os.environ['TAG']}"])
subprocess.check_call(["git", "push"])
```

- 监控指标：每次部署必写 manifest；回滚耗时（目标 < 5 分钟）。
- CI 检查项：deployment image 必须用 digest；CI 末尾写 manifest 到 git。

- 没有在影子库做演练。

**修复方案**
1. 拆分 DDL，用 instant 算法：

```sql
-- V20260101__add_status.sql
-- MySQL 8.0+ 支持 INSTANT，秒级完成
ALTER TABLE orders ADD COLUMN status VARCHAR(20), ALGORITHM=INSTANT;
-- 默认值用应用层填充，不在 DDL 设 DEFAULT，避免回填
```

2. 老版本用 pt-online-schema-change（gh-ost 也行）：

```bash
pt-online-schema-change \
  --alter "ADD COLUMN status VARCHAR(20)" \
  --set-vars innodb_lock_wait_timeout=1 \
  --max-load Threads_running=50 \
  --critical-load Threads_running=100 \
  --execute D=prod,t=orders
```

3. CI 检查 DDL 是否走 instant：

```python
# check_ddl_online.py
import re, sys

```


- 监控指标：DDL 执行时长、`innodb_row_lock_waits`、`Threads_running`。

### #28 ConfigMap 热更新失效：Pod 没拿到新配置 — P1

**场景描述**

**根因分析**
- ConfigMap 挂载为 volume 时，kubelet 异步刷新（默认 60s–5min），不即时。
- 挂载为 env 的 ConfigMap **不会**自动更新，Pod 重启才生效。
- 应用没监听文件变化主动 reload。

**修复方案**
1. env 形式的 ConfigMap 必须重启 Pod：

```bash

```

2. volume 形式 + 应用 watch 文件变化（Java）：

```java
// ConfigWatcher.java
import java.nio.file.*;
import java.util.concurrent.atomic.AtomicReference;

@Component
public class ConfigWatcher {
  private final AtomicReference<Properties> cfg = new AtomicReference<>();
  @PostConstruct
  void init() throws Exception {
    var path = Paths.get("/etc/app/rate-limit.properties");
    load(path);
    var ws = FileSystems.getDefault().newWatchService();
    path.getParent().register(ws, StandardWatchEventKinds.ENTRY_MODIFY);
    Thread.ofVirtual().start(() -> {
      while (true) {
        try {
          var key = ws.take();
          key.pollEvents().stream()
            .filter(e -> e.context().toString().equals(path.getFileName().toString()))
            .forEach(e -> { load(path); System.out.println("config reloaded"); });
          key.reset();
        } catch (Exception ignored) {}
      }
    });
  }
  void load(Path p) { /* read properties into cfg */ }
}
```

```yaml
  name: api
```

- CI 检查项：env 形式 ConfigMap 变更必须配 Reloader；volume 形式应用必须 watch。

### #30 数据库迁移缺 down 脚本：无法回滚被迫手工救火 — P1

**场景描述**
某团队用 Alembic 做迁移，开发者只写 `upgrade()`，`downgrade()` 是空的。某次部署后才发现新列导致 ORM 报错，回滚时 `alembic downgrade -1` 报 `NotImplementedError`，只能手工 `ALTER TABLE DROP COLUMN`，还忘了删索引，留下隐患。

**根因分析**
- `downgrade()` 不写，回滚靠手工。
- CI 没检查 downgrade 是否为空。
- 没有回滚演练。

**修复方案**
1. Alembic migration 必须实现 downgrade：

```python
# migrations/versions/a1b2_add_user_status.py
from alembic import op
import sqlalchemy as sa

def upgrade():
    op.add_column('users', sa.Column('status', sa.String(20), nullable=True))
    op.create_index('idx_users_status', 'users', ['status'])

def downgrade():
    op.drop_index('idx_users_status', table_name='users')
    op.drop_column('users', 'status')
```

2. CI 检查 downgrade 非空（Python AST）：

```python
# check_downgrade.py
import ast, sys, glob
for f in glob.glob("migrations/versions/*.py"):
    tree = ast.parse(open(f).read())
    for node in ast.walk(tree):
        if isinstance(node, ast.FunctionDef) and node.name == "downgrade":
            body = [n for n in node.body if not isinstance(n, (ast.Pass, ast.Expr, ast.Constant))]
            if len(body) == 0 or (len(body) == 1 and isinstance(body[0], ast.Raise)):
                print(f"[BLOCK] {f}: downgrade 为空或仅 raise NotImplementedError")
                sys.exit(1)
print("all downgrade implemented")
```

3. CI 跑 up→down→up 往返测试：

```yaml
migration-roundtrip:
  services:
    - postgres:15
  script:
    - alembic upgrade head
    - alembic downgrade -1
    - alembic upgrade head
    - pytest -m "not slow"
```

**预防措施**
- 监控指标：迁移回滚成功率、回滚耗时。
- CI 检查项：downgrade 必须 AST 非空；up→down→up 往返测试通过。
- 不可逆 DDL（删列/删表）单独审批，不进自动迁移。

## 附录：通用预防清单（CI 检查项速查）

1. **流水线**：Runner `concurrent` 限制；cache key 按 lockfile 哈希；secret 变量 masked；生产 deploy `resource_group`；`pull_request_target` 禁配 PR checkout。
2. **镜像**：base image pin `@sha256`；`.dockerignore` 必备；多阶段构建后跑 smoke test；Trivy 分层扫描 + ignore 带 owner；Harbor 复制 digest 校验。
3. **部署**：readinessProbe + `progressDeadlineSeconds`；Argo Rollouts 窗口 ≥ 2m；蓝绿切流前 drain；feature flag 默认 `false` 且 CI 校验存在；DB 迁移走 Expand-Contract 三阶段。
4. **门禁**：SonarQube 仅扫新代码；SBOM + 锁文件扫传递依赖；Gitleaks fixture allowlist；CodeQL 路径过滤 + heap；Cosign keyless issuer 一致性。
5. **监控**：Alertmanager `group_by` + `inhibit`；Loki ERROR 独立 stream；MTTR 用 incident 口径；ArgoCD 回滚走 git revert；部署写 release manifest。
6. **数据库**：大表 DDL `ALGORITHM=INSTANT` 或 pt-osc；changeset 不可变，改库加新版本；ConfigMap 配 Reloader；Secret 单一真源（Vault）；downgrade 非空 + 往返测试。
