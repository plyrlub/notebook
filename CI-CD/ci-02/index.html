    第二章：环境与前置技能¶

    学习目标：掌握 CI/CD 跑起来之前必须具备的四项前置能力——Git 工作流选型（分支模型与协作）、Docker 容器基础（构建、多阶段、最佳实践）、YAML 语法（所有 CI 工具的配置语言）、制品仓库概念（存放构建产物的地方）。
    这一章是"跑通最小流水线"的地基。不学这章直接去 GitHub Actions，会遇到每一步都卡的情况。

    2.1 Git 工作流选型与对比¶

    为什么这是第一章：分支模型决定了流水线的触发规则、版本号策略、环境晋升逻辑。用错分支模型，后面的 CI/CD 再努力也会拧巴。

    2.1.1 三大主流分支模型¶

    2026 年 CI/CD 场景下的主流分支模型是三种 + 若干变体。核心差异在"分支数量"和"合主干的时机"：

    表 2-1：三大主流 Git 工作流核心差异

    维度 GitFlow GitHub Flow Trunk-based Development
    核心分支 main + develop + feature + release + hotfix（5 类） main + feature（2 类） 只有 main 主干 + 极短生命周期 feature 分支
    feature 切出点 从 develop 切 从 main 切 从 main 切
    合主干时机 通过 release 分支合 main（按批次） 功能完成就合 main 功能完成立刻合 main（甚至小步多次合）
    发布方式 切 release 分支，经测试后合 main main HEAD 即发布 main HEAD 永远可发布
    配套能力 不需要额外工具 PR Review + CI 门禁 Feature Flag（特性开关）必须有
    适合团队规模 大团队、多版本并行维护 中小团队、单版本快速迭代 高效能团队、小步快跑、追求 DORA 高指标
    学习成本 高（5 类分支容易晕） 低 中低（概念简单，但 Flag 工程化有门槛）

    2.1.2 与用户 P1 模型的对照¶

    → 见「我的实践记录」P1。此处只做分支模型归类，不做优劣判断。

    你的 P1 模型（dev/test/stage/main，feature 从 main 切、独立合入各环境）本质是 GitFlow 的改良变体，对照如下：

    表 2-2：用户 P1 模型与三种主流模型的对照

    维度 经典 GitFlow 用户 P1 模型 Trunk-based
    核心分支数 5 类 4 类（dev/test/stage/main） 1 类（main）
    feature 切出 从 develop 从 main 从 main
    环境晋升方式 release 分支批量晋升 feature 独立合入每个环境（最细粒度） 版本号推进
    合 main 时机 release 测完合 单 feature 走完 4 环境合 功能完成即合
    环境与分支绑定 否（release=候选） 是（4 分支对应 4 环境） 否（main 绑定 prod，其他环境靠 Flag 或版本号）
    需要 Flag 吗？ 不需要 不需要 必须有

    一句话归类：P1 在分支数量上接近 GitFlow，但在"feature 切出点（main）"和"合入粒度（单 feature 级）"上更接近 Trunk-based，是一个吸收了两侧优点的折中改良。

    2.1.3 Trunk-based + Feature Flag：2026 主选模型细节¶

    Trunk-based 是 2026 年 CI/CD 主选模型。但很多教程只说"大家都合主干"，没讲关键问题：没开发完的代码合主干不会把生产搞坏吗？

    答案是：Feature Flag（特性开关）。 没开发完的功能合主干时默认关，Flag 控制是否对用户可见。

    表 2-3：Trunk-based 下 Feature Flag 的四种典型使用场景

    Flag 类型 用途 生命周期 示例
    Release Flag（发布开关） 控制新功能是否对用户开放 发布完稳定后删除 is_new_checkout_enabled
    Experiment Flag（实验开关） A/B 测试、灰度放量 实验结论出来后删除 10% 用户启用新推荐算法
    Ops Flag（运维开关） 限流、降级、开关第三方依赖 长期保留 payment_provider_use_new_api
    Kill Switch（熔断开关） 紧急关闭高风险功能 长期保留 disable_llm_stream_output

    Flag 工程化的三个坑（必须提前踩平）：
    1. Flag 爆炸：100 个 Flag 没人清理 → 代码里全是 if flag 分支，复杂度剧增。做法：每个 Release Flag 加"清理截止日期"，发版后 2 周必删。
    2. Flag 组合爆炸：N 个 Flag 有 2^N 种状态 → 不可能全测。做法：Flag 数量设上限（单仓库不超 20 个活跃 Flag），Flag 中心做依赖声明。
    3. Flag 配置泄露影响生产：Flag 配置与代码解耦，不能写死在仓库里。做法：独立 Flag 中心（Unleash/LaunchDarkly/Flagsmith），后端服务通过 SDK 拉取。

    → 更多 Flag 细节见补充专题 S7。

    2.1.4 Release Flow（微软模型，折中备选）¶

    如果 Trunk-based 的 Flag 工程化成本对团队太高（团队小、没 Flag 基础设施），但又不想回到 GitFlow 的 5 类分支复杂度，可以用微软的 Release Flow：

    main：日常开发，小步合入
  │
  ├── 发版时切 release/1.2（分支即版本号）
  │      │
  │      ├── 发现 bug：在 release/1.2 修
  │      │      │
  │      │      └── 修完同时合回 release/1.2 + cherry-pick 回 main
  │      │
  │      └── 发布完成：release/1.2 打 Tag v1.2.0，分支保留（热修入口）
  │
  ├── 热修 v1.2.1：直接在 release/1.2 切 hotfix，修完反合 main
  │
  └── 下个发版：切 release/1.3（基于 main 最新 HEAD）

    Release Flow 适合场景：中等发布频率（每月 1~4 次）、需要独立维护若干已发布小版本的团队。

    2.1.5 现阶段最佳实践（2026）¶

    1. 能上 Trunk-based 就上，但前提是有 Flag 基础设施——不要在没 Flag 的情况下硬上 Trunk-based，会变成"合主干但不敢发"的尴尬局面。
    2. P1 这类改良 GitFlow 变体在特定场景依然合理（小团队、强合规、低频发布、对环境即分支心智模型强依赖），不要为了"主流"而硬改。
    3. 无论选哪个模型，两条通用规则必须守：
    4. main/master 永远受保护（Branch Protection Rules），禁止直推，必须走 PR + CI 通过。
    5. 禁止在已发版的分支上反向前行——热修修完必须反合回主干（cherry-pick 或 merge），不能让 release 和 main 分叉。

    2.2 Docker 基础与 CI/CD 场景最佳实践¶

    为什么这是前置：90% 以上的 CI/CD 流水线最终产物是容器镜像，构建镜像是 Package 阶段的核心动作。Docker 写得差，流水线构建慢、镜像大、安全漏洞多。

    2.2.1 核心概念速检（你应该已经会了）¶

    如果以下任一概念模糊，请暂停本节，先补 Docker 基础再往下：

    • 镜像（Image）vs 容器（Container）vs Dockerfile 区别
    • FROM / RUN / COPY / ADD / CMD / ENTRYPOINT / EXPOSE / ENV 各指令作用
    • 镜像分层原理：每一条指令一层，相同层跨构建缓存复用
    • docker build / docker tag / docker push / docker pull
    • .dockerignore 的作用（类似 .gitignore，避免把源码、日志、依赖目录打进镜像）

    2.2.2 多阶段构建（Multi-stage Build）¶

    这是 2026 年所有 CI/CD 场景下必用的模式——不再有"编译用的 JDK/Node/Python 跟着生产镜像跑"的问题。

    # ========== 构建阶段（Builder Stage）：只在构建镜像时用，不进最终产物 ==========
FROM python:3.12-slim AS builder
WORKDIR /build

# 先只拷贝依赖文件，利用缓存层（依赖不变，这层永远命中缓存）
COPY pyproject.toml poetry.lock ./
RUN pip install --no-cache-dir poetry \
    && poetry config virtualenvs.create false \
    && poetry install --no-dev --no-interaction

# 再拷贝源代码（依赖不变时，代码修改不会触发依赖重装）
COPY src/ ./src/

# 如果有编译步骤（Cython 扩展、前端 build），在这里做
# RUN poetry run cythonize -i src/xxx.pyx

# ========== 运行阶段（Final Stage）：只包含运行时必需内容 ==========
FROM python:3.12-slim AS final

# 非 root 用户：生产最佳实践，避免容器被攻破后拿到 root 权限
RUN groupadd -r appuser && useradd -r -g appuser appuser

WORKDIR /app

# 从 builder 阶段拷入已安装的依赖和源码（不拷 build 工具链）
COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY --from=builder /build/src /app/src

# 切换到非 root 用户
USER appuser

# 健康检查：部署后 Verify 阶段用，也是 K8s Readiness/Liveness 的基础
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

EXPOSE 8080
CMD ["python", "-m", "src.main"]

    多阶段构建的三个关键点：
    1. 阶段命名：AS builder、AS final，用 COPY --from=builder 跨阶段复制。
    2. COPY 顺序：先拷依赖文件（锁文件 / pom.xml / package.json），再拷源码。缓存命中率从 <10% 提到 90%+（见 S10 缓存最佳实践）。
    3. Final Stage 基础镜像选最小：slim < alpine < distroless < scratch，越往右体积越小越安全，但越难调试（没有 shell）。Java/Python 选 slim。Go/Rust 这类编译型语言可以直接到 distroless 或 scratch。

    2.2.3 Java 场景：Maven + JDK 多阶段模板（后端栈匹配你的技术）¶

    # ========== Builder 阶段：用 JDK + Maven 构建 ==========
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /build

# 先拷 pom.xml + 所有子模块 pom（多模块项目）
COPY pom.xml ./
COPY module-a/pom.xml ./module-a/
COPY module-b/pom.xml ./module-b/
# 只下载依赖，不编译；依赖不变时永久命中缓存
RUN mvn -B -f pom.xml dependency:go-offline -DskipTests

# 再拷源码
COPY src ./src
COPY module-a/src ./module-a/src
COPY module-b/src ./module-b/src
RUN mvn -B clean package -DskipTests -Pprod

# ========== Final 阶段：只带 JRE ==========
FROM eclipse-temurin:21-jre-noble AS final

RUN groupadd -r appuser && useradd -r -g appuser appuser
WORKDIR /app
# 只拷单个可执行 jar（Maven 输出路径按实际项目改）
COPY --from=builder /build/module-a/target/module-a.jar /app/app.jar

USER appuser
HEALTHCHECK --interval=30s --timeout=5s CMD \
  curl -f http://localhost:8080/actuator/health || exit 1
EXPOSE 8080
CMD ["java", "-XX:+UseG1GC", "-XX:MaxRAMPercentage=75.0", "-jar", "/app/app.jar"]

    Java 构建两个高频优化：
    1. JVM 参数用 MaxRAMPercentage，不用写死 Xmx：容器里 cgroup 内存变了不用改镜像。
    2. Maven + Spring Boot 用 -DskipTests，单元测试让 CI 单独跑：不要在 Docker build 里跑单测（build 慢且缓存难命中），单测在 CI 的 Test Stage 跑，跑完覆盖率报告交给 Sonar。

    2.2.4 Lua/OpenResty 场景：多阶段模板（匹配你的 Lua 技术栈）¶

    # ========== Builder 阶段：luarocks 装依赖 + 可选编译扩展 ==========
FROM openresty/openresty:1.25.3.1-0-jammy AS builder
WORKDIR /build
# 安装 luarocks 依赖（JSON 库、HTTP 客户端等）
RUN apt-get update && apt-get install -y unzip git \
    && luarocks install lua-cjson 2.1.0-1 \
    && luarocks install lua-resty-http 0.16.1-0
# 拷贝源码 + 预做 luacheck 静态检查（把 Lint Stage 结果同步打进来）
COPY nginx/ /build/nginx/
# COPY lua_modules/ /build/lua_modules/

# ========== Final 阶段：最小运行镜像 ==========
FROM openresty/openresty:1.25.3.1-0-jammy AS final
RUN groupadd -r appuser && useradd -r -g appuser appuser
# 从 builder 拷 luarocks 安装后的模块
COPY --from=builder /usr/local/lib/lua /usr/local/lib/lua
COPY --from=builder /usr/local/share/lua /usr/local/share/lua
# 拷配置和代码
COPY --from=builder /build/nginx /usr/local/openresty/nginx/
# 日志目录权限（非 root 用户可写）
RUN mkdir -p /var/log/nginx && chown -R appuser:appuser /var/log/nginx /usr/local/openresty/nginx
USER appuser
EXPOSE 8080
CMD ["/usr/local/openresty/bin/openresty", "-g", "daemon off;"]

    2.2.5 Dockerfile 反模式（2026 仍高频踩坑）¶

    表 2-4：CI/CD 场景下的 Dockerfile 常见反模式与修正

    反模式 问题 正确做法
    FROM ubuntu:latest + 手动装 JDK/Python 镜像 500MB+，OS 漏洞满满 用官方 <lang>-slim 或 eclipse-temurin 这类干净基础镜
    每条 RUN 都装包不清理缓存 /var/cache/apt 里残留几百 MB 一条 RUN 链：apt-get update && apt-get install -y xxx && rm -rf /var/lib/apt/lists/*
    COPY . /app 在最开头 改任何文件（哪怕 README）都导致依赖层缓存失效 锁文件/依赖先拷，源码后拷
    USER root 跑生产容器 容器逃逸 = 宿主机 root（CVE 高发路径） 必须建非 root 用户，USER 切换
    用 ADD 下载远程包（ADD https://...tar.gz） ADD 自带解压但缓存不好控 + URL 变更难追踪 RUN curl -L ... 或在 CI 外部下载再 COPY 进镜像
    CMD ["python", "app.py"] + 镜像里写死配置 同一份镜像在 dev/test/stage 跑不起来（配置不同） 配置用 ENV / K8s ConfigMap 注入；镜像里不含任何环境特定配置
    latest 作部署标签 每次部署都拉到不同版本，线上跑的什么说不清 推三类确定标签：版本号 + gitSHA + major.minor（见 S10.4）

    2.2.6 现阶段最佳实践（2026）¶

    1. 所有镜像必须多阶段构建，单阶段构建在 CI/CD 里属于反模式。
    2. 构建顺序 = 依赖先拷、源码后拷，这是 CI 缓存命中的生命线。
    3. 非 root 用户 + Healthcheck，生产镜像二件套必加。
    4. 基础镜像锁定 SHA（如 python:3.12-slim@sha256:abc123），不要用浮动 tag。
    5. BuildKit（DOCKER_BUILDKIT=1）作为默认构建器，性能和缓存都比传统 build 强一个数量级。

    2.3 YAML 语法速查（CI 配置文件必知必会）¶

    为什么这是前置：所有主流 CI 工具（GitHub Actions / GitLab CI / Tekton / Argo）的配置文件都是 YAML。不会 YAML 直接写 pipeline = 每一步都踩坑。

    2.3.1 数据类型与缩进¶

    四条铁律：
    1. 缩进只用空格，不许用 Tab（GitHub Actions/GitLab 都会炸）。
    2. 同一层级的项必须左对齐（空格数一致）。推荐 2 空格一层。
    3. key: value 冒号后必须有空格。
    4. 字符串有特殊字符（: # { } & * | >）时，加引号包起来。

    # ========== 基本类型 ==========
name: CI Pipeline                       # 字符串
version: 1.2                            # 数字（注意：某些场景会被转字符串，需要的话用 "1.2"）
enabled: true                           # 布尔：true/false
disabled: false
log_level: null                         # null（空值）

# ========== 列表（两种写法） ==========
branches:
  - main
  - develop
  - "release/*"                         # 含通配符，加引号

branches_short: [main, develop, 'release/*']  # 行内写法

# ========== 字典（嵌套） ==========
jobs:
  build:
    runs-on: ubuntu-latest
    steps:                              # 列表里再嵌字典（最常见的 CI 写法）
      - name: Checkout
        uses: actions/checkout@v4
      - name: Install deps
        run: pip install -r requirements.txt

# ========== 多行字符串（关键！Run 脚本、配置文件内嵌常用） ==========
# 写法 1：| 保留换行（shell 脚本首选）
build_script: |
  echo "Building project..."
  mkdir -p dist
  python build.py --env prod
  echo "Build done"

# 写法 2：> 折叠换行（段落文字用，shell 基本不用）
description: >
  This pipeline runs lint, build, test, scan, package, publish
  and deploy stages. All failures except medium ones are blocked.

# ========== 特殊情况：以 * & 开头的 YAML 锚点与别名 ==========
# 锚点：& 标记一段可复用内容；别名：* 引用它
# GitLab extends、GitHub Actions composite action 提供了更优雅的复用，但基础语法要知道
.defaults: &defaults
  image: python:3.12-slim
  before_script:
    - pip install -r requirements.txt

job_a:
  <<: *defaults                         # 合并锚点
  script: pytest -m a

job_b:
  <<: *defaults
  script: pytest -m b

    2.3.2 CI 场景下的 YAML 高频坑点表¶

    表 2-5：CI YAML 最常踩的 10 个坑

    坑 表现 修正
    Tab 缩进 GitHub/GitLab 直接报"mapping not allowed here" 全量转空格，编辑器设 tab=2space
    no / yes / off / on 被自动转布尔 env: { DEBUG: off } → 变成 false 而非字符串 "off" 加引号：DEBUG: "off"
    纯数字版本号丢失前导 0 version: 012 → 变成数字 12 加引号：version: "012"
    : 出现在字符串中间 script: echo "Done: 100%" → : 被误判为字典分隔 整句加引号或用
    行内列表/字典缺逗号 tags: [v1, v2 v3]（v2 和 v3 间没逗号） 补逗号或用分行列表
    Anchor 跨文件不生效 include 另一个 YAML 再 *anchor 引用不了 用工具原生复用机制（Reusable Workflow / include + extends / Anchors 仅限同文件）
    << 合并键后再覆写字段顺序 顺序错 = 覆盖错，后写的才赢 始终先 <<: *defaults，再写覆写字段
    字符串里的 ${VAR} 在 CI YAML 里是 CI 变量展开，不是 YAML 语法 不要与 $HOME 这种 shell 变量混，shell 脚本里用双美元 $$HOME 转义
    超长行没折行 100+ 字符的 run 脚本不可读 一律用 | 多行写
    true 写成 True / TRUE YAML 规范三种都认，但不同解析器行为不一致（极老版本） 统一写全小写 true / false

    2.3.3 现阶段最佳实践（2026）¶

    1. 所有 YAML 文件提交前过 lint：yamllint（通用）+ actionlint（GitHub Actions 专用）+ gitlab-ci-lint（GitLab 专用），作为 Lint Stage 的第一步。
    2. Shell 脚本一律用 | 多行写，不要把 5 个命令塞在一行用 && 连起来——错误时根本不知道哪步挂了，可读性极差。
    3. 敏感值绝不写死在 YAML，全部走 secrets.X / variables (masked) / Vault 注入（见 S1 密钥管理专题）。

    2.4 制品仓库全景¶

    为什么这是前置：CI/CD 的 Publish 阶段 = 把制品推到仓库，Deploy 阶段 = 从仓库拉对应版本的制品。不理解制品仓，跑起来的 pipeline 只是"构建了个寂寞"——产物没地方存。

    2.4.1 制品分类：三种最常见的制品类型¶

    1. 镜像仓（Container Registry）：存 Docker/OCI 镜像。所有后端项目最终的部署形态。
    2. 包仓（Package Repository）：语言级依赖包。Maven（Java jar）、PyPI（Python wheel）、npm（前端）、LuaRocks（Lua）、Go Module Proxy。
    3. 通用制品仓（Binary Repository）：存任何二进制——编译好的二进制（.so/.exe）、前端打包产物（dist/）、数据库迁移脚本（SQL）、SBOM 文件、部署 Helm Chart。

    2.4.4 四个必须在选型时问自己的问题（90% 团队漏问）¶

    1. 不可变标签（Immutable Tags）是否支持？ — 不支持的绝对不要选。防"同一个 v1.2.0 被覆盖，线上跑的是什么说不清"。
    2. CVE 扫描 + 阻断推送支持吗？ — Trivy 集成在 CI 是一道，但镜像仓做第二道闸（Harbor 的 Pre-requisites 策略：发现 CRITICAL 漏洞不让拉取），双层保险。
    3. 复制/镜像策略支持吗？ — 多地域部署时，prod 环境的镜像仓只允许从镜像复制来，不许 CI 直接推 prod。
    4. 保留策略怎么配置？ — nightly 构建保留 30 天、正式 Tag 永久保留，磁盘别半年撑爆。

    2.4.5 现阶段最佳实践（2026）¶

    1. 镜像仓与包仓可以分开，不要为了"一个仓库所有事"硬上。镜像仓选 Harbor，包仓选 Nexus 组合非常常见。
    2. CI 推制品必须带元数据标签（见 S10.3/S10.4）：git SHA、构建号、流水线链接、SBOM 附件。制品追溯时这些标签是生命线。
    3. prod 镜像仓不允许 CI 直接写。dev → test → stage → prod 的正确路径是"版本号晋升时，制品在仓库间复制（Promotion）"，而不是 CI 给 prod 推送。这正是"不可变制品"原则的落地。
