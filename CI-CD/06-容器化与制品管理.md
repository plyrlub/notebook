## 6.2 Dockerfile 最佳实践进阶

> 第 05 章已经给了三语言的基础 Dockerfile 模板（Builder + Final 分层、非 root、HEALTHCHECK）。本章进阶讲**为什么这样写**以及**还可以怎么优化**。

### 6.2.1 镜像分层与缓存原理

**图 6-1：Docker 镜像分层结构**

```
┌───────────────────────────────────┐  ← 可写层（容器运行时产生）
│  Container Writable Layer         │     运行时写入，停止即丢
├───────────────────────────────────┤
│  Layer N: CMD ["python", "main"]  │  ← 指令层（每条指令 = 1 层）
├───────────────────────────────────┤
│  Layer N-1: COPY app/ ./app/      │  ← 源码层（源码变了这层失效）
├───────────────────────────────────┤
│  Layer N-2: RUN uv sync ...       │  ← 依赖层（lockfile 变了这层失效）
├───────────────────────────────────┤
│  Layer N-3: COPY pyproject.toml   │  ← 依赖声明层（lockfile 变了这层失效）
├───────────────────────────────────┤
│  Layer 1: FROM python:3.12-slim   │  ← 基础镜像层（很少变）
└───────────────────────────────────┘
```

**缓存命中核心原则**：**某一层变了，它和它后面的所有层都失效，需要重新构建。**

所以 Dockerfile 指令顺序的核心策略：
1. **变化频率从低到高排列**：基础镜像 → 系统依赖 → 项目依赖声明 → 项目依赖安装 → 源码 → CMD
2. **先 COPY 依赖声明文件，再 RUN 安装，最后 COPY 源码**：源码每 commit 都变，但依赖不变 → 依赖层命中缓存，只有源码层重建

> 这就是为什么第 05 章 Dockerfile 模板里 `COPY pyproject.toml uv.lock` 在 `COPY app/` 前面。

### 6.2.2 镜像瘦身策略

**表 6-1：三种基础镜像方案对比**

| 方案 | 典型大小 | 优点 | 缺点 | 适用场景 |
| ---- | -------- | ---- | ---- | -------- |
| **slim**（如 `python:3.12-slim`） | 150-200MB | 有 shell + 基础工具，调试方便 | 比 distroless 大 | 大多数项目（推荐起点） |
| **alpine**（如 `python:3.12-alpine`） | 50-80MB | 最小 | musl libc 兼容性差，C 扩展可能编译失败 | 纯 Python/Go 静态编译 |
| **distroless**（如 `gcr.io/distroless/python3-debian12`） | 80-120MB | 无 shell（安全），极小攻击面 | 无法 `docker exec sh` 调试 | 生产环境（安全要求高） |

**选择建议**：
- **新项目起步**：用 `slim`，够小且好调试
- **生产安全加固**：迁移到 `distroless`（无 shell = 攻击者拿到 RCE 也没法执行命令）
- **alpine 慎用**：musl libc 会导致很多 C 扩展（如 `numpy`、`grpcio`）需要从源码编译，反而更慢

#### dev/test 用 slim + stage/prod 用 distroless（分层方案）

> **推荐策略**：开发和测试环境用 slim（可 `docker exec sh` 调试），stage 和 prod 用 distroless（无 shell 安全加固）。两者都是 Debian 基础，glibc 一致，不会出现 dev 测试通过、prod 翻车的问题。

**表 6-2：分层方案对比**

| 维度 | dev/test 用 slim | stage/prod 用 distroless |
| ---- | ---------------- | ----------------------- |
| 调试 | ✅ `docker exec sh` 进去查问题 | ❌ 没 shell，没法 exec |
| 安全攻击面 | dev 无所谓 | ✅ 攻击者拿到 RCE 也执行不了命令 |
| 镜像大小 | 150-200MB 够用 | ✅ 80-120MB 更小 |
| glibc 一致性 | Debian glibc | Debian glibc（和 slim 一致，不翻车） |

**一个 Dockerfile + build arg 切换 Final 基础镜像**（不用写两个 Dockerfile）：

```dockerfile
# ========== Builder（dev/test/stage/prod 共用） ==========
FROM python:3.12-slim AS builder

ENV UV_VERSION=0.6.6 UV_CACHE_DIR=/root/.cache/uv
ADD --chmod=755 https://astral.sh/uv/${UV_VERSION}/install.sh /install-uv.sh
RUN sh /install-uv.sh && rm /install-uv.sh

WORKDIR /build
COPY pyproject.toml uv.lock ./
# 关键：--python-preference only-managed 让 .venv 自带独立 Python 解释器
# 这样拷到 distroless（没有系统 Python）也能跑
RUN uv sync --frozen --no-dev --no-project --python-preference only-managed
COPY app/ ./app/

# ========== Final（按环境切换基础镜像） ==========
# 构建时传入 BASE_IMAGE，默认 slim
ARG BASE_IMAGE=python:3.12-slim
FROM ${BASE_IMAGE} AS final

# slim 有 shell，可以 groupadd；distroless 没有，用内置 nonroot 用户
# distroless:nonroot 镜像自带 uid=65532 的 nonroot 用户
COPY --from=builder /build/.venv /app/.venv
COPY --from=builder /build/app /app/app
ENV PATH="/app/.venv/bin:$PATH"

# 注意：distroless 不支持 HEALTHCHECK 指令，prod 的健康检查交给 K8s livenessProbe
# slim 版可以保留 HEALTHCHECK，distroless 版会忽略
USER appuser

EXPOSE 8080
CMD ["python", "-m", "app.main"]
```

**GitLab CI 按环境传不同 `BASE_IMAGE`**：

```yaml
# .gitlab-ci.yml
build:dev:
  variables:
    BASE_IMAGE: "python:3.12-slim"
  script:
    - /kaniko/executor --build-arg BASE_IMAGE=$BASE_IMAGE --destination $IMAGE_TAG:dev

build:prod:
  rules:
    - if: $CI_COMMIT_TAG
  variables:
    BASE_IMAGE: "gcr.io/distroless/python3-debian12:nonroot"
  script:
    - /kaniko/executor --build-arg BASE_IMAGE=$BASE_IMAGE --destination $IMAGE_TAG:prod
```

**两个实操注意点**：

1. **distroless 不支持 `HEALTHCHECK` 指令** → prod 的健康检查交给 K8s `livenessProbe`（prod 本来就该用 K8s 探针）：

```yaml
# K8s deployment
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 30
```

2. **distroless 没有系统 Python** → UV 必须用 `--python-preference only-managed` 让 `.venv` 自带独立解释器，否则 `.venv` 里的 python 软链接指向系统 Python，拷到 distroless 上找不到就报错。

> **Java 版同理**：dev/test 用 `eclipse-temurin:17-jre-slim`，prod 用 `gcr.io/distroless/java17-debian12:nonroot`。

### 6.2.3 安全加固

在 05 章 Dockerfile 基础上，生产环境额外加固：

```dockerfile
FROM python:3.12-slim AS final

# 1. 非 root 用户
RUN groupadd -r appuser && useradd -r -g appuser appuser

# 2. 创建临时目录并赋权（只读 FS 模式下 /tmp 需要可写）
RUN mkdir -p /tmp/app && chown appuser:appuser /tmp/app

WORKDIR /app

COPY --from=builder /build/.venv /app/.venv
COPY --from=builder /build/app /app/app

ENV PATH="/app/.venv/bin:$PATH"

USER appuser

EXPOSE 8080

# 3. HEALTHCHECK（05 章已有）
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health', timeout=3)" || exit 1

CMD ["python", "-m", "app.main"]
```

**运行时安全加固（在 K8s deployment 里配置，不是 Dockerfile）**：

| 加固项 | K8s 配置 | 作用 |
| ------ | -------- | ---- |
| 只读文件系统 | `readOnlyRootFilesystem: true` | 攻击者无法写入恶意文件 |
| drop 所有能力 | `drop: [ALL]` | 限制内核能力 |
| 非 root 运行 | `runAsNonRoot: true` + `runAsUser: 1000` | 防止提权 |
| 只读 /tmp | `emptyDir` 挂载到 /tmp | 只读 FS 下 /tmp 需要可写 |

### 6.2.4 镜像标签策略（策略层面）

**表 6-3：镜像标签策略对比**

| 策略 | 示例 | 优点 | 缺点 | 推荐度 |
| ---- | ---- | ---- | ---- | :--: |
| **immutable tag（不可变）** | `v1.2.0` / `gitsha-abc1234` | 同一 tag 永远指向同一镜像，可追溯 | tag 数量多 | ⭐⭐⭐⭐⭐ |
| **mutable tag（可变）** | `latest` / `dev` | 简单 | 同一 tag 可能指向不同镜像，无法回滚 | ⭐ |
| **混合策略** | `v1.2.0` + `dev-v1.2.0-abc1234` | 发版用 immutable，环境用可变 | 需要命名规范 | ⭐⭐⭐⭐ |

**最佳实践**：
- **生产环境**：必须用 immutable tag（`v1.2.0` 或 `gitsha-abc1234`），禁止 `latest`
- **dev/test 环境**：可以用 `dev-${CI_COMMIT_SHORT_SHA}` 这种"可变但有标识"的 tag
- **镜像仓开启不可变标签**：GitLab Registry 和 Harbor 都支持"一旦 push 了某个 tag 就不能再覆盖"

> 这对应你的 [P1.1 实践](./我的实践记录.md)：打 Tag 发版 = immutable tag，回滚 = 拉旧 Tag 重新部署。
>
> 具体命名规范的落地见 **6.6.3**（标签策略的"用什么名字"）。

### 6.2.5 开源项目 Dockerfile 选型参考（知识性）

> 参考来源：Docker 官方开发指南 + Google distroless 官方仓库 + Kubernetes 社区多语言 Dockerfile 模板。

**Docker 官方 3 条生产级补充规则**（前 4 条基础规则见 05 章）：

| 规则 | 说明 | 落地方式 |
| ---- | ---- | -------- |
| 不要在 Dockerfile 里放 Secret | `RUN echo $SECRET_KEY > .env` 会把 Secret 留在镜像层历史，`docker history` 可见 | Secret 全部走运行时注入，不要 `COPY` 或 `RUN echo` |
| BuildKit 临时传 Secret（Kaniko 也支持） | Build 时要拉私有包，用 `--mount=type=secret`，Build 完即销毁，不留历史痕迹 | 下方示例 |
| HEALTHCHECK 不要用 curl | distroless 无 curl；slim 用 curl 增加攻击面 | Python 用 `urllib.request` 或二进制自带健康端口 |

**BuildKit / Kaniko 临时传 Secret 示例（拉私有 PyPI 包）**：

```dockerfile
# Build 时传入：docker build --secret id=pypi_token,src=$HOME/.pypi-token .
# Kaniko 传入：/kaniko/executor --secret id=pypi_token,dst=/root/.pypi-token
FROM python:3.12-slim AS builder
WORKDIR /build
COPY pyproject.toml uv.lock ./
RUN --mount=type=secret,id=pypi_token,dst=/root/.pypi-token \
    export UV_PUBLISH_TOKEN=$(cat /root/.pypi-token) && \
    uv sync --frozen --no-dev --no-project
```

**知名开源项目基础镜像选型对照**：

| 项目 | 语言 | dev/test → prod 选型 | 理由 |
| ---- | ---- | -------------------- | ---- |
| Kubernetes Dashboard | Go | `golang:bookworm` → `distroless/static-debian12:nonroot` | Go 静态编译，prod 直接 distroless |
| GitLab CE | Ruby+Go | 自构多阶段 builder → `debian:bookworm-slim` | 依赖多，distroless 跑不起来 |
| FastAPI 官方示例 | Python | `python:3.12-slim-bookworm` → 可选 alpine | 官方推荐 slim，alpine 仅镜像大小刚需时用 |
| Spring Boot 官方模板 | Java | `eclipse-temurin:17-jdk` → `eclipse-temurin:17-jre` 或 distroless java17 | 官方 JRE 比 Alpine musl JDK 稳定 |

**一句话结论**：你采用的「dev/test slim + stage/prod distroless」分层方案，与 Kubernetes Dashboard、Spring 官方模板的选型思路完全一致。

> **生产级踩坑与操作优化**（HEALTHCHECK 误用、Secret 被历史读出、alpine musl 编译翻车、USER/distroless 切换报错等常见坑）统一收录于 **6.8.1**。

## 6.3 Trivy 漏洞扫描（双位置）

> 完整的扫描工具选型对比参见 [S9 质量安全扫描集成](./补充专题/S9-质量安全扫描集成.md)。本节聚焦 Trivy 在 GitLab CI 里的双位置扫描配置。

### 6.3.1 Trivy 扫描原理与扫描类型

Trivy 是 2026 最主流的漏洞扫描工具（Aqua Security 出品，CNCF 项目），一个工具覆盖：

| 扫描类型 | 扫什么 | 什么时候扫 | 本章小节 |
| -------- | ------ | ---------- | -------- |
| **FS（文件系统）** | 项目目录里的依赖锁文件（uv.lock / pom.xml / package-lock.json） | Build 前 | 6.3.2 |
| **Image（镜像）** | 构建出来的容器镜像（OS 包 + 应用依赖，含传递依赖） | Build 后 / Push 前 | 6.3.3 |
| **Repo（代码仓）** | IaC 配置错误（Dockerfile / K8s YAML） | 任意位置 | — |
| **Config** | K8s / Docker / Terraform 配置安全 | 任意位置 | — |

**为什么需要双位置扫描**：
- FS 扫描快（不构建镜像），能在 Build 前就发现问题
- Image 扫描更全面（包含 OS 包漏洞 + 传递依赖），但需要先构建镜像

**语言差异（FS 扫描覆盖度）**：

| 语言 | FS 扫描全不全 | 原因 |
| ---- | ------------- | ---- |
| **Python** | ✅ 比较全 | `uv.lock` / `poetry.lock` 包含所有依赖（含传递依赖），锁定版本 |
| **Java** | ⚠️ 不全 | `pom.xml` 只声明直接依赖，传递依赖看不到（除非用 `mvn dependency:tree` 导出） |
| **Node.js** | ✅ 比较全 | `package-lock.json` 包含完整依赖树 |

> 所以 Java 项目尤其需要双位置扫描：FS 扫描只能发现直接声明的依赖漏洞，传递依赖引入的漏洞必须靠 Image 扫描才能发现。Python 因为 lockfile 包含完整依赖树，FS 扫描覆盖度更高，但 Image 扫描还能额外发现 OS 包漏洞，所以两个都要。

**Log4j 漏洞的例子**：Log4Shell（CVE-2021-44228）
- 如果 pom.xml 直接写了 log4j → FS 扫描能发现
- 如果通过传递依赖引入（项目 pom.xml 没写 log4j，但某个库 A 依赖它）→ FS 扫描发现不了，必须 Image 扫描（镜像里有 log4j-core-2.14.1.jar）才能发现

### 6.3.2 文件系统扫描（Build 前）

```yaml
# .gitlab-ci.yml
trivy:fs:
  stage: test              # 放在 test stage，Build 前就跑
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  script:
    # 扫描项目目录（读 uv.lock / pom.xml 等锁文件）
    - trivy fs --severity HIGH,CRITICAL --exit-code 1 --format json --output trivy-fs-report.json .
  artifacts:
    when: always
    reports:
      dependency_scanning: trivy-fs-report.json
  allow_failure: false     # HIGH/CRITICAL 漏洞 → 阻断 Build
```

### 6.3.3 镜像扫描（Build 后 / Push 前，硬阻断）

```yaml
# .gitlab-ci.yml
trivy:image:
  stage: build             # 放在 build stage，镜像构建后、推送前
  needs:
    - build                # 等 build job 构建出镜像
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  variables:
    IMAGE_REF: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  script:
    # 方式一：镜像已在本地 docker daemon（docker build 场景）
    - trivy image --severity HIGH,CRITICAL --exit-code 1 --format json --output trivy-image-report.json $IMAGE_REF

    # 方式二：Kaniko 构建场景（镜像不在本地 daemon，需要先导出 tar）
    # Kaniko 构建时加 --no-push --tar-path /tmp/image.tar
    # - trivy image --input /tmp/image.tar --severity HIGH,CRITICAL --exit-code 1
  artifacts:
    when: always
    reports:
      container_scanning: trivy-image-report.json
  allow_failure: false     # HIGH/CRITICAL 漏洞 → 阻断推送
```

> **Kaniko 场景特别注意**：Kaniko 不启动 docker daemon，Trivy 无法用 `trivy image <ref>` 直接扫。两种解法：
> 1. Kaniko 构建时加 `--no-push --tar-path /tmp/image.tar`，Trivy 用 `--input` 扫 tar 包
> 2. 先推到镜像仓的临时 tag，Trivy 扫完再决定是否保留（多了网络开销）

### 6.3.4 .trivyignore 与严重级别策略

**策略表**：

| 严重级别 | 处理方式 | allow_failure | 说明 |
| -------- | -------- | :---: | ---- |
| CRITICAL | 硬阻断 | false | 必须修才能过 |
| HIGH | 硬阻断 | false | 必须修才能过 |
| MEDIUM | 软告警 | true | 不阻断但报告 |
| LOW | 仅报告 | true | 只记录不告警 |

**.trivyignore 文件**（项目根目录，排除已知误报或暂不修的漏洞）：

```
# CVE-2024-12345：已知误报，当前版本不受影响
CVE-2024-12345

# CVE-2024-67890：上游暂未修复，已开 Ticket 跟踪
CVE-2024-67890
```

> **注意**：.trivyignore 要定期 review，每条都要有注释说明"为什么不修 + 什么时候修"。不要变成"永久忽略列表"。

> **生产落地操作与踩坑**（漏洞库缓存、SLA 分级、给开发者修复指引、Java 项目提高 FS 扫描覆盖度）统一收录于 **6.8.2**。

## 6.4 镜像仓库选型与接入

### 6.4.1 三大镜像仓选型与演进路径

> 完整对比参见 [S11 包仓库](./补充专题/S11-包仓库Nexus-Harbor-GitLabRegistry.md)。这里只给选型结论 + 演进路径 + 职责划分。

**表 6-4：选型速查**

| 场景 | 推荐方案 | 理由 |
| ---- | -------- | ---- |
| **你已经在用 GitLab CI**（读者场景） | GitLab Container Registry | 零成本，一体化，`$CI_REGISTRY_IMAGE` 直接用 |
| 镜像安全要求高（Cosign / 复制 / CVE 扫描） | Harbor | 镜像仓能力最强 |
| 需要代理公共源（Maven/PyPI/npm 缓存） | Nexus 3 | 代理能力强 |
| 大团队全栈 | Harbor（镜像）+ Nexus（包） | 各取所长 |

#### 镜像仓演进路径（小团队 → 团队增长）

**阶段 1：小团队（1 个机房，镜像 < 1 万 tag）**

```
Nexus           → Maven/PyPI/npm 代理 + jar/wheel/npm 制品存储
GitLab Registry → 容器镜像 + Helm Chart
```

- GitLab Registry 零成本，`$CI_JOB_TOKEN` 自动认证
- 镜像 CVE 扫描用 CI 里的 Trivy 覆盖（不依赖镜像仓内置扫描）
- Cosign 签名 GitLab Registry 也支持
- 不可变标签 GitLab Registry 也支持
- **唯一短板**：无多地域复制（单机房不是问题）

**阶段 2：团队增长（仍 1 个机房，镜像 < 1 万 tag）**

- 不用换，继续 GitLab Registry
- 加保留策略清理旧镜像就行

**阶段 3：多机房 / 合规要求 / 镜像爆炸**

```
Nexus           → Maven/PyPI/npm 代理 + jar/wheel/npm 制品存储（不变）
Harbor          → 容器镜像 + Helm Chart（替代 GitLab Registry）
```

**什么时候该从 GitLab Registry 切换到 Harbor**（4 个信号，满足 2 个就值得切）：

| 信号 | 说明 | GitLab Registry 能不能扛 |
| ---- | ---- | ----------------------- |
| 多机房 / 多地域 | 需要镜像同步到多个机房 | ❌ GitLab Geo 是全量同步，太重 |
| 镜像数量爆炸 | > 1 万个 tag，需要精细的保留策略 + 配额 | ❌ GitLab Registry 策略较弱 |
| 合规要求镜像签名验证 | 部署前必须验证 Cosign 签名，Harbor 原生集成 | ⚠️ GitLab 支持但不如 Harbor 顺 |
| 镜像安全策略前置 | 要求"未扫描通过的镜像不能 Push"或"未签名不能 Pull" | ❌ GitLab 做不到 Push 前阻断 |

**Harbor 独有的 3 个能力**（GitLab Registry 给不了的）：

1. **Push 前扫描策略**：配"CVE CRITICAL > 0 则拒绝 Push"，镜像根本进不了仓
2. **多地域复制**：Pull-based 复制，只同步需要的镜像，不是全量
3. **配额管理**：按项目设镜像数量 / 总大小上限，防止某个团队把仓撑爆

> **不一定要切 Harbor**：如果团队永远只有一个机房、镜像数量不大、没有合规强制要求，GitLab Registry 一直用下去也没问题。切 Harbor 的成本（部署 + 运维 + CI 改配置）要和收益对等。

#### Nexus 与镜像仓的职责划分原则

**核心原则**：让 Nexus 专注做包仓（它最强），镜像交给专业的镜像仓。不要让 Nexus 越界做它不擅长的事。

| 职责 | Nexus | GitLab Registry / Harbor |
| ---- | :---: | :----------------------: |
| Maven/PyPI/npm 代理公共源 | ✅ 最强 | ⚠️ GitLab 支持 / ❌ Harbor 不支持 |
| jar/wheel/npm 制品存储 | ✅ 最全（25+ 格式） | ⚠️ 主流格式 |
| 容器镜像存储 | ⚠️ 能用但短板多 | ✅ 专业 |
| 镜像 CVE 扫描 | ❌ 需商业版 | ✅ 内置 |
| Cosign 签名集成 | ❌ 不强支持 | ✅ 支持 |
| 多地域复制 | ❌ 商业版 | ✅ 支持 |

> 有些团队为了"少维护一套系统"让 Nexus 既存包又存镜像。这个可以，但要接受 Nexus 镜像仓的 4 个短板（无内置扫描 / 无签名 / 无不可变标签 / 无多地域复制）。**推荐分工：Nexus 管包，镜像仓管镜像**。

### 6.4.2 GitLab Container Registry 接入

GitLab 内置 Registry，**零配置**，开箱即用：

```yaml
# .gitlab-ci.yml（Kaniko 推送到 GitLab Registry）
variables:
  # GitLab 自动注入的变量，不用自己配
  # $CI_REGISTRY = registry.gitlab.cn
  # $CI_REGISTRY_IMAGE = registry.gitlab.cn/mygroup/myproject
  # $CI_REGISTRY_USER = gitlab-ci-token
  # $CI_REGISTRY_PASSWORD = $CI_JOB_TOKEN（自动过期）
  IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

build:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile Dockerfile
      --destination $IMAGE_TAG
      --cache=true
      --cache-repo $CI_REGISTRY_IMAGE/cache
```

**GitLab Registry 的优势**：
- `CI_JOB_TOKEN` 自动认证，不用配 Secret
- 与 GitLab MR / 环境 / 审计一体化
- 支持不可变标签（项目设置里开启）

**GitLab Registry 的短板——不支持代理公共镜像（CE 版）**：
- GitLab Dependency Proxy 功能只在 **Premium/Ultimate 版**提供，且只代理 Docker Hub（不支持 GCR / 其他 Registry）
- GitLab CE（开源版）**完全不支持**镜像代理
- 如果用 GitLab CE，CI 拉公共镜像走 Docker Hub 直连，可能遇到 Rate Limit（匿名 100 次/6 小时）
- **解法**：搭配 Nexus 或 Harbor 做镜像代理仓（详见 6.4.5 三仓代理对比）

### 6.4.3 Harbor 接入（高级功能补充）

Harbor 提供 GitLab Registry 没有的高级功能：**镜像复制（多地域同步）** + **Cosign 原生集成** + **漏洞扫描策略**。

```yaml
# .gitlab-ci.yml（推送到 Harbor）
variables:
  HARBOR_URL: "harbor.example.com"
  HARBOR_PROJECT: "myteam"
  IMAGE_TAG: "$HARBOR_URL/$HARBOR_PROJECT/myapp:$CI_COMMIT_SHORT_SHA"

build:harbor:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  before_script:
    # Harbor 认证：用 CI 变量配置 Harbor 的 Service Account
    - echo "{\"auths\":{\"$HARBOR_URL\":{\"auth\":\"$(echo -n $HARBOR_USER:$HARBOR_PASSWORD | base64)\"}}}" > /kaniko/.docker/config.json
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile Dockerfile
      --destination $IMAGE_TAG
```

> Harbor 的完整部署与配置参见 [S11 包仓库](./补充专题/S11-包仓库Nexus-Harbor-GitLabRegistry.md) 的 Harbor 部分。

**Harbor 的代理公共镜像能力**：Harbor 2.0+ 支持 Proxy Cache 项目类型，可以代理 Docker Hub / GCR / 其他 Harbor 等外部 Registry。配置方式：新建项目时选择"Proxy Cache"类型，填入目标 Registry 地址即可。CI 拉公共镜像时用 Harbor 的 Proxy Cache 项目地址替代 Docker Hub。详见 6.4.5 对比表。

### 6.4.4 Nexus 接入（通用制品仓 + 镜像仓）

> Nexus 的核心定位是**通用制品仓**（25+ 格式），镜像仓只是其中一项能力。如果团队同时需要 Maven/PyPI/npm 代理 + 镜像存储，Nexus 是一站式选择。

#### Nexus 镜像仓 vs GitLab Registry / Harbor 的差异

| 维度 | Nexus 镜像仓 | GitLab Registry | Harbor |
| ---- | ------------ | --------------- | ------ |
| 镜像 push/pull | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| CVE 漏洞扫描 | ❌ 需商业版 Nexus IQ | ✅ 内置 Trivy | ✅ 内置 Trivy/Clair |
| Cosign 签名 | ❌ 不强支持 | ✅ 支持 | ✅ 原生支持 |
| 多地域复制 | ❌ 商业版 | ✅ GitLab Geo | ✅ 原生支持 |
| **代理公共源** | ✅ **最强**（Maven/PyPI/npm/Go 全覆盖） | ✅ 支持 | ❌ 不支持 |
| **非镜像制品**（jar/wheel/npm） | ✅ **最全**（25+ 格式） | ✅ 主流格式 | ❌ 有限 |

**结论**：如果只存镜像，Nexus 不是最优选（Harbor/GitLab Registry 更强）。但如果团队已经有 Nexus 做 Maven/PyPI 代理，**顺便用它存镜像**是合理的——少维护一套系统。

#### Nexus 镜像仓的 Repository 类型

Nexus 镜像仓用 Docker 格式，分三种 Repository 类型：

| 类型 | 作用 | 类比 |
| ---- | ---- | ---- |
| **hosted** | 自己 push 上去的镜像存储 | 私有仓 |
| **proxy** | 代理 Docker Hub / 其他 Registry，缓存拉取的镜像 | 代理仓 |
| **group** | 把 hosted + proxy 组合成一个入口 | 统一入口 |

#### Kaniko 推送到 Nexus 镜像仓

```yaml
# .gitlab-ci.yml（推送到 Nexus Docker hosted 仓）
variables:
  # Nexus 镜像仓地址（Nexus 管理员配置的 Docker hosted repository 端口）
  NEXUS_REGISTRY: "nexus.example.com:8082"
  NEXUS_PROJECT: "myteam"
  IMAGE_TAG: "$NEXUS_REGISTRY/$NEXUS_PROJECT/myapp:$CI_COMMIT_SHORT_SHA"

build:nexus:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  before_script:
    # Nexus 认证：用 CI 变量配置 Nexus 的 Service Account
    - echo "{\"auths\":{\"$NEXUS_REGISTRY\":{\"auth\":\"$(echo -n $NEXUS_USER:$NEXUS_PASSWORD | base64)\"}}}" > /kaniko/.docker/config.json
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile Dockerfile
      --destination $IMAGE_TAG
      --cache=true
      --cache-repo $NEXUS_REGISTRY/$NEXUS_PROJECT/cache
```

#### Nexus 代理仓加速拉取公共镜像

Nexus 的 proxy repository 可以缓存 Docker Hub 的镜像，CI 里拉公共镜像（如 `python:3.12-slim`）走 Nexus 代理，不用每次都去 Docker Hub。配置方式见 6.4.5 三仓代理对比，Kaniko 中具体怎么配见 **6.6.2**（通过 `registry-mirrors` 配置，不用改 Dockerfile）。

#### Nexus 镜像仓的局限性

| 局限 | 说明 | 解法 |
| ---- | ---- | ---- |
| 无内置 CVE 扫描 | Nexus 开源版不支持镜像漏洞扫描 | 在 CI 里用 Trivy Image 扫描（见 6.3.3） |
| 无 Cosign 签名集成 | Nexus 不支持签名验证 | 在 CI 里用 Cosign 签名 + 部署前 verify（见 6.5） |
| 无不可变标签 | Nexus 不原生支持 tag 锁定 | 用保留策略 + 命名规范管理（见 6.4.6） |
| 无多地域复制 | 开源版不支持 | 商业版或用 Harbor 补充 |

> Nexus 的完整部署与配置（三种 Repository 配置 + 代理公共源 + 权限管理）参见 [S11 包仓库](./补充专题/S11-包仓库Nexus-Harbor-GitLabRegistry.md) 的 Nexus 部分。

### 6.4.5 三仓代理公共镜像能力对比

> "代理公共镜像"= 缓存 Docker Hub / GCR 等外部 Registry 的镜像，CI 拉公共镜像走本地代理，不每次都去外网，同时避免 Docker Hub Rate Limit。

**表 6-5：三镜像仓代理公共镜像能力对比**

| 能力 | Nexus | Harbor | GitLab Registry |
| ---- | ----- | ------ | --------------- |
| **代理外部镜像仓** | ✅ Proxy Repository（最强，支持任何 Registry） | ✅ Proxy Cache 项目（2.0+，支持 Docker Hub / GCR / 其他 Harbor） | ⚠️ Dependency Proxy（仅 Premium/Ultimate 版，只代理 Docker Hub） |
| **代理 Maven/PyPI/npm 等非镜像包** | ✅ **最强**（25+ 格式全覆盖） | ❌ 不支持 | ✅ 支持（Maven/PyPI/npm/Conan 等） |
| **缓存命中后拉取速度** | 快（本地缓存） | 快（本地缓存） | 快（本地缓存） |
| **免 Docker Hub Rate Limit** | ✅ | ✅ | ✅ |
| **配置复杂度** | 中（配 proxy repo + group） | 低（创建 Proxy Cache 项目即可） | 低（开启 Dependency Proxy 即可，但需 Premium） |
| **开源版可用** | ✅ | ✅ | ❌ 需 Premium/Ultimate |

**结论**：

- **Nexus**：代理能力最全面，镜像 + 包都能代理，开源版即可用。如果团队需要同时代理 Maven/PyPI/npm + Docker Hub，Nexus 是唯一选择。
- **Harbor**：镜像代理能力够用（Proxy Cache 项目），配置简单。如果只代理 Docker Hub / GCR 镜像，Harbor 完全可以替代 Nexus 的镜像代理功能。
- **GitLab Registry**：Dependency Proxy 只在 Premium 版提供，且只代理 Docker Hub。如果是 GitLab CE（开源版），**不支持**镜像代理。这是 GitLab Registry 的一个明显短板。

> **对小团队的实际影响**：如果用 GitLab CE（免费版），拉公共镜像走 Docker Hub 直连，可能遇到 Rate Limit（匿名 100 次/6 小时，认证 200 次/6 小时）。解决方案：
> 1. 用 Nexus 或 Harbor 做代理仓（推荐）
> 2. 给 Kaniko 配 Docker Hub 账号认证（`docker login`），提高 Rate Limit 上限
> 3. 把常用基础镜像预推到 GitLab Registry（手动同步，维护成本高）

### 6.4.6 不可变标签与保留策略

**什么是不可变标签**：同一个 tag 名（如 `v1.2.3`）一旦被推送到镜像仓，任何人/任何 CI Job 都不能用相同的 tag 名覆盖它。第二次 push `v1.2.3` 会被仓库直接拒绝。

**表 6-6：默认行为 vs 开启不可变标签**

| 行为 | 默认（可变标签） | 不可变标签（开启后） |
| ---- | --------------- | ------------------- |
| 第一次 push `v1.2.3` | ✅ 成功 | ✅ 成功 |
| 第二次 push `v1.2.3`（相同/不同内容） | ✅ **覆盖**（静默替换） | ❌ **拒绝**（报错） |
| 风险 | 线上跑的 v1.2.3 被悄悄换了内容 | 不会被换 |

**为什么必须开**：

```
场景：你打了 tag v1.2.3 发版到生产，跑得好好的。
      某人（或 CI bug）又 push 了一次 v1.2.3（内容变了）。
      此时如果需要回滚到 v1.2.3 → 拉到的已经是被覆盖的新镜像，不是原来发版的那个。
      → 回滚失效，事故。
```

开了不可变标签后，第二次 push 直接报错，从根上杜绝这个问题。

**配置位置**：
- GitLab Registry：项目设置 → General → Visibility → "Container Registry tag immutability"
- Harbor：项目配置 → 策略 → 不可变标签规则（支持正则匹配，如 `v\d+\.\d+\.\d+`）

> **与 P1.1 实践的关联**：你的 P1.1 实践里 dev/test 用 commit SHA（如 `app:abc1234`），SHA 天然唯一不会被覆盖，不需要额外保护；prod 用版本 Tag（如 `v1.2.3`），**必须开不可变标签**，防止发版 tag 被覆盖导致回滚失效。

**保留策略**（自动清理旧镜像）：

| 策略 | 示例 | 说明 |
| ---- | ---- | ---- |
| 保留最近 N 个 | 保留最近 30 个 tag | 超过 30 个的自动删除 |
| 保留最近 N 天 | 保留最近 90 天 | 90 天前的自动删除 |
| 按正则保留 | `v\d+\.\d+\.\d+` 永久保留 | 发版 tag 永不删 |

> **建议**：dev/test 镜像保留 30 天或 50 个；生产发版 tag（`v*`）永久保留。

> **生产运维踩坑**（Proxy Cache TTL、不可变标签正则、Pull-based 复制、配额、Nexus Blob Store 分离、Compact 任务、GitLab Runner 全局 registry-mirrors）统一收录于 **6.8.3**。

## 6.5 SBOM 生成与镜像签名

> 完整的 SBOM 格式对比、Cosign 三种签名模式、GitHub Actions 完整示例参见 [S4 供应链安全 SBOM](./补充专题/S4-供应链安全SBOM.md)。本节聚焦 GitLab CI 集成。

### 6.5.1 SBOM 与 Cosign 概念速览

#### SBOM 是什么（镜像的"配料表"）

**SBOM（Software Bill of Materials，软件物料清单）**= 镜像的"配料表"。

一个镜像看起来是一个 Python 应用，但实际里面有：

```
app:1.0.0 镜像配料表（SBOM）
├── 操作系统层
│   ├── debian 12.5
│   ├── openssl 3.0.13        ← 这个可能有 CVE
│   ├── libcurl 8.4.0
│   └── ca-certificates 20240101
├── Python 运行时
│   └── python 3.12.3
├── 应用依赖（pyproject.toml 声明的）
│   ├── fastapi 0.111.0
│   ├── pydantic 2.7.0
│   └── uvicorn 0.30.0
└── 传递依赖（你没声明但自动装的）
    ├── starlette 0.37.0      ← fastapi 依赖它
    ├── anyio 4.3.0           ← starlette 依赖它
    └── h11 0.14.0            ← anyio 依赖它
```

**SBOM 的两个核心用途**：

| 用途 | 说明 |
| ---- | ---- |
| **漏洞快速定位** | 新 CVE 爆发时，拿 CVE 号去 SBOM 库里搜，秒级定位受影响镜像 |
| **合规审计** | 客户/监管要求你证明"这个版本上线时镜像里有什么"，SBOM 就是证据 |

**没有 SBOM 时的痛点**：Log4Shell 爆发时，很多团队的第一个问题是"我们的镜像里到底有没有 log4j？哪个版本？"——答不上来，只能一个一个镜像 `find / -name "log4j*"`，耗时几天。有 SBOM 后 3 秒查出。

#### Cosign 是什么（镜像的"防伪章"）

**Cosign = 给镜像盖"防伪章"**，证明这个镜像是你的 CI 构建的，没被篡改。

**没有签名时的风险**：

```
攻击路径：黑客拿到镜像仓密码
  → 推一个恶意镜像，tag 名也叫 v1.2.3（如果没开不可变标签）
  → 或者推一个 v1.2.4（看起来像正常发版）
  → 部署系统拉到恶意镜像 → 运行挖矿程序
  → 你以为是正常发版，根本不知道镜像被换了
```

**有签名后**：

```
构建端（CI）                          部署端（K8s/服务器）
  镜像 build                            拉镜像
  ↓                                      ↓
  Cosign sign（私钥签名）                Cosign verify（公钥验证）
  ↓                                      ↓
  镜像 + 签名推到仓库                    ✅ 验证通过 → 部署
                                        ❌ 验证失败 → 拒绝（镜像可能被篡改）
```

**Cosign 三种签名模式**（从简单到高级）：

| 模式 | 原理 | 适合场景 |
| ---- | ---- | -------- |
| **Key 签名** | 你保管一对密钥，私钥签名、公钥验证 | 小团队，最简单 |
| **Keyless 签名** | 不用管密钥，用 CI 的 OIDC Token 自动签名（GitLab/GitHub 短期证书） | 中大团队，密钥不用人管更安全 |
| **KMS 签名** | 密钥托管在云 KMS（AWS KMS / GCP KMS），调用 API 签名 | 大企业，有合规要求 |

#### SBOM 和 Cosign 各管各的

| | SBOM | Cosign 签名 |
|--|------|-------------|
| 输出物 | JSON 文件（配料表） | 签名数据（防伪章） |
| 存哪里 | Dependency-Track（专用平台） | 镜像仓（OCI 附件） |
| 解决什么 | "出事了知道谁受影响" | "部署的镜像是不是我的" |
| 查询方式 | 在 Dependency-Track 里按 CVE 搜 | 部署时 Cosign verify |

### 6.5.2 SBOM 生成（Syft）

```yaml
# .gitlab-ci.yml
sbom:
  stage: build
  needs:
    - build            # 镜像构建完后生成 SBOM
  image:
    name: anchore/syft:latest
    entrypoint: [""]
  variables:
    IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  script:
    # 扫镜像生成 CycloneDX 格式 SBOM
    - syft $IMAGE_TAG -o cyclonedx-json > sbom.json
    # 上传到 Dependency-Track（详见 6.5.5）
    - |
      curl -X POST "$DT_URL/api/v1/bom" \
        -H "X-Api-Key: $DT_API_KEY" \
        -H "Content-Type: application/json" \
        -d "{\"project\":\"$DT_PROJECT_ID\",\"bom\":\"$(base64 sbom.json)\"}"
  artifacts:
    paths:
      - sbom.json
    expire_in: 90 days   # SBOM 至少保留 90 天（合规要求）
```

### 6.5.3 Cosign 签名

> Cosign 三种签名模式（Key / Keyless / KMS）的完整对比参见 [S4.4.2](./补充专题/S4-供应链安全SBOM.md)。

**GitLab CI 用 Keyless 签名（OIDC，2026 推荐）**：

```yaml
# .gitlab-ci.yml
sign:
  stage: build
  needs:
    - build            # 镜像构建完后签名
  image:
    name: gcr.io/projectsigstore/cosign:latest
    entrypoint: [""]
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com    # GitLab OIDC audience
  variables:
    IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  before_script:
    # 用 GitLab OIDC Token 换取 Sigstore 证书
    - cosign login $CI_REGISTRY -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD
  script:
    # Keyless 签名：用 OIDC Token，不需要管理密钥
    - cosign sign --yes --identity-token="$GITLAB_OIDC_TOKEN" $IMAGE_TAG
  rules:
    # 只有打 Tag 才签名（生产镜像才签）
    - if: $CI_COMMIT_TAG
```

**Key 签名（自管密钥，企业内部用）**：

```yaml
sign:key:
  stage: build
  needs:
    - build
  image: gcr.io/projectsigstore/cosign:latest
  variables:
    IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  script:
    # COSIGN_PRIVATE_KEY / COSIGN_PASSWORD 从 GitLab CI masked variable 注入
    - cosign sign --key env://COSIGN_PRIVATE_KEY $IMAGE_TAG
```

> **密钥管理**：`COSIGN_PRIVATE_KEY` 必须用 GitLab CI 的 **masked + protected** 变量（参见 [04 章 4.8.2](./04-核心工具深入.md)）。更安全的做法是用 KMS（参见 [S1 Secret 管理](./补充专题/S1-Secret管理.md)）。

### 6.5.4 签名验证门禁（部署前 verify）

```yaml
# .gitlab-ci.yml（部署前验证签名）
verify-signature:
  stage: deploy
  needs:
    - sign
  image: gcr.io/projectsigstore/cosign:latest
  variables:
    IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  script:
    # Keyless 验证：检查签名者是否是预期的 GitLab 项目
    - cosign verify $IMAGE_TAG
      --certificate-identity-regexp="https://gitlab.com/mygroup/myproject/.+"
      --certificate-oidc-issuer="https://gitlab.com"
  rules:
    - if: $CI_COMMIT_TAG    # 生产部署前才验证
  allow_failure: false       # 签名验证失败 → 阻断部署
```

### 6.5.5 SBOM 存储与持续监控（Dependency-Track）

> 6.5.2 生成的 sbom.json 只是一个 JSON 文件，**存哪里、怎么搜**才是落地的关键。只放在 GitLab artifacts 里会过期且无法搜索，必须放到专用平台。

#### SBOM 存储方案对比（从差到好）

| 方案 | 原理 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **GitLab artifacts** | sbom.json 上传到 artifacts | 零成本 | 7-30 天过期；无搜索功能 |
| **Cosign attach** | SBOM 作为 OCI 附件跟着镜像 | SBOM 和镜像绑定，删镜像就删 SBOM | 不能反向搜"哪些镜像包含 log4j" |
| **Dependency-Track** | 上传到专用 SBOM 管理平台 | 集中存储 + 反向搜索 + 持续监控 | 需要额外部署一个服务 |
| **GitLab Ultimate** | GitLab 原生 SBOM 管理 | 不用额外部署 | 需 Ultimate 版（CE/Premium 无） |

#### Dependency-Track 核心价值

| 能力 | 说明 |
| ---- | ---- |
| 集中存储 | 所有项目/镜像的 SBOM 永久存储，不过期 |
| 反向搜索 | 输入 CVE 号 → 秒级返回所有受影响的项目/镜像 |
| 持续监控 | SBOM 上传后持续用最新 CVE 库匹配，**不是生成时扫一次就完了** |
| 漏洞告警 | 新 CVE 发布 → 自动匹配已存储的 SBOM → 主动告警 |
| 可视化 | 每个项目的依赖树、漏洞数、风险趋势 |

**持续监控 vs Trivy 一次性扫描**（关键区别）：

```
Trivy 扫描（Build 时）：
  Build 时 log4j 2.14.1 没有 CVE → 扫描通过 → 镜像发布
  3 个月后 Log4Shell 爆发
  → Trivy 不会重新扫已发布的镜像（只在 Build 时扫）
  → 你不知道线上镜像受影响

Dependency-Track（持续监控）：
  SBOM 上传时 log4j 2.14.1 没有 CVE → 记录
  3 个月后 Log4Shell 爆发
  → Dependency-Track 自动用新 CVE 库匹配已存储的 SBOM
  → 主动告警："你的 5 个镜像包含 log4j 2.14.1，受 CVE-2021-44228 影响"
  → 你第一时间知道
```

#### Dependency-Track 部署（小团队吃得消）

**资源需求**：

```
Docker Compose 起三个容器：
  - dependency-track-apiserver：2C / 4G
  - dependency-track-frontend：  0.5C / 0.5G
  - postgres：                   1C / 2G

存储：PostgreSQL 5-10GB

总成本：一台 4C/8G 机器，和 GitLab Runner / Nexus 混部也行
```

**对比已有服务的资源量**：

| 服务 | 大致资源 | 运维复杂度 |
| ---- | -------- | ---------- |
| GitLab CE | 4C/8G+ | 中 |
| Nexus | 2C/4G | 低 |
| **Dependency-Track** | **2C/4G** | **低（和 Nexus 差不多）** |

**部署方式**：一个 `docker-compose.yml` 搞定：

```yaml
# /opt/dependency-track/docker-compose.yml
version: '3.8'
services:
  apiserver:
    image: dependencytrack/apiserver:4.x
    ports:
      - "8081:8080"
    volumes:
      - dt-data:/data
    environment:
      - ALPINE_DATABASE_MODE=external
      - ALPINE_DATABASE_URL=jdbc:postgresql://postgres:5432/dtdb
      - ALPINE_DATABASE_DRIVER=org.postgresql.Driver
      - ALPINE_DATABASE_USERNAME=dt
      - ALPINE_DATABASE_PASSWORD=${DT_DB_PASSWORD}

  frontend:
    image: dependencytrack/frontend:4.x
    ports:
      - "8080:8080"
    depends_on:
      - apiserver

  postgres:
    image: postgres:16
    volumes:
      - pg-data:/var/lib/postgresql/data
    environment:
      - POSTGRES_DB=dtdb
      - POSTGRES_USER=dt
      - POSTGRES_PASSWORD=${DT_DB_PASSWORD}

volumes:
  dt-data:
  pg-data:
```

`docker compose up -d` 即可。首次启动全量拉 NVD 漏洞库（约 1-2GB），需 20-30 分钟，之后增量更新无感。

**运维成本**：

| 事项 | 频率 | 说明 |
| ---- | ---- | ---- |
| 升级版本 | 半年一次 | Docker pull 新镜像，重启 |
| 备份 PostgreSQL | 每天 | 和备份 GitLab 一起 |
| CVE 库更新 | 自动 | Dependency-Track 自动从 NVD/OSS-Index 拉取 |
| 磁盘清理 | 不用 | SBOM 是文本 JSON，10GB 能存几千个镜像 |

#### 什么规模值得部署

| 镜像数量 | 建议 |
| -------- | ---- |
| < 5 个 | 暂时不用，Trivy + Cosign attach 够用 |
| 5-10 个 | 可以部署，ROI 开始显现 |
| **> 10 个** | **建议部署**，手动查 SBOM 已经不现实 |

> 小团队判断标准：3 个以上项目 × dev/test/prod 三个镜像 = 9 个镜像，加上不同版本 = 可能 30+ 镜像。这个规模就值得部署了。

### 6.5.6 完整安全链路总结

```
CI 构建镜像
  → Trivy 扫镜像漏洞          ← 扫描"配料表里有没有坏配料"（Build 时一次性）
  → Syft 生成 SBOM            ← 生成配料表
  → Cosign 签名镜像           ← 配料表和镜像都盖防伪章
  → SBOM 上传到 Dependency-Track  ← 集中存储 + 持续监控
  → 镜像推到 Registry

部署时：
  → Cosign verify 验证签名    ← 确认防伪章是真的
  → 部署

日常运维：
  → Dependency-Track 持续监控 CVE  ← 新 CVE 爆发主动告警
```

| 环节 | 工具 | 解决什么 |
| ---- | ---- | -------- |
| 漏洞扫描（Build 时） | Trivy | 镜像构建时检查已知漏洞 |
| 物料清单 | Syft | 生成镜像配料表 |
| 镜像签名 | Cosign | 证明镜像没被篡改 |
| SBOM 存储 + 持续监控 | Dependency-Track | 新 CVE 爆发时秒级定位受影响镜像 |
| 签名验证（部署前） | Cosign verify | 没签名的镜像不能部署 |

> **生产落地运维要点**（Project+Version 与 P1.1 对齐、Prometheus 告警规则、4 角色权限划分、每周邮件 Digest）统一收录于 **6.8.4**。

## 6.6 Kaniko 镜像构建与推送全流程

### 6.6.1 Kaniko vs DinD + 不依赖 K8s + 执行流程

| 方案 | 原理 | 安全性 | 性能 | 2026 状态 |
| ---- | ---- | ------ | ---- | --------- |
| **Kaniko** | 在容器内部模拟 Docker Build，不需要 docker daemon | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | GitLab CI 首选 |
| docker-in-docker（DinD） | 启动一个 docker daemon 容器 | ⭐⭐（需要 privileged） | ⭐⭐⭐ | 仍可用但不推荐 |
| BuildKit（buildx） | Docker 官方推荐 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 速度最快，但 GitLab Runner 支持 Kaniko 更成熟 |

**Kaniko 核心优势**：不需要 `privileged` 模式的 Runner，安全性更好。这在共享 Runner 环境下非常重要。

#### Kaniko 不依赖 K8s

**常见误解**：Kaniko 是 K8s 专属工具。

**实际**：Kaniko 本质就是一个容器镜像（`gcr.io/kaniko-project/executor`），在任何能跑 Docker 容器的地方都能用：

| 环境 | 能不能用 Kaniko | 说明 |
| ---- | :---: | ---- |
| K8s + GitLab Runner (Kubernetes executor) | ✅ | 最常见，Kaniko 在 K8s Pod 里跑 |
| **普通服务器 + GitLab Runner (Docker executor)** | ✅ | **小团队场景**，Runner 在 Docker 容器里跑 Kaniko 镜像 |
| 普通服务器 + Shell executor | ⚠️ 能用但没必要 | Shell executor 直接装 Docker 就能 build |

**小团队 GitLab CE + Docker 直接用**，Runner 配置不需要开 privileged：

```toml
# /etc/gitlab-runner/config.toml
[[runners]]
  name = "my-runner"
  executor = "docker"          # Docker executor
  [runners.docker]
    image = "alpine:latest"
    privileged = false          # ← 不需要开 privileged，Kaniko 能跑
    volumes = ["/cache"]
```

#### Kaniko 执行流程

```
GitLab Runner 启动 Kaniko 容器
  → Kaniko 读取 Dockerfile
  → 按 Dockerfile 指令逐步执行：
      FROM python:3.12-slim    → Kaniko 拉基础镜像
      RUN uv sync              → Kaniko 在容器里装依赖（拉 PyPI 包，配了 Nexus 代理走内网）
      COPY app/ ./app/         → Kaniko 拷贝源码
  → Build 完成，得到新镜像
  → Kaniko push 到 Registry
  → Kaniko 容器销毁，所有中间产物随之消失
```

**和 docker build 的本质区别**：

```
docker build（DinD）：
  CI 容器（发指令）→ 宿主机 docker daemon（拉镜像、跑指令、生成镜像）
  → 需要 docker daemon + privileged 权限

Kaniko：
  Kaniko 容器自己干所有事（拉镜像、跑指令、生成镜像、push）
  不和宿主机的 docker daemon 交互
  → 不需要 docker daemon，不需要 privileged
```

#### Kaniko 拉基础镜像走代理仓（引用 6.4.5）

Kaniko 拉基础镜像（如 `python:3.12-slim`）默认走 Docker Hub，可能遇到 Rate Limit。配 Nexus/Harbor 代理仓（参见 6.4.5）后，通过 `registry-mirrors` 配置走内网缓存，Dockerfile 不用改。具体配置见 6.6.2 的 `before_script` 部分。

### 6.6.2 Kaniko 完整 GitLab CI 配置

```yaml
# .gitlab-ci.yml（Kaniko 完整配置：镜像代理 + 构建 + 缓存 + 多环境 BASE_IMAGE + 推送）
build:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  variables:
    # 基础镜像代理仓（Nexus group 仓，参见 6.4.4 + 6.4.5）
    # 格式：http://nexus.example.com:8084
    IMAGE_MIRROR: "$NEXUS_GROUP_REGISTRY"
    # 分层方案：按环境切换 Final 基础镜像（参见 6.2.2）
    # dev/test 用 slim，stage/prod 用 distroless
    BASE_IMAGE_SLIM: "python:3.12-slim"
    BASE_IMAGE_DISTROLESS: "gcr.io/distroless/python3-debian12:nonroot"
  before_script:
    # Kaniko 认证 + 镜像代理（参见 6.4.5，不用改 Dockerfile）
    - |
      cat > /kaniko/.docker/config.json << EOF
      {
        "auths": {
          "$CI_REGISTRY": {
            "username": "$CI_REGISTRY_USER",
            "password": "$CI_REGISTRY_PASSWORD"
          }
        },
        "registry-mirrors": ["$IMAGE_MIRROR"]
      }
      EOF
  script:
    - |
      # 根据分支选择 BASE_IMAGE：dev/test 用 slim，stage/main（prod）用 distroless
      case "$CI_COMMIT_BRANCH" in
        dev|test) BASE_IMAGE="$BASE_IMAGE_SLIM" ;;
        stage|main) BASE_IMAGE="$BASE_IMAGE_DISTROLESS" ;;
        *) BASE_IMAGE="$BASE_IMAGE_SLIM" ;;
      esac

      # Tag 发版时，tag 分支不存在，CI_COMMIT_BRANCH 为空，按 prod 用 distroless
      if [ -n "$CI_COMMIT_TAG" ]; then
        BASE_IMAGE="$BASE_IMAGE_DISTROLESS"
      fi

      /kaniko/executor \
        --context $CI_PROJECT_DIR \
        --dockerfile $CI_PROJECT_DIR/Dockerfile \
        --build-arg BASE_IMAGE="$BASE_IMAGE" \
        --build-arg GIT_COMMIT=$CI_COMMIT_SHA \
        --build-arg BUILD_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ") \
        --build-arg VERSION=${CI_COMMIT_TAG:-$CI_COMMIT_SHORT_SHA} \
        --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA \
        --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG \
        --cache=true \
        --cache-dir=/cache \
        --cache-repo $CI_REGISTRY_IMAGE/cache \
        --no-push=false
  rules:
    # 只有环境分支和 Tag 才构建（对应 P1.3 实践）
    - if: $CI_COMMIT_BRANCH =~ /^(dev|test|stage|main)$/
    - if: $CI_COMMIT_TAG
```

> **Dockerfile 里不用改**：照常写 `FROM python:3.12-slim`，Kaniko 自动通过 `registry-mirrors` 走 Nexus/Harbor 代理拉基础镜像（参见 6.4.5 代理能力对比）。

**Kaniko 常见坑**：

| 坑 | 说明 | 避坑 |
| -- | ---- | ---- |
| `--mount=type=cache` 不生效 | Kaniko 不支持 BuildKit 语法 | 用 `--cache=true --cache-repo` 替代 |
| 认证文件路径不对 | Kaniko 读 `/kaniko/.docker/config.json` | `before_script` 里 echo 到这个路径 |
| 镜像太大构建超时 | Kaniko 没有层缓存或缓存命中率低 | 开 `--cache-repo` 把缓存层推到 Registry |
| `.dockerignore` 不生效 | Kaniko 默认上传整个 context | 确保项目根目录有 `.dockerignore` |
| BuildKit mount cache 失效 | Kaniko 不支持 BuildKit 的 `--mount=type=cache` | 去掉 `--mount=type=cache`，改用 GitLab CI `cache:` 缓存依赖目录（参见 05 章 5.5） |

### 6.6.3 镜像标签命名规范（P1.1 实践落地）

> 本小节是 6.2.4 标签策略的**落地命名**（6.2.4 讲"用哪种策略"，这里讲"具体叫什么名字"）。

**表 6-7：镜像标签命名规范**

| 环境 | 标签格式 | 示例 | 说明 |
| ---- | -------- | ---- | ---- |
| dev | `dev-${CI_COMMIT_SHORT_SHA}` | `dev-abc1234` | 可变，每次 push 覆盖；CI_COMMIT_SHORT_SHA 可追溯 |
| test | `test-${CI_COMMIT_SHORT_SHA}` | `test-abc1234` | 可变 |
| stage | `stage-${CI_COMMIT_SHORT_SHA}` | `stage-abc1234` | 可变 |
| prod | `${CI_COMMIT_TAG}` | `v1.2.0` | **不可变**（Tag 发版，6.4.6 要开镜像仓不可变标签保护） |
| 通用 | `${CI_COMMIT_SHORT_SHA}` | `abc1234` | 唯一标识，所有环境共用（Trace 用） |

> 对应你的 [P1.1 实践](./我的实践记录.md)：
> - 生产用 Tag 发版 → `${CI_COMMIT_TAG}` = immutable tag，必须配合 6.4.6 镜像仓不可变标签
> - dev/test/stage 用 commit SHA → 虽然名字可变，但 SHA 是唯一的，天然可追溯

**小团队完整缓存链路**（三层缓存各管一段，互不冲突）：

```
拉基础镜像：Docker Hub → Nexus/Harbor 代理仓缓存 → Kaniko 拉取       （6.4.5）
拉依赖包：  PyPI/Maven → Nexus 代理仓缓存        → UV/Maven 拉取      （05 章 5.5.3）
构建缓存：  -          → GitLab CI cache          → Runner 本地复用   （05 章 5.5）
```

> **生产构建优化与常见坑**（大镜像参数、多架构构建、.dockerignore 规范）统一收录于 **6.8.5**。

### 6.7.2 现阶段最佳实践速记（2026）

- Dockerfile 指令顺序：基础镜像 → 系统依赖 → 依赖声明 → 依赖安装 → 源码 → CMD
- 基础镜像分层方案：dev/test 用 slim（可调试），stage/prod 用 distroless（安全加固）；都是 Debian glibc，不翻车
- Trivy 双位置扫描：FS 扫描（Build 前）+ Image 扫描（Push 前），HIGH/CRITICAL 硬阻断；Java 项目 Image 扫描尤其重要
- 镜像仓分工：Nexus 管包 + 代理公共源，GitLab Registry / Harbor 管镜像
- 镜像仓演进：GitLab Registry（起步）→ 镜像数量/合规/多地域 → Harbor（补足能力）；不满足 2 个切换信号不用切
- 镜像标签：生产用 immutable（Tag / gitSHA）+ 镜像仓开不可变标签保护；dev/test 可变但带 SHA 可追溯
- SBOM 不存 artifacts，上传到 Dependency-Track 集中存储 + 持续监控（> 10 个镜像值得部署）
- Cosign 签名：Keyless（OIDC）优先，部署前 `cosign verify` 硬阻断
- Kaniko 不依赖 K8s，不用 privileged Runner；通过 `registry-mirrors` 走 Nexus/Harbor 代理，Dockerfile 不用改
- 三层缓存：基础镜像代理仓（Nexus/Harbor）+ 依赖包代理仓（Nexus）+ GitLab CI cache

## 6.8 生产常见问题与事故复盘（汇总，醒目直查）

> 本节统一汇总 6.2 ~ 6.6 所有生产落地的操作优化、真实事故复盘、运维踩坑。遇到 CI 扫不出来、镜像仓撑爆、构建慢等问题，直接来本节查，不用再翻各三级小节。

### 6.8.1 Dockerfile 生产踩坑（对应 6.2）

**常见事故 1：Secret 写进镜像层被 `docker history` 读出**
- 场景：`RUN echo DB_PWD=xxx > .env` 或 `COPY .env .` 把敏感文件打包进镜像
- 后果：`docker history --no-trunc <image>` 直接看见密码，或 `docker save` 导出层 tar 也能看到
- 解法：① Secret 全部走运行时 K8s Secret 注入 ② Build 时必须用的私钥用 `--mount=type=secret`（见 6.2.5 示例） ③ CI 扫完加一步：`docker history <image> | grep -i "password\|token\|pwd"` 兜底检测

**常见事故 2：alpine musl libc 让 numpy / grpcio 等 C 扩展在生产突然 segfault**
- 场景：dev 用 slim 测通过，prod 贪小换 alpine，C 扩展用 musl 重编行为异常
- 解法：你选定的 slim→distroless 分层方案天然避开这个坑，不要在 prod 用 alpine；纯 Python/Go 静态编译才值得考虑 alpine

**常见事故 3：distroless 无 shell + 无 HEALTHCHECK，livenessProbe 未配导致 K8s 一直重启**
- 场景：Dockerfile 写了 HEALTHCHECK（distroless 不支持）但 K8s 又忘了加 livenessProbe/readinessProbe
- 解法：① prod 的健康检查完全交给 K8s Startup + Readiness + Liveness 三探针（见 07 章 7.3.1） ② distroless 的 USER 用内置 65532 nonroot，不要自己 groupadd（distroless 没 shell / no groupadd）

### 6.8.2 Trivy 扫描生产四大操作要点（对应 6.3）

**要点 1：漏洞库缓存（每次 CI 省 2~5 分钟）**

```yaml
trivy:fs:
  stage: test
  image: { name: aquasec/trivy:latest, entrypoint: [""] }
  variables:
    TRIVY_CACHE_DIR: "$CI_PROJECT_DIR/.trivycache"
  cache:
    key: "trivy-cache-$(date +%Y-%m-%d -d 'last monday')"   # 每周强制刷新一次
    paths: [ .trivycache/ ]
  script:
    - trivy fs --skip-db-update --severity HIGH,CRITICAL --exit-code 1 .
```

**要点 2：漏洞 SLA（抓大放小，不要什么都修）**

| 级别 | 修复期限 | 超期处理 |
| ---- | -------- | -------- |
| CRITICAL | 24h P0 | 阻断发版 + hotfix |
| HIGH | 7d P1 | 阻断发版 / .trivyignore 申请延期 + 审批人 |
| MEDIUM | 30d P2 | 不阻断 + 缺陷工单 |
| LOW | 下季度 | 季度统一清理 |

**要点 3：给开发者明确的修复命令，不要只报红**
- 解析 Trivy JSON 报告的 `FixedVersion` 字段输出：
  ```
  CVE-2024-12345 fastapi 0.100.0 → 升级到 0.110.1，命令：uv add fastapi@0.110.1
  ```
- Dependency-Track 的修复建议列直接给开发者看，省去二次查资料

**要点 4：Java FS 扫描补 `mvn dependency:tree`（补传递依赖）**
```yaml
trivy:fs:java:
  image: maven:3.9-eclipse-temurin-17
  before_script:
    - mvn dependency:tree -DoutputType=text -DoutputFile=dependency-tree.txt -q
  script:
    - trivy fs --severity HIGH,CRITICAL --exit-code 1 .
```

### 6.8.3 镜像仓运维踩坑（对应 6.4，Harbor/Nexus/GitLab）

**Harbor 生产 4 条必配（出问题再补就晚了）**：

| 配置项 | 做法 | 防止什么事故 |
| ------ | ---- | ------------ |
| Proxy Cache TTL | Proxy Cache 项目 → Cache TTL = 7 天 | 镜像永不过期撑爆磁盘 |
| 不可变标签按正则 | 规则① `v\d+\.\d+\.\d+` 禁删+禁覆盖；规则② `*-prod-*` 禁覆盖 | 全局配导致 dev/test 可变 tag 推不进去 |
| Pull-based 复制 | 目标 Harbor 注册源 → 复制策略触发模式 Pull-based | Push-based 跨机房同步失败重试成本高 |
| 项目配额 | 每项目 ≤ 500GB / ≤ 2000 tag | 某团队 3 月 8000 tag 占 2TB 拖垮全仓 |

**Nexus Docker 镜像仓 3 条运维要点**：
1. Docker Blob Store 独立分一个，不和 Maven 共用（清理互相影响）
2. 每周定期 Compact Blob Store（删镜像后空间不自动释放）
3. Group 仓成员顺序：hosted 放第一位，proxy 放最后（防止同名 tag 被公共镜像覆盖）

**GitLab CE 补一条**：Runner 全局 `config.toml` 预挂 `registry-mirrors` 到 `/kaniko-config`，各项目不用在 `.gitlab-ci.yml` 重复写（2-3 个项目时可以先每个项目手写，更直观）。

### 6.8.4 Dependency-Track 运维与事故预防（对应 6.5）

**要点 1：Project + Version 与 P1.1 对齐**
```
order-service → v1.2.0 (Tag)、v1.2.1 (Tag)、dev、stage
user-service → v2.0.0、dev、stage
```
- SBOM 上传 CI 选择 `$CI_COMMIT_TAG`（Tag）或 `$CI_COMMIT_BRANCH`（dev/test/stage）做 Version

**要点 2：Prometheus 告警规则（Dependency-Track 4.x 自带 /metrics）**
```yaml
groups:
  - name: dependency-track
    rules:
      - alert: NewCriticalVulnerability
        expr: dt_project_vulnerability_severity{severity="CRITICAL"} > 0
        for: 1m
        labels: { severity: P0 }
        annotations: { summary: "项目 {{ $labels.project }} 发现 CRITICAL 漏洞" }
      - alert: TooManyHighVulns
        expr: dt_project_vulnerability_severity{severity="HIGH"} > 5
        for: 24h
        labels: { severity: P1 }
```

**要点 3：4 角色权限（防误删 SBOM 历史）**
- ADMIN（2-3 人平台/SRE）、PORTFOLIO_MANAGER（安全合规）、PROJECT_MANAGER（各 Tech Lead）、VIEWER（普通开发者默认只读）
- 不要全公司共用 admin

**要点 4：开启每周「Vulnerability Digest」邮件自动推送给 Project Manager**
- 过去一周新漏洞 + 严重级别分布 + 修复链接；避免安全团队追着业务跑

### 6.8.5 Kaniko 构建性能与常见坑（对应 6.6）

**优化 1：大镜像（>2GB）加 `--use-new-run=true --snapshot-mode=redo --ignore-var-run=true`，提速 30%+；<500MB 镜像默认参数即可**

**优化 2：多架构（2026 ARM 开发机 + x86 生产）用 `--customPlatforms=linux/amd64,linux/arm64`**
- 只在 dev 环境构建 ARM；prod 只构建 AMD64（除非生产有 ARM 节点）
- 多架构缓存命中率会降低

**优化 3：`.dockerignore` 必须写对**
```
.venv/
__pycache__/
*.pyc
.pytest_cache/
.git/
README.md
docs/
tests/
*.log
```
- 验证：`tar --exclude-from=.dockerignore -cf /tmp/ctx.tar . && du -sh /tmp/ctx.tar` → 打包后 <50MB 算合格
