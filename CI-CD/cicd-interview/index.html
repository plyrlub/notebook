    一、CI/CD 基础概念¶

    Q1. 请解释 CI、CD（持续交付）和 CD（持续部署）三者的区别 【初级】🔥¶

    参考答案要点：
    - CI（持续集成）：开发人员频繁将代码合并到主干，每次合并自动触发构建 + 测试，目标是尽早发现集成错误
    - CD（持续交付）：在 CI 基础上，保证代码始终处于可部署状态，但部署到生产需人工点击触发
    - CD（持续部署）：进一步自动化，每次通过测试的变更自动部署到生产，无需人工干预
    - 关键区别：是否需要人工 gate（交付需要，部署不需要）
    - 一句话记忆：「CI 验证能不能合，Delivery 验证能不能发，Deployment 直接发」

    对应 01 章 1.1 节

    Q2. 一条典型的 CI/CD 流水线包含哪些阶段？ 【初级】🔥¶

    参考答案要点：
    1. Source（代码提交触发）→ 2. Build（构建）→ 3. Test（测试）→ 4. Scan（安全扫描）→ 5. Package/Publish（制品入库）→ 6. Deploy to Staging → 7. E2E/验收测试 → 8. Approve（审批）→ 9. Deploy to Production → 10. Verify/Monitor

    对应 01 章「黄金八段」

    Q3. 什么是 DORA 指标？包含哪四个核心指标？ 【中级】🔥¶

    参考答案要点：

    指标 含义
    部署频率 单位时间内成功部署到生产的次数
    变更前置时间 从代码提交到运行在生产的时间
    MTTR 生产故障从发生到恢复的时间
    变更失败率 导致生产故障的变更占比
    • DORA 按四项指标分四档：Low → Medium → High → Elite
    • Elite 级典型阈值：部署频率「按需多次/天」、Lead Time「<1 小时」、MTTR「<1 小时」、变更失败率「0-15%」
    • 2023 年新增第五指标 Reliability（基于 SLO 达成度）

    对应 S3 DORA 四指标 + 10 章 10.4 节

    Q4. CI/CD 能给团队带来哪些收益？落地时常见阻力有哪些？ 【中级】¶

    参考答案要点：
    收益：缩短交付周期、降低缺陷逃逸率、标准化流程减少人肉失误、每次变更可追溯
    常见阻力：历史项目缺自动化测试、跨团队协作边界不清、流水线慢开发者抗拒、老旧单体难容器化

    Q5. 流水线「越快越好」是否一定正确？如何权衡速度与质量？ 【高级】¶

    参考答案要点：
    - 不是。盲目追求速度可能牺牲质量门、跳过测试
    - 推荐做法：分层流水线（快速反馈先行，慢任务异步并行）、fail fast（易失败检查前置）、缓存优化、质量门不可妥协
    - 用 DORA 综合评估，而非单看构建时长

    二、Git 工作流与分支策略¶

    Q6. 对比 GitFlow 与 Trunk-based Development 的核心差异 【中级】🔥¶

    参考答案要点：

    维度 GitFlow Trunk-based
    主分支 master + develop 双长生命周期分支 单一 main/trunk
    feature 分支 长，可存在数周 短，通常 <1 天
    release 分支 有独立 release 分支 无，靠 tag
    适合团队 发版周期长、企业级 高频发布、CI 成熟
    配合 CD 较难（分支多） 极佳

    对应 02 章 Git 工作流 + 我的实践记录 P1

    Q7. GitLab Flow 和 GitHub Flow 各是什么？ 【中级】¶

    参考答案要点：
    - GitHub Flow：极简，只有 main + feature 分支，PR 合并即部署
    - GitLab Flow：引入「环境分支」概念（production、pre-prod），feature → main → pre-prod → production 逐级推进
    - 复杂度：GitFlow > GitLab Flow > GitHub Flow

    Q8. 描述一次完整的 hotfix 流程 【初级】🔥¶

    参考答案要点（以 GitFlow 为例）：
    1. 从 master 拉 hotfix/xxx 分支（不是从 develop）
    2. 修复 + 测试
    3. 合并回 master（打新 tag）和 develop（保证修复不丢失）
    4. 触发生产部署流水线
    5. 删除 hotfix 分支
    - 关键：必须双向合并，推荐 --no-ff

    对应 07 章 7.4.4 main 分支回退策略

    Q9. feature 分支长期不合并会有什么问题？如何缓解？ 【中级】¶

    参考答案要点：
    问题：冲突越来越大（merge hell）、集成晚问题晚暴露、其他人相关变更难同步
    缓解：限制分支生命周期（<2 天）、每日 rebase 主干、大特性拆小、采用 Trunk-based + Feature Flag

    Q10. 什么是 monorepo？monorepo 下分支策略有何特殊考量？ 【高级】¶

    参考答案要点：
    - 多个项目/模块放在同一 Git 仓库
    - 挑战：CI 构建慢（需增量构建）、权限控制、分支规模大
    - 策略：Trunk-based + 增量 CI（按 affected paths 触发）+ Bazel/Nx/Turborepo + CODEOWNERS

    对应 10 章 10.2 节 Monorepo

    三、GitLab CI / GitHub Actions¶

    Q11. .gitlab-ci.yml 的基本结构是什么？stages、jobs、script 的关系？ 【初级】🔥¶

    参考答案要点：
    - stages 定义阶段顺序，同 stage 的 job 并行，不同 stage 串行
    - 每个 job 必须有 script，YAML 用空格缩进不能用 tab
    - job 失败默认中止后续 stage（可用 allow_failure: true 放行）

    对应 04 章核心工具深入

    Q12. GitLab Runner 是什么？shared runner 和 specific runner 区别？ 【初级】🔥¶

    参考答案要点：
    - Runner：执行 CI/CD job 的执行器
    - Shared Runner：项目级/组级共享，按 fair usage 调度
    - Specific Runner：绑定到具体项目，资源独占
    - Executor 类型：shell、docker、kubernetes、docker-machine
    - 生产推荐 kubernetes executor

    Q13. cache 和 artifacts 的区别？什么场景用哪个？ 【中级】🔥¶

    参考答案要点：

    维度 cache artifacts
    用途 加速构建（依赖包） job 产物传递给下游 job
    生命周期 跨 pipeline 可复用 默认 pipeline 结束清理
    典型场景 node_modules、.m2、pip cache 编译产物 jar、镜像 tar、测试报告
    是否可靠 不保证可用（可能被清理） 确定性产物

    对应 S10 Pipeline 最佳实践

    Q14. GitLab CI 中 rules 和 only/except 有什么区别？如何按分支触发？ 【中级】¶

    参考答案要点：
    - only/except：老语法，基于分支/tag 简单过滤，已不推荐
    - rules：新语法（GitLab 12.3+），支持 if 表达式 + changes + exists，按顺序匹配命中即停

    对应 04 章 GitLab CI rules + 我的实践记录 P1.3 触发机制

    Q15. GitHub Actions 的核心概念？workflow / job / step / action 关系？ 【初级】🔥¶

    参考答案要点：
    - Workflow（YAML 文件）→ Job（一组 step，默认并行，可用 needs 串行）→ Step（顺序执行的命令或 action）→ Action（可复用步骤单元）
    - Runner：GitHub 提供 Ubuntu/Windows/macOS 托管 runner，也支持 self-hosted
    - 触发器：push、pull_request、schedule、workflow_dispatch

    Q16. GitHub Actions 如何做矩阵构建（matrix）和缓存？ 【中级】¶

    参考答案要点：
    矩阵构建：strategy.matrix 配置多版本/多平台并行
    缓存：actions/cache@v3，key 命名推荐「OS + 依赖锁文件 hash」，命中失败回退到 restore-keys 前缀匹配

    Q17. 如何防止 CI 配置中的密钥泄漏？ 【中级】🔥¶

    参考答案要点：
    - GitLab：Settings → CI/CD → Variables，标记 Masked + Protected
    - GitHub：Settings → Secrets and variables → Actions
    - 最佳实践：密钥不入仓库、OIDC + 短期凭证、Secret Detection 扫描、定期轮换

    对应 S1 Secret 管理 + 08 章 8.4 节

    四、Docker 与容器化¶

    Q18. Dockerfile 最佳实践有哪些？ 【初级】🔥¶

    参考答案要点：
    1. 选小基础镜像（alpine/distroless/slim）
    2. 合并 RUN 指令减少 layer
    3. 指令顺序优化（不常变的放前面利用 cache）
    4. .dockerignore 排除无关文件
    5. 不跑 root（USER appuser）
    6. 用 COPY 而非 ADD
    7. 固定版本 tag 不用 latest
    8. 声明 HEALTHCHECK

    对应 06 章 Dockerfile 最佳实践

    Q19. 什么是多阶段构建？解决了什么问题？ 【中级】🔥¶

    参考答案要点：
    - 一个 Dockerfile 中多个 FROM，第一阶段编译，第二阶段只 COPY 产物
    - 解决：最终镜像不含编译器/源码/构建工具，体积小、攻击面小
    - 效果：从几百 MB 降到几十 MB

    Q20. 如何给 Docker 镜像瘦身？列举至少 5 种手段 【中级】¶

    参考答案要点：
    1. 多阶段构建 2. alpine/distroless/scratch 基础镜像 3. 合并 RUN 清理缓存 4. .dockerignore 5. 静态编译 + scratch（Go） 6. docker-slim/dive 工具 7. 不打包测试代码/文档 8. --no-cache

    Q21. Kaniko 和 Docker-in-Docker（DinD）有什么区别？K8s 中该选哪个？ 【高级】🔥¶

    参考答案要点：

    维度 DinD Kaniko
    原理 容器内跑完整 dockerd 无 daemon，用户态解析 Dockerfile
    权限 需要 --privileged（安全风险大） 不需要特权模式
    K8s 兼容 K8s 1.24+ 弃用 Docker 后需额外配置 原生支持
    安全 特权容器 = 宿主机 root 隔离好，安全

    结论：K8s 环境优先选 Kaniko

    对应 06 章 Kaniko

    Q22. Docker 镜像的分层（layer）机制是什么？对 CI 有何影响？ 【中级】¶

    参考答案要点：
    - 镜像由多个只读 layer 叠加，每条 Dockerfile 指令生成一层
    - 对 CI 影响：layer 可被 cache（指令顺序影响命中率）、push/pull 按 layer 增量传输、多镜像共享 base layer 节省存储

    Q23. 如何为生产镜像做安全加固？ 【高级】¶

    参考答案要点：
    1. distroless/scratch 基础镜像 2. 非 root 用户 3. 只读根文件系统 4. 删除 setuid/setgid 5. 镜像扫描 + 阻断高危 6. 镜像签名 + 部署时校验 7. admission controller 强制策略 8. 最小权限

    对应 06 章镜像安全 + S4 供应链安全

    五、安全与质量门禁¶

    Q24. 解释 SAST、SCA、DAST、IAST 的区别及在流水线中的位置 【中级】🔥¶

    参考答案要点：

    类型 扫描对象 阶段 工具举例
    SAST 源码/字节码 CI 阶段（最早） SonarQube, Semgrep, Bandit
    SCA 第三方依赖漏洞 CI 阶段 Snyk, Dependabot, pip-audit
    DAST 运行中的应用 Staging 部署后 OWASP ZAP, Burp Suite
    IAST 运行时（带探针） 测试阶段 Contrast

    对应 08 章 8.1.2 四类扫描

    Q25. 什么是 Secret Detection？如何在 CI 中落地？ 【中级】🔥¶

    参考答案要点：
    - 扫描代码/历史/配置中误提交的密钥
    - 工具：Gitleaks、TruffleHog、GitLab 内置
    - 落地位置：pre-commit hook → CI 流水线（fail 阻断合并）→ 全历史扫描
    - 配合 push protection 直接阻止密钥入库

    对应 08 章 8.4 节

    Q26. 什么是「安全左移」？为什么重要？ 【初级】🔥¶

    参考答案要点：
    - 把安全检查从「发布前/上线后」提前到「编码、提交、CI」早期阶段
    - 依据：缺陷越晚发现修复成本越高（NIST：生产阶段修复成本是 PR 阶段的 375 倍）
    - 实践：IDE 插件、pre-commit 钩子、PR 自动跑 SAST + SCA

    对应 08 章 8.1.1 安全左移

    Q27. 什么是 Quality Gate？如何设计？ 【中级】🔥¶

    参考答案要点：
    - 流水线中一道「是否允许继续」的判定关卡，不达标即 fail
    - 典型条件：新代码覆盖率 ≥ 80%、Bug = 0、Critical/Blocker = 0、重复率 < 3%
    - 设计原则：针对新代码（new code）而非全量，避免历史包袱阻塞；阈值循序渐进

    对应 08 章 8.5 节质量门禁设计

    Q28. 扫描出大量历史漏洞但无法立即修复，如何处理？ 【高级】¶

    参考答案要点：
    1. 分级（CVSS + 利用条件 + 暴露面）2. 基线管理（记录为安全债）3. 新代码强约束（只卡新增）4. 缓解措施（WAF/隔离）5. 逐步偿还排期 6. 例外审批流程
    - 关键：避免全量阻塞 CI 导致开发停滞

    对应 08 章 8.5.3 白名单管理 + 踩坑文档案例

    六、部署策略¶

    Q29. 对比蓝绿部署、金丝雀发布、滚动发布 【中级】🔥¶

    参考答案要点：

    策略 机制 资源占用 回滚速度 适用场景
    蓝绿 新版本整套就绪后切流量 2x 极快 数据库无关服务
    金丝雀 小比例流量先到新版，逐步扩大 1.x 倍 中 大规模服务
    滚动 一批批替换旧 Pod 1.x 倍 慢 K8s 默认策略

    对应 07 章 7.2 发布策略

    Q30. 什么是 Feature Flag？解决什么问题？ 【中级】🔥¶

    参考答案要点：
    - 通过运行时配置控制功能是否对用户可见，解耦「部署」与「发布」
    - 价值：未完成功能合并主干但隐藏、线上灰度/A/B 测试、出问题秒级关闭（kill switch）
    - 代价：代码复杂度上升、技术债需清理过期 flag

    对应 07 章 7.5 Feature Flag + S7 Feature Flag

    Q31. 什么是 GitOps？ArgoCD 如何工作？ 【高级】🔥¶

    参考答案要点：
    - GitOps：以 Git 仓库作为系统期望状态的唯一真实来源，通过声明式配置 + 自动协调让集群状态趋近期望
    - 三大支柱：声明式描述、Git 作为 SSOT、持续协调
    - ArgoCD：K8s 原生 GitOps controller，监听 Git → diff 集群状态 → 自动/手动 sync
    - 优势：审计天然、回滚即 git revert、权限收敛到 Git

    对应 07 章 7.3 GitOps

    Q32. 数据库迁移在蓝绿/金丝雀部署中有什么特殊挑战？ 【高级】¶

    参考答案要点：
    - 蓝绿两套环境共用一个数据库，schema 变更必须前向 + 后向兼容
    - 解决模式：Expand-Contract（Expand 加列 → Migrate 双写 → Contract 删旧列）
    - 避免破坏性变更一次性完成，每个迁移版本必须可独立部署

    对应 07 章 7.7 Expand-Contract + S6 数据库迁移

    Q33. 如何实现零停机部署？关键技术有哪些？ 【高级】¶

    参考答案要点：
    1. 健康检查 readinessProbe 2. 滚动更新 3. 优雅停机（SIGTERM + preStop + grace period）4. 负载均衡健康检查 5. 数据库兼容 schema 6. Feature Flag 7. 金丝雀 + 监控自动回滚

    对应 07 章零停机部署

    七、监控与可观测性¶

    Q34. 可观测性的三大支柱是什么？ 【初级】🔥¶

    参考答案要点：
    - Metrics 指标：数值时序数据（QPS/延迟/错误率），工具 Prometheus
    - Logs 日志：离散事件记录，工具 Loki / ELK
    - Traces 链路追踪：请求在分布式系统中的调用路径，工具 Jaeger / Tempo
    - 区别：监控告诉你「系统挂没挂」，可观测性告诉你「为什么挂」

    对应 09 章 9.1.2 三大支柱

    Q35. Prometheus 的数据模型和 PromQL 基础 【中级】¶

    参考答案要点：
    - 数据模型：时序数据 = metric name + labels(key=value)，每个唯一 label 组合是一条 time series
    - 四种 metric 类型：Counter（单调递增）、Gauge（可增可减）、Histogram（分桶）、Summary（分位数）
    - 采集方式：pull 模型（Prometheus 主动抓 /metrics），短任务用 Pushgateway

    对应 09 章 9.2 Prometheus

    Q36. SLI、SLO、SLA 的区别？如何设定？ 【中级】🔥¶

    参考答案要点：
    - SLI：服务等级指标（如成功率、P99 延迟）
    - SLO：对 SLI 的目标值（如成功率 99.9%/月）
    - SLA：对外合同承诺（违反赔款），通常比 SLO 更宽松
    - Error Budget：SLO=99.9% 意味着每月允许 43 分钟故障，预算耗尽应冻结发布

    对应 09 章 9.6 SLO/SLI

    Q37. 告警如何分级？避免告警风暴？ 【中级】🔥¶

    参考答案要点：
    分级：P0 电话叫醒、P1 IM+工单、P2 工单、P3 日报
    避免风暴：告警抑制（inhibit，上游挂时抑制下游告警）、分组（grouping 合并同源告警）、分级路由、基于 SLO 而非原始指标、定期 review 清理「狼来了」

    对应 09 章 9.7 告警分级 + 踩坑文档告警风暴案例

    Q38. 生产故障的标准回滚策略有哪些？ 【中级】🔥¶

    参考答案要点：
    1. 代码回滚（git revert + ArgoCD sync）2. 镜像回滚（kubectl rollout undo）3. Feature Flag 关闭（秒级）4. 数据库回滚（通常不回滚，依赖 Expand-Contract 保证兼容）5. 流量切换（蓝绿切回）
    - 黄金法则：回滚必须可重复演练，不能等真故障才第一次试

    对应 09 章 9.8 回滚策略

    Q39. Prometheus + Grafana 如何落地告警？告警链路是怎样的？ 【中级】¶

    参考答案要点：
    链路：Prometheus（采集 + 规则评估）→ Alertmanager（去重/分组/路由/静默）→ 通知渠道
    告警规则在 Prometheus 配置（PromQL + for 持续时间），Alertmanager 处理 inhibit/silence/route

    对应 09 章 9.7.2 Alertmanager

    八、实际场景题¶

    Q40. 流水线突然失败了，你的排查思路是什么？ 【中级】🔥¶

    参考答案要点：
    1. 看失败位置（哪个 stage/job/step）2. 分类原因（代码/环境/配置/外部依赖）3. 复现 4. 看变更（最近成功→失败的 commit diff）5. 判断是否阻塞 6. 修复 + 加防护

    Q41. 部署后服务起不来，如何排查（K8s 场景）？ 【中级】🔥¶

    参考答案要点：
    K8s 排查五步法：
    1. kubectl get pods 看 Pod 状态（Pending/ImagePullBackOff/CrashLoopBackOff）
    2. kubectl logs <pod> --previous 看崩溃日志
    3. kubectl describe pod 看 Events
    4. kubectl exec 进入容器排查
    5. 常见根因：配置错误、端口冲突、probe 路径错、RBAC、OOM、DB 连不上
    6. 终极手段：回滚到上一版本

    Q42. 部署后服务起来了但无法访问，怎么排查？ 【中级】¶

    参考答案要点：
    逐层排查（OSI 自下而上）：Pod running？→ Service endpoints 是否为空？→ Ingress 规则？→ NetworkPolicy？→ DNS 解析？→ 外部 LB 健康检查？→ 证书/域名？

    Q43. 数据库迁移在 CI/CD 中如何安全执行？ 【高级】🔥¶

    参考答案要点：
    核心原则：迁移脚本必须幂等、可回滚、向前兼容
    1. 工具：Flyway / Liquibase / Alembic
    2. CI 集成：迁移脚本随 PR 提交，CI 中 dry-run 校验
    3. 安全规范：禁止破坏性操作（用 Expand-Contract）、大表 DDL 在低峰执行
    4. 回滚策略：代码可回滚，schema 通常不回滚

    对应 S6 数据库迁移 + 踩坑文档数据库迁移案例

    Q44. 流水线越来越慢（从 5 分钟到 30 分钟），如何优化？ 【高级】¶

    参考答案要点：
    1. 分析瓶颈（拆 job 看每个 stage 耗时）2. 并行化（同 stage 自动并行，跨 stage 用 needs）3. 缓存（依赖/Docker layer/test cache）4. 增量构建（monorepo 按 affected paths）5. 减少 IO（--depth 1）6. runner 升级 7. 拆分快速反馈 vs 完整验证 8. BuildKit 并行构建

    对应 S2 成本与配额 + S10 Pipeline 最佳实践

    Q45. 凌晨 3 点告警：生产某服务错误率飙升，作为值班 SRE，你的处置流程？ 【高级】🔥¶

    参考答案要点：
    1. 确认告警真实性 2. 评估影响范围 3. 止损优先于根因（回滚/限流/降级）4. 拉群通报 5. 根因分析（logs/traces/metrics）6. 修复 + 验证 7. 事后复盘（Postmortem，无责备文化）
    - 关键原则：MTTR 优先，止损 > 找原因

    对应 09 章 9.8.4 回滚决策树
