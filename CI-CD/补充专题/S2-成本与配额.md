# S2. 成本与配额意识

> **专题编号：S2**。被引用章节：第 03、04、10 章。

---

## 一、介绍：CI 是云成本黑洞

**问题**：CI 是云成本黑洞，一个团队一年烧几十万在 CI 上很常见，但很少人监控。原因：
- CI 跑量随 PR 数线性增长，团队扩张后跑量爆炸
- 失败重试、缓存失效、并发没上限都会让账单飙升
- 没人盯 CI 账单，账单只在云账单里被合并显示

**真实数据参考**：
- GitHub Actions 公共仓库免费额度用完后，每分钟约 0.008~0.016 美元；Linux 4 核 Runner 一年跑 100 万分钟 ≈ 1.2 万美元
- GitLab SaaS Runner 1000 分钟/月免费，超出后按 1000 分钟/$10 计
- AWS CodeBuild 100 build.minutes 免费，超出按 $0.005/分钟

---

## 二、关键指标（必须监控）

| 指标 | 计算方式 | 健康基线 | 说明 |
| ---- | -------- | -------- | ---- |
| **单次构建成本** | (执行时长 × Runner 单价) + 存储 + 网络出口 | 因项目而异 | 这是基础计量单位 |
| **缓存命中率** | 命中缓存构建数 / 总构建数 | **>80% 才算合格** | 低于 80% 说明缓存键设计有问题 |
| **并发利用率** | 峰值并发 / 平均并发 | <3.0 | 比值过高说明配额设计有浪费 |
| **失败重试浪费率** | 重试次数 × 单次成本 / 总成本 | <10% | >10% 说明流水线稳定性差 |
| **平均构建时长** | 总构建时长 / 构建次数 | 因项目而异 | 比上月增长 >10% 就要查原因 |

## 三、五大降本手段

### 3.1 缓存依赖（命中率从 10% 到 90% 的关键）

**反模式**：每个 Job 都 `pip install` 全量依赖。

**正确做法**：缓存键用锁文件 hash，锁文件不变就命中缓存。

```yaml
# GitHub Actions 示例
- uses: actions/cache@v4
  with:
    path: |
      ~/.cache/pip
      .venv
    key: ${{ runner.os }}-pip-${{ hashFiles('**/poetry.lock') }}
    restore-keys: |
      ${{ runner.os }}-pip-
```

**不同语言缓存键策略**：

| 语言 | 缓存路径 | 键策略 |
| ---- | -------- | ------ |
| Python (poetry) | `~/.cache/pip`, `.venv` | `os-pip-hash(poetry.lock)` |
| Java (Maven) | `~/.m2/repository` | `os-maven-hash(pom.xml)` |
| Java (Gradle) | `~/.gradle/caches` | `os-gradle-hash(build.gradle)` |
| Node (pnpm) | `~/.pnpm-store` | `os-pnpm-hash(pnpm-lock.yaml)` |
| Go | `~/go/pkg/mod` | `os-go-hash(go.sum)` |

### 3.2 Self-hosted Runner（长期跑量大的团队必备）

**何时该上 Self-hosted**：云 Runner 月账单 > 自建一台 4 核 8G 服务器的月成本（约 $30~50）时，就该上 Self-hosted。

**Self-hosted Runner 三种部署形态**：

| 形态 | 适用 | 成本 | 安全性 |
| ---- | ---- | ---- | ------ |
| 静态 Runner（常驻 VM） | 跑量稳定、内部代码 | 低 | 中（需要清理脚本） |
| 弹性 Runner（K8s + HPA） | 跑量波动大 | 中 | 高（每个 Job 一个 Pod） |
| 云 Runner + Self-hosted 混用 | 公网 PR 走云、内部走自建 | 中 | 高（公网 PR 隔离） |

**K8s Runner 弹性扩展示例**（GitLab + K8s Runner）：
```yaml
# values.yaml
gitlab-runner:
  runners:
    config: |
      [[runners]]
        name = "k8s-runner"
        executor = "kubernetes"
        [runners.kubernetes]
          namespace = "gitlab-runner"
          image = "alpine:3.18"
  rbac:
    create: true
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
  # HPA 按队列长度扩缩
  autoscaling:
    enabled: true
    minReplicas: 1
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70
```

### 3.3 并发上限（防止配额被打满）

**问题**：每个 PR 起 10 个 Job，团队 5 人同时提 5 个 PR = 50 个 Job 同时跑，账单瞬间爆炸。

**解法**：在工具层配置并发上限。

```yaml
# GitHub Actions：限制同一 PR 并发
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true   # 新 commit 推上来取消旧 commit 的运行
```

```yaml
# GitLab CI：限制并发
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      auto_cancel:
        on_new_commit: interruptible
```

### 3.4 按需扩缩（K8s Runner 用 HPA）

K8s Runner 用 HPA 按**队列长度**（不是 CPU）扩缩，没 Job 时缩到 0，有 Job 时按队列长度扩。

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: gitlab-runner
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: gitlab-runner
  minReplicas: 0
  maxReplicas: 20
  metrics:
    - type: External
      external:
        metric:
          name: gitlab_job_queue_length
        target:
          type: AverageValue
          averageValue: 1
```

### 3.5 失败快停（Fail Fast）

**问题**：单元测试失败还在跑 E2E，纯浪费。

**解法**：便宜的检查放前面，失败立即终止后续 Stage。

```yaml
# GitLab CI 示例
stages:
  - lint          # 最便宜，秒级
  - unit-test     # 几分钟
  - integration   # 十几分钟
  - e2e           # 最贵，小时级

# 默认行为：Stage 内任一 Job 失败，下一 Stage 不跑
# 显式失败快停：
lint:
  stage: lint
  script: ruff check .
  allow_failure: false   # 失败必终止
```

## 四、成本监控实现

### 4.1 GitHub Actions 成本监控

用 `actions/usage` API + Prometheus exporter 拉到 Grafana：
- [github-actions-runner-metrics](https://github.com/matti/github-actions-runner-metrics) 项目
- 关键指标：仓库维度月度分钟数、Job 失败率、缓存命中率

### 4.2 GitLab CI 成本监控

GitLab 自带 CI/CD Catalog 和 Usage Queues，管理后台 → Admin → CI/CD → Usage。
自定义监控用 Prometheus + `gitlab-ci-pipelines-exporter`。

### 4.3 自建 Runner 成本归因

按仓库打标签 → 按 label 归因成本：
- 给每个 Runner Job 打 `repository` + `team` label
- 用 Loki / ELK 收集 Job 日志
- 按 label 聚合，按月生成团队成本报表
