    S6. 数据库迁移与 CI/CD 协调¶

    专题编号：S6。被引用章节：第 03、04、08 章。

    一、介绍：后端工程师最痛点¶

    问题：应用部署是原子的，但数据库 schema 迁移不是。新代码上线前要兼容旧 schema，旧代码下线前要兼容新 schema。

    典型故障场景：

    1. 旧版应用 v1.0 在跑（schema v1）
2. 新版应用 v2.0 部署 → 同时把 schema 升级到 v2（DROP COLUMN old_field）
3. v2.0 启动失败（启动时还在跑 v1 代码，找不到 old_field）
4. 服务整体宕机

    核心原则：数据库迁移必须与代码部署解耦，分多步进行。

    二、Expand-Contract 模式（业界共识最佳实践）¶

    2.1 三阶段流程¶

    阶段 1：Expand（扩展）
   - 新 schema 与旧 schema 兼容共存
   - 例：添加新列（NULL 允许），保留旧列
   - 旧代码可读旧列，新代码读写新列
   ↓
阶段 2：Migrate（迁移）
   - 分批把旧列数据迁移到新列
   - 应用逐步切换到读写新列
   ↓
阶段 3：Contract（收缩）
   - 确认无旧代码访问后，删除旧列
   - 此时新旧版本应用都已下线

    2.2 4 种常见变更的 Expand-Contract¶

    表 6-1：常见 schema 变更的 Expand-Contract 实施

    变更类型 Expand Migrate Contract 不可逆操作（必须避免）
    加列 ALTER TABLE ADD COLUMN new_x NULL 后台 job 写入 new_x 不需要（新列保留即可） —
    删列 应用代码停止读写 old_x 验证无引用 ALTER TABLE DROP COLUMN old_x ❌ 直接 DROP（旧代码会炸）
    改列类型 加新列 new_x（新类型） 数据迁移 + 双写 删 old_x ❌ ALTER COLUMN TYPE（锁表 + 旧代码不兼容）
    重命名 加 new_name 列，双写 后台同步数据 + 应用切到 new_name 删 old_name ❌ ALTER TABLE RENAME（旧代码不认）
    加非空约束 加列允许 NULL 数据回填 ALTER COLUMN SET NOT NULL ❌ 加列时直接 NOT NULL（旧数据不满足）
    加唯一约束 应用层先做去重 + 加 partial unique 数据清理 ALTER TABLE ADD UNIQUE ❌ 直接加（脏数据会让 ALTER 失败）

    3.1 工具对照¶

    表 6-2：主流数据库迁移工具对比

    工具 语言/生态 支持数据库 特点 推荐场景
    Flyway Java MySQL/PG/Oracle/SQL Server 简单 SQL 文件，按版本号执行 Java 团队首选

    3.2 Flyway 基本使用（Java 团队）¶

    目录结构：

    src/main/resources/db/migration/
├── V1.0.0__create_users.sql
├── V1.0.1__add_email_index.sql
├── V1.1.0__expand_add_new_column.sql
├── V1.1.1__migrate_data_to_new_column.sql
└── V1.2.0__contract_drop_old_column.sql

    版本号规则：V<版本>__<描述>.sql，按字典序执行，已执行的不可修改。

    Spring Boot 集成：

    # application.yml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true       # 已有库时从 baseline 开始
    baseline-version: 0
    out-of-order: false             # 不允许乱序执行

    V1.1.0 Expand 示例：

    -- V1.1.0__expand_add_new_column.sql
-- 添加新列，允许 NULL，旧代码不感知
ALTER TABLE users ADD COLUMN email_normalized VARCHAR(255);
CREATE INDEX CONCURRENTLY idx_users_email_normalized ON users(email_normalized);

    V1.1.1 Migrate 示例（数据回填）：

    -- V1.1.1__migrate_data.sql
-- 分批回填，避免长事务锁表
DO $$
DECLARE
  batch_size INT := 1000;
  affected INT := 1;
BEGIN
  WHILE affected > 0 LOOP
    UPDATE users
    SET email_normalized = LOWER(TRIM(email))
    WHERE id IN (
      SELECT id FROM users WHERE email_normalized IS NULL LIMIT batch_size
    );
    GET DIAGNOSTICS affected = ROW_COUNT;
    PERFORM pg_sleep(0.1);  -- 给主从同步留时间
  END LOOP;
END $$;

    V1.2.0 Contract 示例（删旧列）：

    -- V1.2.0__contract.sql
-- 前提：所有应用版本都已升级到 v1.1.x，不再读 old_email
ALTER TABLE users DROP COLUMN old_email;

    3.3 Alembic 基本使用（Python 团队）¶

    初始化：

    pip install alembic
cd your-project
alembic init alembic

    配置（alembic.ini）：

    sqlalchemy.url = postgresql://user:pass@localhost/mydb

    生成迁移：

    # 自动检测模型变化生成迁移脚本
alembic revision --autogenerate -m "expand add new column"

# 手动写迁移
alembic revision -m "manual migration"

    迁移脚本示例：

    """expand add new column

Revision ID: a1b2c3
Revises: previous_rev
Create Date: 2026-08-01
"""
from alembic import op
import sqlalchemy as sa

revision = 'a1b2c3'
down_revision = 'previous_rev'

def upgrade():
    # Expand：加列
    op.add_column('users',
        sa.Column('email_normalized', sa.String(255), nullable=True))
    op.create_index('idx_users_email_normalized', 'users', ['email_normalized'])

def downgrade():
    # 回滚（CI 必测）
    op.drop_index('idx_users_email_normalized', table_name='users')
    op.drop_column('users', 'email_normalized')

    执行：

    alembic upgrade head       # 升级到最新
alembic downgrade -1       # 回滚一个版本
alembic current            # 查看当前版本
alembic history            # 查看迁移历史

    四、CI 中的迁移测试¶

    4.1 CI 必做的 3 类测试¶

    1. 向前测试（up test）：迁移脚本能在干净库上跑通
    2. 向后测试（down test）：迁移脚本能回滚
    3. 数据兼容测试：迁移后旧代码 + 新代码都能正常读写

    4.2 CI 流水线集成示例¶

    # GitLab CI 示例
migration-test:
  stage: test
  image: python:3.12
  services:
    - postgres:16-alpine
  variables:
    POSTGRES_DB: testdb
    POSTGRES_USER: test
    POSTGRES_PASSWORD: test
    DATABASE_URL: postgresql://test:test@postgres/testdb
  script:
    # 1. 初始化旧 schema
    - alembic upgrade base

    # 2. 灌入测试数据
    - python scripts/seed_test_data.py

    # 3. 升级到目标版本
    - alembic upgrade head

    # 4. 跑应用代码（验证新 schema 兼容）
    - pytest tests/test_compat_new_schema.py

    # 5. 回滚到上一版本（验证 down 可逆）
    - alembic downgrade -1
    - pytest tests/test_compat_old_schema.py

    # 6. 部署前校验：当前生产 schema 版本 ≤ 代码期望版本
    - python scripts/check_schema_version.py --expected $(cat .schema-version)

    4.3 部署时的迁移策略¶

    表 6-3：三种迁移时机的取舍

    时机 优点 缺点 适用
    应用启动时自动迁移 简单，零额外步骤 多实例同时启动会冲突 单实例应用
    部署前独立 Job 跑迁移 一次执行，应用启动只连库 多一步运维操作 多实例应用（推荐）
    K8s Init Container 跑迁移 与 Pod 生命周期绑定 Init Container 失败 Pod 不启动 K8s 场景

    K8s Init Container 示例：

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      initContainers:
        - name: migrate
          image: myapp-migrate:v1.2.0
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: url
          # 迁移成功才允许 app 容器启动
      containers:
        - name: app
          image: myapp:v1.2.0

    五、零停机迁移 7 条铁律¶

    1. 绝不直接 DROP COLUMN：先停写，再删（Expand-Contract）
    2. 绝不直接 ALTER COLUMN TYPE：加新列、双写、切流、删旧列
    3. 大表加索引用 CONCURRENTLY（PostgreSQL）：不锁表
    4. 大表数据回填分批进行：每批 1000~10000 行，间隔 100ms
    5. 迁移脚本必须有 down：CI 测 up + down 都能跑
    6. 迁移与代码部署解耦：迁移作为独立 Job/Step，不与应用启动绑定
    7. 生产迁移前必在 staging 跑一遍：用真实数据量测试性能
