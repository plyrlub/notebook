# S5. 流水线自身的安全

> **专题编号：S5**。被引用章节：第 04、08 章。

---

## 一、介绍：CI/CD 本身就是攻击面

**背景**：Codecov 事件、CircleCI Token 泄露事件表明，**CI/CD 本身也是攻击面**。一旦流水线被攻破，攻击者拿到部署密钥就能横向移动到生产环境。

**典型攻击路径**：
```
恶意 PR（公网可提交）
    ↓
触发 CI 跑通恶意代码
    ↓
代码读取 CI 环境变量（含 Token / Secret）
    ↓
把 Token 外发到攻击者服务器
    ↓
攻击者拿 Token 访问生产环境 / 制品仓
    ↓
横向移动，植入后门到下游应用
```

---

## 二、五大核心防护

### 2.1 第三方 Action pin 到 SHA（防供应链劫持）

**问题**：用 `uses: actions/checkout@v4`，万一 `v4` 标签被作者（或攻击者）指向恶意 commit，下一次 CI 跑就是恶意代码。

**正确做法**：pin 到不可变 SHA。

```yaml
# 反模式
- uses: actions/checkout@v4

# 正确
- uses: actions/checkout@1d96c772d19495a3e5e539265bbf29063c8b3b4a  # v4.1.3
```

**自动化工具**：用 [dependabot](https://docs.github.com/en/code-security/dependabot) 自动检查 Action 版本并提 PR 升级。

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

### 2.2 最小权限 Token

**问题**：GitHub 默认 `GITHUB_TOKEN` 给的权限过大，可能让 PR 代码推送 commit 到主干。

**正确做法**：用 `permissions:` 显式声明每个 Job 的权限。

```yaml
# 反模式：继承默认（默认可能给 contents:write）
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

# 正确：最小权限
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read        # 只读代码
      id-token: write       # OIDC 用
      packages: write       # 推镜像用
    steps:
      - uses: actions/checkout@v4
```

**权限原则**：
- 默认读，显式写
- 公网 PR 的 Job **不要给** `packages: write` / `contents: write`
- 需要 push 的 Job（如自动版本号提交）用独立 PAT，且只给该 Job

### 2.3 Runner 隔离

**问题**：公网 PR + Self-hosted Runner 同台机器，恶意 PR 可以读上一个 Job 的缓存 / 残留密钥。

**三种 Runner 隔离级别**：

| 隔离级别 | 隔离方式 | 适用 |
| -------- | -------- | ---- |
| **零隔离**（Shell executor） | 同宿主机跑，残留文件/环境变量都在 | ❌ 禁用 |
| **进程隔离**（Docker executor） | 每个 Job 一个容器，文件系统隔离 | ✅ 内部代码可用 |
| **Pod 隔离**（K8s executor） | 每个 Job 一个 Pod，资源/网络隔离 | ✅ 公网 PR 必备 |

**GitHub Actions Runner 分类**：
```yaml
# 公网 PR 用云 Runner（每次新 VM，零信任）
- runs-on: ubuntu-latest

# 内部代码用 Self-hosted
- runs-on: self-hosted

# 绝不混用：公网 PR 不能跑在 self-hosted 上
```

**GitLab Runner Tags 隔离**：
```yaml
# .gitlab-ci.yml
test:
  tags:
    - internal-docker     # 内部 PR 用这个
  script: pytest

public-test:
  tags:
    - cloud-runner        # 公网 PR 用这个
  script: pytest
```

### 2.4 只读仓库 Token

**问题**：CI 拉代码用同一个 Token 既读又写，万一泄露就被攻击者拿到写权限。

**正确做法**：
- CI 默认用只读 Token（如 GitHub 的 `GITHUB_TOKEN` 默认 contents:read）
- 需要写回（版本号提交、自动改 changelog）用独立受限 PAT
- PAT 设过期时间（30~90 天），到期强制轮换

**GitLab 项目级 Deploy Token（只读）**：
```bash
# 在 GitLab UI → 项目 → Settings → Repository → Deploy Tokens
# 创建只读 Deploy Token，CI 用这个拉代码
GITLAB_DEPLOY_TOKEN=xxx
```

### 2.5 审计流水线变更

**问题**：CI 配置本身不被 Review，攻击者改一行 CI 配置就能植入后门。

**正确做法**：
- CI 配置（`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile`）必须 Code Review
- 受保护分支（main/master）禁止直推 CI 配置文件
- CI 配置变更触发告警通知安全团队

```yaml
# GitLab 受保护文件路径
# 项目 → Settings → Repository → Protected branches
# main: 不允许直接 push，CI 配置必须走 MR
```

## 三、深度防护：CI 加固进阶

### 3.1 限制环境变量范围

**反模式**：所有 Job 都能读所有 Secret。

**正确**：用 Environment 隔离 Secret。

```yaml
# GitHub Actions：用 environment 隔离
jobs:
  deploy-prod:
    environment:
      name: production       # 只有这个 environment 的 Job 能读 prod secret
      url: https://app.example.com
    steps:
      - run: deploy
    env:
      PROD_DB_PASSWORD: ${{ secrets.PROD_DB_PASSWORD }}  # 只在 prod environment 暴露
```

### 3.2 加固 Runner 镜像

Self-hosted Runner 的基础镜像**不能直接用 ubuntu:22.04**，要：
1. 安装最新安全补丁
2. 移除不必要的工具（curl/wget 在某些场景可禁）
3. 限制网络出站（只允许访问 CI 控制台和必要的云 API）

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get upgrade -y && \
    apt-get install -y --no-install-recommends \
    git docker.io python3 && \
    rm -rf /var/lib/apt/lists/*
# 不装 curl、不装 wget，减少攻击面
```

### 3.3 网络出口限制

CI Runner 网络出口要受限：
- 允许：CI 控制台、制品仓、部署目标、必需的依赖源（pypi/maven central）
- 禁止：任意公网（防数据外泄）

**K8s Runner 用 NetworkPolicy**：
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: runner-egress
spec:
  podSelector:
    matchLabels:
      app: gitlab-runner
  policyTypes: [Egress]
  egress:
    - to:
        - ipBlock:
            cidr: 10.0.0.0/8       # 内网
    - to:
        - namespaceSelector: {}    # 同集群
    - to:
        - ipBlock:
            cidr: 0.0.0.0/0
      ports:
        - protocol: TCP
          port: 443                # 只允许 HTTPS 出站
```

## 四、安全事件应急响应

### 4.1 怀疑 CI 被攻击时的紧急步骤

1. **立即停所有 CI 运行**（GitHub Actions → Pause，GitLab → Cancel all pipelines）
2. **轮换所有可能泄露的 Token/Secret**
3. **审计最近 30 天 CI 日志**，找异常外发请求
4. **检查 CI 产出的制品**有没有被篡改（比对签名）
5. **通知安全团队**，按事件响应流程处理

### 4.2 日志监控告警

监控 CI 日志中的可疑模式：
- 异常外发请求（curl POST 到未知 IP）
- 读取大量环境变量后外发
- 修改 CI 配置文件的 commit

用 ELK / Loki 收集 CI 日志 + Sigma 规则匹配：

```yaml
# Sigma 规则示例：检测 CI 中可疑外发
title: CI Suspicious Egress
logsource:
  product: ci
  service: actions
detection:
  selection:
    message|contains:
      - "curl"
      - "wget"
      - "POST"
  filter:
    message|contains:
      - "github.com"
      - "pypi.org"
  condition: selection and not filter
level: high
```

## 五、流水线安全 Checklist

- [ ] 所有第三方 Action pin 到 SHA
- [ ] 所有 Job 显式声明 `permissions:`，最小权限
- [ ] 公网 PR 用云 Runner，不跑在 self-hosted
- [ ] CI 拉代码用只读 Token
- [ ] CI 配置变更必须 Code Review
- [ ] Secret 按 environment 隔离
- [ ] Runner 网络出口受限
- [ ] CI 日志接监控告警
