    CI/CD 踩坑经验集锦¶

    本文汇总 2024–2026 年真实生产环境与社区反馈中高频出现的 CI/CD 踩坑案例，覆盖流水线自身、容器化与镜像、部署与发布、安全与质量门禁、监控与回滚、数据库与配置六大领域。
    每条案例均含场景、根因、可运行修复脚本（Python/Java/Lua/Bash/YAML，不含 TypeScript）、预防措施与来源链接，并在末尾交叉引用本项目相关章节，便于跳转深读。

    严重等级定义：
    - P0：生产宕机 / 数据损坏 / 密钥外泄，需立即响应
    - P1：流水线阻塞 / 部分功能受损 / 安全门禁失效，需当日修复
    - P2：效率下降 / 噪音告警 / 体验问题，需迭代修复

    #01 GitLab Runner 雪崩：共享 Runner 大并发拖垮主库 — P0¶

    场景描述
    某中型团队 200+ 仓库共用一套 8 节点共享 Runner。某日批量推送触发 600+ 并发 pipeline，Runner 纷纷回源 GitLab 拉代码、上传 artifacts，导致 GitLab 主库 PostgreSQL 连接池打满，Web 页面 502，所有项目 CI 同时瘫痪。

    根因分析
    - Runner 无并发上限（concurrent = 10 × 8 节点 = 80，但每个 job 又触发多次 git clone/fetch）。
    - artifacts 上传走 Sidekiq，堆积后反压到 PostgreSQL。
    - 没有 request_concurrency 与队列优先级，长任务挤占短任务。

    修复方案
    1. 限制 Runner 并发与单 job 资源：

    # /etc/gitlab-runner/config.toml
concurrent = 4
check_interval = 0
limit = 4
[[runners]]
  request_concurrency = 2
  [runners.cache]
    MaxUploadedArchiveSize = 5000000  # 5MB，超大 artifacts 走对象存储
    1. artifacts 改走对象存储（S3/MinIO），不经过 Sidekiq：
    # gitlab.rb
gitlab_rails['artifacts_enabled'] = true
gitlab_rails['artifacts_object_store_enabled'] = true
gitlab_rails['artifacts_object_store_remote_directory'] = "gitlab-artifacts"
gitlab_rails['artifacts_object_store_connection'] = {
  'provider'             => 'AWS',
  'region'               => 'us-east-1',
  'aws_access_key_id'    => 'AKIAXXX',
  'aws_secret_access_key' => 'SECRET'
}
    1. 用 Lua 脚本在 Nginx 层对 git clone 限速（OpenResty 场景）：
    -- /usr/local/openresty/nginx/conf/gitlab_ratelimit.lua
local limit_req = require "resty.limit.req"
local lim, err = limit_req.new("gitlab_clone", 30, 60)  -- 30 r/s, burst 60
if not lim then ngx.log(ngx.ERR, err); return end
local delay, err = lim:enter(ngx.var.remote_addr)
if not delay then
    if err == "rejected" then
        ngx.exit(429)
    end
    return
end

    预防措施
    - 监控指标：gitlab_runner_jobs、sidekiq_queue_length、postgres_connections_active。
    - CI 检查项：Runner concurrent ≤ CPU 核数的 1.5 倍；artifacts 单文件 ≤ 50MB。
    - 引入分租户 Runner Pool（生产/测试/实验隔离）。

    来源
    - GitLab Runner timeout 排查
    - GitLab CI Pipelines 架构

    #02 CI 缓存毒化：被污染的 pip 缓存让产物带后门 — P0¶

    场景描述
    某团队用 GitLab CI 的共享 cache 缓存 ~/.cache/pip。某次一个被入侵的依赖（typosquatting 包 requets）混入缓存，后续所有构建都从缓存命中该恶意包，导致一周内 12 个服务镜像全部带后门。缓存 key 仅按 branch 分，未按 lockfile 哈希分。

    根因分析
    - cache key 过粗（key: ${CI_COMMIT_REF_SLUG}），分支内任意提交共享同一份缓存。
    - 缓存可被任意 job 写入，无签名校验。
    - pip 默认信任缓存目录，不再校验哈希。

    修复方案
    1. cache key 按 lockfile 内容哈希：

    # .gitlab-ci.yml
build:
  cache:
    key:
      files:
        - requirements.txt
        - poetry.lock
      prefix: pip-${CI_COMMIT_REF_SLUG}
    paths:
      - .cache/pip
    policy: pull-push  # 仅构建 job push，其余 pull
  variables:
    PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
  script:
    - pip install --require-hashes -r requirements.txt
    1. 开启 pip 哈希校验，缓存被改也无法命中：
    # requirements.txt 末尾固化哈希
requests==2.32.3 \
    --hash=sha256:55465c2f6f2c2c8c5c2c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1c1
pip install --require-hashes -r requirements.txt
    1. 定期清理缓存（GitLab API）：
    # clear_cache.py
import requests, os
GITLAB = "https://gitlab.example.com/api/v4"
TOKEN = os.environ["GITLAB_TOKEN"]
pid = 123
for branch in ("main", "develop"):
    requests.delete(
        f"{GITLAB}/projects/{pid}/cache/branches/{branch}",
        headers={"PRIVATE-TOKEN": TOKEN},
    )
print("cache cleared")

    预防措施
    - 监控指标：缓存命中率突变（骤降可能是清理，骤升可能是毒化复用）。
    - CI 检查项：--require-hashes 必须开启；私有 PyPI 走 HTTPS + token。
    - 高敏项目用 policy: pull 只读缓存，写入集中到一个 update-cache job。

    来源
    - CI/CD 供应链攻击挖掘实战
    - 恶意 npm 包潜入 GitHub Actions

    #03 密钥泄漏进构建日志：$CI_JOB_TOKEN 被打印 — P0¶

    场景描述
    某 Java 项目在调试阶段把 mvn deploy 输出重定向到日志，但 -X（debug）模式会把 Authorization: Basic base64(user:pass) 明文打到 stdout，日志被采集到 Loki 后任何内网员工可检索。事后审计发现 3 个仓库日志含明文 Nexus 凭据。

    根因分析
    - debug 日志未脱敏，凭据随 artifacts/日志流转。
    - CI 日志默认对仓库所有 Developer 可见，权限过宽。
    - 没有用 masked variable，而是普通 variables。

    修复方案
    1. GitLab 把变量标记为 masked（仅支持 base64 字符集的值）：

    variables:
  NEXUS_PASSWORD:
    value: ""
    description: "由 CI/CD Settings 注入，标记 Masked"
    1. Java 项目用 settings.xml 读环境变量，不在命令行传参：
    <!-- ~/.m2/settings.xml -->
<settings>
  <servers>
    <server>
      <id>nexus-releases</id>
      <username>${env.NEXUS_USER}</username>
      <password>${env.NEXUS_PASSWORD}</password>
    </server>
  </servers>
</settings>

    mvn -s settings.xml deploy -DskipTests  # 不加 -X
    1. 加日志脱敏前置脚本（Python 检查）：
    # check_log_secrets.py
import re, sys
PATTERNS = [
    r"Authorization:\s*Basic\s+[A-Za-z0-9+/=]+",
    r"AKIA[0-9A-Z]{16}",            # AWS access key
    r"-----BEGIN (RSA |EC )?PRIVATE KEY-----",
]
leak = False
for line in sys.stdin:
    for p in PATTERNS:
        if re.search(p, line):
            print(f"[LEAK] {line.strip()[:60]}...")
            leak = True
sys.exit(1 if leak else 0)

    after_script:
  - cat build.log | python check_log_secrets.py || exit 1

    预防措施
    - 监控指标：日志中 secret 命中数（接 Gitleaks / TruffleHog 扫历史日志）。
    - CI 检查项：所有 *_TOKEN、*_PASSWORD 变量必须 masked；debug 日志默认关闭。
    - 定期 rotate Nexus/Harbor/GitLab token，缩短泄漏窗口。

    来源
    - Aqua Secrets Management
    - GitLab 身份认证绕过 CVE-2024-5655

    #04 concurrency 失控：100 个并发任务同时部署生产 — P1¶

    场景描述
    某团队 monorepo 有 50 个微服务，每次 push 触发 50 条 pipeline，每条 pipeline 都有 deploy:prod job。一次合并大 PR 后 50 个 deploy 同时跑，Helm 并发 install 把目标集群 apiserver 打到 90% CPU，多个 release 半成品状态，回滚困难。

    根因分析
    - 没有 resource_group 或 concurrency 限制部署并发。
    - monorepo 未做路径过滤，无关服务也部署。
    - 集群无 PDB / LimitRange，apiserver 无优先级保护。

    修复方案
    1. GitLab 用 resource_group 串行化生产部署：

    deploy:prod:
  stage: deploy
  resource_group: production-deploy
  script:
    - helm upgrade --install api ./chart --wait --timeout 5m
  only:
    refs: [main]
    changes:
      - "services/api/**/*"
    1. GitHub Actions 用 concurrency：
    deploy:
  concurrency:
    group: prod-deploy-${{ matrix.service }}
    cancel-in-progress: false
  strategy:
    matrix:
      service: [api, web, worker]
  steps:
    - run: kubectl rollout status deploy/${{ matrix.service }}
    1. monorepo 路径过滤，避免无关服务部署（Python 脚本生成矩阵）：
    # gen_matrix.py
import os, json, subprocess
changed = subprocess.check_output(
    ["git", "diff", "--name-only", os.environ["PREV_SHA"], "HEAD"], text=True
).split()
services = sorted({l.split("/")[1] for l in changed if l.startswith("services/")})
print(json.dumps({"service": services}))

    预防措施
    - 监控指标：apiserver_request_latencies_p99、部署队列堆积深度。
    - CI 检查项：生产 deploy job 必须 resource_group；monorepo 必须 changes 过滤。
    - 集群侧加 PriorityClass，部署 controller 用高优先级避免被业务 pod 挤掉。

    来源
    - AI 时代的 CI/CD 工具选型
    - GitLab CI Pipelines 配置

    #05 pull_request_target 误用：恶意 PR 提权窃取 Token — P0¶

    场景描述
    某开源项目 GitHub Actions workflow 用了 on: pull_request_target，并在 job 里直接 actions/checkout@v4 拉取 PR 分支代码并执行 npm test。攻击者提交一个 PR，在测试脚本里 echo $GITHUB_TOKEN 并外传，盗取了仓库写权限 token，篡改 release 产物。

    根因分析
    - pull_request_target 用的是 base 分支的 secrets，权限等同写仓库。
    - checkout PR 代码后执行任意命令 = 把 secrets 送给不可信代码。
    - 对 fork PR 没有隔离沙箱。

    修复方案
    1. 永远不要在 pull_request_target 里 checkout PR 代码并执行；改为两阶段：

    # 阶段 1：低权限跑 PR 代码
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -e . && pytest

    # 阶段 2：PR 合并后才用 secrets
on:
  push:
    branches: [main]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker push ...
    1. 若必须跑 PR 代码 + label 门禁，用 pull_request_target 仅做 label，再触发另一个 workflow：
    on: pull_request_target
jobs:
  label:
    if: github.event.action == 'opened'
    steps:
      - uses: actions/labeler@v5
        with:
          repo-token: ${{ secrets.GITHUB_TOKEN }}
    1. 用 Java 写一个 token 最小化审计器（扫描 workflow 文件）：
    // WorkflowAudit.java
import java.nio.file.*;
import java.util.*;
public class WorkflowAudit {
  public static void main(String[] args) throws Exception {
    for (var f : Files.find(Paths.get(".github"), 10,
        (p,a) -> p.toString().endsWith(".yml")).toList()) {
      var lines = Files.readAllLines(f);
      boolean hasTarget = lines.stream().anyMatch(l -> l.contains("pull_request_target"));
      boolean hasCheckout = lines.stream().anyMatch(l -> l.contains("checkout") && l.contains("${{"));
      if (hasTarget && hasCheckout) {
        System.err.println("[DANGER] " + f + " mixes pull_request_target with PR checkout");
      }
    }
  }
}

    预防措施
    - 监控指标：workflow secrets: 引用次数、pull_request_target + checkout 组合告警。
    - CI 检查项：扫描所有 workflow，禁止 pull_request_target 同 job 内 checkout PR。
    - 对 fork PR 强制 require approval，token 最小化（只读）。

    来源
    - CI/CD 供应链攻击挖掘实战
    - 2024 年顶级云原生威胁

    #06 Dockerfile 用 latest tag 导致构建不可复现 — P1¶

    场景描述
    某 Python 服务 FROM python:latest，某天上游推了 python:3.13，新构建里 pip install 因 3.13 移除的 distutils 失败，所有 PR 突然变红。开发者本地 python:3.11 却完全正常，排查 2 小时。

    根因分析
    - base image 用浮动 tag，上游变更直接破坏复现性。
    - 没有 pin 到 digest。
    - 没有锁 base image 版本的 CI 检查。

    修复方案
    1. 固定版本 + digest：

    # Dockerfile
FROM python:3.11.9-slim@sha256:abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-m", "app.main"]
    1. 用 Renovate / Dependabot 自动升级 base image，PR 触发测试：
    # .github/renovate.json
{
  "extends": ["config:recommended"],
  "dockerfile": { "pinDigests": true },
  "packageRules": [
    { "matchDatasources": ["docker"], "schedule": ["before 6am on Monday"] }
  ]
}
    1. CI 加 digest 一致性检查（Bash）：
    #!/usr/bin/env bash
set -euo pipefail
IMAGE=$(grep -oP '^FROM \K\S+' Dockerfile | head -1)
if [[ "$IMAGE" != *@sha256:* ]]; then
  echo "FAIL: $IMAGE 未 pin digest"; exit 1
fi
echo "OK: $IMAGE"

    预防措施
    - 监控指标：base image 漂移告警（每周对比 digest）。
    - CI 检查项：Dockerfile base image 必须 pin 到 @sha256:；禁止 latest/stable。
    - 维护内部 golden image，所有服务基于它构建。

    来源
    - Docker 镜像构建与 Dockerfile 最佳实践

    #07 构建上下文过大：.dockerignore 缺失把数据集打进上下文 — P1¶

    场景描述
    某 AI 服务仓库根目录有 8GB 训练数据集（data/）和 node_modules/。某次 docker build 没配 .dockerignore，构建上下文上传耗时 6 分钟，CI 队列堆积。开发者本地 build 也要等 5 分钟才能开始第一步。

    根因分析
    - Docker daemon 把整个 build context 发送给 daemon，无 .dockerignore 时全量打包。
    - COPY . . 把不该进镜像的东西也复制进去，镜像膨胀。
    - CI 上每次都重新传 8GB，缓存失效。

    修复方案
    1. 配置 .dockerignore：

    # .dockerignore
.git
.github
.gitlab
data/
*.csv
*.parquet
node_modules/
__pycache__/
*.pyc
.venv/
.env
tests/
*.md
.idea/
.vscode/
    1. 用 BuildKit 的 --mount=type=cache 加速 pip：
    # syntax=docker/dockerfile:1.7
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
COPY app/ ./app/
CMD ["python", "-m", "app.main"]
    1. CI 启用 BuildKit：
    export DOCKER_BUILDKIT=1
docker build -t myapp:ci .

    预防措施
    - 监控指标：docker build 上下文大小（docker build --progress=plain 日志里会打印 transferring context: X MB）。
    - CI 检查项：仓库根有 .dockerignore；上下文 > 100MB 告警。
    - 大数据集走对象存储 / DVC，不进 git。

    来源
    - Docker 镜像构建最佳实践

    #08 镜像瘦身翻车：多阶段构建误删运行时依赖 — P1¶

    场景描述

      failureLimit: 3

        prometheus:
          address: http://prometheus:9090

            templates:
              - templateName: success-rate
                args:
                  - name: service-name

        - analysis:

              - templateName: success-rate

  public void onApplicationEvent(WebServerGracefulShutdownEvent event) {

    场景描述

    - kubectl 直改集群绕过 GitOps，与 ArgoCD 冲突。
    - 没有 "ArgoCD 回滚应通过 git revert" 的规范。

# 1. git revert 部署清单
git revert --no-edit HEAD
git push origin main

# 3. 确认 sync 完成
argocd app wait prod-api --sync

    argocd app set prod-api --sync-policy none       # 临时关 auto-sync
argocd app rollback prod-api <revision>
# 修复 git 后重新开
argocd app set prod-api --sync-policy automated --self-heal

    apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-api
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true           # 集群被改后自动拉回 git
    syncOptions:
      - CreateNamespace=true

    #25 黑盒回滚：缺少版本-镜像映射表无法回滚 — P1¶

    场景描述
    某次故障需要回滚，但没人记得上一版镜像 tag 是什么。kubectl rollout history 显示 <none>（因为 deployment 没用 change-cause），Git 历史里也是 image: api:latest。最终花 40 分钟翻 CI 日志才找到上一版 digest。

    根因分析
    - 用 latest tag，无版本可追溯。
    - kubectl apply 没记录 change-cause。
    - 没有部署台账（release manifest）。

    修复方案
    1. 部署时强制记录 change-cause + 用 digest：

    #!/usr/bin/env bash
set -euo pipefail
TAG=$(git rev-parse --short HEAD)-$(date +%Y%m%d%H%M)
DIGEST=$(docker buildx imagetools inspect harbor.example.com/prod/api:$TAG --format '{{.Manifest.Digest}}')
kubectl set image deploy/api api=harbor.example.com/prod/api@$DIGEST \
  --record --change-cause="deploy $TAG by $GITLAB_USER_LOGIN"
    1. 每次部署写一份 release manifest 到 git（Python）：
    # write_manifest.py
import json, os, subprocess, datetime
digest = subprocess.check_output(
    ["docker", "buildx", "imagetools", "inspect",
     f"harbor.example.com/prod/api:{os.environ['TAG']}", "--format", "{{.Manifest.Digest}}"], text=True).strip()
manifest = {
    "service": "api",
    "version": os.environ["TAG"],
    "digest": digest,
    "git_sha": subprocess.check_output(["git","rev-parse","HEAD"], text=True).strip(),
    "deployed_at": datetime.datetime.utcnow().isoformat(),
    "deployed_by": os.environ.get("GITLAB_USER_LOGIN", "ci"),
}
path = f"releases/api/{os.environ['TAG']}.json"
open(path, "w").write(json.dumps(manifest, indent=2))
subprocess.check_call(["git", "add", path])
subprocess.check_call(["git", "commit", "-m", f"release {os.environ['TAG']}"])
subprocess.check_call(["git", "push"])
    1. 回滚脚本一键找上一版：
    #!/usr/bin/env bash
set -euo pipefail
PREV=$(ls -1t releases/api/*.json | sed -n '2p')
DIGEST=$(jq -r .digest "$PREV")
kubectl set image deploy/api api=harbor.example.com/prod/api@$DIGEST --record --change-cause="rollback to $(jq -r .version $PREV)"

    预防措施
    - 监控指标：每次部署必写 manifest；回滚耗时（目标 < 5 分钟）。
    - CI 检查项：deployment image 必须用 digest；CI 末尾写 manifest 到 git。
    - 维护"上一版"快速回滚能力（脚本化）。

    来源
    - K8s Deployment 工作机制

    #26 Flyway 锁表：大表 ADD COLUMN 锁库 30 分钟 — P0¶

    场景描述
    某订单表 8 亿行，Flyway 迁移 ALTER TABLE orders ADD COLUMN status VARCHAR(20) DEFAULT 'pending'。MySQL 8.0 之前 ADD COLUMN ... DEFAULT 会做全表 inplace 重建，锁表 30 分钟，期间所有下单失败。

    根因分析
    - 大表 DDL 没用 online DDL（ALGORITHM=INSTANT / INPLACE）。
    - DEFAULT 非 NULL 触发全表回填。
    - 没有在影子库做演练。

    修复方案
    1. 拆分 DDL，用 instant 算法：

    -- V20260101__add_status.sql
-- MySQL 8.0+ 支持 INSTANT，秒级完成
ALTER TABLE orders ADD COLUMN status VARCHAR(20), ALGORITHM=INSTANT;
-- 默认值用应用层填充，不在 DDL 设 DEFAULT，避免回填
    1. 老版本用 pt-online-schema-change（gh-ost 也行）：
    pt-online-schema-change \
  --alter "ADD COLUMN status VARCHAR(20)" \
  --set-vars innodb_lock_wait_timeout=1 \
  --max-load Threads_running=50 \
  --critical-load Threads_running=100 \
  --execute D=prod,t=orders
    1. CI 检查 DDL 是否走 instant：
    # check_ddl_online.py
import re, sys
for f in sys.argv[1:]:
    sql = open(f).read()
    if re.search(r"ALTER\s+TABLE", sql, re.I) and "ALGORITHM" not in sql.upper():
        print(f"[WARN] {f}: ALTER TABLE 未声明 ALGORITHM，可能锁表")
        # 大表必须显式 INSTANT 或走 pt-osc
    1. Lua 在 OpenResty 给迁移加全局开关（紧急熔断）：
    -- migration_gate.lua
local mc = require "resty.memcached"
local m = mc:new()
m:connect("127.0.0.1", 11211)
local gate, _ = m:get("migration_gate")
if gate == "closed" then
    ngx.log(ngx.ERR, "migration gate closed, skip flyway")
    os.exit(0)
end

    预防措施
    - 监控指标：DDL 执行时长、innodb_row_lock_waits、Threads_running。
    - CI 检查项：大表 ALTER 必须含 ALGORITHM；DEFAULT 用 NULL 或应用层填。
    - 影子库演练 + 慢查询日志 review。

    来源
    - Spring Boot 中恢复 Flyway 失败的迁移
    - Flyway/Liquibase 多环境发版

    #27 Liquibase checksum 失败：手工改 SQL 导致流水线阻塞 — P1¶

    场景描述
    某团队 DBA 在生产环境手工改了某条已应用的 Liquibase changeset 的 SQL（修了个 typo），下次 CI 部署 Liquibase 启动报 Validation Failed: checksum mismatch，应用起不来，生产部署中断。

    根因分析
    - 已应用的 changeset 被手工修改，DATABASECHANGELOG 里 checksum 与文件不匹配。
    - 没有 clearCheckSums 的应急预案。
    - DBA 直连生产改库，绕过版本控制。

    修复方案
    1. 紧急修复：清掉旧 checksum（Bash）：

    #!/usr/bin/env bash
set -euo pipefail
# 备份后清 checksum
PGPASSWORD=$DB_PASS psql -h $DB_HOST -U $DB_USER -d prod -c \
  "UPDATE databasechangelog SET md5sum = NULL WHERE id = '20260101-add-index';"
# 重新部署，Liquibase 会重算
    1. 正确做法：新增一个 changeset 修正，不改正老 SQL：
    <!-- db/changelog/20260102-fix-index.xml -->
<databaseChangeLog>
  <changeSet id="20260102-drop-bad-index" author="dba">
    <dropIndex tableName="orders" indexName="idx_bad"/>
  </changeSet>
  <changeSet id="20260102-add-correct-index" author="dba">
    <createIndex tableName="orders" indexName="idx_correct">
      <column name="user_id"/>
    </createIndex>
  </changeSet>
</databaseChangeLog>
    1. CI 启动前校验 checksum：
    # liquibase_check.py
import subprocess, sys
out = subprocess.check_output(
    ["liquibase", "--changelog-file=changelog.xml", "status", "--verbose"], text=True)
if "checksum" in out.lower():
    print("[BLOCK] checksum mismatch, 需手工处理")
    print(out); sys.exit(1)
print("checksum ok")
    1. DBA 改库走 PR，CI 强制 review：
    # .gitlab/merge_request_rules.yml
- name: DBA-approval-for-prod-DDL
  conditions:
    files: ["db/changelog/prod/**"]
  actions:
    require_approvals: 2

    预防措施
    - 监控指标：Liquibase 启动失败数、checksum 校验告警。
    - CI 检查项：启动前 liquibase status 校验；禁止直连生产改库。
    - changeset 不可变约定，改库必加新 changeset。

    - Flyway/Liquibase 对比

    #28 ConfigMap 热更新失效：Pod 没拿到新配置 — P1¶

    场景描述
    某 Java 服务用 ConfigMap 挂配置文件，改了 ConfigMap 后 kubectl apply，但 Pod 里仍是旧配置。开发者以为热更新，结果用户还在用旧 rate limit，被刷接口 1 小时。

    根因分析
    - ConfigMap 挂载为 volume 时，kubelet 异步刷新（默认 60s–5min），不即时。
    - 挂载为 env 的 ConfigMap 不会自动更新，Pod 重启才生效。
    - 应用没监听文件变化主动 reload。

    修复方案
    1. env 形式的 ConfigMap 必须重启 Pod：

    kubectl rollout restart deploy/api
    1. volume 形式 + 应用 watch 文件变化（Java）：
    // ConfigWatcher.java
import java.nio.file.*;
import java.util.concurrent.atomic.AtomicReference;

@Component
public class ConfigWatcher {
  private final AtomicReference<Properties> cfg = new AtomicReference<>();
  @PostConstruct
  void init() throws Exception {
    var path = Paths.get("/etc/app/rate-limit.properties");
    load(path);
    var ws = FileSystems.getDefault().newWatchService();
    path.getParent().register(ws, StandardWatchEventKinds.ENTRY_MODIFY);
    Thread.ofVirtual().start(() -> {
      while (true) {
        try {
          var key = ws.take();
          key.pollEvents().stream()
            .filter(e -> e.context().toString().equals(path.getFileName().toString()))
            .forEach(e -> { load(path); System.out.println("config reloaded"); });
          key.reset();
        } catch (Exception ignored) {}
      }
    });
  }
  void load(Path p) { /* read properties into cfg */ }
}
    1. 用 Reloader 自动重启 Pod on ConfigMap 变更：
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  annotations:
    reloader.stakater.com/auto: "true"   # 关联 ConfigMap/Secret 变更自动 rollout
spec: { ... }

    helm install reloader stakater/reloader -n kube-system

    预防措施
    - 监控指标：ConfigMap 更新到 Pod 生效的延迟、配置版本号（在 /actuator/info 暴露）。
    - CI 检查项：env 形式 ConfigMap 变更必须配 Reloader；volume 形式应用必须 watch。
    - 配置变更走灰度（先 1 个 Pod 验证）。

    来源
    - K8s 生产运维 20 条

    #29 Secret 轮换炸 CI：rotation 未同步刷新 CI 变量 — P0¶

    场景描述
    某团队每 90 天轮换 DB 密码，运维改了 Vault 里的 secret，但忘了同步更新 GitLab CI/CD Variables 里的 DB_PASSWORD。下次 CI 部署用旧密码跑迁移，连接被拒，所有 deploy job 失败 2 小时，期间生产紧急 hotfix 也无法走 CI。

    根因分析
    - Secret 多处副本（Vault、CI 变量、K8s Secret），轮换不同步。
    - 没有"轮换后自动验证 CI"的检查。
    - CI 变量没有 owner/到期时间。

    修复方案
    1. CI 不存 secret，运行时从 Vault 拉（Python）：

    # vault_get.py
import os, requests
VAULT = os.environ["VAULT_ADDR"]
ROLE = os.environ["VAULT_ROLE"]
# 1. 用 JWT 登 Vault
jwt = open("/var/run/secrets/kubernetes.io/serviceaccount/token").read()
login = requests.post(f"{VAULT}/v1/auth/kubernetes/login",
                     json={"role": ROLE, "jwt": jwt}).json()
token = login["auth"]["client_token"]
# 2. 读 secret
secret = requests.get(f"{VAULT}/v1/secret/data/prod/db",
                     headers={"X-Vault-Token": token}).json()
os.environ["DB_PASSWORD"] = secret["data"]["data"]["password"]
# 3. exec 子进程
import subprocess
subprocess.run(["python", "-m", "app.main"])
    1. K8s 用 ExternalSecret Operator 同步 Vault → K8s Secret：
    apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-cred
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-cred
  data:
    - secretKey: password
      remoteRef:
        key: prod/db
        property: password
    1. 轮换后自动跑 CI 验证（GitLab scheduled pipeline）：
    # .gitlab-ci.yml
verify-secret-rotation:
  schedule: "0 3 1 */3 *"  # 每季度 1 号轮换后跑
  script:
    - python -c "import os; from db import ping; ping(os.environ['DB_PASSWORD'])"
    - kubectl rollout restart deploy/api  # 让 Pod 拉新 secret

    预防措施
    - 监控指标：Secret 年龄、轮换失败率、CI 连接 DB 失败数。
    - CI 检查项：CI 变量有 expires_at 元数据；secret 单一真源（Vault）。
    - 轮换 SOP 含"轮换后立即触发验证 pipeline"。

    #30 数据库迁移缺 down 脚本：无法回滚被迫手工救火 — P1¶

    场景描述
    某团队用 Alembic 做迁移，开发者只写 upgrade()，downgrade() 是空的。某次部署后才发现新列导致 ORM 报错，回滚时 alembic downgrade -1 报 NotImplementedError，只能手工 ALTER TABLE DROP COLUMN，还忘了删索引，留下隐患。

    根因分析
    - downgrade() 不写，回滚靠手工。
    - CI 没检查 downgrade 是否为空。
    - 没有回滚演练。

    修复方案
    1. Alembic migration 必须实现 downgrade：

    # migrations/versions/a1b2_add_user_status.py
from alembic import op
import sqlalchemy as sa

def upgrade():
    op.add_column('users', sa.Column('status', sa.String(20), nullable=True))
    op.create_index('idx_users_status', 'users', ['status'])

def downgrade():
    op.drop_index('idx_users_status', table_name='users')
    op.drop_column('users', 'status')
    1. CI 检查 downgrade 非空（Python AST）：
    # check_downgrade.py
import ast, sys, glob
for f in glob.glob("migrations/versions/*.py"):
    tree = ast.parse(open(f).read())
    for node in ast.walk(tree):
        if isinstance(node, ast.FunctionDef) and node.name == "downgrade":
            body = [n for n in node.body if not isinstance(n, (ast.Pass, ast.Expr, ast.Constant))]
            if len(body) == 0 or (len(body) == 1 and isinstance(body[0], ast.Raise)):
                print(f"[BLOCK] {f}: downgrade 为空或仅 raise NotImplementedError")
                sys.exit(1)
print("all downgrade implemented")
    1. CI 跑 up→down→up 往返测试：
    migration-roundtrip:
  services:
    - postgres:15
  script:
    - alembic upgrade head
    - alembic downgrade -1
    - alembic upgrade head
    - pytest -m "not slow"

    预防措施
    - 监控指标：迁移回滚成功率、回滚耗时。
    - CI 检查项：downgrade 必须 AST 非空；up→down→up 往返测试通过。
    - 不可逆 DDL（删列/删表）单独审批，不进自动迁移。

    来源
    - Spring Boot Flyway 恢复失败迁移
    - 数据库迁移（S6 补充专题）
