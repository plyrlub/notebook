# 后端缓存补充·CDN协同

> 本文件只覆盖 Redis 系列未涉及的**增量视角**：CDN 层缓存与前后端缓存的协同设计。

## 1. CDN 在缓存体系中的位置

```
用户浏览器（TTL/SWR 客户端缓存）
  ↓ 未命中
CDN 边缘节点（s-maxage 共享缓存）
  ↓ 未命中
Nginx 反向代理（proxy_cache）
  ↓ 未命中
后端应用（Redis 缓存 → DB）
```

CDN 是**离用户最近的共享缓存层**：一个边缘节点缓存一份，服务该区域所有用户（共享缓存 vs 浏览器私有缓存）。

## 2. CDN 缓存的关键头：s-maxage

- `Cache-Control: max-age=60` —— **浏览器**缓存 60s
- `Cache-Control: s-maxage=300` —— **CDN/共享缓存**缓存 300s（浏览器忽略 s-maxage）
- `public/private` —— 是否允许共享缓存缓存

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=60, s-maxage=300
ETag: "v1"
```

> **关键认知**：`s-maxage` 让你能**区分浏览器和 CDN 的缓存时长**——浏览器 60s 保证个体实时，CDN 300s 减少回源。这是「前后端协同」的第一个落点。

## 3. 协同设计：谁缓存什么

| 内容类型 | 浏览器 | CDN | Nginx/后端 | 说明 |
|---|---|---|---|---|
| 静态资源（带 hash） | ✅ 长缓存 immutable | ✅ 长缓存 | - | CDN 主力，回源极少 |
| 动态报表/统计（分钟级） | ✅ TTL 短 | ✅ s-maxage 中 | Redis hash + 304 | CDN 减少回源，后端 304 兜底 |
| 个性化内容（登录态） | ✅ TTL 短 | ❌ private 禁共享 | Redis | CDN 不能缓存用户私有数据 |
| 实时数据 | ❌ no-cache | ❌ | SSE/WS 推送 | 任何缓存层都不适用 |

> **归属原则延伸**：静态归 CDN、动态报表 CDN+后端双层、个性化 private 只走后端、实时不上缓存（与总览一致）。

## 4. 缓存失效的协同（三级失效）

CDN 引入了新的失效复杂度——**CDN 边缘节点遍布各地，主动失效要通知所有节点**：

| 失效手段 | 机制 | 时效 |
|---|---|---|
| TTL 自然过期 | 等 s-maxage 到点 | 慢但简单 |
| URL 版本化（推新不失效） | 新文件名 = 新 URL，旧 URL 自然淘汰 | 静态资源首选 |
| CDN API 主动 purge | 调 CDN 厂商 API 清指定 URL | 秒级，按量计费 |
| 回源 304 联动 | CDN 带 If-None-Match 回源，后端 304 则 CDN 也更新 | 秒级~分钟级 |

> **最佳实践**：静态资源用 **URL 版本化**（文件名带 hash，内容变 URL 变，零失效成本）；动态内容用 **s-maxage 短过期 + 后端 304 联动**；紧急下线用 **purge API**。

## 5. 常见踩坑

- 忘了 `s-maxage`：CDN 用 max-age 缓存 60s，回源压力没降下来
- 个性化内容没标 `private`：CDN 把 A 用户数据缓存后发给 B 用户（严重事故）
- 静态资源无 hash 版本化 + CDN 长缓存：发布后用户拿到旧资源（缓存永不失效）
- CDN 与后端缓存两层叠加：后端改了数据，CDN 还在 s-maxage 期内 → 用户仍看旧值，需 purge 或等过期
- 只配了 CDN 没配后端 304：CDN 回源每次都拉全量 body，后端白算

## 6. 小结

- CDN 是离用户最近的**共享缓存**，用 `s-maxage` 区分与浏览器的缓存时长
- 协同三层：静态 URL 版本化、动态 s-maxage + 后端 304、个性化 private
- 失效三级：TTL 过期 / URL 版本化 / purge API，按内容类型选
- 记住：CDN 缓存的是「不常变的大内容」，个性化与实时数据远离 CDN
