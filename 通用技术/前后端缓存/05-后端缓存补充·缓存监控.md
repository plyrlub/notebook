# 后端缓存补充·缓存监控

> 本文件只覆盖 Redis 系列未涉及的**增量视角**：缓存运行状态的监控指标体系与告警。
> 完整后端缓存方案（穿透/击穿/雪崩/多级缓存/一致性）见 [00-前后端缓存总览](00-前后端缓存总览.md)。

---

## 1. 为什么要监控缓存

缓存是「看不见的加速层」——它坏了不会报错，只是**悄悄变慢**（请求穿透到 DB）。不监控就不知道：
- 缓存到底命中率多少（还是白加了）
- 有没有在穿透打 DB（雪崩前兆）
- 内存/连接有没有异常增长

## 2. 核心指标：三级监控

| 层级 | 指标 | 怎么看 | 异常信号 |
|---|---|---|---|
| **命中率** | 缓存命中率（hits / (hits+misses)） | 读多写少场景应 > 90% | 突然下降 → 可能有穿透/失效风暴 |
| **容量** | 内存使用率、key 数量、过期淘汰量 | 淘汰量说明内存吃紧 | 持续淘汰 → TTL 或容量配置要调 |
| **运行时** | 连接数、QPS、延迟、大 key/热 key | 与基线对比 | 连接数暴涨 → 排查热 key/大 key |

### 命中率的分场景基线

| 场景 | 健康命中率 | 说明 |
|---|---|---|
| 静态配置类 | > 95% | 几乎不变，应该极高 |
| 业务读多写少 | 80~95% | 正常波动 |
| 写频繁/实时类 | < 50% 也正常 | 这类内容本来就不该上缓存 |

## 3. 怎么监控：工具与手段

### Redis 侧（服务端缓存核心）

```bash
# 命中率：keyspace_hits / (keyspace_hits + keyspace_misses)
redis-cli info stats | grep -E "keyspace_hits|keyspace_misses"

# 内存与淘汰
redis-cli info memory | grep -E "used_memory|maxmemory"
redis-cli info stats | grep evicted_keys

# 大 key / 热 key（生产用 redis-rdb-tools / hotkey 插件，避免阻塞）
redis-cli --bigkeys   # 只建议测试环境
```

- **Prometheus**：redis_exporter 采集以上指标，Grafana 出看板
- **告警阈值**：命中率 < 80%（持续 5min）、内存 > 80% maxmemory、evicted_keys 突增

### CDN 侧

- 厂商控制台自带：命中率、回源带宽、流量、边缘状态码
- 关注**回源率**（回源请求/总请求）：回源率上升 = CDN 命中下降

### 业务侧（自定义）

- 埋点：业务代码里统计「读缓存命中/未命中/回源 DB」计数，打点上报
- 缓存穿透计数器：DB 层记录「无缓存直接打到 DB」的请求数，超过阈值告警（穿透前兆）

## 4. 监控驱动的优化动作

| 监控发现 | 动作 |
|---|---|
| 命中率低但业务适合缓存 | 查 key 设计（key 太碎/带时间戳导致命中不了）、TTL 是否太短 |
| 内存持续淘汰 | 调大 maxmemory / 换淘汰策略（见 **03-Redis过期删除与内存淘汰详解**（见知识库）） |
| 热 key 打爆单节点 | 热 key 分散（多副本/本地缓存，见 **05-Redis缓存三大问题与分布式锁详解**（见知识库）） |
| 穿透激增 | 布隆过滤器 / 空值缓存 |
| 回源率上升 | 查 CDN 缓存头是否被改、s-maxage 是否失效 |

## 5. 常见踩坑

- 只看命中率不看基线：不同场景健康值不同，一刀切阈值会误报
- 不监控淘汰量：内存淘汰是缓慢恶化，等告警时已影响性能
- 大 key 检测用 --bigkeys 上生产：会阻塞，只限测试环境或低峰期
- 只监控 Redis 不监控 CDN/业务侧：缓存链路是三层，缺一层就看不见全貌
- 命中率下降不追查：命中率是结果指标，要往下挖「为什么」（key 设计/TTL/穿透）

## 6. 小结

- 三级指标：命中率（效果）、容量（内存）、运行时（健康）
- 命中率要分场景看基线，不搞一刀切
- 工具链：redis_exporter + Prometheus + Grafana，CDN 用厂商控制台，业务侧埋点
- 监控的价值在驱动优化：发现问题 → 定位原因 → 调整（key/TTL/策略）
