# 后端缓存补充·缓存更新策略

> 本文件只覆盖 Redis 系列未涉及的**增量视角**：缓存更新策略的全景对比与选型决策。

## 1. 三种更新策略：是什么

缓存更新策略解决「**数据变了，缓存怎么跟着变**」。三条路线：

| 策略 | 机制 | 实时性 | 实现成本 |
|---|---|---|---|
| **TTL 过期** | 缓存设过期时间，到点自动失效，下次请求回源 | 延迟 = TTL | 最低 |
| **主动失效（变更驱动）** | 数据变更时，显式删除/更新对应缓存 key | 秒级 | 中 |
| **事件驱动** | 数据变更发消息（MQ/binlog），消费方异步刷新缓存 | 秒级~最终一致 | 高 |

## 2. 怎么选：决策表

| 场景 | 首选 | 理由 |
|---|---|---|
| 读多写少、可容忍短暂旧数据 | **TTL 过期** | 简单可靠，成本最低 |
| 写后必须立刻读新（一致性敏感） | **主动失效** | 变更即清缓存，秒级一致 |
| 多服务/多节点都要刷缓存 | **事件驱动（MQ/binlog）** | 广播失效，各节点各自刷新 |
| 低频冷数据 | **TTL + 长过期** | 几乎不变，没必要主动管 |
| 热点数据 + 一致性要求 | **主动失效 + TTL 兜底** | 双保险：主动清 + 过期自愈 |

> **最佳实践组合**：主动失效保一致 + 短 TTL 兜底防漏（漏删时缓存也会自愈过期）。

## 3. 与「生成时同步更新 hash」的关系

协商缓存篇（**02-协商缓存详解**（见知识库））的「生成时更新 Redis hash」本质就是**主动失效**的一种特例：
- 生成新数据 → 更新 hash（相当于主动作废旧缓存）
- 忘记更新 = 失效漏执行 → 一直 304 旧数据

**核心教训**：主动失效的可靠性取决于「**变更路径上必须挂钩失效逻辑**」——要么在业务代码里调，要么用 binlog 监听兜底，否则漏一处就是线上事故。

## 4. 常见踩坑

- TTL 一刀切：所有 key 同过期时间 → 同时过期造成**缓存雪崩**（见 **05-Redis 缓存三大问题与分布式锁详解**（见知识库））→ 过期时间加随机抖动
- 主动失效漏挂：改库的代码路径忘了删缓存 → 脏数据直到 TTL 才恢复
- 事件驱动乱序：binlog 消费乱序导致旧值覆盖新值 → 消息带版本号/时间戳，消费端比较后再写
- 更新 vs 删除：更新缓存（写新值）并发下容易写旧值，**删缓存**更安全（下次读时重建）

## 5. 小结

- 三策略：TTL 简单延迟大、主动失效秒级要挂钩、事件驱动最灵活成本高
- 选型看「一致性敏感度 + 节点数」：单机低敏感用 TTL，多节点高一致用事件驱动
- 主动失效必须挂在变更路径上，漏一处就是脏数据
- 最佳实践：主动失效 + 短 TTL 兜底
