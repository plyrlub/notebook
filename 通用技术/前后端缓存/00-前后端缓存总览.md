# 前后端缓存总览

> 受众：Java 后端开发（兼写前端），已了解 HTTP 基础与浏览器缓存机制，想系统建立「什么时候该用哪种缓存、什么时候别用」的决策框架。

## 一、核心思想：分清「省什么」

很多缓存方案争论的根源，是**把两种不同的「省」混为一谈**。先建立坐标系：

| 方案 | 真正省了什么 | 站在哪一侧 | 治什么病 |
|---|---|---|---|
| 客户端缓存（TTL/SWR） | 请求次数（客户端不发请求） | 客户端主动 | 请求太多、太慢 |
| 协商缓存（ETag/304） | 大数据体的字节/带宽、后端重复计算 | 服务端配合 | 数据太大、后端太重 |
| 服务端缓存（Redis） | 后端重复计算 | 服务端主动 | 多客户端重复查询 |
| SSE/WebSocket 推送 | 轮询产生的请求 | 服务端主动 | 必须秒级实时 |

> **关键认知**：ETag/304 **不省请求次数**，也不一定能省后端计算——它只省「**大数据体的传输字节**」，且要求「**判断变化很便宜**」，否则就是纯增加复杂度。

## 二、完整决策表

| 需求 | 首选方案 |
|---|---|
| 省请求 + 一定实时性 | **TTL 缓存** / **SWR** |
| 不卡顿 + 数据慢慢变新 | **SWR** |
| 大数据体反复传 | **ETag/304 协商缓存** |
| 多客户端都要省后端计算 | **服务端缓存（Redis）** |
| 必须秒级实时 | **SSE / WebSocket 推送** |
| 用户狂点导致请求多 | **防抖 + 请求合并** |

### 最佳实践组合

```
TTL 缓存 / SWR（前端，主缓存层）
  + ETag 304（后端，大数据体二次过滤）
  + 防抖（前端，控触发频率）
  + （仅当真要实时）SSE 推送
```

## 五、重要原则：优化要对齐瓶颈，避免过度设计

> **优化的价值 = 省下的成本 vs 增加的复杂度。只有当「省下的成本」是真实瓶颈、且「增加的复杂度」可控时，优化才值得做。**

### 反面案例

在「数据变化很慢、定时任务几分钟才跑一次」的场景下：
- 不该去优化「生成时算一次 hash」——它本身很便宜，低频执行，毫无压力
- 为了省它去加「内容比对是否相同、相同就不更新」的逻辑，是**拿复杂度换几乎为零的收益**，属于**过度设计**
- **优化只该对准真正的瓶颈**：这里是大 body 的传输，用 304 解决即可，多一分都是过度设计

### 何时「别优化」的判断标准

- 操作**低频**（非请求路径）→ 成本可忽略，别优化
- 优化会**牺牲可读性/可维护性**，而收益可忽略 → 该砍
- 增加的复杂度 > 省下的成本 → 不做

## 六、一页速览

- **分清楚「省什么」**：客户端缓存省请求、协商缓存省流量、服务端缓存省计算、推送省轮询
- **TTL/SWR**：客户端缓存，简单平衡，SWR 更不卡
- **ETag/304**：只适合「大 + 不常变 + 判断便宜」，用 Redis 存 hash、状态码用 304、生成时同步更新 hash
- **归属**：静态归 CDN/Nginx，动态报表/配置/长文档归后端，实时不用 304
- **别过度设计**：低频低成本操作不值得优化，复杂度要对齐瓶颈
