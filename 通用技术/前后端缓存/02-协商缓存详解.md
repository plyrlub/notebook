# 协商缓存详解

> 上一篇：[01-客户端缓存详解](01-客户端缓存详解.md)
> 下一篇：回到 [00-前后端缓存总览](00-前后端缓存总览.md)

> 受众：已了解强缓存/协商缓存机制（见 **06-Web应用加速**（见知识库） 2.2），本篇聚焦**决策与设计**——什么内容值得 304、Redis hash 设计、归属边界、反过度设计。
> 机制层不重复：缓存头（Cache-Control/ETag/Last-Modified）、Nginx/Spring Boot 配置见 **06-Web应用加速**（见知识库）。

## 1. 核心机制（简要回顾）

```
【生成】定时任务 → 生成数据 → 算 hash → 写文件 + 更新 Redis(report:hash)
【请求1】客户端首次 → 后端读文件 → 200 + 数据 + ETag: "v1"
【请求2】客户端刷新 → 带 If-None-Match: "v1"
        → 后端查 Redis hash：仍 v1 → 304（不传 body，客户端用旧缓存）
                            已变 v2 → 200 + 新数据 + ETag: "v2"
```

### 状态码：用 304，不是 403

- **304 Not Modified** —— 「内容没变，用你缓存的吧」（标准语义）
- ~~403 Forbidden~~ —— 语义是「禁止访问」，与缓存无关，**不要用**

### 为什么用 Redis 存 hash（而不是每次算文件）

- hash 计算有成本，尤其大文件
- 把 hash **前置到生成时算一次**存 Redis，请求时**只做 O(1) 的 Redis 查**，把「判断变化」成本压到最低
- 这是协商缓存划算的核心：**最贵的（算 hash）放到生成时，最便宜的（查 Redis）放到请求时**

### ⚠️ 关键坑：生成时必须同步更新 Redis hash

如果生成新数据却没更新 Redis 里的 hash，会**一直返回 304，用户看不到新数据**（缓存不实时）。

## 2. 适用边界：必须同时满足三个前提

1. **响应体大**（不然省不了流量）
2. **数据不常变**（不然永远 304 不到）
3. **判断变化很便宜**（用 mtime/hash/版本，不重算）

### 谁该管 304 —— 归属边界

| 内容 | 谁管缓存/304 | 后端要不要碰 |
|---|---|---|
| 静态 JS/CSS/图片 | **Nginx / CDN** | ❌ 不碰 |
| 动态生成的报表/统计 | 后端 + Redis hash | ✅ 该管 |
| 低频配置清单 | 后端（变更驱动失效） | ✅ 该管 |
| 归档长文档 | 后端/存储层 | ✅ 可管 |
| 大媒体 | CDN | ❌ 不碰 |
| 实时数据 | 不适用 304 | ❌ 别用 |

> **一句话归属原则**：后端该做 304 的，只有「**动态生成 + 不常变 + 体量大**」的内容。静态的归 CDN/Nginx，实时的根本不用 304。

### 具体适合场景

1. **静态资源（JS/CSS/图片）**：Nginx/CDN 管，除非是「动态计算出来」的静态资源（→ 与报表一致，归后端）
2. **配置/清单类**：需后端设计「变更驱动失效」——列出哪些配置项会改，改动时作废对应 hash
3. **聚合统计/大盘**（分钟级）：定时任务更新，与报表一致
4. **长文本/大文档**（公告、协议、文章）：要归档的持久内容，可 304，存储放 DB/对象存储
5. **大媒体**：CDN 管

### 明确不适合的场景

| 场景 | 原因 |
|---|---|
| 实时聊天消息 | 数据小、变化极快，304 无意义 |
| 实时股票/行情 | 变化太快，永远 304 不到 |
| 实时订单状态 | 变化频繁，etag 老变 |
| 极小响应（几十字节） | 省不了多少流量，纯增加复杂度 |

## 3. 后端实现要点（Spring Boot 示意）

```java
// 1. 生成时：算 hash 存 Redis（低频任务里做，成本可忽略）
String hash = DigestUtils.md5DigestAsHex(bytes);
redisTemplate.opsForValue().set("report:hash", hash);  // ⚠️ 必须与生成同步更新

// 2. 请求时：只做 O(1) 的 Redis 查（请求路径要便宜）
@GetMapping("/api/report")
public ResponseEntity<byte[]> report(
        @RequestHeader(value = "If-None-Match", required = false) String ifNoneMatch) {
    String current = redisTemplate.opsForValue().get("report:hash");
    if (current != null && current.equals(ifNoneMatch)) {
        return ResponseEntity.status(HttpStatus.NOT_MODIFIED).build();  // 304
    }
    byte[] body = reportService.loadFile();
    return ResponseEntity.ok()
            .eTag(current)
            .body(body);
}
```

## 4. 常见踩坑

- 生成时忘更新 Redis hash → 一直 304，用户看不到新数据（本文档核心坑）
- 把 403 当 304 用 → 语义错误，客户端可能不按缓存逻辑处理
- 实时数据套 304 → etag 每次都变，304 形同虚设还多一次判断
- 小响应套 304 → 省不了流量，纯增加复杂度
- 判断变化用「重新计算」而不是「查 hash」→ 请求路径变贵，违背前提 3

## 5. 小结

- 304 只适合「**大 + 不常变 + 判断便宜**」，缺一不可
- 设计核心：**hash 前置到生成时算、请求时只查 Redis**（贵的放低频，便宜的放高频）
- 归属原则：静态归 CDN/Nginx，动态报表/配置/长文档归后端，实时别用 304
- 最贵的教训：**生成时必须同步更新 Redis hash**，否则缓存永不失效
