# 客户端缓存详解

## 1. 思路：将已获取的数据缓存在浏览器

把已获取的数据缓存在浏览器内存/本地存储，设定过期策略，有效期内重复请求直接读缓存。

- **省什么**：请求次数（客户端不发请求）
- **代价**：缓存期间数据可能不是最新

## 2. TTL（Time-To-Live）

```
now - fetchTime < TTL  → 用缓存
否则                    → 重新请求
```

- **优点**：简单、有效、平衡实时性与请求量
- **代价**：TTL 期间数据可能不是最新

```js
// 前端 TTL 缓存示意（内存实现）
const cache = new Map();

async function fetchWithTTL(url, ttl = 60_000) {
  const hit = cache.get(url);
  if (hit && Date.now() - hit.time < ttl) {
    return hit.data;             // 有效期内直接读缓存
  }
  const data = await fetch(url).then(r => r.json());
  cache.set(url, { data, time: Date.now() });
  return data;
}
```

## 3. 升级版：Stale-While-Revalidate（SWR）

> 缓存过期时，**先用旧数据立刻渲染（秒开）**，同时后台重新拉数据，拉到后悄悄替换。

- 用户**永远不卡**（不显示 loading）
- 数据**会慢慢变新**（不像纯 TTL 那样一直旧）
- 请求量**可控**

```js
// SWR 示意：先返回旧数据，后台刷新
let cacheData = null, cacheTime = 0;

async function fetchSWR(url, staleMs = 60_000) {
  const stale = Date.now() - cacheTime > staleMs;
  if (cacheData && !stale) return cacheData;   // 新鲜，直接返回

  const fresh = fetch(url).then(r => r.json());  // 后台拉新
  if (cacheData) {
    fresh.then(d => { cacheData = d; cacheTime = Date.now(); });
    return cacheData;                             // 秒开：先给旧数据
  }
  cacheData = await fresh; cacheTime = Date.now();
  return cacheData;
}
```

> 工程落地：React 生态的 **SWR 库 / React Query** 已把 TTL + SWR + 请求合并 + 缓存共享封装成标准方案，无需手写（见最佳实践）。

## 4. TTL 要分场景，不要一刀切

| 数据类型 | TTL 建议 | 理由 |
|---|---|---|
| 金额/用量（慢变） | 30s ~ 1min | 不追求实时到秒 |
| 任务状态/进度（快变） | 3~5s | 需较快看到变化 |
| 静态配置（几乎不变） | 5min+ | 没必要频繁拉 |

## 5. 配套手段

### 5.1 防抖（debounce）

用户连续操作（输入/滚动/缩放），等**停止后**再发最后一次请求，避免每次都触发。

```js
function debounce(fn, wait = 300) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}
// 输入框搜索：用户停止输入 300ms 后才请求
searchInput.addEventListener('input', debounce(() => doSearch(), 300));
```

### 5.2 请求合并（request coalescing）

短时间内多次请求**同一资源**，合并成一次，结果广播给所有等待者。

```js
let pending = new Map();
function dedupeFetch(url) {
  if (pending.has(url)) return pending.get(url);   // 已有进行中的请求，直接复用
  const p = fetch(url).then(r => r.json()).finally(() => pending.delete(url));
  pending.set(url, p);
  return p;
}
```

## 6. 最佳实践

- **分层使用**：主缓存层用 TTL/SWR，二次过滤用 304，触发控制用防抖（见总览「最佳实践组合」）
- 工程上优先用 **SWR 库 / React Query**：内置 TTL、SWR、请求合并、跨组件缓存共享、自动重试
- 内存缓存适合单页会话数据；**localStorage/sessionStorage** 适合跨会话低频数据（注意容量与序列化成本）

## 7. 常见踩坑

- TTL 一刀切：所有数据同 TTL，导致慢变数据频繁拉、快变数据一直旧 → 按 4 的场景表分级
- 防抖误用于「必须立刻响应」的场景（如点赞），会引入明显延迟 → 防抖只用于可容忍延迟的触发
- SWR 的「秒开旧数据」被误当最新数据展示（如金额），需要 UI 上区分「旧值 + 刷新中」状态
- 内存缓存不做失效管理，页面长期不刷新时内存膨胀 → 给缓存加容量上限或按路由清理

## 8. 小结

- 客户端缓存省**请求次数**，TTL 简单平衡、SWR 更不卡
- TTL 分场景：慢变 30s~1min / 快变 3~5s / 静态 5min+
- 配套防抖（控触发频率）+ 请求合并（同资源合并）
- 工程落地优先 SWR/React Query，别手写轮子
