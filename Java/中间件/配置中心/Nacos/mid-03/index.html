    Nacos 服务注册与发现详解¶

    Nacos 三合一中的服务发现/注册中心能力。讲清：服务数据模型、临时 vs 持久实例、健康检查、订阅推送、权重/保护阈值、CP vs AP 一致性。
    定位：本域放 Nacos 组件本身实现；微服务架构层讲「怎么用 Nacos 搭微服务」→ 00-微服务总览。本机无多实例注册场景，按权威资料整理。

    1. 服务发现是什么、注册中心地位¶

    一句话：服务发现 = 服务提供者把实例注册进注册中心，服务消费者按服务名查/订阅到可用实例列表，再选一个发起调用。

    服务提供者 ——注册实例/心跳——> Nacos注册中心
                                  │ 保存 服务-实例 映射 + 健康状态 + 权重
服务消费者 ←—查询/订阅实例列表—— Nacos注册中心（实例变化推送）
   ↓ 按负载均衡选一个实例
  调用

    为什么注册中心重要：微服务实例数量动态伸缩(启停/扩容/故障)，消费者不能写死 IP，必须动态感知——注册中心是服务间解耦 + 高可用的基石（对应微服务注册/发现）。

    ⚠️ 注册中心≠流量治理引擎/服务网格数据面——它只做"某服务现在有哪些可用实例"，权重/LB 是否真正按权重分发取决于上层框架（如 Spring Cloud LoadBalancer / Dubbo）。

    2. 服务数据模型：服务-集群-实例三层（⭐）¶

    Nacos 提炼的是服务 → 集群 → 实例三层模型（为大规模/多环境设计，比 ZK 的抽象树、Eureka/Consul 的实例级更贴合业务）：

    Namespace(命名空间: 隔离环境/租户)
   └── Group(分组)
        └── Service(服务: 发现单元,消费者按服务名查)
             └── Cluster(集群: 按机房/区域/部署单元分组)
                  └── Instance(实例: ip+port+cluster+元数据)
    层 作用 例子
    Namespace 隔离环境/租户/业务域 dev/test/prod、租户A
    Group 命名空间内继续分组服务 DEFAULT_GROUP
    Service 服务发现单元 user-service
    Cluster Service 下集群分组（机房/区域） default、zone-a
    Instance 具体实例（ip:port + 元数据） 10.0.0.1:8080

    💡 三层模型让多机房部署能在 Cluster 层差异化（不同区域不同配置/权重），是 Nacos 相对 Eureka/ZK 的模型优势。

    3. 临时实例 vs 持久实例（⭐ 核心）¶

    注册实例时的 ephemeral 字段决定实例生命周期与一致性路径（同一 Service 类型必须一致，不能混用）：

    维度 临时实例 (ephemeral=true) 持久实例 (ephemeral=false)
    生命周期 依赖客户端存活，连接断开/心跳超时→自动移除 主动删除才移除，进程死只标不健康
    典型来源 应用运行进程（gRPC/HTTP 客户端注册） 管理流程维护（MySQL/DNS 等服务）
    健康检查 客户端心跳续约（临时服务健康） 服务端主动健康检查
    一致性 AP：Distro 协议（弱一致,靠心跳补偿） CP：JRaft 协议（强一致,持久化）
    持久化 不落盘，仅内存（元数据） 持久化到磁盘/MySQL
    适用场景 K8S/Docker 动态启停、频繁上下线 需要长期稳定、审计的服务
    默认 true（微服务默认临时） 需显式指定

    🔥 关键语义：
    - 临时实例是"运行时状态"，进程挂了 Nacos 自动摘除 → 微服务正确。
    - 持久实例是"管理者维护的持久资源"，进程死也不删（只标不健康）→ 适合数据库这类稳定服务。
    - 别把持久实例当只是"不做健康检查的临时"——它走 CP + 服务端主动健康检查。

    心跳参数（HTTP 兼容客户端）：
    - preserved.heart.beat.interval 心跳间隔
    - preserved.heart.beat.timeout 超时标记不健康
    - preserved.ip.delete.timeout 可删除前超时

    4. 注册与健康检查（心跳/健康检测）¶

    Nacos 健康检查机制按实例类型分两种：

    类型 健康检查 机制
    临时实例 心跳续约 客户端定期心跳，服务端超时未收到→标不健康→再超时剔除；心跳恢复→重新注册
    持久实例 服务端主动健康检查 服务端定期探测（如 TCP/HTTP），失败标不健康

    实例生命周期：注册 → 被发现 → 更新 → 注销 → 清理。
    - gRPC SDK：实例挂客户端连接，连接断开即移除（连接维度的 publisher/subscriber 状态）。
    - 心跳补偿：丢数据靠心跳快速补齐（这就是 AP 弱一致能保可用性的原因）。

    ⚠️ healthy 由心跳/健康检查/manual 更新/节点同步决定；enabled 由运维(可禁用实例)。实例存在 ≠ 会被发现自己，查不到先看 enabled/healthy/cluster 过滤/保护阈值。

    5. 查询 vs 订阅（推送）¶

    动作 适用 机制
    查询 一次性读（启动时读地址、无需监变化） 拉当前 ServiceInfo
    订阅 长期运行应用感知变化 客户端连接下记录 subscriber，返回当前视图，实例变化服务端推送

    订阅推送流程：

    客户端订阅 → 返回当前 ServiceInfo 视图
服务实例变化(上下线/权重/健康) → 服务端向订阅者推送新视图
客户端更新内存缓存(+磁盘缓存)  → 按 diff 通知 listener

    - 推送是"尽力投递"：同一连接生命周期内；推送失败服务端延迟重试，客户端靠重新查询/重连 redo/本地缓存恢复。
    - Java SDK：一键维护连接/监听/订阅/缓存/重连恢复，业务应用优先复用 SDK，别拼内部请求。

    💡 2.x gRPC 长连接 + Push：服务端用 Client 对象记录 gRPC 连接发布了哪些服务/订阅了哪些，构建索引后通过 gRPC Stream 推送 → 比 1.x HTTP 30s 心跳模拟长连接内存/性能都大幅优化（性能提升 10 倍）。

    6. 权重与保护阈值（⭐ 使用）¶

    6.1 权重 weight（实例级）¶

    • 用于客户端权重选择，权重越大分到流量越多；weight<=0 的实例通常被选择逻辑忽略。
    • Nacos 保存/返回权重，是否按权重 LB 取决于上层框架（客户端/Spring Cloud/Dubbo）。

    6.2 保护阈值 protectThreshold（服务级）¶

    防雪崩的可用性保护：当健康实例比例 ≤ 保护阈值(0~1) 时，服务端进入【保护视图】——返回更宽的实例集合（含不健康），避免流量全压到少数健康实例导致压垮。

    # 服务二级 保护阈值(如 0.6 = 健康实例<60%时启用保护)

    ⚠️ 保护阈值是可用性保护，不表示实例真实健康——看到保护阈值生效应排查为什么健康实例骤减（雪崩根因），而非以为系统正常。

    🔑 记忆：权重管"分多少流量"，保护阈值管"别把所有流量都给我"（防雪崩）。

    7. 一致性：Distro(AP) vs JRaft(CP)（⭐ 原理）¶

    Nacos 单集群同时运行两套协议，根据数据一致性要求拆分（这是它的设计精髓）：

    场景 协议 一致性 原因
    临时服务(注册发现) Distro（自研,AP） 弱一致/最终一致 注册中心要尽量可用；CP 半数节点挂了就罢工；配合心跳自动补偿数据
    持久服务实例 JRaft（CP） 强一致 需可靠持久化（磁盘/MySQL），Leader 选举
    配置文件(CP路径) JRaft/内置一致性 强一致(无DB时) 保证配置一致；生产用外置库

    🔗 AP vs CP 取舍（CAP 理论见 02-CAP与BASE理论详解）：
    - 注册发现选 AP：宁可短暂读到不一致，也要保证可用（服务能注册/发现），且心跳能自动补数据。
    - 配置/持久实例选 CP：配置必须强一致，不能出现两节点配置不同的"脑裂"。

    💡 Distro = Nacos 自研最终一致协议（各节点存分片/复制）；JRaft = 对 Raft 的改造实现（Leader 选举 + 日志复制）。生产：临时服务 AP 高可用，持久服务/配置 CP 强一致，各司其职。

    8. 与 Eureka / Consul / ZooKeeper 对比¶

    维度 Nacos Eureka Consul ZooKeeper
    一致性 临时AP(Distro)+持久CP(JRaft) AP CP/Raft CP(ZAB)
    数据模型 服务-集群-实例三层 实例级 实例级(带健康) 抽象树形 K-V
    健康检查 临时心跳/持久主动探测 心跳 主动探测 TCP/session
    自我保护 保护阈值 自我保护 无 无
    配置能力 ✅ 内置 ❌ ✅(KV) ✅(KV手动)
    语言/生态 Java Java 多语言 多语言
    定位 注册+配置+动态DNS 注册 注册+KV+多DC 通用协调
    适用 阿里系Spring Cloud 简化注册 强一致/多DC 分布式协调(锁/队列)

    💡 一句话：Nacos 是"注册+配置"一体、灵活 AG/CP 双模式；Eureka 纯 AP 注册但已闭源维护；Consul 强一致 + KV + 多数据中心；ZK 是通用协调（锁/队列），强一致但注册模型弱。

    9. 面试高频 Q&A¶

    • Nacos 临时 vs 持久实例？ 临时依赖客户端存活(心跳,挂了自动摘,AP/Distro)；持久主动删才移除(服务端探测,CP/JRaft持久化)；微服务用临时。
    • Nacos 一致性 CP/AP？ 临时服务(注册发现)用 AP(Distro,保可用+心跳补偿)；持久实例/配置用 CP(JRaft,强一致)。
    • 健康检查怎么做的？ 临时=客户端心跳超时剔除+恢复重注册；持久=服务端主动健康探测。
    • 查询 vs 订阅？ 查询一次性拉取；订阅长期监听,实例变化服务端推送(gRPC Stream)。
    • 权重和保护阈值？ 权重管流量分配；保护阈值(健康比例过低时)防把流量全压给少数健康实例导致雪崩。
    • Nacos vs Consul/ZK？ Nacos 注册+配置一体+AP/CP；Consul 强一致多DC；ZK 通用协调但注册模型弱。
    • 实例注册不上/查不到？ 先回家 enabled/healthy/保护阈值/cluster 过滤，再检查心跳与连接。
