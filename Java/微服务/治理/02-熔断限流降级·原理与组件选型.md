## 1. 三大手段的本质与区别（⭐）

| 手段 | 解决什么 | 本质 | 判断依据 |
|---|---|---|---|
| **限流** | 瞬时流量超量 | **控制进入速率/并发**，超限拒绝或排队 | 当前 QPS/并发 vs 阈值 |
| **熔断** | 下游持续故障 | **主动切断对下游的调用**，避免故障扩散 | 统计区间错误率/RT 持续超标 |
| **降级** | 故障后给什么响应 | **兜底**（返回默认值/缓存/提示）| 限流/熔断/异常发生后 |

**一句话区分**：
- **限流**：预防"峰"（防自己被打爆）。
- **熔断**：应对"下游挂"（防故障蔓延）。
- **降级**：处理"结果"（兜底返回）。

> 🔑 核心考点：**限流是"挡"、熔断是"断"、降级是"退"**。三者配合——先限流挡超量，下游挂即熔断短暂不可靠调用，被挡/被断的请求走降级兜底。

## 2. 雪崩与级联：为什么要这三者

```
服务A → 服务B → 服务C
            A对B的调用超时/失败 → B线程堆积
            → B线程池耗尽 → B不可用
            → A还请求B → A也堆线程 → A崩溃
            → 层层放大 → 整个调用链雪崩
```

- 一次下游延迟，经**线程堆积**成**级联故障**，最终全链路不可用（**雪崩**）。
- **限流**挡住入口超量、**熔断**切断对故障下游的调用、**降级**兜底——配合**隔离**（线程池/信号量）让故障不穿透本地线程池。

## 3. 限流算法详解（⭐）

| 算法 | 原理 | 优点 | 缺点/注意 | 突发 |
|---|---|---|---|---|
| **固定窗口** | 每区间(如1s)计数超限拒 | 简单 | **临界问题**：区间边界突发 | 允许 |
| **滑动窗口** | 窗口内小桶滚动统计 | 更平滑 | 存N个桶，略耗内存 | 更准 |
| **漏桶** | 请求进桶,按固定速率漏出 | **输出恒定**(削峰) | 拒绝排队(超桶弃),不能处理突发 | 平滑 |
| **令牌桶** | 以固定速率生成令牌,拿令牌才通过 | 允许**少量突发**(桶存token) | 突发上限=桶容量 | 允许 |

### 3.1 固定窗口（临界缺陷）

```
[0-1s 计10个] [1-2s 计10个]   若阈值=10
 最后0.5s 10个 + 后0.5s 10个 = 边界处 20个 突袭 → 临界问题
```

### 3.2 滑动窗口（Sentinel 采用）

把区间再分 N 个小桶，随窗口滑动滚出过期桶：

```
阈值10: [桶][桶][桶]... 窗口滑动, 只统计窗口内 → 缓解临界
```
> Sentinel 的 `LeapArray` 就是滑动窗口实现（见 [01-Sentinel流量控制详解](01-Sentinel流量控制详解.md) §3）。

### 3.3 漏桶（固定速率）

```
         ┌──────────┐   固定速率漏出
请求→ 入桶 →  漏桶(队列) ──────────→ 处理
          └──────────┘    (匀速,超桶拒绝)
```
- **输出恒速**，削峰填谷，适合消息下发、批处理等需匀速的场景。
- 缺点：**不能应对突发**，桶满即拒。

### 3.4 令牌桶（允许突发）

```
固定速率注入token ──→ 令牌桶(容量M) → 请求需要1个token才放行
                       (Burst=桶容量)
```
- 平时积累 token，突发时可用积存 token 处理（**允许短时突发**）。
- 桶容量=最大突发量。**Guava `RateLimiter` 就是令牌桶**。

> 💡 选算法一句话：**固定窗口简单但有临界；滑动窗口平滑(Sentinel)；漏桶恒速削峰；令牌桶允许突发(Guava)**。即时流量用滑动/令牌桶，匀速场景用漏桶。

## 4. 熔断器状态机（⭐）

借鉴电子**断路器**：持续故障 → 断开(拒绝) → 试恢复。

```
Closed(关闭/正常) ── 错误率/慢调用超阈值 ──→ Open(打开/熔断)
      ↑                                              │
      │ 恢复(trial成功count次)                        │ timeWindow 到期
      └──────────── Half-Open(半开/试探) ←────────────┘
```

| 状态 | 行为 |
|---|---|
| **Closed** | 正常放行，统计错误率/RT |
| **Open** | 熔断，直接拒绝（走降级），持续 `timeWindow` |
| **Half-Open** | 窗口到期，放少量试探请求；**成功→Closed**，**失败→回Open** |

**触发参数**：`failureRateThreshold`(失败阈值)、`slowCallRateThreshold`(慢调用阈值)、`minimumNumberOfCalls`(最少请求数,防冷启动误判)、`waitDurationInOpenState`(open持续时间)、`permittedNumberOfCallsInHalfOpenState`(半开试探数)。

> 🔑 面试点：**熔断三状态 + 半开的试探恢复**（防太激进恢复再次打爆 / 防一直熔断不恢复）。Resilience4j / Sentinel / Hystrix 都遵循此状态机。

## 5. 隔离策略：线程池 vs 信号量（舱壁）

把依赖故障隔离在独立"舱壁"里，**不耗尽主线程**：

| 隔离 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **线程池隔离**(Hystrix默认) | 每个下游用独立线程池 | 硬隔离，不阻塞主线程，可降级 | **线程开销大**(每池N线程),上下文切换 |
| **信号量隔离**(Sentinel/Resilience4j) | 用信号量限制到下游的并发数 | 轻量,无线程开销,快 | 不隔离线程阻塞(请求仍占主链接/线程) |

- **线程池**：原子性隔离（故障独占，不影响主泳池），代价重。
- **信号量**：并发数闸（`tryAcquire`），轻量，适合同一 JVM 类依赖 / 高频低时延。

> 🔑 记忆：**线程池=重隔离(隔线程)、信号量=轻隔离(限并发)**。Hystrix 靠线程池，Sentinel/Resilience4j 用信号量（轻）。

## 6. 降级 Fallback 兜底

#### 超时：降级/熔断的先行条件（遗漏补充 ⭐）

> 🔑 很多故障的**根子**是「没设超时」——下游慢但不超时，请求挂起堆积，最后才熔断/限流。

**三大层超时都要设**（从上到下）：

| 层 | 超时 | 说明 |
|---|---|---|
| 连接层 | `connectTimeout` | 建立 TCP 连接超时（防连不上挂起）|
| 读/写层 | `readTimeout` / `writeTimeout` | 读/写响应超时（防下游响应慢拖死）|
| 业务层 | `timeout`（如 HTTP/RPC client timeout）| 整调用超时，兜底 |

```yaml
# HTTP/OpenFeign 超时(连接+读)
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connectTimeout: 2000    # 连接超时 2s
            readTimeout: 3000       # 读超时 3s
```

**超时 → 异常/慢调用 → 触发熔断/降级**：
```
不设超时: 下游慢 → 请求无限挂起 → 线程堆满 → 崩
设超时:   下游慢 → 超时抛异常 → 统计慢调用 → 熔断降级 → 保住自身
```
> 一句话：**超时是降级熔断的'触发源'**。没设超时，熔断机制根本统计不到慢调用/异常。

被限流/熔断/异常后的**兜底返回**：

| 策略 | 返回 |
|---|---|
| 默认值 | 返回默认对象/空列表 |
| 缓存数据 | 返回本地/Redis 旧数据(容忍陈旧)|
| 静态提示 | 返回"服务繁忙"提示/降级页 |
| 关闭功能 | 非核心功能直接关闭(如推荐位)|

> 降级公式：**Fallback 方法 = 兜底逻辑**。核心是把"不可用"转成"可接受结果"，避免异常抛给上游把故障扩散。

## 7. Resilience4j 详解（⭐）

Sentinel 外最主流，**轻量函数式容错库**，Spring Cloud 官方推荐（无 Alibaba 依赖）。

### 7.1 核心模块

| 模块 | 作用 | 等价 Sentinel |
|---|---|---|
| **CircuitBreaker** | 熔断状态机 | 熔断降级 |
| **RateLimiter / Bulkhead** | 限流 / 隔离(信号量或线程池) | 限流/隔离 |
| **Retry** | 重试 | (Sentinel 无) |
| **TimeLimiter** | 超时 | (Sentinel 无)|
| **Fallback** | 兜底降级 | 降级 |
| **Cache** | 读缓存(读穿/写穿) | — |

### 7.2 Java 使用（函数式）

```java
// 熔断器
CircuitBreakerConfig cfg = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)              // 失败比例50%触发
    .waitDurationInOpenState(Duration.ofSeconds(10))  // open 10秒
    .permittedNumberOfCallsInHalfOpenState(3)          // 半开试探3次
    .build();
CircuitBreaker cb = CircuitBreaker.of("pay", cfg);

// 限流器(令牌桶/漏桶)
RateLimiter rl = RateLimiter.of("rl", RateLimiterConfig.custom()
    .limitRefreshPeriod(Duration.ofMinutes(1))   // 刷新周期
    .limitForPeriod(100)                          // 每周期100次
    .build());

// 装饰函数式调用
Supplier<String> decorated = CircuitBreaker.decorateSupplier(cb,
                                () -> payService.doPay());
Supplier<String> withRl   = RateLimiter.decorateSupplier(rl, decorated);
String result = withRl.get();
```

### 7.3 Spring Boot 集成

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
```
```yaml
resilience4j:
  circuitbreaker:
    instances:
      pay:
        slidingWindowSize: 100        # 滑动窗口大小
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
  ratelimiter:
    instances:
      pay:
        limitForPeriod: 100
        limitRefreshPeriod: 1m
```
```java
// 用 Spring Cloud CircuitBreaker 工厂(与 Feign/RestTemplate 集成)
@CircuitBreaker(name = "pay", fallbackMethod = "payFallback")
public String pay(Order o) { return payClient.pay(o); }
public String payFallback(Order o, Throwable t) { return "fallback"; }
```

> 💡 Resilience4j 与 Sentinel 的关键差异：**Resilience4j 轻量函数式 + 模块解耦(重试/超时是独立模块)**，靠注解/装饰器融入现有调用；Sentinel 是**接入层流量治理**(控制台/热点/集群/系统保护更强)。选型见 §8。

### 7.4 重试机制 + 幂等陷阱（遗漏补充 ⭐）

**重试 vs 熔断的关系**：重试给"可恢复的临对"（如下游 500/超时）再试几次，熔断给"持续故障"直接切断——两者配合：**先重试(少量) / 重试仍失效则计入失败→触发熔断**。

**Resilience4j Retry 模块（各装饰器可组合）**：

```java
RetryConfig rc = RetryConfig.custom()
    .maxAttempts(3)                  // 最多重试3次
    .waitDuration(Duration.ofMillis(500))   // 重试间隔
    .retryExceptions(IOException.class, TimeoutException.class)  // 对哪些异常重试
    .ignoreExceptions(IllegalArgumentException.class)             // 这些异常不重试
    .build();
Retry retry = Retry.of("r", rc);
// 组合: 先重试 → 再熔断 → 最后降级(fallback)
Supplier<String> s = Retry.decorateSupplier(retry, CircuitBreaker.decorateSupplier(cb, origin));
```

**Spring Cloud 里结合**（Feign/RestTemplate + Resilience4j）：

```yaml
resilience4j:
  retry:
    instances:
      pay:
        maxAttempts: 3
        waitDuration: 500ms
        retryExceptions: [I/O超时类]  # 只对瞬时故障重试
```

**幂等重试陷阱（生产必知 ⭐）**：

> ⚠️ 只有**幂等操作**才安全重试；非幂等(如扣款/下单)重试会**重复执行**造成脏数据。

| 操作 | 可否重试 | 做法 |
|---|---|---|
| 读操作/查询 | ✅ | 可重试 |
| 幂等写(幂等键/去重) | ✅ | 带幂等键重试 |
| 非幂等写(扣款/转账) | ❌ | 不自动重试,靠人工/幂等号 |

> 对策：**写接口加幂等键**（请求方生成唯一 requestId），下游去重，重试就安全。**面试常问**：为什么读可重试写不能？答——重试可能把同一操作执行多次，非幂等写累计副作用。

## 8. 限流/熔断组件选型总表

| 维度 | Sentinel | Resilience4j | Hystrix(停更) |
|---|---|---|---|
| 定位 | 全链路流量治理 | 轻量函数式容错 | 老牌熔断 |
| 隔离 | 信号量 | 信号量/线程池 | 线程池/信号量 |
| 熔断 | ✅ 三种策略 | ✅ | ✅(仅异常比) |
| 限流 | ✅ QPS+热点+集群整形 | RateLimiter | 有限 |
| 重试/超时 | ❌(需配合) | ✅ 独立模块 | ❌ |
| 控制台/监控 | ✅ 开箱即用 | ❌ | 不完善 |
| 系统保护/热点/集群 | ✅✅ | ❌ | ❌ |
| 生态 | Spring Cloud Alibaba | Spring Cloud 官方 | 弃用 |
| **选型** | 国内微服务主流/要治理+控制台 | **轻量/无 Alibaba 依赖/要重试超时** | ❌ |

> 💡 一句话：**要流量治理全套+控制台 → Sentinel；要轻量函数式+官方轻依赖+重试超时能力 → Resilience4j**。二选一即可，Hystrix 别选。

## 9. 面试高频 Q&A

- **限流/熔断/降级区别？** 限流挡超量、熔断断故障下游、降级兜底响应。
- **限流算法？** 固定窗口(简单/临界)、滑动窗口(平滑,Sentinel)、漏桶(恒速削峰)、令牌桶(允许突发,Guava)。
- **熔断状态机？** Closed→Open→Half-Open→Closed；半开试探恢复防抖。
- **线程池 vs 信号量隔离？** 线程池防火墙重/开销大(Hystrix)；信号量轻/限并发(Sentinel/Resilience4j)。
- **Fallback 有什么用？** 被限/熔/异常时兜底，避免故障扩散。
- **Resilience4j 和 Sentinel？** R4j 轻量函数式+重试超时模块；Sentinel 全链路+控制台+热点集群系统保护。
- **雪崩怎么防？** 限流+熔断+降级+隔离+超时+重试熔断。
