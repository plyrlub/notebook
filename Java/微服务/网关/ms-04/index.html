    内置过滤器详解：断言 / 过滤器工厂 / 对比¶

    承接 01-Spring Cloud Gateway详解。本文把「内置断言、内置过滤器工厂、三种过滤器对比」从详解总篇拆出独立成章，涵盖三个一组主题：
    - §1 内置断言工厂逐个详解
    - §2 内置过滤器工厂逐个详解（含 Shortcut 配置写法）
    - §3 三种过滤器对比：GlobalFilter vs GatewayFilter vs default-filters
    - §4 跨域 / 重试 / 熔断
    关联：内置 GlobalFilter 见 05-内置GlobalFilter深度；限流见 03-限流降级与分层防御（见知识库）；Actuator 观察见 06-Actuator运维实操。

    1. 内置断言工厂逐个详解¶

    断言工厂实现 RoutePredicateFactory，用于创建 Predicate<ServerWebExchange>。多个断言以逻辑 and 组合，全部满足才命中。以下逐个给出配置与匹配说明（配置在 predicates 列表中）。

    1.1 Path — 路径匹配¶

    predicates:
  - Path=/api/order/**,/api/user/*

    - * 匹配一段路径；** 匹配多层路径。
    - 逗号分隔多个路径，满足任一即命中（多路径为 or，与不同谓词之间的 and 不同）。

    1.2 Method — 请求方法¶

    predicates:
  - Method=GET,POST,PUT

    命中条件：请求方法属于列表之一（GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS）。

    1.3 Header — 请求头¶

    predicates:
  - Header=X-Token, ^\d{6}$

    格式：Header=请求头名, 值(支持正则)。请求头 X-Token 存在且值匹配 ^\d{6}$ 时才命中。
    当然也可以多行描述，具体参考源码:
    predicates:
  - name: Header
    args:
      header: key
      regexp: value.*

    1.4 Query — 查询参数¶

    predicates:
  - Query=page, ^\d+$        # 参数名 + 可选正则
  - Query=<param>            # 只要求参数存在

    命中条件：请求含指定查询参数，且（若给正则）值匹配。

    1.5 Cookie — Cookie 匹配¶

    predicates:
  - Cookie=sessionId, ^abc[0-9]+$

    命中条件：请求带指定 Cookie 名，且值匹配正则。

    1.6 Host — Host 域名¶

    predicates:
  - Host=**.example.com, api.other.com

    ** 为多级通配；多个 Host 逗号分隔（or）。常用于按域名分流。

    1.7 Before / After / Between — 时间窗口¶

    predicates:
  - Before=2026-12-31T23:59:59.000+08:00[Asia/Shanghai]   # 在此时间前命中
  - After=2026-01-01T00:00:00Z                            # 在此时间后命中
  - Between=2026-01-01T00:00:00Z, 2026-12-31T23:59:59Z    # 在此区间内命中

    时间格式采用 Java ZonedDateTime，可带 [时区] 后缀（如 [Asia/Shanghai]）或偏移量 +08:00。常用于灰度 / 上线时间窗。

    1.8 RemoteAddr — 客户端 IP 段¶

    predicates:
  - RemoteAddr=192.168.0.0/16, 10.0.0.0/8

    基于来源 IP 的 CIDR 网段匹配，逗号分隔多网段。注意：在反向代理（Nginx）之后，需正确传递 X-Forwarded-For 否则取到的可能是代理 IP。

    1.9 Weight — 加权路由¶

    spring:
  cloud:
    gateway:
      routes:
        - id: order-v1
          uri: lb://order-service
          predicates:
            - Weight=group1, 8
          filters: [ SetStatus=200 ]
        - id: order-v2
          uri: lb://order-service
          predicates:
            - Weight=group1, 2

    同一 group（此处 group1）下按权重比例分发流量，8:2 即 80% / 20%。用于灰度发布 / 金丝雀。权重总和非 100 也可以，按相对比例计算。

    1.10 其它（低频）¶

    断言 配置格式 说明
    CloudFoundry CloudFoundry=rc Cloud Foundry 路由匹配
    ReadBody ReadBody=...,...,... 读取请求体内容匹配（需配合其他处理）

    2. 内置过滤器工厂逐个详解¶

    筛选器工厂实现 GatewayFilterFactory，用于创建 GatewayFilter（仅作用于绑定它的路由）。配置有 Shortcut 短路径 与 name+args 完整写法 两种等价形式。本节按功能分组，并给出必需及可选参数。

    2.1 配置两种写法（Shortcut vs 完整）¶

    filters:
  - AddRequestHeader=X-Id, 123            # Shortcut 短路径（'逗号'分隔参数）

    等价于：
    filters:
  - name: AddRequestHeader
    args:
      name: X-Id
      value: "123"

    适用性：多数工厂支持 Shortcut；部分支持 spEL 或需要复杂参数（如 RewritePath 的正则以命名组方式）时用完整写法更清晰。参数可引用配置属性 ${...} 占位。

    2.2 路径类¶

    过滤器 参数 作用/示例
    StripPrefix parts 去除路径指定前缀段数。StripPrefix=2：/api/order/1 → /order/1
    PrefixPath prefix 路径加前缀。PrefixPath=/api：/user → /api/user
    RewritePath regexp, replacement 正则重写路径。RewritePath=/api/(?<seg>.*), /$\{seg}：/api/user → /user。命名组保留段。
    RedirectTo status, url 重定向。RedirectTo=302, https://new.example.com

    RewritePath yaml 中用命名组的写法须转义 $\{seg}：

    filters:
  - RewritePath=/api/v1/(?<segment>.*), /$\{segment}

    2.3 请求头 / 响应头类¶

    过滤器 参数 作用
    AddRequestHeader name, value 新增请求头
    AddResponseHeader name, value 新增响应头（可做跨域）
    RemoveRequestHeader name 移除请求头（敏感头不下发）
    RemoveResponseHeader name 移除响应头（后端暴露的头可在此清理）
    SetRequestHeader name, value 覆盖请求头值
    SetResponseHeader name, value 覆盖响应头值
    DedupeResponseHeader name, strategy 去重响应头。strategy 可为 RETAIN_FIRST / RETAIN_LAST / RETAIN_UNIQUE（逗号拼接时保留首个/末个/唯一）
    PreserveHostHeader — 转发时保留原始 Host 头（否则可能用目标地址覆盖）

    2.4 请求体 / 参数类¶

    过滤器 参数 作用
    AddRequestParameter name, value 新增查询参数
    ModifyRequestBody 需代码实现 RewriteFunction 以函数式方式改写请求体（如加字段）
    ModifyResponseBody 需代码实现 改写响应体（如统一脱敏 / 结构）

    ModifyRequestBody 示例（DSL / 代码中注册 Rewriter）：

    ModifyRequestBodyGatewayFilterFactory.Config cfg =
    new ModifyRequestBodyGatewayFilterFactory.Config()
        .setRewriteFunction(String.class, String.class, (ex, body) ->
            Mono.just(body.toUpperCase())); // 处理前转换（示意）

    过滤器 参数 作用

    CircuitBreaker name、fallbackUri 熔断降级（配合 Resilience4j，见 §4.3）

    2.5 关联核心过滤器（按需展开）¶

    • LoadBalancerClientFilter（全局）：将 uri: lb://service 解析为具体实例地址，通过 ReactiveLoadBalancer 实现负载均衡。
    • NettyRoutingFilter（全局）：负责将请求通过 Netty 转发至目标地址，WebsocketRoutingFilter 处理 ws:///wss://。
    • RouteToRequestUrlFilter（全局）：把 Route 的 uri 写入 GATEWAY_REQUEST_URL_ATTR，供后续转发过滤器读取。

    内置全局过滤器（Global Filter）对所有路由生效，负责转发、负载均衡、路由到 URL 改写、Websocket 处理等通用能力；开发自定义时通常关注顺序在其中的位置。

    3. 三种过滤器对比：GlobalFilter vs GatewayFilter vs default-filters¶

    三种「过滤器生效方式」经常混淆，这里单独成章对比。核心区分是作用范围与排序来源；三者最终都合并进同一条有序链路执行。

    3.1 三类过滤器总览¶

    维度 GatewayFilter（路由过滤器） GlobalFilter（全局过滤器） default-filters（默认过滤器）
    本质类型 GatewayFilter GlobalFilter 仍是 GatewayFilter
    作用范围 仅绑定的那条路由 所有路由（前提：路由匹配成功） 批量给所有路由套上的 GatewayFilter
    注册方式 配在 routes[].filters 实现接口 + 注册为 Spring Bean，自动生效 配在 spring.cloud.gateway.default-filters
    排序依据 声明顺序（框架分配 order）或显式 @Order / Ordered.getOrder() 声明顺序
    是否有独立 Bean 无 有（GlobalFilter Bean） 无
    典型用途 AddRequestHeader、限流、重试、改路径 统一鉴权、日志、跨域、TokenRelay 全局统一加头、统一 StripPrefix

    3.2 GlobalFilter vs GatewayFilter¶

    维度 GatewayFilter（路由过滤器） GlobalFilter（全局过滤器）
    作用范围 仅匹配的那条路由 所有路由（前提：路由匹配成功）
    注册方式 配在 routes[].filters 或 default-filters 实现接口 + 注册为 Spring Bean，自动生效
    排序依据 声明顺序（框架分配 order） @Order / Ordered.getOrder()
    典型用途 AddRequestHeader、限流、重试、改路径 统一鉴权、日志、跨域、TokenRelay

    3.3 default-filters 澄清¶

    default-filters 不是 GlobalFilter——它配的仍然是路由过滤器（GatewayFilter），只是「批量给所有路由套上」。它本质是 GatewayFilter：没有 Bean、没有 @Order，靠声明顺序排序。真正「全局」的是实现了 GlobalFilter 接口的 Bean。

    spring:
  cloud:
    gateway:
      default-filters:           # 仍然是 GatewayFilter，不是 GlobalFilter
        - AddResponseHeader=X-Gateway, true
        - StripPrefix=1

    3.4 选择指南¶

    场景 选择
    跨切面、所有路由都要的（鉴权、日志、跨域、统一响应包装） GlobalFilter + @Order
    只跟某条路由绑定的业务行为（给某个服务加特定头、某路由限流、重试） 配在 routes[].filters
    需要全局生效但又是配置式的 default-filters

    3.5 设计案例：终端路由过滤器为何是 GlobalFilter¶

    现象：ReactiveLoadBalancerClientFilter、WebsocketRoutingFilter、NettyRoutingFilter、ForwardRoutingFilter 都是 GlobalFilter，但看起来只对特定类型的路由生效（lb://、ws://、http(s)://、forward://）。这种"跟路由绑定"的行为，为什么不用 GatewayFilter 实现？

    机制：全局注册、按 scheme 自选择

    四者对每条路由的链都存在、每个请求都会经过；是否真正做事，由内部检查 GATEWAY_REQUEST_URL_ATTR 的 scheme 决定：

    // 终端路由过滤器的通用模式（简化，各过滤器判断各自的 scheme）
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    URI requestUrl = exchange.getRequiredAttribute(GATEWAY_REQUEST_URL_ATTR);
    String scheme = requestUrl.getScheme();
    if (isAlreadyRouted(exchange) || !"forward".equals(scheme)) {
        return chain.filter(exchange);   // 不是我的 scheme → 直接放行，不做事
    }
    setAlreadyRouted(exchange);          // 是我的 scheme → 接管转发
    return dispatch(exchange);           // Netty 发 HTTP / DispatcherHandler 本地转发 / WebSocket 代理
}

    全局注册 ≠ 全局生效：过滤器在链里的位置是全局的，生效与否由运行时 URI scheme 决定。

    一次 lb://order-service 请求的 scheme 自选择过程（见上图）：

    终端过滤器 检查的 scheme 结果 动作
    ReactiveLoadBalancerClientFilter lb:// ✓ 命中 解析实例地址，URL 改写为 http://ip:port
    WebsocketRoutingFilter ws:// / wss:// ✗ 放行 chain.filter 直通
    NettyRoutingFilter http(s):// ✓ 命中 Netty HttpClient 转发（最终发出）
    ForwardRoutingFilter forward:// ✗ 放行 已路由（isAlreadyRouted），直通

    不做成 GatewayFilter 的设计考量：

    1. URI scheme 已声明意图，零配置派生——路由写 uri: forward:/fallback 时转发行为已确定；若做成路由过滤器，每条 forward 路由还要再配一行 - Forward，同一意图声明两遍。
    2. 终端转发是框架管道，不是用户可选项——每条链的结尾必须有过滤器真正把请求发出。GlobalFilter 保证永远在场、order 固定最大（NettyRoutingFilter 为 Integer.MAX_VALUE），所有用户过滤器一定先执行完；做成路由过滤器则可能漏配或排序错误，导致链跑完请求未发出。
    3. 动态路由 / 服务发现路由没有显式 filter 列表——discovery.locator 自动生成、Nacos 动态下发的路由可能不配任何 filter，转发必须照常工作。
    4. 分类标准是注册与绑定方式，不是生效范围——GatewayFilter 在配置期静态绑定到路由；GlobalFilter 由框架运行期统一拉进每条链。终端路由过滤器属于框架基础设施，归 GlobalFilter 符合定位。

    要点：GatewayFilter / GlobalFilter 的划分依据是注册与绑定方式，不是生效范围。终端路由过滤器"全局注册、按 scheme 自选择"——uri 声明一次，转发行为零配置自动派生。

    3.6 面试追问¶

    • GatewayFilter vs GlobalFilter 本质区别？ 不是执行时机不同，而是作用范围不同——两者最终合并进同一条链统一排序执行。
    • default-filters 是 GlobalFilter 吗？ 不是，它仍然是路由过滤器，只是批量给所有路由套上。
    • GlobalFilter 什么时候注册进链？ 运行时动态合并。GlobalFilter 注册为 Bean 后，启动时收集到列表里，但每次请求都要等路由匹配成功后，才把当前的 GlobalFilter 列表拉进那条路由的链。
    • 断言匹配失败，GlobalFilter 会执行吗？ 不会。断言没匹配上 → 没有 Route → FilteringWebHandler 不被调用 → 过滤器链不存在 → 404 在过滤器链之前就返回了。所以全量请求日志应放在 Gateway 前面（Nginx 或 Servlet Filter 层）。
    • 断言和过滤器能不能同时生效？ 不能。断言是匹配条件，过滤器是处理逻辑——断言先跑完、选出路由，过滤器才开始跑。两者是串行先后关系。
    • 终端路由过滤器（Netty / Forward / Websocket / LoadBalancer）为什么是 GlobalFilter 而不是 GatewayFilter？ 划分依据是注册与绑定方式而非生效范围；全局注册保证永远在场、order 固定在链尾，生效范围由 URI scheme 运行时自选择（全局注册、按需生效），使 uri: forward://xxx / lb://xxx 零配置自动工作。
    • Route 可以理解为"服务集合"吗？ 不准确。Route 是一条转发规则（断言 + URI + 过滤器）；"服务集合"是 lb://服务名 背后注册中心里的多实例集群，运行时由 LoadBalancer 解析。N 条 Route 代理 N 个服务，同一服务也可配多条 Route。
    • uri: forward:/xxx 是不是触发了两次转发？ 真正移动请求只有一次（ForwardRoutingFilter 本地移交 DispatcherHandler，不出网关）；URL 属性被改写一次（RouteToRequestUrlFilter），路径被解析两次（Gateway 断言 + WebFlux HandlerMapping），但第二次是框架内部找 Handler，不是 Gateway 路由匹配重复执行。

    4. 跨域 / 重试 / 熔断¶

    spring:
  cloud:
    gateway:
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "https://front.example.com"   # 限定来源, 一般不用 *
            allowedMethods: "*"
            allowedHeaders: "*"
      routes:
        - id: retry-route
          uri: lb://backend
          predicates: [ Path=/api/** ]
          filters:
            - name: Retry
              args:
                retries: 3                       # 最多重试 3 次
                statuses: BAD_GATEWAY, SERVICE_UNAVAILABLE   # 500/502/503 重试
                methods: GET                     # 默认只重试幂等方法(GET)
                backoff:
                  firstBackoff: 10ms
                  maxBackoff: 1s
                  factor: 2                      # 退避指数
            - name: CircuitBreaker
              args:
                name: cb
                fallbackUri: forward:/fallback   # 熔断后降级地址
    机制 说明 注意
    CORS 网关统一配置跨域，避免各服务各自配置 来源尽量限定具体域名；* 与携带凭证叠加不安全
    Retry 对可重试状态码（502/503）退避重试 默认仅重试幂等方法（GET）；POST 需谨慎避免重复提交
    CircuitBreaker 配合 Resilience4j 做服务级熔断 + fallback fallbackUri: forward:/fallback 指向本地兜底接口
