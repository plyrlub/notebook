    3. 核心知识点¶

    3.1 为什么需要数据库版本管理¶

    开发中最常见的三个痛点：

    1. 环境不一致：开发、测试、生产环境的表结构差异越滚越大，最后"本地能跑、线上爆炸"。
    2. 变更无法追溯：谁改的、什么时候改的、为什么改——全靠记忆和聊天记录。
    3. 协作冲突：多人同时改库，互相覆盖。

    传统 vs 版本管理：

    方式 改表怎么做 结果
    传统 手写 SQL 发给 DBA，聊天记录留存 没人记录版本，无法追溯
    版本管理 带版本号的脚本进 Git，工具按序自动执行 可重放、可追溯、可审计

    核心思想一句话：把数据库结构当代码管（"数据库的 Git"）。每次变更写成带版本号的脚本，提交进 Git，由工具按顺序自动执行，任何环境都能重放。

    类比：代码没版本管理 = 压缩包发来发去；数据库没版本管理 = 结构改了没人记得，出了事对不上。

    3.2 主流工具与选型 ★¶

    工具 语言生态 特点 适用
    Flyway Java（Spring 首选） SQL 优先、极简、强版本控制 传统 SQL 数据库，与 Spring Boot 无缝集成
    Liquibase Java changelog 抽象、支持 50+ 数据库 多数据库、需要精细编排（前置条件/上下文/流程）
    Alembic Python 与 SQLAlchemy 深度集成 Python 技术栈
    Goose Go 轻量、支持回滚 Go 微服务
    Atlas / Skeema 声明式 声明目标状态，自动生成迁移 云原生、K8s 场景

    为什么以 Flyway 为主？
    - 与 Spring Boot 集成度最高，几乎零配置。
    - 设计哲学极简：编号 SQL 文件 + flyway migrate，团队会写 SQL 就能用。
    - 社区成熟、生态最广，教程和踩坑资料多。

    什么时候考虑 Liquibase？
    - 需要用一个 changelog 同时面向几十种异构数据库（Flyway 支持 20+，Liquibase 50+）。
    - 需要 preconditions（前置条件）、contexts（上下文）、flows（流程编排）等精细控制。
    - 代价：要学 XML/YAML/JSON changelog 语法，比 Flyway 重。

    结论：常规 Spring Boot + 单/少数数据库 → Flyway 足够；跨异构数据库、复杂编排 → Liquibase。多数团队选 Flyway。

    3.3 Flyway 核心机制¶

    脚本命名约定¶

    前缀 含义 用法
    V{版本号}__{描述}.sql 版本化迁移，只执行一次 结构变更（建表/加列/改类型）
    R__{描述}.sql 可重复迁移，内容变化则重跑 视图、存储过程、数据修复
    U{版本号}__{描述}.sql 撤销迁移（配 undo；社区版不支持自动回滚） 回滚

    示例目录：

    src/main/resources/db/migration/
├── V1__create_user_table.sql
├── V2__add_email_to_user.sql
├── V3__modify_user_status.sql
└── R__user_view.sql

    元数据表 flyway_schema_history¶

    Flyway 的"心脏"，记录所有已执行迁移：版本号、描述、脚本名、checksum（脚本内容哈希）等。

    • checksum 校验：已执行过的脚本一旦被改 → 校验失败 → 防止"偷偷改历史"。
    • 执行流程：启动 → 连库 → 查历史表 → 扫描脚本 → 计算待执行列表 → 按版本排序 → 依次执行 → 更新历史表。
    • 惰性/幂等：Flyway 只执行"没跑过"的版本化脚本；R__ 脚本每次启动都比对内容，变了才重跑。

    常见命令¶

    命令 作用
    flyway migrate 执行迁移（Spring Boot 启动时自动触发）
    flyway info 查看迁移状态
    flyway validate 校验 checksum，检查历史脚本是否被篡改
    flyway baseline 旧库接入时打基线，跳过历史版本
    flyway repair 修复校验和/错误记录（谨慎使用）
    flyway clean 清空数据库（仅限开发/测试，生产禁用）

    3.4 Spring Boot 集成实战¶

    ① 加依赖¶

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>

    说明：spring-boot-starter-jdbc 提供数据源；flyway-core 是 Flyway 本体。花 Boot 自动装配会检测到 dataSource 后默认启动 Flyway。若用 MySQL，Flyway 子模块按需引入。

    ② 配置 application.yml¶

    spring:
  datasource:
    url: jdbc:mysql://localhost:3306/demo
    username: demo
    password: demo
  flyway:
    enabled: true                # 是否启用（默认 true）
    baseline-on-migrate: true    # 已有旧库时建议开启（空库自动建历史表）
    locations: classpath:db/migration   # 脚本目录
    clean-disabled: true         # 生产环境务必禁用 clean（防误清库）

    ③ 放脚本，启动即执行¶

    把 V1__...、V2__... 放到 db/migration 目录，应用启动自动迁移。

    ④ 旧库接入（baseline）¶

    已有数据库（非空 schema）直接启动会报 Found non-empty schema(s) without baseline。解决：

    flyway baseline -baselineVersion=1

    让 Flyway 把当前库结构当作基线，之后只执行新增脚本。不重建、不动已有表。

    关键点：baseline-on-migrate: true 只对"空库"自动建历史表；非空旧库必须先手动 baseline。

    3.5 大表变更与锁表问题 ★¶

    这是很多团队对"自动迁移"最大的担忧——有道理，但风险在 SQL 本身，不在工具。Flyway 只是按顺序执行你写好的脚本，它不会替你生成 SQL。

    为什么 ALTER 会锁表（MySQL）：
    - ALTER TABLE ... MODIFY COLUMN（改字段类型）可能触发全表重建。
    - 给大表加带默认值的 NOT NULL 列，某些版本/引擎会重建表。
    - 即使不重建，DDL 也可能长时间持有元数据锁（MDL），阻塞所有读写。

    解药一：MySQL 8.0 原生在线 DDL¶

    ALTER TABLE users
    ADD COLUMN age INT NULL,
    ALGORITHM=INPLACE, LOCK=NONE;   -- 不阻塞读写

    说明：ALGORITHM=INPLACE 原地改不加表重建，LOCK=NONE 不锁读写。MySQL 8.0 对部分操作支持 ALGORITHM=INSTANT / INPLACE + LOCK=NONE，可在线完成无需停机。

    解药二：专门的在线 DDL 工具（更稳）¶

    工具 出品 原理
    gh-ost GitHub 无触发器，通过 binlog 流式复制数据，改完瞬间切换表
    pt-online-schema-change Percona 触发器 + 影子表，老牌成熟

    两者共同思路：建一张影子表 → 在新表上做结构变更 → 持续同步数据 → 原子切换表名，全程业务无感知。

    关键点：这些工具的调用命令可以写进 Flyway 脚本。Flyway 负责版本和顺序，真正执行的是在线变更——两者互补，不冲突。

    解药三：把执行权拿回人手里¶

    Flyway 默认行为是"应用启动即执行"，这在生产环境是危险的：

    • 代码里加了 V3__modify_column.sql → 应用一发布 → 启动自动执行 → ALTER 锁表 → 生产挂了。

    成熟团队用法：
    - 生产环境：迁移作为 CI/CD 里的独立、显式步骤，由人触发、可卡审批（flyway migrate 或 Maven 插件单独跑），绝不让应用启动时裸跑。
    - 开发环境：才让应用启动时自动跑，方便迭代。

    3.6 零停机迁移 Expand/Contract ★¶

    一次"改字段类型 + 删列"的大变更，如果一把梭，风险极大。标准做法拆成安全小步：

    阶段1 Expand（扩）:  新增列，允许为空          → 无锁、向后兼容
阶段2 Migrate（迁）: 分批回填数据（后台任务）   → 不阻塞业务
阶段3 Switch（切）:  应用切换到用新列           → 发版，两列并存
阶段4 Contract（缩）: 等代码确认后再删旧列       → 绝不在同一版本里删

    对应 Flyway 脚本：

    -- V4: 扩 - 新增列，允许为空
ALTER TABLE orders ADD COLUMN status_new VARCHAR(20) NULL;

-- (后台任务) 分批回填: 每次少量、可断点续跑
UPDATE orders SET status_new = status
WHERE status_new IS NULL
LIMIT 1000;

-- V5: 缩 - 代码确认已切换到新列后，再删旧列
ALTER TABLE orders DROP COLUMN status;

    说明：每一步都是向后兼容的小变更，任何一步失败都可以停住回退，不需要"锁表 + 停机窗口"。回填 LIMIT 分批避免长时间持锁。第 5 步（删列）务必在应用代码确认不再用旧列之后才执行。

    3.7 国内使用现状与选型思考¶

    为什么国内 Flyway 少见？
    - DBA 主导文化：很多公司建表/改表由 DBA 或运维手动执行，开发碰不到生产库，"应用自动迁移"模式用不上。
    - 快速开发平台生态：国内大量项目基于若依这类平台，建表靠代码生成器一次性生成 SQL 导入，没人愿意维护版本脚本。
    - 教程缺失：国内 Java 教程集中在 Spring Boot + MyBatis 三件套，数据库 DevOps 工具几乎不出现。
    - 团队规模：小团队单库、几个人改一个库，聊天记录管理"够用"，没到需要版本管理的痛感。

    但它仍是"该用而没用"的技术：

    Flyway 与持久层框架（MyBatis / JPA）完全无关——它管的是纯 SQL 脚本执行。国内 MyBatis 系采用率超过 85%，Spring Data JPA 仅约 6%，但这不影响 Flyway 搭配任何一个：
    - JPA 团队不用 Flyway → 退化成危险的 ddl-auto=update（自动改表、无记录、不可控）。
    - MyBatis 团队不用 Flyway → DDL 全靠手写散落各处、口口相传。

    恰恰因为 MyBatis 团队连 SQL 都是手写的，把这些 DDL 版本化成本几乎为零，反而更该用。

    与 Python 工具（Alembic）对比：

    维度 Alembic（Python） Flyway（Java）
    生成方式 可自动 diff 生成迁移 手写 SQL，强版本控制
    哲学 与 ORM 绑定 与数据库绑定，ORM 无关
    锁表风险 同样存在（在 SQL 里） 同样存在（在 SQL 里）

    两者风险同源——风险在 DDL 本身，用什么工具都得靠在线 DDL / Expand-Contract 规避。工具管记录和顺序，人管审查和风险。

    3.8 常见坑¶

    • 改已执行的脚本 → checksum 不匹配，Flyway 拒绝启动。正确做法：不修改 V{n}，新增 V{n+1} 修正。
    • 生产环境 clean → 清库（灾难）。clean-disabled: true。
    • 应用启动裸跑迁移 → 大表 DDL 锁表。生产用 CI/CD 显式步骤。
    • 误以为 Flyway 能自动回滚 → 社区版不支持，靠备份 + 补偿迁移。
    • 旧库不 baseline 直接上 → Found non-empty schema(s) without baseline 报错。
    • DDL 隐式提交 → MySQL/Oracle 的 DDL 不参与事务回滚，别指望"失败自动回滚"。

    4. 最佳实践¶

    • 已发布的迁移脚本不可修改——发现问题就新增 V{n+1} 修正脚本，而不是改 V{n}。
    • 生产环境不让应用裸跑迁移——放 CI/CD 显式步骤，先备份再执行。
    • 给 Flyway 建专用最小权限账号——不要用 DBA 账号跑迁移。
    • 大表变更走在线 DDL / Expand-Contract——不依赖"停机窗口"。
    • 脚本要幂等：CREATE TABLE IF NOT EXISTS 等。
    • 回滚策略：备份 + 补偿迁移（V{n+1}__undo_change.sql），不依赖自动回滚。
    • 多数据库：按 db/migration/common + db/migration/mysql 分目录，用 profile 切换。
    • 每批小步走：一次迁移只做一个逻辑变更，别混改。
    • 脚本开头注释：说明修改原因和影响范围，便于回溯。

    5. 常见踩坑¶

    • 生产大表 DDL 直接锁表 → 用 gh-ost / pt-osc / MySQL 8.0 原生在线 DDL。
    • 一次迁移里"改类型 + 删列 + 加约束"一把梭 → 拆成 Expand/Contract 多步。
    • 生产用应用账号（DBA 权限）跑 Flyway → 建专用最小权限账号。
    • flyway clean 误执行 → 生产 clean-disabled: true，权限收紧。
    • 改历史脚本导致 checksum 冲突 → 加新版本脚本，别回头改。

    6. 小结¶

    • 数据库版本管理 = "数据库的 Git"，把 DDL 当代码管。
    • Flyway 为主（SQL 优先、Spring Boot 零配置），Liquibase 为辅（多数据库、精细编排）。
    • 核心机制：命名（V/R/U）+ flyway_schema_history + checksum 防篡改。
    • 锁表的担忧是对的，但解药不是放弃工具：在线 DDL（gh-ost / pt-osc / MySQL 8.0 原生）+ Expand/Contract + 人工把控执行时机。
    • 风险在 SQL 本身，不在工具；工具管记录和顺序，人管审查和风险。
    • 国内用得少是团队习惯问题，不是技术适配问题；与 MyBatis/JPA 都无关，都可配合。
