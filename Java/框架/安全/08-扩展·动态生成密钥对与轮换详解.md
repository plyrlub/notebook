## 1. 动态生成密钥对（★ 核心）

**为什么要"动态"生成**：密钥不该写死在代码/配置文件，而应在部署时或运行时生成、存到安全介质（KeyStore/HSM），并支持**轮换重建**。这正是前面 springboot 配置篇密钥管理那档"Vault 存主密钥 + 配置存密文"的底层——非对称场景里，密钥对是平台动态造的。

### 1.1 KeyPairGenerator 生成（RSA / EC / EdDSA）

核心 API：JCA 的 `KeyPairGenerator` + `initialize` + `generateKeyPair()`。

```java
import java.security.*;
import java.security.spec.ECGenParameterSpec;

// —— RSA（最通用，握手/加解密/签名都行）——
KeyPairGenerator g = KeyPairGenerator.getInstance("RSA");
g.initialize(2048);                    // NIST 建议 ≥2048；越高越慢
KeyPair rsa = g.generateKeyPair();
PublicKey pub = rsa.getPublic();
PrivateKey prv = rsa.getPrivate();

// —— ECC（密钥短、快，移动端好，EdDSA 更推荐签名）——
KeyPairGenerator ec = KeyPairGenerator.getInstance("EC");
ec.initialize(new ECGenParameterSpec("secp256r1"));   // 等价 P-256
KeyPair ecc = ec.generateKeyPair();

// —— EdDSA（JDK15+ 部分支持，必要时 Bouncy Castle）——
KeyPairGenerator ed = KeyPairGenerator.getInstance("Ed25519");
KeyPair eddsa = ed.generateKeyPair();
```

> **为什么推荐 ECC/EdDSA**：ECC 256bit≈RSA 3072bit 强度且更快；EdDSA 签名实现不易出错、抗侧信道。性能好、现代标准。但**兼容性**旧系统可能只要 RSA——见踩坑。
>
> **initialize 两种方式**：`initialize(int keysize)`（RSA/EdDSA 用）与 `initialize(AlgorithmParameterSpec)`（EC 用曲线参数）。建议带 `SecureRandom`：`g.initialize(2048, new SecureRandom())`——确保用 CSPRNG。

### 1.2 密钥存储：禁止明文，用 KeyStore

**绝对禁止**把私钥明文写文件（泄露=全暴露）。用 Java **KeyStore**（PKCS12 更通用，Java9+ 默认）以密码保护存储。

> **写入最稳的姿势：用 keytool 生成+存库**（见 1.3），代码只需**读回**——避免手写证书链（Java 标准 API 生成自签证书要 `sun.security` 内部类或第三方库，代码冗长易错）。生产用 keytool + KMS/KeyStore 密码注入最可靠。

**读回（核心可抄代码）**：

```java
import java.security.*;
import java.security.KeyStore.*;
import java.nio.file.*;

// 1. 加载 KeyStore（p12 由 keytool -genkeypair 生成）
KeyStore ks = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("my.p12"))) {
    ks.load(in, "yourKeystorePassword".toCharArray());
}

char[] pwd = "yourKeystorePassword".toCharArray();
// 2. 取私钥（需强转，见踩坑）
PrivateKey prv = (PrivateKey) ks.getKey("myalias", pwd);
// 3. 取公钥/证书
Certificate cert = ks.getCertificate("myalias");
PublicKey pub = cert.getPublicKey();
```

> 若确实要用纯代码生成并写入（不用 keytool），需自签证书链——Java 标准 API 做 X.509 自签要 ```sun.security.x509.Date``` 等内部类（不受官方保证 API），**建议改用 keytool 或 Bouncy Castle 的 `X509v3CertificateBuilder`**。见踩坑。

> ⚠️ **未实测标注**：以上读回代码基于标准 KeyStore API（结构正确），本机未运行验证——生产使用前本机跑一遍。生成自签证书代码未展开（不建议手写），如需见 Bouncy Castle API。

### 1.3 keytool 命令行（懒人首选）

Java 自带管理密钥库工具，生成 + 存库一步到位：

```bash
keytool -genkeypair -alias mykey -keyalg RSA -keysize 2048 \
        -storetype PKCS12 -keystore my.p12 -validity 365 -dname "CN=MyApp"
```

- `-alias`：密钥别名，库内唯一标识
- `-keyalg`：RSA / EC（`-groupname secp256r1`）
- `-keysize`：RSA 2048+；EC 用 `-groupname`
- `-storetype`：PKCS12（推荐，跨平台）或 JKS
- `-validity`：天数，证书有效期
- 注意：keytool 需要终端输入 storepass；脚本化用 `-storepass` 但注意命令会被 ps 看到——生产走 KMS/Env 注入。

> **运行期读回**：`KeyStore.load(输入流, 口令)` → `ks.getKey(alias, pwd)` 拿私钥、`ks.getCertificate(alias).getPublicKey()` 拿公钥。见踩坑"读回类型强转"。

## 2. 密钥轮换（★ 你认可的核心里解）

### 2.1 为什么轮换：对称 vs 非对称的差异

- **HMAC/对称（HS256）**：签发方与验证方共用同一密钥——换密钥时**所有验证方都得同步更新**，无法安全无感轮换。这是 JWT 高安全系统弃用 HS、改用非对称（RS256/ES256）的主因。
- **非对称（RS256/ES256）**：签发方用**私钥**签名，验证方只有**公钥**验签。**换私钥不影响验证方**（公钥不变仍能验旧 token），可零停机平滑轮换。

### 2.2 零停机轮换的关键：kid + 多版本密钥仓库

JWT Header 带 `kid` 标识"这次用哪把密钥"；验证端维护**多个有效密钥版本**，用 kid 选对应公钥验签。

```java
// Header 加 kid
{
  "alg": "RS256",
  "kid": "key-2026-08-A"   // 告诉我用哪个版本验
}
```

轮换时间轴（无停机）：

```
10/01  用 keypair_A 签发，验证端只持 A
10/10  生成 keypair_B，验证端加入 B(作次级)
       新签发→B；旧 token→A 仍能验（重叠期）
10/20  A 的 token 全过期/生命周期结束，删除 A
```

| 时间点 | 签发用 | 验证端持有 | 动作 |
|---|---|---|---|
| 10/01 | A | [A] | 初始 |
| 10/10 | B | [A, B] | 上 B、新签发用 B，老 token 撞 A 仍验 |
| 10/20 | B | [B] | A 过期删除 |

> **重叠期约束**：重叠时长 ≥ 最长 token 生命周期，确保已签发 token 在轮换后仍能验到过期。删除旧 key 前必须确认所有该 key 签发的 token 已失效。

### 2.3 唯一分发点 + 独立轮换

- 公钥通过**统一端点**（`/public-key` 或 JWKS）发布，验证方/加密方都从这里拿"当前有效公钥集"。轮换私钥只需更新这个端点，**一处变更所有调用方自动拿到新公钥**。
- **签名密钥对与加密密钥对分开两套**，各自独立 kid/轮换/撤销——不要共用一对（见 4.1）。

## 3. 混合加密流程（★ 纠正常见方向误区）

### 3.1 先纠正：加密 vs 签名的方向铁律

| 动作 | 用什么密钥 | 谁能解开/验证 |
|---|---|---|
| **加密数据** | 用**对方**的公钥 | 只有**对方私钥**能解 |
| **签名** | 用**自己**的私钥 | 只有**自己公钥**能验 |

> 常见误区：「后端用私钥加密盐给前端，前端用公钥拿到盐」——**方向错**。你私钥加密的东西只有你**公钥**能解，而公钥公开，等于没加密。正确方向：**前端生成对称密钥，用"公钥"加密后发后端，后端"私钥"解开**。

### 3.2 为什么混合：性能和长度

- **公钥加密（RSA）有长度硬限**：RSA-2048 一次最多加密约 **245 字节**（留 OAEP 填充），不适合直接加密大文本/整条数据。
- **对称加密（AES）**：快、无长度问题，但有密钥分发难题。
- **结合**：数据用 AES 对称加密（快不限长），**只把对称密钥用 RSA 加密**（够短）安全传递——**混合加密（Hybrid Encryption）**。

### 3.3 完整流程（前端生成对称密钥版）

```
后端                         前端(调用方)
 │  生成 RSA 密钥对，私钥内存持有
 │ ──── /public-key 分发公钥 ────▶ 拿公钥
 │                               生成随机 AES 对称密钥 key
 │                               用「公钥」加密 key → RSA(key)
 │                               用 key 加密数据 → AES_cipher(data)
 │ ◀──  RSA(key) + AES_cipher(data) ──
 │ 用「私钥」解出 key
 │ 用 key AES 解密 → 明文
```

**前端伪码**（对称密钥由前端生成，正是你认可的点）：

```
key = AES.randomKey()                // 前端生成随机对称密钥(你说的"盐/会话密钥")
encryptedKey = RSA_encrypt(pub, key) // 用后端公钥加密这个密钥
ciphertext = AES_encrypt(key, data)  // 用对称密钥加密整条数据
send(encryptedKey, ciphertext)       // 两者都发给后端
```

**后端承接**（Java）：

```java
// 入参来自请求体：encryptedKey(公钥加密后的对称密钥)、iv、ciphertext
// 假设已：解出对称密钥
Cipher rsaDec = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
rsaDec.init(Cipher.DECRYPT_MODE, prv);
byte[] key = rsaDec.doFinal(encryptedKey);          // 得到 AES 密钥(对称密钥)

// AES-GCM 解密数据（参考 06 篇完整示例）
Cipher aes = Cipher.getInstance("AES/GCM/NoPadding");
SecretKeySpec sk = new SecretKeySpec(key, "AES");
aes.init(Cipher.DECRYPT_MODE, sk, new GCMParameterSpec(128, iv)); // iv 随请求一起发来的随机向量
byte[] plain = aes.doFinal(ciphertext);             // 明文
```

> `RSA/ECB/OAEPWithSHA-256AndMGF1Padding` 的 `ECB` 字样在单块加密时无关紧要（不分组）——RSA 加密只有一块，`ECB` 是 JCA 填充模式的占位，别误解成块加密。
>
> **为什么用 OAEP**：RSA 直接用 PKCS1 v1.5 填充有 Bleichenbacher 攻击风险，现代标准用 OAEP（`RSA/ECB/OAEPWithSHA*/MGF1Padding`）。见踩坑。
>
> **哪边生成对称密钥**：取决于"谁是需要它的那一端"。前端生成（后端私钥解出）适合"前端加密、后端解密"；TLS 场景反之。核心不变：**对称密钥被非对称安全送达即可**，理论见 **07-非对称加密·密钥交换与数字签名详解**（见知识库） 的 RSA 密钥交换节。

## 4. 安全防御落地（★ 接口设计）

### 4.1 签名密钥与加密密钥必须分开

**不要共用一对**密钥既签名又加密：
- 数学上，RSA 同一密钥对既作加密又作签名存在**理论攻击面**（某些方案可被分析），业界惯例**按用途隔离**。
- 实务上，分两套才能**独立轮换/撤销**：签名密钥泄露和加密密钥泄露要能分开处置。

落地：
```java
KeyPair signKey   = gen("RSA");  // 用 kid "sign-..."，只管签名/验签
KeyPair encKey    = gen("RSA");  // 用 kid "enc-..."，只管加密/解密
```
发布时：JWKS/sign 端点给验签公钥；/public-key 给加密公钥——各自独立、可分别轮换。

### 4.2 公钥接口：缓存 + IP 限流（防高频拖垮）

你提的"缓存"与"限流"都是对的，且分层清楚：

- **缓存（顺带就是防爆破手段）**：公钥本就不保密，接口压力是唯一风险。缓存后即使被刷，后端**不重新生成、不重算**，直接从缓存返回，攻击只打到缓存读。
  - **会话级 vs 方法级**：取决于**密钥是否按客户端区分**。
    - 密钥**所有人共用**（最常见的通用一对）→ **方法级缓存**即可（所有人一份，存一段时间），简单高效。
    - 密钥**按用户/会话分配**（per-user，密钥泄露只影响单用户）→ **会话级缓存**，key = `uid`/`sessionId`，随会话失效。**你的"密钥不同人不同 → 会话级 + key用uid"判断正确**，但前提是你真按人分密钥；否则方法级更优，别过度设计。
- **IP 限流**：单 IP 每秒 N 次，超限返回 **429**，加全局限流兜底，再可配 CDN/WAF 层。

### 4.3 机密/解密接口：防爆破（你的验证码思路正确）

真正要保护的不是"读公钥"，而是**解密接口/验签接口**——攻击者可发随机/恶意密文狂打，**RSA 解密计算贵，CPU 打满 = DoS**。你的方案是对的，我按防御栈补全：

| 层次 | 手段 | 作用 |
|---|---|---|
| 入口 | **验证码/滑块/行为校验** | 挡脚本批量，爆破成本提高到不可接受（你认可） |
| 应用 | **限流**（IP + 账号 + 全局限流，滑动窗口） | 拖慢高频 |
| 密钥 | 解密前**先验格式/长度**，别盲目 RSA 解密 | 防计算型 DoS |
| 响应 | **失败统一**、防 oracle 差异（成功/失败不要可区分） | 防侧信道/信息泄露 |

- **验证码用在哪里**：验证码/滑块**留给真正需要身份的入口**（注册、登录、提交机密数据、解密）。**公钥接口是公开的，别加验证码**（多余 + 影响体验），它用缓存+限流就够。
- **防 oracle**：解密失败和成功**不可被外部区分**（返回一致），否则攻击者能做 padding oracle/穷举探测。

### 4.4 alg 混淆攻击（必须防）

攻击者把 JWT header 的 `RS256` 改成 `HS256`，拿**公开的 RSA 公钥当 HMAC 密钥**伪造签名——若校验逻辑信任 header 的 alg，会接受伪造 token。

```java
// 错误：读 header alg 决定验签算法
// 正确：写死允许的算法白名单
Set<String> allowed = Set.of("RS256", "ES256");
String alg = header.getAlgorithm();
if (!allowed.contains(alg)) throw new SecurityException("alg not allowed");
// 并：RSA(非对称) 与 HMAC(对称) 校验走完全分开的代码路径
```

**要点**：固定算法白名单 + HMAC 与 RSA 校验代码路径分离；不信任 header 传递的算法选择器。

## 5. 踩坑速查

- **RSA 长度**：RSA-2048 一次只能加密约 245 字节 → 加密长文本必须走**混合加密**（AES 加密数据 + RSA 加密对称密钥），别直接 RSA 加密全文。
- **私钥明文存储**：绝对禁止；用 KeyStore/HSM/KMS 加密保护。私钥泄露=永久加密被破。
- **RSA 填充**：加密用 **OAEP**（`RSA/ECB/OAEPWithSHA-256...`），别用脆弱的 PKCS1 v1.5 直接加密（Bleichenbacher）。
- **密钥未按用途隔离**：签名/加密**分两套**密钥对，别共复用一对；独立 kid/轮换。
- **轮换无重叠期**：删除旧 key 前先保证其签发 token 全过期；重叠时长≥最长 token 生命周期。
- **alg 混淆**：写死 `RS256/ES256` 白名单，HMAC 与 RSA 校验分离。
- **解密接口未防 oracle**：失败/成功响应要统一，防侧信道；先验格式/长度再解密。
- **KeyStore 读回类型**：`getKey()` 返回 `Key` 需强转 `PrivateKey`；`getCertificate()` 拿公钥；PKCS12 数组索引从 0。
- **私钥写入勿手写自签证书**：Java 标准 API 做 X.509 自签依赖 `sun.security` 内部类（非官方保证）；写入用 **keytool** 或 Bouncy Castle `X509v3CertificateBuilder`。
- **Ed25519 兼容**：JDK15+ 部分支持；老旧 JDK/环境需 **Bouncy Castle** 注册 Provider，否则 `getInstance("Ed25519")` 抛 NoSuchAlgorithmException。
- **keytool 密码入命令**：`-storepass` 会出现在进程列表，生产用 Env/KMS 注入，不硬编码。
- **前端证书/公钥类型**：前端拿到是字符串(Base64)，Java 端 `X509EncodedKeySpec` + `KeyFactory` 反序列化回 `PublicKey`。
