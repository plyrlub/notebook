## #1 配置/环境类

### #1.1 MySQL 容器时区默认 UTC 差 8 小时

**现象**：Docker 部署的 MySQL 容器默认时区为 UTC，Java 应用写入的 `DATETIME` / `TIMESTAMP` 字段在数据库内显示比实际时间少 8 小时。ShardingSphere-Proxy 连接该 MySQL 后，ShardingSphere 日志时间也偏移。

**原因**：MySQL 官方 Docker 镜像默认 `TZ=UTC`，`--default-time-zone` 未设置，容器启动后 `SELECT @@global.time_zone, @@session.time_zone` 返回 `SYSTEM`（即 UTC）。

**解决方案**：

```bash
# 启动时指定时区
docker run -d \
  --name mysql-shard \
  -e MYSQL_ROOT_PASSWORD=root \
  -e TZ=Asia/Shanghai \
  --default-time-zone=+08:00 \
  -p 3306:3306 \
  mysql:8.0
```

**验证**：

```bash
# 进入容器检查
docker exec -it mysql-shard mysql -uroot -proot -e "SELECT @@global.time_zone, @@session.time_zone;"
# 预期输出：+08:00 | +08:00
```

### #1.2 ShardingSphere-Proxy 官方 Docker 镜像不含 MySQL JDBC 驱动

**现象**：ShardingSphere-Proxy 5.5.x 官方 Docker 镜像启动后，连接 MySQL 时报错 `No suitable driver found` 或 `Cannot load driver class: com.mysql.cj.jdbc.Driver`。

**原因**：Apache 官方发布的 ShardingSphere-Proxy Docker 镜像不内置 MySQL JDBC 驱动（仅内置 H2 驱动），需要手动挂载 `mysql-connector-j` jar 包到 `ext-lib` 目录。

**解决方案**：

```bash
# 1. 下载 MySQL JDBC 驱动（8.0+ 使用 mysql-connector-j）
wget https://repo1.maven.org/maven2/com/mysql/mysql-connector-j/8.0.33/mysql-connector-j-8.0.33.jar

# 2. 启动容器时挂载到 ext-lib
docker run -d \
  --name shardingsphere-proxy \
  -v /path/to/mysql-connector-j-8.0.33.jar:/opt/shardingsphere-proxy/ext-lib/mysql-connector-j-8.0.33.jar \
  -p 3307:3307 \
  apache/shardingsphere-proxy:5.5.2
```

**注意**：ShardingSphere-Proxy 5.5.x 基于 Java 17，确保 MySQL JDBC 驱动版本兼容 Java 17。

### #1.3 国内 Maven 镜像无 shardingsphere-jdbc-core 5.5.2

**现象**：在 `pom.xml` 中引入 `shardingsphere-jdbc-core` 5.5.2，Maven 构建报错 `Could not resolve dependency`，即使配置了阿里云或华为云 Maven 镜像也无法下载。

**原因**：国内主流 Maven 镜像（阿里云/华为云/Tencent）的 ShardingSphere 版本同步不及时，5.5.2 版本发布后一段时间内未同步到镜像库。Maven Central 在国内直连速度慢或不可达。

**解决方案**：

```bash
# 方案 A：使用代理访问 Maven Central（推荐）
# 在 ~/.m2/settings.xml 中配置代理
# 或 mvn 命令加 -DproxySet=true -DproxyHost=... -DproxyPort=...

# 方案 B：回退到镜像已同步的可用版本（如 5.5.1）
# pom.xml 中改为 5.5.1
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core</artifactId>
    <version>5.5.1</version>
</dependency>

# 方案 C：手动下载 jar 安装到本地 Maven 仓库
mvn install:install-file \
  -Dfile=shardingsphere-jdbc-core-5.5.2.jar \
  -DgroupId=org.apache.shardingsphere \
  -DartifactId=shardingsphere-jdbc-core \
  -Dversion=5.5.2 \
  -Dpackaging=jar
```

## #2 分片/算法类

### #2.1 非分片键查询触发全路由（全分片扫描）

**现象**：不带分片键的 `SELECT` 查询耗时远高于预期。例如 `SELECT * FROM t_order WHERE status = 1` 在分 16 片时耗时 ≥ 单分片查询的 16 倍。慢查询日志显示所有分片都被扫描。

**原因**：分片键未命中时，ShardingSphere 将 SQL 广播到所有分片（全路由），每个分片独立执行后归并结果。分片数越多，网络开销 + 归并开销线性增长。

**解决方案**（按优先级）：

| 方案 | 做法 | 代价 |
|------|------|------|
| 1. 走分片键 | 查询条件带上分片键（如 `WHERE user_id = ? AND status = 1`） | 需业务层传递分片键 |
| 2. 二级索引 | 用 ES 或中间表维护「非分片键→分片键」映射，先查 ES 拿到分片键值再回查 DB | 引入 ES 运维成本，数据同步延迟 |
| 3. 冗余字段 | 将高频查询的非分片键冗余到分片键所在表（反范式） | 存储空间增加，更新一致性需维护 |
| 4. Hint 路由 | 通过 ThreadLocal 手动指定分片（分片键在上下文中的场景） | 代码侵入，需谨慎管理 HintManager 生命周期 |

### #2.2 取模分片非倍扩容迁移量几乎全量（~80%）

**现象**：分片数从 4 扩容到 5（非倍扩容）后，大量查询路由到错误分片，数据丢失或查询结果不完整。迁移后发现 80%+ 的数据需要重新分布。

**原因**：取模分片依赖除数 = 分片数。从 `%4` 变为 `%5` 时，除数变化导致几乎所有 key 的映射关系改变。实测 10,000 key 从 `%4` 扩容到 `%5` 的迁移率为 **80.17%**（理论值 ≈ 80-100%）。只有倍扩容（如 `%4→%8`）才能将迁移率控制在 ~50%。

**解决方案**：

- **方案 A（推荐）**：初次分片数取 2 的幂次（16/32/64/128），后续只做倍扩容，迁移率 ≈ 50%
- **方案 B（平滑扩容）**：改用一致性哈希算法，+1 节点扩容迁移率仅 ~20%
- **方案 C（停机迁移）**：停服 → 导出数据 → 按新分片数重新分布 → 导入 → 切换配置
- **方案 D（在线双写）**：旧分片 + 新分片同时写入 → 历史数据迁移 → 切换读流量 → 下线旧分片

**迁移量参考**（10,000 key 实测）：

| 扩容方式 | 迁移率 | 说明 |
|:--------:|:-----:|------|
| %4→%8（倍扩容 2x） | 49.42% | 可接受，每个旧分片一半数据迁移 |
| %4→%5（非倍扩容 1.25x） | 80.17% | 灾难，近乎全量迁移 |
| 一致性哈希 4→5（+1 节点） | 20.39% | 平滑，仅迁移相邻节点区域 |

### #2.3 范围分片 0 迁移但热点倾斜/数据不均风险

**现象**：按时间范围分片后，最新分片写入 QPS 持续走高，成为瓶颈；历史分片数据量远大于最新分片，冷热数据分布极不均匀。例如按月分片 12 个月后，第 12 个月分片写入压力大，前 11 个月分片只读。

**原因**：范围分片天然存在「尾部热点」——所有写入集中在当前时间窗口分片，无法横向扩展写入能力。同时，历史数据持续累积，分片间数据量差异随时间增大。

**解决方案**：

- **复合分片**：`hash(user_id) % N` 做库路由 + 时间范围做表路由，写入分散到多个库
- **预热新分片**：在时间窗口切换前预先创建新分片并分配更多资源（Buffer Pool / IOPS）
- **冷热分离**：将历史分片数据迁移到廉价存储（如 MySQL 归档到 ClickHouse / TiDB），减少热分片数据量
- **定期合并**：对历史分片做合并（如 12 个月前的月分片合并为年分片），控制分片总数

**判断标准**：
- 如果最新分片的写入 QPS > 其他分片的 2 倍 → 触发热点
- 如果最大分片数据量 > 最小分片数据量的 5 倍 → 数据倾斜严重
