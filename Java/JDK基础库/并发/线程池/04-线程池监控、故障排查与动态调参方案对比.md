## 一、监控指标全集

ThreadPoolExecutor 原生暴露的监控指标：

| 指标 | 获取方法 | 含义 | 什么时候看 |
| --- | --- | --- | --- |
| 当前线程数 | `getPoolSize()` | 含核心+非核心的现存线程数 | 与 core/max 对比判断池是否"够用" |
| 活跃线程数 | `getActiveCount()` | 正在执行任务的线程数 | 活跃数≈池大小时说明线程全忙 |
| 核心线程数 | `getCorePoolSize()` | 当前配置值 | 调参后确认生效 |
| 最大线程数 | `getMaximumPoolSize()` | 当前配置值 | 同上 |
| 队列大小 | `getQueue().size()` | 积压任务数 | **队列持续增长 = 消费能力不足** |
| 队列容量 | `((BlockingQueue) getQueue()).remainingCapacity()` | 剩余容量 | 容量将尽 → 即将触发拒绝 |
| 完成任务数 | `getCompletedTaskCount()` | 累计完成任务 | 两次采样差值算吞吐 |
| 提交任务数 | `getTaskCount()` | 累计提交（含排队） | 完成数/提交数 = 处理进度 |
| 历史峰值线程 | `getLargestPoolSize()` | 运行以来最大线程数 | 判断是否曾触及 max |
| 拒绝次数 | 无原生计数！ | - | 需自定义 handler 计数（见第三章） |

拒绝次数是**最关键的过载信号**但原生不提供——必须通过自定义拒绝策略统计（见 [01-Java线程池原理与参数详解](01-Java线程池原理与参数详解.md)）。

## 二、指标获取途径

| 途径 | 方式 | 适用 |
| --- | --- | --- |
| JMX | ThreadPoolExecutorMXBean（只读，含池大小/活跃数/队列大小） | JConsole/JMC 人工查看 |
| Micrometer | `ExecutorServiceMetrics.monitor(registry, pool, "orderPool")` | Prometheus + Grafana 自动化监控 |
| 自定义封装 | 定时采样 getter 写入日志/指标库 | 需要拒绝次数等定制指标 |

Micrometer 接入示例：

```java
@Configuration
public class PoolMetricsConfig {
    @Bean
    public ExecutorService orderPool(MeterRegistry registry) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(10, 20, 60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1000), namedFactory("order-pool-%d"), callerRuns());
        ExecutorServiceMetrics.monitor(registry, pool, "orderPool");  // 自动暴露池指标
        return pool;
    }
}
```

Micrometer 自动暴露的指标（Grafana 面板直接可用）：`executor.active`、`executor.queued`、`executor.pool.size`、`executor.completed`、`executor.queued.remaining` 等。

## 三、生产级监控封装示例

```java
public class MonitoredThreadPool {
    private final ThreadPoolExecutor pool;
    private final AtomicLong rejectedCount = new AtomicLong();

    public MonitoredThreadPool(int core, int max, int queueCapacity) {
        this.pool = new ThreadPoolExecutor(core, max, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(queueCapacity),
            new ThreadFactoryBuilder().setNameFormat("order-%d").build(),
            this::onReject);                                  // 自定义拒绝：计数 + 落库
    }

    private void onReject(Runnable r, ThreadPoolExecutor executor) {
        long n = rejectedCount.incrementAndGet();
        log.warn("task rejected #{}: queue={}, active={}, pool={}",
            n, executor.getQueue().size(), executor.getActiveCount(), executor.getPoolSize());
        retryStore.save(r);                                   // 被拒任务落库补偿
        alert.ifThreshold(n);                                 // 达到阈值告警
    }

    // 定时健康快照（ScheduledExecutorService 每 30s 调一次）
    public void report() {
        int queueSize = pool.getQueue().size();
        int capacity  = ((ArrayBlockingQueue<?>) pool.getQueue()).remainingCapacity() + queueSize;
        metrics.gauge("pool.queue.usage", queueSize * 100.0 / capacity);  // 队列水位 %
        metrics.gauge("pool.active",   pool.getActiveCount());
        metrics.gauge("pool.rejected", rejectedCount.get());
        // 告警规则示例：队列水位 > 80% 持续 2 个周期 → 预警限流；拒绝次数增长 → 立刻告警
    }
}
```

告警阈值经验值：队列水位 > 80% 预警（即将拒绝）；拒绝次数 > 0 即告警（过载已发生）；活跃线程 = max 持续多个周期（扩容空间耗尽）。

## 四、故障排查实战

### 场景一：任务积压、接口响应变慢

定位链路：

1. **看指标**：getQueue().size() 持续增长？→ 消费跟不上。
2. **看吞吐**：completedTaskCount 差值（每秒完成数）是否下降 → 任务变慢还是线程不够。
3. **看 CPU**：进程 CPU 高 → 任务本身重（CPU 密集过载）；CPU 低但队列堆积 → 线程阻塞在 IO/锁（线程不够或死锁）。
4. **jstack 看线程状态**：

```
"order-pool-1" #12 prio=5 WAITING (parking)     → 空闲等任务（take 阻塞），正常
"order-pool-2" #13 prio=5 RUNNABLE              → 正在执行，看堆栈是否卡在奇怪位置
"order-pool-3" #14 prio=5 BLOCKED on monitor    → 锁竞争/死锁，看等待哪把锁
"order-pool-4" #15 prio=5 TIMED_WAITING (sleep) → 业务 sleep 或 poll 超时
```

5. **Arthas thread 命令**：`thread -n 3` 看最忙线程堆栈；`thread --state BLOCKED` 找锁等待。

### 场景二：线程池拒绝异常刷屏

- 确认队列是否打满（remainingCapacity = 0）、活跃线程是否已到 max。
- 看拒绝策略：AbortPolicy 会抛异常；如果线上是 CallerRunsPolicy，接口 RT 会急剧上升（反压生效）——两者都是过载信号，需要扩容或限流，不是改代码能解决的。
- 治理方向：① 扩容（core/max/队列）② 上游限流 ③ 拒绝任务降级落库重试 ④ 异步化削峰。

### 场景三：应用关不掉 / 线程泄漏

- 线程池未 shutdown：jstack 看到一堆 WAITING 的池线程，应用退出卡住。
- 排查：扫描代码中 ExecutorService 是否在 Spring @PreDestroy / 应用关闭钩子里 shutdown；用 `-XX:+HeapDumpOnOutOfMemoryError` + MAT 分析线程对象持有者（见 [JVM调优实战](../../../JVM/JVM调优实战.md)）。
- 治理：统一封装池的生命周期管理，Spring 场景让池 Bean 走容器销毁回调；堆栈与内存分析见 [JVM调优实战](../../../JVM/JVM调优实战.md)。

### 场景四：慢任务拖垮整个池

- 现象：个别任务耗时秒级（如第三方 RPC 超时重试），占住线程，队列堆积。
- 治理：① 任务内设置超时（Future.get(timeout) / HttpClient 超时）② 长任务与短任务分池隔离 ③ 监控任务执行耗时分布（TP99），见 [05-DynamicTp动态线程池详解](05-DynamicTp动态线程池详解.md)。

## 五、动态调参四方案

背景：参数静态化（启动写死）的痛点是流量预测困难、调参要发版重启。ThreadPoolExecutor 原生六个 set 方法（[01-Java线程池原理与参数详解](01-Java线程池原理与参数详解.md)）是"调参的扳手"，但**何时调、谁去调、怎么防抖**需要方案承载。业界四条路线：

### 方案一：JMX 手动调参

思路：注册管理 MBean 暴露 set 操作，JConsole / JMC 连接手动调整。

- ThreadPoolExecutorMXBean 只有 getter（只读），需自行注册管理 MBean：

```java
public interface PoolMBean {
    void setCorePoolSize(int core);
    void setMaximumPoolSize(int max);
    int getPoolSize();
}

ManagementFactory.getPlatformMBeanServer().registerMBean(
        new PoolManager(pool),
        new ObjectName("com.example:type=ThreadPoolManager,name=orderPool"));
```

- 运维侧 JConsole 连上 `-Dcom.sun.management.jmxremote` 端口点按钮调整。

| 维度 | 评价 |
| --- | --- |
| 改代码 | 是（注册 MBean） |
| 实时性 | 实时 |
| 运维成本 | 开 JMX 端口（需认证，有安全面） |
| 适用 | 内网小规模、无配置中心的环境 |

### 方案二：Arthas 线上热调参

思路：零侵入，不重启不改代码，ognl 表达式直接调用 set 方法。

```bash
# 定位线程池对象（vmtool 取实例）
vmtool --action getInstances --className com.example.OrderService \
       --express 'instances[0].orderPool'

# ognl 调用 set 方法，实时生效
ognl -x 1 '#pool=@com.example.SpringContextUtil@getBean("orderPool"), \
  #pool.setCorePoolSize(30), #pool.setMaximumPoolSize(100)'

# 配合诊断：thread -n 3 看最忙线程；watch 观察拒绝/队列
```

| 维度 | 评价 |
| --- | --- |
| 改代码 | 否（零侵入） |
| 实时性 | 实时 |
| 运维成本 | SSH + 手工命令，适合应急 |
| 适用 | 线上故障应急、临时验证参数；不适合作常态化自动调整 |
| 风险 | 命令即代码需双人复核；Agent 挂载需审计 |

### 方案三：代码内自适应调节

思路：应用内调度线程定时采样指标（CPU、队列深度、活跃线程），按决策规则调用 set 方法，形成"监控 → 决策 → 调整"闭环。

```java
ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
scheduler.scheduleWithFixedDelay(() -> {
    double cpu = processCpuLoad();                       // com.sun.management.OperatingSystemMXBean
    int active = pool.getActiveCount();
    int queueSize = pool.getQueue().size();
    int capacity = queueSize + ((ArrayBlockingQueue<?>) pool.getQueue()).remainingCapacity();

    if (queueSize > capacity * 0.8 && cpu < 0.85) {
        // 队列积压 + CPU 有余量 → 扩容（先 max 后 core）
        pool.setMaximumPoolSize(pool.getMaximumPoolSize() + 10);
        pool.setCorePoolSize(pool.getCorePoolSize() + 10);
    } else if (cpu > 0.90 || (queueSize == 0 && active < pool.getCorePoolSize())) {
        // CPU 打满或空闲 → 收缩（先 core 后 max）
        pool.setCorePoolSize(Math.max(MIN_CORE, pool.getCorePoolSize() - 10));
        pool.setMaximumPoolSize(Math.max(MIN_MAX, pool.getMaximumPoolSize() - 10));
    }
}, 0, 3, TimeUnit.SECONDS);
```

设计要点（决定成败）：

① **指标来源**：进程 CPU 用 `com.sun.management.OperatingSystemMXBean.getProcessCpuLoad()`（进程级）；不要用 getSystemLoadAverage（整机负载，受同机其他进程干扰）。

② **滞回区（hysteresis）**：加线程与减线程阈值留空隙（如队列 >80% 加、<30% 减），避免边界抖动导致线程频繁创建/销毁。

③ **采样平滑**：CPU 瞬时值波动大，用滑动平均（最近 5 次均值）再决策。

④ **硬上下限**：core/max 设配置化的最小值/最大值，防决策失控。

⑤ **调整顺序**：调大先 max 后 core，调小先 core 后 max（见 [01-Java线程池原理与参数详解](01-Java线程池原理与参数详解.md) 的 core>max 坑）。

⑥ **任务耗时维度**：公式 `线程数 = 核数 × (1 + W/C)`（[03-线程数设置与虚拟线程选型](03-线程数设置与虚拟线程选型.md)）说明 IO 密集池可远超核数，决策模型应纳入任务平均执行时间与 IO 占比。

| 维度 | 评价 |
| --- | --- |
| 改代码 | 是（自研决策逻辑，侵入业务模块） |
| 实时性 | 定时轮询周期 |
| 运维成本 | 无额外组件，但决策模型需长期调优 |
| 适用 | **单体应用**；微服务下每个服务复制一套逻辑 → 模块代码混乱 |
| 风险 | 决策模型写错可能把池调到失控，必须有兜底（拒绝策略 + 告警） |

### 方案四：开源框架方案（DynamicTp / Hippo4j）

思路：把"监控 + 决策 + 调整 + 告警"沉淀为通用框架，业务零侵入（配置外置配置中心），天然适配微服务。

- **DynamicTp**（dromara，2022 开源，当前 1.2.2/1.2.2-x）：轻量、多配置中心驱动、六类告警、20+ 指标、可接管十余种中间件线程池。详见 [05-DynamicTp动态线程池详解](05-DynamicTp动态线程池详解.md)。
- **Hippo4j**（opengoofy 开源）：动态变更 + 四维告警 + 控制台可视化，形态平台化，迭代节奏慢于 DynamicTp。

共同骨架：线程池注册管理（Registry）→ 监听配置中心变更 → 触发调整（本质仍是 set 方法）→ 指标采集 + 告警 → 适配器接管三方线程池。

| 维度 | 评价 |
| --- | --- |
| 改代码 | 否（业务零侵入，配置外置） |
| 实时性 | 配置中心变更即实时 |
| 运维成本 | 引入框架依赖 + 配置中心（一般已有） |
| 适用 | **微服务架构首选**；调整逻辑收敛在框架 |
| 风险 | 引入第三方依赖，需评估维护活跃度 |

## 六、四方案对比与选型建议

| 维度 | 方案一 JMX | 方案二 Arthas | 方案三 代码自适应 | 方案四 开源框架 |
| --- | --- | --- | --- | --- |
| 是否改代码 | 需注册 MBean | 否 | 是（侵入业务） | 否 |
| 实时性 | 实时 | 实时 | 定时轮询 | 配置变更即实时 |
| 运维成本 | 开 JMX 端口 | SSH + 手工命令 | 自研维护决策模型 | 引入框架 + 配置中心 |
| 微服务适配 | 差（逐个连） | 中（逐台操作） | 差（逻辑散落） | 好（框架统一） |
| 常态化自动调 | 否 | 否 | 可 | 可 |
| 应急调参 | 可用 | **首选** | 不适用 | 可用 |
| 落地成本 | 低 | 最低 | 高 | 中 |

选型建议：

- **线上应急、临时验证** → 方案二 Arthas，零侵入秒级生效。
- **单体应用、想自研闭环** → 方案三，注意滞回区与上下限兜底。
- **微服务、生产常态化** → 方案四 DynamicTp，业务零侵入。
- **无配置中心的内网小环境** → 方案一 JMX 兜底。
- **纯监控不调参** → 不必上框架，Micrometer + Prometheus + Grafana 即可（第二章）。
