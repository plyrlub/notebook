## 一、线程数设置基础

| 任务类型 | 经验值 | 理由 |
| --- | --- | --- |
| CPU 密集型 | CPU 核数 + 1 | 线程数 ≈ 核数即可跑满 CPU；+1 是补偿偶发页缺失/GC 停顿导致的计算核空转 |
| IO 密集型 | CPU 核数 × 2 或更高 | 线程大量时间在等 IO，更多线程可重叠等待时间提高吞吐 |

为什么不是"核数"而是"核数 + 1"：单个线程在运行中可能因缺页中断、GC、系统调用短暂让出 CPU，多一个线程可以填补这些空档，理论上让 CPU 利用率趋近 100%。

为什么 IO 密集要远超核数：IO 等待（数据库、RPC、磁盘）期间线程不占 CPU，若线程数 = 核数，等待期间 CPU 全空转。线程数翻倍甚至更高，让等待与计算互相重叠。

注意：这些是**起点经验值**，不是答案。真实取值必须回到第三节的压测。

## 二、Brian Goetz 公式推导

《Java Concurrency in Practice》给出的通用公式：

```
线程数 = CPU 核数 × (1 + 平均等待时间 / 平均计算时间)
        = CPU 核数 × (1 + W / C)
```

推导思路：

- 一个线程的完整处理周期 = 计算时间 C + 等待时间 W。
- 单核下，要达到 CPU 利用率 100%，需要让计算从不间断：线程数 = (C + W) / C = 1 + W/C。
- 多核放大：总线程数 = 核数 × (1 + W/C)。

示例计算：

| 场景 | 核数 | W/C 比值 | 结果 |
| --- | --- | --- | --- |
| 纯计算（W≈0） | 8 | 0 | 8×1 = 8（≈核数） |
| 任务 20% 计算 80% 等待 | 8 | 4 | 8×5 = 40 |
| 任务 10% 计算 90% 等待 | 8 | 9 | 8×10 = 80 |

公式含义：IO 占比越高，线程数可以也应当越大。这与"CPU 核数 × 2"的经验值一致（W/C ≈ 1 时线程数 = 2×核数），但公式允许按实际耗时比精细计算。

实践要点：W 和 C 用压测/链路追踪（如 SkyWalking span 耗时）统计平均值得出，比拍脑袋可靠。公式算出的值是理论最优，工程上还要留 20%~30% 余量并配动态调整（见 [04-线程池监控、故障排查与动态调参方案对比](04-线程池监控、故障排查与动态调参方案对比.md)）。

## 三、压测验证方法

线程数设置最终以压测数据为准，标准流程：

1. **构造压测任务**：用真实业务接口或等比例模拟（同样比例的 IO 等待），不能只用纯 sleep 或纯计算——两者的 W/C 完全不同。
2. **加压观察**：逐步提高并发，记录四类指标：
   - 吞吐量（TPS/QPS）：主指标，找到吞吐拐点
   - 延迟（P99/P999）：吞吐上去了延迟不能失控
   - CPU 利用率：目标 70%~85%（过低说明线程不够，过高说明过载）
   - 线程池自身指标：活跃线程数、队列深度、拒绝次数（见 [04-线程池监控、故障排查与动态调参方案对比](04-线程池监控、故障排查与动态调参方案对比.md)）
3. **判定**：取"吞吐不再随线程数显著增长"的拐点值为最优线程数；再往上是延迟劣化区。

工具：JMH（微基准）、JMeter / wrk（接口压测）、压测机与目标机分离避免互相干扰。

## 四、ForkJoinPool 与 CompletableFuture

### ForkJoinPool

- 线程模型：每个工作线程一个**双端任务队列**（deque），线程执行完自己的任务后，从**其他线程队列尾部**窃取任务执行（工作窃取算法），实现负载自动均衡。
- 默认池 commonPool：大小 = CPU 核数 - 1（`ForkJoinPool.getCommonPoolParallelism()`），可通过 `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N` 调整。
- 适用：可分治的 CPU 密集计算（RecursiveTask 拆分归并）；不保证 FIFO，不适合有序任务。
- 与普通线程池的关系：ForkJoinPool 是"并行计算池"（面向任务树），ThreadPoolExecutor 是"通用任务池"（面向队列），不可互相替代。

### CompletableFuture

- 异步编排 API（JDK 8+），内部默认使用 ForkJoinPool.commonPool 执行异步任务。
- **坑**：commonPool 大小 = 核数 - 1，且被全 JVM 共享。IO 密集任务用 CompletableFuture 默认池，会把共享池线程占满，影响其他并行流/异步任务。生产应显式传自定义线程池：

```java
ExecutorService bizPool = new ThreadPoolExecutor(10, 20, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000), namedFactory, callerRunsPolicy);

CompletableFuture.supplyAsync(() -> queryDb(), bizPool)   // 显式指定，不占 commonPool
        .thenApplyAsync(result -> enrich(result), bizPool)
        .exceptionally(e -> fallback());
```

- 与虚拟线程搭配：JDK 21 后可传 `Executors.newVirtualThreadPerTaskExecutor()` 给 supplyAsync，IO 密集编排无需再纠结池大小。

## 五、虚拟线程详解

### 原理（JEP 444，JDK 21 正式）

- 虚拟线程是 JVM 管理的轻量线程，**不直接绑定 OS 线程**：由 JVM 调度器挂载到少量"载体线程"（carrier，平台线程）上执行，阻塞时自动卸载，让载体线程去跑别的虚拟线程。
- 数量级：普通线程受内存（栈 512KB~1MB）限制，一台机器几千~几万；虚拟线程栈可扩展，**百万级**可承载。
- 创建成本：极低（毫秒级创建/销毁），因此"每任务一线程"模型成为现实，**不需要池化**。

### 适用场景

| 场景 | 是否适合 | 原因 |
| --- | --- | --- |
| IO 密集（DB/RPC/文件/网络） | ✅ 非常适合 | 等待期间虚拟线程卸载，载体线程复用 |
| CPU 密集 | ⚠️ 需限流 | 计算占满载体线程无卸载机会，需信号量/固定池限制并发 |
| 高频 synchronized 阻塞 | ⚠️ JDK 21 有 pin 问题（见下） | JDK 24 起由 JEP 491 修复 |
| 线程隔离/资源限额 | ❌ 不适合 | 无池概念，无法限制线程数、无法拒绝 |

### pin 问题（JEP 491）

**现象**（JDK 21~23）：虚拟线程在 `synchronized` 块/方法内阻塞（如 IO 等待、Object.wait）时，会 **pin 住载体平台线程**——载体线程无法被其他虚拟线程复用，退化为"1 虚拟线程占 1 平台线程"，虚拟线程的优势消失。

**根因**：JDK 21 及以前，synchronized 锁的监视器记录在载体线程上；虚拟线程卸载后锁的归属丢失，JVM 为保持锁语义只能让虚拟线程在载体上原地阻塞。

**修复**：JEP 491（Synchronize Virtual Threads without Pinning）在 **JDK 24** 落地，重构监视器归属（锁记在虚拟线程自身而非载体），synchronized 内阻塞不再 pin。JDK 24 仍有**残余 pin**：native 帧（JNI）、类加载、Linux 上的本地文件 IO。

**检测方法**：

```bash
# 1. 启动参数：pin 发生时打印线程转储
-Djdk.tracePinnedThreads=full

# 2. JFR 事件（JDK 24+）：jdk.VirtualThreadPinned，含事件线程与堆栈
#    jcmd <pid> JFR.start / JFR.dump 或用 JDK Mission Control 查看
```

**迁移注意**（JDK 21 生产落地）：把 synchronized 换成 ReentrantLock 可避免 pin；或直接升级 JDK 24 依赖 JEP 491。

### 正确使用姿势（JDK 21）

```java
// 每请求一线程：不再需要线程池调优
ExecutorService vtPool = Executors.newVirtualThreadPerTaskExecutor();
vtPool.execute(() -> handleRequest());     // 百万级并发也扛得住

// CPU 密集段仍需限流：信号量限制并发数
Semaphore sem = new Semaphore(Runtime.getRuntime().availableProcessors());
vtPool.execute(() -> {
    sem.acquire();
    try { computeHeavy(); } finally { sem.release(); }
});
```

## 六、选型决策

| 维度 | 平台线程池（ThreadPoolExecutor） | 虚拟线程（JDK 21+） |
| --- | --- | --- |
| 适用任务 | CPU 密集、需要隔离/限额、任务有优先级 | IO 密集、每请求一线程 |
| 线程数量级 | 几十~几千（受栈内存限制） | 百万级 |
| 池化/调参 | 可调 core/max/队列/拒绝（[01-Java线程池原理与参数详解](01-Java线程池原理与参数详解.md)） | 无池化概念 |
| 阻塞开销 | 线程阻塞占资源 | 阻塞自动卸载载体 |
| synchronized 阻塞 | 无影响 | JDK 21 pin（JEP 491 于 24 修复） |
| 资源限额 | 有界队列+拒绝策略可限额 | 需信号量自行限流 |
| 任务顺序 | 队列保证 FIFO（视队列） | 不保证 |
| 迁移成本 | - | 线程池 API 兼容（ExecutorService），改创建方式即可 |

决策建议：

- **IO 密集 + JDK 21+** → 虚拟线程，直接替代大部分 IO 型线程池（含 DynamicTp 等框架管理的池，见 [05-DynamicTp动态线程池详解](05-DynamicTp动态线程池详解.md)）。
- **CPU 密集或需要线程数硬限额** → 传统 ThreadPoolExecutor。
- **JDK 21 且大量 synchronized 阻塞代码** → 要么升级 JDK 24，要么先迁移 ReentrantLock 再上虚拟线程。
