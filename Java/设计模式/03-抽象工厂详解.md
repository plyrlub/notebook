# 抽象工厂模式详解

> 本篇讲工厂模式的进阶版：工厂方法管**一种产品**的多个实现，抽象工厂管**一族产品**的配套创建，并辨析它与工厂方法的适用边界。

## 📋 总纲

抽象工厂的目的是**成族创建一组相互关联的产品**，保证「同一族的产品配套一致」。它是创建型里抽象度最高、最容易与工厂方法混淆的一个。

## 1. 是什么 / 为什么用（原理）

**问题**：UI 控件常分**族**——如「Windows 风格」和「Mac 风格」，默认窗口不能混搭。如果一个工厂只管单个控件，很容易在运行时组装出「Windows 按钮 + Mac 弹窗」这种串味组合。

**解决思路**：提供一个「**族的工厂**」，它能创建一族内的所有产品，且保证每次都成套来自同一族。

**生活类比**：**家具全家桶**——有的商家卖「红木全家」(桌+椅+柜)，有的卖「铁艺全家」。你说「我要红木全家」，它给你一套配套的；不会给你红木桌配铁艺椅。

## 2. 结构（类图）

```
            ┌──────────────┐
            │  AbstractFactory(接口)│──── 抽象工厂
            └──────────────┘
               │createButton()   createDialog()
               │        ▲
     ┌─────────┴─────┐  │
  WindowFactory   MacFactory ───── 具体工厂（一族一个）
     │              │
 createButton→WindowButton   createButton→MacButton
 createDialog→WindowDialog   createDialog→MacDialog

 产品族：Button、Dialog 两个「产品族」的维度，
 Window/Mac 是「族」（风格）维度。
```

## 3. 代码示例（跨风格 UI 控件）

```java
// ── 产品族一：按钮
public interface Button { void render(); }
public class WinButton implements Button {
    public void render() { System.out.println("Windows 风格按钮"); }
}
public class MacButton implements Button {
    public void render() { System.out.println("Mac 风格按钮"); }
}

// ── 产品族二：对话框
public interface Dialog { void show(); }
public class WinDialog implements Dialog {
    public void show() { System.out.println("Windows 风格对话框"); }
}
public class MacDialog implements Dialog {
    public void show() { System.out.println("Mac 风格对话框"); }
}

// ── 抽象工厂：一族的工厂必须能创建「族内所有产品」
public interface UIFactory {
    Button createButton();
    Dialog createDialog();
}

// ── 具体工厂：每个族一套
public class WindowFactory implements UIFactory {
    public Button createButton() { return new WinButton(); }
    public Dialog createDialog() { return new WinDialog(); }
}
public class MacFactory implements UIFactory {
    public Button createButton() { return new MacButton(); }
    public Dialog createDialog() { return new MacDialog(); }
}

// ── 客户端：面向抽象工厂，一次拿一族
public class Client {
    public static void main(String[] args) {
        UIFactory factory = new MacFactory();    // 切换风格，只需换一个工厂
        Button b = factory.createButton();
        Dialog d = factory.createDialog();
        b.render();   // Mac 风格按钮
        d.show();     // Mac 风格对话框
    }
}
```

**说明**：
- 外层只换 `factory`（`MacFactory` ↔ `WindowFactory`），**整套产品随之一起换**，天然保证配套一致。
- 每个具体工厂管一族（一种风格），不跨越产品族。

## 4. 抽象工厂 vs 工厂方法（关键对比）

| 维度 | 工厂方法 | 抽象工厂 |
|---|---|---|
| 管理的产品 | 一种产品的一**个实现类型** | **一族**（多种）产品 |
| 新增产品**族**（如加 Linux 风格） | — | 加一个具体工厂子类，不改现有代码（开闭） |
| 新增产品**类型**（如加 slider 滑杆） | — | **要改抽象工厂接口**（加方法）+ 每个工厂实现（破坏开闭 ❌） |
| 复杂度 | 低 | 高 |
| 典型场景 | 单产品多实现 | 产品族须成套（UI 套件、数据库驱动套件） |

**一句话**：工厂方法面向「一个产品线的深度」，抽象工厂面向「一族产品的成套」。抽象工厂的痛点是「产品类型横向扩展很不友好（要动抽象接口）」，所以只在该「族」本身稳定时才值得用。

## 5. 代价与边界

- **优点是成套、隔离**：客户端只知道抽象工厂，不知道家族具体实现，且换族零改动。
- **代价是僵化**：产品族一旦要加新「产品维度」，抽象工厂接口和所有具体工厂都得改。
- 适用范围窄：只有当「产品族 + 产品维度」两个维度都稳定、且确实需要成套保证时才上。**绝大多数业务用不到抽象工厂**，别硬套。

## 6. 现实印证

- Java GUI：AWT 的 `Toolkit` 抽象工厂（不同平台 Native 实现）。
- 数据库访问：JDBC `DriverManager` 按驱动产生不同产品，是工厂思想的体现。
- 结合工厂方法：**抽象工厂里往往每个创建方法由「工厂方法」实现**（具体工厂里的 createButton 又可能是小工厂）——两者常叠加使用。

## 7. 最佳实践

1. 只有「多族 × 多产品、且必须成套」才用抽象工厂；否则优先简单工厂/工厂方法。
2. 客户端只依赖抽象工厂与产品接口，绝不 touch 具体实现类。
3. 抽象工厂与工厂方法可嵌套：抽象工厂的每个 createX 方法内部交给工厂方法/新工厂。

## 9. 小结

- 抽象工厂 = **一族产品的成套工厂**，换来更换族的零改动、保证配套一致。
- 与工厂方法的差别：工厂方法是产品深度，抽象工厂是产品族的广度。
- 代价是产品类型横向扩展要动抽象接口（僵化），故只在「族稳定」时用。
