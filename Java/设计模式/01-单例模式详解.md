# 单例模式详解

> 本篇从原理到实现，拆解 6 种单例写法的线程安全性、代价与破坏方式，并给出工程选型结论。

## 📋 总纲

单例模式保证**一个类在全局只有唯一实例**，并提供一个统一访问点。它是创建型模式里最简单、面试最高频、却最容易在「线程安全」和「破坏方式」上翻车的一个。

## 1. 是什么 / 为什么用（原理）

**定义**：保证一个类仅有一个实例，并提供一个访问它的全局点。

**为什么需要它**：某些资源（配置文件、数据库连接池、线程池、Spring 容器本身）在系统里只需要一份，重复创建既浪费又可能导致状态不一致。单例让「一份」在结构上被强制保证，而不是靠约定。

**生活类比**：整栋楼的**物业公司**只有一家，所有人都去同一个柜台办事（全局访问点），不会出现两家物业管同一栋楼。

## 2. 单例的本质（底层原理）

单例的两个核心机制：

1. **私有构造器**：`private` 阻止外部 `new`，这是「只能有一个」的入口开关。
2. **静态字段 + 静态方法**：实例挂在 `static` 上，`getInstance()` 全局可见，保证唯一访问路径。

**核心矛盾**：静态字段初始化「时机」×「线程安全」的不同组合，衍生出下面 6 种写法。

## 3. 六种实现逐一拆解

### 3.1 饿汉式（Eager）

实例在**类加载时**就创建，最简单、线程安全（JVM 类加载保证只执行一次）。

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

**说明与取舍**：
- ✅ 线程安全（`static final` 由类加载器保证唯一初始化）
- ✅ 写法最简、无反序列化问题（若类实现 Serializable 需补 `readResolve`）
- ❌ **如果对象很重且大概率用不到**，类一加载就白白创建 → 启动变慢、浪费资源
- 适用：确定会被用到、创建开销可接受的场景

### 3.2 懒汉式（非线程安全，反例）

实例在**首次调用 getInstance 时**才创建，但不加锁会竞态。

```java
public class Singleton {
    private static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {       // 竞态：两个线程同时进来
            instance = new Singleton();
        }
        return instance;
    }
}
```

**说明**：核心问题在 `if (instance == null)` 的「检查-创建」并非原子。线程 A 进入 `if` 后让出 CPU，线程 B 也进入并创建了实例，A 回来又 `new` 一个 → 多实例。**工程上不可用**，仅用于理解竞态。

### 3.3 懒汉式（方法加锁，线程安全但慢）

给 `getInstance()` 整体加 `synchronized`。

```java
public static synchronized Singleton getInstance() {
    if (instance == null) instance = new Singleton();
    return instance;
}
```

**说明**：线程安全了，但**每次调用都上锁**，而真正需要同步的只有「首次创建那一下」。高并发调用频繁时锁竞争是白花开销。性能差，现已很少用。

### 3.4 DCL 双重检查锁 double-checked locking（关键）

先 `if` 快路径免锁，命中 `null` 才进同步块，内部做**第二次判空**。

```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {              // 快路径：多数情况无锁
            synchronized (Singleton.class) {
                if (instance == null) {      // 二次判空：同步块内再查一次
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**说明**：
- **为什么二次判空**：同步块外已有线程持锁创建了实例，等锁的线程进块后不能盲目再 new，必须再检查一次。
- **为什么必须 `volatile`**：`new Singleton()` 分三步——①分配内存 ②执行构造器 ③赋值引用。**指令重排**可能让③先于②，其他线程会读到「非 null 但没构造完」的半成品。`volatile` 禁止这种重排（它保证 happens-before 与写后可见）。
- 属于**懒加载 + 线程安全 + 性能兼顾**的均衡方案，但写法最绕，副作用是有 `volatile` 可见性开销（可忽略）。

> 参考踩坑：[#1.2 DCL 必须加 volatile](../99-设计模式踩坑记录.md)

### 3.5 静态内部类（推荐·优雅懒加载）

利用 JVM 的「**静态内部类在首次使用时才加载**」特性，天然实现懒加载 + 线程安全。

```java
public class Singleton {
    private Singleton() {}

    // 静态内部类：仅当 getInstance() 被调用时才装载
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

**说明**：
- **原理**：外部类 `Singleton` 加载时，`Holder` 内部类**不会**随之加载；只有调用 `Holder.INSTANCE`（即 getInstance）才触发 `Holder` 类初始化，此时 JVM 保证只初始化一次 → **懒加载 + 线程安全双收**。
- ✅ 写法清晰、无锁、无 volatile 开销，是懒加载单例的**首选推荐**。
- 与饿汉区别：饿汉在外部类加载就建，静态内部类延后到真用到才建。

### 3.6 枚举单例（最推荐·终极方案）

```java
public enum Singleton {
    INSTANCE;   // 唯一的实例

    private Integer count = 0;
    public void doSomething() { System.out.println("singleton:" + ++count); }
}
```

**说明**：
- ✅ 线程安全：枚举实例的创建由 JVM 保证。
- ✅ **天然防御反射**：构造器是 JVM 内部管理的，反射 `newInstance` 会被拒绝。
- ✅ **天然防御反序列化**：枚举反序列化时不会新建对象，直接返回唯一既有实例 → 单例永不被序列化破坏。
- ❌ 不能懒加载（枚举类加载即建，但其实枚举本身就是「用时就加载」的轻只初始化）。
- 缺陷：若单例要继承某个类（非枚举），或需要更复杂的自定义构造，枚举就不适合。**日常场景枚举是王道**。

## 4. 两个常见破坏方式（面试必问）

### 4.1 反射破坏

私有构造器挡不住 `Constructor#setAccessible(true)`：

```java
Class<Singleton> clazz = Singleton.class;
Constructor<Singleton> c = clazz.getDeclaredConstructor(null);
c.setAccessible(true);                 // 突破 private
Singleton s2 = c.newInstance();        // 又造一个实例！单例被破坏
```

**抵御方案**：在私有构造器里抛异常：

```java
private Singleton() {
    if (INSTANCE != null) {
        throw new RuntimeException("禁止反射创建");
    }
}
```

> 参考踩坑：[#1.1](../99-设计模式踩坑记录.md)

### 4.2 反序列化破坏

Java 序列化默认在 `readObject` 时会**重新 new 一个对象**（不调用构造器），破坏单例。防御：加 `readResolve()`，反序列化时返回已有实例：

```java
private Object readResolve() {   // 返回值将取代反序列化新建的对象
    return INSTANCE;
}
```

> 参考踩坑：[#1.1](../99-设计模式踩坑记录.md)

## 5. 六种写法对比（决策表）

| 写法 | 懒加载 | 线程安全 | 防反射 | 防序列化 | 性能 | 推荐度 |
|---|---|---|---|---|---|---|
| 饿汉式 | ❌ | ✅ | ❌ | ❌(需补readResolve) | 高 | ⭐ 简单场景 |
| 懒汉(无锁) | ✅ | ❌ | ❌ | ❌ | — | ❌ 不可用 |
| 懒汉(方法锁) | ✅ | ✅ | ❌ | ❌ | 低(全量锁) | ❌ 已淘汰 |
| DCL+volatile | ✅ | ✅ | ❌ | ❌ | 高 | ⭐ 学原理 |
| 静态内部类 | ✅ | ✅ | ❌ | ❌ | 高 | ⭐⭐ 推荐 |
| 枚举 | ✅(天然) | ✅ | ✅ | ✅ | 高 | ⭐⭐⭐ 首选 |

**工程结论**：
- 能枚举就枚举（Spring 以外的多数业务单例）。
- 要懒加载又不想枚举的继承限制 → 静态内部类。
- 序列化 + 非枚举场景 → 静态内部类/饿汉 + `readResolve()`。

## 6. Spring 容器中的单例

Spring 的 Bean 默认是**单例作用域**（singleton scope），但它是「**容器级单例**」——由 Spring 的 BeanFactory 持有，同一个 `ApplicationContext` 内一个 bean 定义只有一个实例。这与 GoF 单例不同：Spring 不强制私有构造器，而是**由 IoC 容器保证每个名字一个实例**（普通类 + 容器管理）。这也是「忘掉单例破坏，容器作保」的现代实践——**优先用 Spring 管理单例，而不是自己写 GoF 单例**。

## 7. 最佳实践

1. 业务对象优先交给 Spring 容器的单例 Bean，别手写 GoF 单例。
2. 确需手写：默认枚举，其次静态内部类。
3. 序列化场景：记得 `readResolve()`；反射防御：私有构造器加判空抛异常。
4. 不要用「懒汉无锁」和「方法锁」这两个旧写法。

## 9. 小结

- 单例 = 私有构造器 + 静态访问点，「唯一 + 线程安全」是核心。
- 6 种实现里，**枚举**是终极方案（天然防反射/序列化），**静态内部类**是懒加载优雅之选。
- 两个必问破坏点：反射 `setAccessible`、反序列化 `readObject`。
- 现代工程更倾向**框架容器级单例**（Spring Bean），手写 GoF 单例场景在缩小。
