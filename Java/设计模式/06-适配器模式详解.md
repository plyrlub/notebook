# 适配器模式详解

> 本篇讲适配器模式如何让「接口不匹配」的类协同工作，分析类适配器 vs 对象适配器的写法与取舍，并给出现实印证。

## 📋 总纲

适配器的核心是**把「客户端期望的接口」翻译成「现有类的接口」**，让本来不兼容的双方在不改源码的情况下接上线。它的关键词是「适配」而非「扩展」——不新增能力，只做接口转换。

## 1. 是什么 / 为什么用（原理）

**问题**：系统里有一个现成实现 `LegacyReader`（它有自己的接口），但新代码需要的接口是 `Reader`，两者对不上。改 LegacyReader 源码成本高/不可控，直接不兼容。

**解决思路**：加一个**适配器**，它实现客户端要的接口，内部包装并调用 LegacyReader 的旧方法，把调用「翻译」过去。

**生活类比**：**充电转接头**——手机需要一个 Type-C 接口，但插座是 USB-A，转接头把类型翻译一下，两端各连各的。适配器不改手机也不改插座，中间加个转层。

## 2. 两种实现形式

### 2.1 对象适配器（组合方式，推荐）

通过**持有被适配对象**（组合）实现转换：

```java
// 客户端期望的目标接口
public interface Reader {
    String read(String path);
}

// 已有实现：接口不匹配
public class LegacyReader {
    public String readFile(String file) {   // 方法签名不同
        return "读取文件内容: " + file;
    }
}

// 适配器：实现目标接口，组合并调用旧实现
public class ReaderAdapter implements Reader {
    private final LegacyReader legacy;      // 组合：持有被适配者

    public ReaderAdapter(LegacyReader legacy) {
        this.legacy = legacy;
    }

    @Override
    public String read(String path) {
        // 把新接口调用翻译成旧接口调用
        return legacy.readFile(path);
    }
}
```

```java
public class Client {
    public static void main(String[] args) {
        Reader reader = new ReaderAdapter(new LegacyReader()); // 接上适配器
        System.out.println(reader.read("/a.txt"));
        // 输出：读取文件内容: /a.txt
    }
}
```

**说明**：适配器实现 `Reader`（客户端看到的），内部 `legacy.readFile()` 完成翻译。**优点**：组合灵活，一个适配器可配多个被适配者，且不影响被适配者自身。

### 2.2 类适配器（继承方式）

通过**继承被适配类**实现，需要多继承才能同时兼得被适配类的接口——但 Java 单继承，所以只能用实现接口+继承类：

```java
public class ReaderAdapter extends LegacyReader implements Reader {
    @Override
    public String read(String path) {
        return readFile(path);   // 直接复用父类方法
    }
}
```

**说明**：若 `LegacyReader` 不是接口而是类，类适配器就是「继承被适配类 + 实现目标接口」。**缺点**：受 Java 单继承限制，只能适配一个被适配类，耦合更高。**不如对象适配器常用**。

## 3. 两种方式对比

| 维度 | 对象适配器 | 类适配器 |
|---|---|---|
| 实现 | 组合（持有被适配者） | 继承（extends 被适配类） |
| 灵活性 | 高（可组合多个、可配不同实例） | 低（固死一个类） |
| 被适配者种类 | 支持子类（多态选） | 只支持被继承的具体类 |
| 耦合 | 低 | 高（强依赖继承） |
| 推荐度 | ⭐⭐⭐ | ⭐ 仅需简单复用 |

**工程结论**：绝大多数用**对象适配器**（组合优先于继承，与设计原则一致）。

## 4. 适配器 vs 其他易混模式

### vs 外观（Facade）——「翻译单接口」 vs 「提供简化入口」
- 适配器：改**接口形状**，让客户端用既有接口接上新实现。
- 外观：给一整套复杂子系统一个**简单统一入口**，不改接口形状。
> 一句话：适配器是「转接口」，外观是「简化入口」。

### vs 代理（Proxy）——「转换接口」 vs 「保持接口加控制」
- 适配器：客户端和目标**接口不同**，需要转换。
- 代理：客户端和目标**接口相同**，代理不加能力只做拦截/延迟/控制。

## 5. 现实印证

- Java `InputStreamReader`：把 `InputStream`（字节流）适配成 `Reader`（字符流），正是有名的适配器。
- `Arrays.asList()`：把数组适配成 `List` 接口。
- Spring `JpaVendorAdapter`：把不同 JPA 实现（Hibernate/TopLink）适配成统一接口供 Spring 使用。

## 6. 最佳实践

1. 默认用**对象适配器**（组合）。
2. 适配器只做**接口翻译**，不混入业务逻辑——职责要单一。
3. 优先考虑：能否改目标接口本身？能否用更简单的「直接兼容」？适配器是「最后兜底」手段，别为不存在的兼容问题提前上。

## 7. 常见踩坑

- 把适配器写成「既转换又改逻辑」的超类，职责混乱。
- 本阶段适配器无独立踩坑条目，通用原则见 [99-设计模式踩坑记录](99-设计模式踩坑记录.md) 各模式横向注意事项。

## 8. 小结

- 适配器 = 「接口转接头」，实现目标接口 + 组合/继承被适配者。
- 对象适配器（组合）优于类适配器（继承）。
- 与代理/外观区分：适配器「改接口形状」、代理「同接口加控制」、外观「简化入口」。
- 现实里遍地都是（InputStreamReader、Arrays.asList）。
