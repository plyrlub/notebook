# 建造者模式详解

> 本篇拆解建造者模式如何解决「多可选参构造混乱」的问题，对比链式调用 / telescoping 构造 / Lombok @Builder，并给出工程选型。

## 📋 总纲

建造者模式**分步骤构建一个复杂对象**，把「怎么选参数组装」从目标对象里解耦出去，得到可读、可校验、不可变的对象构造方式。它的现代 Java 形态就是**链式 Builder**。

## 1. 是什么 / 为什么用（原理）

**问题**：一个对象有大量可选的字段（比如一份请求配置：路径、超时、重试、编码、代理……）。用构造函数怎么写都别扭：

- 全参构造函数：调用时很难看出「每个位置是谁」，且可选参也得传（传 `null` 难看）。
- 构造器重载（telescoping）：随字段增多爆量，组合爆炸。

**解决思路**：把「组装」交给独立的 Builder——链式设置字段，最后 `build()` 产出校验后的目标对象。

**生活类比**：**点赛百味三明治**——面包、荤菜、蔬菜、酱料一步步选，店员按你的选择组装，而不是让你一口气背出所有参数。

## 2. 结构

```

        ┌──────────────┐     调用链      ┌────────────────┐
        │   Director   │──────────────▶│    Builder(可选) │
        │ (导向/编排步骤) │               └────────────────┘
        └──────────────┘                        │ build()产出
                                               ▼
                                        ┌──────────────┐
                                        │   Product     │
                                        │  (被构造对象)   │
                                        └──────────────┘
```

一般 Java 里习惯把 `Builder` 作为目标类的**静态内部类**（`Product.builder()`），Director 常省略，由调用方直接用 Builder 编排。

## 3. 代码示例（链式 Builder）

```java
public class HttpConfig {
    private final String url;
    private final int timeoutMs;
    private final int retries;
    private final boolean followRedirects;

    private HttpConfig(Builder b) {
        this.url = b.url;
        this.timeoutMs = b.timeoutMs;
        this.retries = b.retries;
        this.followRedirects = b.followRedirects;
    }

    public static class Builder {
        private String url;            // 必填，不改默认
        private int timeoutMs = 3000;  // 可选，带默认
        private int retries = 0;
        private boolean followRedirects = true;

        public Builder url(String v) { this.url = v; return this; }
        public Builder timeoutMs(int v) { this.timeoutMs = v; return this; }
        public Builder retries(int v) { this.retries = v; return this; }
        public Builder followRedirects(boolean v) { this.followRedirects = v; return this; }

        public HttpConfig build() {
            if (url == null) {                  // build 时统一校验
                throw new IllegalStateException("url 必填");
            }
            if (timeoutMs <= 0) {
                throw new IllegalArgumentException("timeoutMs 必须 > 0");
            }
            return new HttpConfig(this);
        }
    }
}
```

**调用**：

```java
HttpConfig cfg = HttpConfig.builder()   // 或 new HttpConfig.Builder().url(...)
        .url("https://api.example.com")
        .timeoutMs(5000)
        .retries(3)
        .build();
```

**说明与取舍**：
- 链式 setter **每个返回 `this`**，才能 `.url().timeoutMs()` 串起来。
- **字段全 final** → 对象不可变，线程安全、更安全。
- `build()` 统一做**必填+合法校验**，替代分散在 setter 的检查。
- 副作用：类结构变长（多了 Builder 内部类），字段多才划算。

## 4. 三种同类写法对比

| 方式 | 可读性 | 可选参处理 | 不可变 | 代码量 | 推荐 |
|---|---|---|---|---|---|
| 全参构造 | 差（不知道谁是谁） | 需传占位 null | ✅ | 少 | ❌ 字段多时 |
| telescoping 重载 | 中（版本暴增） | ✅ 但组合爆炸 | ✅ | 随字段爆炸 | ❌ |
| 链式 Builder | 好（字段名即标签） | ✅ 优雅 | ✅ | 多（+Builder 类） | ⭐⭐ |
| Lombok @Builder | 好 | ✅ 自动 | ✅ | 几乎零 | ⭐⭐⭐（可用 Lombo的） |

### 4.1 Lombok @Builder 自动生成

```java
import lombok.Builder;

@Builder
public class HttpConfig {
    private String url;
    private int timeoutMs = 3000;
    private int retries;
    private boolean followRedirects;
}
```

**说明**：`@Builder` 自动生成静态 `builder()` 与内部 `Builder` 类，省去手写。但注意：
- 字段不再要求 `final`（Lombok 生成的可变字段），若要保持不可变需结合 `@Data` 权衡。
- `build()` 校验需手写静态方法 `static void validate()` 或另处校验；Lombok 默认不做校验。
- 团队可用 Lombok 时优先；否则手写 Builder。

## 5. 什么时候不需要（过度设计）

- 字段少（≤3-4）且大多必填 → 直接构造器更清晰。
- 没有新增可选字段的扩展诉求 → 别为仪式感上 Builder。**字段少就别用**。

> 参考踩坑：[#3.1 必填字段被链式 setter 绕过，缺失校验](../99-设计模式踩坑记录.md)

## 6. 最佳实践

1. 字段多 + 多可选 + 需不可变 → 链式 Builder（Lombok 优先）。
2. 必填项/合法校验集中在 `build()` 一处。
3. Builder 一般放目标类静态内部类，语义内聚。

## 8. 小结

- 建造者解决「多可选参构造」的混乱：链式设置 + build 校验 + 不可变。
- 对比：全参/telescoping 都不如 Builder 可读；Lombok `@Builder` 是零样板实现。
- 判据：字段多且可选、要不可变、要校验 → 用；否则别硬上。
