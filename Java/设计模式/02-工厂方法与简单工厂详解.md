# 工厂方法与简单工厂详解

> 本篇拆解**简单工厂**与**工厂方法**两种创建模式，讲清「为什么从简单工厂进化到工厂方法」及其在 Spring 中的应用。

## 📋 总纲

工厂模式的核心：**把「创建哪种对象」的决定权从客户端手中收走**，让客户端面向抽象创建产品，新产品加入不用改客户端。简单工厂是入门，工厂方法是对它的「开闭」补强。

## 1. 是什么 / 为什么用（原理）

**问题**：假设有图形产品的多种实现，客户端如果直接 `new`，那么每加一个产品、每换一个创建逻辑，客户端都要跟着改——违反「开闭原则」（对扩展开放、对修改关闭）。

**解决思路**：加一层「工厂」隔离创建。客户端表达「我要一个图形」，工厂负责「具体 new 哪个实现」。

**生活类比**：餐厅**点菜**——你说「一条鱼」，厨师后厨做（工厂），你不需要知道自己吃的是哪种做法、原料从哪来，后厨加新菜你只管点单。

## 2. 简单工厂（Simple Factory）

**不是** GoF 的正式模式（GoF 只有工厂方法/抽象工厂），但它是理解工厂的起点。

### 2.1 产品接口 + 具体产品

```java
// 产品接口：客户端只依赖它
public interface Shape {
    void draw();
}

public class Circle implements Shape {
    public void draw() { System.out.println("画圆"); }
}

public class Square implements Shape {
    public void draw() { System.out.println("画方"); }
}
```

### 2.2 工厂类：用类型参数决定创建哪个

```java
public class ShapeFactory {
    public static Shape create(String type) {
        return switch (type) {
            case "circle" -> new Circle();
            case "square" -> new Square();
            default -> throw new IllegalArgumentException("未知类型: " + type);
        };
    }
}
```

### 2.3 客户端只依赖接口 + 工厂，不依赖具体类

```java
public class Client {
    public static void main(String[] args) {
        Shape s = ShapeFactory.create("circle");
        s.draw();   // 输出：画圆
    }
}
```

### 2.4 说明与取舍

- ✅ **客户端依赖抽象**：`Client` 里没有 `new Circle/Square`，换产品只改工厂一处。
- ❌ **加新产品要改工厂**：`create` 里每加一个 case 就要改 → 工厂类对修改不闭合。
- 适用：产品类型少、变化不频繁。它是工厂方法退化的简化版。

## 3. 工厂方法（Factory Method）

**关键升级**：把「创建逻辑」从一个大工厂里**下沉到子类**——每个产品一个专门工厂，谁来做？由「工厂接口 + 各产品工厂实现」决定。

```java
// 抽象工厂：定义产品工厂的骨架
public interface ShapeFactory {
    Shape create();
}

// 每个具体产品对应一个工厂
public class CircleFactory implements ShapeFactory {
    public Shape create() { return new Circle(); }
}

public class SquareFactory implements ShapeFactory {
    public Shape create() { return new Square(); }
}
```

**客户端**：持有工厂接口，具体工厂由外部注入/选择：

```java
public class Client {
    public static void main(String[] args) {
        ShapeFactory factory = new CircleFactory();   // 可选哪种工厂
        Shape s = factory.create();
        s.draw();
    }
}
```

### 3.1 为什么工厂方法更好（对比简单工厂）

| 维度 | 简单工厂 | 工厂方法 |
|---|---|---|
| 创建逻辑位置 | 集中在工厂类一个 switch | 分散到每个产品的子工厂 |
| 加新产品 | **要改工厂类**（不闭合） | **加一个新工厂子类即可**（不修改现有代码） |
| 客户端依赖 | 依赖「类型字符串 + 工厂」 | 依赖「工厂接口 + 具体工厂」 |
| 开闭原则 | ❌ | ✅ |
| 灵活性 | 差（一锅端） | 好（可组合不同工厂） |

**一句话**：工厂方法把「简单工厂的修改」变成了「新增」，用「多写几个类」换「对扩展开放」——这正是面向对象高级写法的体现。

## 4. 工厂模式在 Spring 里的印证

- **BeanFactory / ApplicationContext** 就是「对象工厂」：`getBean("beanName")` 按配置/注解决定创建哪个 Bean，客户端不 `new` 具体 Bean。
- **FactoryBean** 接口：当你要自定义「如何创建一个复杂 Bean」时，实现 `FactoryBean<T>`，Spring 调用 `getObject()` 产出对象——本质是工厂方法的框架级落地。
- 高版本 `getBean` 还支持泛型。

## 5. 何时用 / 何时别用（避免过度设计）

**该用**：对象创建逻辑复杂、产品类型多、客户端不应知道具体实现、需要统一创建入口（如连接池、各种配置解析器）。

**别用**：只有一个或固定几个类、没有扩展诉求时，直接 `new` + 简单工厂反而更清晰。**过度抽象工厂是常见反模式**。

> 参考踩坑：[#2.1 工厂只能撑必要场景，别为仪式感上抽象工厂](99-设计模式踩坑记录.md)

## 6. 最佳实践

1. 先写最简单的 `new`，等「创建逻辑集中、类型频繁扩展」真出现再上工厂。
2. 用工厂方法优先于简单工厂——扩展性好，「加类型=加子类」。
3. 客户端只依赖抽象（接口/工厂接口），杜绝依赖具体产品类。

## 8. 小结

- 简单工厂：一个工厂里 switch 分派，入门最直观，但加类型要改工厂。
- 工厂方法：工厂接口 + 各产品子工厂，加类型=加子类，对扩展开放。
- 核心思想：**面向接口创建，把「选哪个」的决定权从客户端收走**。
- Spring 的 BeanFactory / FactoryBean 是工厂模式的框架级实证。
