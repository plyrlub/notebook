# 原型模式详解

> 本篇讲原型模式的原理：用「克隆已有对象」代替「重新构造」，并重点辨析深浅克隆这个高频坑。

## 📋 总纲

原型模式的核心是**通过复制已有实例来产生新实例**，而不走构造器。它的价值在于：当对象构造代价高、且字段很多时，克隆比一个个重建更快更省。

## 1. 是什么 / 为什么用（原理）

**问题**：有些对象创建很「贵」——例如要查库、大量字段初始化、或结构复杂。直接用 `new FishTail().setX()...` 重建既要重跑初始化流程，代码又啰嗦。

**解决思路**：拿到一个现成实例，**克隆一份**作为新对象，再改需要的字段。Java 用 `Cloneable` + `Object.clone()` 实现。

**生活类比**：**印章刻好一份模板**，要多少印多少张，而不是每张都重新镌刻一份。

## 2. 浅克隆（Java 默认）

`Object.clone()` 默认做**浅拷贝**：所有基本类型字段完整复制值，但**引用类型字段只是复制了指针**（新旧对象指向同一个引用对象）。

```java
public class Sheep implements Cloneable {
    private String name;
    private Owner owner;      // 引用类型

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return super.clone();   // 浅拷贝：owner 是同一个引用
    }
}
```

```java
Sheep s1 = new Sheep();
Owner o = new Owner("张三");
s1.setOwner(o);

Sheep s2 = (Sheep) s1.clone();       // 克隆得到 s2
s1.getOwner().setName("李四");        // 改的是同一个 owner 引用
System.out.println(s2.getOwner().getName());  // 李四！?? s2 被连带改了
```

**说明**：
- `clone()` 是 `protected`，实现 `Cloneable` 接口（**标记接口**，空方法体）后才能调用。
- 浅克隆**共享引用**：只克隆「外壳」，内部引用还是同一个，改任一方的引用对象双方都变——这是多数原型 bug 的来源。

## 3. 深克隆（需要独立副本时）

要让引用字段也独立复制，需在 `clone()` 里**手动克隆引用字段**：

```java
public class Sheep implements Cloneable {
    private Owner owner;

    @Override
    protected Object clone() throws CloneNotSupportedException {
        Sheep copy = (Sheep) super.clone();       // 先浅拷贝外壳
        copy.owner = new Owner(this.owner.getName()); // 再深拷贝引用
        return copy;
    }
}
```

**说明**：深克隆要 `super.clone()` 后手动 `new`/clone 每个引用字段。若对象引用图很复杂（嵌套引用），手写极易漏，可改用**序列化复制**（对象实现 `Serializable`，写进/读出字节流，得到全深拷贝）或用 JSON 拷贝工具。

## 4. 深浅对比与选型

| 维度 | 浅克隆 | 深克隆 |
|---|---|---|
| 基本类型字段 | 值复制 ✅ | 值复制 ✅ |
| 引用类型字段 | 只复制指针（**共享**引用） | 独立复制（**不共享**） |
| 实现 | `super.clone()` 默认 | 手动 clone 引用 / 序列化/JSON |
| 性能 | 快 | 较慢 |
| 改对方影响 | 会被连带影响 | 互不影响 |

**选型**：若引用是**不可变对象/枚举/值对象**（如 String、Integer），浅克隆就够（共享无害）；若要**独立可变副本**（如集合、业务对象），必须深克隆。

## 5. 与单例的区别（易混考点）

| | 原型 | 单例 |
|---|---|---|
| 实例数 | 多份（每 clone 一份） | 唯一 |
| 目的 | 复制得到独立副本 | 全局唯一 |

## 6. 何时用 / 代价

- **该用**：对象创建代价大（重初始化/查询）、又需要多份独立但大部分字段相同的数据（如基于一份默认模板产生多个配置实例、游戏里的敌人/子弹批量生成）。
- **代价**：深克隆在对象引用图复杂时很难维护；克隆绕过构造器意味着**构造器里的校验/初始化逻辑不会执行**，需留意。
- 现代实践：多数场景用 **Java 记录（record）+ 构造器/** MapStruct 等拷贝工具也能达成，原生 `Cloneable` 用得不多。**原型是低频模式**，精而简掌握即可。

> 参考踩坑：[#4.1 浅克隆共享引用，改一个全变](99-设计模式踩坑记录.md)

## 7. 最佳实践

1. 默认浅克隆只用于「引用字段不可变」的场景。
2. 需要独立可变副本 → 深克隆（手动 clone 或序列化/JSON）。
3. 极低频模式，别到处套；先想是否普通 `new` + 字段复制即可。

## 9. 小结

- 原型 = `Cloneable` + `clone()`，克隆已有实例替代重建。
- 浅克隆共享引用，是高频坑；要独立副本须深克隆。
- 低频模式，仅「构造贵 + 要独立多份」时用；与单例的「多份 vs 唯一」是易混点。
