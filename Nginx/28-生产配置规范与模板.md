## 2. 核心知识点

### 2.1 知识点一：配置文件目录规范

#### 为什么需要目录规范

开发阶段写 Nginx 配置，最常见的就是一个 `nginx.conf` 把所有 server、upstream、location 全塞进去。这种"一锅炖"在机器数量少、站点少时勉强能用，但一旦上生产就会暴露三个问题：

1. **合并冲突**：多人同时改一个 `nginx.conf`，git merge 几乎必冲突。
2. **复用困难**：每个站点都重复写一遍 proxy_set_header、ssl 配置、gzip 配置，改一处要改 N 处，漏改就是事故。
3. **职责不清**：全局参数、站点配置、通用片段混在一起，不知道哪行该动、哪行不能动。

生产规范的核心思路是**分层 + include**：主配置只管全局，站点配置按文件拆分，通用片段抽成 snippets 用 `include` 引入。

#### 推荐目录结构

```text
/etc/nginx/
├── nginx.conf                      # 主配置：只放全局参数、events、http 框架，不写具体 server
├── conf.d/                         # 站点配置目录：一个站点一个文件，nginx.conf 用 include conf.d/*.conf 加载
│   ├── example.com.conf            #   主站 HTTPS
│   ├── api.example.com.conf        #   API 子域名
│   ├── admin.example.com.conf      #   后台子域名
│   └── default.conf                #   兜底 server（default_server）
├── snippets/                       # 通用配置片段：用 include 引入，避免复制粘贴
│   ├── proxy_params.conf           #   统一的 proxy 头透传
│   ├── ssl_params.conf             #   统一的 SSL 安全参数
│   ├── gzip_params.conf            #   统一的 gzip 配置
│   ├── security_headers.conf       #   统一的安全响应头
│   └── websocket_params.conf       #   WebSocket 升级头
├── ssl/                            # 证书目录：权限收紧（root:root 600）
│   ├── example.com/
│   │   ├── fullchain.crt           #   服务器证书 + 中间证书（合并文件）
│   │   └── private.key             #   私钥
│   └── api.example.com/
│       ├── fullchain.crt
│       └── private.key
├── upstream/                       # upstream 池配置（可选拆分，便于多站点共享同一个后端池）
│   ├── user_service.conf
│   └── order_service.conf
├── maps/                           # map 块配置（可选拆分，灰度路由、变量映射）
│   └── canary.conf
├── logs/                           # 日志目录（或软链到 /var/log/nginx）
│   ├── access.log
│   ├── error.log
│   └── example.com.access.log     #   分站点日志
└── modules/                        # 动态模块目录（如有第三方模块）
    └── ngx_http_js_module.so
```

逐层说明：

1. **`nginx.conf`（主配置）**——只写"全局级"内容：`user`/`worker_processes`/`error_log`/`pid`/`events`/`http` 块的框架指令（mime、log_format、sendfile、keepalive 等全局 HTTP 参数），以及 `include conf.d/*.conf;` 这一行加载站点。**绝不在这里写具体的 server 块**。
2. **`conf.d/`（站点配置）**——每个域名或每个服务一个 `.conf` 文件。Nginx 官方包安装后默认就有这个目录，`nginx.conf` 里默认 `include /etc/nginx/conf.d/*.conf;`。文件粒度小，git 改动一目了然，谁改了哪个站点清清楚楚。
3. **`snippets/`（通用片段）**——把多处复用的配置抽成独立文件，用 `include snippets/xxx.conf;` 引入。改一处即全局生效，杜绝"改了 A 站忘改 B 站"。
4. **`ssl/`（证书）**——证书集中存放，按域名分子目录。权限收紧为 `root:root` 且私钥 `chmod 600`，防止私钥泄露。
5. **`upstream/`、`maps/`（可选拆分）**——当 upstream 池被多个站点共享、或 map 规则较复杂时，单独拆目录管理更清晰。小项目可不必，直接写在站点文件里。
6. **`logs/`（日志）**——生产建议按站点拆日志（`access_by_host` 或每站点独立 `access_log`），便于按域名排查。

#### nginx.conf 如何加载这些目录

```nginx
# /etc/nginx/nginx.conf 的 http 块末尾
http {
    # ... 全局参数 ...

    # 加载所有 map 块（必须在使用变量的 server 之前 include）
    include /etc/nginx/maps/*.conf;

    # 加载所有 upstream 池（必须在 proxy_pass 引用之前 include）
    include /etc/nginx/upstream/*.conf;

    # 加载所有站点配置
    include /etc/nginx/conf.d/*.conf;
}
```

逐行说明：

- `include /etc/nginx/maps/*.conf;`——map 块定义变量映射，必须在引用该变量的 server 之前加载，所以放最前面。
- `include /etc/nginx/upstream/*.conf;`——upstream 池定义，需在 proxy_pass 引用前加载；单独拆出便于多站点共享同一个后端池。
- `include /etc/nginx/conf.d/*.conf;`——站点配置，放最后；按文件名字母序加载，建议用 `00-`、`99-` 前缀控制加载顺序（如 `00-default.conf` 兜底）。

> **加载顺序要点**：Nginx 按 `include` 的 glob 匹配结果按**文件名字母序**加载。如果配置间有依赖（如 map 必须先于 server），用数字前缀强制排序。

#### 特例说明

1. **Kubernetes Ingress-Controller 不用这套目录规范**：Ingress-Nginx 的配置由控制器自动生成到 `/etc/nginx/nginx.conf`，人工不该手改。本规范适用于"自管 Nginx"场景。
2. **源码编译安装没有 `conf.d/`**：源码安装默认只有 `nginx.conf`，`conf.d/`、`snippets/` 需自己 `mkdir` 并在 `nginx.conf` 里加 `include`。
3. **某些发行版用 `sites-available/` + `sites-enabled/`**：Debian/Ubuntu 系借鉴 Apache 的风格，用 `sites-enabled/` 放软链到 `sites-available/`。这与 `conf.d/` 是两种风格，选其一即可，不要混用。

> **参考踩坑**：[#1.8 root 放在 location 内导致未匹配 location 无根目录](99-踩坑记录与解决方案.md#18-root-放在-location-内导致未匹配-location-无根目录)——root 应放 server 层级继承，目录规范配合层级规范才不会漏。

### 2.2 知识点二：命名规范

#### 为什么命名规范重要

配置文件是"基础设施即代码"（IaC）的一部分。命名混乱会让排障变成考古：看到一个 `upstream b1`，你不知道它是用户服务还是订单服务；看到一个 `location /a/`，你不知道它指向哪。统一的命名让配置"自文档化"，看名字就能猜出用途。

#### 四条命名铁律

**铁律一：站点配置文件命名——`domain.conf` 或 `service-name.conf`**

```text
# ✅ 推荐：用域名或服务名命名，一眼看出是谁
conf.d/example.com.conf              # 主站
conf.d/api.example.com.conf          # API 子域
conf.d/admin.example.com.conf        # 后台子域
conf.d/user-service.conf             # 内部服务（无对外域名时用服务名）

# ❌ 避免：含义不明
conf.d/1.conf
conf.d/test.conf
conf.d/new.conf
conf.d/backup2.conf
```

说明：对外站点用完整域名（`example.com.conf`），内部服务用服务名（`user-service.conf`）。需要控制加载顺序时加数字前缀：`00-default.conf`、`99-redirect.conf`。

**铁律二：upstream 命名——`服务名_upstream`**

```nginx
# ✅ 推荐：服务名 + _upstream 后缀，与站点文件名呼应
upstream user_service_upstream {
    server 10.0.0.1:8080;
}
upstream order_service_upstream {
    server 10.0.0.2:8080;
}

# ❌ 避免：太短或含义不明
upstream b1 { ... }
upstream backend { ... }       # 多个服务都用 backend 就分不清了
upstream upstream1 { ... }
```

说明：`_upstream` 后缀是为了在 proxy_pass 引用时一眼区分"这是上游池"还是"普通变量"。proxy_pass 写 `http://user_service_upstream` 时语义清晰。

**铁律三：location 路径命名——统一加尾斜杠或统一不加**

```nginx
# ✅ 风格 A：目录型路径统一加尾斜杠
location /api/ { ... }        # 加 /
location /static/ { ... }     # 加 /
location /ws/ { ... }         # 加 /
location = /health { ... }    # 精确匹配除外（单个资源不加）

# ✅ 风格 B：也可以统一不加，但要在 proxy_pass 时注意 URI 改写
# location /api { ... }
# location /static { ... }

# ❌ 避免：混用，导致尾斜杠语义不一致
location /api/ { ... }        # 加了
location /static { ... }      # 没加
```

说明：尾斜杠是否加，关系到 `proxy_pass` 的 URI 改写行为（带尾斜杠会替换前缀）。团队内**统一一种风格**比"哪种对"更重要。推荐目录型路径统一加尾斜杠，单资源精确匹配（`=`）不加。

> **参考踩坑**：[#1.4 proxy_pass 末尾斜杠导致 URI 被改写](99-踩坑记录与解决方案.md#14-proxy_pass-末尾斜杠导致-uri-被改写)——尾斜杠的语义与 location 命名规范强相关。

**铁律四：变量命名——`snake_case`**

```nginx
# ✅ 推荐：自定义变量用 snake_case，与 Nginx 内置变量风格一致
map $http_x_canary $is_canary_user {
    default 0;
    "true" 1;
}
set $backend_version "v2";

# ❌ 避免：驼峰或无意义缩写
map $http_x_canary $isCanaryUser { ... }   # 驼峰，不符合 Nginx 习惯
set $bv "v2";                               # 缩写无意义
```

说明：Nginx 内置变量全是 `snake_case`（`$remote_addr`、`$proxy_host`、`$request_uri`），自定义变量应保持一致，避免读配置时风格割裂。变量名要能自解释，宁可长一点也不要无意义缩写。

#### 特例说明

1. **多环境命名**：dev/staging/prod 环境建议用不同域名或不同 conf.d 目录隔离，而不是在文件名里加环境后缀（`example.com.prod.conf` 容易被误加载到测试环境）。推荐 `/etc/nginx/conf.d/` 只放当前环境的配置，环境差异由部署流程管理。
2. **upstream 名不能带下划线以外的特殊字符**：upstream 名只能用字母、数字、下划线，不能用 `-`（连字符在 proxy_pass 的 host 解析里有歧义）。所以 `user_service_upstream` 合法，`user-service-upstream` 非法。
3. **变量名不要与内置变量冲突**：自定义变量别用 `$host`、`$uri` 等内置名，会覆盖导致行为异常。

> **参考踩坑**：[#1.11 含下划线的请求头被静默丢弃](99-踩坑记录与解决方案.md#111-含下划线的请求头被静默丢弃)——命名规范里"下划线"用于变量/upstream 是安全的，但用于**请求头名**会被默认丢弃，需 `underscores_in_headers on`。

### 2.3 知识点三：通用配置片段（snippets）

#### snippets 的价值

没有 snippets 时，每个站点的 SSL 配置、proxy 头、gzip 配置都要复制粘贴一遍。一旦要调整（比如升级加密套件、新增一个安全头），得改 N 个文件，漏一个就是安全隐患。snippets 把"通用部分"抽成独立文件，用 `include` 引入，改一处全局生效。

#### snippet 一：proxy_params.conf（统一 proxy 头透传）

```nginx
# /etc/nginx/snippets/proxy_params.conf
# 作用：统一的反向代理请求头透传，所有 proxy_pass 的 location 都 include 它

# 传递客户端访问的原始域名给后端（默认是 $proxy_host 即上游地址，会导致后端基于 Host 的路由失效）
proxy_set_header Host              $host;

# 客户端真实 IP（直连 Nginx 的那个 IP，非 XFF 链）
proxy_set_header X-Real-IP         $remote_addr;

# 转发链：把已有 XFF + 当前直连 IP 追加进去，后端取最右侧即为真实客户端
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;

# 原始协议（http 还是 https），后端据此生成正确的回调 URL
proxy_set_header X-Forwarded-Proto $scheme;

# 原始 Host（部分后端框架需要），与 Host 一致但语义是"原始请求主机"
proxy_set_header X-Forwarded-Host  $host;

# 连接类型：开 upstream keepalive 时必须清空 Connection 头，否则长连接不复用
proxy_set_header Connection        "";

# HTTP 版本：1.29.7+ 默认已是 1.1，显式声明便于旧版兼容与可读性
proxy_http_version 1.1;
```

逐行说明：

- `Host $host`——后端拿到的 Host 是用户访问的域名，而不是上游 IP。若不设，默认 `$proxy_host` 会让后端的虚拟主机路由、签名校验失效。
- `X-Real-IP $remote_addr`——后端日志/鉴权看到的真实客户端 IP。
- `X-Forwarded-For $proxy_add_x_forwarded_for`——标准转发链，后端从可信代理链最右侧取真实 IP。
- `X-Forwarded-Proto $scheme`——后端据此判断原始是 http/https，生成正确的协议链接。
- `Connection ""`——清空 Connection 头是 upstream keepalive 生效的前提。
- `proxy_http_version 1.1`——HTTP/1.1 才支持 keepalive。

使用方式：

```nginx
location /api/ {
    proxy_pass http://user_service_upstream;
    include /etc/nginx/snippets/proxy_params.conf;   # 一行引入全部头
}
```

> **参考踩坑**：[#5.4 后端拿不到真实客户端 IP](99-踩坑记录与解决方案.md#54-后端拿不到真实客户端-ip)——不 include proxy_params 或漏写 X-Real-IP 的典型后果。

#### snippet 二：ssl_params.conf（统一 SSL 安全配置）

```nginx
# /etc/nginx/snippets/ssl_params.conf
# 作用：统一的 SSL/TLS 安全参数，所有 HTTPS server 都 include 它

# 仅启用 TLS1.2/1.3，禁用已不安全的 SSLv3/TLS1.0/TLS1.1
ssl_protocols TLSv1.2 TLSv1.3;

# 加密套件：优先 ECDHE 前向保密 + GCM 认证加密；TLS1.3 套件由协议自动协商
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

# TLS1.3 下建议 off，让客户端决定套件（客户端更知道自己的硬件加速）
ssl_prefer_server_ciphers off;

# 会话缓存：共享内存 50m（约 4 万个会话），减少 TLS 握手开销
ssl_session_cache shared:SSL:50m;

# 会话超时：1 天内可复用会话票证
ssl_session_timeout 1d;

# 会话票证：开启后单机即可跨连接复用（集群部署需共享密钥）
ssl_session_tickets on;

# OCSP Stapling：Nginx 主动获取证书吊销状态下发给客户端，省去客户端联网查询
ssl_stapling on;
ssl_stapling_verify on;

# OCSP 验证需要完整的证书链（含中间证书）
ssl_trusted_certificate /etc/nginx/ssl/example.com/fullchain.crt;

# OCSP 解析需要 DNS resolver
resolver 8.8.8.8 8.8.4.4 valid=300s;
resolver_timeout 5s;
```

逐行说明：

- `ssl_protocols TLSv1.2 TLSv1.3`——禁用旧协议是安全基线，TLS1.0/1.1 有 BEAST/POODLE 风险。
- `ssl_ciphers`——只保留前向保密（ECDHE）+ 认证加密（GCM/CHACHA20），杜绝 RC4/CBC 等弱套件。
- `ssl_session_cache shared:SSL:50m`——`shared` 表示所有 worker 共享，`50m` 约 4 万会话，高并发下显著降低握手开销。
- `ssl_stapling on`——OCSP Stapling，避免客户端联网查吊销状态（慢且泄露隐私）。

使用方式：

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/example.com/fullchain.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com/private.key;
    include /etc/nginx/snippets/ssl_params.conf;   # 引入统一 SSL 参数
}
```

> **特例**：证书文件路径因域名不同无法统一到 snippet，所以 `ssl_certificate` / `ssl_certificate_key` 留在各 server 里，snippet 只放"与域名无关的安全参数"。

#### snippet 三：gzip_params.conf（统一 gzip 配置）

```nginx
# /etc/nginx/snippets/gzip_params.conf
# 作用：统一的 gzip 压缩配置，减少传输体积

# 开启 gzip
gzip on;

# 压缩级别 1-9，5 是性能与压缩比的平衡点（9 几乎不增加压缩率却显著增加 CPU）
gzip_comp_level 5;

# 最小压缩体积：小于 1k 的文件压缩收益小反而增加 CPU 开销
gzip_min_length 1024;

# 压缩的 MIME 类型：文本类才压缩，图片/视频已压缩再 gzip 无益
gzip_types text/plain text/css text/xml text/javascript
           application/javascript application/json application/xml
           application/rss+xml application/atom+xml
           image/svg+xml font/ttf font/otf;

# 对代理请求也启用压缩（默认 off，因为后端可能已压缩）
gzip_proxied any;

# 添加 Vary: Accept-Encoding 响应头，避免缓存服务器给不支持 gzip 的客户端返回压缩内容
gzip_vary on;

# 禁用对 IE6 的压缩（IE6 对 gzip 有 bug）
gzip_disable "MSIE [1-6]\.";
```

逐行说明：

- `gzip_comp_level 5`——级别越高 CPU 越高，5 是经验最佳点。
- `gzip_min_length 1024`——小文件压缩收益小，1k 是经验阈值。
- `gzip_types`——只压缩文本类，二进制（图片/视频）已压缩，再 gzip 反而浪费 CPU。
- `gzip_vary on`——缓存正确性的关键，不加可能导致 CDN 缓存错版本。

使用方式：在 `nginx.conf` 的 http 块里 include 一次即可全局生效：

```nginx
http {
    # ...
    include /etc/nginx/snippets/gzip_params.conf;
}
```

#### snippet 四：security_headers.conf（统一安全响应头）

```nginx
# /etc/nginx/snippets/security_headers.conf
# 作用：统一的安全响应头，所有 server 都 include，防 XSS/点击劫持/MIME 嗅探

# HSTS：强制浏览器后续都用 HTTPS 访问（max-age 1 年，含子域）
# 注意：确认全站 HTTPS 后再启用，否则会"锁死"仍需 HTTP 的资源
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

# 防点击劫持：禁止被 iframe 嵌套（SAMEORIGIN 允许同源嵌套）
add_header X-Frame-Options "SAMEORIGIN" always;

# 防 MIME 嗅探：浏览器严格按 Content-Type 解析，不猜测
add_header X-Content-Type-Options "nosniff" always;

# CSP 内容安全策略：限制资源加载来源（按业务调整，示例是宽松版）
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;" always;

# Referrer 策略：只向同源发送完整 referrer，跨源只发 origin
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

# 权限策略：禁用不需要的浏览器能力（摄像头/麦克风/地理位置）
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

逐行说明：

- `Strict-Transport-Security`——HSTS，防止中间人降级攻击。
- `X-Frame-Options SAMEORIGIN`——防点击劫持（Clickjacking）。
- `X-Content-Type-Options nosniff`——防 MIME 嗅探。
- `Content-Security-Policy`——CSP，防 XSS 的最强手段，需按业务精细调整。
- `always` 后缀——即使响应是 4xx/5xx 也下发该头（不加 only-on-2xx 默认行为会漏掉错误页）。

使用方式：

```nginx
server {
    listen 443 ssl;
    # ...
    include /etc/nginx/snippets/security_headers.conf;
}
```

> **特例**：`add_header` 在 Nginx 里有**继承覆盖**语义——如果 location 里写了任何 `add_header`，server 层的 `add_header` 不会继承下来。所以要么把所有 add_header 集中在 server 层，要么在 location 里重新 include snippet。

#### websocket_params.conf（补充片段）

```nginx
# /etc/nginx/snippets/websocket_params.conf
# 作用：WebSocket 协议升级头，专门给 /ws/ 路径用

# HTTP/1.1 是 WebSocket 握手的前提
proxy_http_version 1.1;

# 透传客户端的 Upgrade 头（websocket 或空）
proxy_set_header Upgrade $http_upgrade;

# Connection 设为 upgrade，通知后端做协议升级
proxy_set_header Connection "upgrade";

# WebSocket 长连接，默认 60s 会断，需调大读超时
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

> **参考踩坑**：[#5.3 WebSocket 代理未升级协议头](99-踩坑记录与解决方案.md#53-websocket-代理未升级协议头)——不 include 此片段的典型后果是 101 握手失败。

### 2.4 知识点四：生产 nginx.conf 主配置模板

#### 设计原则

主配置 `nginx.conf` 是整个 Nginx 的"宪法"：它定义全局运行参数（进程、文件描述符、日志）和 http 块的框架（mime、log_format、全局优化参数），但**不写任何具体 server**。具体站点通过 `include conf.d/*.conf` 加载。这样主配置几乎不需要改动，所有业务变更都在 conf.d 里完成。

#### 完整生产模板

```nginx
# /etc/nginx/nginx.conf
# 生产级主配置模板 · Nginx 1.30.4
# 设计原则：主配置只管全局，站点配置见 conf.d/

# ============ 全局参数（main 上下文） ============

# 运行用户：生产建议用非 root 的专用用户，降低提权风险
user nginx;

# worker 进程数：auto 自动匹配 CPU 核心数，避免过多进程争抢 CPU
worker_processes auto;

# worker 进程的 CPU 亲和性：auto 让操作系统自动绑核
worker_cpu_affinity auto;

# 错误日志：级别 warn 足够排障，debug 日志量过大只用于开发
error_log /var/log/nginx/error.log warn;

# PID 文件位置（包安装默认在 /run/nginx.pid）
pid /run/nginx.pid;

# worker 进程能打开的最大文件描述符数：与系统 ulimit 配合
worker_rlimit_nofile 65535;

# ============ events 块（事件模型） ============

events {
    # 单 worker 最大连接数：反代场景每客户端占 2 条连接，按 worker*connections/4 估算
    worker_connections 16384;

    # 事件模型：Linux 用 epoll，macOS 用 kqueue，Nginx 会自动选，显式写可读性更好
    use epoll;

    # 允许一个 worker 同时接受多个连接：高并发突发场景减少锁竞争
    multi_accept on;
}

# ============ http 块 ============

http {
    # ---- 基础设置 ----

    # 加载 MIME 类型映射表
    include /etc/nginx/mime.types;

    # 默认 Content-Type：避免未匹配类型时浏览器猜测
    default_type application/octet-stream;

    # 隐藏版本号：错误页/响应头只显示 nginx 不显示版本，避免被针对性攻击
    server_tokens off;

    # 允许下划线请求头：部分后端/客户端用下划线命名头（如 X_My_Header）
    underscores_in_headers on;

    # ---- 日志格式 ----

    # 定义 JSON 格式日志（详见知识点七），便于 ELK/Loki 直接消费
    log_format json_combined escape=json
        '{'
            '"time":"$time_iso8601",'
            '"remote_addr":"$remote_addr",'
            '"x_forwarded_for":"$http_x_forwarded_for",'
            '"request_method":"$request_method",'
            '"request_uri":"$request_uri",'
            '"server_name":"$server_name",'
            '"status":$status,'
            '"body_bytes_sent":$body_bytes_sent,'
            '"request_time":$request_time,'
            '"upstream_response_time":"$upstream_response_time",'
            '"upstream_addr":"$upstream_addr",'
            '"http_referer":"$http_referer",'
            '"http_user_agent":"$http_user_agent"'
        '}';

    # 主访问日志：用 JSON 格式
    access_log /var/log/nginx/access.log json_combined;

    # ---- 性能优化（全局） ----

    # 零拷贝发送文件：静态资源传输不走用户态，性能大幅提升
    sendfile on;

    # 配合 sendfile：数据攒够一个完整 TCP 段再发，减少小包
    tcp_nopush on;

    # keepalive 空闲时禁用 Nagle，及时发送 keepalive 探测
    tcp_nodelay on;

    # 客户端长连接超时：65s 略大于常见 LB 的 60s 探测间隔，避免被 LB 误断
    keepalive_timeout 65s;

    # 单连接最大请求数：1000 是默认值，高 QPS 场景可调大
    keepalive_requests 1000;

    # 客户端请求体大小限制：防止大文件上传打爆内存（按业务调整）
    client_max_body_size 20m;

    # 客户端请求头缓冲：默认 1k 太小，大 header（多 cookie）会落临时文件
    client_header_buffer_size 4k;
    large_client_header_buffers 4 16k;

    # 客户端请求体缓冲：小于此值走内存，超过落临时文件
    client_body_buffer_size 128k;

    # ---- 全局 snippets ----

    # gzip 全局开启（也可放各 server，全局更省事）
    include /etc/nginx/snippets/gzip_params.conf;

    # ---- 加载 map（必须在使用变量的 server 前） ----
    include /etc/nginx/maps/*.conf;

    # ---- 加载 upstream 池（必须在 proxy_pass 引用前） ----
    include /etc/nginx/upstream/*.conf;

    # ---- 加载所有站点配置 ----
    include /etc/nginx/conf.d/*.conf;
}
```

逐段说明：

- **全局参数段**——`user nginx` 用非 root 账户运行（worker 进程是 root 会放大提权风险）；`worker_processes auto` 让 Nginx 自动按 CPU 核心数起 worker（手动设错反而争抢 CPU）；`worker_rlimit_nofile 65535` 提升 worker 的文件描述符上限，配合系统 ulimit。
- **events 段**——`worker_connections 16384` 是单 worker 最大连接数，反代场景按 `worker数 × connections / 4` 估算并发；`multi_accept on` 让一个 worker 一次 accept 多个连接，应对突发。
- **http 基础段**——`server_tokens off` 隐藏版本号；`underscores_in_headers on` 允许下划线请求头。
- **日志段**——`log_format json_combined escape=json` 定义 JSON 日志，`escape=json` 自动转义特殊字符，避免日志注入破坏 JSON 解析。
- **性能优化段**——`sendfile on` + `tcp_nopush on` + `tcp_nodelay on` 是静态资源性能三件套；`keepalive_timeout 65s` 略大于 LB 探测间隔避免误断。
- **include 段**——按依赖顺序加载 map → upstream → 站点配置。

> **参考踩坑**：[#2.1 worker_processes 设置不当](99-踩坑记录与解决方案.md#21-worker_processes-设置不当)——`auto` 是最稳妥的选择，手动设错是常见性能问题。

> **特例**：`worker_processes auto` 在容器环境（CPU 限制通过 cgroup）可能识别不准，需按容器分配的 CPU 数手动指定（如 `worker_processes 4;`）。

### 2.5 知识点五：生产站点配置模板

本知识点给出三种最常用的站点模板：HTTP 跳转、HTTPS 全套、API 反代（带限流缓存）。它们都遵循"snippet 复用 + 配置自文档化"的风格，可以直接落到 `conf.d/` 里使用。

#### 模板一：HTTP 站点（HTTP → HTTPS 重定向）

```nginx
# /etc/nginx/conf.d/example.com.conf
# 作用：把 80 端口的 HTTP 请求 301 永久重定向到 HTTPS

# HTTP server：只做重定向，不处理业务
server {
    # 监听 80 端口，标记为该端口的默认 server（兜底）
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    # 301 永久重定向到 HTTPS，保留原始 URI 和参数
    # 用 $request_uri 而非 $uri：$request_uri 是原始请求不会被 rewrite 改写
    return 301 https://$host$request_uri;
}
```

逐行说明：

- `listen 80;`——监听 HTTP 端口。一个 server 块只做重定向，不在这里处理任何业务请求。
- `server_name example.com www.example.com;`——匹配这两个域名。带 `www` 和不带 `www` 都跳到 HTTPS。
- `return 301 https://$host$request_uri;`——`$host` 是用户访问的域名，`$request_uri` 是原始请求路径（含查询参数）。用 `return` 而非 `rewrite` 是官方推荐做法，性能更好且不会触发 rewrite 循环。

> **特例**：如果要让 `www.example.com` 跳到 `example.com`（去 www），重定向目标应写死 `https://example.com$request_uri;` 而非用 `$host`，否则会跳回 `www` 自己。

> **参考踩坑**：[#1.6 $uri 在内部跳转后被改写](99-踩坑记录与解决方案.md#16-uri-在内部跳转后被改写)——重定向要用 `$request_uri` 而非 `$uri`。

#### 模板二：HTTPS 站点（完整 SSL + HTTP/2 + 安全头）

```nginx
# /etc/nginx/conf.d/example.com.conf（HTTPS 段，与上面的 HTTP 段同文件）
# 作用：主站 HTTPS 服务，含静态资源 + 后端反代 + 安全头

server {
    # 监听 443，开启 SSL；HTTP/2 用独立指令（1.25.1+ 新写法）
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;

    server_name example.com www.example.com;

    # root 放 server 层级，所有 location 继承，避免漏写 root 导致 404
    root /var/www/example.com;
    index index.html index.htm;

    # ---- 证书：路径因域名不同，不进 snippet ----
    ssl_certificate     /etc/nginx/ssl/example.com/fullchain.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com/private.key;

    # ---- SSL 安全参数：snippet 统一管理 ----
    include /etc/nginx/snippets/ssl_params.conf;

    # ---- 安全响应头：snippet 统一管理 ----
    include /etc/nginx/snippets/security_headers.conf;

    # ---- 分站点访问日志 ----
    access_log /var/log/nginx/example.com.access.log json_combined;
    error_log  /var/log/nginx/example.com.error.log warn;

    # ---- 健康检查端点：LB 探测用，不走后端 ----
    location = /health {
        access_log off;          # 健康检查不打日志，避免刷屏
        return 200 "ok\n";
        add_header Content-Type text/plain;
    }

    # ---- 静态资源：Nginx 直接服务，命中不了再回退 ----
    location / {
        # 先找文件、再找目录、最后回退到 index.html（SPA 单页应用常用）
        try_files $uri $uri/ /index.html;
    }

    # ---- 静态资源缓存：独立 location，长缓存 ----
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?|ttf|otf|eot)$ {
        # 浏览器缓存 30 天
        expires 30d;
        # 添加 immutable，告诉浏览器资源不变无需重新验证
        add_header Cache-Control "public, immutable";
        access_log off;          # 静态资源不打访问日志
    }

    # ---- favicon：单独处理，404 不记日志 ----
    location = /favicon.ico {
        log_not_found off;
        access_log off;
    }

    # ---- 隐藏文件拦截：禁止访问点开头的文件（.git/.env 等） ----
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }
}
```

逐段说明：

- **`http2 on;`**——1.25.1 起改用独立指令，旧的 `listen 443 ssl http2;` 已弃用。
- **`root /var/www/example.com;`**——root 放 server 层级是关键，所有 location 自动继承，避免每个 location 重复写或漏写。
- **证书 + ssl_params**——证书路径因域名不同留在 server，SSL 安全参数用 snippet 统一。
- **健康检查 `location = /health`**——`=` 精确匹配，最高优先级；LB 探测这个端点判断 Nginx 是否存活，不走后端，且不打日志。
- **`try_files $uri $uri/ /index.html;`**——SPA 路由的标准写法，前端路由刷新 404 时回退到 index.html。
- **静态资源 `expires 30d`**——长缓存减少回源，配合文件名 hash 实现缓存更新。
- **`location ~ /\.`**——拦截 `.git`、`.env` 等隐藏文件，防止源码/配置泄露。

> **参考踩坑**：[#1.8 root 放在 location 内导致未匹配 location 无根目录](99-踩坑记录与解决方案.md#18-root-放在-location-内导致未匹配-location-无根目录)——本模板把 root 放 server 层正是规避此坑。

> **参考踩坑**：[#4.6 HTTP/2 配置坑](99-踩坑记录与解决方案.md#46-http2-配置坑listen-与-http2-指令)——1.25.1+ 必须用 `http2 on;`。

#### 模板三：API 反代站点（upstream + 限流 + 缓存）

```nginx
# /etc/nginx/conf.d/api.example.com.conf
# 作用：API 子域名反代，含限流、缓存、超时控制

# ---- 限流区定义：放在 server 外（http 上下文），按客户端 IP 限流 ----
# 每秒 10 个请求的令牌桶
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

# ---- 缓存区定义：proxy_cache 的存储路径 ----
# levels=两级目录，keys_zone=共享内存名:大小，max_size=磁盘上限，inactive=多久不访问清理
proxy_cache_path /var/cache/nginx/api
    levels=1:2
    keys_zone=api_cache:50m
    max_size=1g
    inactive=30m
    use_temp_path=off;

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/ssl/api.example.com/fullchain.crt;
    ssl_certificate_key /etc/nginx/ssl/api.example.com/private.key;
    include /etc/nginx/snippets/ssl_params.conf;
    include /etc/nginx/snippets/security_headers.conf;

    access_log /var/log/nginx/api.example.com.access.log json_combined;

    # ---- /api/users/：用户接口，限流 + 缓存 ----
    location /api/users/ {
        # 引入统一 proxy 头
        include /etc/nginx/snippets/proxy_params.conf;

        # 转发到用户服务 upstream（剥掉 /api 前缀，注意尾斜杠语义）
        proxy_pass http://user_service_upstream/;

        # 限流：突发桶 burst=20，nodelay 表示突发请求不延迟直接处理
        limit_req zone=api_limit burst=20 nodelay;

        # 缓存：GET 请求缓存，POST 不缓存
        proxy_cache api_cache;
        proxy_cache_methods GET HEAD;
        proxy_cache_valid 200 10m;      # 200 响应缓存 10 分钟
        proxy_cache_valid 404 1m;       # 404 缓存 1 分钟
        proxy_cache_key "$scheme$request_method$host$request_uri";
        # 命中缓存时加响应头便于观测
        add_header X-Cache-Status $upstream_cache_status;

        # 超时控制：连接 5s，读 30s，发 30s
        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;
        proxy_send_timeout    30s;

        # 写接口（POST/PUT/DELETE）禁止重试到下一台，避免重复提交
        proxy_next_upstream off;
    }

    # ---- /api/orders/：订单接口，仅限流不缓存 ----
    location /api/orders/ {
        include /etc/nginx/snippets/proxy_params.conf;
        proxy_pass http://order_service_upstream/;
        limit_req zone=api_limit burst=20 nodelay;

        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;   # 订单可能慢，读超时调大
        proxy_send_timeout    30s;

        # 订单写接口禁止重试
        proxy_next_upstream off;
    }

    # ---- /ws/：WebSocket，独立片段 ----
    location /ws/ {
        proxy_pass http://user_service_upstream;
        include /etc/nginx/snippets/proxy_params.conf;
        include /etc/nginx/snippets/websocket_params.conf;
    }
}
```

逐段说明：

- **`limit_req_zone`**——定义令牌桶：`$binary_remote_addr` 用二进制 IP 作 key（比字符串 IP 省内存），`zone=api_limit:10m` 分配 10m 共享内存（约 16 万个 IP），`rate=10r/s` 平均每秒 10 个请求。
- **`proxy_cache_path`**——定义缓存存储：`levels=1:2` 两级子目录加速查找，`keys_zone=api_cache:50m` 50m 内存存 key，`max_size=1g` 磁盘上限，`inactive=30m` 30 分钟未访问清理，`use_temp_path=off` 直接写最终路径省一次拷贝。
- **`limit_req ... burst=20 nodelay`**——`burst=20` 允许瞬间 20 个突发请求排队，`nodelay` 让突发请求立即处理而非匀速放行。
- **`proxy_cache`**——开启缓存；`proxy_cache_valid 200 10m` 仅缓存 200 响应 10 分钟。
- **`proxy_next_upstream off`**——写接口禁止重试，避免 POST 在后端超时后被重发到另一台造成重复提交。
- **WebSocket `location /ws/`**——同时 include proxy_params 和 websocket_params，注意 websocket_params 里的 `Connection "upgrade"` 会覆盖 proxy_params 里的 `Connection ""`，这是预期行为。

> **参考踩坑**：[#5.7 proxy_next_upstream 导致非幂等请求被重试](99-踩坑记录与解决方案.md#57-proxy_next_upstream-导致非幂等请求被重试)——写接口必须 `proxy_next_upstream off`。

> **特例**：`limit_req_zone` 和 `proxy_cache_path` 必须在 `http` 上下文定义（不能在 server/location 里），所以本模板把它们写在 server 块之前。如果你的 conf.d 文件被 `include` 进 http 块，这是合法的。

### 2.6 知识点六：upstream 配置模板

upstream 是 Nginx 负载均衡的核心。本知识点给出三种生产模板：标准 keepalive 池、灰度权重池、读写分离池。它们都放在 `upstream/` 目录，由 `nginx.conf` 统一 `include`。

#### 模板一：标准 upstream（keepalive + 健康检查）

```nginx
# /etc/nginx/upstream/user_service.conf
# 作用：用户服务的标准负载均衡池，含 keepalive 复用 + 被动健康检查

upstream user_service_upstream {
    # 负载均衡方法：默认 round-robin（轮询），这里显式注释说明
    # 可选：least_conn（最少连接）/ ip_hash（会话保持）/ hash $key（一致性哈希）

    # 后端实例 1：3 次失败后下线 30s，30s 后重试
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    # 后端实例 2
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
    # 后端实例 3
    server 10.0.0.3:8080 max_fails=3 fail_timeout=30s;

    # keepalive：每个 worker 缓存的空闲长连接数（不是总连接数）
    # 1.29.7+ 默认已开启，显式声明便于旧版兼容与可读性
    keepalive 32;

    # 单连接最大请求数：达到后关闭重建，防止连接老化
    keepalive_requests 1000;

    # 单连接最大存活时间：1 小时后强制关闭
    keepalive_time 1h;

    # 空闲连接超时：60s 没有请求则关闭
    keepalive_timeout 60s;
}
```

逐行说明：

- `server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;`——`max_fails=3` 在 30s 内失败 3 次才标记下线（默认 `max_fails=1` 太敏感，一次抖动就下线）；`fail_timeout=30s` 下线 30s 后重新试探。
- `keepalive 32;`——每个 worker 最多缓存 32 条空闲长连接。注意这是"空闲缓存"上限，不是"总连接"上限。设过大（如 1000）会压垮后端连接池。
- `keepalive_requests/time/timeout`——控制连接生命周期，避免老连接累积导致后端资源泄漏。

> **参考踩坑**：[#2.3 未启用 upstream keepalive](99-踩坑记录与解决方案.md#23-未启用-upstream-keepalive长连接复用)——不开 keepalive 后端大量 TIME_WAIT。

> **参考踩坑**：[#5.6 长连接复用导致后端连接数被压垮](99-踩坑记录与解决方案.md#56-长连接复用导致后端连接数被压垮)——keepalive 别设太大。

> **特例**：1.29.7 起 upstream keepalive 默认开启，但 `keepalive_requests`/`keepalive_time`/`keepalive_timeout` 仍需显式配置才有合理上限。单台后端时 `max_fails` 失效，需加 `backup`。

#### 模板二：灰度发布 upstream（权重金丝雀）

```nginx
# /etc/nginx/upstream/user_service_canary.conf
# 作用：通过权重实现金丝雀发布——新版本只接小比例流量

upstream user_service_upstream {
    # 旧版本（v1）：权重 9，承担约 90% 流量
    server 10.0.0.1:8080 weight=9 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=9 max_fails=3 fail_timeout=30s;

    # 新版本（v2）：权重 1，承担约 10% 流量（金丝雀）
    server 10.0.0.3:8080 weight=1 max_fails=3 fail_timeout=30s;

    keepalive 32;
}
```

逐行说明：

- `weight=9` / `weight=1`——权重决定流量分配比例。v1 两台各 weight=9 共 18，v2 一台 weight=1，所以 v2 承担 `1/(18+1)≈5%` 流量。
- 金丝雀发布流程：先给 v2 小权重（如 1），观察监控无异常后逐步调大（1→3→9），最后把 v1 权重调到 0 完成全量切换。

> **特例**：权重分流是**粗粒度**的——它按请求数比例分配，无法保证"特定用户始终走 v2"。需要按用户/cookie 精确分流时，用知识点十的 map + 变量方案。

#### 模板三：读写分离 upstream

```nginx
# /etc/nginx/upstream/db_service.conf
# 作用：读写分离——读请求走只读副本，写请求走主库

# 读池：多个只读副本，轮询
upstream db_read_upstream {
    server 10.0.0.11:3306 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:3306 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:3306 max_fails=3 fail_timeout=30s;
    keepalive 16;
}

# 写池：只有主库，配 backup 防止 max_fails 失效
upstream db_write_upstream {
    server 10.0.0.10:3306 max_fails=3 fail_timeout=30s;
    server 10.0.0.11:3306 backup;   # 主库全挂时的兜底（慎用，可能写到只读副本）
    keepalive 16;
}
```

逐行说明：

- 拆成 `db_read_upstream` 和 `db_write_upstream` 两个池，分别承载读、写。
- 写池配 `backup`——因为只有一台主库时 `max_fails` 失效（参见 #5.2），加 backup 让主库挂时至少有兜底。但注意：如果 backup 是只读副本，写请求会失败，需谨慎。

在站点里按方法分流：

```nginx
# 站点配置里按 HTTP 方法路由到不同 upstream
location /db/ {
    include /etc/nginx/snippets/proxy_params.conf;

    # GET/HEAD/POST-查询 走读池；POST/PUT/DELETE-写 走写池
    # 这里用 $request_method 做简单分流（更复杂的用 map）
    proxy_pass http://db_read_upstream;

    # 注意：proxy_pass 不能在 if 里直接切换 upstream（if is evil）
    # 复杂场景用 map 把 method 映射成变量再 proxy_pass $变量
}
```

> **参考踩坑**：[#5.2 单台后端时 max_fails/fail_timeout 失效](99-踩坑记录与解决方案.md#52-单台后端时-max_failsfail_timeout-失效)——单台后端必须加 backup。

> **特例**：`proxy_pass $变量` 时不能带 URI 部分（带路径会报错），所以读写分离若用 map 变量切换，location 必须用 `proxy_pass http://$upstream;` 而非 `proxy_pass http://$upstream/;`。

### 2.7 知识点七：日志配置规范

#### 为什么日志要规范

生产环境的日志有两个用途：一是排障（出问题时回溯请求链路），二是监控分析（QPS、延迟、错误率）。默认的 Nginx 日志是空格分隔的文本，难以被 ELK/Loki 直接解析。规范的做法是用 **JSON 格式 + 分级存储 + 轮转**，让日志成为可计算的数据。

#### 生产 log_format（JSON 格式）

```nginx
# /etc/nginx/nginx.conf 的 http 块
# 作用：定义 JSON 格式访问日志，便于日志系统直接消费

log_format json_main escape=json
    '{'
        # 时间：ISO8601 带时区，比默认的 local time 更标准
        '"time":"$time_iso8601",'

        # 客户端信息
        '"remote_addr":"$remote_addr",'              # 直连 Nginx 的 IP
        '"x_forwarded_for":"$http_x_forwarded_for",' # XFF 转发链（追溯真实客户端）

        # 请求信息
        '"request_method":"$request_method",'        # GET/POST/...
        '"request_uri":"$request_uri",'              # 原始 URI（含参数，不被 rewrite 改写）
        '"server_name":"$server_name",'              # 命中的 server_name
        '"host":"$host",'                            # 请求 Host 头
        '"scheme":"$scheme",'                        # http/https

        # 响应信息
        '"status":$status,'                          # 响状态码（数字，不加引号便于聚合）
        '"body_bytes_sent":$body_bytes_sent,'        # 响应体字节数
        '"request_time":$request_time,'              # 总请求耗时（秒，含后端）

        # 上游信息
        '"upstream_addr":"$upstream_addr",'          # 后端地址（多台时逗号分隔）
        '"upstream_response_time":"$upstream_response_time",'  # 后端响应耗时
        '"upstream_status":"$upstream_status",'      # 后端返回的状态码

        # 客户端元数据
        '"http_referer":"$http_referer",'            # 来源页
        '"http_user_agent":"$http_user_agent",'      # UA
        '"request_id":"$request_id"'                 # 请求唯一 ID（内置，便于链路追踪）
    '}';
```

逐行说明：

- `escape=json`——关键参数。它自动把变量值里的 `"`、`\`、控制字符转义，确保输出永远是合法 JSON。不加这个，一旦 UA 里带引号就会破坏 JSON 解析。
- 数字字段（`status`、`body_bytes_sent`、`request_time`）**不加引号**，让日志系统识别为数值类型而非字符串，便于做聚合统计（如平均延迟）。
- `$request_id`——Nginx 1.11.0+ 内置变量，每个请求自动生成唯一 ID。后端可把这个 ID 带回日志，实现 Nginx ↔ 后端的链路串联。

使用方式：

```nginx
# 全局日志
access_log /var/log/nginx/access.log json_main;

# 分站点日志（每站点独立文件，便于按域名排查）
server {
    server_name api.example.com;
    access_log /var/log/nginx/api.example.com.access.log json_main;
}
```

> **特例**：`$upstream_response_time` 在请求未走到后端时为空（如命中缓存、return 直接返回），JSON 里会变成 `"upstream_response_time":""`，日志系统需容忍空值。

#### 日志轮转配置（logrotate）

Nginx 本身不做日志轮转，靠系统的 `logrotate`。配置文件通常放 `/etc/logrotate.d/nginx`：

```text
# /etc/logrotate.d/nginx
# 作用：按天轮转 Nginx 日志，保留 30 天，压缩归档

/var/log/nginx/*.log {
    # 每天轮转一次
    daily

    # 缺失文件不报错
    missingok

    # 保留 30 个归档（约 30 天）
    rotate 30

    # 空文件不轮转
    notifempty

    # 轮转后用 gzip 压缩
    compress

    # 延迟压缩：下一个轮转周期才压缩上一个（避免刚切割就被压，影响写入）
    delaycompress

    # 即使多个匹配项也只跑一次 sharedscripts
    sharedscripts

    # 轮转后执行：给 master 发 USR1 信号，让它重新打开日志文件
    postrotate
        if [ -f /run/nginx.pid ]; then
            kill -USR1 `cat /run/nginx.pid`
        fi
    endscript
}
```

逐行说明：

- `daily` + `rotate 30`——每天切一个，留 30 天。
- `compress` + `delaycompress`——压缩归档省磁盘，延迟压缩避免切割瞬间写入冲突。
- `postrotate ... kill -USR1`——关键步骤。日志被 mv 走后，Nginx 的文件描述符还指向旧 inode，继续往旧文件写。`USR1` 信号让 Nginx 重新打开日志文件（指向新文件）。

> **原理**：`kill -USR1` 让 master 重新打开所有 `access_log`/`error_log` 指定的文件，worker 继承新的文件描述符。这是 Nginx 日志轮转的标准做法，无需重启。

#### 日志分级存储

```nginx
# 错误日志分级：error_log 可写多个级别 debug/info/notice/warn/error/crit/alert/emerg
# 生产用 warn（够排障又不太吵），排障时临时调 info/debug

error_log /var/log/nginx/error.log warn;       # 生产常态
# error_log /var/log/nginx/error.log info;     # 排障临时开启
# error_log /var/log/nginx/error.log debug;    # 深度排障（需编译带 --with-debug）

# 访问日志分级：用 map 把状态码映射成 0/1 标志位
# 4xx/5xx 标记为 1（错误），其余标记为 0（正常）
map $status $is_error_request {
    default   0;     # 2xx/3xx 正常
    ~^[45]    1;     # 4xx/5xx 错误
}

server {
    server_name api.example.com;

    # 正常请求日志：if= 变量非空且非 0 才记录，$is_error_request 为 0 时不记错误日志
    access_log /var/log/nginx/api.access.log json_main;
    # 错误请求日志单独存：只在 $is_error_request=1 时记录
    access_log /var/log/nginx/api.error_access.log json_main if=$is_error_request;
}
```

说明：通过 `if=` 条件控制是否记日志，可以把 4xx/5xx 单独写到 `error_access.log`，排障时只看这个文件，不被正常请求淹没。第一条 `access_log` 记全部请求，第二条用 `if=$is_error_request` 只在错误时额外记一份到独立文件，两份互补。

> **特例**：`access_log` 的 `if=` 参数里只能用变量不能写复杂表达式。需要"状态码是 4xx/5xx"这种判断时，先用 `map` 把判断结果存成变量（如 `$is_error_request`），再 `if=$is_error_request`。`if=` 的规则是变量值非空且非 `0` 才记录。

> **参考踩坑**：[#5.4 后端拿不到真实客户端 IP](99-踩坑记录与解决方案.md#54-后端拿不到真实客户端-ip)——日志里记录 `x_forwarded_for` 正是为了在多级代理下追溯真实 IP。

### 2.8 知识点八：安全加固配置清单

生产 Nginx 上线前必须过一遍安全清单。本知识点把分散在各处的安全指令汇总成一份"加固 checklist"，可直接对照执行。

#### 安全加固清单总览

| 加固项 | 指令 | 放置位置 | 作用 |
|--------|------|----------|------|
| 隐藏版本号 | `server_tokens off` | http | 不暴露 Nginx 版本 |
| 允许下划线头 | `underscores_in_headers on` | http | 按需开启 |
| SSL 协议 | `ssl_protocols TLSv1.2 TLSv1.3` | server/snippet | 禁用旧协议 |
| 安全响应头 | `add_header ... always` | server/snippet | 防 XSS/点击劫持 |
| 限制方法 | `limit_except` | location | 只放行需要的方法 |
| 限制 body | `client_max_body_size` | http/server | 防大请求体 |
| 隐藏文件 | `location ~ /\.` | server | 防 .git/.env 泄露 |
| 证书权限 | `chmod 600 *.key` | 文件系统 | 防私钥泄露 |

#### 完整安全加固配置

```nginx
# ============ http 层加固（放 nginx.conf） ============

http {
    # 1. 隐藏版本号：错误页/响应头只显示 nginx，不显示 1.30.4
    server_tokens off;

    # 2. 允许下划线请求头（按需开启：若后端/客户端用 X_My_Header 形式）
    underscores_in_headers on;

    # 3. 限制请求体大小：防止超大上传打爆内存/磁盘
    # 全局 20m，可在 server/location 按业务覆盖（如上传接口 100m）
    client_max_body_size 20m;

    # 4. 限制请求头缓冲：防止超大 header 攻击（slowloris 类）
    client_header_buffer_size 4k;
    large_client_header_buffers 4 16k;

    # 5. 限制请求头读取超时：慢速攻击防御
    client_header_timeout 30s;
    client_body_timeout 30s;
}

# ============ server 层加固（放各站点） ============

server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    # 6. SSL 安全参数（snippet 统一）
    include /etc/nginx/snippets/ssl_params.conf;

    # 7. 安全响应头（snippet 统一）
    include /etc/nginx/snippets/security_headers.conf;

    # 8. 隐藏 Nginx 默认错误页的特征（自定义错误页）
    # 不用默认 50x 页，避免暴露 nginx 字样给指纹识别
    error_page 404 /custom_404.html;
    error_page 500 502 503 504 /custom_50x.html;
    location = /custom_404.html { root /usr/share/nginx/html; internal; }
    location = /custom_50x.html { root /usr/share/nginx/html; internal; }

    # 9. 拦截隐藏文件：禁止访问点开头的文件（.git/.env/.htaccess）
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }

    # 10. 拦截备份/敏感文件
    location ~* \.(bak|swp|sql|log|sh|conf)$ {
        deny all;
        access_log off;
    }

    # ---- 业务 location：限制 HTTP 方法 ----
    location /api/ {
        include /etc/nginx/snippets/proxy_params.conf;
        proxy_pass http://user_service_upstream/;

        # 11. 只允许 GET/POST/HEAD，其余方法（DELETE/PUT/TRACE）拒绝
        # limit_except 后面跟允许的方法列表，其余返回 403
        limit_except GET POST HEAD {
            deny all;
        }
    }

    # ---- 上传接口：放开 body 限制 ----
    location /api/upload/ {
        include /etc/nginx/snippets/proxy_params.conf;
        proxy_pass http://user_service_upstream/;

        # 上传接口单独放大 body 限制
        client_max_body_size 100m;

        # 上传只允许 POST
        limit_except POST {
            deny all;
        }
    }
}
```

逐项说明：

1. **`server_tokens off`**——最基础也最重要。开着会暴露 `nginx/1.30.4`，攻击者可针对性利用该版本已知漏洞。
2. **`underscores_in_headers on`**——默认 off 会静默丢弃 `X_My_Header` 这类下划线头，按需开启。
3. **`client_max_body_size 20m`**——限制请求体大小，防止超大上传耗尽内存。上传接口单独覆盖。
4. **`client_header_timeout`/`client_body_timeout`**——慢速攻击（Slowloris）防御，客户端故意慢慢发请求占用连接，超时即断开。
5. **自定义错误页**——不用 Nginx 默认 50x 页，避免暴露 nginx 字样被指纹识别。
6. **`location ~ /\.`**——拦截 `.git`、`.env`、`.htaccess` 等隐藏文件，防止源码/配置泄露。
7. **`limit_except GET POST HEAD`**——只放行需要的方法，拒绝 `TRACE`（可被 XST 攻击）、`DELETE`/`PUT`（除非业务需要）。
8. **证书权限**——文件系统层面：`chmod 600 /etc/nginx/ssl/*/private.key`，私钥只能 root 读。

> **参考踩坑**：[#3.1 暴露 Nginx 版本号](99-踩坑记录与解决方案.md#31-暴露-nginx-版本号)——`server_tokens off` 是安全基线第一步。

> **参考踩坑**：[#1.11 含下划线的请求头被静默丢弃](99-踩坑记录与解决方案.md#111-含下划线的请求头被静默丢弃)——`underscores_in_headers on` 的必要性。

> **特例**：`limit_except` 实际是用 `deny all` 拦截未列出的方法。注意 `limit_except GET` 表示"只允许 GET"（语法反直觉），而 `limit_except GET POST` 表示"只允许 GET 和 POST"。

### 2.9 知识点九：性能优化配置清单

性能优化和安全加固一样，是上线前的必过清单。本知识点按"进程 → 事件 → 连接 → 缓冲 → 压缩"五个层次给出优化配置。

#### 性能优化清单总览

| 层次 | 指令 | 取值建议 | 作用 |
|------|------|----------|------|
| 进程 | `worker_processes` | auto | worker 数=CPU 核 |
| 进程 | `worker_rlimit_nofile` | 65535 | 文件描述符上限 |
| 事件 | `worker_connections` | 16384 | 单 worker 连接数 |
| 事件 | `multi_accept` | on | 突发并发 accept |
| 连接 | `keepalive_timeout` | 65s | 客户端长连接 |
| 连接 | `upstream keepalive` | 32 | 后端连接复用 |
| 缓冲 | `proxy_buffer_size` | 16k | 响应首部缓冲 |
| 缓冲 | `proxy_buffers` | 8 16k | 响应体缓冲 |
| 传输 | `sendfile`/`tcp_nopush` | on | 零拷贝 |
| 压缩 | `gzip` | on | 减少传输体积 |

#### 完整性能优化配置

```nginx
# ============ 进程层（main 上下文） ============

# worker 数：auto 自动匹配 CPU 核心数（最稳妥，手动设错反而争抢 CPU）
worker_processes auto;

# CPU 亲和性：auto 让 OS 自动绑核，减少跨核调度
worker_cpu_affinity auto;

# worker 能打开的最大文件描述符：配合系统 ulimit
worker_rlimit_nofile 65535;

# ============ 事件层（events 上下文） ============

events {
    # 单 worker 最大连接数
    # 反代场景每客户端占 2 条连接，按 worker数×connections/4 估算并发
    worker_connections 16384;

    # 事件模型：Linux 用 epoll（Nginx 会自动选，显式写可读性更好）
    use epoll;

    # 一次 accept 多个连接：应对突发流量
    multi_accept on;
}

# ============ http 层连接与传输优化 ============

http {
    # 零拷贝发送文件：静态资源不走用户态，性能大幅提升
    sendfile on;

    # 配合 sendfile：攒够一个完整 TCP 段再发，减少小包
    tcp_nopush on;

    # keepalive 连接上禁用 Nagle 算法，及时发送小包
    tcp_nodelay on;

    # 客户端长连接超时：65s 略大于常见 LB 的 60s 探测间隔
    keepalive_timeout 65s;

    # 单连接最大请求数：1000 是默认值，高 QPS 可调大
    keepalive_requests 1000;

    # ---- gzip 压缩（snippet 统一） ----
    include /etc/nginx/snippets/gzip_params.conf;
}

# ============ upstream 层连接复用 ============

upstream user_service_upstream {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;

    # 后端长连接复用：避免每请求新建 TCP，减少 TIME_WAIT
    keepalive 32;
    keepalive_requests 1000;
    keepalive_time 1h;
    keepalive_timeout 60s;
}

# ============ location 层缓冲优化 ============

server {
    location /api/ {
        include /etc/nginx/snippets/proxy_params.conf;
        proxy_pass http://user_service_upstream/;

        # 响应首部缓冲：默认 4k/8k 太小，大 header 会落临时文件
        proxy_buffer_size 16k;

        # 响应体缓冲：8 块 × 16k = 128k，小于此走内存
        proxy_buffers 8 16k;

        # 忙时缓冲：忙时合并写入的缓冲大小
        proxy_busy_buffers_size 32k;

        # 连接后端超时
        proxy_connect_timeout 5s;
        # 读后端响应超时
        proxy_read_timeout 30s;
        # 向后端发送超时
        proxy_send_timeout 30s;
    }
}
```

逐层说明：

- **进程层**——`worker_processes auto` 是最稳妥的选择，Nginx 自动按 CPU 核心数起 worker。`worker_rlimit_nofile 65535` 提升 worker 的文件描述符上限，配合系统 `ulimit -n` 才能扛高并发。
- **事件层**——`worker_connections 16384` 是单 worker 最大连接数，反代场景按 `worker数 × connections / 4` 估算并发能力。`multi_accept on` 让 worker 一次从全连接队列 accept 多个连接，应对突发。
- **连接层**——`sendfile on` + `tcp_nopush on` + `tcp_nodelay on` 是静态资源性能三件套：零拷贝 + 攒包 + 及时发。`keepalive_timeout 65s` 略大于 LB 探测间隔，避免被 LB 误断长连接。
- **upstream 连接复用**——`keepalive 32` 让 Nginx 到后端复用长连接，避免每请求新建 TCP（减少握手开销和 TIME_WAIT）。
- **缓冲层**——`proxy_buffer_size 16k` + `proxy_buffers 8 16k` 把响应缓冲调大，避免大响应落临时文件（磁盘 IO 飙升）。

> **参考踩坑**：[#2.1 worker_processes 设置不当](99-踩坑记录与解决方案.md#21-worker_processes-设置不当)——`auto` 是最稳妥的，手动设错是常见性能问题。

> **参考踩坑**：[#2.2 worker_connections 与最大连接数计算错误](99-踩坑记录与解决方案.md#22-worker_connections-与最大连接数计算错误)——反代时连接数要除以 4 估算。

> **参考踩坑**：[#2.5 proxy buffer 过小导致落盘或响应被截断](99-踩坑记录与解决方案.md#25-proxy-buffer-过小导致落盘或响应被截断)——buffer 要按后端响应大小调。

> **特例**：
> - `sendfile on` 在 VirtualBox 虚拟机内可能有问题，需 `sendfile off`。
> - SSE/流式响应必须 `proxy_buffering off`，否则响应会被缓冲导致实时性丢失。
> - gzip 对已压缩的二进制（图片/视频）无效且浪费 CPU，`gzip_types` 只列文本类。

### 2.10 知识点十：灰度发布配置

灰度发布（又称金丝雀发布）是生产变更的关键能力：新版本先接一小部分流量，验证无异常后再逐步扩大，出问题随时回滚。Nginx 原生支持三种灰度方式，按粒度从粗到细分别是：upstream weight、map 变量路由、header/cookie 精确分流。

#### 三种灰度方式对比

| 方式 | 粒度 | 实现复杂度 | 适用场景 | 局限 |
|------|------|-----------|----------|------|
| upstream weight | 按请求数比例 | 低 | 新版本整体灰度 | 无法保证特定用户始终走新版本 |
| map + 变量路由 | 按请求特征 | 中 | 按 URI/方法分流 | 仍按特征而非用户个体 |
| header/cookie | 按用户个体 | 高 | 内测用户、A/B 测试 | 需客户端配合带标识 |

#### 方式一：基于 upstream weight 的金丝雀

```nginx
# /etc/nginx/upstream/user_service.conf
# 作用：通过权重让新版本只接小比例流量

upstream user_service_upstream {
    # 旧版本 v1：两台，各 weight=9
    server 10.0.0.1:8080 weight=9 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=9 max_fails=3 fail_timeout=30s;

    # 新版本 v2：一台，weight=1，承担约 5% 流量
    server 10.0.0.3:8080 weight=1 max_fails=3 fail_timeout=30s;

    keepalive 32;
}
```

逐行说明：

- `weight=9` / `weight=1`——按权重分配。总权重 `9+9+1=19`，v2 承担 `1/19≈5%`。
- 发布节奏：v2 weight 从 1 → 3 → 9 逐步调大，每次 reload 后观察监控（错误率、延迟），无异常再继续，有异常立即把 v2 weight 调回 0 回滚。

> **特例**：权重分流是"概率性"的——某个用户第一次请求可能走 v2，第二次走 v1，体验不一致。对有状态服务（需会话保持）不适用，需用 ip_hash 或 cookie 方式。

#### 方式二：基于 map + 变量的路由分流

```nginx
# /etc/nginx/maps/canary.conf
# 作用：按请求 URI 前缀把部分路径整体切到新版本

# 把 /api/v2/ 开头的请求标记为走新版本
map $request_uri $upstream_target {
    default                "user_service_v1_upstream";   # 默认走 v1
    ~^/api/v2/             "user_service_v2_upstream";   # /api/v2/ 走 v2
}

# 两个 upstream 池
upstream user_service_v1_upstream {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
    keepalive 32;
}
upstream user_service_v2_upstream {
    server 10.0.0.3:8080 max_fails=3 fail_timeout=30s;
    keepalive 32;
}
```

```nginx
# 站点配置里用变量做 proxy_pass
location /api/ {
    include /etc/nginx/snippets/proxy_params.conf;

    # 用 map 出来的变量做上游地址
    # 注意：proxy_pass 用变量时不能带 URI 部分（不能写 $upstream_target/）
    proxy_pass http://$upstream_target;

    # 因为不能带 URI，/api/ 前缀不会被剥掉，后端会收到 /api/xxx
    # 若需剥前缀，用 rewrite + break 配合
    rewrite ^/api/(.*)$ /$1 break;
}
```

逐行说明：

- `map $request_uri $upstream_target`——把请求 URI 映射成 upstream 名。`~^/api/v2/` 是正则匹配，命中则走 v2 池。
- `proxy_pass http://$upstream_target;`——用变量动态选择上游。这是 Nginx 的"动态上游"能力，无需 reload 即可切换（配合外部更新 map 的来源）。
- `rewrite ^/api/(.*)$ /$1 break;`——因为 `proxy_pass $变量` 不能带 URI（带路径会报错），前缀剥不掉，需用 rewrite 手动剥。

> **特例**：`proxy_pass` 用变量时，Nginx 会在运行时解析变量值作为上游名，此时**不能**在 proxy_pass 后带 URI 部分（`http://$upstream/` 会报错）。这是与固定 upstream 最大的区别。

#### 方式三：基于 header/cookie 的灰度

```nginx
# /etc/nginx/maps/canary.conf
# 作用：按请求头/cookie 把特定用户（内测用户）路由到新版本

# 方式 A：按请求头 X-Canary: true 路由
map $http_x_canary $upstream_target {
    default                "user_service_v1_upstream";
    "true"                 "user_service_v2_upstream";
}

# 方式 B：按 cookie canary=on 路由（更常用，因为客户端可自动带 cookie）
map $cookie_canary $upstream_target {
    default                "user_service_v1_upstream";
    "on"                   "user_service_v2_upstream";
}

# 方式 C：按用户 ID 取模灰度（如用户 ID 尾号 0-9 的走 v2，即 10% 用户）
# 假设请求头 X-User-Id 带用户 ID
map $http_x_user_id $upstream_target {
    default                "user_service_v1_upstream";
    ~[0-9]$                "user_service_v2_upstream";   # 尾号 0-9 走 v2（可调成 ~[0-4]$ 表示 50%）
}
```

```nginx
# 站点配置
location /api/ {
    include /etc/nginx/snippets/proxy_params.conf;
    proxy_pass http://$upstream_target;
    rewrite ^/api/(.*)$ /$1 break;
}
```

逐行说明：

- `map $http_x_canary`——`$http_x_canary` 是请求头 `X-Canary` 的值。客户端带 `X-Canary: true` 则走 v2。
- `map $cookie_canary`——`$cookie_canary` 是 cookie `canary` 的值。比 header 更常用，因为浏览器会自动带 cookie，无需客户端改代码。
- `map $http_x_user_id ~[0-9]$`——按用户 ID 尾号分流，可精确控制灰度比例（`~[0-4]$` = 50%，`~[0]$` = 10%）。

> **特例**：cookie/header 灰度需要客户端配合——要么前端代码里给内测用户种 cookie，要么网关层根据用户登录态注入 header。纯 Nginx 无法"自动识别谁是内测用户"。

#### 三种方式的发布流程

```text
1. 准备阶段：v2 后端部署完成，upstream 池已定义但 weight=0（不接流量）
2. 灰度阶段：
   - 方式一：v2 weight 从 1 开始，观察 10 分钟监控
   - 方式二：先灰度 /api/v2/ 路径，让部分接口先走 v2
   - 方式三：先灰度内测用户（cookie/header 标记），验证体验
3. 扩量阶段：无异常则逐步扩大（weight 调大 / 路径增多 / 用户比例提高）
4. 全量阶段：v2 承担 100% 流量，v1 weight 调 0 下线
5. 回滚（出问题时）：v2 weight 调 0，reload，流量全部回到 v1
```

> **关键认知**：灰度的核心不是"怎么配"，而是"敢不敢回滚"。每次扩大流量前必须有明确的监控指标（错误率、延迟、业务成功率）和预设的回滚阈值。

### 2.11 知识点十一：配置变更管理流程

生产环境改 Nginx 配置是高风险操作——一个语法错误或逻辑错误可能导致全站 502。本知识点把"改配置"变成一套可回滚的工程流程。

#### 标准变更流程

```text
┌─────────┐    ┌──────────┐    ┌─────────┐    ┌──────────┐    ┌──────────┐
│ 1. 修改  │ -> │ 2. 测试  │ -> │ 3. 备份 │ -> │ 4. reload│ -> │ 5. 验证  │
│  配置文件│    │ nginx -t │    │  旧配置 │    │  平滑加载│    │  业务正常│
└─────────┘    └──────────┘    └─────────┘    └──────────┘    └──────────┘
                                                                      │
                                                                      │ 异常
                                                                      ▼
                                                              ┌──────────────┐
                                                              │ 6. 回滚      │
                                                              │  恢复备份配置│
                                                              └──────────────┘
```

#### 步骤详解

**步骤一：修改配置**

在 git 仓库里修改配置文件，遵循目录规范（站点改 conf.d，片段改 snippets）。改完先本地 review。

```bash
# 在配置仓库里修改
cd /etc/nginx
vim conf.d/api.example.com.conf
```

**步骤二：测试配置（nginx -t）**

`nginx -t` 是变更流程的"安全网"——它检查配置语法和引用的文件是否存在，但**不实际加载**。这是 reload 前必做的一步。

```bash
# 测试配置：检查语法 + 引用的文件是否存在，不实际 reload
nginx -t
# 输出：
# nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# nginx: configuration file /etc/nginx/nginx.conf test is successful

# 测试并显示完整配置（排障用，会打印所有 include 展开后的内容）
nginx -T | grep -A 20 "server_name api"
```

逐行说明：

- `nginx -t`——`-t` 表示 test。它会加载配置文件解析，但不启动 worker、不影响运行中的服务。语法错误或引用了不存在的文件会在这里报错。
- `nginx -T`——`-T` 是 test + dump，把所有 include 展开后的完整配置打印出来，排障时非常有用（确认 include 是否正确加载）。

> **关键**：`nginx -t` 只能抓"语法错误"和"文件引用错误"，**抓不到逻辑错误**（如 location 匹配错了、proxy_pass 指向错误的上游）。逻辑错误要靠步骤五的验证。

**步骤三：备份旧配置**

reload 前备份当前生效的配置，出问题时能秒级回滚。

```bash
# 备份当前配置（带时间戳）
cp -r /etc/nginx /etc/nginx.bak.$(date +%Y%m%d_%H%M%S)

# 或用 git（配置仓库化，见下文）
cd /etc/nginx
git stash    # 暂存当前未提交的改动，便于回滚
```

**步骤四：reload 平滑加载**

`nginx -s reload` 让 master 重新加载配置，新 worker 处理新请求，旧 worker 处理完存量请求后退出，全程不中断服务。

```bash
# 平滑 reload：master 重新读配置，起一批新 worker，老 worker 优雅退出
nginx -s reload

# 或用 kill 信号（等价）
kill -HUP $(cat /run/nginx.pid)
```

逐行说明：

- `nginx -s reload`——发送 HUP 信号给 master。master 重新加载配置，启动新的 worker 进程处理新请求，同时通知老 worker 不再接受新连接、处理完存量请求后退出。整个过程对客户端透明。
- `kill -HUP`——等价于 `nginx -s reload`，直接发 HUP 信号。

> **特例**：reload 不是万能的——某些配置变更需要**完全重启**才生效，如：`worker_processes` 改变、加载新动态模块（`load_module`）、改变 `user`。这些场景 reload 会告警但不生效，需 `nginx -s stop && nginx`。

**步骤五：验证业务**

reload 后立即验证业务是否正常，不能只看 Nginx 没报错就认为成功。

```bash
# 1. 检查 Nginx 进程是否正常
ps aux | grep nginx
# 应看到 master + 多个 worker

# 2. 检查 error.log 是否有新报错
tail -f /var/log/nginx/error.log

# 3. 实际请求验证业务
curl -I https://api.example.com/health
curl -I https://api.example.com/api/users/

# 4. 检查响应头是否正确（如安全头、缓存状态）
curl -sI https://example.com | grep -i "x-\|strict-transport"
```

逐行说明：

- `ps aux | grep nginx`——确认 master 和 worker 进程都在，且 worker 数量符合 `worker_processes`。
- `tail -f error.log`——观察是否有新的 error 日志（如 upstream 连接失败、配置告警）。
- `curl -I`——实际发请求验证，`-I` 只取响应头，检查状态码和头是否符合预期。

**步骤六：回滚（出问题时）**

验证发现异常，立即回滚到备份配置。

```bash
# 方式一：git 回滚（配置仓库化时）
cd /etc/nginx
git checkout -- .          # 丢弃所有未提交改动，恢复到上次 commit
nginx -t && nginx -s reload

# 方式二：恢复备份目录
rm -rf /etc/nginx/conf.d/*
cp /etc/nginx.bak.20260805_140000/conf.d/* /etc/nginx/conf.d/
nginx -t && nginx -s reload
```

> **回滚原则**：回滚要快、要简单。reload 是秒级的，所以"备份 + git + reload"能在 1 分钟内完成回滚。不要在出问题时还去 debug 新配置——先回滚恢复服务，再慢慢查问题。

#### 配置版本管理（git）

生产配置必须纳入 git 管理，让每次变更有记录、可追溯、可回滚。

```bash
# 初始化配置仓库
cd /etc/nginx
git init
git add .
git commit -m "init: 生产 Nginx 配置基线"

# 日常变更流程
git checkout -b feature/add-order-api    # 新建分支
vim conf.d/api.example.com.conf          # 修改
nginx -t                                  # 测试
git add conf.d/api.example.com.conf
git commit -m "feat: 新增 /api/orders/ 反代配置"
git checkout master && git merge feature/add-order-api   # 合并
nginx -s reload                           # 部署
```

说明：

- 配置文件用 git 管理，每次变更一个 commit，message 说明改了什么、为什么改。
- 重要变更走分支 + review，避免直接改 master。
- 配置仓库可与部署流程集成（CI/CD 推送配置到服务器并 reload）。

#### 灰度发布流程

对于高风险变更（如切换上游、改路由），不要一次性全量 reload，而是分批灰度。

```text
1. 多机部署：Nginx 有多台（如 4 台 LB），逐台变更
2. 第一台变更：改配置 → nginx -t → reload → 验证
3. 观察 10-30 分钟：监控错误率、延迟、业务指标
4. 无异常继续第二台，有异常立即回滚第一台
5. 直到全部机器完成
```

> **特例**：单台 Nginx 无法分机灰度，此时用知识点十的 upstream weight / map 变量灰度，在配置层面控制流量比例，而非分机器。

#### 完整变更检查清单

| 检查项 | 命令/动作 | 通过标准 |
|--------|----------|----------|
| 语法测试 | `nginx -t` | `test is successful` |
| 配置展开 | `nginx -T` | include 正确、无遗漏 |
| 备份 | `git stash` 或 `cp -r` | 备份存在 |
| 进程检查 | `ps aux \| grep nginx` | master + worker 正常 |
| 错误日志 | `tail error.log` | 无新 error |
| 业务验证 | `curl -I` 关键接口 | 状态码符合预期 |
| 监控观察 | 观察 10-30 分钟 | 错误率/延迟正常 |

## 3. 最佳实践

### 3.1 目录与组织

- **主配置只管全局**：`nginx.conf` 只写全局参数和 http 框架，绝不写具体 server。所有业务变更都在 `conf.d/` 完成，主配置几乎不需要改动。
- **通用片段抽 snippets**：SSL 参数、proxy 头、gzip、安全头这些多处复用的配置，抽成 snippet 用 `include` 引入，改一处全局生效，杜绝"改了 A 站忘改 B 站"。
- **按域名/服务拆文件**：一个站点一个 `.conf`，git 改动一目了然，合并冲突概率最低。
- **证书集中管理 + 权限收紧**：`/etc/nginx/ssl/` 按域名分子目录，私钥 `chmod 600`，防止泄露。

### 3.2 命名

- **统一比正确更重要**：location 尾斜杠、变量命名风格，团队内统一一种即可，不要混用。
- **自文档化命名**：站点文件用域名、upstream 用 `服务名_upstream`、变量用 `snake_case`，看名字就能猜出用途。
- **upstream 名只用字母数字下划线**：不能用连字符，否则 proxy_pass 解析歧义。

### 3.3 安全

- **`server_tokens off` 是底线**：上线第一件事就是关版本号。
- **安全响应头用 snippet 统一下发**：HSTS、X-Frame-Options、CSP 等用 `include security_headers.conf`，且加 `always` 后缀确保错误页也下发。
- **限制 HTTP 方法与 body 大小**：业务不需要的方法（TRACE/PUT/DELETE）一律拒，body 大小按业务设上限。
- **拦截隐藏文件与备份文件**：`.git`/`.env`/`.bak` 等一律 `deny all`。

### 3.4 性能

- **`worker_processes auto` 最稳妥**：别手动设错 worker 数。
- **三件套必开**：`sendfile on` + `tcp_nopush on` + `tcp_nodelay on`。
- **upstream keepalive 必开**：但别设太大（16-64 即可），避免压垮后端连接池。
- **buffer 按响应大小调**：默认 4k/8k 太小，大响应会落临时文件，建议 `proxy_buffers 8 16k`。
- **gzip 只压文本**：`gzip_types` 只列文本类，图片/视频已压缩再 gzip 浪费 CPU。

### 3.5 变更管理

- **reload 前必 `nginx -t`**：这是变更流程的安全网，但记住它抓不到逻辑错误。
- **配置纳入 git**：每次变更一个 commit，可追溯可回滚。
- **高风险变更分批灰度**：多机逐台变更，或用 upstream weight 在配置层灰度。
- **回滚要快**：出问题先回滚恢复服务，再慢慢查问题，别在生产环境 debug。

### 3.6 可观测性

- **日志用 JSON 格式**：`escape=json` 确保合法 JSON，便于 ELK/Loki 直接消费。
- **记录 request_id**：用内置 `$request_id` 串联 Nginx 与后端日志。
- **分站点日志**：每站点独立 `access_log`，按域名排查更高效。
- **日志轮转**：logrotate + `kill -USR1`，按天切、留 30 天、压缩归档。

## 5. 小结

本篇是 Nginx 系列的"工程化收口"，把前面 27 篇散落的指令、模板、最佳实践，收敛成一套可直接抄到生产环境的规范与模板库。核心要点回顾：

1. **目录规范是地基**：`nginx.conf` 只管全局，`conf.d/` 按站点拆，`snippets/` 放通用片段，`ssl/` 集中放证书。分层 + include 让配置可维护、可复用、可追溯。
2. **命名规范让配置自文档化**：站点用域名、upstream 用 `服务名_upstream`、location 尾斜杠统一、变量用 snake_case。"统一"比"对错"更重要。
3. **snippets 是复用的关键**：proxy_params / ssl_params / gzip_params / security_headers 四个片段覆盖了 80% 的通用配置，用 include 引入而非复制粘贴。
4. **三套模板覆盖主流场景**：HTTP 重定向、HTTPS 全套、API 反代（带限流缓存），按业务选对应模板落地到 conf.d。
5. **upstream 三种形态**：标准 keepalive 池、灰度权重池、读写分离池，理解 keepalive 缓存与被动健康检查的配合。
6. **日志要 JSON 化**：`escape=json` + `$request_id` + 分站点 + logrotate 轮转，让日志成为可计算的数据。
7. **安全与性能是上线必过清单**：server_tokens off / 安全头 / 方法限制 / body 限制 是安全基线；worker auto / 三件套 / keepalive / buffer 调大 / gzip 是性能基线。
8. **灰度三招**：upstream weight（粗粒度）、map 变量路由（中粒度）、header/cookie（用户级）。核心不是怎么配，而是"敢不敢回滚"。
9. **变更流程六步**：修改 → `nginx -t` → 备份 → reload → 验证 → 回滚。配置纳入 git，高风险变更分批灰度，回滚要快。

一句话总结：**生产 Nginx 配置的本质是"用工程化手段把易错的配置变成可复用、可测试、可回滚的代码"**——目录分层是组织，命名规范是沟通，snippets 是复用，模板是标准化，变更流程是风险控制。把这套规范落地，Nginx 配置就不再是"上线改一次提心吊胆一次"的黑盒，而是可演进的基础设施代码。
