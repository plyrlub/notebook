    说明¶

    本文档是 Nginx 日常运维的命令速查表。所有命令按功能场景分类，每条命令配有用途说明和可直接复制的示例。

    阅读约定：

    • nginx 命令本身需要 root 权限或通过 sudo 执行（因为要绑定 80/443 端口、读取配置文件）。
    • 路径以常见的 Linux 发行版默认安装路径为准（/etc/nginx/、/var/log/nginx/、/var/run/nginx.pid）。如果你的发行版不同，请自行替换。
    • 示例中的 host、example.com 等为占位符，使用时替换为实际值。
    • 标注 # root 的命令需要 root 权限；标注 $ user 的命令普通用户即可执行。

    前置知识：建议先完成 03-进程模型与控制管理，理解 master/worker 进程模型后再使用本文档，你会更清楚每个信号到底在做什么。

    一、Nginx 命令行¶

    Nginx 二进制本身就是一个功能完整的命令行工具。下面是最常用的 nginx 命令行参数。

    1.1 nginx -t — 测试配置文件语法¶

    # root 权限执行
sudo nginx -t

# 指定配置文件路径（非默认 /etc/nginx/nginx.conf）
sudo nginx -t -c /etc/nginx/nginx.conf

    用途：检查配置文件语法是否正确，但不实际 reload。修改配置后必须先执行此命令，确认输出 syntax is ok 和 test is successful 后再 reload。

    典型输出：

    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

    踩坑提醒：nginx -t 只检查语法，不检查语义逻辑。比如 proxy_pass 指向一个不存在的 upstream，语法上是合法的，-t 不会报错，但实际请求会 502。

    1.2 nginx -T — 打印完整生效配置¶

    # root 权限，打印所有已生效的配置（包括 include 进来的文件）
sudo nginx -T

# 打印并搜索特定关键字
sudo nginx -T | grep server_name
sudo nginx -T | grep -A 5 "upstream"

    用途：把 Nginx 当前实际加载的所有配置（包括 include 指令引入的子配置文件）合并打印出来。非常适合排查"我改了配置但不确定最终生效的是哪个文件"的问题。

    踩坑提醒：-T 输出的是解析后展开的完整配置，不是原始文件内容。如果你在多个文件里重复定义了同一个指令，-T 只显示最终生效的那一份。

    1.3 nginx -V — 查看编译参数和模块¶

    # 查看版本和编译参数（注意大写 V）
sudo nginx -V

# 只看版本号（小写 v）
sudo nginx -v

    用途：

    • -v（小写）：只打印版本号，如 nginx version: nginx/1.30.4。
    • -V（大写）：打印版本号 + 完整的编译参数，包括 configure arguments、编译器版本、启用/禁用的模块等。

    -V 的典型输出（截取关键部分）：

    nginx version: nginx/1.30.4
built by gcc 11.4.1 20230605 (Red Hat 11.4.1-2)
built with OpenSSL 3.0.9
configure arguments: --prefix=/etc/nginx --sbin-path=/usr/sbin/nginx
  --with-http_ssl_module --with-http_v2_module --with-http_realip_module
  --with-http_stub_status_module --with-stream --with-stream_ssl_module ...

    常见用途：确认你的 Nginx 是否编译了某个模块（如 --with-http_stub_status_module、--with-stream）。如果没有，需要重新编译或安装动态模块。

    1.4 nginx -s signal — 发送控制信号¶

    # 优雅停止：处理完当前请求后退出（发送 QUIT 信号给 master）
sudo nginx -s quit

# 快速停止：立即退出（发送 TERM 信号给 master）
sudo nginx -s stop

# 重新加载配置（发送 HUP 信号给 master）
sudo nginx -s reload

# 重新打开日志文件（发送 USR1 信号给 master，用于日志轮转）
sudo nginx -s reopen
    信号 等价的 kill 信号 行为
    stop TERM 立即停止，丢弃正在处理的请求
    quit QUIT 优雅停止，等当前请求处理完毕后退出
    reload HUP 重新加载配置，旧 worker 处理完手中请求后退出，新 worker 用新配置启动
    reopen USR1 重新打开日志文件（配合 logrotate 使用）

    踩坑提醒：reload 不是"重启"。reload 时 master 进程不会退出，它只是重新读取配置并启动新的 worker 进程。如果你改了 listen 端口，reload 是可以生效的；但如果你升级了 Nginx 二进制文件，必须用 USR2 + WINCH 信号做热升级，reload 不会加载新的二进制。详见 03-进程模型与控制管理。

    1.5 nginx -c /path/to/conf — 指定配置文件¶

    # 用指定的配置文件启动 Nginx（而不是默认的 /etc/nginx/nginx.conf）
sudo nginx -c /etc/nginx/nginx.conf

# 用自定义配置文件启动（常用于测试）
sudo nginx -c /tmp/nginx_test.conf

    用途：Nginx 默认读取编译时 --conf-path 指定的配置文件（通常是 /etc/nginx/nginx.conf）。用 -c 可以指定其他路径。常用于：

    • 多实例部署（同一台机器跑多个 Nginx，各用不同配置和端口）。
    • 测试新配置而不影响线上服务。

    1.6 nginx -g "directive" — 设置全局指令¶

    # 启动时覆盖配置文件中的某条指令
sudo nginx -g "daemon off;"

# 临时修改 worker_processes
sudo nginx -g "worker_processes 4;"

# 指定错误日志路径
sudo nginx -g "error_log /tmp/nginx_test_error.log;"

    用途：在命令行设置全局指令，优先级高于配置文件中的同名指令。最常见的是 daemon off;——在前台运行 Nginx，这是 Docker 容器中运行 Nginx 的标准做法。

    注意：-g 设置的指令必须以分号结尾，和配置文件里的语法一致。多个指令用分号分隔。

    1.7 nginx -p prefix — 指定 prefix 路径¶

    # 指定 Nginx 的 prefix 目录（影响相对路径解析）
sudo nginx -p /usr/local/nginx/

    用途：设置 Nginx 的 prefix 路径。配置文件中的相对路径（如 include mime.types;、error_log logs/error.log;）会基于这个 prefix 解析。默认 prefix 是编译时 --prefix 指定的路径（通常是 /etc/nginx 或 /usr/local/nginx）。

    常见场景：用源码编译安装的 Nginx 如果安装在非标准路径，可能需要 -p 指定。大多数包管理器安装的 Nginx 不需要手动指定。

    速查总结表¶

    命令 用途 常用程度
    nginx -t 测试配置语法 每天用
    nginx -T 打印完整生效配置 排障时用
    nginx -V 查看编译参数和模块 排障/选型时用
    nginx -v 查看版本号 偶尔用
    nginx -s reload 重新加载配置 每天用
    nginx -s quit 优雅停止 偶尔用
    nginx -s stop 快速停止 偶尔用
    nginx -s reopen 重新打开日志 日志轮转时用
    nginx -c <path> 指定配置文件 多实例/测试时用
    nginx -g "directive" 命令行设置全局指令 Docker 中常用
    nginx -p <prefix> 指定 prefix 路径 源码安装时用

    二、systemd 服务管理¶

    现代 Linux 发行版（CentOS 7+、Ubuntu 16.04+、Debian 8+）都用 systemd 管理服务。通过包管理器安装的 Nginx 会自动注册为 systemd 服务。

    2.1 基本服务管理¶

    # 启动 Nginx
sudo systemctl start nginx

# 停止 Nginx
sudo systemctl stop nginx

# 重新加载配置（等价于 nginx -s reload，但 systemd 会等待完成）
sudo systemctl reload nginx

# 重启 Nginx（先 stop 再 start，会有短暂中断）
sudo systemctl restart nginx

# 查看 Nginx 运行状态
sudo systemctl status nginx

    systemctl status nginx 典型输出：

    ● nginx.service - The nginx HTTP and reverse proxy server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: disabled)
     Active: active (running) since Tue 2026-08-05 10:00:00 CST; 2h ago
   Main PID: 12345 (nginx)
      Tasks: 9 (limit: 4915)
     Memory: 25.0M
        CPU: 1.234s
     CGroup: /system.slice/nginx.service
             ├─12345 nginx: master process /usr/sbin/nginx
             └─12346 nginx: worker process
    字段 含义
    Loaded 服务文件是否加载、是否开机自启（enabled = 自启，disabled = 不自启）
    Active 服务状态（active (running) = 运行中，inactive = 已停止，failed = 启动失败）
    Main PID master 进程 PID

    reload vs restart：reload 不会中断服务（优雅重载配置），restart 会先停止再启动（有短暂中断）。生产环境永远优先用 reload，只有升级二进制或修改了 listen 端口等必须重启的场景才用 restart。

    2.2 开机自启管理¶

    # 设置开机自启
sudo systemctl enable nginx

# 取消开机自启
sudo systemctl disable nginx

# 查看是否已设置开机自启
systemctl is-enabled nginx

    2.3 journalctl — 查看服务日志¶

    # 查看 Nginx 服务日志（systemd 日志）
sudo journalctl -u nginx

# 只看最近的 50 行
sudo journalctl -u nginx -n 50

# 实时跟踪日志（类似 tail -f）
sudo journalctl -u nginx -f

# 查看今天的日志
sudo journalctl -u nginx --since today

# 查看某个时间段的日志
sudo journalctl -u nginx --since "2026-08-05 10:00:00" --until "2026-08-05 12:00:00"

# 查看启动失败的日志（排查启动失败）
sudo journalctl -u nginx --no-pager | tail -50

    用途：journalctl 是 systemd 的日志查看工具。当 Nginx 启动失败（systemctl start nginx 报错）时，第一时间看 journalctl，通常能看到配置文件哪一行出错。

    踩坑提醒：Nginx 的错误日志在两个地方——/var/log/nginx/error.log（Nginx 自己的日志）和 journalctl -u nginx（systemd 捕获的启动/停止日志）。启动失败时两个都要看。systemd 日志通常能看到 nginx -t 都查不出来的问题，比如端口被占用、权限不足等。

    三、进程查看与管理¶

    3.1 ps — 查看进程¶

    # 查看所有 Nginx 进程（最常用）
ps -ef | grep nginx

# 只看进程树和 PID
ps aux | grep nginx | grep -v grep

    典型输出：

    root      12345     1  0 10:00 ?        00:00:00 nginx: master process /usr/sbin/nginx
nginx     12346 12345  0 10:00 ?        00:00:00 nginx: worker process
nginx     12347 12345  0 10:00 ?        00:00:00 nginx: worker process
nginx     12348 12345  0 10:00 ?        00:00:00 nginx: worker process
nginx     12349 12345  0 10:00 ?        00:00:00 nginx: worker process
    列 含义
    第一列（root） 进程运行用户。master 通常是 root（需要绑定特权端口 80）
    第二列（12345） PID
    第三列（1/12345） 父进程 PID。worker 的父进程是 master
    最后一列 进程名（master process / worker process）

    3.2 pstree — 查看进程树¶

    # 以树状结构查看 Nginx 进程关系
pstree -p $(pgrep -o nginx)

# 或者查看完整的进程树
pstree -p $(cat /var/run/nginx.pid)

    典型输出：

    nginx(12345)───nginx(12346)
               ├─nginx(12347)
               ├─nginx(12348)
               └─nginx(12349)

    用途：直观地看到 master 进程和它下面的 worker 进程的父子关系。-p 显示 PID。

    3.3 kill — 发送信号给 master 进程¶

    # 获取 master PID（两种方式）
cat /var/run/nginx.pid
pgrep -o nginx   # -o 表示 oldest（最老的进程，即 master）

# 优雅停止（等价于 nginx -s quit）
kill -s QUIT $(cat /var/run/nginx.pid)

# 重新加载配置（等价于 nginx -s reload）
kill -s HUP $(cat /var/run/nginx.pid)

# 重新打开日志文件（等价于 nginx -s reopen）
kill -s USR1 $(cat /var/run/nginx.pid)

# 热升级：启动新 master 进程
kill -s USR2 $(cat /var/run/nginx.pid)

# 热升级：让旧 master 的 worker 优雅退出
kill -s WINCH $(cat /var/run/nginx.pid)
    信号 用途 等价命令
    TERM / INT 快速停止 nginx -s stop
    QUIT 优雅停止 nginx -s quit
    HUP 重新加载配置 nginx -s reload
    USR1 重新打开日志 nginx -s reopen
    USR2 热升级（启动新 master） 无等价命令行参数
    WINCH 让旧 worker 优雅退出（配合 USR2 做热升级） 无等价命令行参数

    踩坑提醒：kill 命令的信号名不带 SIG 前缀。写 kill -SIGQUIT 是错的，应该写 kill -s QUIT 或 kill -QUIT。另外，只给 master 发信号，不要给 worker 发——给 worker 发信号可能导致 worker 异常退出。

    四、配置测试与查看¶

    4.1 nginx -t — 语法测试¶

    # 测试默认配置
sudo nginx -t

# 测试指定配置文件
sudo nginx -t -c /etc/nginx/nginx.conf

    用途：检查配置文件语法是否正确。每次修改配置后、reload 之前，必须先 -t。

    最佳实践：可以写成一行：sudo nginx -t && sudo nginx -s reload，只有测试通过才 reload。

    4.2 nginx -T — 打印完整配置¶

    # 打印所有生效配置
sudo nginx -T

# 配合 grep 搜索特定配置
sudo nginx -T | grep server_name
sudo nginx -T | grep -n "proxy_pass"
sudo nginx -T | grep -A 10 "upstream backend"

# 打印到文件方便对比
sudo nginx -T > /tmp/nginx_full_config.txt

    用途：把所有 include 进来的配置文件合并展开后打印。当你有大量 include 文件、不确定最终生效配置时，这是最直接的排查手段。

    4.3 查看编译模块¶

    # 查看所有编译参数，按行拆分后筛选模块
sudo nginx -V 2>&1 | tr ' ' '\n' | grep module

# 查看是否包含某个特定模块
sudo nginx -V 2>&1 | tr ' ' '\n' | grep ssl
sudo nginx -V 2>&1 | tr ' ' '\n' | grep stream
sudo nginx -V 2>&1 | tr ' ' '\n' | grep stub_status

    原理解释：

    • nginx -V 的输出到 stderr（标准错误流），所以要用 2>&1 重定向到 stdout。
    • 编译参数是空格分隔的一长串，用 tr ' ' '\n' 把空格换成换行，每行一个参数，再 grep 筛选。

    典型输出：

    --with-http_ssl_module
--with-http_v2_module
--with-http_realip_module
--with-http_stub_status_module
--with-stream
--with-stream_ssl_module

    常见用途：排查"为什么某条指令不识别"——很可能是因为对应的模块没有编译进去。例如 stub_status 指令需要 --with-http_stub_status_module，stream 块需要 --with-stream。

    4.4 查看编译参数¶

    # 查看所有 --with 编译参数
sudo nginx -V 2>&1 | grep --color=auto with

# 查看完整编译参数（不做处理）
sudo nginx -V 2>&1

    用途：查看 Nginx 编译时启用了哪些功能和模块。--with-xxx 表示启用的模块，没有 --with- 前缀的是默认启用的。

    五、日志排查命令¶

    5.1 实时查看日志¶

    # 实时查看错误日志（排障首选）
sudo tail -f /var/log/nginx/error.log

# 实时查看访问日志
sudo tail -f /var/log/nginx/access.log

# 查看最后 100 行错误日志
sudo tail -n 100 /var/log/nginx/error.log

# 实时查看并高亮关键字（如果有颜色 grep）
sudo tail -f /var/log/nginx/error.log | grep --color=auto -E "error|warn|crit"

    用途：tail -f 是最常用的实时日志查看命令。排障时通常开两个终端，一个看 error.log，一个看 access.log。

    5.2 筛选错误状态码¶

    # 查看所有 5xx 错误请求
sudo grep "500\|502\|503\|504" /var/log/nginx/access.log

# 查看并统计各种 5xx 错误的数量
sudo grep -oE 'HTTP/[0-9.]+" [50][0-9][0-9]' /var/log/nginx/access.log | grep -oE '[50][0-9][0-9]' | sort | uniq -c | sort -rn

# 查看今天某个时间段的 502 错误
sudo grep "502" /var/log/nginx/access.log | grep "05/Aug/2026:1[0-2]:"

    用途：快速定位 5xx 错误。502 通常是后端挂了，504 是后端超时，500 是后端代码报错。

    5.3 IP 访问统计¶

    # 统计访问量最大的前 20 个 IP
sudo awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 统计某个 IP 的访问次数
sudo grep "192.168.1.100" /var/log/nginx/access.log | wc -l

    用途：排查恶意 IP 刷接口、CC 攻击等。如果某个 IP 的请求量远超正常水平，可能需要用 limit_req 或 deny 限制。

    命令解析：

    步骤 命令 作用
    1 awk '{print $1}' 提取第 1 列（客户端 IP）
    2 sort 排序（为 uniq 做准备）
    3 uniq -c 去重并统计每行出现次数
    4 sort -rn 按次数倒序排序（-r 逆序，-n 按数字）
    5 head -20 取前 20 行

    5.4 URL 访问统计¶

    # 统计访问量最大的前 20 个 URL
sudo awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 统计某个 URL 的访问次数
sudo grep "/api/login" /var/log/nginx/access.log | wc -l

# 统计 5xx 错误最多的 URL
sudo awk '$9 ~ /^5/ {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

    用途：找出热点 URL 或出错的 URL。$7 是请求的 URI 路径（如 /api/users），$9 是 HTTP 状态码。

    注意：默认的 combined 日志格式中，$1=IP，$7=URI，$9=状态码，$NF（最后一列）= $request_time（如果日志格式包含的话）。如果你的 log_format 是自定义的，字段位置可能不同。先 head -1 access.log 看一下格式。

    5.5 慢请求分析¶

    # 找出请求时间超过 1 秒的慢请求（$request_time > 1）
sudo awk '($NF > 1) {print}' /var/log/nginx/access.log

# 找出请求时间超过 1 秒的慢请求，并按时间倒序
sudo awk '($NF > 1) {print $NF, $7}' /var/log/nginx/access.log | sort -rn | head -20

# 统计后端响应时间（$upstream_response_time）超过 2 秒的请求
sudo awk '$NF > 2 {print $7, $NF}' /var/log/nginx/access.log | sort -rn | head -20

# 统计慢请求占比
sudo awk '{total++; if($NF>1) slow++} END {printf "total=%d, slow=%d, ratio=%.2f%%\n", total, slow, slow*100/total}' /var/log/nginx/access.log

    用途：定位性能瓶颈。$NF 表示最后一列——如果你的日志格式最后一列是 $request_time（请求总耗时），那 awk '($NF > 1)' 就是找出耗时超过 1 秒的请求。

    踩坑提醒：$NF 是最后一列，这取决于你的 log_format。标准 combined 格式最后一列是 $http_user_agent，不是 $request_time。你需要在 log_format 中显式加上 $request_time 才能用这个命令。建议生产环境日志格式包含 $request_time 和 $upstream_response_time。

    六、网络连接排查¶

    6.1 netstat — 查看监听端口¶

    # 查看 Nginx 监听的所有端口
sudo netstat -tlnp | grep nginx

# 参数解释：
# -t  TCP 连接
# -l  只看监听状态（LISTEN）
# -n  不解析域名（显示 IP 而非主机名，更快）
# -p  显示进程信息（需要 root 权限）

    典型输出：

    tcp        0      0 0.0.0.0:80              0.0.0.0:*               LISTEN      12345/nginx: master
tcp        0      0 0.0.0.0:443             0.0.0.0:*               LISTEN      12345/nginx: master
tcp6       0      0 :::80                   :::*                    LISTEN      12345/nginx: master
tcp6       0      0 :::443                  :::*                    LISTEN      12345/nginx: master

    注意：netstat 在较新的发行版中可能未默认安装（被 ss 替代）。如果没有 netstat，安装 net-tools 包或直接用 ss。

    6.2 ss — 现代替代工具（推荐）¶

    # 查看 Nginx 监听的所有端口（推荐，比 netstat 快）
sudo ss -tlnp | grep nginx

# 查看所有到 Nginx 的已建立连接
sudo ss -tnp | grep nginx

# 查看 Nginx 的连接状态统计
sudo ss -s

    ss -s 典型输出：

    Total: 1500
TCP:   800 (estab 200, closed 500, orphaned 0, timewait 400)

Transport Total     IP        IPv6
TCP       800       400       400
    字段 含义
    Total 所有套接字总数
    TCP TCP 连接总数
    estab 已建立的连接数
    closed 已关闭的连接数
    timewait TIME_WAIT 状态的连接数

    用途：ss 比 netstat 快得多（直接读内核 netlink 而非遍历 /proc），在高并发服务器上推荐用 ss。

    6.3 lsof — 查看进程打开的文件¶

    # 查看 master 进程打开的所有文件（包括网络套接字）
sudo lsof -p $(pgrep nginx | head -1)

# 查看 80 端口被哪个进程占用
sudo lsof -i :80

# 查看 Nginx 打开的网络连接
sudo lsof -p $(pgrep nginx | head -1) -i

    用途：

    • lsof -p <pid>：查看某个进程打开了哪些文件、网络套接字。排查"文件描述符不够用"问题时很有用。
    • lsof -i :80：查看谁占用了 80 端口。如果 Nginx 启动报 bind() failed (98: Address already in use)，用这个命令找出占用者。

    踩坑提醒：如果 lsof 显示 Nginx 打开了大量文件（接近 worker_connections 或系统 ulimit -n 上限），说明连接数快要耗尽了，需要调大 worker_connections 和系统文件描述符限制。详见 19-性能调优。

    七、性能观测¶

    7.1 stub_status — 查看 Nginx 连接状态¶

    # 查看 Nginx 内置的状态页（需要编译 --with-http_stub_status_module）
curl -s http://localhost/nginx_status

    典型输出：

    Active connections: 15
server accepts handled requests
 8456 8456 32891
Reading: 0
Writing: 3
Waiting: 12
    指标 含义
    Active connections 当前活跃连接数
    accepts 已接受的连接总数
    handled 已处理的连接总数
    requests 已处理的请求总数
    Reading 正在读取请求头的连接数
    Writing 正在返回响应的连接数
    Waiting 空闲等待中的连接数（通常是 keepalive 长连接）

    配置要求：需要在 Nginx 配置中添加 stub_status location 才能访问：

    location /nginx_status {
    stub_status;
    allow 127.0.0.1;  # 只允许本机访问
    deny all;
}

    7.2 ab — Apache Bench 压测工具¶

    # 基本压测：10000 个请求，100 并发
ab -n 10000 -c 100 http://localhost/

# 带 Keep-Alive 的压测（更接近真实浏览器行为）
ab -n 10000 -c 100 -k http://localhost/

# 压测 HTTPS（忽略证书验证）
ab -n 10000 -c 100 -s 30 https://localhost/

# 带自定义 Header
ab -n 10000 -c 100 -H "Authorization: Bearer token123" http://localhost/api/

    关键输出指标：

    指标 含义
    Requests per second 每秒处理请求数（QPS），最重要的指标
    Time per request 每个请求平均耗时（ms）
    Time per request (across all concurrent requests) 每个请求平均耗时（考虑并发）
    Failed requests 失败请求数
    Transfer rate 传输速率（KB/s）

    踩坑提醒：ab 本身也是客户端，压测时客户端机器的端口数可能成为瓶颈。如果 ab 报 apr_socket_recv: Connection reset by peer，可能是因为客户端端口耗尽（TIME_WAIT 太多）。可以调短 TIME_WAIT 或用多台机器压测。

    7.3 wrk — 现代压测工具¶

    # 基本压测：4 线程，100 连接，持续 30 秒
wrk -t4 -c100 -d30s http://localhost/

# 带 Keep-Alive（wrk 默认就启用长连接）
wrk -t4 -c100 -d30s --latency http://localhost/

# 使用 Lua 脚本进行 POST 请求压测
wrk -t4 -c100 -d30s -s post.lua http://localhost/api/

    post.lua 示例：

    wrk.method = "POST"
wrk.body = '{"key":"value"}'
wrk.headers["Content-Type"] = "application/json"

    wrk vs ab：wrk 使用多线程 + 事件驱动，本身性能远高于 ab（ab 是单线程的），适合压测高并发场景。wrk 默认启用 Keep-Alive，测试结果更接近真实场景。

    7.4 top — 查看 Nginx 进程资源占用¶

    # 实时查看 master 进程的 CPU 和内存使用
top -p $(pgrep nginx | head -1)

# 查看所有 Nginx 进程（master + workers）
top -p $(pgrep nginx | tr '\n' ',' | sed 's/,$//')

# 使用 htop（更友好的界面，推荐安装）
htop -p $(pgrep nginx | head -1)

    用途：实时监控 Nginx 进程的 CPU、内存使用情况。正常情况下 worker 进程的 CPU 占用应该比较均匀，如果某个 worker 的 CPU 飙高，可能有慢请求或异常连接。

    排查思路：如果所有 worker 的 CPU 都接近 100%，说明 Nginx 已经到达性能瓶颈，需要考虑：增加 worker_processes、开启 reuseport、或水平扩展到多台服务器。如果只有某个 worker CPU 飙高，可能是某个慢请求卡住了这个 worker 的事件循环。

    八、SSL 证书相关¶

    8.1 查看证书信息¶

    # 连接到服务器并查看证书链（交互式）
openssl s_client -connect example.com:443 -servername example.com

# 查看证书的详细信息（从证书文件）
openssl x509 -in /etc/nginx/ssl/cert.pem -text -noout

# 查看证书的有效期
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates

# 查看证书的颁发者和使用者
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -subject -issuer

    openssl x509 -dates 典型输出：

    notBefore=Jan  1 00:00:00 2026 GMT
notAfter=Mar  1 23:59:59 2026 GMT
    字段 含义
    notBefore 证书生效时间
    notAfter 证书过期时间

    运维提醒：生产环境一定要监控证书过期时间！证书过期会导致 HTTPS 全线不可用。可以用 certbot 的自动续期，或写脚本定期检查 notAfter 并告警。

    8.2 查看完整证书链¶

    # 查看服务器返回的完整证书链（包括中间证书）
openssl s_client -connect example.com:443 -showcerts

    用途：排查证书链不完整的问题。如果服务器只返回了终端证书而没有返回中间证书，部分客户端（尤其是 Android、Java 客户端）会报"证书不可信"。

    踩坑提醒：Nginx 的 ssl_certificate 指令应该指向一个包含终端证书 + 中间证书的完整链文件（fullchain.pem），而不是只有终端证书（cert.pem）。Let's Encrypt 生成的 fullchain.pem 已经包含了完整链，直接用即可。详见踩坑记录 #4.1。

    8.3 快速检查证书过期时间（一行命令）¶

    # 一行命令检查证书过期时间（适合写进监控脚本）
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates

# 检查证书还有多少天过期
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -enddate \
  | cut -d= -f2 \
  | xargs -I{} date -d "{}" +%s \
  | xargs -I{} bash -c 'echo $(( ({} - $(date +%s)) / 86400 )) days remaining'

    用途：写进定时任务，每天检查证书过期时间，剩余不足 14 天时告警。

    九、调试技巧¶

    9.1 curl -v — 查看详细请求/响应头¶

    # 查看完整的请求和响应头（包括 TLS 握手过程）
curl -v http://localhost/

# HTTPS 查看完整 TLS 握手过程
curl -v https://localhost/

    典型输出（截取关键部分）：

    > GET / HTTP/1.1              ← 请求行
> Host: localhost             ← 请求头
> User-Agent: curl/7.81.0
> Accept: */*
>
< HTTP/1.1 200 OK             ← 响应行
< Server: nginx/1.30.4        ← 响应头
< Content-Type: text/html
< Content-Length: 612
<
    • > 开头的行：curl 发出的请求头。
    • < 开头的行：服务器返回的响应头。
    • * 开头的行：curl 自身的调试信息（如 TLS 握手、连接信息）。

    用途：排查请求/响应头问题。比如确认 X-Forwarded-For 是否正确传递、Content-Type 是否正确、重定向是否正常等。

    9.2 curl -I — 只看响应头¶

    # 只获取响应头（发送 HEAD 请求）
curl -I http://localhost/

# 只获取响应头（发送 GET 请求但丢弃 body）
curl -s -D - -o /dev/null http://localhost/

    用途：快速检查响应状态码和响应头，不下载 body 内容。适合检查重定向、缓存命中状态等。

    9.3 curl -H — 指定请求头¶

    # 指定 Host 头（测试虚拟主机配置）
curl -H "Host: example.com" http://localhost/

# 指定多个请求头
curl -H "Host: example.com" -H "Authorization: Bearer token123" http://localhost/

# 指定 User-Agent
curl -H "User-Agent: Mozilla/5.0" http://localhost/

# 发送 JSON 请求体
curl -X POST -H "Content-Type: application/json" -d '{"key":"value"}' http://localhost/api/

    用途：

    • 指定 Host 头：当你通过 IP 访问但想测试基于域名的虚拟主机时，用 -H "Host: example.com" 让 Nginx 根据 Host 头路由到正确的 server 块。这是最常用的调试技巧之一。
    • 指定 Authorization：测试需要认证的接口。

    9.4 curl -k — 忽略证书验证¶

    # 忽略 TLS 证书验证（自签名证书时使用）
curl -k https://localhost/

# 忽略证书验证并查看详细头
curl -k -v https://localhost/

    用途：测试使用自签名证书或证书过期/域名不匹配的 HTTPS 服务。-k（--insecure）让 curl 跳过证书验证。

    注意：-k 只在调试时使用，生产环境永远不要忽略证书验证。

    9.5 curl --resolve — DNS 覆盖¶

    # 绕过 DNS，直接将 example.com 解析到 127.0.0.1
curl --resolve example.com:443:127.0.0.1 https://example.com/

# 绕过 DNS，HTTP 场景
curl --resolve example.com:80:127.0.0.1 http://example.com/

# 多个域名同时覆盖
curl --resolve example.com:443:127.0.0.1 --resolve api.example.com:443:127.0.0.1 https://example.com/

    用途：最强大的调试技巧之一。当你要测试 HTTPS + 域名路由，但 DNS 还没有指向你的服务器时，用 --resolve 可以绕过 DNS 解析，直接连到指定 IP，同时保持 Host 头和 SNI 正确。

    对比三种方式：

    方式 命令 适用场景 缺点
    -H "Host:" curl -H "Host: example.com" http://localhost/ HTTP 虚拟主机测试 不适用 HTTPS（SNI 不对）
    --resolve curl --resolve example.com:443:127.0.0.1 https://example.com/ HTTPS + 域名路由测试 无
    修改 /etc/hosts 编辑 hosts 文件 全局生效 影响所有程序

    最佳实践：HTTPS 调试首选 --resolve。它不影响系统 DNS，只对当前 curl 命令生效，而且 SNI 会正确发送域名。

    十、Docker 相关¶

    10.1 在容器中执行 Nginx 命令¶

    # 在容器中测试配置
docker exec nginx nginx -t

# 在容器中重新加载配置
docker exec nginx nginx -s reload

# 在容器中打印完整配置
docker exec nginx nginx -T

# 在容器中查看版本和编译参数
docker exec nginx nginx -V

    用途：Docker 容器中运行的 Nginx 也可以通过 docker exec 执行 nginx 命令。nginx 是容器名（也可以用容器 ID）。

    注意：docker exec nginx nginx -t 中，第一个 nginx 是容器名，第二个 nginx 是容器内的命令。容易混淆，可以起一个更明确的容器名，如 docker exec web nginx -t。

    10.2 查看容器日志¶

    # 查看 Nginx 容器的日志（stdout/stderr）
docker logs nginx

# 实时跟踪容器日志
docker logs -f nginx

# 查看最后 50 行
docker logs --tail 50 nginx

# 查看 docker compose 管理的 Nginx 日志
docker compose logs -f nginx
docker compose logs --tail 100 nginx

    用途：Docker 官方 Nginx 镜像默认将 access_log 和 error_log 输出到 stdout/stderr，这样可以用 docker logs 直接查看。如果是自定义镜像或修改了日志路径，需要 docker exec 进入容器查看日志文件。

    原理：Docker 官方 Nginx 镜像在 Dockerfile 中做了软链接：

    ln -sf /dev/stdout /var/log/nginx/access.log
ln -sf /dev/stderr /var/log/nginx/error.log

    这样 Nginx 的日志直接输出到容器的 stdout/stderr，被 Docker 日志驱动捕获。

    10.3 进入容器¶

    # 进入容器的交互式 shell
docker exec -it nginx /bin/bash

# 如果容器内没有 bash（如 Alpine 基础镜像），用 sh
docker exec -it nginx /bin/sh

# 进入容器并查看配置文件
docker exec -it nginx /bin/bash -c "cat /etc/nginx/nginx.conf"

# 进入容器并编辑配置
docker exec -it nginx /bin/bash -c "vi /etc/nginx/nginx.conf"

    用途：需要在容器内执行交互式操作（如查看文件、编辑配置、安装调试工具）时使用。-i 保持 stdin 打开，-t 分配伪终端。

    最佳实践：生产环境不建议直接 docker exec 进入容器修改配置（容器重建后修改会丢失）。正确做法是将配置文件通过 volume 挂载到容器中，在宿主机修改配置后 docker exec nginx nginx -s reload。

    10.4 Docker Compose 常用命令¶

    # 启动服务（后台运行）
docker compose up -d

# 重新加载 Nginx 配置（修改挂载的配置文件后）
docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload

# 重启 Nginx 容器
docker compose restart nginx

# 查看服务状态
docker compose ps

# 停止并删除容器
docker compose down

# 重新构建并启动
docker compose up -d --build

    典型 docker-compose.yml 片段（配置文件挂载）：

    services:
  nginx:
    image: nginx:1.30.4
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./nginx/ssl:/etc/nginx/ssl:ro
      - ./nginx/logs:/var/log/nginx
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped

    将配置文件、SSL 证书、日志目录、静态资源都通过 volume 挂载，这样在宿主机修改后 reload 即可生效，不需要重建容器。

    小结¶

    本文档按十大功能场景整理了 Nginx 日常运维中最常用的命令。回顾一下使用频率最高的几个：

    场景 首选命令 说明
    修改配置后验证 nginx -t 每次改配置必做
    重载配置 nginx -s reload 或 systemctl reload nginx 验证通过后执行
    排查启动失败 journalctl -u nginx 看 systemd 日志
    排查 5xx 错误 tail -f /var/log/nginx/error.log 实时看错误日志
    查看生效配置 nginx -T 排查配置不生效
    查看编译模块 nginx -V 2>&1 \| tr ' ' '\n' \| grep module 排查指令不识别
    查看连接状态 curl -s http://localhost/nginx_status stub_status
    调试虚拟主机 curl --resolve example.com:443:127.0.0.1 https://example.com/ DNS 覆盖
    容器内操作 docker exec nginx nginx -t Docker 环境
    查看监听端口 ss -tlnp \| grep nginx 确认端口绑定

    日常运维工作流（修改配置的标准流程）：

    # 1. 修改配置文件
sudo vi /etc/nginx/conf.d/example.conf

# 2. 测试语法
sudo nginx -t

# 3. 测试通过后重载
sudo nginx -s reload

# 4. 验证服务正常
curl -I http://localhost/

# 5. 如果出问题，看日志
sudo tail -f /var/log/nginx/error.log

    把这套流程变成肌肉记忆，你就能安全地管理 Nginx 了。
