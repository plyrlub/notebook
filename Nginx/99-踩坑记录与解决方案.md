## 一、配置类坑点

### #1.1 location 匹配优先级陷阱

**现象**：写了多个 location，请求却命中了意料之外的那个。以为 `location /api` 会优先于 `location /`，结果被正则 location 抢走。

**原因**：location 匹配顺序不是"谁写在前面谁优先"，而是按类型优先级：

1. `=` 精确匹配（最高优先级）
2. `^~` 前缀匹配（命中后不再走正则）
3. 正则 `~`/`~*`（按配置中出现顺序，首个命中即停止）
4. 普通前缀匹配（最长前缀优先，最低优先级）

普通前缀即使更长，只要正则命中，正则也优先（除非用 `^~` 或 `=`）。

**解决方案**：

```nginx
# 精确匹配：最高优先级，常用于特定文件
location = /favicon.ico {
    log_not_found off;
    access_log off;
}

# 不希望被正则覆盖的前缀
location ^~ /api/ {
    proxy_pass http://backend;
}

# 正则匹配：注意它优先于普通前缀
location ~* \.(gif|jpg|png|css|js)$ {
    expires 1h;
}

# 普通前缀：最低优先级
location / {
    try_files $uri $uri/ /index.html;
}
```

> **参考文档**：[07-location匹配规则.md](03-核心机制/07-location匹配规则.md)

### #1.2 root vs alias 混淆

**现象**：`location /img/ { root /data/w3; }` 请求 `/img/a.png` 能取到，但实际读取的是 `/data/w3/img/a.png`（root 把 location 路径也拼了进去）。而用 alias 时路径替换逻辑不同，常导致 404。

**原因**：

- `root`：把 root 路径 + **完整 URI** 拼接。`root /data; location /img/` → 查找 `/data/img/a.png`
- `alias`：把 location 匹配的部分**替换**为 alias 路径。`alias /data/; location /img/` → 查找 `/data/a.png`
- alias 末尾斜杠与 location 末尾斜杠要对应，否则路径错乱

**解决方案**：

```nginx
# 方式一：root（追加语义）
location /img/ {
    root /data/w3;  # 请求 /img/a.png → /data/w3/img/a.png
}

# 方式二：alias（替换语义）
location /img/ {
    alias /data/images/;  # 请求 /img/a.png → /data/images/a.png
    # 注意：location 和 alias 末尾都要加 /
}
```

> **记忆口诀**：root 是"追加"，alias 是"替换"。官方建议 root 放在 server 层级，location 内只在需要时覆盖。

### #1.3 try_files 误用 / 用 if 判断文件存在

**现象**：用 `if (!-f $request_filename)` 判断文件是否存在，导致行为异常、性能差甚至段错误。

**原因**：`if` 指令在 location 上下文中"是邪恶的"（If Is Evil），只能安全地使用 `return` 和 `rewrite ... last`，其他指令行为不可预测。判断文件存在应使用 `try_files`。

**解决方案**：

```nginx
# ❌ 错误：用 if 判断文件存在
location / {
    if (!-f $request_filename) {
        # 危险！行为不可预测
        proxy_pass http://backend;
    }
}

# ✅ 正确：用 try_files
location / {
    # 按顺序尝试：$uri 文件 → $uri/ 目录 → 回退到 index.html
    try_files $uri $uri/ /index.html;
}
```

### #1.4 proxy_pass 末尾斜杠导致 URI 被改写

**现象**：`location /api/ { proxy_pass http://backend/; }` 与 `proxy_pass http://backend;`（无斜杠）转发给后端的 URI 不同，常导致后端 404 或路径重复/丢失。

**原因**：proxy_pass 是否带 URI（哪怕只是一个 `/`）决定了 URI 改写行为：

- **不带 URI**（`proxy_pass http://backend;`）：原样把完整请求 URI 传给后端
- **带 URI**（`proxy_pass http://backend/;` 或带路径）：用 proxy_pass 中的 URI 部分替换掉 location 匹配的前缀部分
- **特例**：当 location 使用正则或命名 location 时，proxy_pass **不能**带 URI 部分，否则报错

**解决方案**：

```nginx
# 场景一：剥掉前缀再转发
# 请求 /api/users → 后端 /users
location /api/ {
    proxy_pass http://backend/;  # 带尾斜杠，替换 /api/ 为 /
}

# 场景二：保留完整路径
# 请求 /api/users → 后端 /api/users
location /api/ {
    proxy_pass http://backend;  # 不带尾斜杠，原样转发
}

# 场景三：正则 location 不能带 URI
location ~ ^/api/(.*)$ {
    # proxy_pass http://backend/$1;  # ❌ 报错！
    proxy_pass http://backend;  # ✅ 只能不带 URI
}
```

> **参考文档**：[09-反向代理proxy_pass.md](04-反向代理与负载均衡/09-反向代理proxy_pass.md)

### #1.5 rewrite 的 last 与 break 区别

**现象**：rewrite 后要么"重新走 location 匹配"陷入循环，要么"停在当前 location 找不到文件"。

**原因**：

- `last`：停止当前 rewrite 指令集，**用新 URI 重新进行 location 匹配**（可能再触发别的 rewrite）
- `break`：停止 rewrite 处理，**留在当前 location** 继续后续处理（不再重新匹配 location）

**解决方案**：

```nginx
# 场景一：改写后希望走到另一个 location
location /old {
    rewrite ^/old/(.*)$ /new/$1 last;  # last → 重新匹配 location
}

location /new {
    # 请求会被路由到这里
    proxy_pass http://new_backend;
}

# 场景二：改写后仅修改内部路径，在当前 location 处理
location /download/ {
    rewrite ^/download/(.*)$ /files/$1 break;  # break → 留在当前 location
    # 配合 root/alias 读取文件
    root /data;
}
```

> **注意**：rewrite 默认最多循环 10 次，超限返回 500 错误。

### #1.6 $uri 在内部跳转后被改写

**现象**：用 `try_files $uri /index.php?$uri` 时，`$uri` 已经被 rewrite 改成新值，传给后端的参数不符预期。

**原因**：

- `$uri`：当前规范化后的请求 URI，会随 rewrite/try_files 内部跳转而**变化**
- `$request_uri`：原始请求 URI（含参数），**始终不变**

**解决方案**：

```nginx
# ❌ $uri 可能已被改写
try_files $uri /index.php?$uri;

# ✅ 需要原始路径时用 $request_uri
return 301 https://example.com$request_uri;  # 优于 rewrite 方式
```

### #1.7 if is evil（在 location 中滥用 if）

**现象**：在 location 里用 `if` 做条件判断，出现 add_header 只生效一个、proxy_pass URI 没改写、try_files 失效，甚至 SIGSEGV 段错误。

**原因**：`if` 属于 rewrite 模块（指令式），而 Nginx 配置整体是声明式的，二者在 location 上下文混合会导致不可预测行为。唯一 100% 安全的是 `return` 和 `rewrite ... last`。

**解决方案**：

```nginx
# ❌ 危险：在 if 里做各种操作
location / {
    if ($http_user_agent ~* "bot") {
        proxy_pass http://bot_backend;  # 行为不可预测
    }
    proxy_pass http://normal_backend;
}

# ✅ 方案一：用多个 server 块替代基于 Host 的 if
server {
    server_name www.example.com;
    return 301 $scheme://example.com$request_uri;
}
server {
    server_name example.com;
    # ... 正常配置
}

# ✅ 方案二：用 error_page + 命名 location 替代
location / {
    error_page 418 = @bot;
    if ($http_user_agent ~* "bot") {
        return 418;
    }
    proxy_pass http://normal_backend;
}

location @bot {
    proxy_pass http://bot_backend;
}

# ✅ 方案三：用 map 替代 if 变量判断
map $http_user_agent $is_bot {
    default 0;
    ~*bot 1;
}
```

> **参考文档**：[15-rewrite重写规则.md](05-安全与传输/15-rewrite重写规则.md)

### #1.8 root 放在 location 内导致未匹配 location 无根目录

**现象**：新增一个 location 忘了写 root，该 location 请求 404 或用了默认路径。

**原因**：root 应放 server 层级继承；每个 location 重复写 root 时，漏写的 location 会落到默认值。

**解决方案**：

```nginx
server {
    root /var/www/html;  # ✅ 在 server 块顶部写一次 root

    location / {
        # 继承 server 的 root
        try_files $uri $uri/ /index.html;
    }

    location /static/ {
        # 需要不同路径时再覆盖
        root /var/www/static;
    }
}
```

### #1.9 把所有请求都交给后端（包括静态资源）

**现象**：图片/CSS/JS 也经过 PHP/后端处理，性能极差。

**原因**：`location / { fastcgi_pass ...; }` 把一切请求都代理出去。

**解决方案**：

```nginx
# ✅ 让 Nginx 优先直接服务静态文件，命中不了再代理
location / {
    try_files $uri $uri/ @proxy;
}

location @proxy {
    proxy_pass http://backend;
}

# 也可以单独分流静态资源
location ~* \.(js|css|png|jpg|gif|ico|svg|woff2?)$ {
    root /var/www/static;
    expires 30d;
    access_log off;
}
```

### #1.10 rewrite 缺少 http:// 前缀

**现象**：`rewrite ^ example.com permanent;` 被当作相对路径，重定向到 `http://当前域名/example.com`。

**原因**：rewrite 不带 `http://` 或 `https://` 前缀时是相对重写。

**解决方案**：

```nginx
# ❌ 错误
rewrite ^ example.com permanent;

# ✅ 正确
rewrite ^ http://example.com permanent;

# ✅ 更推荐用 return
return 301 http://example.com$request_uri;
```

---

### #1.11 含下划线的请求头被静默丢弃

**现象**：自定义头 `X_My_Header` 在后端收不到，但 `X-My-Header` 可以。

**原因**：默认 `underscores_in_headers off`，Nginx 静默丢弃带下划线的头（为避免映射到 CGI 变量时的歧义）。

**解决方案**：

```nginx
http {
    underscores_in_headers on;  # 允许下划线请求头
    # 或修改后端/客户端用连字符命名
}
```

### #1.12 alias 下 SCRIPT_FILENAME 拼接出错

**现象**：`location /api/ { alias /app/www/; ... fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name; }` 请求 `/api/test.php` 时得到错误路径 `/app/www//api/test.php`。

**原因**：alias 下 `$document_root` 指向 alias 路径，再拼 `$fastcgi_script_name`（含 `/api/`）会重复。

**解决方案**：

```nginx
location /api/ {
    alias /app/www/;
    # ✅ 改用 $request_filename
    fastcgi_param SCRIPT_FILENAME $request_filename;
    fastcgi_pass unix:/var/run/php-fpm.sock;
}
```

## 二、性能类坑点

### #2.1 worker_processes 设置不当

**现象**：CPU 利用不均或进程数过多导致上下文切换开销大。

**原因**：`worker_processes` 决定 worker 进程数，过多无益反而争抢 CPU。

**解决方案**：

```nginx
# 设为 CPU 核心数，或直接让 Nginx 自动判断
worker_processes auto;

# 可配合 worker_cpu_affinity 绑核（2 核示例）
# worker_cpu_affinity 01 10;
```

> **参考文档**：[19-性能调优.md](06-高级与优化/19-性能调优.md)

---

### #2.2 worker_connections 与最大连接数计算错误

**现象**：以为 `worker_processes * worker_connections` 就是最大客户端数，实际作为反向代理时连接数打对折甚至 1/4。

**原因**：反向代理场景每个客户端会占用两条连接（客户端→Nginx、Nginx→后端），且 keepalive 还会占用连接。理论公式为 `worker_processes * worker_connections / 4`（保守估计）。

**解决方案**：

```nginx
events {
    worker_connections 65535;  # 单 worker 最大连接数
}

# 同时提升系统文件描述符上限
# worker_rlimit_nofile 65535;

# 系统层面（/etc/security/limits.conf）：
# *  soft  nofile  65535
# *  hard  nofile  65535
# 并执行 ulimit -n 65535
```

---

### #2.3 未启用 upstream keepalive（长连接复用）

**现象**：Nginx 到后端每个请求都新建 TCP 连接，后端出现大量 TIME_WAIT，QPS 上不去。

**原因**：旧版 Nginx 默认到上游用短连接，连接建立/关闭开销大。

**解决方案**：

```nginx
upstream backend {
    server 127.0.0.1:8080;
    keepalive 32;  # 每个 worker 的空闲长连接数
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;          # > 1.29.7 起默认 1.1
        proxy_set_header Connection "";  # > 1.29.7 起默认已清理
    }
}
```

> **注意**：`keepalive` 限制的是每个 worker 的**空闲**长连接数，不是总连接数，设过大会压垮后端。可配 `keepalive_requests`、`keepalive_time`、`keepalive_timeout` 控制连接生命周期。

---

### #2.4 客户端 keepalive 未合理配置

**现象**：高并发短请求下大量 TIME_WAIT 堆积。

**原因**：`keepalive_timeout` 设为 0 或过小，连接无法复用。

**解决方案**：

```nginx
http {
    keepalive_timeout 75s;      # 客户端长连接超时（默认 75s，0 为关闭）
    keepalive_requests 1000;    # 单连接最大请求数（默认 1000）
}
```

> **补充**：配合内核参数 `net.ipv4.tcp_tw_reuse = 1` 缓解 TIME_WAIT。

---

### #2.5 proxy buffer 过小导致落盘或响应被截断

**现象**：后端响应较大时，Nginx 写入临时文件磁盘 IO 飙升；或首部超过 buffer 被判为 invalid header。

**原因**：`proxy_buffer_size`（读响应首部）、`proxy_buffers`（读响应体）、`proxy_busy_buffers_size` 默认较小（4k/8k），大响应会落临时文件。

**解决方案**：

```nginx
location / {
    proxy_pass http://backend;
    proxy_buffer_size 16k;        # 响应首部缓冲
    proxy_buffers 8 16k;          # 响应体缓冲（8 块 × 16k）
    proxy_busy_buffers_size 32k;  # 忙时缓冲

    # SSE/流式响应关闭缓冲
    # proxy_buffering off;
}
```

### #2.6 文件描述符 / sendfile 限制

**现象**：高并发报 `too many open files`。

**原因**：系统 ulimit 与 `worker_rlimit_nofile` 不足。

**解决方案**：

```nginx
# nginx.conf
worker_rlimit_nofile 65535;

events {
    worker_connections 65535;
}

http {
    # 静态文件传输开启 sendfile（零拷贝）
    sendfile on;
    # 大文件开启 tcp_nopush（配合 sendfile）
    tcp_nopush on;
}
```

> **特例**：VirtualBox 虚拟机内 sendfile 可能有问题，需 `sendfile off;`。

## 三、安全类坑点

### #3.1 暴露 Nginx 版本号

**现象**：错误页/响应头显示 `nginx/1.30.4`，便于攻击者针对性利用。

**原因**：默认 `server_tokens on`。

**解决方案**：

```nginx
http {
    server_tokens off;  # 隐藏版本号，只显示 nginx
}
```

---

### #3.2 危险的 document root（目录穿越/任意文件读取）

**现象**：请求 `/etc/passwd` 居然返回了系统文件内容。

**原因**：把 `root /;` 或 root 设为根目录，配合 try_files 当文件找不到时交给后端执行，导致任意路径文件被读取/执行。

**解决方案**：

```nginx
# ❌ 永远不要这样做
# root /;
# root /root;

# ✅ 使用专用目录
root /var/www/html;
# 或 /srv/www /usr/share/www

# 永远不要 chmod 777 站点目录
```

---

### #3.3 把任意 .php 请求交给 PHP-FPM（远程代码执行）

**现象**：请求 `/forum/avatar/123.jpg/file.php`（图片存在）时，PHP 执行了该图片，若图片内含 PHP 代码即被任意执行。

**原因**：`location ~ \.php$ { fastcgi_pass ...; }` 把所有 .php 交给后端，而 PHP 默认 `cgi.fix_pathinfo` 会"猜"路径执行。

**解决方案**（任选组合）：

```nginx
# 1. php.ini 设置 cgi.fix_pathinfo=0

# 2. Nginx 侧用 try_files 过滤不存在的文件
location ~ \.php$ {
    try_files $uri =404;
    fastcgi_pass unix:/var/run/php-fpm.sock;
    # ...
}

# 3. 上传目录禁止执行 PHP
location ^~ /uploads/ {
    location ~ \.php$ {
        return 403;
    }
}

# 4. 嵌套 location 过滤路径穿越式 .php
location ~ \..*/.*\.php$ {
    return 404;
}
```

---

### #3.4 SSRF / proxy_pass 可被用户控制的变量影响

**现象**：`proxy_pass $arg_target;` 把用户可控变量直接拼到上游地址，导致内网探测（SSRF）。

**原因**：proxy_pass 支持变量，若变量来自请求参数/头部，攻击者可让 Nginx 代理到任意内网地址。

**解决方案**：

```nginx
# ❌ 危险：用户可控变量直接作为上游地址
location /proxy {
    proxy_pass $arg_target;
}

# ✅ 对上游做白名单校验，或用 map 限定
map $arg_target $upstream {
    default "";
    "api1" "http://10.0.0.1:8080";
    "api2" "http://10.0.0.2:8080";
}

location /proxy {
    proxy_pass $upstream;
}
```

---

### #3.5 不当的 proxy_set_header / Host 头问题

**现象**：后端拿到的 Host 是上游 IP（`$proxy_host`）而非用户访问的域名，导致基于 Host 的路由/虚拟主机/签名校验失效。

**原因**：proxy_set_header 默认 `Host $proxy_host`（上游地址），不显式设置则不传递客户端信息。

**解决方案**：

```nginx
location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;                    # 传递用户访问的域名
    proxy_set_header X-Real-IP $remote_addr;        # 客户端真实 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 转发链
    proxy_set_header X-Forwarded-Proto $scheme;     # 原始协议
}
```

> **注意**：header 在 http→server→location 间有继承规则，location 层再 set 会覆盖（非追加）server 层的设置。

---

### #3.6 不信任 X-Forwarded-For 链

**现象**：后端直接取 XFF 第一个值做 IP 鉴权，被攻击者伪造头绕过。

**原因**：XFF 可被客户端伪造，Nginx 用 `$proxy_add_x_forwarded_for` 是"追加"而非"重置"。

**解决方案**：

```nginx
# 边缘 Nginx（最外层）应重置 XFF 为真实直连 IP
location / {
    proxy_pass http://backend;
    proxy_set_header X-Forwarded-For $remote_addr;  # 重置而非追加
}
# 后端从可信代理链最右侧取值
```

---

### #3.7 alias 目录穿越

**现象**：`location /files { alias /data/files/; }`（location 无尾斜杠而 alias 有），请求 `/files../etc/passwd` 可能穿越。

**原因**：alias 与 location 的尾斜杠不匹配会留下路径拼接漏洞。

**解决方案**：

```nginx
# location 与 alias 末尾斜杠保持一致
location /files/ {
    alias /data/files/;  # 都带尾斜杠
}
# 或用 root 替代
location /files/ {
    root /data;  # /data/files/xxx
}
```

## 四、HTTPS/TLS 类坑点

### #4.1 证书链不完整（中间证书缺失）

**现象**：浏览器报 `NET::ERR_CERT_AUTHORITY_INVALID`，部分客户端（Android/旧 Java）校验失败，但桌面 Chrome 正常。

**原因**：`ssl_certificate` 只配了服务器证书，未包含中间证书。

**解决方案**：

```bash
# 把服务器证书 + 中间证书合并成一个文件（服务器证书在前）
cat server.crt intermediate.crt > fullchain.crt
```

```nginx
ssl_certificate /etc/nginx/ssl/fullchain.crt;
ssl_certificate_key /etc/nginx/ssl/server.key;
```

```bash
# 验证证书链
openssl s_client -connect example.com:443 -servername example.com
```

> **参考文档**：[14-HTTPS与TLS配置.md](05-安全与传输/14-HTTPS与TLS配置.md)

---

### #4.2 未启用 HSTS

**现象**：用户用 HTTP 访问可被中间人降级，即使有 HTTPS。

**原因**：未下发 `Strict-Transport-Security` 头。

**解决方案**：

```nginx
server {
    listen 443 ssl;
    # ... SSL 配置 ...

    # 确认全站 HTTPS 后再启用，否则会"锁死"HTTP 资源
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}
```

---

### #4.3 混合内容（Mixed Content）

**现象**：HTTPS 页面引用 HTTP 资源，浏览器报错并阻断加载。

**原因**：页面内静态资源仍用 `http://` 链接。

**解决方案**：

```nginx
# 资源改用 https:// 或相对协议 //
# 开启 HSTS 后浏览器会自动将同域 HTTP 资源升级为 HTTPS

# 对跨域 HTTP 接口用 Nginx 反向代理成同域 HTTPS
location /external-api/ {
    proxy_pass http://external-service/;  # 内部代理，对外仍是 HTTPS
}
```

---

### #4.4 OCSP Stapling 未启用

**现象**：客户端校验证书时需联网查 OCSP，慢且可能泄露隐私。

**解决方案**：

```nginx
ssl_stapling on;
ssl_stapling_verify on;
ssl_trusted_certificate /etc/nginx/ssl/chain.crt;  # 含中间证书
resolver 8.8.8.8 valid=300s;   # OCSP 解析需要 resolver
resolver_timeout 5s;
```

---

### #4.5 TLS 协议与加密套件过旧

**现象**：仍启用 SSLv3/TLS1.0/1.1，存在 POODLE/BEAST 等风险；SSL Labs 评分低。

**解决方案**：

```nginx
# 仅启用 TLS1.2/1.3
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
ssl_prefer_server_ciphers off;  # TLS1.3 下建议 off
```

---

### #4.6 HTTP/2 配置坑（listen 与 http2 指令）

**现象**：旧写法 `listen 443 ssl http2;` 在新版可能告警。

**原因**：自 Nginx 1.25.1 起，HTTP/2 改用独立指令 `http2 on;`，旧 `listen ... http2` 参数被弃用。

**解决方案**：

```nginx
# 1.25.1+ 新写法
server {
    listen 443 ssl;
    http2 on;  # 独立指令
    # ...
}

# 旧写法（1.25.0 及以下）
# listen 443 ssl http2;  # 已弃用
```

> **版本提示**：HTTP/2 要求 TLS（h2 over TLS）。

## 五、负载均衡/反向代理类坑点

### #5.1 upstream 被动健康检查误判

**现象**：后端宕机后仍持续把请求转过去，过一会才剔除；或偶发错误被误判下线。

**原因**：开源版 Nginx 只有**被动**健康检查，靠 `max_fails`（默认 1）+ `fail_timeout`（默认 10s）统计失败。默认 `max_fails=1` 太敏感，一次失败即下线 10s。

**解决方案**：

```nginx
upstream backend {
    server backend1:8080 max_fails=3 fail_timeout=30s;  # 3 次失败后下线 30s
    server backend2:8080 max_fails=3 fail_timeout=30s;
}
```

> **说明**：主动健康检查需 NGINX Plus 的 `health_check` 或第三方模块 `nginx_upstream_check_module`。

> **参考文档**：[10-upstream负载均衡算法.md](04-反向代理与负载均衡/10-upstream负载均衡算法.md)

---

### #5.2 单台后端时 max_fails/fail_timeout 失效

**现象**：upstream 只有一台 server，宕机了 Nginx 还是不断重试、不剔除。

**原因**：官方文档明确——只有一台 server 时 `max_fails`、`fail_timeout`、`slow_start` 被忽略，该 server 永远不会被标记为不可用。

**解决方案**：

```nginx
# 至少加一台 backup，或用 proxy_next_upstream 配合重试
upstream backend {
    server primary:8080 max_fails=3 fail_timeout=30s;
    server backup:8080 backup;  # 主节点宕机时启用
}
```

---

### #5.3 WebSocket 代理未升级协议头

**现象**：WebSocket 连接立即断开或 101 切换失败。

**原因**：代理 WebSocket 需要把 `Upgrade`/`Connection` 头透传给后端，且用 HTTP/1.1。

**解决方案**：

```nginx
location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;  # 长连接避免被默认 60s 超时断开
}
```

> **注意**：开了 upstream keepalive 时，WebSocket 所在 location 不要 `proxy_set_header Connection ""`，否则与 Upgrade 冲突。

> **参考文档**：[12-WebSocket代理.md](04-反向代理与负载均衡/12-WebSocket代理.md)

---

### #5.4 后端拿不到真实客户端 IP

**现象**：后端日志/鉴权看到的都是 Nginx 的内网 IP。

**原因**：未传递 X-Real-IP / X-Forwarded-For，或后端未配置信任代理。

**解决方案**：

```nginx
# Nginx 侧
location / {
    proxy_pass http://backend;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

```python
# Python（Flask 示例）需配置 ProxyFix
from flask import Flask
from werkzeug.middleware.proxy_fix import ProxyFix
app = Flask(__name__)
app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1)
```

```java
// Java（Spring Boot）需配置
// application.properties
// server.forward-headers-strategy=NATIVE
```

---

### #5.5 upstream keepalive 与负载均衡方法顺序（旧版）

**现象**：旧版 Nginx 配 `ip_hash`/`least_conn` 后 keepalive 不生效或报错。

**原因**：1.29.7 前，使用非默认 round-robin 的负载均衡方法时，必须先声明该方法再写 `keepalive`。

**解决方案**：

```nginx
upstream backend {
    ip_hash;          # 先声明负载均衡方法
    server backend1:8080;
    server backend2:8080;
    keepalive 32;     # 再写 keepalive
}
# 1.29.7+ 已默认开启 keepalive，顺序不再强制
```

> **版本提示**：Nginx 1.29.7 起默认开启 upstream keepalive。

---

### #5.6 长连接复用导致后端连接数被压垮

**现象**：`keepalive 1000;` 设过大，后端连接池被打满。

**原因**：`keepalive` 限制的是每个 worker 的空闲缓存连接，不是总连接数；设过大后端无法处理新连接。

**解决方案**：

```nginx
upstream backend {
    server backend1:8080;
    keepalive 32;  # 设为后端可接受的小值（16-64）
    keepalive_requests 1000;  # 单连接最大请求数
    keepalive_time 1h;        # 单连接最大存活时间
    keepalive_timeout 60s;    # 空闲超时
}
```

---

### #5.7 proxy_next_upstream 导致非幂等请求被重试

**现象**：POST 请求在后端超时后被重试到另一台，造成重复提交。

**原因**：`proxy_next_upstream` 默认对 error/timeout 重试，可能把非幂等请求重复发送。

**解决方案**：

```nginx
location /api/ {
    proxy_pass http://backend;
    # 写接口（POST/PUT/DELETE）禁止重试
    proxy_next_upstream off;
    # 或只在 error 时重试（不含 timeout）
    # proxy_next_upstream error;
}
```
