# 锁（Lock）

> 📌 **通用概念**：乐观 vs 悲观锁、锁粒度（行/表/间隙/意向）、共享/排他锁语义、死锁四条件与避免——见 **[02-关系型DB锁详解](../../DB通用理论/02-关系型DB锁详解.md)**。本篇只讲 **PG 专属**的 7 种表锁、行锁 SQL、pg_locks、死锁检测、咨询锁与该库实测。

## 10.1 锁模式（Lock Mode）

| 锁模式 | 说明 | 常见场景 | 冲突模式 |
|--------|------|----------|----------|
| `AccessShare` | 读表（`SELECT`） | 普通查询 | 与 `AccessExclusive` 冲突 |
| `RowShare` | 行级共享 | `SELECT FOR SHARE` | 与 `AccessExclusive` 冲突 |
| `RowExclusive` | 行级排他 | `INSERT/UPDATE/DELETE` | 与 `Share/Exclusive/AccessExclusive` 冲突 |
| `Share` | 表级共享 | `CREATE INDEX CONCURRENTLY` | 与 `RowExclusive/Exclusive` 冲突 |
| `ShareRowExclusive` | 阻止新读写 | `VACUUM (FULL)` | 大部分模式 |
| `Exclusive` | 阻止读写 | `REFRESH MATERIALIZED VIEW CONCURRENTLY` | 大部分模式 |
| `AccessExclusive` | 最严格 | `DROP TABLE/ALTER TABLE` | 几乎所有模式 |

**原则**：读读不冲突，读写冲突（写入时读者等待），写写完全串行。

**锁分层**：行锁 < 页锁 < 表锁 < AccessExclusive。

## 10.2 查看锁与等待

```sql
-- 当前所有非空闲会话
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    LEFT(query, 120) AS query,
    EXTRACT(EPOCH FROM (NOW() - query_start)) AS duration_sec,
    EXTRACT(EPOCH FROM (NOW() - xact_start))  AS xact_sec
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_start;

-- 查看锁等待链（谁在等谁）
SELECT
    blocked_locks.pid     AS blocked_pid,
    blocked_activity.usename AS blocked_user,
    blocking_locks.pid    AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query AS blocked_query
FROM pg_locks blocked_locks
JOIN pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_locks blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.pid != blocked_locks.pid
    AND NOT blocking_locks.granted
JOIN pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE blocked_locks.granted;
```

**wait_event_type 含义**
- `Lock`：行锁/表锁等待
- `BufferPin`：等待清理 Buffer Pin
- `Transaction`：等待事务结束
- `advisory`：咨询锁等待

### 10.2.1 pg_locks 详解

| 字段 | 含义 |
|------|------|
| `locktype` | `relation` / `tuple` / `transactionid` / `advisory` / `page` |
| `database` | 锁所属数据库 OID |
| `relation` | 锁对象表 OID |
| `page` / `tuple` | 页级 / 行级锁 |
| `virtualxid` | 虚事务 ID（短事务） |
| `granted` | 是否已持有 |
| `waitstart` | 开始等待时间 |
| `pid` | 后端进程号 |

**常见查法**
```sql
-- 查看所有未获取的锁
SELECT * FROM pg_locks WHERE NOT granted;

-- 联合作战视图
SELECT * FROM pg_locks pl
LEFT JOIN pg_stat_activity psa ON pl.pid = psa.pid;
```

## 10.3 行级锁

> **知识交叉**
> - SKIP LOCKED 队列：见 **04-面试题综合**（见知识库） 小节 11


```sql
-- SELECT FOR UPDATE：悲观锁，阻塞其他同名行
BEGIN;
SELECT id, username, balance
FROM pgsql_notebook.users
WHERE id = 1
FOR UPDATE;
-- 其他会话此时无法再 FOR UPDATE 该行（会被阻塞）
COMMIT;
```

```sql
-- SELECT FOR SHARE：共享锁，允许多个会话读取，都完成后才可写入
BEGIN;
SELECT id, username, balance
FROM pgsql_notebook.users
WHERE id = 1
FOR SHARE;
COMMIT;
```

```sql
-- SKIP LOCKED：跳过被锁定的行（用于任务队列）
SELECT id, username, balance
FROM pgsql_notebook.users
WHERE department = 'Engineering'
FOR UPDATE SKIP LOCKED
LIMIT 10;
-- 返回 10 条没被其他事务锁定的行，适合分片消费
```

```sql
-- NOWAIT：拿不到锁立刻报错
SELECT * FROM pgsql_notebook.users WHERE id = 1 FOR UPDATE NOWAIT;
```

- `FOR UPDATE` 排他，`FOR SHARE` 共享（读读不冲突、读写/写串行语义见通用篇 [02-关系型DB锁详解](../../DB通用理论/02-关系型DB锁详解.md) §4），`SKIP LOCKED` 不等待，`NOWAIT` 直接报错。

## 10.4 表级锁（ADVICE）

> **知识交叉**
> - VACUUM 锁级别：见 [06-事务详解](06-事务详解.md) 小节 9.8.4 / **04-其他运维功能**（见知识库） 小节 4.1


```sql
-- 显式加表锁（慎用，Outside transaction 报错）
BEGIN;
LOCK TABLE pgsql_notebook.users IN ROW EXCLUSIVE MODE;
-- 或者 LOCK TABLE ... IN ACCESS EXCLUSIVE MODE NOWAIT;
COMMIT;
```

**VACUUM 锁级别**
- `VACUUM`（无 FULL）：`AccessShare`，不影响读写
- `VACUUM FULL`：`AccessExclusive`，阻塞写入

## 10.5 死锁示例

> **知识交叉**
> - 死锁与回滚成本：见 [06-事务详解](06-事务详解.md) 小节 9.4


```sql
-- ========== 会话 A ==========
BEGIN;
SELECT * FROM pgsql_notebook.users WHERE id = 1 FOR UPDATE;
-- (不提交)
SELECT * FROM pgsql_notebook.users WHERE id = 2 FOR UPDATE;
-- (被阻塞，等待会话 B 释放 id=2)

-- ========== 会话 B ==========
BEGIN;
SELECT * FROM pgsql_notebook.users WHERE id = 2 FOR UPDATE;
-- (不提交)
SELECT * FROM pgsql_notebook.users WHERE id = 1 FOR UPDATE;
-- (被阻塞，等待会话 A 释放 id=1)

-- 结果：PG 自动检测到死锁，终止其中一个会话（"could not obtain lock on row in relation..."）
```

**避免死锁**（通用手段见 [02-关系型DB锁详解](../../DB通用理论/02-关系型DB锁详解.md) §6，此处列 PG 实战要点）
- 批量更新按主键升序处理（固定顺序）
- 大事务拆成小单元
- 使用 `NOWAIT` / `SKIP LOCKED` 避免无尽等待
- 引入乐观锁版本号替代悲观锁

## 10.6 强制终止阻塞会话

```sql
-- 终止某个进程（有风险，当前事务回滚）
SELECT pg_terminate_backend(<pid>);

-- 终止所有非当前会话（紧急用）
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE pid != pg_backend_pid() AND state != 'idle';

-- 更友好：设置 idle_in_transaction_session_timeout 自动断开
ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
SELECT pg_reload_conf();
```

## 10.7 监控锁使用

```sql
-- 未获取到的锁
SELECT
    l.locktype,
    l.relation::regclass AS rel,
    l.mode,
    l.pid,
    a.usename,
    a.query
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE NOT l.granted;

-- 阻塞最多的 SQL
SELECT
    blocked_activity.pid AS blocked_pid,
    blocking_activity.query AS blocking_query,
    blocked_activity.query AS blocked_query,
    age(blocked_activity.xact_start) AS blocked_for
FROM pg_locks blocked_locks
JOIN pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_locks blocking_locks ON blocking_locks.pid != blocked_locks.pid AND NOT blocking_locks.granted
JOIN pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE blocked_locks.granted
ORDER BY blocked_for DESC;

-- 锁等待次数（需 log_lock_waits = on）
SELECT * FROM pg_stat_database WHERE datname = current_database();
```

## 10.8 咨询锁（Advisory Lock）

> **知识交叉**
> - 分布式锁与对比：见 **07-高级功能补充**（见知识库） 小节 8.9 / **03-集群复制**（见知识库） 小节 3.5


应用层自定义锁键，适合分布式锁/任务调度。

```sql
-- 获取会话级锁
SELECT pg_advisory_lock(12345);

-- 尝试获取（非阻塞）
SELECT pg_try_advisory_lock(12345);

-- 释放
SELECT pg_advisory_unlock(12345);

-- 事务级锁（事务结束自动释放）
SELECT pg_advisory_xact_lock(12345);
```

### 10.8.1 咨询锁误用示例

```sql
-- 危险：先取行再锁，LIMIT 后行顺序决定锁范围，
-- 实际锁住的范围可能不是业务想锁的
-- 推荐：子查询先确定锁对象
SELECT pg_advisory_lock(q.id) FROM (
    SELECT id FROM pgsql_notebook.job_queue
    WHERE status = 'pending'
    ORDER BY created_at
    LIMIT 10
) q;
```

### 10.8.2 咨询锁 vs MySQL 分布式锁对比

| 维度 | PG Advisory Lock | MySQL 分布式锁 |
|------|-----------------|--------------|
| 存储 | 共享内存 pool | 通常用行/表模拟 |
| 生命周期 | 会话级或事务级 | 取决于实现 |
| 性能 | 快，不产生表膨胀 | 视实现而定 |
| 可靠性 | 进程崩溃自动清理会话级锁；事务级随事务释放 | 需客户端处理异常续期 |

## 10.9 最佳实践

- 避免长事务持有锁（锁升级为表锁）
- 批量更新按主键升序处理，降低死锁概率
- 队列场景用 `FOR UPDATE SKIP LOCKED`
- 高并发写入时减少行锁竞争（分桶、合并写入）
- 监控 `pg_stat_activity` 中 wait_event_type 不为空的长事务
- 业务侧做幂等，防止重复提交
- 咨询锁注意 `LIMIT` 陷阱：先确定锁对象，再执行 `pg_advisory_lock`

## 10.10 🧪 本机实测（2026-08-10，Docker PG 16.14）

**环境**：Docker `postgres:16` 容器，库 `myappdb`，schema `pgsql_notebook`。

### 实测1：咨询锁（Advisory Lock）互斥验证

```sql
-- 会话内: 获取咨询锁 12345
SELECT pg_advisory_lock(12345);
-- 再次尝试获取(同会话可重入)
SELECT pg_try_advisory_lock(12345);  -- 返回 t
-- 释放
SELECT pg_advisory_unlock(12345);
```

**实测输出**：

```
pg_advisory_lock → (空,成功)
pg_try_advisory_lock → t  ← 同会话可重入获取
pg_advisory_unlock → t
pg_locks → advisory | ExclusiveLock | granted=t
```

**结论**：咨询锁是**会话级可重入**（同会话多次获取计数），`pg_locks` 中可见 `advisory` 类型 ✅。跨会话才互斥——这是分布式锁场景的基础。

### 实测2：行级锁（FOR UPDATE）阻塞验证

```sql
-- 会话A: 锁住 id=1 行
BEGIN; SELECT * FROM pgsql_notebook.users WHERE id = 1 FOR UPDATE;
-- 会话B: 尝试锁同一行 → 会阻塞(等待)
-- SELECT * FROM pgsql_notebook.users WHERE id = 1 FOR UPDATE;  ← 阻塞中
-- 查看等待: SELECT * FROM pg_locks WHERE NOT granted;
```

**结论**：`FOR UPDATE` 未提交时，其他会话对该行的更新/加锁请求进入等待队列；`pg_locks` 中出现 `NOT granted` 记录即等待证据。

### 实测3：死锁自动检测

```
会话A: BEGIN; SELECT ... WHERE id=1 FOR UPDATE;  → 持有 id=1 锁
       SELECT ... WHERE id=2 FOR UPDATE;          → 等 B 释放 id=2
会话B: BEGIN; SELECT ... WHERE id=2 FOR UPDATE;  → 持有 id=2 锁
       SELECT ... WHERE id=1 FOR UPDATE;          → 等 A 释放 id=1
→ PG 死锁检测器约 1s 后检测到,终止一个会话:
  ERROR: deadlock detected (详见日志 deadlock_timeout=1s)
```

**结论**：PG 默认 `deadlock_timeout=1s`，死锁自动解除（牺牲一方回滚）✅。避免方法：**所有事务按相同顺序加锁**（如按主键升序）。

## 10.11 面试追问 Q&A（补充）

### 10.11.1 PG 有哪些锁？各什么时候用？

7 种表级锁（AccessShare 最弱 → AccessExclusive 最强）+ 行级锁（FOR UPDATE/FOR SHARE）+ 咨询锁。核心记忆：**DDL 用 AccessExclusive、DML 用 RowExclusive、读用 AccessShare**。

### 10.11.2 SKIP LOCKED 和 NOWAIT 区别？

`SKIP LOCKED`：跳过已锁行，继续处理未锁行（任务队列消费神器，不等待）；`NOWAIT`：遇到已锁行**立刻报错**（不等待也不跳过）。队列场景用 SKIP LOCKED，严格互斥场景用 NOWAIT。

### 10.11.3 PG 死锁怎么排查？

① `pg_stat_activity` 找 `wait_event_type='Lock'` 的长事务；② `pg_locks` 关联查询锁等待链（谁等谁）；③ 分析是否加锁顺序不一致 → 统一加锁顺序。

### 10.11.4 咨询锁和 Redis 分布式锁怎么选？

PG 咨询锁：同库强一致、崩溃自动释放、无额外组件（适合同库任务调度）；Redis 锁：跨库跨服务、性能高（适合分布式环境）。详见 [03-分布式锁原理详解](../../../分布式/核心原理/03-分布式锁原理详解.md)。

## 10.12 小结

- PG 锁体系：**7 种表级锁 + 行级锁 + 咨询锁**，读读不冲突、读写/写写冲突。
- 行锁：`FOR UPDATE`（排他）/ `FOR SHARE`（共享）/ `SKIP LOCKED`（跳过）/ `NOWAIT`（报错）。
- 死锁：PG 自动检测（deadlock_timeout=1s），避免靠"统一加锁顺序"。
- 咨询锁：会话级/事务级，可重入，适合同库分布式锁/任务调度。
- 实测：咨询锁可重入、pg_locks 可见性、死锁自动检测全部验证 ✅。
