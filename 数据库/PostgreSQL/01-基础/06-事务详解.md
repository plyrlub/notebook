# 事务（Transaction）

## 9.1 ACID 特性详解

| 特性 | 说明 | PG 实现 |
|------|------|---------|
| Atomicity | 原子性：全部成功 or 全部失败 | 事务日志（WAL） |
| Consistency | 一致性：事务前后完整性 | 约束/触发器保障 |
| Isolation | 隔离：并发不干扰 | MVCC + 锁 |
| Durability | 持久：提交不丢 | WAL + fsync |

**ACID 缺一不可**：D 保证进程崩溃不丢数据，I 保证并发行不串行。

## 9.2 自动提交模式

> **知识交叉**
> - psql 脚本行为：见 **02-库表操作与约束**（见知识库） 小节 4.1


**PostgreSQL 默认自动提交**。每条独立的 DML/DDL 语句都包装在隐式事务中，执行后自动提交，无法回滚。

```sql
-- 这是两条独立事务
INSERT INTO pgsql_notebook.users (username, email) VALUES ('tx1', 'tx1@example.com');
UPDATE pgsql_notebook.users SET balance = 100 WHERE username = 'tx1';
-- 第一条插入成功，第二条更新失败，第一条不回滚
```

**psql 特殊情况**
- `BEGIN` 开始显式事务
- `\o` / `\i` 脚本中每句默认自动提交，除非显式 `BEGIN`

## 9.3 手动事务

```sql
-- 开始事务
BEGIN;
-- 或 BEGIN TRANSACTION

-- 执行操作
UPDATE pgsql_notebook.users SET balance = balance + 100 WHERE id = 1;
UPDATE pgsql_notebook.users SET balance = balance - 100 WHERE id = 2;

-- 提交（永久生效）
COMMIT;
-- 或 END
```

**隐式与显式混用陷阱**：如果前面已经执行了 SELECT 等自动提交语句，这里 BEGIN 实际上开始新事务。推荐每条事务块开头对齐。

## 9.4 回滚（ROLLBACK）

```sql
BEGIN;

UPDATE pgsql_notebook.users SET balance = balance - 9999 WHERE id = 1;
-- 发现错误，回滚
ROLLBACK;

-- 回滚后 balance 恢复到 BEGIN 之前的值
```

**ROLLBACK 成本**：回滚的事务不会清理写入的 temp 文件，长时间事务回滚会导致 temp 堆积和 IO 峰。

## 9.5 保存点（SAVEPOINT）

> 📌 保存点是事务内「部分回滚」的通用概念，PG 的实现见下方 SQL。概念（为什么需要/嵌套保存点/与 NESTED 的关系）见 **[01-关系型DB事务详解](../../DB通用理论/01-关系型DB事务详解.md) §6**。

保存点允许 Partial Rollback，只回滚部分操作（PG SQL 写法）：

```sql
BEGIN;

UPDATE pgsql_notebook.users SET balance = balance + 10 WHERE id = 1;
UPDATE pgsql_notebook.users SET balance = balance + 10 WHERE id = 2;

SAVEPOINT sp1;  -- 设置保存点

UPDATE pgsql_notebook.users SET balance = balance - 200 WHERE id = 1;
-- 发现错误，只回滚 sp1 之后的

ROLLBACK TO SAVEPOINT sp1;
-- 现在 balance = 100.00 + 10.00（只撤销了减 200）

-- 继续或提交
COMMIT;
```

**嵌套保存点**：可设多个，只回滚到最近保存点。

## 9.6 事务隔离级别

> 📌 隔离级别的四级别定义与三异常（脏读/不可重复读/幻读）是**通用概念**，见 **[01-关系型DB事务详解](../../DB通用理论/01-关系型DB事务详解.md) §4 / §5**。本节只讲 PG 特有的语法、默认值与本机实测。

**PG 特有要点**：
- PG 默认 **Read Committed**（快照每语句刷新）。
- PG 的 `Read Uncommitted` **映射为 Read Committed**——架构上无脏读（见 §9.10.1），与 MySQL 的真脏读不同。
- PG 支持 `Repeatable Read` / `Serializable`（SSI），需事务内显式设置或改配置。

```sql
-- 查看当前隔离级别
SHOW transaction_isolation;

-- 事务内设置（仅当前事务生效）
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM pgsql_notebook.users WHERE age = 25;
-- 同一事务内再次查询结果一致（MVCC 快照不变）
COMMIT;

-- 可串行化（严格但可能报错：could not serialize access）
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- 事务中出现写冲突或依赖环时 PG 抛异常，应用层需重试
COMMIT;
```

**各场景推荐（PG 视角）**
- 通用场景：`Read Committed`（PG 默认，吞吐最高）
- 金融/支付：`Repeatable Read` 或 `Serializable`（写冲突敏感、可接受重试）
- 报表/分析：允许部分脏数据时可用 `Read Committed`

## 9.7 两阶段提交（2PC）

> **知识交叉**
> - 分布式事务与复制：见 **03-集群复制**（见知识库） 小节 3.6


PostgreSQL 支持分布式事务的 Prepare + Commit 两阶段：

```sql
-- 准备提交（阻塞，资源已锁定）
PREPARE TRANSACTION 'tx1';

-- 提交已准备好的事务
COMMIT PREPARED 'tx1';

-- 回滚已准备好的事务
ROLLBACK PREPARED 'tx1';

-- 查看已准备事务
SELECT * FROM pg_prepared_xacts;
```

**限制**
- 事务中不能有临时表
- 不能有持有中的 advisory 锁
- prepare 后直到 commit/rollback 会一直持有锁和 WAL

## 9.8 MVCC 与可见性

> 📌 **通用概念**：MVCC 是什么/为什么（多版本、读写不互阻塞）、两大方案（PG vs MySQL undo）、快照机制见 **[03-关系型DB-MVCC详解](../../DB通用理论/03-关系型DB-MVCC详解.md)**。
> 📌 **原理深挖**：这篇讲 MVCC 用法与入门，底层机制（页面/元组布局、hint bits、Visibility Map、HOT 更新、clog、快照构建、VACUUM 内部、膨胀链路）见 **[03-MVCC深入原理](../02-设计原理/03-MVCC深入原理.md)**。

MVCC（多版本并发控制）是 PG 核心：修改不直接覆盖旧版本，而是插入新版本，旧版本留给发起更早的事务看（PG 侧实现见下）。

### 9.8.1 行版本结构

| 隐藏字段 | 含义 |
|---------|------|
| `xmin` | 插入该行的事务 ID |
| `xmax` | 删除/更新该行的事务 ID（0 表示当前存活） |
| `cmin/cmax` | 同一事务内命令号（0 开始计数） |
| `cmax` | 当前事务内创建该版本的命令号 |

### 9.8.2 可见性判断规则

1. 取当前事务快照：`(xmin, xmax)` 活跃事务 ID 范围
2. 对某行：
   - 如果 `xmin` 在当前快照中，且 `xmax=0`，则该行对当前事务可见
   - 如果 `xmax` 等于当前事务 ID，则该行已被本事务删除，不可见
   - 如果 `xmin` 在当前快照前的已提交事务，且 `xmax` 不在活跃范围内，可见
3. `HEAP` 页上每条记录都有 `t_infomask`，标记可见性状态，减少判断开销

```sql
-- 查看行版本
SELECT xmin, xmax, * FROM pgsql_notebook.users WHERE id = 1;

-- 当前事务快照
SELECT txid_current(), txid_current_snapshot();
```

### 9.8.3 快照

```sql
-- 查看当前事务 ID
SELECT txid_current();

-- 事务开始时间（与快照有关）
SELECT txid_current_snapshot();
```

- `READ COMMITTED`：每条 SQL 重新取快照
- `REPEATABLE READ` / `SERIALIZABLE`：事务开始时拍一张快照，全程复用

### 9.8.4 VACUUM 清理

> **知识交叉**
> - 膨胀与性能：见 **01-性能优化**（见知识库） 小节 3.3 / **04-其他运维功能**（见知识库） 小节 4.1


```sql
-- 查看死行比例
SELECT relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_pct
FROM pg_stat_user_tables
WHERE schemaname = 'pgsql_notebook'
ORDER BY dead_pct DESC;

-- 手动触发
VACUUM VERBOSE pgsql_notebook.users;
```

### 9.8.5 事务 ID 回卷保护

- XID 是 32 位整数，约 20 亿次后会回卷
- PG 每 10 亿次自动执行一次 `VACUUM FREEZE`，把旧 XID 替换为 `FrozenXID`
- 监控：`SELECT datfrozenxid, age(datfrozenxid) FROM pg_database WHERE datname = current_database();`

### 9.8.6 只读事务优化

```sql
-- 只读事务起自事务开始拍快照，不持有 XID 写锁
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT * FROM pgsql_notebook.users WHERE age BETWEEN 20 AND 30;
COMMIT;
```

- 只读事务在 `hot_standby_feedback=on` 下可安全跑在备库
- 不产生 WAL，不阻塞 autovacuum

### 9.8.7 延迟约束

```sql
-- 批量导入时推迟约束检查到 COMMIT
SET CONSTRAINTS ALL DEFERRED;
-- 事务结束统一检查，避免中途失败
COMMIT;
```

### 9.8.8 SSI 与真串行化

> **知识交叉**
> - 串行化与锁竞争：见 [07-锁详解](07-锁详解.md) 小节 10.5


- PG9.1 起实现 `Serializable Snapshot Isolation（SSI）`
- 通过检测 RW 冲突图中有无环来判断是否可串行化
- 若有环则报错：`could not serialize access`
- 代价：比 Repeatable Read 略慢，因为有依赖性检查开销

```
灾难性事务示例（SSI 会报错并终止）：
Tx1: UPDATE users SET balance = balance - 100 WHERE user_id = 1;
Tx2: UPDATE users SET balance = balance + 100 WHERE user_id = 2;
Tx1: UPDATE users SET balance = balance + 100 WHERE user_id = 2;  -- 冲突点
Tx2: UPDATE users SET balance = balance - 100 WHERE user_id = 1;
```

### 9.8.9 MVCC vs MySQL InnoDB 对比

> 📌 完整对比表已迁移至通用篇 **[03-关系型DB-MVCC详解](../../DB通用理论/03-关系型DB-MVCC详解.md) §2**（两套方案对比表）。此处仅留 PG 侧一句话口诀：

> **PG = 堆表多留旧版 + VACUUM 清理**；MySQL = undo log 回滚段 + purge 清理。PG 靠 xmin/xmax 旧行标记，MySQL 原地更新记 undo——方向相反，殊途同归。

（PG 侧更多底层差异——VM/HOT/clog 与 InnoDB 的对照——见 [03-MVCC深入原理](../02-设计原理/03-MVCC深入原理.md) §10。）

### 9.8.10 最佳实践

| 建议 | 原因 |
|------|------|
| 事务尽量短 | 减少锁持有，避免阻塞 vacuum |
| 避免用户交互在事务中 | 长事务导致膨胀 |
| 监控长事务 | `SELECT pid, now() - xact_start FROM pg_stat_activity WHERE state='active' AND now() - xact_start > interval '1 minute';` |
| 批量导入时 `SET CONSTRAINTS ALL DEFERRED` | 减少中途失败 |
| 报表用只读事务 | 减少写入开销 |
| 频繁冲突场景用 `SKIP LOCKED` | 避免死锁/长时间等待 |

## 9.9 🧪 本机实测（2026-08-10，Docker PG 16.14）

**环境**：Docker `postgres:16` 容器，库 `myappdb`，schema `pgsql_notebook`。

### 实测1：默认隔离级别

```sql
SHOW transaction_isolation;
```

**实测输出**：

```
transaction_isolation
----------------------
 read committed
```

**结论**：PG 默认 **Read Committed** ✅（与官方文档一致）。

### 实测2：MVCC 行版本可见字段

```sql
SELECT xmin, xmax, id, username FROM pgsql_notebook.users WHERE id = 1;
```

**实测输出**：

```
 xmin | xmax | id | username
------+------+----+----------
  848 |  881 |  1 | user_1
```

**解读**：`xmin=848`（行由事务 848 插入）、`xmax=881`（行被事务 881 更新过，旧版本标记失效）——这正是 MVCC"新版本插入、旧版本靠 xmax 标记"的直接证据 ✅。

### 实测3：事务 ID 与快照

```sql
SELECT txid_current(), txid_current_snapshot();
```

**实测输出**：

```
 txid_current | txid_current_snapshot
--------------+-----------------------
          896 | 896:896:
```

**解读**：当前事务 ID=896；快照 `896:896:` 表示"活跃事务只有 896 自己"（格式：`xmin:xmax:活跃列表`）✅。

### 实测4：事务 ID 回卷保护状态

```sql
SELECT datfrozenxid, age(datfrozenxid) FROM pg_database WHERE datname = 'myappdb';
```

**实测输出**：

```
 datfrozenxid | age
--------------+-----
          723 | 174
```

**解读**：冻结水位 723，当前年龄 174（远低于 20 亿阈值），无回卷风险 ✅。`age()` 监控是生产必查项。

## 9.10 面试追问 Q&A（补充）

### 9.10.1 PG 的 Read Uncommitted 为什么等于 Read Committed？

PG 的 MVCC 实现下，**脏读在架构上就不可能发生**（读只看到已提交版本），所以 Read Uncommitted 直接映射为 Read Committed——这是 PG 与 MySQL 的重要差异（MySQL 的 RU 是真脏读）。

### 9.10.2 长事务有什么危害？怎么发现？

长事务阻塞 autovacuum 清理死元组 → 表膨胀 → 查询变慢、磁盘暴涨。发现：

```sql
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE now() - xact_start > interval '1 minute';
```

### 9.10.3 事务隔离级别怎么选？

- 默认 RC（吞吐最高）——通用业务。
- RR（事务内快照一致）——金融对账、需要事务内多次读一致。
- Serializable（SSI 真串行）——写冲突敏感场景，接受"冲突报错重试"代价。

### 9.10.4 PREPARE TRANSACTION 有什么用？

分布式事务（2PC）的参与者协调：事务先 PREPARE（持锁待命），协调者确认后 COMMIT PREPARED。注意：`max_prepared_transactions` 默认 0（禁用），用 XA 需先开启——这与 [04-分布式事务详解](../../../分布式/核心原理/04-分布式事务详解.md) 的 XA 模式对应。

## 9.11 小结

- PG 默认 **Read Committed**（快照每句刷新）；RR 事务首快照；Serializable 用 SSI 检测冲突。
- MVCC：行有 `xmin/xmax` 标记版本，读不阻塞写、写不阻塞读；旧版本靠 VACUUM 清理。
- 2PC：`PREPARE TRANSACTION` + `COMMIT PREPARED` 支持分布式事务。
- 长事务 → 膨胀；事务 ID → 回卷保护（VACUUM FREEZE）。
- 实测：隔离级别 RC、xmin/xmax 可见、快照格式 `xmin:xmax:active` 全部验证 ✅。
