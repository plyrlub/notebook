# 关系型数据库 MVCC 详解

> **一句话记忆**：MVCC（Multi-Version Concurrency Control，多版本并发控制）= 让同一行数据同时存在多个历史版本，每个事务看到自己"应该看到"的版本，从而实现**读不阻塞写、写不阻塞读**。PG 靠堆表多留旧版，MySQL 靠 undo log 存旧版——方向相反，殊途同归。

**本篇定位**：DB 通用理论层——讲清 MVCC **是什么/为什么/两套方案/快照概念/各库差异**这些通用概念与跨库对比。某库的内部实现（PG 元组头/VM/HOT/clog/VACUUM，MySQL undo/purge/Read View/Next-Key）在各库笔记详述，MySQL 尚以占位块标注待补充。

## 1. MVCC 是什么、为什么

**是什么**：MVCC 让同一行数据同时存在多个版本，每个事务通过**快照**只看到"对自己可见的版本"。

**为什么（读不阻塞写的根因）**：
- **写操作**（INSERT/UPDATE/DELETE）只是**新增一个新版本**、把旧版本标记作废，**不改动已存在的版本内容**。
- **读操作**按快照规则挑版本，**不加锁**。
- 因此读和写**完全不碰同一份数据**，自然互不等待——这就是"读不阻塞写、写不阻塞读"的根本原因。

**一句话类比**（共同编辑文档）：每个人看到的都是"自己打开时那版"，别人怎么改都不影响自己阅读；提交后别人下次刷新才看到新版。旧版不是凭空造出来的，是"改动时没直接删掉旧页，而是新写一页"。

**哪个数据库没有 MVCC 会怎样**：若只有锁，读也要加锁、写要等读释放，并发度大幅下降。MVCC 用"空间（多版本）换并发"，把读写从锁竞争中解放出来。

## 2. 两套方案对比（核心考点）

两大主流关系数据库走的是**方向相反的 MVCC 实现**：

| 维度 | PostgreSQL | MySQL InnoDB |
|------|-----------|--------------|
| 旧版本存哪 | **堆表多版本元组**（xmin/xmax） | **undo log 回滚段** |
| 修改方式 | 插入新行 + 旧行标失效 | **原地更新** + 记录 undo |
| 回滚日志 | 无独立回滚段，靠 clog + 戳判断 | undo log + read view |
| 清理方式 | 后台 VACUUM 回收死元组 | purge 线程清理 undo |
| 隔离级别实现 | 每语句快照(RC) / 每事务快照 | Read View + undo chain |
| 可见性映射 | VM（加速仅索引扫描） | 无直接对应，secondary index 靠回表 |
| 索引更新优化 | **HOT**（不碰索引键则不动索引） | change buffer（缓冲二级索引变更） |
| 长事务代价 | 表/索引**膨胀** | 回滚段膨胀、purge 滞后 |
| 可串行化 | **SSI**（冲突图检测） | Next-Key 锁 + 快照读 |
| 快照构建 | 事务表 + clog | Read View + undo 链 |

> 🔑 **一句话记忆主线**：PG 的 MVCC 是"**写了不删、旧版留着、靠戳判断、定期打扫（VACUUM）**"；MySQL InnoDB 是"**原地改、旧版记进 undo、Read View 判断、purge 清理**"。理解各自的旧版本载体，就抓住了实现差异的纲。

> **知识交叉**：PG 侧底层机制详解（元组头/clog/hint bits/VM/HOT/VACUUM/膨胀）见 [03-MVCC深入原理](../PostgreSQL/02-设计原理/03-MVCC深入原理.md)；PG 用法入门见 [06-事务详解](../PostgreSQL/01-基础/06-事务详解.md) §9.8。

## 3. 快照机制与隔离级别依赖

**是什么**：判断"当前事务能看到哪些版本的修改"，需要一张**快照**——即"当前活跃事务集合 + 本事务自己的状态"。

**快照范围示意**：
- 比快照起点更早且已提交的事务改动 → **可见**。
- 正活跃（未提交）事务的改动 → **不可见**。
- 比快照终点更晚才启动的事务 → **不可见**。

**隔离级别决定快照粒度（关键）**：

| 隔离级别 | 快照获取时机 | 读取一致性 |
|---------|-------------|-----------|
| **Read Committed** | **每条语句**取新快照 | 同一事务内两次查询可能不同（可见别人新提交的） |
| **Repeatable Read** | **事务第一条语句**取快照，全程复用 | 事务内读一致 |
| **Serializable** | 事务首快照 + 冲突检测 | 事务内读一致 + 可串行 |

> 💡 **一句话**：快照 = "哪些事务还没干完"的名单。RC 每次语句都重看名单（看到最新已提交）；RR 开头看一次就锁死（事务内不变）。**隔离级别本质上是"拍快照的频率"**。

> 📌 注意：快照只解决**读**的一致性；要"读到最新并加锁"的当前读（`FOR UPDATE` 等）需要配合锁（见 [02-关系型DB锁详解](02-关系型DB锁详解.md)）。

## 4. 各库差异总对比（快照层面）

| 维度 | PostgreSQL | MySQL InnoDB |
|------|-----------|--------------|
| 事务标识 | 32 位 XID（需防回卷） | 事务 ID + 回滚段指针 |
| 旧版本判断 | 元组头 xmin/xmax + clog | undo log + Read View |
| 加速可见性 | hint bits + VM | Read View 直接计算 |
| 读不阻塞写 | ✅ 快照读 | ✅ 快照读（MVCC） |
| 阻止幻读 | 靠 Serializable 级别 | Next-Key 间隙锁（RR 下即拦） |
| 长事务危害 | 表/索引膨胀 | undo 回滚段膨胀 |

> 📌 这张表聚焦"快照/可见性"层面的差异；更完整的底层机制差异见 §2。各库细节回链：[03-MVCC深入原理](../PostgreSQL/02-设计原理/03-MVCC深入原理.md)、占位 **00-MySQL总览**（见知识库）。

## 6. 小结

- MVCC = **多留旧版本 + 快照判断 + 定期清理**；读写不互堵的根因是"写不改旧版本、读不加锁"。
- 两套方案：PG 堆表多版本元组（VACUUM 清理）；MySQL undo log 回滚段（purge 清理）。
- 快照是隔离级别的载体：RC 每语句刷、RR 事务首快照。
- 各库底层机制、MySQL undo/Next-Key 等实现细节回链各库笔记与占位块。
