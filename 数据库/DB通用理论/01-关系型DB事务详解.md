# 关系型数据库事务详解

> **一句话记忆**：事务 = 一组「要么全成功、要么全失败」的操作，靠 ACID 四特性撑起；隔离级别决定并发事务之间「互相看到多少脏数据/不一致」。

## 1. 什么是事务

**是什么**：事务（Transaction）是把一组数据库操作打包成**一个原子单位**：要么全部成功提交（commit），要么全部撤销（rollback）。中间绝不允许「做了一半」。

**为什么（类比）**：就像银行转账——转出扣款和转入入账必须「同时成功或同时失败」。如果只扣了款没入账，账就不平了。

**事务的组成维度**：

| 维度 | 说明 |
|------|------|
| 边界 | 明确的开始与结束（BEGIN…COMMIT/ROLLBACK） |
| 原子性 | 全成功 or 全失败，无中间态 |
| 隔离性 | 并发事务互不可见（隔离级别控制） |
| 持久性 | 提交后不因崩溃丢失 |

## 2. ACID 四特性详解

### 2.1 四个特性的定义

| 特性 | 英文 | 定义 | 通俗理解 |
|------|------|------|---------|
| **原子性** | Atomicity | 事务内所有操作要么全成功、要么全失败 | 不可拆分的整体 |
| **一致性** | Consistency | 事务前后数据库完整性约束不被破坏（账总和不变） | 从一个合法状态到另一个合法状态 |
| **隔离性** | Isolation | 并发事务之间互相隔离，不看到彼此的中间态 | 各干各的，互不干扰 |
| **持久性** | Durability | 已提交的事务结果永久生效，崩溃不丢 | 提交即不丢 |

### 2.2 各库 ACID 的实现侧重

> **知识交叉**
> - PG：见 [06-事务详解](../PostgreSQL/01-基础/06-事务详解.md) §9.1（PG 的 WAL 日志保证 D、MVCC+锁保证 I）
> - MySQL：InnoDB 用 redo log 保持久、undo log 保原子/回滚

| 特性 | 主要靠什么保证 | PG 实现 | MySQL InnoDB 实现 |
|------|--------------|---------|------------------|
| 原子性 | 事务日志 + 回滚机制 | WAL + 事务回滚 | undo log（回滚段） |
| 一致性 | 约束/触发器 + 应用逻辑 | 约束、触发器 | 外键、约束 |
| 隔离性 | MVCC + 锁 | MVCC + 锁 | MVCC + 锁/间隙锁 |
| 持久性 | 持久化日志 + fsync | WAL + fsync | redo log |

> 🔑 **关键理解**：ACID 不是孤立的四件事，而是**协作体**：A（原子）靠日志，D（持久）靠日志+落盘，I（隔离）靠 MVCC+锁，C（一致）是被前三个共同支撑出来的结果。

### 2.3 常见误区

- ❌ 「一致性能靠数据库自动保证」——数据库只保证**约束层面**的一致，业务语义的一致（如转账总额守恒）需要应用自己写对。
- ❌ 「A 和 D 是一回事」——A 是「失败要回到原点」，D 是「成功后不许丢」。崩溃恢复时两者配合：未提交的撤销（A），已提交的补落盘（D）。

## 3. 事务边界：BEGIN / COMMIT / ROLLBACK

**是什么**：事务必须有明确的边界标记，让数据库知道「从哪里开始打包、到哪里落定」。

| 命令 | 语义 | 通俗理解 |
|------|------|---------|
| `BEGIN`（或 `START TRANSACTION`） | 显式开启一个事务 | 「开始打包」 |
| `COMMIT` | 提交，使改动永久生效 | 「确认放行」 |
| `ROLLBACK` | 回滚，撤销本次事务所有改动 | 「撤销，回到开始前」 |

**概念层要点（不点名某库 SQL）**：
- **自动提交模式**：会话默认每条独立语句自动开一个隐式事务并自动提交，无法回滚；只有显式 `BEGIN` 才能把多条语句包进同一个事务。
- **提交**：`COMMIT` 是事务唯一的「成功出口」，一旦提交，改动对其它已提交事务可见（具体可见度还受隔离级别约束）。
- **回滚**：`ROLLBACK` 是「失败出口」，撤销本事务所有已执行的改动，恢复原状。
- **隐式与显式混用**：如果在前面已自动提交的语句后再 `BEGIN`，实际开启的是全新事务，需注意设计。

> 💡 **为什么需要边界**：数据库无法猜测「哪几条语句算一组业务操作」，必须由应用用 BEGIN/COMMIT/ROLLBACK 划出边界，一个边界内就是一个事务单元。

## 4. 隔离级别：四级别 + 三个并发异常

### 4.1 三个并发异常的定义（先搞清楚问题）

> 这是理解隔离级别的**前置概念**，务必先分清：

| 异常 | 定义 | 通俗类比 |
|------|------|---------|
| **脏读** | 读到另一个事务**未提交**的数据，且该事务可能回滚 | 看到别人写了但还没保存就以为是真的 |
| **不可重复读** | 同一事务内，同一行**两次读取结果不一致**（因别的已提交事务在两次读之间改了它） | 同一页书第一次看到一个数字，翻回来再看变了 |
| **幻读** | 同一事务内，相同查询**两次返回的行集合不同**（别的已提交事务插入/删除了符合条件的行） | 第一次数了 5 个人，第二次数出 6 个，多出一个"幻影" |

**脏读 vs 不可重复读 vs 幻读 关键区分**：
- **脏读** = 读到**未提交**数据。
- **不可重复读** = 已提交事务**更新**了同一行（行值变了）。
- **幻读** = 已提交事务**插入/删除**了行（行**数量**变了，出现新行/少了行）。

### 4.2 四级别纵览

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现思路（概念层） |
|---------|:---:|:---:|:---:|------------------|
| **Read Uncommitted** | 可能 | 可能 | 可能 | 不做隔离，读不加锁/不看快照 |
| **Read Committed** | 否 | 可能 | 可能 | 只读已提交版本（每语句取快照） |
| **Repeatable Read** | 否 | 否 | 可能 | 事务内快照一致（阻止不可重复读） |
| **Serializable** | 否 | 否 | 否 | 完全串行化/冲突检测（阻止全部） |

> 📌 **记忆锚点**：隔离级别是从上到下越来越严，代价是并发性能越来越低。**Read Committed 是多数数据库默认**，Repeatable Read 常被 MySQL 用作默认。

### 4.3 隔离级别怎么选

- **通用业务**：`Read Committed`（吞吐最高，看到的是提交后的数据即可）。
- **金融/对账**：`Repeatable Read`（事务内多次读要一致）。
- **写冲突敏感业务**：`Serializable`（能接受"冲突报错重试"的代价）。

> ⚠️ **易错点**：隔离级别不是越高越好——Serializable 生产很少用，因为并发大幅下降且可能抛"无法串行化"冲突错误，需要应用层重试。**用最低能满足业务的级别**才是最佳实践。

## 5. 各库默认隔离级别对比

| 数据库 | 默认隔离级别 | 说明 |
|--------|:---:|------|
| **PostgreSQL** | Read Committed | 可升 RR/Serializable；Read Uncommitted 映射为 RC（架构上无脏读） |
| **MySQL InnoDB** | Repeatable Read | 靠 MVCC + Next-Key 间隙锁避免了大多数幻读 |
| **Oracle** | Read Committed | 快照读 |
| **SQL Server** | Read Committed | 默认读加共享锁 |

> 📌 具体某库设置语法与实测见各库笔记：PG 见 [06-事务详解](../PostgreSQL/01-基础/06-事务详解.md) §9.6；MySQL 细节待 **00-MySQL总览**（见知识库） 转正后补充。

## 6. 保存点 SAVEPOINT：部分回滚

**是什么**：保存点（Savepoint）允许在事务**内部设置一个退回点**，`ROLLBACK TO SAVEPOINT` 只回滚到该点之后的操作，**而非整个事务**——即「部分回滚」。

**为什么（场景）**：一个长事务里有多步独立操作，某一步失败不想连累前面已成功的步骤，只想撤销失败这一步。

**概念流程**：

```
BEGIN
├─ 操作1 成功
├─ SAVEPOINT sp1        ← 打点
├─ 操作2 失败
└─ ROLLBACK TO sp1      ← 只撤销 sp1 之后（操作2），保留操作1
（仍可继续或最终 COMMIT）
```

**要点**：
- 可设**多个嵌套保存点**，回滚到最近的一个。
- 保存点只是「位置标记」，不是新事务——事务整体仍只有一个，最终 COMMIT/ROLLBACK 影响整个事务。
- 回滚保存点后释放该点之后持有的锁、撤销该点之后的改动。

**实际体现**：
- SQL 层：`SAVEPOINT` / `ROLLBACK TO SAVEPOINT`（PG 见 [06-事务详解](../PostgreSQL/01-基础/06-事务详解.md) §9.5）。
- 框架层：Spring 的传播行为 `NESTED` 就是依赖数据库保存点能力实现子事务部分回滚（见 Spring 事务 [09-Spring事务管理详解](../../Java/框架/spring/09-Spring事务管理详解.md) §3.2.1）。

> 💡 **类比**：保存点像给长文档"分章保存"——某一章写崩了只退回这一章开头重写，前面写好的章节不受影响。

## 7. 事务长短的影响

| 维度 | 短事务 | 长事务 |
|------|--------|--------|
| 锁持有时间 | 短，并发好 | 长，阻塞他人、锁升级风险 |
| 日志/undo 量 | 小 | 大，undo/回滚段膨胀 |
| 清理压力 | 小 | 阻塞旧版本清理（PG 表膨胀 / MySQL undo 膨胀） |
| 崩溃恢复 | 快 | 慢 |
| 最佳实践 | **尽量短** | 避免；别在事务里等用户交互、反复远程调用 |

> 🔑 **核心结论**：事务长短直接影响并发与存储膨胀。**事务尽量短、不在事务里做慢操作/用户交互**，是所有关系型数据库共享的铁律。

---

## 8. 小结

- 事务 = 原子打包的一组操作，靠 ACID 保证可靠；A 靠日志回滚、D 靠日志持久、I 靠 MVCC+锁、C 是前三者共同支撑的结果。
- 三个并发异常：**脏读**（读未提交）、**不可重复读**（同一行值两次读不同）、**幻读**（行集合两次读不同）。
- 四级别从 Read Uncommitted 到 Serializable 越来越严、性能越来越低；**Read Committed 是多数库默认**。
- 保存点提供**部分回滚**，是长事务里局部撤销的手段，也是 NESTED 传播行为的基础。
- 事务尽量短是放之各库皆准的并发与膨胀治理铁律。
