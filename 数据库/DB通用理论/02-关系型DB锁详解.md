# 关系型数据库锁详解

> **一句话记忆**：锁 = 数据库用来「管住并发访问」的机制。乐观锁靠数据校验、悲观锁靠加锁排队；按粒度分行锁/表锁/间隙锁，按兼容性分享共/排他；真正难的是**死锁**——好在有必要条件可绕开。

**本篇定位**：DB 通用理论层——讲**所有关系型数据库共享的锁模型**（乐观/悲观、粒度、共享排他、死锁），不展开具体某库实现。PG 专属的 7 种表锁/行锁 SQL/咨询锁、MySQL 的间隙锁细节见各库笔记。

## 1. 为什么需要锁

**问题**：并发环境下多个事务同时读写同一份数据，若不加控制，会产生竞态：

**丢失更新（Lost Update）**：两个事务同时读到同一份数据、各自修改、后提交的覆盖先提交的——更新丢失。这是「读写并发必须用锁/MVCC 解决」的根本原因。

**并发读写的经典矛盾**：
- 读读：天然安全，可并行。
- 读写/写写：有冲突，需要协调——协调工具就是**锁**（或用 MVCC 让读写互不阻塞，见 [03-关系型DB-MVCC详解](03-关系型DB-MVCC详解.md)）。

> 🔑 **一句话**：锁解决的是「写入之间的冲突」以及「没有 MVCC 时读写之间的冲突」。

## 2. 乐观锁 vs 悲观锁

两种截然不同的并发控制思路：

| 维度 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 前提假设 | 认为冲突**必然发生**，先锁住再干活 | 认为冲突**很少发生**，干活时不加锁 |
| 做法 | 更新前先加锁，阻塞他人 | 不加锁，提交时校验版本是否被改 |
| 常用实现 | `SELECT ... FOR UPDATE` | 版本号字段 / CAS（比较并交换） |
| 并发度 | 低（要排队） | 高（并发读不阻塞） |
| 冲突代价 | 排队等待 | **提交失败重试** |
| 适用 | 写冲突频繁、无法重试 | 读多写少、冲突概率低 |

**乐观锁经典流程（版本号）**：

```
读数据(带 version=3)
→ 业务处理
→ UPDATE ... SET x=新值, version=4 WHERE id=1 AND version=3
   若影响行数=0 → 版本变了，别人改过 → 重试
```

> 💡 **类比**：悲观锁像图书馆借书——借了别人就不能借；乐观锁像多人协作文档——大家先各改各的，保存时若发现别人已改过就提示冲突重来。

> ⚠️ **权衡**：悲观锁并发低但**无重试成本**；乐观锁并发高但**冲突时重试成本高**。选型看业务写冲突频率。

## 3. 锁粒度

锁作用的数据范围大小不同，粒度从细到粗：

| 粒度 | 锁住的单位 | 特点 |
|------|-----------|------|
| **行锁** | 具体一行 | 并发最细、开销最大，高并发最佳 |
| **页锁** | 一个数据页 | 介于行锁与表锁之间 |
| **表锁** | 整张表 | 简单粗放、并发差，用于 DDL/全表操作 |
| **间隙锁**（Gap） | 行之间的"间隙" | 专门防**幻读**（锁住一个范围而非具体行） |

**意向锁（Intention Lock）**：不是直接锁数据，而是「预告」——做行锁/间隙锁时，先在表上打一个意向标记，让表级操作（如 ALTER TABLE）尽快判断"有没有行锁冲突"，避免逐个检查行。它**协调行锁与表锁的兼容性**。

| 粒度对比 | 并发度 | 开销 | 用途 |
|---------|:---:|:---:|------|
| 行锁 | 高 | 大 | DML（增删改一行） |
| 间隙锁 | 高 | 中 | 防幻读 |
| 表锁 | 低 | 小 | DDL、全表操作 |
| 意向锁 | — | — | 行锁与表锁之间的协调标记 |

> 🔑 **锁粒度的权衡**：粒度越细并发越高但管理越复杂；粒度越粗实现越简单但并发越差。**行锁 + 表锁/意向锁配合**是通用主流方案。

## 4. 共享锁与排他锁的语义

锁有两种基本兼容语义，几乎所有锁模型都基于它：

**共享锁（Shared, S）**：加锁者只能**读**，允许多人同时持有共享锁（读读不冲突）。

**排他锁（Exclusive, X）**：加锁者既能读也能**写**，与任何其他锁（共享/排他）都冲突，同一资源同时只能有一个排他锁。

**兼容性矩阵（关键）**：

| 当前持有 | 新请求 | 共享锁(S) | 排他锁(X) |
|:---:|:---:|:---:|:---:|
| **共享锁(S)** | 能（读读兼容） | **不能**（阻塞） |
| **排他锁(X)** | **不能**（阻塞） | **不能**（阻塞） |

**一句话记忆**：**读读不冲突、读写冲突（写要等读释放）、写写串行**。

> 📌 MySQL 的共享锁 `SELECT ... LOCK IN SHARE MODE`、排他锁 `SELECT ... FOR UPDATE`；PG 的 `FOR SHARE` / `FOR UPDATE`（见 [07-锁详解](../PostgreSQL/01-基础/07-锁详解.md) §10.3）。

## 5. 锁升级

**是什么**：数据库**动态放大锁的范围**——把锁从行级升级到更粗的粒度（如行锁→表锁）。

**为什么发生**：
- 事务持锁的行**超过阈值**，数据库判断"逐行加锁太浪费"，直接升级为表锁。
- 或者某个操作本身就需要锁整表（如大量更新）。

**危害**：导致**并发度骤降**——原本并发的行级操作因锁升级变成全表串行。

**常见诱因**：一次 UPDATE 影响行数过多、长事务持有过多行锁。

> 💡 避免：控制单事务影响行数、拆分大事务、监控锁升级。

## 6. 死锁：四个必要条件与避免

### 6.1 什么是死锁

**是什么**：两个或多个事务**互相持有对方需要的资源锁**，且都在等待对方释放——形成循环等待，谁都进行不下去。

```
事务 A: 锁住行 1 → 等行 2
事务 B: 锁住行 2 → 等行 1
      → 互相等，死锁！
```

### 6.2 四个必要条件（缺一不可）

1. **互斥**：资源一次只能被一个事务占用。
2. **占有并等待**：事务已持有资源，还在等别的资源。
3. **不可剥夺**：已持有的资源不能被强行抢走。
4. **循环等待**：A 等 B、B 等 A 形成环。

> 🔑 **推论**：只要打破任意一个条件，就不会发生死锁。绝大多数规避策略都从"**打破循环等待**"入手——**让所有事务按同一固定顺序加锁**。

### 6.3 数据库如何应对死锁

- **自动检测**：数据库有死锁检测器，检测到循环等待后**牺牲（回滚）其中一个事务**，让其释放锁，其余事务继续。
- **超时兜底**：`lock_timeout` / 检测间隔超时后强制回滚等待的事务。

### 6.4 避免死锁的最佳实践

| 手段 | 说明 |
|------|------|
| **固定加锁顺序** | 所有事务按主键/某字段统一升序加锁（打破循环等待，最有效） |
| 事务尽量短 | 减少持锁时间 |
| 大事务拆小 | 减少同时涉及多资源的窗口 |
| 非阻塞尝试 | 用 `NOWAIT` / 超时快速失败，避免无尽等待 |
| 改用乐观锁 | 用版本号替代悲观锁，从根上避免死锁 |

## 7. 锁与事务、MVCC 的关系

**锁与事务**：锁的**持有周期由事务边界决定**——事务提交/回滚时释放持有的锁。所以"长事务持锁"是并发杀手。

**锁与 MVCC**：
- **MVCC（快照读）**：靠多版本让**读写互不阻塞**——读走快照、拿旧版本，不加锁；写只改自己版本。
- **锁（当前读/写）**：处理**写写冲突**以及需要"读到最新已提交数据"的操作（`SELECT ... FOR UPDATE` 这类当前读必须加锁）。

```
快照读（MVCC）：不加锁，读旧版本 → 读不阻塞写
当前读/写（锁）：加锁 → 写写互斥、当前读保证读到最新
```

> 🔑 **一句话**：MVCC 把"读写"从锁竞争中解放出来（读写不互堵），锁仍然管"写写"与"需要最新一致性读取"的场景。两者**分工配合**，不是二选一。

## 8. 小结

- 锁解决并发写冲突：**乐观锁**靠版本校验（冲突重试）、**悲观锁**靠加锁排队。
- 锁粒度：行/页/表/间隙；**意向锁**协调行锁与表锁兼容性；间隙锁专防幻读。
- 共享/排他核心语义：**读读不冲突、读写冲突、写写串行**。
- 锁升级会放大锁范围、坑并发度。
- 死锁四必要条件（互斥/占有等待/不可剥夺/循环等待）打破任一即解；最有效是**统一加锁顺序**。
- 锁与 MVCC 分工：MVCC 读写不互堵，锁管写写冲突与当前读。
