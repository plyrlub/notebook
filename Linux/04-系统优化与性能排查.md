# 04-系统优化与性能排查

> **受众**：后端工程师、Linux 基础较弱。本篇学完能独立处理：CPU 飙高、内存吃紧、磁盘告警、端口/连接异常四类经典问题，并掌握常用内核参数与资源限制调优。
> **版本**：命令双版本通用（监控体系两发行版一致）；软件包安装差异已标注。
> **定位**：应用层为主——监控指标讲「怎么读、什么算异常」，不追内核调度器/内存回收源码。

---

## 学习目标

1. 会读 top/free/df/iostat 关键指标，区分正常与告警

3. 会用 sysctl 调整常用内核参数（文件句柄、连接队列、TCP 优化）
4. 会处理 ulimit 文件描述符限制（Too many open files）
5. 会配置 crontab 定时任务与 logrotate 日志轮转

## 1. 监控指标怎么读

### 1.1 top：第一眼

```
top - 09:00:01 up 3 days,  2 users,  load average: 0.10, 0.15, 0.20
%Cpu(s):  2.3 us,  1.0 sy,  0.0 ni, 96.3 id,  0.3 wa
MiB Mem :  15940.2 total,   8021.2 free,   3120.5 used,   4798.5 buff/cache
```

| 指标 | 含义 | 异常阈值 |
| ---- | ---- | ---- |
| load average | 1/5/15 分钟平均负载（**运行+不可中断进程数**） | 长期 > CPU 核数（nproc） |
| us / sy | 用户态 / 内核态 CPU | sy 常驻 >30% 查内核/IO |
| wa | IO 等待 | >10% 持续 = 磁盘瓶颈 |
| buff/cache | 文件缓存（**可回收，不是内存泄漏**） | 高是正常的 |

> 💡 **核心认知**：`free` 里 buff/cache 高**不是**内存不够——Linux 把空闲内存当缓存用，应用要时自动释放。判断内存不足看 `free -h` 的 available 列，不是 used。

### 1.2 常用监控命令

```bash
uptime                    # load average 速览（配合 nproc 判断）
nproc                     # CPU 核数
free -h                   # 内存（看 available！）
df -h && df -i            # 磁盘容量 + inode
iostat -x 1               # 磁盘 IO（%util 持续高=瓶颈）
vmstat 1                  # 综合：r=运行队列 b=阻塞 si/so=换页
mpstat -P ALL 1           # 每核 CPU（单核打满排查）
sar -u 1 5                # 历史/实时 CPU 采样（sysstat 包）
```

## 2. 四类经典问题排查套路

### 2.1 CPU 飙高

```bash
# ① 找到 CPU 高的进程
top -o %CPU               # 按 CPU 排序（或 top 里按 P）
# ② 若是 Java 进程：定位线程
top -H -p <PID>           # 进程内线程按 CPU 排序，记下高 CPU 线程 TID
printf '%x\n' <TID>       # 转 16 进制（jstack 需要）
jstack <PID> | grep -A 20 'nid=0x<十六进制TID>'   # 定位到代码行
# ③ 若是 Python/Node：py-spy dump / 火焰图
```

**判断**：用户态 us 高 = 业务代码问题（死循环/大计算）；sy 高 = 系统调用/锁竞争；wa 高 = IO 等待拖累 CPU。

### 2.2 内存高

```bash
free -h                    # ① 看 available 是否真不足
# ② 按内存排序找进程
top -o %MEM
ps aux --sort=-%mem | head
# ③ Java 场景：堆外内存排查
jmap -heap <PID>           # 堆内
pmap <PID> | tail          # 堆外映射
```

**判断**：available 充足 → 只是缓存，不用管；available 持续下降 → 进程内存泄漏（Java 看 GC 日志 / 堆栈，Python 看对象增长）；OOM 后查 `dmesg | grep -i oom` 或 `journalctl -k | grep oom`。

### 2.3 磁盘满 / IO 高

```bash
df -h && df -i             # ① 容量 or inode
du -sh /var/log/* | sort -rh | head   # ② 找大头
find / -xdev -type f -size +1G 2>/dev/null -exec ls -lh {} \;
lsof +L1 | grep deleted    # ③ 已删仍占（进程持有）
iostat -x 1                # ④ IO 高排查（%util、await）
```

**处理**：日志过大 → logrotate（见 §6）；IO 高 → 找出热文件（`iotop` 需 root），日志/数据库文件是常客。

### 2.4 端口/连接异常

```bash
ss -tlnp | grep :8080      # ① 监听了吗
curl -v http://127.0.0.1:8080  # ② 本机通吗
ss -s                      # ③ 连接数总览（TIME_WAIT 堆积？）
ss -tn state time-wait | wc -l
ss -tn state established | wc -l
# ④ 连接数限制
ulimit -n                  # 进程文件描述符上限
cat /proc/sys/net/core/somaxconn   # 半连接队列
cat /proc/sys/net/ipv4/tcp_max_syn_backlog
```

**判断**：TIME_WAIT 多 = 短连接频繁（高并发正常现象，调 `net.ipv4.tcp_tw_reuse`）；established 打满 = 服务/连接泄漏；`Too many open files` → ulimit（见 §5）。

## 3. 内核参数调优（sysctl）

```bash
sysctl -a | grep xxx       # 查当前值
sysctl -w net.ipv4.ip_forward=1   # 临时改（重启失效）
vim /etc/sysctl.conf       # 永久改（或 /etc/sysctl.d/99-custom.conf）
sudo sysctl -p             # 生效
```

**后端常用参数清单**（附一句话理由）：

| 参数 | 建议值 | 场景 |
| ---- | ---- | ---- |
| `fs.file-max` | 655356 起 | 全局限文件句柄（Too many open files 的全局层） |
| `net.core.somaxconn` | 4096 | 高并发连接队列（nginx/网关） |
| `net.ipv4.tcp_tw_reuse` | 1 | TIME_WAIT 复用（短连接场景） |
| `net.ipv4.tcp_fin_timeout` | 30 | 快速回收 FIN 等待 |
| `vm.swappiness` | 10（默认 60） | 减少 swap 倾向（内存够用时的服务器） |
| `net.core.rmem_max / wmem_max` | 8388608 | 大流量 TCP 缓冲 |

> ⚠️ **易错点**：调参前先 `sysctl -a | grep` 看当前值并记录；一次只调少数几个，观察 1~2 天；`vm.swappiness=0` 不推荐（可能触发 OOM），10 是稳妥值。

## 4. 资源限制（ulimit）

### 4.1 文件描述符（后端高频坑）

```bash
ulimit -n                  # 当前限制（默认 1024 太少！）
ulimit -n 65535            # 临时提升（当前会话）
# 永久：/etc/security/limits.conf
# deploy soft nofile 65535
# deploy hard nofile 65535
# systemd 服务：单元文件里加 LimitNOFILE=65535
```

**症状**：日志报 `Too many open files` / `SocketException: Too many open files`。

> ⚠️ **易错点**：改 limits.conf 后需**重新登录**生效；systemd 管理的服务不受 limits.conf 影响，必须写 `LimitNOFILE` 到单元文件；Java 应用容器化后还要看 Docker 的 ulimit。

### 4.2 其他限制

```bash
ulimit -u                  # 最大进程数
ulimit -s                  # 栈大小（默认 8192KB）
```

## 5. 定时任务（crontab）

```bash
crontab -e                 # 编辑当前用户任务
crontab -l                 # 查看
# 格式：分 时 日 月 周  命令
# 每天 2:30 备份
30 2 * * * /opt/scripts/backup.sh
# 每 5 分钟健康检查
*/5 * * * * /opt/scripts/health.sh >> /var/log/health.log 2>&1
# 每周日 3:00 清理
0 3 * * 0 /opt/scripts/cleanup.sh
```

**最佳实践**：
- 脚本里输出重定向 `>> log 2>&1`——cron 环境无终端，不重定向输出会以邮件形式丢失
- 脚本开头 `#!/bin/bash` + `set -e`，cron 不加载 shell 环境变量，**绝对路径写全**
- 系统级任务用 `/etc/crontab`（可指定用户），用户任务 `crontab -e`

> ⚠️ **易错点**：cron 里 `PATH` 极简（通常只有 /usr/bin:/bin），脚本里用到非标准路径命令（如 node/nginx）必须写绝对路径或脚本内 export PATH。

## 6. 日志轮转（logrotate）

日志无限增长是磁盘杀手，logrotate 自动切割/压缩/清理：

```bash
cat /etc/logrotate.d/myapp
# /var/log/myapp/*.log {
#     daily          # 每天切
#     rotate 7       # 保留 7 份
#     compress       # 压缩旧日志
#     missingok      # 无日志不报错
#     notifempty     # 空文件不切
#     copytruncate   # 复制+清空（进程不重启也安全，适合 Java logback）
# }
```

```bash
sudo logrotate -d /etc/logrotate.d/myapp   # 调试模式（dry-run，不实际执行）
sudo logrotate -f /etc/logrotate.d/myapp   # 强制执行一次
```

> ⚠️ **易错点**：Java 应用（logback/log4j）配 logrotate 用 `copytruncate`（复制后清空，进程继续写），不要用默认的 rename 方案——rename 后应用还在写旧 inode，日志不轮转还占磁盘。

## 7. 系统优化最佳实践

1. **先观察再调参**：任何一个指标异常，先用 top/free/iostat 采集 5~10 分钟数据，定位到进程/线程层再动手
2. **文件句柄三件套**：limits.conf + systemd LimitNOFILE + Docker ulimit，三层都要配
3. **日志治理**：所有应用日志配 logrotate，Java 用 copytruncate；日志级别生产用 info
4. **定时任务规范化**：脚本独立目录 `/opt/scripts/`，输出重定向，绝对路径，`set -e`
5. **调参留痕**：改 /etc/sysctl.conf 前先 `cp` 备份，`sysctl -p` 后记录基线值
6. **内核升级**：Ubuntu `apt upgrade` / CentOS `dnf update` 定期打安全补丁（先测试环境验证）

## 8. 常见踩坑

| 现象 | 原因 | 解决 |
| ---- | ---- | ---- |
| 内存看着 80% 但系统不卡 | buff/cache 是缓存 | 看 free 的 available |
| Too many open files | ulimit 1024 默认 | 三层配置提升 |
| 高并发连接排队 | somaxconn 太小 | sysctl 提升到 4096 |
| cron 任务不执行/报错 | PATH 不全/没重定向 | 绝对路径 + 重定向 |
| 日志不轮转磁盘爆 | Java 进程 hold 旧文件 | copytruncate |
| OOM 杀进程 | 内存不足/swap 太小 | 查 dmesg + 调 swappiness/加内存 |

## 9. 小结

- 读指标：load vs 核数、free 看 available、wa 高查 IO、df -i 查 inode——先会读再会调
- 四类排查：CPU（top -H + jstack）、内存（top -o %MEM + dmesg）、磁盘（du 逐层 + lsof +L1）、连接（ss + ulimit）
- 调优三件：sysctl 内核参数（留痕）、ulimit 文件句柄（三层）、logrotate 日志治理（copytruncate）
- 自动化：crontab 规范化 + systemd 服务管理，取代裸跑脚本
